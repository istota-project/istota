# Web UI design language

This guide applies to both Claude Code and Codex. Read it from disk in bounded sections through the end before UI work; the automatically injected copy may be truncated. From a root-level session, load it explicitly before planning the change.

Read the shared project memory as directed by the root `AGENTS.md`, especially `feedback_web_alerts_follow_chat.md`. Out-of-band action failures use the existing notice drawer through `notifyError` / `notifyWarning`; lasting conditions use `Alert`. Field errors and failed sends stay beside their field or message. The detailed rules below govern each case.

Rules for building and changing the SvelteKit frontend in `web/`. Read this before adding a page, a component, or a color.

This file is the single source for the frontend design language — the inventory, the rules, and the reasoning behind each. `.claude/rules/web-ui.md` is its backend counterpart: the route and endpoint map, the admin Logs and Configuration panes, and the settings/module-services split. It does not restate anything here. When the two disagree with the tree, the source files win and both docs are stale.

## Before you write anything

1. `cat src/lib/components/ui/index.ts` — the full primitive inventory. If a primitive fits, use it; do not hand-roll a second one.
2. `grep -n '^\s*--' src/lib/styles/tokens.css` — the token roster. Every color you write must be an existing token, or a new token pair added to **both** theme blocks: in `tokens.css` for a role in the design system, in `app-tokens.css` for one that names a product surface (chat, rooms, the app bar).
3. `ls src/lib/platform/` — the native-shell facade. Anything that behaves differently inside the iOS app goes through it and nowhere else.
4. Find the nearest sibling page and read it. A new money page copies `routes/money/transactions`; a new module settings page copies `routes/feeds/settings`. Match its structure before inventing one.
5. `npm run lint:design` before you commit. Eleven rules: a color literal in any notation (`raw-color`), a `var()` naming a token nothing defines — two rules, split by whether a fallback is written (`undefined-token`, `undefined-token-fallback`) — a spacing value off the scale (`off-scale-space`), an `@media` width off the three breakpoints (`off-scale-breakpoint`, the one rule that also reads the style layers), a redefined primitive class: a `ui/` primitive's, the table family's or a `primitives.css` shared block's (`redefined-primitive`), a per-page theme override (`theme-override`), a native dialog (`native-dialog`, which catches `confirm`/`alert`/`prompt` bare as well as on `window`), a deep import past a barrel, `ui`, `notifications` or `search` (`deep-import`), a `:global(.money-*)` written outside the money layout (`stray-money-global`), and an empty state written as a class rather than `EmptyState` (`hand-rolled-empty-state`).
6. `npm run format` — prettier, 2-space, single quotes, 100 cols. Never tabs.

## Component inventory

Import everything from the barrel: `import { Button, Modal } from '$lib/components/ui';`

`components/ui/` is the unit the shared library takes, so it holds primitives only, and the barrel exports every component in it (`barrel.test.ts`). A component only another primitive mounts lives in `ui/internal/` and is never exported: `NavLink` (inside `HeaderNav`), `NoticeDrawer` (inside `AppShell`) and `linkOrButton`, the element rule `Button` and `IconButton` share. Product components sit beside `ui/` with barrels of their own: the notification inbox in `components/notifications/`, global search in `components/search/` (see "Shared beyond `ui/`"). Nothing in `components/ui/` or `lib/ui/` imports `$lib/` outside those two folders and the notices store, `clipboard` and `dateFormat`, which the library takes with it; `boundary.test.ts` holds that, with `Avatar`'s `avatarUrl` as the one named exception until `Avatar` takes a `src` prop.

| `Button`            | Every button, and any button-shaped link                                             | Variants: `primary`, `secondary`, `pill` (the default), `danger` (also the quiet delete at the start of a dialog footer, at `size="sm"`). **Transient feedback goes through `notify()`, and only if it is out-of-band.** `import { notify, notifyError, notifySuccess, notifyWarning } from '$lib/stores/notices'` and call it from anywhere — a store, a component, an event handler. It renders in a band that slides down from under the section header, overlaying content without reflowing it. `AppShell` mounts the host, so no page renders anything.

The severities are `info` / `success` / `warning` / `error`. All but `error` auto-dismiss; an error stays until dismissed, as does any notice carrying an `action` (`{ label, run }`) — expiring a decision out from under a reaching finger removes the only way to take it. Concurrent notices queue, because the drawer is one slot; a pinned one hands the slot over after 30s once something is waiting behind it, so an unanswered error can't silence the channel for the life of the tab.

**`sticky: true` is for a condition rather than an event** — something true for as long as it is true, whose raiser takes it down. Chat's offline notice is the one caller. It is exempt from the three ways an event is retracted (the navigation clear, the 30s handover, the `MAX_QUEUE` trim), because each would retract it while it still held; a plain `duration: 0` notice is defeated by all three. It is not exempt from yielding: a sticky head steps aside for any event the moment one arrives and takes the slot back when the queue drains to it, so an outage cannot silence the channel. Reach for it only where you can prove the condition ended — otherwise it never goes.

Repeats of the same message coalesce into a count rather than stacking. Pass `key` to coalesce notices whose wording differs but which are the same event — a progress line, then its outcome. On that path a repeat overrides only what it states: omit `severity` or `action` and the existing one is kept, so a progress update can't silently downgrade an error or delete the Retry button the first call offered. Keys are one global namespace, so prefix them by feature (`chat:room-delete`, `feeds:star`) rather than using a bare `sync`.

Notices clear on navigation — a notice comments on the surface that raised it. The corollary: raise one _after_ a `goto`, not before. A `sticky` one is the exception and does not clear, so the page that raised it must dismiss it on unmount.

**Copying goes through `copyText`.** `import { copyText } from '$lib/clipboard'` — it writes the text, raises the confirmation, and handles the two failures that otherwise pass for success: `navigator.clipboard` is absent outside a secure context, and a write can be refused. All copies share one notice key, so copying several blocks in a row counts up rather than queueing identical banners. Do not call `navigator.clipboard.writeText` directly. A copy button is `CopyButton`, and a value shown to be copied is `CopyField`.

In the chat transcript the message actions live in one **turn action row** under the message body — copy, star, reply, delete, left to right in ascending consequence, so the destructive button ends the row rather than sitting beside the benign one. The row is revealed on hover (or on tap of the active row, via `tapActivation`) but keeps its layout box either way, so revealing it never reflows the transcript.

**A system row gets the same row**, and it goes **inside the `.cmd-row`'s `.content` column** — that row is a two-column flex (gutter mark + content), so a third child would sit beside the card rather than under it. The row was withheld for a while on the reading that a notice is not a turn, but each button does something the server already supports on a `role='system'` row: copy takes the markdown a `!command` wrote, `DELETE /chat/messages/{id}` accepts its id, and a reply cites it through the snapshot path that already names a system parent as one of its cases. The one carve-out left is a **search-results** row, which renders cards rather than markdown and so has no source worth copying. Gating is otherwise the same derived values a turn uses.

`.cmd-output`, `.external` and `DraftCard` share one uniform `var(--space-2)` padding. They are the filled blocks a turn's content column holds and they stack under one another, so their text has to start at one inset; a wider horizontal pad on one put its first character a step right of the block above it.

**Reply** stages a citation rather than acting on the row, which is why it sits after the star and before delete. It is gated on a durable `msgId` like the other two, and additionally withheld in the aggregate panes: All / Starred have no composer, so a staged reply would have nowhere to go. Four buttons still tile cleanly under a thumb because the touch overlays are sized at the **button pitch** (`calc(100% + var(--gap))`) rather than at a flat 44px — at a flat width they would overlap and hand a tap in the seam to whichever won the stacking order. The composer's chip and the rendered quote block both cap their excerpt at `REPLY_EXCERPT_CHARS`, the same number the server sends back, so what you see while composing is what a reload shows. `MessageReply.deleted` is optional and must be **truthy-tested, never compared to `false`**: a citation staged in the composer carries no flag, and treating absence as deleted renders every fresh reply muted.

What copy puts on the clipboard is `messageCopyText` (`stores/segments.ts`): the turn's prose groups joined by a blank line, activity chips and tool traces excluded — a tool trace is never something you want to paste. It is the **markdown source, not the rendered html**, which is also why fenced code carries no copy button of its own: the source keeps its fences, so copying the message already yields the code ready to paste. Copy is withheld while the turn is still streaming, because half an answer is not an answer. The star is not — it marks the row, not the text — which is why it survives a streaming turn where copy does not.

The row's star is the only star on a turn (ISSUE-691). A starred row is marked at rest by a 4px `--accent-amber` rule along its left edge, drawn as a `::before` border inside the row's inline padding: a real border would shift the avatar and text off the column they share with the headings, a box-shadow would vanish in forced-colors mode, and the pseudo-element is inset vertically so two starred rows read as two segments. A visually hidden "Starred" carries the state to assistive tech, since the `aria-pressed` toggle is in the hidden row. The per-turn metadata (`#task · model · duration · tools`) is the last member of the same row, right-aligned, and follows its reveal; it used to float in a hover bar over a continuation row's first line, where nothing reserved space for it. System rows show no metadata, as before.

**A user row also reports its own send** (`.send-pending` / `.send-failed` under the body, driven by the `sendState` lifecycle on `ChatMessage`). The failure goes there and nowhere else — it used to be written into the assistant placeholder, which made "your message never left" read as "the assistant errored replying". Three rules the marks encode. The pending mark is withheld for a grace period rather than shown on every send: a send resolves in well under 100ms, so an unconditional indicator flashes for a frame and teaches you to ignore the one place a real problem would be reported. **A turn carries exactly one progress indicator at a time**, which is why the assistant placeholder is appended on the ack rather than on submit — pre-ack the user row owns the indicator, post-ack the assistant row does. Appended up front it spun its ack verb before the message had reached the server, so a slow send showed two spinners and the assistant one was claiming work that had not started; a `!command` runs inside the request, so it made that certain rather than occasional. The cost is a sub-grace window with no indicator, which is the user's own bubble arriving, and the reason the append is guarded on the room — it now runs after an await, and `messages` is rebuilt per room. And the turn action row is withheld entirely from a failed send — copy, star and delete all act on a durable turn, and this one never became one, so a lone copy button would only compete with the Retry that is the actual next move. Retry is offered only where it can work: an expired session and any other 4xx that is a verdict on the request (409 archived, 400 over-cap, 413) get the report without the button, on the same reasoning that governs the star's `starrable` gate — an affordance that cannot succeed is worse than none.

**A bordered `Alert`'s type sizes belong to the component: `--text-base` for the title, `--text-sm` for the body; an inline one has the `.banner` box's one size.** A caller styling markup inside the slot sets weight, colour, opacity and layout — those are what tell a label from its detail — and never a `font-size`. Both sizes used to be raw literals in the component, which is subtler than it looks: a caller cannot read a literal it can only see rendered, so a slot wanting to sit with the title wrote its own approximation of it. The admin standalone notice sized its lead, labels and detail lines at 0.9/0.85rem and so rendered a step above every other banner in the app — and being the notice a reader meets on a fresh local install, the one that looked wrong was the one most likely to be seen. `Alert.typography.test.ts` is the net, over the component and over every call site that classes its slot content.

**Out-of-band means it has no natural home on the page.** A background sync failed, a link was copied, an optimistic update rolled back silently. In-band state stays where it is: a failed send belongs on its own message bubble, a validation error under its field, and a page that failed to load in that page's banner where it can stay put and be re-read. Routing those through a notice double-reports the failure and then takes the report away after four seconds. Where a surface has no banner for such a failure, a notice beats silence — but reaching for one there is a sign the surface is missing a banner, not a licence to skip it.

**Global search uses `Modal variant="palette"`.** It sits near the top on desktop and fills the viewport at phone widths. Its two stacking tokens keep it above an open viewer or lightbox. Modal owns focus and Esc and stops page shortcuts while palette controls hold focus. `createUrlSelection` handles same-route `goto` changes as well as Back/Forward, so result links can change a selection without remounting its page.

**The shared content viewer is `Modal variant="viewer"`.** File previews, expanded feed entries and room-note file editors use its compact header, metadata/actions snippets and visible Close. Viewers default to 960px wide and fill the safe viewport height, with the shared outer margins. Keep these dimensions stable across file types and content changes. Long content scrolls inside; text and source areas fill the available body. `bodyKey` resets scroll only when the item changes. Optional `ViewerNavigation` stays inside the dialog focus scope, beside the body on desktop and in the header on phones. Its arrow keys ignore editable content, native media controls and nested dialogs. bits-ui owns focus, dismissal and scroll locking; keep source-specific fetching and actions in the callers. The viewer uses `--scrim-viewer-bg` and viewer stacking tokens; default Modal dialogs keep their existing appearance.

Three shapes look like these and are deliberately not them. A wait for one request's answer (`waitForDoctorRun`, a shared block's Run now, a health extraction, the config editor's `RequestProgress`) is a bounded loop that awaits each read, returns a result or throws to its caller, and in `RequestProgress` backs off on failure; `startPolling` fires on a fixed interval with nothing awaited and no end, so it is not that loop. A store poll with its own backoff (`notifications`, `navUnread`, `connectivity`) schedules its next delay from the last answer, which a fixed interval cannot do; `notifications` and `connectivity` use `onDocumentVisible` for the return only. ### Settings pages

Every module settings page is `SettingsLayout` → `Card` → `Field`, the last two from the `ui` barrel; a credential is the barrel's `SecretField`. Do not build a settings page out of raw markup. A card's `actions` are for actions belonging to _that card_ ("Refresh all now"), not the page's save, see below.

| Component        | Use for                                                                                                                                                                                              |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SettingsLayout` | The page frame: `title`, `description`, `loading`, `error`, `info`, `headerActions`. `title` is optional — omit it when the `ShellHeader` above already names the page, and the header row collapses |
| `HeaderSave`     | The app bar's slot for a page's single save. Pair with `useSettingsSave`                                                                                                                             |
| `ServiceCard`    | A connected-service card on `/settings` or a module settings page                                                                                                                                    |
| `GarminCard`     | The Garmin connect/MFA/disconnect flow — a `custom_ui` service whose auth is an interactive exchange, not a set of writable fields                                                                   |

**A settings page has exactly one Save, and it lives in the app bar.** Call `useSettingsSave(() => ({ dirty, saving, save }))` during component init and render `<HeaderSave />` in the `ShellHeader`'s `tools` snippet — in the page itself for `/settings`, in the module `+layout.svelte` for a module settings page, where it renders nothing on every other page of the section. Return `null` from the callback to withdraw the contribution (a page whose module is switched off has nothing to save). Do not put a page-level Save on a `Card`.

**`dirty` comes from `createDraft` (`lib/ui/draft.svelte.ts`), not a hand-kept JSON snapshot.** `createDraft(initial)` holds the record the form edits as `value` and says whether it differs from the saved copy: `dirty`, `reset(next)` to load a record as clean, `reset()` after a save, `changed(of?)` for the fields that differ (by `changedProfileFields`' rule, so a page that sends a patch sends only those), and `saved` for the copy itself. A form whose saved shape is computed from several pieces of state rather than held as one record (a briefing payload, health settings' visible height input) uses `trackChanges(() => shape)` beside it, which is the same check over a getter, with `mark()` for the save. Number and list fields parse through `lib/ui/parse.ts`: `parseNumber`, `parseOptionalInt` (blank is `null`, which unsets; text below `min` or not a whole number is `undefined`, which leaves the setting alone), `parseList` (comma or one per line) and `formatList`.

**Contributors aggregate; they do not replace each other.** `/settings` edits the profile _and_ holds a `ServiceCard` per connected service, each writing through a different endpoint — so `ServiceCard` registers itself and has no button of its own, and one header Save covers the lot, asking only the parts actually holding edits. This is why `/money/settings` and `/location/settings` get a working header Save from their `ServiceCard`s alone, with no page-level registration. Before this, `/settings` carried three copies of the same-looking button (Identity, Preferences, Karakeep) and a fourth card would have added a fourth.

Two placement rules the component depends on. `<HeaderSave />` goes **before** the section's settings cog, so the cog keeps the bar's right edge and does not move as the save comes and goes. And the "Unsaved changes" badge is always in the layout, merely `visibility: hidden` when clean — `.header-tools` is right-aligned, so a badge that appeared as you type would shove everything to its left sideways mid-edit.

Still their own buttons, because they are per-record forms rather than the page's state: "save this source" / "save this shared block" on briefings settings, and the entity/service modals on money settings. Clearing a stored secret also stays immediate and separately confirmed — a deletion is not an edit awaiting a Save.

**`Field` supplementary text is three-slotted by whether the user must see it.** `hint` is optional guidance and renders in a `HintPopover` behind a "?" beside the label. `warning` and `error` render inline, because a hover popover is discoverable, not seen. A data-integrity notice ("this client is never invoiced automatically") is a `warning`, not a `hint` — do not put anything the user needs to act on behind hover.

**A control takes its `Field` caption through context, never by being inside a `<label>`.** A `<label>` makes its first labelable descendant its control, so a button in the slot became a second way to press it: a "Tracking" caption stopped location tracking, and a "Sender filters" caption deleted a sender. `Field` is a `<div>` and publishes `{ controlId, labelId, describedBy, invalid, required }` (`setFieldContext` / `getFieldContext`). `Input`, `TextArea`, `AutocompleteInput` and `Checkbox` claim it as native controls: they take the id the caption's `<label for>` names, so clicking the caption focuses or toggles them. `Select`, `MultiSelect` and `DateRangeFilter` claim it by `aria-labelledby`, the caption is a `<span>`, and clicking it does nothing. A field nothing claims (a chip list, a row of checkboxes, read-only text) is a `role="group"` its caption names. The first control to claim a field wins, so two never share an id; `Modal` and `MultiSelect` hide an outer field from their content. A new form control reads the context the same way rather than taking its own label prop.

## Color

Every recurring meaning-bearing color is a token in `lib/styles/tokens.css` (or `app-tokens.css`, for a product surface), defined in **both** the `:root` and `:root[data-theme='light']` blocks. Four roles:

- `--status-{danger,warn,success,info}-{fg,bg}` — severity. `-fg` for a bare status label, `-bg` for a filled chip's fill (pairs with the same `-fg`). Errors, warnings, status chips, badges, danger buttons, delete links.
- `--accent` — the primary-action fill. `Button`'s `primary` variant is filled with it, and that is normative: health carried a second `.btn` system that outlined `primary` in `--accent-blue` instead, and the two could not both be right.
- `--accent-blue` — the _interactive_ blue: active tabs, focus rings, in-app cross-references. Distinct from `--status-info-fg`, which marks a severity rather than something actionable. Not primary buttons — see `--accent` above.
- `--accent-amber` — the bot's identity accent, and the "starred" color. `--accent-amber-fill{,-hover,-fg}` is its filled-button form.
- `--status-dot-{success,danger,warn,info}` — the live-status dots, read only by `StatusDot` (the admin dashboard, the notification panel). Named on the status scale, not `ok`/`bad`. Off the `-fg` tint scale on purpose, and one value in both themes: a dot carries no text, so it needs saturation a tint cannot give it, and a theme-tracking dot reads as two states rather than one.
- `--link` — content links, and the single decision point for them. A surface joins by putting `prose` on its container, **not** by writing a local `a` rule; chat, the briefings reader and the feeds reader each had their own before, so briefing links were not visibly links and feed links were grey and permanently underlined. Hover is the underline only — the color already marks the link, and moving both reads as a state change. A button that reads as a content link takes `.link-action`, which draws it in this token.
- `--money-{income,expense}` — signed-amount direction. Deliberately off the status scale: an expense is not an error.
- `--map-marker-{live,browser}` — the location map's current-position dot, tracker green and the orange browser-geolocation fallback. Darker in light, where the bright green washes out on light tiles. They replaced a per-component light override in `LocationMap`.
- `--hover-{bg,fg}` and `--selected-bg` — the pointer-over fill of a button, menu item or list row, and the fill that stays on the current or selected one. Both are the raised surface today, named apart so either can move alone; a rule that covers both states (`:hover, .active`) uses the hover pair. Each is resolved on `:root`, so a scope that redefines `--text-primary` restates `--hover-fg` beside it (the chat pane does). The labs matrix is outside them on purpose: its hover is an inset overlay mixed from `--text-primary` at 4%, because an opaque fill would hide the tinted and flagged cells under it. A table row is the other exception: an interactive row (`.table--interactive`) hovers in `--surface-card` while the selected row (`.is-selected`) takes `--selected-bg`, so a hovered row and the selected one stay two looks; `.table--on-card` moves both a step up for a table drawn on a card (table.css).
- `--row-{danger,warn}-bg` — the wash on a table row or record card flagged as an error or a warning, faint enough that the row's text keeps its own colour. Not the `--status-*-bg` fills, which are for a chip. A table row takes it through `.is-danger` / `.is-warn`, never a page rule.

`--status-critical-{bg,fg}` is a fifth severity above danger, for a value that is not merely out of range but clinically critical (the bloodwork `flag-C` cell). Unlike the four above it, it is a solid saturated fill rather than a tint, so its `-fg` is the text laid _on_ `-bg`.

`--status-partial-{bg,fg}` sits beside the severity scale rather than on it, for a state that is part-done rather than late (an incomplete vaccine series). It is a token pair and not a categorical hue because two pages were each carrying the same purple plus its own light override; what keeps it off the ramp is that ranking it against "overdue" would say something false.

Supporting scales: `--surface-{base,card,raised,badge,overlay,reading,reading-card}`, `--text-{primary,secondary,muted,dim,reading}`, `--border-{default,subtle,hover}`, `--text-{2xs,xs,sm,base,lg,xl}`, `--font-{sans,mono}`, `--shadow-{overlay,md,lg}`.

**Type** has a token for every value a rule sets, so no stylesheet writes a bare weight, leading or caps tracking:

- `--weight-{regular,medium,semibold,bold}` — 400 / 500 / 600 / 700.
- `--leading-{none,tight,snug,normal,relaxed}` — 1 / 1.2 / 1.4 / 1.5 / 1.6, unitless so the leading follows the element's own size. `none` is a single line box (a glyph button, a badge), `tight` a heading, a dense label or a text control (the `font: inherit` pin below), `snug` a card or list line, `normal` body text, `relaxed` long prose at a reading measure. A value between steps is rounded onto one, never written out.
- `--tracking-caps` — 0.04em, the letter-spacing of every uppercase run: `.micro-label`, table headers, `Badge`.

**Motion** is `--duration-{fast,slow}` (0.15s / 0.3s) and `--ease-standard`, plus `--ease-decelerate` for a panel sliding in from an edge (the sidebar drawer), with `--transition-fast` built from the first and the last; an `animation` cannot take the transition shorthand, which is why the parts are tokens too. A spinner's or a pulse's own length is a rhythm rather than a response, and stays on the animation. `--disabled-opacity` (0.5) is how a disabled control is drawn, at reduced strength rather than recoloured. `--icon-{xs,sm,md,lg,xl}` (0.75 / 0.875 / 1 / 1.25 / 1.75rem) is the icon box, in rem so an icon tracks the text-scale preference; `Icon` is how a glyph reads it.

**Spacing** is `--space-{1,2,3,4,6,8}` — a 4px ramp (0.25 / 0.5 / 0.75 / 1 / 1.5 / 2rem) in `rem`, so it tracks the text-scale preference. Use a step; the `off-scale-space` rule flags a raw `rem` in a spacing property. Values below `--space-1` are off the ramp on purpose (hairline nudges, icon gaps) and are baselined rather than rounded. `px` is right for a border, `em` for something sized against its own control.

**Radius** is `--radius-{sm,md,pill}`, with `--radius-card` written as `var(--radius-md)` rather than a second copy of the value, so the two spellings cannot drift, and `--radius-round` (50%) for a circle. **Stacking** is `--z-{sticky,drawer-backdrop,drawer,notice,modal,modal-panel,viewer,viewer-control,lightbox,palette,palette-panel,popover,toast}`, with three hard constraints: `--z-popover` must clear `--z-modal-panel`, because every money form is a `Select` inside a `Modal` and both portal to `<body>`; and `--z-lightbox` must clear `--z-viewer-control`, because the image zoom opens from inside the feed reader; and `--z-palette` / `--z-palette-panel` must clear the lightbox, because global search can open over a reader or preview. A small integer inside a component's own stacking context (a sticky table corner, the chat FAB) is not on this scale and should not be — it orders siblings, not layers, and naming it after app-wide chrome would claim a reach it does not have.

**Focus** is one global `:focus-visible` rule in `primitives.css`, in `--focus-ring-color` at `--focus-ring-width` and `--focus-ring-offset`. It is 2px because that is the WCAG 2.2 floor and a ring you have to look for is not doing its job. Do not add a per-component ring. A full-bleed row that would push the ring outside its own box pulls it inward with `outline-offset: calc(-1 * var(--focus-ring-width))` rather than removing it. If a control genuinely needs the outline suppressed — a bits-ui popover focused on open, a text input inside a wrapper that carries `:focus-within` — say why in a comment, because three suppressions had nothing standing in for them.

**A text field shows focus by its border, not the ring.** A browser treats a focused text input as focus-visible however it was focused, so a ring would draw on every click; text fields are exempt from the ring, and one rule beside that exemption gives them `border-color: var(--focus-field-border)` instead (the interactive blue, declared in both theme blocks). It covers `Input`, `TextArea` and the full-width `Select` trigger (an adorned `Input` draws it on its box by `:focus-within`), and it is element-qualified so it beats a component's resting border and loses to `.invalid`, which keeps its red while focused. A control that draws its own edge and that rule cannot reach (a ghost `Input`, whose transparency outranks it) keeps a local focus rule in the same token; `fieldCascade.test.ts` fails a focus-only rule that gives a border any other colour. The chat composer is the one exemption: its pill's `:focus-within` border is part of the composer's own look.

`lib/styles/tokens.test.ts` reads the two token sheets as one and holds four of these invariants so they are checked rather than remembered: **theme parity** (every color token — found by prefix, the role-named `--hover-*`, `--selected-*`, `--row-*` and `--focus-field-*` included, plus every `*-filter`, which corrects an asset the theme does not control and fails the same way — has a light value, the light theme defines none the dark lacks, with a `THEME_INVARIANT` allowlist naming the deliberately single-valued ones — `--on-accent-fg`, `--on-scrim-fg`, `--scrim-bg`, the `--accent-amber-fill` trio, `--status-dot-*`, `--status-critical-fg`); the **z ladder** being strictly ordered, duplicate-free and satisfying the constraints above; the **control heights** being defined, ordered, and in `rem`; and the **type and motion scales** (weights, leading and icon sizes ordered, leading unitless, `--transition-fast` built from the duration and easing tokens, and none of those families redefined in the light block).

Not colors, but declared alongside them and read the same way: `--font-sans`, `--chip-{padding-x,gap}`, and in `app-tokens.css` `--chat-{row-inline,gutter,avatar,avatar-gap,body-max}` (the last one is the readable width every block in a turn's content column caps at — the prose body, a command's output, an expanded activity chain, the citation above a reply; the first three carried the same literal separately across two files, agreeing only by a comment saying they had to), `--sigil-filter` (tints the octopus mark per theme, also in `app-tokens.css`), `--calendar-icon-filter` (the same, for the browser's own calendar glyph on a date input — a UA pseudo-element that can only be filtered, never restyled), `--map-icon-filter` (the same again, for MapLibre's control glyphs), and the geometry tokens `--safe-{top,bottom,left,right}` / `--app-height` / `--kb-height`. The last three groups are written by code, not by a stylesheet — see "Platform and the native shell".

- `--surface-overlay` — chrome floating _over_ content: a feed card's title overlay, the fixed status badge, an autocomplete popover, jump-to-latest.
- `--surface-reading` / `--text-reading` — a long-form reading pane (the chat transcript, the briefings reader) and its softened body text. The surface is card-colored in dark but pure white in light.
- `--surface-reading-card` — a card inside a reading pane (a received mail, an external turn, the activity chip, a citation). Not `--surface-card`, which is the reading surface itself in dark, and not `--surface-badge`, the pill fill.
- `--border-hover` — one step stronger than `--border-default`, for the hover state of an interactive card or link-tile. Use it rather than a literal, or the hover affordance silently vanishes on white.

For chrome that sits on a surface the theme does _not_ control: `--on-accent-fg` (text on a filled accent), `--on-scrim-fg` (text on a scrim that stays dark in both themes), `--scrim-pill-{bg,fg}` (a pill over media, which flips scrim direction), `--shimmer-tint`, `--shadow-overlay`. The first two are deliberately one value in both themes, like `--status-dot-*`.

**The anti-pattern:** hardcode a dark-theme hex, then hand-write a `:global(:root[data-theme='light'])` rule beside it. Doing that per page is how the app accumulated roughly ten different reds for one meaning, and how several chips ended up with no light rule at all and rendered dark fills on white. Reach for a token. If a genuinely new meaning appears, add a token pair to both theme blocks — never a local override. The parity half of that rule is now enforced by `tokens.test.ts` (above), so a token added to one block only fails there rather than shipping.

Legitimately exempt, and enforced by an allow comment rather than a habit:

- **Categorical palettes**, where the hue encodes a _kind_ rather than a severity — health encounter-type badges, the admin `SOURCE_COLOR` constants, the location activity/speed palettes. Collapsing these onto the status scale would erase the distinction they carry.
- **Data visualization** — Chart.js and MapLibre are handed a config object rather than reading the cascade, so they cannot resolve `var()` at all. Chart _chrome_ (grid, ticks, tooltip) is centralized in `$lib/chartTheme`, which is theme-aware; only series colors belong on the page. See the `dataviz` skill before picking them.
- **Third-party DOM** — `!important` rules restyling vendor markup (`.maplibregl-*`) are overriding another stylesheet, not expressing our design language.
- **Fixed-surface chrome** — lightbox, avatar fills, media letterboxes.

Mark an exemption in whichever form fits the shape of what you are exempting. Every form takes a reason after the colon — an unexplained exemption is indistinguishable from an oversight.

| Form                                             | Covers                                                | Reach for it when                                                                                             |
| ------------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `/* design-lint-allow: reason */`                | The next line carrying code (or its own line, inline) | One declaration. The comment may span several lines; blank and comment lines between it and the code are fine |
| `/* design-lint-allow-begin: reason */` … `-end` | Everything between the markers                        | A contiguous block — a categorical palette, a chart config                                                    |
| `<!-- design-lint-allow-file: reason -->`        | The whole file                                        | The file exists to hold literals. Blankets anything added later, so prefer a region                           |

Not linted at all: `*.test.ts`, which asserts on the very literals the rules forbid; hexes appearing inside comments, which are documentation rather than declarations; and HTML numeric entities like `&#9654;`, which only look like hex.

## Sizing and layout

- Type and spacing are `rem`; the root font-size percentage is the text-scale preference (`small` unscaled / `medium` 110% default / `large` 120%). Scaling the root is deliberate — type and the space around it grow together. Do not scale only the type tokens.
- A `<button>` does not inherit font. If you size a control in `em`, set `font: inherit` on it, or the `em` resolves against the UA's ~13px and the control stops tracking the text-scale preference.
- Fixed `px` is correct for borders and SVG chart labels, which should not scale.
- **Size a text control through a `--text-*` token, never a literal and never by inheritance.** iOS zooms the page on focusing an `input`/`select`/`textarea` that computes under 16px and does not cleanly zoom back out, and every token a control uses (`--text-2xs` through `--text-base`) is under that line. `app.css` floors it by redefining those tokens _on the control_ under `@media (pointer: coarse)`, so a rule reading `var(--text-sm)` is covered however it is written and whatever its specificity — but a raw `font-size: 12px`, or a `font: inherit` taking its size from a wrapper, reads no token and drops straight back through. `touchZoom.test.ts` is the net for those (it scans `:global(input)` too, which is how a page used to reach into a control) and holds the exemption list: the chat composer, which owns its size from the pill around it, and the file editor and plain-text file view, which keep their desktop density on a phone. Each exempt control pins the viewport's zoom while focused instead (`lib/zoomPin.ts`), and the test fails on one that does not. The fallback in that block is wrapped in `:where()` on purpose: a control may still ask for _more_ than the floor.
- **A row that mixes a text input with buttons or selects is a `.control-row`** — the field tier, and the only way the shared-height rule survives touch. The 16px floor lifts native controls but not `Button`, `Chip` or the compact `Select` triggers, which are actions rather than fields, so an unscoped mixed row sits taller in its inputs than its buttons on a phone. The scope (`app.css`) redefines `--control-height-{sm,md}` onto `--control-height-lg` and `--control-radius` onto `--radius-sm`, and every control resolves them — bigger and squarer than the app bar's compact pills, which is also what tells the two zones apart. It sets tokens and no layout, so adding the class to an existing flex container cannot move anything sideways. `Field` composes it, so every settings form is already a field tier; a body toolbar opts in at the container (`toolbar control-row` on the money and admin filter bars, `.money-section-tools`). The tier is floored on touch too, so the whole row lands on one number rather than the inputs overshooting. Do not re-tune `--control-height-*` against a touch screenshot; `controlTier.test.ts` is the net.
- **Anything declaring `font: inherit` on a text control must pin `line-height` beside it.** The shorthand also sets leading, pulling in the body's 1.5 at a specificity no weightless rule outside the component can correct — which is what made a 16px-floored input compute taller than the tier around it and stand proud of every control in its row. `Input` and `Field` both do this; the full-width `Select` trigger used to pin 1.5 to chase that inherited leading, and no longer needs to.
- **Touch targets use `.touch-target` from `primitives.css`, gated by `(pointer: coarse)`.** The floor is `--touch-min` (24 CSS px in each direction), or the WCAG 2.5.8 spacing alternative: a 24px circle centred on an undersized target must clear other targets and their undersized-target circles. Inline links in running text and browser-sized controls are exempt. The feed card star and mobile section dropdown trigger use `--touch-comfort` (44px) because they were reported as hard to hit; dropdown option rows are also 44px on touch. Fine pointers keep the visible control as the target.
- A row of small icon controls needs its touch targets reasoned about **together**. Add `.touch-target` to the interactive element and set `--touch-target-w` / `--touch-target-h` where it needs more than the floor; `100%` prevents expansion on an axis with a close neighbour. The shared out-of-flow `::before` keeps the bar height unchanged. Do not write another overlay in a component. Widen the row gap where needed so neighbouring targets do not overlap. For tightly packed rows, a width of `calc(100% + var(--gap))` tiles targets at the button pitch; the chat turn action row is the worked example. Preserve the migrated sidebar, nav, turn-action, queued-send and notice target sizes.
- **Measure touch targets in the browser.** Paste `scripts/touch-audit.js` into Chrome with touch emulation enabled at 375×667 and 768×1024. It measures ancestor-clipped hit areas and reports both floor/spacing failures and sampled overlaps. Inspect the reported states: open backdrops occlude controls, scroll edges clip targets, and the feed star intentionally intercepts its card. Scroll a reported control fully into view before judging its size. Check hidden message actions too. An overlay clipped below the floor needs padding or room in its container. Chrome emulation does not replace an iOS device check.
- Controls that share a row share a height: `--control-height-{sm,md}` (plus `--control-height-lg`, the field tier above), applied as `min-height`. Corners come from `--control-radius`, whose root value is the app bar's pill — so adopting the channel in a new control changes nothing until it lands in a `.control-row`. `Button`, `Chip` and the `Select` trigger each used to compute their own box from a font size, a padding and (for `Select`) a border, and landed on four different answers — a `Select` beside a `Button` sat ~2.6px short, by an amount that _changed with the text-scale setting_, since everything but the border is in `rem`. Set both on any new inline control. `min-height` rather than `height`, so a wrapped label still sets the box.
- **A dashboard's content column caps at `--content-max` via `.content-frame`** — never a page-local `max-width`. The cap is `px` while nearly everything else here is `rem`, because it bounds the screen a layout may claim rather than the type inside it: a `rem` cap would widen the column at the large text-scale setting, which is the setting picked to make lines easier to follow. The `.card-pane` sections (dashboard, briefings, groups, admin) cap at `--card-pane-max` (1600px) instead, a wider cap for a wall of cards; feeds lifts it, since its fourth and fifth columns need more room.
- **A wall of cards picks rows or masonry by how much the heights differ.** Masonry (`CardGrid masonry`) suits cards of very different heights that the reader does not compare across, like the groups overview. A dashboard whose cards are close in height reads better in plain rows: masonry was tried on `/admin` Status and the packed columns looked jumbled where equal rows line up. In rows, source order sets each row, so order the cards into groups of the column cap (three by default) and give a table or a wall of sub-cards `data-width="full"`. A card that can end up alone in a row, because a full-width card follows it or because a card before it is optional, gets `data-fill` rather than a page-side span computed from which cards rendered. `/admin` Status is the worked example: `data-fill` on Task activity covers two columns, and on the bot icon it covers a missing subscription card.
- A status chip needs a `min-width`, or its variable width shifts every column after it, row by row.
- A toolbar holding only a result count needs a `min-height` so it matches one holding filters; `.toolbar` carries it (see "Small shared blocks").
- **Do not style scrollbars.** Touching `::-webkit-scrollbar`, `scrollbar-width` or `scrollbar-color` opts out of the fading overlay bar the platform draws and gets a permanent one whose track takes width. That was tolerable while pages scrolled as documents; the app is now one screen tall and scrolls inside its panes, so a styled bar becomes a fixed strip beside every list.
- **An edge-pinned element pads with `max(<its own padding>, var(--safe-*))`**, never with the inset alone — the inset is 0 on a device without a notch, and the element would then sit flush against the edge. A `position: fixed` overlay escapes every ancestor's padding, so it has to carry the insets itself. `Modal` pins its panel to the viewport centre and subtracts `--safe-*` from both ends of its `max-width` and `max-height`, so a full-height dialog stays inside the safe box; reach for `Modal` rather than a new fixed overlay.
- **Never reintroduce `100vh` or `calc(100vh - Npx)`** for a full-height surface. Height comes from `--app-height` and `--kb-height`; see below.
- **A viewport breakpoint is one of three steps**, each written as a pair so a `max-width` rule and a `min-width` rule never both match at the boundary:

  | Step | Below the step        | From the step         | Where it bites                                                                           |
  | ---- | --------------------- | --------------------- | ---------------------------------------------------------------------------------------- |
  | `sm` | `(max-width: 640px)`  | `(min-width: 641px)`  | phone layouts: stacked forms, hidden table columns, the 0.75rem inline edge              |
  | `md` | `(max-width: 768px)`  | `(min-width: 769px)`  | the sidebar becomes a drawer, `HeaderNav` a dropdown                                     |
  | `lg` | `(max-width: 1023px)` | `(min-width: 1024px)` | the app nav hands off to its overflow menu; side-by-side panes stack (labs panel/upload) |

  A custom property cannot appear in a media query, so the table is the definition and `off-scale-breakpoint` holds it, in the style layers as well as the components. A layout that sizes itself by the box it sits in rather than the window is a container query instead, which the rule does not check: `CardGrid`, the settings shell, and the health document, condition and encounter grids, which step at CardGrid's 40 and 64rem because the same grid sits directly on one page and inside a card on another.

- Below 640px the nav, the shell header and the settings wrapper all align on an inline edge of **0.75rem** — the same figure the money shell fixes. A page that sets its own drifts out of line with the bar above it.
- **Touch affordances reveal on tap, not on hover.** iOS synthesizes `:hover` on tap and then leaves it applied, so a hover-revealed control stays lit on the row you last touched. `chat/tapActivation.ts` is the shared primitive: a tap is a press within its slop and time bounds, and one active row at a time stands in for hover. Reveal instantly — a fade on an affordance the user has already reached for reads as lag.
- **A fill that encodes state may be named only by the state's own rule, and never transitioned.** Where a control's colour _is_ its mode — the chat send button, blue to send and red to stop — one rule per mode declares the fill and no interaction state — `:hover`, `:active`, `:focus` — may re-declare it, at any specificity or through a custom property. An interaction adjusts what is there (`filter: brightness()`) instead. `:disabled` is the single exception, because it is the absence of an interaction rather than one the mode could disagree with: a disabled control has to go grey, and expressing that through a `:disabled` variant of every mode rule would double the count this rule exists to hold at two. Order it ahead of the mode rules, so a mode still wins the tie. This is not tidiness: a hover rule re-asserting the idle fill outranks the mode class by a compound, so it repaints the running state in the idle colour while the icon stays put — and under a synthesized hover that is the resting appearance, not a flicker. Easing such a fill has the same effect for the length of the ease, so it flips rather than transitions. `Composer.svelte`'s `.mode-btn.send` is the worked example, with the invariant pinned in `Composer.sendButton.svelte.test.ts`.

## Page skeletons

**Module page** (`routes/<module>/+layout.svelte`): `AppShell` with a `ShellHeader` header snippet (`SidebarToggle` in `leading`, `HeaderNav` in `nav`, a `Cog` link to `<module>/settings` in `tools`) and a `Sidebar` when the module has a list/detail split. `routes/briefings/+layout.svelte` is the cleanest example.

**Module settings page** (`routes/<module>/settings/+page.svelte`): `SettingsLayout` wrapping `Card`s. Call `getModuleServices(<module>)` first and render the "Module disabled" banner when `module_enabled` is false, instead of the configuration UI.

**Module settings with sections** (money — Connections | Invoicing | Portfolio): each section is a route under `settings/`, and each is still the page above. Two placements are not free choices. The module-disabled gate and the `getModuleServices` call move up into `settings/+layout.svelte`, which persists across a section switch — so the check costs one request per visit rather than one per navigation, and the section that renders the service cards reads them out of context instead of fetching the same endpoint twice. The **sidebar** goes in the _module_ layout (`routes/<module>/+layout.svelte`), gated on being on a settings route, because that layout owns the `AppShell` and a `Sidebar` has to be a sibling of `.shell-main` to be a column rather than a block scrolling inside the pane. Keep the section list in `lib/<module>/settingsSections.ts` so the two files cannot drift, render it with `SidebarNav`, and add `SidebarToggle` to the app bar's `leading` slot on settings routes only.

**Every top-level route renders an `AppShell` and is listed in the `app-content-fill` class on `routes/+layout.svelte`'s `<main>`.** The two are one decision, not two: without the shell nothing pins the app nav, and without the class the document scrolls and carries the nav off the top of the screen — which is only noticeable on a phone or in the iOS app, where the nav is the only way back to another section. The class also locks document scrolling and stops overscroll chaining, so touch scrolling belongs to the panes rather than the page — a fill route that scrolls the document has lost its nav. A single-page section (`/`, `/chat`, `/settings`) puts the shell in its `+page.svelte`; a section with sub-routes puts it in `+layout.svelte` — `/admin` moved from the first to the second when it grew Configuration and Logs beside Status. `ShellHeader`'s `title` is the page's name in the fixed bar.

There are two exceptions. The first is `routes/+error.svelte`, which renders no `AppShell` — an error page has no section to be in — and instead flattens `main.app-content` from inside itself. The second is `routes/setup/`, the first-run setup page, which the setup server serves before any config, user or `/api/me` exists: `routes/+layout.svelte` renders it bare, ahead of the identity gate, with no `getMe()`, no nav, no notification poll, no connectivity probe and no service worker, and it is deliberately not in `app-content-fill`, since it has no shell and scrolls as a document. Its frame is `components/setup/SetupFrame.svelte` (the settings shell narrowed to `--setup-max`), and its API calls go through the `*Setup*` functions in `$lib/api`, which do not use `apiFetch` because a 401 there means "locked", not "signed out". Adding a route means adding it to that class list; several in-tree comments still count the routes by hand and go stale, so trust the class list, not the count beside it.

**A page reads the signed-in user from context; it never fetches `/me` itself.** `routes/+layout.svelte` gates the whole app on `getMe()` and publishes what it resolved through `lib/userContext.ts` (`setCurrentUser` there, `getCurrentUser()` in the page) — the same layout-fetches / page-reads shape as `lib/money/settingsContext.ts`. Children render only inside the layout's `{:else if user}` branch, so the value is non-null by construction and a page needs no null handling and no wait for it.

Two properties of that are load-bearing. **`user` is a getter, so read it through `$derived`** — the layout swaps a cached identity for the live one when the connection returns (ISSUE-354), and a page that read it once at mount would pin the stale copy for the life of the page. And **it is display data**: it may be the cached record, and every authorization check is server-side regardless, so branch on it to decide what is _shown_ and never what is _permitted_.

Four routes used to fetch `/me` privately (plus a dead duplicate in `lib/money/api.ts`, since deleted), and the dashboard's copy is why this rule exists (ISSUE-355): offline its `getMe()` rejected, the mount returned early, and the whole page body sat behind a null check while the shell and the header rendered around nothing — a "Dashboard" heading over an empty frame on every cold launch with no connection. A page that needs something the identity does not carry still fetches that something; a page that needs the identity _fresh_ rather than merely current calls `reload()` on the context (the settings page does, for `nextcloud_token`) rather than making a second request of its own.

**Loading and load-failure states** are `LoadState`, which writes the chain below once; a page hands it `loading`, `error` and `empty` rather than writing the `{#if}` chain out. They use `.center-msg`, the one shared whole-pane status message, and the page holds its chrome back behind the load so the message centres on the pane rather than under a half-drawn header. **A pane's loading state is `<PageLoading />`** (`label` for anything but "Loading…"), never `.center-msg` with text in it. It keeps the slot as an empty `.center-msg`, carries the label for a screen reader, and while mounted raises `PageLoader`, one thin bar fixed to the top of the viewport and mounted once in the root layout. Centred text moved two or three times on a cold load, from the middle of the viewport to the middle of the pane once the nav rendered, then again when a module sidebar narrowed the pane (ISSUE-752). The bar fades in after 150ms, so a fast load shows nothing; to look at it against the mock backend, which answers inside that, run it with `VITE_MOCK_LATENCY_MS=1500`. A loading line inside a card is not a pane state: it is `<p class="caption">Loading…</p>` (or `LoadState scope="card"`, which renders the same line), one spelling where there were five. The chat transcript is the one surface with its own: `LoadingOctopus`, the sigil pulsing in opacity alone, so it never changes shape or position. The failure spelling is `.center-msg error` — it is the exclusive twin of the loading branch in the same `{#if}` chain, so it must be the same box, and the older `.loading` / `.error-msg` pair survives only for a line inside a card. Do not reach for `.banner error` there either: a banner sits _above_ a layout that is still rendered, which is a different state, and using it for a whole-pane failure is how three modules ended up rendering the same failure at three sizes and two alignments. `scripts/pane-error-state.test.ts` holds the invariant, over inline controls and over the tree, and reads a pane `LoadState` as a whole-pane failure, so a `{#if !loading}` gate beside one still fails it. **Empty is not one of them**: it is `EmptyState`, at the top of the pane rather than centred in it, because a list with no rows sits where its first row would have been, under the toolbar that is still showing. Vertically centred, it read as a different state on every page whose toolbar height differed.

**The stylesheet is four layers behind `src/app.css`, and the order is the contract.** `app.css` is now nothing but an ordered `@import` list; the rules live in `lib/styles/`.

| Layer            | Holds                                                                                                                   | Travels?      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------- |
| `tokens.css`     | the palette, the scales, both themes, the text-scale roots                                                              | yes           |
| `app-tokens.css` | this app's own tokens: chat metrics, room colours, the app bar, the setup column, the sigil filter                      | no — this app |
| `primitives.css` | the reset, the shared blocks below, `:focus-visible`, the iOS input fixes, `.control-row`, `.content-frame`, `body`/`a` | yes           |
| `app-shell.css`  | `.app-nav` (its overflow menu is `Menu`), the wordmark and sigil, `.app-content`, `.center-msg`                         | no — this app |
| `markdown.css`   | `.markdown`, `.prose` links, the highlight.js palette                                                                   | optional      |

The two module sheets (`settings.css`, `cards.css`) load between the reusable layers and the app's own, which is where they were before the split and where their specificity assumes they are. `table.css` (the table family, below) loads after them and before `primitives.css`: it travels with the reusable pair, and loses ties to `primitives.css` the way the module sheets do. `tokens.css` leads because it declares custom properties on `:root` and nothing else, so it can win no cascade it does not already own — that is what made moving it to the front safe, and it is the only thing the split reordered.

Layers 1 and 2 are the design system: they name no page, no module and no product, and a second project takes the pair unchanged and writes its own `app-shell.css` and `app-tokens.css`. The brand seam is the surface/text/border/accent values in `tokens.css`'s two theme blocks — everything downstream reads them by name. Splitting the file is what makes that line visible; as one 1267-line file it was a matter of knowing which third you were in.

`app-tokens.css` loads straight after `tokens.css` and, like it, declares custom properties and nothing else, so its place decides no tie. A token goes in one sheet, never both; `tokens.test.ts` fails a token declared twice and a product prefix back in `tokens.css`. `--money-*` is still in `tokens.css`, until the library's `--signed-*` pair gives it an alias.

Tests read the stylesheet through `lib/styles/cascade.ts` (`readCascade()` for "does a rule exist anywhere", `readLayer('tokens')` for "what does `:root` declare"), which parses the import list out of `app.css` rather than restating it. Do not hardcode a layer path in a test.

**Small shared blocks live as globals in `lib/styles/primitives.css`** (loaded by `app.css`, see the layering above), because each had been written out verbatim in a dozen files. Use them; do not re-declare them. `redefined-primitive` fails a component rule written from one of these names at the top level (`.caption { … }`), as it does for the primitives' own classes; a page places one under its own container (`.form .caption`).

- **Layout utilities**: `.hstack` (a centred flex row, gap `--space-2`), `.vstack` (a flex column, gap `--space-3`), `.wrap` (adds `flex-wrap: wrap` to either), `.list-reset` (a `<ul>`/`<ol>` with no bullets, margin or padding), `.truncate` (one line with an ellipsis, plus the `min-width: 0` a flex child needs before it will shrink) and `.button-reset` (a `<button>` that reads as its content: no chrome, `font: inherit` with the leading pinned, `color: inherit`). Each was a rule written out in twenty-odd files under a different name. Put the class on the element and delete the local rule; keep a local rule only for what it adds (a `justify-content`, a breakpoint that turns the row into a column), which wins because the utility scores one class. Another gap is `style:--hstack-gap` / `style:--vstack-gap` on the element (the money forms run `--space-2` stacks), not a second rule. They come first in the sheet, so a role on the same element wins a tie: `button-reset caption` keeps the caption's size and colour. `.row` is deliberately not a name: it meant "a wrapping row of controls" under `.settings`, which is now `hstack wrap`. Not chased: the 260 centred rows that also set something else, which stay page rules. `ListRow` truncates its label itself, so a sidebar label never needs `.truncate`.

- `.content-frame` — the wide-dashboard content column: caps at `--content-max` (1280px) and centres in whatever pane it is given. Health, money's portfolio and money's reports share it; health carried the four declarations privately until portfolio wanted the same column. Geometry only, no padding — the adopter's own shell pads it (`.health-frame`, `.report-frame`), and spacing stays at the call site the way `.micro-label`'s does. It caps **content, not chrome**: a bar above it (the app bar, a money section header) stays full-bleed. Pinned by `lib/styles/contentFrame.test.ts`, which fails if a module restates the cap instead of reading the token, or frames a section header.

  `/admin` is not framed either. Its pages keep the settings shell (`class="settings admin-page"`) as their page frame, draw their panels with `Card` and their tables with the table family, and are `.card-pane` pages like briefings, groups and feeds, so `.card-pane`'s `--card-pane-max` replaces the shell's 980px form column and the admin layout carries no width rule. Each page used to widen it by hand and all three landed on the same 1100px with nothing saying they had to agree.

- `.toolbar` — a row of controls over a list or a pane: filters, a search, a selection's actions, a result count. A centred, wrapping flex row at `--space-2` with the field tier's `min-height`, so a bar holding only a count is as tall as one holding filters. `.toolbar--bar` is the strip form, inset `--space-2` / `--space-3` and ruled off with `--border-subtle` (the money toolbars, the files folder bar). Layout only: a toolbar that mixes a text input with buttons carries `.control-row` beside it for the field tier, and a filter in it is `Input size="toolbar"` with a placement class. A count in a toolbar is `.caption .num`, which takes the tier height there and centres in it, so it lands at one height whether the bar fits one line or wraps. A page rule keeps only what its bar adds (`justify-content: space-between`, `nowrap`, a margin). A class rather than a component, because no two toolbars hold the same things.
- `.micro-label` — the small uppercase section heading or `<dt>` label (43 hand-written copies across 23 files). Deliberately typography only: a section heading and a `<dt>` want different space around them, and folding margins in is what produced the variants. Spacing stays at the call site.
- `.caption` / `.muted` / `.description` — the supporting-text roles, and the lowercase siblings of `.micro-label`. `.caption` is `--text-xs` on `--text-dim`: a hint under a field, a timestamp under a title, the detail line under a value, a result count, a field label in a dense form. `.muted` changes **colour only** (`--text-muted`), so it can be dropped onto a span mid-sentence without shrinking it. `.description` is `--text-sm` on `--text-muted` at a `60ch` measure: the line under a page, card or modal title (`SettingsLayout`, `Card` and `Modal` render theirs with it). Caption and muted are two roles because the two tokens are two distinct steps (#888 against #666), and the size coming down with the colour is what makes one a caption rather than merely de-emphasized text. Extra-small text on `--text-muted` is a caption, not a third role: the fourteen rules spelling it moved onto `.caption` one step dimmer. A label or unit at some other size (a `--text-sm` suffix, a legend) is `.muted` plus a local `font-size`, not `.description`, which is for a line that explains. `.muted` is one colour everywhere; the per-theme value is the token's, and no scope may restate the class (settings.css used to, on `--text-dim`). All of these had been everywhere and named nowhere — the caption was spelled `.hint` on four pages, `.meta` on five more and `muted small` on two, and the description was `.settings .hint`, scoped to the settings shell. `.hint` is retired; it named two roles. Typography only, like `.micro-label` (the measure is `.description`'s one piece of geometry); spacing (including a `<p>`'s `margin: 0` reset) stays at the call site, and the one shared placement is `.settings :where(.description)`, a step under a settings page title. Pinned by `lib/styles/captions.test.ts`, which allows a call site to _place_ a class but fails if one restates its colour or size, and fails any rule outside `primitives.css` that writes a role's typography out under a name of its own with nothing beside it but placement. A rule that also draws a surface (a pill, a sortable header, a tab) is a component sharing the type and is not caught. Two exemptions: chat's reading surface (`Message`, `MailCard`, `DraftCard`, `ActivityTrace`, the composer) keeps its own type, and the column header, which `table.css` writes once on `.table thead th` because a `<th>` cannot take a class. `.meta` survives as a page-local name only where it means layout rather than supporting text (the chat message's author row, the bloodwork marker's stat row, the encounter card).
- **Headings**: every `h1`–`h4` starts at `--weight-semibold` with no margin (a weightless base, so any class or page rule wins; `.prose` content keeps the browser's heading rhythm). Three typography-only title steps: `.title-page` (`--text-lg`, semibold: `SettingsLayout`'s title and every health page title), `.title-section` (`--text-base`, semibold: `Card`, `Modal`, a bordered `Alert`, the admin cards), `.title-card` (`--text-sm`, medium: a record or card name, a weight under the section title above it). Put the class on the element; a page rule places the heading and never sets its weight. `typeRoles.test.ts` fails a component that sets `font-weight` on a bare heading without a `heading-weight:` reason comment inside the rule (the error page's lighter statement is the one). The app bar title is chrome and keeps its own `1rem`. A bare `h3` inside a `Card` is its sub-heading (sm, semibold, muted) at element weight, so a `.micro-label` or any other class on the heading wins.

**A page rule whose subject moves into a component silently stops applying.** Svelte prunes a selector whose subject it cannot see in the file, with no error — so migrating markup onto `Field`, `Button` or `Badge` quietly kills the page rules that were targeting it. ## Platform and the native shell

The web app also runs inside a native iOS shell (its own repo, `istota-mobile` — a Capacitor WKWebView pointed at the deployment URL, so the URL is the only build-time coupling). `src/lib/platform/` is the facade over everything that differs there. Two rules govern it, and both exist because the web deploys in minutes while the shell binary lags a TestFlight cycle:

1. **Every export degrades to plain-web behaviour off the shell** — a no-op, or the browser's own control. Nothing may require the shell to work.
2. **Every shell-dependent capability is gated on the shell version that introduced it**, via `shellAtLeast()`. An older app must get a working page that says what it cannot do, not a control that silently fails.

**Detection is the `IstotaApp/<version>` user-agent token, not `window.Capacitor`.** The UA is present on the first request, survives SSR, and carries a version the injected bridge does not — and a page can carry a `Capacitor` shim without being in the shell at all, so a plugin object's presence is not evidence of the shell. Route every call through one accessor that checks both the gate and the plugin, so the two cannot diverge: shipping six of eight tracker calls gated on the plugin alone is a defect this rule already caught.

Capabilities and their gates: soft-keyboard geometry (0.2.0), camera / photo library / document picker (0.3.0), upload-from-disk (`IstotaUploader`, presence-detected), the background location tracker (0.6.0) and the QR scanner (0.7.0) — the last two gated separately, so a 0.6.0 app tracks but says it cannot scan. Native push registration, permissions, app badges and notification opens use `nativePush.ts`, gated at 0.11.0. The root layout starts badge synchronization and pending-open consumption after live authentication; browser and older-shell settings retain preferences and device removal. The generic shell's connection plugin is `nativeConnection.ts`, gated at 0.12.0: the connection context and push registration receipt, the Preferences device card (titled by `deviceModel()` in `native.ts`, "iPhone" or "iPad", with a "Device settings" button, `openAppSettings`), and the native sign-out (`signOutOfApp`). A server route that redirects to another site, such as Nextcloud `/reconnect` and `/google/connect`, cannot be a full-page navigation there: the app refuses an off-site redirect the user did not tap and loses the page. `offSiteRoutesOpenInBrowser()` gates those buttons to a `target="_blank"` link, which the app opens in its browser view, with a note that the user may have to sign in to Istota there. `LogoutButton` hands sign-out to the app there instead of navigating to `/logout`, because the app has to stop tracking, remove the push enrollment and clear website data before another account can sign in; the app asks its own question, so the web dialog is skipped, and a cancel is not an error. The app also intercepts a navigation to `/logout` and turns it into the same question. Where a capability's _shape_ changed rather than its existence, feature-detect the response instead of adding a version (the pickers returning a path rather than base64).

**The height model.** `--app-height` and `--kb-height` are written by `lib/viewport.ts`; body height is `calc(var(--app-height, 100dvh) - var(--kb-height, 0px))`. Four invariants worth knowing before touching it:

- `--app-height` is published **only in standalone**. A browser tab keeps `dvh`, because there `innerHeight` is the layout viewport and does not track a collapsing toolbar — which is what `dvh` was adopted for. It exists at all because of an iOS 26 WebKit bug where, after a keyboard dismissal, the visual viewport stays short and `dvh` follows it down.
- The published height is the **tallest viewport seen**, and short readings are never published. A keyboard can only make a viewport smaller, so a smaller reading is never evidence of how tall the app should be; holding a slightly-too-tall height briefly beats a band nothing later corrects. The one path that adopts a smaller baseline is a shrink outlasting the whole settle window with nothing focused — a split view or a resized window, not a keyboard.
- The keyboard gate takes focus as the signal and overrules a focused field only when **both** viewports are back within tolerance. Requiring both is what makes it right on either platform: an installed app resizes the layout viewport, a browser tab only the visual one. Testing one turned an intermittent gap into a permanent one.
- `--kb-height` bypasses the settle machinery entirely — it comes from the shell's `keyboardWillShow`, at the start of the animation rather than after it, and that number does not lie. It has to come from the shell because viewport units deliberately ignore virtual keyboards.

`?vpdebug=1` turns on an on-device readout of the shell version and the live geometry (`?vpdebug=0` clears it). It is the only way to see this subsystem working on a real phone, and it prints the version precisely so "a gate with no height behind it" is visible without a rebuild.

## Client-local preferences

Theme and text scale are localStorage-persisted per browser, not profile fields — they must apply before first paint, and profile data arrives after it. Both follow one shape: a `writable` seeded from `loadSetting`, a normalizer folding any unrecognized value onto the default, an `apply*` setting an attribute on `<html>`, and a matching branch in the single blocking `<script>` in `app.html`. Add to that script; never add a second one. Controls for these live in the **Appearance** card on `/settings`, which sits outside the `{#if profile}` block and applies on change — keep client-local controls out of the profile cards, whose fields need the shared Save button.

The theme is stated in three places that must agree: the token in `app.css`, the `theme-color` meta seeded by that same pre-paint script in `app.html`, and `applyTheme` in `stores/theme.ts`, which keeps the meta current as the user switches. A test asserts all three, so changing the dark surface color in one place fails there rather than shipping a browser chrome that no longer matches the app.

Not everything client-local is a preference. `stores/drafts.ts` — unsent chat composer text, per room — sits beside these and goes through the same `persisted.ts`, but deliberately does **not** take the shape above: nothing is applied to `<html>`, there is no pre-paint branch and no `/settings` control, because a draft is state the user produced rather than a setting they chose. What it does share is the reason for being client-local: it has to be there the instant the composer mounts, before any request could answer, and half-written text is not something to publish to a server. It also needs collecting, which no preference does — a room that is deleted or never revisited would otherwise hold its draft forever — hence the TTL and entry cap it carries. It carries two size caps as well, one per draft and one for the whole map, for a different reason again: every draft shares a single storage entry, so one oversized paste used to blow the origin quota for the map and silently stop _every_ room's draft being saved. `writeDraft` returns the text it actually stored, and a caller keeping its own copy of what it wrote must keep that one — see `.claude/rules/web-chat.md`. `stores/sendQueue.ts` is its sibling and is shaped from it deliberately, down to the key and the caps: messages that cannot be sent yet and are waiting to be, either because a turn is running (ISSUE-238) or because there is no connection (ISSUE-202). What differs is what the text means — a draft is half a thought and a queued message is one the user has committed to sending — so its TTL is a week rather than a month, and its `writeQueue` return is deliberately _not_ adopted back into the live queue, since a storage bound trimming that would delete a message already on screen.

## Shipping a build

**The service worker registers in the native shell only** (`src/service-worker.ts`, ISSUE-202). Kit's automatic registration is off (`kit.serviceWorker.register: false`) and `routes/+layout.svelte` registers it behind `shellRunsServiceWorker()`: 0.10.0 and 0.11.0, the versions that declare the app-bound domains WebKit needs before it will run one. From 0.12.0 the app connects to a server chosen at runtime, has no app-bound domains and so no worker, and the layout does not register one. A worker is the one client artifact that can pin a client to a build the server has deleted and this app deploys continuously, so the phone gets it (it needs it to open with no connection at all) and the desktop keeps exactly what it had. It precaches the build, every prerendered document and an allowlist of icons under a `istota-${version}` cache, never touches `${base}/api/` or an `Accept: text/event-stream` request, and leaves `version.json` on the network so the update prompt below still fires. Settings → "Clear offline data" (shell-gated on `shellAtLeast('0.10.0')`) unregisters it and drops its caches; in 0.12.0 its text says the app itself is not stored. Everything else is HTTP headers plus SvelteKit's own version poll, and the server sends two classes: hashed `_app/immutable/` assets are immutable for a year, everything else — the HTML shell, `version.json`, the manifest, the icons — is `no-cache` and revalidates. Sending neither (the previous state) let an installed home-screen app pin the shell indefinitely and then ask for hashed chunks the server had already deleted.

A new build is surfaced, not forced: the root layout watches SvelteKit's `updated` state and shows a toast with a Reload button. It is a tap rather than an automatic reload because reloading discards a half-typed message. It also re-checks on `visibilitychange`, since the poll timer is throttled in a background tab and stopped outright in a suspended PWA — without that, a phone returning to the app after a day would be running whatever it had.

**Render bundles are a second build.** `src/render/<name>/main.ts` entries are built by `vite.render.config.ts` into self-contained `build-render/<name>.html` files the daemon sends to the browser service to turn into an image (the location share map for Talk and WhatsApp). They are not routes and the web never serves them. An entry calls `registerRenderer` from `src/render/host.ts` and mounts app components with `mount`; it makes no API call, since everything it draws arrives in the payload. The contract is in `.claude/rules/leaf-modules.md` under `browser/document_render.py`.

`static/` holds the manifest and the four icons. Manifest paths stay **relative** and head links go through `%sveltekit.assets%`, because the whole app is served under the `/istota` base and at varying route depths.

**Mock `$lib/api` through `src/lib/test/apiDouble.ts`, never with a hand-written factory.** A `vi.mock('$lib/api', () => ({ ... }))` factory replaces the whole module, so every export it does not list is `undefined` at runtime and correct-looking in the editor — which is how twenty-odd files came to omit `AuthError` and sit one `e instanceof AuthError` away from a crash (ISSUE-468). The double reads its export list off the real module instead: functions become `vi.fn()`, the error classes and constants pass through as themselves, so `instanceof` in the component matches what a test throws.

```ts
const api = vi.hoisted(() => ({}) as ApiDouble);
vi.mock('$lib/api', () => api);
await fillApiDouble(api, { getProfile: vi.fn(async () => ({ profile })) });
```

The second argument is how a file keeps control of its own mock — a default implementation, a canned return, or a spy for a name the module does not export. The other permitted shape is a factory built on the real module (`...(await importOriginal())`), which cannot omit an export either; `apiDouble.test.ts` fails on anything else.

`lint:design` compares against `scripts/design-lint-baseline.json`, which records permitted violations per file. **The baseline is not empty**, and what is in it is deliberate: 38 files, `off-scale-space` 79 (entirely the two off-ramp bands — sub-`--space-1` hairline nudges, and the sparse tail above `1rem`) and `raw-color` 11. `redefined-primitive` is at zero: a page places a shared class under its own container or under a placement class of its own, never at the top level. Those figures are here so drift is visible; they should go down, not up. It is a list of known exceptions, not a licence — fix the violation, or mark it with an allow comment and a reason. Adding a baseline entry is the last resort and needs one too.

The rules themselves are tested (`scripts/design-lint.test.ts`). A lint whose regex quietly stops matching reports a clean tree, which is exactly what happened while 87 color literals in `rgba()`/`hsla()` notation sat in the source — and while an `accept="image/*"` attribute opened a block comment that never closed, exempting four whole files from every rule.

`npm run lint:design -- --list [rule]` dumps every violation regardless of baseline — the triage view. `-- --update-baseline` regenerates.

A theme override that merely re-points at a token (`:global(:root[data-theme='light']) .card:hover { border-color: var(--border-default); }`) is still a violation, and usually a sign the value wants a token pair of its own. Several of those were also silently inert — restating in light exactly what the resting state already used, so the hover did nothing on white.
