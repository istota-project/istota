# doctor.py — runtime self-check

## doctor.py

Runtime self-check: every environmental fact istota depends on, named once. A whole class of bug here is invisible to the suite by construction — the tests assert against Python objects on a developer's macOS host, while production is a built image, a rendered `config.toml`, a `PATH` and a bubblewrap namespace, and the forge-CLI failures (ISSUE-263 and its neighbours) were all a disagreement between what the code assumed about its runtime and what the runtime was, none of them a Python defect. Each check answers one question about the host, returns a `CheckResult` and never raises. Six entry points: daemon start-up, a scheduler interval, `istota doctor [--only NAME]`, the admin dashboard's Health pane, `!check` and the `self-check` heartbeat — and it is also the **oracle the image and smoke tiers reuse** rather than hand-writing assertions that drift from the code. The last two were the counterexample to that claim until recently: `commands.cmd_check` and `heartbeat._check_self` each carried a near-verbatim copy of the other, the same five probes in the same order, drifting from this registry and from each other, and `tests/test_doctor.py::test_no_hand_rolled_health_probe` is what stops them growing back. Two constraints are easy to violate by accident. **No check on the config-load path may spawn a process**: `_validate_forge_clis` is called unconditionally from `load_config`, which runs in the daemon, the web app, the webhook receiver, every CLI invocation and every host-side skill CLI the proxy spawns *per call*, so `probe=False` is what keeps a free `os.path.exists` from becoming five `--version` spawns. And **a check is only an oracle for a test if the test names the environment that makes it run**, which is why the `developer.*` checks `SKIP` rather than pass when no token is configured. `security.skill_model_credential` is the check ISSUE-409 wanted and nothing had: it answers whether a skill CLI that calls a model of its own — `code_review`, the only one — can authenticate, in **two results because they fail independently**. The `.wiring` half is the drift guard and the one that catches a *re*-regression: `executor.SKILL_MODEL_CALLERS` is a list of skill *names* matched against the loaded index at task-build time, so renaming or removing a skill directory silently stops the injection with no import to break and nothing on a deployment to go red. The `.value` half asks only whether the daemon holds one of `SKILL_MODEL_CREDENTIAL_VARS`, reporting the **name and never the value**, since a `CheckResult` is rendered into the boot log and the admin dashboard; it `SKIP`s with the proxy off, where the CLI is re-exec'd with the daemon's own environment and there is no injection to assert about, and it `SKIP`s again where the environment it is reading is not the daemon's at all. That second one is the correction to the first version of this check: `istota doctor` is a command a *task* can run, a task env is the one ISSUE-390 deliberately strips the token out of, and the two API-key names reach a task env by no route at all — so on that shape all three names are absent whatever the daemon holds, and the check reported `FAIL` and exited 1 about a deployment whose reviews were working. `_non_daemon_env_markers` names the three markers istota's own env builders set (`ISTOTA_TASK_ID` from `build_task_runtime`, which survives into `proxy_base_env` too and is therefore the general one; `ISTOTA_SANDBOXED`; `PRECOMMIT_SCANS_REQUIRED` from `build_stripped_env`, which is what a cron `command` job runs with and whose credential-pattern filter removes all three names by construction), rather than testing the `ISTOTA_` namespace — the daemon's own environment carries `ISTOTA_CONFIG_PATH` and `ISTOTA_ADMINS_FILE`, so a namespace test would skip everywhere and the check could never fail. **Presence stays `OK` wherever it is read**, and that asymmetry is what keeps the skip narrow rather than a hole: `build_clean_env` copies the token out of the daemon's environment into every task's, so seeing it inside a task does answer the question, and only absence is the unanswerable direction. Spawns nothing, so it is safe under `probe=False`. `security.secret_key` is the same shape one layer down and answers for the secrets store's master key: `secrets_store` raises on every encrypt and decrypt without `ISTOTA_SECRET_KEY`, so a deployment missing it can store no credential and read none back, and **the symptom read as normal** — `_native_key_holders` calls `secret_key_available()` and reports *0 holders* rather than an error, so "credentials cannot work here" rendered as "nobody has configured a credential", which is why the standalone wizard shipping no key at all went unreported for seven weeks. The floor and the presence test are `secrets_store`'s own (`secret_key_available`, `_MIN_KEY_LEN`) rather than a second copy, since a second copy is the drift the check exists to catch; the value and every prefix of it stay out of `detail` and `remedy`; and the arms are ordered by the rule above, with a *too short* verdict counted as presence and only absence reaching the `_non_daemon_env_markers` skip — absence inside a task is guaranteed rather than informative, because `build_clean_env` strips the name by construction and `_PROXY_LOOKUP_BLOCKED` stops the proxy handing it back. **A fourth arm sits between the too-short one and the skip, and it is the one the marker list cannot reach**: on standalone the key lives in `istota.env`, `cmd_serve` is the only thing in the tree that sources it, and an operator's shell carries none of the three markers — so `istota doctor` read its own environment, found nothing, and reported `FAIL` and exit 1 about an install whose key was exactly where it belonged, with a remedy naming a line already in the file. An absent variable therefore falls back to the sibling env file the daemon does source (`config.config_path.parent / "istota.env"`, `cli._default_env_file`'s rule restated rather than imported, since `cli` imports `doctor`), and only a key missing from both is absence; the length is all that is ever read out of that file. The remedy is the other place it reads the config, naming that same derived path under `is_standalone` rather than the `~/.config` default — `istota setup -c` puts the env file beside whatever config it was given — and `/data/.secret_key` / `istota_secret_key` otherwise. **`config_visibility` is a gate in front of the whole registry, and the one thing here that is not a check** (ISSUE-412): `load_config` returns a bare `Config()` when no candidate resolves and says so nowhere, so every path-and-policy check then answers about defaults — a relative `data/istota.db`, the default temp dir, a whole `[security]` block the operator never wrote — while reading exactly like a run about the real deployment. Inside a task that is *unconditional*: `build_clean_env` exports `ISTOTA_CONFIG_PATH` naming a file under `config/`, and `config/` is bound into no sandbox by design, so the exported path never resolves in there. Keyed on `config.config_path` rather than on the environment, the way `executor` and `scheduler` already ask the same question — the environment says what was *asked for*, and a deployment can resolve a config with neither variable set. **It splits on the same principle `_deployment_sandboxing` did and deliberately not on the same predicate**, which is the trap: a boundary doing its job is not a fault, so a *task* gets a `SKIP` rather than the ISSUE-381 shape 492a91e9 removed — but the question here is "is this process the daemon", not "would a bwrap probe from here be nested", and `ISTOTA_SANDBOXED` answers only the second. `task_env` sets that marker under `skill_proxy_enabled and effective_sandboxing` while `executor` exports `ISTOTA_CONFIG_PATH` on `config_path is not None` alone, so on a `sandbox_enabled` deployment with the proxy off — warned about since ISSUE-393, and shipped — the marker is absent while `config/` is just as unreachable, and keying on it would `FAIL` a task with a remedy it cannot follow. `_is_task_process` reads `ISTOTA_TASK_ID` or `ISTOTA_SANDBOXED` and **not** `_non_daemon_env_markers`, which is wider by one: `PRECOMMIT_SCANS_REQUIRED` marks a cron `command` job and a heartbeat shell command, both of which run unsandboxed as the daemon user with the config directory in front of them. A task on an *unconfined* deployment reaches none of this, since its exported path resolves — so the wider predicate costs only that a genuinely broken install seen from inside a task reads as a `SKIP`, the trade 492a91e9 accepted for the same reason: every authoritative surface runs in the daemon. **Everything else is a `FAIL`, including "nothing named and nothing found"**, because that invocation used to run 31 checks against defaults and exit 1 on the several that fail, and `verdict`'s own docstring already draws the line for the empty list — a run that checked nothing must not read as a run that passed everything. Only the task arm exits 0. **`cmd_doctor` renders it instead of the registry rather than beside it**, which is the decision the issue wanted: pushing three-state discipline into every config-reading check would touch most of the 31 and would still leave a reader taking `OK runtime.framework_db` as a statement about the deployment, since one honest line among 31 fictional ones does not stop that. **`--scope image` is exempt and `--only` is not**: `IMAGE` is defined a few lines below the status constants as what "can be answered by a bare `docker run` with no volumes", which is precisely a host with no config on any search path, so swallowing that scope would make a loaded config a precondition for the one scope declared not to need one — and it is the image tier's whole oracle. `--only` selects by name across both scopes and carries no such declaration. The gate is on the **CLI** path only. `!check`, the `self-check` heartbeat, the boot run, the interval sweep and the admin pane are in-process daemon and web callers, none of them reachable from a task, so the sandbox case cannot arise there; on the separate shape of a *daemon* started with no config file anywhere they still report the same 31 fictional results, which is left alone deliberately — the fix for that shape is the daemon refusing to boot, not a diagnostic apologising for it. The task arm's whole point is in `detail` rather than `remedy`, because `render_text` prints a remedy only for `WARN` and `FAIL`; the named path goes through `_named_path`, which collapses and caps with a visible cut since both sources are writable by anyone who can set an environment and an operator told a path did not resolve must not be shown a different path from the one that was tried; and the arm is chosen from `source` rather than from the rendered value, since a whitespace path collapses to empty and would otherwise report the wrong cause.

`security.vault_isolation` reports the multi-user vault gate: effective sandboxing passes, an unsandboxed deployment with a vault fails without the operator opt-in, and an opted-in deployment still warns about same-uid exposure. It uses `_deployment_sandboxing` so `probe=False` never spawns. It is outside the config-load checks.

`security.room_scope_confinement` is the same question asked for shared rooms (multiplayer Stage 28). Since ISSUE-576 only a guest's turn and a task nobody asked in a shared room withhold anything; `room_scopes` withholds at six seams, and the sandbox mounts are the only one that keeps a file away from a shell command, so on a deployment with no effective sandbox (the shipped Docker stack, macOS, the standalone install) it WARNs that a guest's turn loses the host's data in the prompt, the skills and the environment but not on the filesystem. A WARN rather than a FAIL: nothing is misconfigured, the deployment shape simply cannot confine it. No SKIP arm any more, since the policy it skipped on is gone. OK where the sandbox is in force, and an unestablished answer is a WARN naming why, through `_deployment_sandboxing` like its neighbour.

`security.credential_vault` and `security.vault_contents` are one feature under two registry names, and the split is a cost decision rather than a shape one. The first answers the four cheap questions about every user who has a vault — is `pykeepass` installed, will a cycle run at all, does each path resolve to a plain file of a sane size, is a passphrase provisioned — and runs wherever doctor runs. **Which users those are changed with the enable**: it iterates the users holding a `vault/passphrase` row, plus any user with a TOML `vault_path`, which is the pair §7 makes the switch — a file in the folder with no passphrase can be read by nothing, and a path with no passphrase is still a misconfiguration worth naming. The schedule arm lost its owned-services line with the service mapping, so it answers one question now rather than two, and the path arm reaches the folder resolver for a user with no configured path — `resolve_user_vault_path(candidate=…)` where a TOML line wrote one, `storage.vault_location_for` where it did not, which is one database read saved per TOML user rather than a style. `VAULT_DIR_EMPTY` then reads as "configured and no file yet" and `VAULT_DIR_UNCHOSEN` as "several files, none chosen", both WARN with the folder named and neither a FAIL, since both are the user's to fix in one step and neither is broken. The second opens each file and reports **counts, never names** — the entry count in place of the owned-service count — since a `CheckResult` is rendered into the boot log *and* the admin Health pane where one user's credential labels are read by every admin. That is the opposite of the rule the *settings card* follows, which lists the names, and the difference is the audience rather than the sensitivity: a card is one user's own page. Half of it is structural rather than a rule kept at the call site, because `VaultStatusReport` carries no values at all — but it does carry `names`, which are written into the **file** by somebody a task in that user's sandbox can be, so the check reads the length and never the list. **§10 says the parse arm is "behind `probe` rather than running on the boot sweep" and that is false in this tree** — `run_checks` defaults `probe=True` and the scheduler's startup run, its hourly sweep and the `self-check` heartbeat all took the default, so it was paying a workspace read, a Fernet decrypt that *writes* `last_accessed_at` on that user's passphrase row, and an Argon2id derivation, per configured vault, on all three. §10's *conclusion* survives (the sync performs the same three in the same process whenever the file changes, so nothing widens the trust domain) and the cost does not, which is why the parse is its own entry: `heartbeat._SELF_CHECK_SKIPPED` and `scheduler.SWEEP_SKIPPED_CHECKS` both exclude by registry **name**, so a fifth arm could not be reached by either without taking the four cheap ones with it. The name is a **sibling rather than a dotted child** for the same mechanism — both selectors match by prefix, so `security.credential_vault.contents` would be pulled in by every caller naming the parent and re-included by any list that skipped it. `pykeepass` is tested with `importlib.util.find_spec` and never an import, because an import on the boot sweep pulls `lxml`, `argon2-cffi` and `pycryptodomex` into the daemon whether or not any user has a vault; the two are indistinguishable on a host that has the library, so the pin patches `find_spec` to answer `None` while the real one sits in the venv. Two more decisions worth having written down. The `db_path.parent` warning is discriminated by **`location.dir_fd is None`** — the absolute form — and not by containment alone: on the standalone shape `setup_wizard` puts `db_path`, the workspace and the temp dir under one directory, so an unconditional test warns about every ordinary *relative* vault there, and `_vault_db_dir` answers `None` for anything but an absolute `db_path` because `Config.db_path` defaults to the relative `data/istota.db` and `Path("").parent` realpaths to the process cwd — wrong in the noisy direction when unset and in the permissive one when relative. And the path arm emits **one finding per user rather than returning on its first non-empty list**: the earlier shape let one refused path drop every other user's finding, the misaimed-at-the-database warning included, and reported a user whose *file* was merely missing under a FAIL whose remedy told them to edit a config line that was correct — invisible to a single-user fixture, which is what every test here was.

`web.auth` is deployment-scoped and returns seven dotted results: `methods`, `site_hostname`, `mail`, `identities`, `admins`, `proxy_ip`, and `session_secret`. Methods reports the effective list and config/default versus environment source, using the registry's `ok` informational status. The other six skip when email is disabled. Email requires a hostname and a resolved session secret; the check reuses `webui.session_secret.resolve`. Database read failures report FAIL rather than pretending identities are absent. Identity counts come from live DB profiles, and passwordless identities remain eligible when mail is enabled. Multiple identities plus an empty admin allowlist fail because task authorization would treat every user as admin. A public hostname with zero trusted proxy hops warns that proxied requests have no IP verification budget. No network, subprocess or test mail is involved; mail-enabled means configured, not proven deliverable.

`users.email_address_uniqueness` names every email address more than one user holds, with its holders, read through `user_profiles.duplicate_email_addresses` so it and the writers' refusal (`find_identity_conflicts`) are one rule. It exists because the writers refuse only a *new* duplicate: a stored one passes a resubmit, and nothing else would ever say it is there. The addresses and user ids are in the detail on purpose, against the counts-not-names rule the vault check follows: the audience is an operator, a count would not say what to fix, and the cross-user exposure is already handled by `!check` and the `self-check` heartbeat giving a non-admin the verdict line only. Opens the database through `connect_read_only`, skips when there is none, WARNs rather than FAILs since nothing is misconfigured, and caps the listing at ten.

`config.operator_persona` says which persona is in force and whether the sync left something for a person (#629, `.claude/rules/prompts.md`). SKIP with no file root (the shipped persona is in force); WARN when the root is not a directory, when `{root}/PERSONA.md` is refused (a link, a pipe, over `PERSONA_MAX_BYTES`, not UTF-8, so the last good copy or the shipped one is quietly in force), when `PERSONA.md.shipped` is waiting to be merged, and when configured users still hold a `{bot_dir}/config/PERSONA.md` that `istota init` has not retired. OK otherwise, saying whether the operator file is empty, follows the shipped persona, is an older shipped version the next sync upgrades, or is edited and kept. **Counts, never user ids or contents**, on the vault check's reasoning, since the detail reaches the boot log and the admin Health pane; the retired-copy count rides in the detail. **Never FAIL**: a per-user folder is writable from its owner's sandbox, so anything counted there is a state a task can produce on demand, and nothing here stops a task. Reads only, through the hardened leaf read and the retirement's own walk (`persona_retire.census_user_personas`), so the two cannot disagree about what a remaining copy is; spawns nothing, so it is safe under `probe=False`.
