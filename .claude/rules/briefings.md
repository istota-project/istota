# Briefings module (`src/istota/briefings/`)

Group research uses `group_runs.create_research_task` to admit an ordinary background task for the current run claim. Only the research prompt enters it. The reserved `__briefings__` identity has no installation account, personal resources, ambient memory or group mounts. `rooms.scopes` withholds every skill except browse, skill discovery and untrusted-input instructions; the existing executor, runtime, SkillProxy, timeout and cancellation paths apply. Deferred writes are discarded. `capture_research_result` accepts completed output only from the matching task and live run claim, then stores it with its task attempt. Scheduler admission and final synthesis are separate callers of these seams.

Group generation uses the existing Briefings scheduler gate and ordinary background task workers. `check_group_briefings` admits recent cron occurrences in the definition’s timezone; `group_runs.advance_runs` renews claims, captures completed research and queues final synthesis. Task retries reuse saved research, and publication is checked against the live definition, grants and lease. `assemble_group_input` reuses source rendering and structured assembly; all synthesis blocks share one tool-less call through `_run_section_brain`, while structured-only editions make no model call. Final task results contain bounded status codes; edition content stays in the run store. Preview uses the same worker and publication checks without recipient rows. Owner succession does not change scheduling or the generator identity.

Group external delivery uses ordinary background tasks queued by `group_delivery.queue_deliveries`. The group store owns recipient claims, immutable message parts and member mutes. Each part rechecks membership intervals, account/module availability, the enabled definition and source grants; Talk also reuses the shared-room refusal gate. Email uses the existing HTML/plain renderer and SMTP sender, Talk uses its existing split/post/readback path, and ntfy uses its existing sender with deterministic UTF-8-bounded parts. No delivery retry calls a Brain. Current group owners alone retry failed rows; uncertain acceptance requires explicit duplicate acknowledgement and preserves the original destination. A persisted email Message-ID identifies an attempt but does not provide SMTP idempotency. An expired send claim becomes uncertain, and confirmed parts are never resent. Disabling a definition cancels old pending sends even if it is later enabled. An already-started network send may finish after revocation; its acknowledgement is recorded. In-app rows are completed in the same transaction that writes their notification; a failed notification write leaves the row pending.

Group APIs live in `group_routes.py`, mounted by the existing host app with the shared session, origin and bounded-body guards. Only current group owners manage definitions, generation and retries; All users uses the existing admin exception. Creator ids grant no authority. Members read published editions and change their own delivery mutes even with their personal Briefings module disabled. Definition responses hide generation instructions from members and expose source approval only to its contributor or current authors. Run responses omit research, grant snapshots and dispatch details. Preview reads revalidate revision and grants; published history remains readable after source revocation. Downloads use the same gate. `notifications/resolvers/group_briefing.py` stores neutral edition and source-request notices, rechecks live membership and closes notices on departure or approval. The scheduler cleanup uses the configured archive retention to prune terminal group runs and their delivery parts together; pending, sending and uncertain recipients hold their run.

Group browse sources and research tasks use the existing browser profile pool under the reserved Briefings identity. The browser's health capability must confirm task isolation before reads. Host-side headers bind retained sessions to a task; research permits the existing read and close operations and refuses credential actions. Anonymous cookies follow the ordinary profile lifecycle. Browser networking and URL checks are unchanged, and nonempty `allowed_domains` settings are refused because Briefings does not enforce a domain allowlist. Personal browsing retains its user profile.

First-class **block/source content module** (`src/istota/briefings/`, spec `Specs/Done/briefings-first-class-module.md`, Stages 1–6 shipped; 7–8 deferred). **Blocks are the sole content model** — the legacy component generator, boolean-defaults expansion (`BriefingDefaultsConfig`/`[briefing_defaults]`), TOML `components =`/`--components-json` authoring, and the executor's legacy fallback were all retired (retire-legacy-briefing-components spec). A briefing is an ordered list of **blocks** — each with a title, an optional synthesis directive, a render mode (`synthesis`/`structured`), and 1..N **sources** — gathered and synthesized into one section per block at generation time. Source kinds (`sources/*`): `rss` (a Feeds subscription/category, soft-degrades when Feeds is off), `email` (shared-pool newsletters, windowed, owner-filtered, fail-closed without the framework DB), `my_email` (the user's own mail from one account per source, `bot`, `google` or `imap:<id>` for one of the user's connected mail accounts; personal only, so it is in neither `GROUP_SOURCE_KINDS` nor `ALLOWED_SHARED_SOURCE_KINDS`, and `sources/group.py` refuses it as an unknown kind; the bot account reuses the email skill's `_mine_criteria` and `_scope_filter` so the ownership rule has one copy, Gmail needs a `gmail` grant and reads through `google_tokens.access_token_for`; `imap:<id>` decrypts the account's IMAP password daemon-side through `mail.accounts.resolve_for_daemon` and reads `default_folder` read-only (`EXAMINE`) with no ownership filter, and an id that no longer resolves (deleted, disabled, another user's, `[mail_accounts]` off) renders the empty "(mail account unavailable)" source rather than failing, with the config left as it is; save validation accepts `bot`, `google` and `imap:<digits>` and checks the id is one of the saving user's accounts; all untrusted, at most `MAX_MESSAGES`; `GET /briefings/email-accounts` lists what the user can pick, an account as unavailable when `[mail_accounts]` is off or its IMAP password is missing), `browse` (a bundled preset or arbitrary URL frontpage via the browser skill), `markets`, `calendar`, `todos`, `reminders`, `notes`, and `shared_block` (below). The `todos`/`reminders`/`notes` sources read a file whose `path` (a source `config` property; no default — blank reads nothing) resolves **relative to the user's own `/Users/<uid>/` folder** (`sources.builtins._resolve_user_path`), so `shared/…` reaches a bot-shared file and `istota/…` the bot workspace; a path already rooted at the user's own folder passes through, `..` segments are stripped, and a path naming another user resolves under the caller's own folder (never a cross-user read). The web editor offers a **server-side-filtered** file autocomplete (`GET /briefings/path-suggest?q=` — the query walks the workspace so a deep/late file still surfaces as the user types, not a fixed on-load pool) via the reusable `ui/AutocompleteInput` component, and shows an **advisory** existence hint (`GET /briefings/path-check`, debounced): it never blocks the save, since the resolver is fail-soft (a missing file contributes a provenance note), so a not-yet-created or transiently-unreachable path can't trap the editor. Gathering is **concurrent** (bounded thread pool, each worker on its own framework connection — SQLite conns aren't thread-safe) and **fail-soft** — a down/unknown source contributes a provenance note, never raises, never kills the briefing (`resolve_source` backstop); per-block output order is deterministic (reassembled by slot, not completion). Blocks/sources/archive live in a per-user SQLite module DB on **local disk** (`Config.module_db_path(user, "briefings")`, WAL); user-facing workspace stays on the mount. Gated by `Config.is_module_enabled(user, "briefings")` (`briefings` in `MODULE_NAMES`); own web tab (reader landing page + archive) and a block/source **+ schedule/delivery** settings editor. Each archived result in the reader sidebar carries a kebab → **Delete** (shared `ConfirmDialog`) that hits `DELETE /api/briefings/archive/{id}` → `db.delete_archived` (single-row, 404 on a missing id) — a user-driven prune alongside the age-based `archive_retention_days` sweep; the sidebar removes the row optimistically and re-points the reader to a neighbour. Content is managed via `istota briefings blocks|sources|archive …` (operator, `cli_briefings.py`), the `briefings` skill facade (`BRIEFINGS_USER`, `untrusted_input` companion, error-envelope exit contract), or the web settings page; **scheduling + delivery stay framework-owned** (cron in user TZ, real `briefing_configs.output` column, `enabled=0` mutes; provision via `istota briefings schedule ensure` or the web UI). **The workspace `BRIEFINGS.md` is retired as an input** — `skills/briefing._load_workspace_briefings` is deleted and `get_briefings_for_user` now returns `UserConfig.briefings` unmodified, which `_apply_user_briefings` builds from `briefing_configs` rows alone. It had to go because it was applied *over* that overlay, so a cron the settings page had just written was overridden by a months-old file while the page kept showing the value the user picked — a divergence with no log line and no surface that reported it. `user_briefings.import_from_workspace_files` carries each user's file into `briefing_configs` once, sentinel-guarded per user in `_migration_state` (`briefings_md_import_v1:{user_id}`), from the scheduler's Phase 7b boot block **after** `import_from_user_configs`. Three decisions there are the non-obvious ones. The file's value **overwrites** an existing row rather than skipping it, on `cron_expression` / `conversation_token` / `output` and nothing else: the bar for a retirement is that nothing observable changes at the switch, and the file was the live authority for those three, so skipping would silently start honouring a web-UI edit the file had been suppressing. `enabled` and `title` are deliberately left with the row, and both **are** changes at the switch rather than exceptions to the rule — in each case the old override was suppressing a web-UI setting rather than expressing one. `_apply_user_briefings` drops an `enabled=0` row from `UserConfig.briefings` and the old file merge added the briefing straight back by name, so a briefing switched off in the UI kept running; importing `enabled = 1` would carry that bug forward as a stored fact instead of ending it. `title` is the same shape: the file's entry replaced the row wholesale with a blank title, so a title typed into the UI was ignored at render. An existing row's `components` are likewise untouched, which is narrower than "components are not imported" — `_apply_user_briefings` reattaches them, so a briefing whose module DB has not yet been initialised can still seed blocks from them. **The sentinel is only burned on positive evidence that the workspace is readable** (`_workspace_is_live`: `os.path.ismount` where `storage_is_nextcloud`, gated exactly as `doctor.check_mount_liveness` gates it since the local install mounts nothing, plus the user's `config/` directory existing). A dropped rclone mount leaves a plain empty directory, so every path under it is ENOENT and `Path.exists()` answers False rather than raising — reading that as "this user had no file" marks them done for ever, and `ensure_user_directories_v2` runs earlier in the same boot and will recreate the workspace on the underlying disk, so the directory alone is not evidence. **Every file is read before the connection is opened**, in three phases (outstanding users → read the mount → write): the obvious one-connection loop takes a write lock at the first user and holds it across every remaining user's stat and read against the FUSE mount, on the foreground boot path — which is the same hazard that moved the startup doctor onto a thread. Each user's write is wrapped in a `SAVEPOINT`, so a partial failure leaves no rows disagreeing with the sentinel it never set. Entry values are type-checked rather than `str()`-coerced (a TOML array otherwise writes its Python repr into the `name` column), an output that resolves to no destination is stored as `talk` rather than as a row `ensure_briefing` would refuse, and the file is read `encoding="utf-8", errors="replace"` because `UnicodeDecodeError` is a `ValueError` and would miss the `OSError` retry, failing every boot for ever. The sentinel is **per user**, not per deployment, because a user whose mount was unreadable on the boot that ran the migration would otherwise never be looked at again and their schedule lives only in that file — and for the same reason an unparseable file leaves the sentinel unset rather than burning it. `components` is **not** carried over: the read path has discarded it since blocks became the content model, so importing it would feed `_migrate._migrate_components` and hand the user content they have not had for releases. `storage.ensure_user_directories_v2` seeds no `BRIEFINGS.md` (an existing one is left on disk — it is the user's file), and `BRIEFINGS_TEMPLATE`, `_build_briefings_seed` and `BRIEFINGS_EXAMPLE` are all gone. That last one was a tombstone in `examples/` pointing at the settings page, and it is now **swept** rather than merely unshipped: `examples/` is bot-managed and rewritten wholesale on every call, so dropping a name from the seed dict only stops the overwrite and leaves the file on every workspace that ever received one, with nothing keeping it current. `RETIRED_EXAMPLES` names it and `storage.remove_regular_file` removes it on the next refresh. **That helper's probe is doing a different job from `write_regular_file`'s**: what `O_NOFOLLOW` + `S_ISREG` buys is that a directory, a device or a link the model planted at the name is refused and reported rather than tidied away. **`unlink` not following a symlink is a claim about the leaf and only the leaf**, and the first draft of this entry overstated it into "the removal could never reach a victim outside the directory". It can. `unlink` resolves every component above the last, so containment there is `_contained_under_user_root`, a realpath comparison rather than an inode-pinned descriptor — the ISSUE-341 window `skills/_loader.open_overlay_dir` exists to close. It is open here and it is wide: the check runs before the five `write_regular_file` calls above the sweep, so a `mv examples examples.real; ln -s /elsewhere examples; mv examples.real examples` inside that window lands the unlink on a regular file named `BRIEFINGS.md` outside the user's tree. The probe does not narrow it either, since the fd is closed before the unlink re-resolves the path by name. **Accepted rather than absent**, on two grounds: it is strictly smaller than the window `write_regular_file` already carries through the same check, where the same swap is an arbitrary *clobber*; and it is bounded by the single hard-coded leaf in `RETIRED_EXAMPLES`, which the sweep now refuses unless it is a bare name so a future entry cannot escape on the join. A second name, or a name from anywhere but a code constant, is the point at which to spend `open_overlay_dir` plus `os.unlink(name, dir_fd=fd)`.

**`[users.X.briefings]` in config.toml is retired too** (admin-briefings spec, Stage 1). `_parse_user_data` reports it `retired` and parses it into `UserConfig.legacy_briefing_seeds`, never into `briefings`. `import_from_user_configs` copies it into the table once per user under `user_config_briefings_import_v1:{user_id}`, set in the same savepoint even for a user with no entries, so neither a deleted row nor an entry added later is ever imported. A name with a row is skipped; an entry with no cron is imported `enabled = 0`. Right after the import, `run_daemon` calls `briefings.seed_retired_config_blocks`, which seeds every seed's `blocks` into the user's module DB through the same per-briefing `migrated_from_components:<name>` sentinel as `ensure_initialised`, for each seed whose row still exists, disabled or held included. Before that the blocks reached the module DB only on first touch, off the in-memory overlay, so an operator who removed the retired TOML block first, as the retired-key problem tells them to, lost them, and a disabled row's were never seeded. `group_migrate` reads the seeds directly where it used to read TOML through `briefings` (the explicit-override lookup in `preserve_legacy_defaults`, and `_current`, which refuses `legacy_personal_initialization_required` only while the user's import is pending). The plan's schedule `briefing_seed_conflict` refusal and its snapshot twin are gone; `_check_content_seeds` stays, because it also guards a pending components migration from a stored row, and `briefing_initialization_required` also counts a seed the pending import has yet to write.

**The two leaf guards overlap deliberately, and the controls are not the obvious ones** — each was measured, and the obvious reading was wrong twice. `test_a_directory_at_the_name_is_refused` needs *both* mutations: dropping `S_ISREG` leaves `unlink`'s own refusal of a directory, and an `rmtree` fallback is unreachable past the probe. `S_ISREG` has no control from the symlink test either, since `O_NOFOLLOW` refuses that at the open — so `test_a_fifo_at_the_name_is_refused` is the one shape where the check is the only thing standing there, and it is the only test that goes red on dropping that block alone. `test_no_sweep_where_the_directory_failed_containment` pins the sweep's *position*: hoisting it out of the containment `else` deletes a victim outside the tree, while rewriting its join to the unresolved path changes nothing, because the guard is the branch. The user's own `config/BRIEFINGS.md` stays untouched — the sweep is for files we wrote, and the distinction between the two is the whole reason the retirement deleted nothing at the time. `skills/briefings_config/skill.md` was the sharpest edge and is rewritten: it is prompt text, and it documented the discarded `[briefings.components]` shape in full with no mention of the DB or the web UI, so the model would write the file, confirm, and change nothing. **Deterministic titles**: a briefing's title is composed by `briefings.generate.resolve_briefing_title` from its configured `briefing_configs.title` (blank → `default_briefing_title` humanizes the _name_, so `morning` → "Morning Briefing") plus the run date in the user's timezone, appended by the renderer ("Morning Briefing — Monday, 27 July"). `scheduler.briefing_title_for_task` dates it from the task's `created_at` (the cron fire). The executor resolves it once into the generation manifest; archive, email and ntfy use that saved title, so live definition edits cannot change a generated edition. The model returns `{"version": 2, "blocks": [{"block_id": 42, "body_md": "…"}]}`. Before completion, `scheduler._normalize_briefing_result` joins bodies to the protected manifest with `briefings.document.normalize_briefing_document`, rejects malformed output through the quiet retry path, and stores `{"body": …, "briefing_document": …}` in `tasks.result`. The body is `document_to_markdown`'s linear projection, used for digest, search and text delivery. Every requested ID must appear exactly once; explicit empty bodies omit cards, and no remaining cards fails with `briefing_no_content`. The version-1 `briefing_meta.json` in the task control directory holds the required manifest (also version 1) and numeric-ID provenance; write or validation failure stops preparation before the model. Archive reads provenance and removes that file after completion; delivery keeps the document/title in memory. A snapshot archives even after its live blocks are deleted. Old body-only tasks retain best-effort provenance and linear delivery without invented boundaries. Previously the archive stored the model's free-styled `subject` (emoji, dates, a summary clause — different every run) while email discarded it and re-derived "Morning Briefing"/"Evening Briefing" by regex-scraping the _prompt_, keyed on the clock (`resolved.hour < 12`) rather than the briefing's name — so an "evening" briefing firing at 11am mailed as "Morning Briefing" and the two surfaces disagreed about the same run. That regex survives as `transport/email/outbound._legacy_briefing_subject`, reached only when no caller title is supplied. Editable via `istota briefings schedule ensure --title`, a settings plan's `title`, and the briefings-settings **Schedule** card, whose rows gained an edit affordance (the POST was already an idempotent upsert keyed on `name`, so an edit is a save with the name held fixed — the table had been add/delete only). At generation the executor's deferred-prompt path (`build_deferred_briefing_prompt` → `_build_module_briefing_prompt`) is the only path — `ensure_initialised` runs the one-time components→blocks migration first, then `assemble_briefing_input`; a briefing with no blocks after migration returns `None` → the task fails with the existing quiet retry (no legacy render). Generation runs on the ISSUE-143 **deferred-prompt worker** (source fetch never touches the dispatch thread); on completion the scheduler archives the delivered briefing and prunes by `[briefings] archive_retention_days` (default 90). Legacy component-based briefings migrate once into blocks/sources **per briefing** (`_migrate.py`, sentinel `migrated_from_components:<name>` — `blocks_from_components` is kept **only** as this one-time migration; `_migrate._migrate_components` prefers a briefing's config `blocks` over the components translation). **Config-authored rich blocks** (config-authored-rich-briefing-blocks spec): an operator authored the full block/source shape in `[[users.X.briefings.blocks]]` + `[[...blocks.sources]]` TOML (now a retired input, read only from `legacy_briefing_seeds`) (per-block `title`/`directive`/`render_mode`/`options` + 1..N sources of any `kind` with arbitrary `config`), seeded once via the per-briefing sentinel, then the briefing is an ordinary editable per-user briefing (operator re-runs never re-clobber). `blocks` is an **in-memory-only `Config` field** (never stored in `briefing_configs`): parsed by `_parse_briefing_specs`, threaded through `_apply_user_briefings` (attached from `legacy_briefing_seeds` to the row of the same name) + `get_briefings_for_user`. **Former default briefings**: `[[default_briefings]]` and per-user `default_briefings` are migration-only inputs. `group_migrate.preserve_legacy_defaults` captures the upgrade registry once, materializes missing effective schedules/content with per-user checkpoints, and preserves DB edits. New users receive no copied defaults. Disabled All users imports, reviewed cutover/rollback and opt-outs use `group_briefing_migrations`; see the group section below. The `briefing` skill (singular) is the output-formatting guideline selected on `source_types:[briefing]` and returns version-2 block-body JSON; the `briefings` skill (plural) is the content-management CLI facade. **Shared curated content** (shared-kv-curated-briefing-content spec): a cross-user **`shared_kv`** table (namespaced JSON, open reads / admin-only writes via the fail-closed `Config.is_shared_kv_writer` — _not_ `is_admin`'s empty-means-all) is the substrate for content that's identical across users. One consuming source kind: `shared_block` (`{name, max_age_hours}` → namespace `briefing_shared_blocks`, key `name`; trust taken from the stored value, not the consumer). The writer picks granularity by value shape — `{"items":[…]}` (share the fetch → per-user synthesis) vs `{"text":…}` (share the synthesis → verbatim splice into a `structured` block); freshness-gated (stale/missing → omitted, fail-soft) and untrusted-wrapped unless `trusted:true`. Writes reach `shared_kv` three ways, all converging on the gate: sandboxed skill (`istota-skill kv set --shared`, deferred `scope:"shared"` op gated on `task.user_id` at apply time in `_process_deferred_kv_ops`), direct skill/CLI (`istota kv set --shared`), all admin-only; set-ops reject `--shared`. **Module-owned shared blocks** (batteries-included): top-level `[[briefing_shared_blocks]]` config (`BriefingSharedBlock`; canonical `world-headlines`/`markets-summary` seeded via `DEFAULT_SHARED_BLOCKS` when unset) are one-block briefings generated **once globally** under the reserved `__system__` identity — `scheduler.check_shared_blocks` (cron in the operator-configured shared-block timezone `[briefings] shared_block_timezone`, default UTC; `cron_max_staleness_minutes`-gated, off-dispatch worker thread) runs `briefings.shared_blocks.run_shared_block` (user-agnostic gather over `browse`/`markets`/`email` only — `rss` + personal built-ins dropped; section-only synthesis via the general-alias Brain) and does a **trusted daemon** `db.shared_kv_set(..., written_by="__system__")` (no `is_shared_kv_writer` gate — the module writing its own content isn't a user task), stamping `briefing_shared_block_state.last_run_at`; an all-empty gather skips the write (last-known-good). Existing briefings can read `world-headlines` through a `shared_block` source; new group editions can generate directly. Escape hatch for arbitrary content: an admin CRON `command:` job writing `shared_kv` directly (`scripts/examples/shared_kv_curation.sh`). **Admin-editable shared blocks** (admin-shared-briefing-blocks spec): shared-block definitions are DB-backed and admin-manageable, not config-only. A `shared_block_configs` framework table (CRUD in `db.py`, `SharedBlockConfigRow`) is seeded once from `DEFAULT_SHARED_BLOCKS`/`[[briefing_shared_blocks]]` (`shared_blocks_store.import_from_config`) and DB-wins thereafter (`config._apply_shared_blocks` overlay — same seed-once + edit-preservation contract as `default_briefings`), so `check_shared_blocks` reads DB-authoritative definitions. Managed via admin-gated web routes on the briefings router (`GET/PUT/DELETE /shared-blocks` + `POST /shared-blocks/{name}/run` behind `require_admin` = `Config.is_shared_kv_writer`, fail-closed; validates cron/`render_mode`/slug + source kind ∈ `ALLOWED_SHARED_SOURCE_KINDS` in `briefings.models`). Run now never generates in the web process: it leaves a request in the reserved `_shared_block_run` `shared_kv` namespace (`briefings/shared_block_runs.py`) for the daemon's `shared-block-request` gate, since on the Docker stack the web container is off the browser's network and its brain breaker is not the daemon's (ISSUE-700). A request stays pending until the daemon records its answer, so a restart mid-run answers it on the next tick, and the page polls the listing until `status.run_answered` names its request. The answer is kept after the request is removed, so each block's Last run cell also shows its last Run now outcome and time, or that one is pending. A run that finishes after the admin has left the page shows on that line, not in a late notice, and a page that loads with a request pending follows it to its answer. `briefing_shared_block_state.last_run_at` stays the cron's clock and Run now does not stamp it, since it is the base `check_shared_blocks` computes the next fire from. That stamp is naive wall-clock time in the shared-block timezone, so `_shared_block_status` returns it as UTC, the clock `run_answered.at` is on. Deleting a block drops its request and answer (`shared_block_runs.forget`), so a block made again under the name starts with neither. The `istota briefings shared list|ensure|remove|run` CLI is the other door, and its `run` generates in the process it is called from. The briefings-settings web page renders an admin-only "Shared blocks" card (reusing the extracted `SourceConfigFields.svelte`, shared with the per-user editor) and any user gets a **Shared block** per-user source kind picking from `GET /shared-block-options`. **Verbatim structured generation**: `render_mode="structured"` now **skips the synthesis brain entirely** (`run_shared_block` → `_assemble_verbatim`, concatenating gathered source text in slot order) — self-formatting data (the markets quote table) is stored verbatim with zero LLM passes; `markets-summary` flipped to structured + `trusted`. The stored value carries a `trusted` flag; the read side (`sources/kv.py`) honors the **stored value's** `trusted` for the `briefing_shared_blocks` namespace (a consuming user can never flip it) and a live `shared_kv` key with no definition row is a valid custom-published block, not "unknown". **`publish_shared_kv` job attribute**: a scheduled job can publish its result text into `shared_kv` on success (`scheduled_jobs.publish_shared_kv` = `"<ns>/<key>"` or bare key → `briefing_shared_blocks`; `publish_shared_kv_trusted`; `cron_loader` parse/round-trip). `process_one_task`'s success path calls `_publish_result_to_shared_kv` — a gated post-success write in the `_process_deferred_*` genre (NOT an `output_target` surface): the identity is always `task.user_id`, gated on `is_shared_kv_writer`; an unauthorized/failed publish is **fail-loud** (ERROR + operator alert + job-failure increment that the success reset withholds), an empty result is a clean skip (last-known-good). This lets an admin's agentic deep-browse prompt (full sandbox + tools) publish its digest for every user to read, keeping the built-in generator tool-less under `__system__`. **Newsletter article links + HTML briefing email** (briefing-newsletter-links-html-email spec): the two halves of "a cited story should be clickable". _Input_ — the `email` source used to flatten newsletter HTML with `skills/briefing._strip_html`, whose blanket tag strip deletes every `<a href>` and keeps only the anchor text, so a newsletter story could never be cited to its own article the way an RSS item (structured `url`) can. `briefings/sources/_html.html_to_markdown` does the same flattening but rewrites each surviving anchor as **inline** `[anchor](url)` (inline, not a trailing reference block, because the story↔link adjacency is what lets the model pick the _right_ article). Newsletters are link soup, so extraction is aggressively filtered: text-less anchors dropped whole, non-`http(s)` dropped, unsubscribe / view-in-browser / preferences / social-share dropped by URL **and** by anchor label (a tracking-wrapped unsubscribe hides the keyword in an opaque redirect, but its label doesn't), duplicates collapsed, and a `[briefings] newsletter_max_links_per_source` cap (default 20, 0 = unlimited) so link soup can't flood the prompt — a filtered or over-cap anchor keeps its text and loses only the destination. Redirect unwrapping is a **conservative** allowlist (`?url=`/`?u=`/`?redirect=`/`?target=`/…) that fires only when the param holds an absolute `http(s)` URL, so `?u=<user-id>` and an opaque `/click/<hash>` are kept rather than mangled — a working tracked link still lands on the article. `bleach` (the `feeds` extra) is preferred for the parse, with a regex fallback that still preserves links, so the feature never depends on the extra. Non-obvious invariant: each emitted link is spliced in **after** the flattening pass via a control-char placeholder, because that pass ends in `html.unescape` and `&copy`/`&reg` are valid entities without a semicolon — an already-decoded URL inserted before it would silently lose part of its query. _Output_ — `skills/briefing.render_briefing_html` renders the skill's constrained markdown subset (links, bold/italic, single-level bullets, `---`, paragraphs; a stray `## ` marker dropped as `strip_markdown` already does) to bare HTML, and `skills/email.send_email`/`reply_to_email` take an `html_body` that makes the send `multipart/alternative` (plain fallback + HTML). `transport/email/outbound._briefing_email_bodies` is the single decision point mapping `(task, body, format)` → `(plain, html_body, content_type)` for all three send sites. **No styling at all** — no `style` attributes, no `<head>`/`<style>`, just a bare `<html><body>` shell so each mail client's own default typography renders (a test asserts this against regression). Escaping happens _first_ and only `http`/`https`/`mailto` reach an `href`, so newsletter-derived `<script>` or a quote inside a URL can never become markup; emphasis is applied by walking link matches rather than one `re.sub`, so an underscored URL can't sprout an `<em>` inside its own `href`. Both halves are fail-soft: a render/parse failure returns empty / falls back to the old tag-strip and the briefing still delivers as plain text. Per-user opt-out `user_profiles.briefing_email_html` (default on) via `istota user ensure --no-briefing-email-html`,  or the briefings-settings **Email delivery** card; off is byte-identical to the pre-feature single-part plain delivery. The toggle lives on `/briefings/settings` rather than the `/settings` Preferences card because it governs only how a briefing reaches the inbox — which put the first page-level (non-per-record) edit on that page, so it registers with the `useSettingsSave` app-bar Save and the briefings layout gained a `HeaderSave` in its `tools` snippet (the feeds-settings pattern). The per-record source/shared-block forms there keep their own buttons, unchanged.


The reader uses `BriefingEdition.svelte` and `BriefingBlockCard.svelte` for immutable editions. Archive detail adds `document`, validated by the DB mapper; archive lists retain their linear body without document payloads. Unknown or malformed documents use the complete linear body. The edition container drives one/two/three columns at 40rem and 64rem, with `auto`/`wide`/`full` spans. `web/src/lib/masonry.ts` places cards in the shortest available columns and matches cards sharing a top edge within 50px and rounds each group up to a 50px height step. A final pass extends cards into gaps of at most 50px before the next overlapping card, so neighboring bottoms can match even when their tops differ. It measures inner content, so snapped space does not feed back into later measurements. The padded reader container uses the shared content width, matching Groups at wide viewports. DOM order stays the saved order; visual rows can differ. Runtime data-attribute selectors are global within the scoped grid selector so Svelte retains the masonry row rules. Card headers keep the title on the left and small square actions on the right, with settings before expand; settings controls appear only for live blocks in DB-managed briefings and link to `?name=&block=` in settings. Partial-source cards show a warning variant of the shared `HintPopover` beside their title, with an accessible label and hover/tap explanation. HTML and plain email renderers omit the source-status notice; saved status remains available to the web reader. Archive subjects reserve two wrapped lines. Cards use the shared Markdown renderer and file-link action. Cards render every Markdown block without truncation or clipping. `Modal variant="viewer"` opens the same complete content through the card's content-only mode. ## Archive read state

Schema version 3 adds nullable `briefing_archive.read_at` after the version-2 structured-document migration and a partial unread index. The migration marks historical rows read once; new archives remain unread across later initialization. `count_unread_archive`, `mark_archived_read` and `mark_archive_as_read` own counting and idempotent updates. Existing first-read timestamps are preserved. Archive and block IDs use separate retained counters through `_id_high_water`; archive deletion and pruning retain the counter before removing rows, so a delayed acknowledgment cannot read a replacement edition. Archive list/detail GETs return `read_at` and never mark anything read; delivery to email or chat does not mark it either.

`POST /api/briefings/archive/{id}/read` marks one archive row and returns `{id, read_at}`, or 404 in the caller's own database. `POST /api/briefings/mark-as-read` accepts `{scope: "all"}` or `{scope: "briefing", briefing_name}` and returns `{status: "ok", updated}`. Both use the authenticated module context and origin guard. Bulk marking uses one worker-thread transaction and one UPDATE across all pages, with exact name matching; rows committed after the update remain unread.

The web reader acknowledges a body only after it renders visibly and still matches the selection. Hidden tabs, stale loads and failed fetches do not consume reads. Failed acknowledgments keep the body readable and show Retry. The header uses the Feeds `Chip`/`CheckCheck` control before Save and settings, only on the reader route. Its confirmation captures the all/name scope when opened and cancels on leaving the reader or changing accounts. Success preserves selection, filters and loaded pages; failures use the shared error notice. Single reads, bulk reads and successful deletion invalidate navigation counts. Read tracking and the header action work with navigation badges disabled.


## Group definitions, runs and delivery

The group owns definitions and editions in the framework DB, not its creator’s module DB. `group_store.py` owns revision-checked saves, current-owner authoring, occurrence uniqueness, attempt leases, immutable publication and recipient/part states. `groups.system` reconciles the reserved `all_users` group from enabled users; ordinary groups require current ownership, while All users has an explicit admin authoring exception. Administrative group management alone grants neither private reading nor authoring. Every reader, download, notification and pending send rechecks current account/membership; future members read retained history without delivery backfill.

`group_runs.py` connects ordinary tasks to research and generation. `group_briefing_research` runs as `__briefings__` through the normal executor, withheld scopes, sandbox and browse skill. The trusted browser identity chooses the service-owned Briefings profile. The final tool-less synthesis reuses `shared_blocks._run_section_brain`; structured-only blocks call no model. Research results are persisted against an attempt before private inputs are gathered. No new tool bridge, runtime, model authentication or browser network policy belongs here.

`source_grants.py` binds exact personal resources, calendar projection/window, membership interval and channel to the future-member audience contract. `sources/group.py` and `sources/contributions.py` use existing pinned readers and calendar clients. A refused source remains fatal through concurrent gather, even with useful public content; it cannot become a fail-soft omission. Grants are revalidated before publish and each pending send. Revocation does not erase retained editions or recall external copies.

`group_delivery.py` queues existing workers and renders the saved edition through existing email/Talk/ntfy senders. The framework transaction publishes the audience once; confirmed parts are never repeated. Expired active sends and ambiguous provider outcomes become uncertain. An owner must acknowledge possible duplication to retry them, and their original destination identity remains fixed. `delivery_refusal` is the common live gate for exclusions, member mutes, membership interval, module/destination availability and grants. Exclusion suppresses both outbound and in-app legs, keeps historical access, and persists by stable user id across rejoin; clearing it never revives skipped rows. Disable/archive stops unsent work. Active or uncertain deliveries hold retention pruning.

`group_routes.py` supplies the target, authoring, reader, approval, preference and delivery APIs. The Briefings editor/reader and Groups deep links share components. Saved targets are immutable; duplicate creates a disabled draft and strips approvals. Preview uses real generation but publishes no audience and remains author-only. An author change supersedes an admitted older revision. Operator CLI and `settings_plan/group_briefings.py` use the same validation; plans cannot create source approvals or bypass migration activation gates.

## Administrator hold and delete

The admin-briefings spec. **A hold is separate from the owner's `enabled`**: `admin_hold_at` and `admin_hold_by` on both `briefing_configs` and `group_briefing_configs`, and a briefing runs only when it is enabled and not held. An admin pause that set `enabled = 0` was rejected because the owner could turn it straight back on. Lifting a hold restores whatever `enabled` the owner had chosen.

Personal: `user_briefings.set_hold` / `clear_hold` key by id across users. Setting one cancels the briefing's pending tasks through `cancel_queued_tasks`; failed ones keep their history, and a running task finishes. `group_migrate.cutover_default` calls the same function with `statuses=("pending", "failed")`. `_apply_user_briefings` keeps a held row, and `db.create_task` (through `user_briefings.require_runnable`) refuses a held briefing with `briefing_held` and one with no row with `briefing_deleted`. That refusal is what stops a briefing in a running daemon, whose overlay is the one loaded at boot: a hold or delete after boot, and a hold in place at boot, so a resume takes effect without a reload. `check_briefings` stamps `last_run` on either refusal, so it is not retried every tick and a resume waits for the next slot; run-now answers "is paused by an administrator" and "no longer exists". The only producer of a `briefing` task is `scheduler._create_briefing_task` (cron tick, trigger file, run-now), and each reads a configured row, so nothing legitimate is refused. `ensure_briefing` never writes the hold columns, so an owner's save keeps the hold and still stores the owner's `enabled`.

Group: `group_store.set_hold` / `clear_hold` take `config` because both re-run `sync_approvals`, and both bump `revision`, so an open editor gets a revision conflict rather than overwriting the hold. `sync_approvals` writes no source-approval request for a held definition and closes its open ones, so a hold sends contributors nothing and a resume writes each request once, for the new revision. A hold runs `stop_definition_work`, the block `save_definition` runs on disable, extracted so both call one function: supersede queued runs, mark pending and failed legs `skipped` with `definition_held`, tag `sending` legs. A run already past publish delivers as on disable, and legs a hold skipped stay skipped after resume. `check_group_briefings` and `enqueue_run` refuse a held definition, `delivery_refusal` checks the live hold, and `validate_definition_save` refuses an owner turning a held definition on (409 `definition_held`). Owners may still edit and disable it. Both payloads carry `held: {at, by_label}`, where `by_label` is the admin's display name from `user_briefings.hold_view`, falling back to "an administrator" and never the id.

Deletes: a personal briefing goes through the owner's own `delete_briefing_by_id`, so archives stay. A group definition is soft-deleted by `group_store.delete_definition`: refused with `migration_pending` while any `group_briefing_migrations` row names it in a state other than `cutover` or `rolled_back`, then stop work with `definition_deleted`, `source_grants.revoke_definition_grants`, open approval notices closed, `deleted_at` / `deleted_by` set, `enabled = 0`, and `name` renamed to `deleted-<id>-<name>` (at most 100 characters) so the group can reuse the name. Authoring readers filter `deleted_at IS NULL`; `get_definition` does not, because edition readers, delivery and notifications need the row. Group routes pass `deleted_ok` for history reads only, and the definition payload says `deleted: true`. Once a definition is deleted, `group_migrate._owned` refuses every review, cutover, rollback and publisher-report step on it with `migration_definition_deleted`, the default report shows no definition, and `import_default` for that default imports a fresh disabled draft rather than returning the deleted one.

A group's current owners delete through the same function, from the settings page's kebab: `DELETE /groups/{group_id}/briefings/{name}` with the editor's `revision`, which passes `expected_revision` (409 `revision_conflict`) and `draft_only` (409 `disable_first` while `enabled`). Owners have no typed name or step-up, as an owner's personal delete has none; turning the briefing off first is the deliberate step. No notice is written, since the actor is one of the people an admin delete would tell.

`admin_routes.py` mounts `/api/admin/briefings` beside the groups router and reuses its `require_admin`, body reader and error mapping. The list is definitions and state only, never blocks, sources, prompts or editions, and includes a personal row whose owner has no profile. Hold and resume are idempotent: the route compares the hold before and after, and only a change logs and notifies. A delete checks the typed name (`confirm`, 409 `confirm_required`) and a pending migration before redeeming the `admin_briefing_delete` step-up, so a refusal the admin must fix first does not spend the code. The host fills `step_up_gate` with `_require_step_up`; an unmounted gate is a 503, never a skipped proof. Each landed write logs `admin_briefing action= kind= id= owner= admin=` with no title. `notifications/resolvers/admin_briefing_change.py` tells the personal owner or the group's current owners, never the acting admin, nobody for All users, and no user without a profile; it is written after the commit and handed to the daemon.

The Admin › Briefings page (`web/src/routes/admin/briefings/`) draws both lists with a client-side filter. Pause asks for confirmation, Resume does not, and Delete goes through `ConfirmDialog`'s typed name and then `StepUpDialog`. A refused code stays in the step-up dialog; every other refusal is a `notifyError`, `migration_pending` saying to cut over or roll back the migration first.

## Migration operations

`group_migrate.py` uses one journal for default preservation/import/review/cutover/rollback and publisher import/report/cutover/rollback. The default registry is captured only for an existing install; a fresh install captures nothing. `istota init` loads paths without DB overlays, migrates, then reloads effective configuration. The entrypoint’s preflight also avoids overlays. This ordering is required when old defaults exist and the journal does not; ordinary loads still refuse pre-init legacy state.

A default report proposes retirement only for positively attributable unchanged copies, with explicit `retire`, `keep` or `mute` decisions for others and a reviewed common timezone. Cutover records old schedule/task outcomes and refuses running work. Publisher import requires operator-supplied generation intent and a dependency inventory; arbitrary commands are neither read nor executed. Cutover requires a successful current-revision preview, explicit confirmation and enabled replacement producers for remaining consumers. It persists a tombstone respected by CRON sync, job enable and cached task admission. Rollback restores schedules without replaying cancelled occurrences; sending/uncertain group legs block it. KV values/timestamps and personal archives remain intact. Actual production migration is a separate operator action documented in `docs/deployment/migrating-group-briefings.md`.

The image upgrade witness in `tests/image/test_upgrade.py::TestGroupBriefingsUpgrade` starts from the real floor schema/config, then runs `seed/group_briefing_state.py` in separate containers before and after a restart. It checks empty exclusion defaults, preserved schedules/opt-outs, idempotent import, CRON retirement, partial/uncertain SMTP outcomes, stable send identities, no regenerated edition and rollback. SMTP is a coarse fake boundary; this is not a live delivery or model/browser smoke. The ordinary skill/proxy/browser integration scripts model and Chrome, while the separate Linux tier witnesses real mounts for both brains.
