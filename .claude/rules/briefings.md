# Briefings module (`src/istota/briefings/`)

First-class **block/source content module** (`src/istota/briefings/`, spec `Specs/Done/briefings-first-class-module.md`, Stages 1–6 shipped; 7–8 deferred). **Blocks are the sole content model** — the legacy component generator, boolean-defaults expansion (`BriefingDefaultsConfig`/`[briefing_defaults]`), TOML `components =`/`--components-json` authoring, and the executor's legacy fallback were all retired (retire-legacy-briefing-components spec). A briefing is an ordered list of **blocks** — each with a title, an optional synthesis directive, a render mode (`synthesis`/`structured`), and 1..N **sources** — gathered and synthesized into one section per block at generation time. Source kinds (`sources/*`): `rss` (a Feeds subscription/category, soft-degrades when Feeds is off), `email` (shared-pool newsletters, windowed, owner-filtered, fail-closed without the framework DB), `browse` (a bundled preset or arbitrary URL frontpage via the browser skill), `markets`, `calendar`, `todos`, `reminders`, `notes`. The `todos`/`reminders`/`notes` sources read a file whose `path` (a source `config` property; no default — blank reads nothing) resolves **relative to the user's own `/Users/<uid>/` folder** (`sources.builtins._resolve_user_path`), so `shared/…` reaches a bot-shared file and `istota/…` the bot workspace; a path already rooted at the user's own folder passes through, `..` segments are stripped, and a path naming another user resolves under the caller's own folder (never a cross-user read). The web editor offers a **server-side-filtered** file autocomplete (`GET /briefings/path-suggest?q=` — the query walks the workspace so a deep/late file still surfaces as the user types, not a fixed on-load pool) via the reusable `ui/AutocompleteInput` component, and shows an **advisory** existence hint (`GET /briefings/path-check`, debounced): it never blocks the save, since the resolver is fail-soft (a missing file contributes a provenance note), so a not-yet-created or transiently-unreachable path can't trap the editor. Gathering is **concurrent** (bounded thread pool, each worker on its own framework connection — SQLite conns aren't thread-safe) and **fail-soft** — a down/unknown source contributes a provenance note, never raises, never kills the briefing (`resolve_source` backstop); per-block output order is deterministic (reassembled by slot, not completion). Blocks/sources/archive live in a per-user SQLite module DB on **local disk** (`Config.module_db_path(user, "briefings")`, WAL); user-facing workspace stays on the mount. Gated by `Config.is_module_enabled(user, "briefings")` (`briefings` in `MODULE_NAMES`); own web tab (reader landing page + archive) and a block/source **+ schedule/delivery** settings editor. Each archived result in the reader sidebar carries a kebab → **Delete** (shared `ConfirmDialog`) that hits `DELETE /api/briefings/archive/{id}` → `db.delete_archived` (single-row, 404 on a missing id) — a user-driven prune alongside the age-based `archive_retention_days` sweep; the sidebar removes the row optimistically and re-points the reader to a neighbour. Content is managed via `istota briefings blocks|sources|archive …` (operator, `cli_briefings.py`), the `briefings` skill facade (`BRIEFINGS_USER`, `untrusted_input` companion, error-envelope exit contract), or the web settings page; **scheduling + delivery stay framework-owned** (cron in user TZ, real `briefing_configs.output` column, `enabled=0` mutes; provision via `istota briefings schedule ensure` or the web UI). **The workspace `BRIEFINGS.md` is retired as an input** — `skills/briefing._load_workspace_briefings` is deleted and `get_briefings_for_user` now returns `UserConfig.briefings` (TOML + the `briefing_configs` overlay) unmodified, so the whole schedule surface is TOML and the DB. It had to go because it was applied *over* that overlay, so a cron the settings page had just written was overridden by a months-old file while the page kept showing the value the user picked — a divergence with no log line and no surface that reported it. `user_briefings.import_from_workspace_files` carries each user's file into `briefing_configs` once, sentinel-guarded per user in `_migration_state` (`briefings_md_import_v1:{user_id}`), from the scheduler's Phase 7b boot block **after** `import_from_user_configs`. Three decisions there are the non-obvious ones. The file's value **overwrites** an existing row rather than skipping it, on `cron_expression` / `conversation_token` / `output` and nothing else: the bar for a retirement is that nothing observable changes at the switch, and the file was the live authority for those three, so skipping would silently start honouring a web-UI edit the file had been suppressing. `enabled` and `title` are deliberately left with the row, and both **are** changes at the switch rather than exceptions to the rule — in each case the old override was suppressing a web-UI setting rather than expressing one. `_apply_user_briefings` drops an `enabled=0` row from `UserConfig.briefings` and the old file merge added the briefing straight back by name, so a briefing switched off in the UI kept running; importing `enabled = 1` would carry that bug forward as a stored fact instead of ending it. `title` is the same shape: the file's entry replaced the row wholesale with a blank title, so a title typed into the UI was ignored at render. An existing row's `components` are likewise untouched, which is narrower than "components are not imported" — `_apply_user_briefings` reattaches them, so a briefing whose module DB has not yet been initialised can still seed blocks from them. **The sentinel is only burned on positive evidence that the workspace is readable** (`_workspace_is_live`: `os.path.ismount` where `storage_is_nextcloud`, gated exactly as `doctor.check_mount_liveness` gates it since the local install mounts nothing, plus the user's `config/` directory existing). A dropped rclone mount leaves a plain empty directory, so every path under it is ENOENT and `Path.exists()` answers False rather than raising — reading that as "this user had no file" marks them done for ever, and `ensure_user_directories_v2` runs earlier in the same boot and will recreate the workspace on the underlying disk, so the directory alone is not evidence. **Every file is read before the connection is opened**, in three phases (outstanding users → read the mount → write): the obvious one-connection loop takes a write lock at the first user and holds it across every remaining user's stat and read against the FUSE mount, on the foreground boot path — which is the same hazard that moved the startup doctor onto a thread. Each user's write is wrapped in a `SAVEPOINT`, so a partial failure leaves no rows disagreeing with the sentinel it never set. Entry values are type-checked rather than `str()`-coerced (a TOML array otherwise writes its Python repr into the `name` column), an output that resolves to no destination is stored as `talk` rather than as a row `ensure_briefing` would refuse, and the file is read `encoding="utf-8", errors="replace"` because `UnicodeDecodeError` is a `ValueError` and would miss the `OSError` retry, failing every boot for ever. The sentinel is **per user**, not per deployment, because a user whose mount was unreadable on the boot that ran the migration would otherwise never be looked at again and their schedule lives only in that file — and for the same reason an unparseable file leaves the sentinel unset rather than burning it. `components` is **not** carried over: the read path has discarded it since blocks became the content model, so importing it would feed `_migrate._migrate_components` and hand the user content they have not had for releases. `storage.ensure_user_directories_v2` seeds no `BRIEFINGS.md` (an existing one is left on disk — it is the user's file), `BRIEFINGS_TEMPLATE` and `_build_briefings_seed` are gone, and `BRIEFINGS_EXAMPLE` is a tombstone pointing at the settings page. `skills/briefings_config/skill.md` was the sharpest edge and is rewritten: it is prompt text, and it documented the discarded `[briefings.components]` shape in full with no mention of the DB or the web UI, so the model would write the file, confirm, and change nothing. **Deterministic titles**: a briefing's title is composed by `briefings.generate.resolve_briefing_title` from its configured `briefing_configs.title` (blank → `default_briefing_title` humanizes the _name_, so `morning` → "Morning Briefing") plus the run date in the user's timezone, appended by the renderer ("Morning Briefing — Monday, 27 July"). `scheduler.briefing_title_for_task` dates it from the task's `created_at` (the cron fire) and is called independently by all three consumers — archive `subject`, email subject, ntfy title — so a pure function of `(task, config)` keeps them identical without plumbing a value between them. The model no longer supplies a title: the envelope is `{"body": …}` (the `subject` key is dropped from both the prompt and `skills/briefing/skill.md`, though `parse_briefing_json` still tolerates one from an in-flight run — it is ignored). Previously the archive stored the model's free-styled `subject` (emoji, dates, a summary clause — different every run) while email discarded it and re-derived "Morning Briefing"/"Evening Briefing" by regex-scraping the _prompt_, keyed on the clock (`resolved.hour < 12`) rather than the briefing's name — so an "evening" briefing firing at 11am mailed as "Morning Briefing" and the two surfaces disagreed about the same run. That regex survives as `transport/email/outbound._legacy_briefing_subject`, reached only when no caller title is supplied. Editable via `istota briefings schedule ensure --title`, `[[users.X.briefings]] title` / `[[default_briefings]] title` TOML (Ansible `istota_default_briefings`), and the briefings-settings **Schedule** card, whose rows gained an edit affordance (the POST was already an idempotent upsert keyed on `name`, so an edit is a save with the name held fixed — the table had been add/delete only). At generation the executor's deferred-prompt path (`build_deferred_briefing_prompt` → `_build_module_briefing_prompt`) is the only path — `ensure_initialised` runs the one-time components→blocks migration first, then `assemble_briefing_input`; a briefing with no blocks after migration returns `None` → the task fails with the existing quiet retry (no legacy render). Generation runs on the ISSUE-143 **deferred-prompt worker** (source fetch never touches the dispatch thread); on completion the scheduler archives the delivered briefing and prunes by `[briefings] archive_retention_days` (default 90). Legacy component-based briefings migrate once into blocks/sources **per briefing** (`_migrate.py`, sentinel `migrated_from_components:<name>` — `blocks_from_components` is kept **only** as this one-time migration; `_migrate._migrate_components` prefers a briefing's config `blocks` over the components translation). **Config-authored rich blocks** (config-authored-rich-briefing-blocks spec): an operator authors the full block/source shape in `[[users.X.briefings.blocks]]` + `[[...blocks.sources]]` TOML (per-block `title`/`directive`/`render_mode`/`options` + 1..N sources of any `kind` with arbitrary `config`), seeded once via the per-briefing sentinel, then the briefing is an ordinary editable per-user briefing (operator re-runs never re-clobber). `blocks` is an **in-memory-only `Config` field** (never stored in `briefing_configs`): parsed by `_parse_briefing_specs`, threaded through `_apply_user_briefings` (re-attached to the DB-shadowed entry by name) + `get_briefings_for_user`. **Default briefings**: a canonical shared set defined once in top-level `[[default_briefings]]` config (Ansible `istota_default_briefings`) is seeded by name into each opted-in user (per-user `default_briefings` flag, default on; user's own briefing wins) in `_apply_user_briefings` — seed-once + edit-preservation fall out of `import_from_user_configs` + the block sentinel for free. The Ansible path renders content-only `[[users.X.briefings]]` stubs (`istota_briefing_blocks_toml` filter) and the `[[default_briefings]]` section (`istota_default_briefings_toml` filter); schedule/delivery flow through `istota briefings schedule ensure` + `istota user ensure --default-briefings/--no-default-briefings`. The `briefing` skill (singular) is the output-formatting guideline selected on `source_types:[briefing]` and returns `{body}` JSON; the `briefings` skill (plural) is the content-management CLI facade. **Shared curated content** (shared-kv-curated-briefing-content spec): a cross-user **`shared_kv`** table (namespaced JSON, open reads / admin-only writes via the fail-closed `Config.is_shared_kv_writer` — _not_ `is_admin`'s empty-means-all) is the substrate for content that's identical across users. One consuming source kind: `shared_block` (`{name, max_age_hours}` → namespace `briefing_shared_blocks`, key `name`; trust taken from the stored value, not the consumer). The writer picks granularity by value shape — `{"items":[…]}` (share the fetch → per-user synthesis) vs `{"text":…}` (share the synthesis → verbatim splice into a `structured` block); freshness-gated (stale/missing → omitted, fail-soft) and untrusted-wrapped unless `trusted:true`. Writes reach `shared_kv` three ways, all converging on the gate: sandboxed skill (`istota-skill kv set --shared`, deferred `scope:"shared"` op gated on `task.user_id` at apply time in `_process_deferred_kv_ops`), direct skill/CLI (`istota kv set --shared`), all admin-only; set-ops reject `--shared`. **Module-owned shared blocks** (batteries-included): top-level `[[briefing_shared_blocks]]` config (`BriefingSharedBlock`; canonical `world-headlines`/`markets-summary` seeded via `DEFAULT_SHARED_BLOCKS` when unset; Ansible `istota_briefing_shared_blocks`) are one-block briefings generated **once globally** under the reserved `__system__` identity — `scheduler.check_shared_blocks` (cron in the operator-configured shared-block timezone `[briefings] shared_block_timezone` / Ansible `istota_briefing_shared_tz`, default UTC; `cron_max_staleness_minutes`-gated, off-dispatch worker thread) runs `briefings.shared_blocks.run_shared_block` (user-agnostic gather over `browse`/`markets`/`email` only — `rss` + personal built-ins dropped; section-only synthesis via the general-alias Brain) and does a **trusted daemon** `db.shared_kv_set(..., written_by="__system__")` (no `is_shared_kv_writer` gate — the module writing its own content isn't a user task), stamping `briefing_shared_block_state.last_run_at`; an all-empty gather skips the write (last-known-good). The seeded default morning briefing reads `world-headlines` via a `shared_block` source, so the N-way frontpage fetch + synthesis collapses to one generation. Escape hatch for arbitrary content: an admin CRON `command:` job writing `shared_kv` directly (`scripts/examples/shared_kv_curation.sh`). **Admin-editable shared blocks** (admin-shared-briefing-blocks spec): shared-block definitions are DB-backed and admin-manageable, not config-only. A `shared_block_configs` framework table (CRUD in `db.py`, `SharedBlockConfigRow`) is seeded once from `DEFAULT_SHARED_BLOCKS`/`[[briefing_shared_blocks]]` (`shared_blocks_store.import_from_config`) and DB-wins thereafter (`config._apply_shared_blocks` overlay — same seed-once + edit-preservation contract as `default_briefings`), so `check_shared_blocks` reads DB-authoritative definitions. Managed via admin-gated web routes on the briefings router (`GET/PUT/DELETE /shared-blocks` + `POST /shared-blocks/{name}/run` behind `require_admin` = `Config.is_shared_kv_writer`, fail-closed; validates cron/`render_mode`/slug + source kind ∈ `ALLOWED_SHARED_SOURCE_KINDS` in `briefings.models`) and the `istota briefings shared list|ensure|remove|run` CLI. The briefings-settings web page renders an admin-only "Shared blocks" card (reusing the extracted `SourceConfigFields.svelte`, shared with the per-user editor) and any user gets a **Shared block** per-user source kind picking from `GET /shared-block-options`. **Verbatim structured generation**: `render_mode="structured"` now **skips the synthesis brain entirely** (`run_shared_block` → `_assemble_verbatim`, concatenating gathered source text in slot order) — self-formatting data (the markets quote table) is stored verbatim with zero LLM passes; `markets-summary` flipped to structured + `trusted`. The stored value carries a `trusted` flag; the read side (`sources/kv.py`) honors the **stored value's** `trusted` for the `briefing_shared_blocks` namespace (a consuming user can never flip it) and a live `shared_kv` key with no definition row is a valid custom-published block, not "unknown". **`publish_shared_kv` job attribute**: a scheduled job can publish its result text into `shared_kv` on success (`scheduled_jobs.publish_shared_kv` = `"<ns>/<key>"` or bare key → `briefing_shared_blocks`; `publish_shared_kv_trusted`; `cron_loader` parse/round-trip). `process_one_task`'s success path calls `_publish_result_to_shared_kv` — a gated post-success write in the `_process_deferred_*` genre (NOT an `output_target` surface): the identity is always `task.user_id`, gated on `is_shared_kv_writer`; an unauthorized/failed publish is **fail-loud** (ERROR + operator alert + job-failure increment that the success reset withholds), an empty result is a clean skip (last-known-good). This lets an admin's agentic deep-browse prompt (full sandbox + tools) publish its digest for every user to read, keeping the built-in generator tool-less under `__system__`. **Newsletter article links + HTML briefing email** (briefing-newsletter-links-html-email spec): the two halves of "a cited story should be clickable". _Input_ — the `email` source used to flatten newsletter HTML with `skills/briefing._strip_html`, whose blanket tag strip deletes every `<a href>` and keeps only the anchor text, so a newsletter story could never be cited to its own article the way an RSS item (structured `url`) can. `briefings/sources/_html.html_to_markdown` does the same flattening but rewrites each surviving anchor as **inline** `[anchor](url)` (inline, not a trailing reference block, because the story↔link adjacency is what lets the model pick the _right_ article). Newsletters are link soup, so extraction is aggressively filtered: text-less anchors dropped whole, non-`http(s)` dropped, unsubscribe / view-in-browser / preferences / social-share dropped by URL **and** by anchor label (a tracking-wrapped unsubscribe hides the keyword in an opaque redirect, but its label doesn't), duplicates collapsed, and a `[briefings] newsletter_max_links_per_source` cap (default 20, 0 = unlimited) so link soup can't flood the prompt — a filtered or over-cap anchor keeps its text and loses only the destination. Redirect unwrapping is a **conservative** allowlist (`?url=`/`?u=`/`?redirect=`/`?target=`/…) that fires only when the param holds an absolute `http(s)` URL, so `?u=<user-id>` and an opaque `/click/<hash>` are kept rather than mangled — a working tracked link still lands on the article. `bleach` (the `feeds` extra) is preferred for the parse, with a regex fallback that still preserves links, so the feature never depends on the extra. Non-obvious invariant: each emitted link is spliced in **after** the flattening pass via a control-char placeholder, because that pass ends in `html.unescape` and `&copy`/`&reg` are valid entities without a semicolon — an already-decoded URL inserted before it would silently lose part of its query. _Output_ — `skills/briefing.render_briefing_html` renders the skill's constrained markdown subset (links, bold/italic, single-level bullets, `---`, paragraphs; a stray `## ` marker dropped as `strip_markdown` already does) to bare HTML, and `skills/email.send_email`/`reply_to_email` take an `html_body` that makes the send `multipart/alternative` (plain fallback + HTML). `transport/email/outbound._briefing_email_bodies` is the single decision point mapping `(task, body, format)` → `(plain, html_body, content_type)` for all three send sites. **No styling at all** — no `style` attributes, no `<head>`/`<style>`, just a bare `<html><body>` shell so each mail client's own default typography renders (a test asserts this against regression). Escaping happens _first_ and only `http`/`https`/`mailto` reach an `href`, so newsletter-derived `<script>` or a quote inside a URL can never become markup; emphasis is applied by walking link matches rather than one `re.sub`, so an underscored URL can't sprout an `<em>` inside its own `href`. Both halves are fail-soft: a render/parse failure returns empty / falls back to the old tag-strip and the briefing still delivers as plain text. Per-user opt-out `user_profiles.briefing_email_html` (default on) via `istota user ensure --no-briefing-email-html`, Ansible `briefing_email_html: false`, or the briefings-settings **Email delivery** card; off is byte-identical to the pre-feature single-part plain delivery. The toggle lives on `/briefings/settings` rather than the `/settings` Preferences card because it governs only how a briefing reaches the inbox — which put the first page-level (non-per-record) edit on that page, so it registers with the `useSettingsSave` app-bar Save and the briefings layout gained a `HeaderSave` in its `tools` snippet (the feeds-settings pattern). The per-record source/shared-block forms there keep their own buttons, unchanged.

## Briefings

First-class **block/source content module** (`src/istota/briefings/`). **Blocks are the sole content model** — the legacy component generator, `[briefing_defaults]` expansion, and TOML `components =` authoring were all retired. A briefing is an ordered list of **blocks** (a title, an optional synthesis directive, a render mode `synthesis`/`structured`, and 1..N **sources**), gathered concurrently and **fail-soft** — a down source contributes a provenance note, never kills the briefing — then synthesized into one section per block. Source kinds (`sources/*`): `rss`, `email`, `browse`, `markets`, `calendar`, `todos`, `reminders`, `notes`, `kv`, `shared_block`. Blocks/sources/archive live in a per-user SQLite module DB on **local disk** (`Config.module_db_path(user, "briefings")`, WAL); gated by `Config.is_module_enabled(user, "briefings")`, with its own web tab (reader + archive) and a block/source + schedule/delivery settings editor. **Scheduling and delivery stay framework-owned** (cron in the user's TZ, the `briefing_configs.output` column, `enabled=0` mutes). Managed via `istota briefings blocks|sources|archive|schedule|shared …`, the `briefings` skill facade, or the web settings page. Generation runs on the ISSUE-143 **deferred-prompt worker** (`build_deferred_briefing_prompt`), so source fetch never touches the dispatch thread; on completion the scheduler archives the delivered briefing and prunes by `archive_retention_days`. Cross-user curated content rides a `shared_kv` table (open reads, admin-only fail-closed writes) with module-owned + admin-editable **shared blocks** generated once globally under the reserved `__system__` identity.
