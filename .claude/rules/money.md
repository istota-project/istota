# Money module

## Money taxes

Quarterly estimated-tax calculator (`src/istota/money/core/tax.py`), the one page in the module that computes a number the user sends to a government.

**Rate data is versioned data, not constants.** `data/tax_rates.json` behind `core/tax_data.py` carries a 51-entry jurisdiction registry (with a `taxes_income` flag), federal years, and per-state years — each year naming the document it was transcribed from (`source`, `source_url`) and the date it was last checked (`verified_on`). It replaced module-level dicts in which the 2026 rows were byte-for-byte copies of 2025, so the page produced 2026 estimates from 2025 law with nothing able to say so; the shipped California figures turned out to be years stale in the same way. Only genuinely *statutory* figures stay as Python constants (FICA rates, the never-indexed Additional Medicare thresholds, the safe-harbor AGI threshold).

**Deliberately not fetched from anywhere.** The IRS publishes no machine-readable rates, the free re-keyings are dead or AGPL, and — decisively — fetching would not have prevented the bug it appears to solve: OBBBA changed the *structure* of 2026 federal tax (the QBI phase-in range moved from 100k/50k to 150k/75k), so a bracket API would have returned current thresholds and still produced a wrong answer. The property wanted is knowing when the numbers are stale, which needs no dependency. Provenance fields keep a future assisted-update path open.

**Three signals fall out of provenance**, rendered on both the taxes page and its settings page: attribution (the authority and check date, per jurisdiction), a **missing-year warning** when resolution fell back to another year (`YearRates.is_fallback` — the old resolver did this silently, which is why 2027 would have computed from 2026 numbers and reported them as 2027), and an **age warning** when `verified_on` predates the tax year. California 2026 is deliberately absent — the FTB publishes in the autumn and its own 2026 Form 540-ES says to use the 2025 table — so the fallback warning is the correct live behaviour, not a gap.

**Jurisdiction is a real dimension.** `TaxConfig.state` (`""` = no state tax, the default) has three modes: unset, a bundled code, and a selectable code we ship nothing for. `compute_state_tax` returns a `StateTaxResult` carrying `available` plus a reason (`no_state` / `no_income_tax` / `no_brackets` / `unknown_state`) rather than a 3-tuple, because a zero is a computed result and those four want different UI; the page drops the state column, card and rows entirely rather than rendering zeros. An override cannot resurrect a no-income-tax state. `starts_from` is the one conformity knob (`federal_agi` / `federal_taxable_income` / `gross_compensation`) — enough for Colorado and Iowa starting from federal *taxable* income and Pennsylvania taxing its own gross compensation, without a conformity engine. `installment_schedule` is per-state; California's 30/40/0/30 used to be applied unconditionally, giving every other state California's payment timing. Bundled: California plus ten flat states; five more flat states are listed in `omitted_states` with the reason each is unverifiable (Ohio taxes business income separately, which is the income this page is about).

**Overrides** live in `tax_schedules`, keyed `(tax_year, jurisdiction, filing_status)`. `save_tax` does **not** write them unless passed `write_schedules=True`: a `TaxConfig` carries one set of values with no record of which coordinates they were read under, so a load-modify-save that changes the year, state or status would file the old coordinates' values under the new ones — the very defect the status dimension exists to fix. Only the two importers pass it, and `cli_money._merge_tax` additionally clears them when the incoming TOML moves a coordinate. Everything else edits through `upsert_tax_schedule` / `delete_tax_schedule`, which name their coordinates. The legacy `tax_year_rates` bracket columns lacked the status dimension, so an override entered while filing jointly silently continued to apply after switching to single; they are read once by the markered `migrate_tax_schedules` and never again, while the payroll scalars stay there. `config_store.UNSET` distinguishes "leave this field alone" from an explicit `None` meaning "revert to bundled" — without it there is no per-field revert, only a whole-row delete.

Write paths are validated at the boundary because a bad value is a *read*-path failure: a non-finite float passes a naive range check, is stored, and then raises on the way out (Starlette renders with `allow_nan=False`) — 500ing both the estimate and the settings page's own loader, so there is no UI route back to the value that broke it. Same reasoning for a string in a payroll REAL column, an out-of-range `tax_year` (`is_stale` builds `date(tax_year, 1, 1)`), and an unrecognised state code. The four legacy bracket columns on `tax_year_rates` are rejected by the year endpoint rather than accepted-and-ignored.

Surfaces: `/money/taxes`, a **Taxes** money-settings section (`/money/settings/taxes`), `GET /config/tax/{jurisdictions,resolved,schedules}` + schedule CRUD, and `istota money tax set|rates|schedule|pattern`. `web/vite-mock-api.ts` reads the same `tax_rates.json` rather than holding its own copy, the way the health mocks read `biomarker_refs.json`. A disclaimer naming what is *not* modelled (local taxes, credits, AMT, itemizing, the OBBBA deductions) renders persistently on both pages, following the health module's `_DISCLAIMER`.

## Money portfolio

Point-in-time investment portfolio tracking inside the money module (`src/istota/money/portfolio.py`): Fidelity Portfolio Positions CSV exports (and fina's history file, the migration source) import as **snapshots** into the per-user `money.db` via the importer registry's `kind="positions"` axis, with content-hash dedup so re-imports are safe. Account registry + symbol classifications are per-user data (auto-populated on import, edited on `/money/settings/portfolio`); classification resolves at read time so edits retroactively reclassify history. New symbols auto-classify on import (`portfolio_autoclass.py`: ticker-metadata lookup, then offline description heuristics), with a `portfolio autoclass` backfill command + settings-card button for the rest. A `source='auto'` write is an `INSERT OR IGNORE`, so it can never replace an existing row whatever its value — user edits always win, including a deliberate `Unclassified` and one made while a lookup is in flight. One classification pass per import (not per snapshot), bounded by a lookup count cap, a wall-clock budget and a per-call timeout; `[money] autoclass_lookup` gates the third-party egress. Surfaces: the **Portfolio** money web tab (Overview | History | Import — allocation charts, holdings, value over time, snapshot diffs; the Import subpage is a single card with a source picker covering Fidelity exports and the one-time fina history migration), `istota money portfolio …`, and `istota-skill money portfolio …`. Snapshots never touch the beancount ledgers. Details in `.claude/rules/skills.md` under the `money` skill.
