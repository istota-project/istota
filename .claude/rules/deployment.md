# Deployment

**`istota doctor` first, on any host, before anything else.** It runs the whole check registry against the loaded config and reports each result as `ok` / `warn` / `fail` / `skip`, with a remedy on everything not `ok`; it exits 1 on any `FAIL`, 0 otherwise, and never raises. `--json` gives a machine-readable payload whose statuses are **lowercase** (the text renderer uppercases them; a consumer filtering on `"FAIL"` matches nothing, a defect this repo has shipped once). `--scope image` answers only what a bare `docker run` can, `--scope deployment` only what needs a real install; `--only <prefix>` narrows, `--deep` opts into the checks that spawn a namespace. The same run happens at daemon start-up, silent unless something is wrong, and `check_doctor` sweeps hourly, alerting each admin's `alerts_channel` on a transition into `FAIL`. A tokenless or disabled developer skill makes the `developer.*` checks `SKIP`, so "no FAIL" is not evidence the forge chain is healthy; check that the forge checks did not skip.

**The supported upgrade span is `scripts/upgrade-floor`**, one hand-edited line naming the oldest release an upgrade to current main is expected to work from. `scripts/test-upgrade.sh --from-floor --shape volume` holds it: it captures that release's `config.toml` (by running that release's own `entrypoint.sh` against a two-endpoint Nextcloud stub) and its schema, boots the current image over both, and requires no `FAIL` plus a `developer.forge_config_drift` `WARN`. Bump the floor deliberately, when a migration stops reaching that far or the span stops being worth the run, and never to make a red run green without reading why. The unqualified `scripts/test-upgrade.sh` is the same run; its old near anchor (the merge-base, the `code` shape) went with the bare-metal auto-update cron.

**Migrations run before anything reads the new schema, and only ordering says so.** `db.init_db` is the only framework migration runner and nothing on a long-running process's startup path calls it (not `get_db`, the scheduler, `webui.app` or `serve`), so a process whose code names a missing column fails on its first task read (`_TASK_COLUMNS` is the SELECT list and `sqlite3.Row` raises `IndexError`). On the stack the daemon's entrypoint runs `istota init` before it execs the scheduler, and `web` waits for `daemon` to be healthy, so neither serves an unmigrated database. A rollback across a migration is refused by the schema stamp (below). Remember the ordering when adding a column to a shipped table.

**Room identity relocation is an offline step, and nothing on the stack runs it for you.** `istota init --relocate-rooms --scheduler-stopped` runs schema initialization, the database relocation, then the mount sweep, stopping at the first nonzero result. `--scheduler-stopped` runs the scheduler's own startup orphan recovery first: `WorkerPool.shutdown()` joins for 10 seconds and exits with an in-flight task still `running`, and with the scheduler stopped that row is an orphan, so without it every relocation that landed mid-task deferred (ISSUE-690). Only a caller that has stopped the scheduler may pass it, and nothing checks that: an `istota task -x` or `istota run` holds a `running` row without the daemon flock, and its row would be requeued and migrated under it. The database half consults the task table only while a legacy room is pending, the `repos_relocate` rule. Pending confirmations and every other refusal fail explicitly; only exit 1 with the exact `refusal: live_tasks` line is a retry. On the stack the window is the procedure in `docs/deployment/running-the-stack.md` (stop `daemon` and `web`, the two room writers, plus `whatsapp-baileys`, whose in-memory hold drops inbound messages after 240 s; run the command in a one-shot `compose run --no-deps` container; `istota-stack up`). The external Nextcloud and the rclone mount stay up: the sweep moves `Channels/` over DAV and refuses when either is unavailable. `istota-stack down` would also work but stops `signaling`, which a registered HPB makes every Talk user on that Nextcloud depend on. The retained-volume upgrade test seeds a legacy room, tasks, transcript and directory, invokes this command, and checks minted identity, unchanged native binding, preserved history and an idempotent sweep. Keep the temporary either-name storage reader until production reports zero outstanding; mapping and forwarding remain permanent.

**The bundle names the commit it came from, when its builder says so.** SvelteKit emits `_app/version.json`, and `web/svelte.config.js` stamps `ISTOTA_BUILD_SHA` into it in place of the build timestamp, so `doctor`'s `web.build_current` can ask whether the served bundle is current (`web.static` only asks whether `index.html` exists and is non-empty). The question is whether `web/` moved since the stamp, not whether HEAD did, so the check runs a `diff --quiet <stamped> HEAD -- web/` through git. It needs git and is therefore **probe-gated**, answering `SKIP` without one. The image build sets no `ISTOTA_BUILD_SHA`, so a stack's bundle carries a timestamp and the check is **skipped** there, as it is for a wheel install and a developer's own `npm run build`; a stamp the checkout cannot resolve skips too. A mismatch is a **WARN**. On the stack the bundle is built into the same image as the code, so it cannot trail it.

**The image names the commit it was built from.** `.dockerignore` keeps `.git` out, so `build_info` has no checkout to read inside a container. `istota-stack`'s `compose()` exports `ISTOTA_BUILD_REVISION` (the checkout's HEAD) and `ISTOTA_BUILD_TAG` (`ISTOTA_TAG`) whenever a caller set `ISTOTA_TAG`, which every build path does with the checkout at that commit; the Dockerfile keeps both as `ENV` and OCI labels, last, so a new commit invalidates no earlier layer. `build_info.version_label` falls back to them: plain for a `v<version>` build, `<version>+<sha7>` otherwise, so a `main-<hex>` deploy no longer reads as the last release. A plain `docker compose build` sets neither and keeps the plain version.

**gh and glab come from the vendors' release `.deb`s**, sha256-verified per architecture and extracted rather than installed, not from the Debian archive, which ships versions far behind the pins. The version and digests are named in `docker/istota/Dockerfile` and `docker/devbox/Dockerfile`; `tests/test_docker_forge_clis.py::TestTheTwoImagesAgreeOnVersions` holds them equal, so bump them together. There is deliberately **no** version floor for these two: any floor true of the verbs the skill uses is also cleared by the archive versions, so it caught nothing. The cost: nothing stops the pins being edited *down* together.

**Default Talk rooms.** `general` / `logs` / `alerts` are provisioned per user by `istota nextcloud provision-rooms` (`src/istota/rooms/provision.py`), as group rooms (`roomType=2`, invite-only), since `#logs` carries the verbose execution log and `#alerts` carries confirmations and security alerts. The entrypoint runs it for the first admin when Talk and Nextcloud are configured; for anyone else it is run through the VM's `istota` wrapper after `istota user ensure`, so a pinned `log_channel` / `alerts_channel` is already in the row. A channel room whose column is set is not created, and a column is seeded only for a room that run made usable, so a rerun cannot refill a channel the user cleared (the ISSUE-102 shape).

- **Matched by remembered token first, by display name only on a first provision** (ISSUE-342). The name belongs to the user; renaming `general` to `#general` (the web UI propagates it to Talk) used to make every run mint a second room. The token goes in the reserved `_provisioned_rooms` `istota_kv` namespace. `general` was the reliable victim because `pending_channel_rooms` drops `logs` and `alerts` once their profile columns hold a token, and `general` has no column. Reusing a remembered room is never `seedable`, so the cleared-channel rule holds.
- **A failed invite leaves a bot-only room**, which the next run adopts and retries rather than duplicating. On the remembered-token arm that retry is gated on the recorded outcome (ISSUE-408), because a user who leaves their own `general` leaves the identical state and was dragged back on every run. The record carries `invite_failed` beside the token; only a recorded failure is retried. The name-matching arm is unchanged. A pre-ISSUE-408 record has no outcome and reads as "no failure", so a stranded pre-upgrade room prints `user not a member`; clearing its `_provisioned_rooms` key puts it back on the name arm. A run that observed nothing (an empty participant read, treated as a failed read) carries the previous outcome forward, or one transient Talk error would disable the retry permanently.
- The bash room provisioning the old entrypoint did (with its `CHANNEL.md` seed and `#alerts` intro, which the CLI never did, ISSUE-115) is gone.

## Docker

`docker/docker-compose.yml` brings up nginx (the only published listener, in the ingress mode `INGRESS` in host.env names), daemon and web (a multi-stage Dockerfile builds the SvelteKit frontend; separate daemon and web services, the web process also serving the webhook receiver's routes (`webui/stack_app.py`)). It ships no Nextcloud (the one-deployment-shape spec's Stage 4): storage is local (`/data/workspace`) unless `[nextcloud] url` is set, and then the workspace is the VM's rclone mount bound at `/mnt/shared` (`rslave`). The old bundled services live on only as the full test tier's fixture, `testbed/compose/nextcloud.yml`, with `provision-nc.sh` beside it; `docs/deployment/moving-the-bundled-nextcloud.md` is the upgrade path. The image installs `bubblewrap` + `tmux`, plus `gh` and `glab` from pinned release `.deb`s, sha256-verified per architecture and extracted to `/usr/local/lib/istota_forge/`, off PATH so the policy wrapper is what a task reaches; `[developer] gh_bin_path` / `glab_bin_path` override the location.

**The config is an input, written once** (the one-deployment-shape spec's Stage 3). `istota setup`, run inside the image as uid 10001 (`istota-stack setup` on the VM; by hand `ISTOTA_CONFIG_READ_ONLY=false docker compose run --rm --no-deps --entrypoint istota-drop daemon istota setup --vm-dir /vm`), writes `/data/config/config.toml`, `/data/config/admins` and `/data/.secret_key` (0600, never replaced). With `--vm-dir` it also updates the stack's `.env` (keeping every line it does not own) and `host.env`, and writes one file per credential under `secrets/`, 0400. The entrypoint reads the config and never writes it; nothing renders it from the environment, and `render-config.sh`, `ISTOTA_CONFIG_RENDER`, `config.toml.prev`, `.api-provisioned` and the `.config-current` readiness flag are gone. An existing install's rendered `config.toml` is kept as the operator's file (`tests/image/test_upgrade.py::TestTheNewEntrypointKeepsARenderedConfig`). `docker/istota/config-diff.py` stays in the image as a one-time comparison tool. The container half of the wizard and its tests are `setup_wizard.run_container_setup` and `tests/test_setup_container.py`; the standalone half was deleted (`.claude/rules/install.md`).

**Credentials are compose secret files**, never `environment:`. `docker-compose.yml` declares `setup_wizard.SECRET_NAMES` (held equal by a test), each a file under `${ISTOTA_SECRETS_DIR:-./secrets}`, and every service built from the image mounts them all. Compose refuses to start a service whose secret file is missing, so the wizard writes every one, empty when unused, and a stack directory needs them present before the first `docker compose run`. `istota-drop` execs `istota-secrets` after the drop, which exports each non-empty `/run/secrets/<name>` as the uppercase variable (`istota_nextcloud_app_password` becomes `ISTOTA_NEXTCLOUD_APP_PASSWORD`, an existing `load_config` override) and refuses with exit 78 on a file uid 10001 cannot read. So the daemon, `web`, the healthcheck and an operator's CLI call all see the same credentials, and `docker inspect` sees none (parity row 12, `tests/image/test_secrets_contract.py`, control `scripts/test-image-negative-control.sh secrets`). Compose does not apply a secret's uid or mode outside Swarm; the 0400 and uid 10001 come from the writer.

**The rule covers every installation credential `Config` reads.** `config_editor.reference.INSTALLATION_CREDENTIALS` maps each credential's config path to its secret file, and `NOT_CREDENTIALS` lists the paths the redaction predicate (`admin_config_view.is_secret_path`) flags that are not credentials, each with a reason. `tests/test_installation_credentials.py` walks the whole `Config` type tree, `servarr.apps` included, and fails on a flagged path in neither list, so a new credential field needs a `SECRET_NAMES` entry (and the compose, role and `role_vars` names held equal to it) or a `NOT_CREDENTIALS` reason. The redaction predicate stays broad on purpose; the guard needs the exact list. A credential still inline in `config.toml` keeps working: doctor's `security.inline_credentials` warns, and Admin > Configuration moves it into its file on the host.

**The entrypoint** (`docker/istota/entrypoint.sh`, under 250 lines) refuses with 78 when there is no config, resolves the master key (`ISTOTA_SECRET_KEY` from a secret, else `/data/.secret_key`, else a new one; an empty file is a refusal) and the web-only token key, runs `istota init`, ensures the first id in the admins file only when `user_profiles` is empty, runs `istota nextcloud provision-rooms` for that admin when Talk and Nextcloud are configured (best-effort), writes Claude Code's credentials file from `CLAUDE_CODE_OAUTH_TOKEN`, and execs the scheduler from the venv. `web` depends on `daemon` being healthy, which closes the window in which `web` served an unmigrated database.

The image has no `USER` directive, and the daemon does not run as root. The `daemon` service starts in a short root phase (`docker/istota/root-phase.sh`): it refuses a cgroup2 mount not rooted at `/` and a cgroup namespace that is not its own (its `/proc/self/cgroup` must read `0::/`, which `cgroup: host` does not), remounts the container's own cgroup read-write and delegates it to uid 10001 (`ISTOTA_TASK_CGROUP_ROOT`), re-execs itself through `setpriv --bounding-set=-sys_admin` with an `--after-remount` flag so it cannot loop (logging `CapBnd` and refusing with 77 if bit 21 is still set), hands `/data` to 10001 once (`/data/.ownership-10001`), checks that bwrap can build a namespace as 10001 (exit 78 with the compose lines to add if not), and execs `istota-drop`, which empties every capability set. `CAP_SYS_ADMIN` is held for the remount alone and never while uid 0 walks the tree 10001 wrote: with it, a bug in the walk could mount a fresh procfs and reach the sysctls AppArmor denies only at their literal paths (the profile refuses a bind or move out of `/proc` and `/sys`, but not a fresh procfs, which bwrap needs; parity row 20; smoke witness `TestTheRootPhaseWalksDataWithoutSysAdmin`, control `Dockerfile.no-sys-admin-drop`). `docker compose exec` does not inherit the drop, so every exec path (the healthcheck, the testbed, an operator's CLI call) goes through `istota-drop`; `web` has no root phase: its entrypoint is `istota-drop` itself, with `cap_drop: [ALL]`, only `SETUID`, `SETGID` and `SETPCAP` (what the drop needs), `no-new-privileges`, `read_only` with a `/tmp` tmpfs, and `ISTOTA_CONFIG_PATH` in place of the old `/app/config` link. The session cookie is `Secure` unless `ISTOTA_WEB_INSECURE_COOKIES=1`, which compose defaults to 0. The wizard and the management role derive it from the ingress on every run: 1 for `local`, which is plain http on loopback where Secure protects nothing and Safari and WKWebView (the Mac app) drop the cookie, and 0 for every other mode, so a move off `local` writes 0 again. The testbed sets 1 because its httpx client sends a Secure cookie over https only. The run contract on the service is in `docker-compose.yml` with its reasoning, and `tests/test_container_security_profiles.py` holds both profiles to the Docker defaults they were derived from. The stack `.env` carries stack-level settings only (`COMPOSE_PROFILES`, `DOMAIN`, `ISTOTA_SECRETS_DIR`, `NGINX_PUBLISH` / `NGINX_PUBLISH_TLS`, `ISTOTA_WEB_INSECURE_COOKIES`).

**The entrypoint's preflight refuses five configs before it writes anything** (exit 78): one naming `http://nextcloud` when no such host resolves (an install that ran the bundled Nextcloud); a workspace that is not on the mount the host provides, which is `fuse.rclone` in full Nextcloud integration (a URL and `workspace_mount_path`) and otherwise whatever `ISTOTA_WORKSPACE_FSTYPE` names (parity row 9's container half; `ISTOTA_TESTBED_SHARED_VOLUME_WORKSPACE=1` is the full tier's concession, set only by its fixture, which narrows it to "a mount point of its own"); a host folder (`ISTOTA_WORKSPACE_MARKER_REQUIRED=1`) without `.istota-workspace` at its root, or a config with no `workspace_mount_path` to use it (row L1); the reverse of row 9, a URL and a workspace on the rclone mount without `workspace_mount_path`, which would run as a local workspace with the mount checks off (doctor's `runtime.workspace_mode` FAILs it too); and, in `direct` or `proxied` ingress, a `[site] hostname` that is not the stack's `DOMAIN`. The two variables come from `istota-stack`, by host.env's `STORAGE` (`nextcloud` gives `fuse.rclone`, `host-folder` gives `virtiofs` and the marker), and compose passes both to daemon and web; a stack started any other way sets neither and keeps the rclone rule alone. A `workspace_mount_path` with no type named and no Nextcloud URL is refused too, because a bind of a plain host directory is a mount point as well: that is host.env saying `STORAGE=local` beside a host folder's config, the state in which the vm tier once had a daemon write a workspace into the rclone mount's empty mount point. Doctor's `runtime.mount_liveness` and `db_backup`'s guard apply the same rule (`lib/workspace_marker.undeclared_mount`); a developer's own mount names its type in `ISTOTA_WORKSPACE_FSTYPE`. A URL with a local workspace (no `workspace_mount_path`) has no mount to check, so a host.env still saying `STORAGE=nextcloud` beside it is not refused. `daemon` and `nginx` both read `host.env` through `env_file` (`required: false`, so a stack without one is `local`).

**nginx** renders its configuration at start from `docker/nginx/` through `istota-ingress.sh` (mounted into the stock image's `/docker-entrypoint.d/`): the mode's server blocks (`listen-local.conf`, `listen-proxied.conf`, `listen-direct.conf` with `direct-http.conf` and `tls.conf`) around the one location template, `istota.conf.template`, which includes `root-locations.conf` (`/` to the web UI, 404 for the rest), or `root-locations-site.conf` when compose sets `ISTOTA_SITE=1`: host.env's `SITE_DIR`, which `istota-stack` passes as `ISTOTA_SITE_DIR` only when it overlaps nothing the stack writes, mounted read-only at `/srv/site` on nginx alone (#804; `ISTOTA_NGINX_ROOT_LOCATIONS`, the full tier's fixture, wins over both). `tests/image/test_nginx_operator_site.py` serves it from the real image. In `direct` with no certificate yet only the port-80 server is rendered. `tests/image/test_nginx_ingress.py` runs `nginx -t` on every mode with both root variants; doctor's `web.tls` is the runtime check for `direct`. While `web` is down (an update, a crash) nginx answers `/istota/` with `starting.html` as a 503 carrying `X-Istota-Upstream`, which the page polls until it is gone; an error the app sends itself passes through, and `/webhooks/` keeps the plain 502. The page inlines the sigil and copies the login page's tokens, held by `tests/test_nginx_starting_page.py`; `tests/image/test_nginx_starting_page.py` runs it in the real image.

## The dedicated VM: host/ and istota-stack

The one deployment shape's host half (the one-deployment-shape spec, Stage 6). `host/provision.sh` turns a fresh Debian 13 machine into one install, idempotently (Docker Engine from Docker's repository, the userns sysctl, zram, the journald cap, the auditd bound) plus what the stack needs: `userland-proxy: false` in `daemon.json` (nginx must see the client's address for the proxied allow list), a host user at uid 10001, the `/srv/app/istota` layout, the Nextcloud mount point outside it at `/srv/mount/nextcloud/content` (the bare-metal installs' path; `ISTOTA_MOUNT_DIR` overrides it for the tests), `allowed_signers` from `RELEASE_SIGNING_KEY`, the AppArmor profile, and every `host/` unit. Under the offline rule (`apt_install`) it installs a package only when missing and never upgrades one, so on a server Docker Engine and containerd.io (runc) move only with the operator's own upgrades, since Debian's unattended-upgrades defaults name no origin but Debian's. The local VM turns unattended-upgrades on and adds `51istota-docker-upgrades`, an `Origins-Pattern` for Docker's repository matched on origin, label and suite (`o=Docker,l=Docker CE,a=${distro_codename},c=stable`), because Docker's `Release` file carries no `Codename`. Whether a server keeps the offline rule is undecided. Units read `/srv/app/istota/host.env` through `EnvironmentFile`, so nothing in `host/` is a template. `tests/test_host_units.py` holds what can be held without a VM; running the script is Stage 7's vm tier. `host/lima/istota.yaml` provisions from a verified release tag (`ISTOTA_TAG`, `RELEASE_SIGNING_KEY`, carrying the third byte-equal copy of the tag check) or from a read-only mount of a Mac checkout (`ISTOTA_REPO`); its two mounts, the checkout and the `WORKSPACE` folder, are all that may cross from the Mac (row L3), and a VM that uses one drops the other at create with `--set`, since Lima refuses an empty mount location. `host/cloud-init.yaml` verifies the release tag before running anything from it; an empty `TAG` there means the newest release. **The project's release key is `host/release-signing-key.pub`**, the one authoritative copy: `install.sh` and the Mac's `istota-stack` carry it as `DEFAULT_SIGNING_KEY`, cloud-init's `host.env` as `RELEASE_SIGNING_KEY`, and the management role as `istota_release_signing_key`'s default, all held equal to it by `tests/test_host_units.py::TestTheProjectReleaseKey`. `install.sh --server` uses the key `host.env` records over the default and refuses a different explicit one. `newest_release_tag` is authoritative in `host/istota-stack` (between `# --- newest release ---` markers) and copied into `install.sh`, the Mac script and cloud-init, held byte-equal by `TestNewestReleaseTag`; it uses `sort -t. -k1,1n -k2,2n -k3,3n`, since macOS's sort has no `-V`.

**`ansible/` is the optional management role for an estate-managed VM** (the one-deployment-shape spec, Stage 8a; it replaced the bare-metal role that lived in `deploy/ansible/`). It writes `host.env`, the `.env` keys `istota setup` owns, one secrets file per `SECRET_NAMES` entry, `rclone.conf`, `config/admins` and an `istota apply` plan from variables, then calls `provision.sh`, `istota-stack update` (in `istota_update_mode: release`, only when `istota_release` differs from `ISTOTA_TAG`; in `latest`, `update --unsigned latest` only when `istota-stack latest-tag`, a read-only `ls-remote`, names a different `main-<hex>`, since an update always rebuilds; `istota_update_force` runs it regardless, and `--tags istota_update` runs only the update, its checks and the health wait; `latest` needs no signing key, and the post-apply rebuild passes `--unsigned` for a tag `.env` marks unsigned) and `istota-stack apply` (`--dry-run` under `--check`). The application settings go through `istota-stack apply --input-format role-vars` in two parts, each a private 0600 envelope removed in an `always`: the config before `check-image` (the stack cannot start without it), and the user settings after the health wait (they need the database the entrypoint's `istota init` makes). The user settings are schema-checked before the config is written, with `istota-stack apply --check --json` on a third envelope of their own (`apply --check` reads no config and no database), so a refusal in them fails the play with nothing written; that check runs under `--check` too and is never a change. Each credential goes with its section, so a value with nowhere to land reaches apply and is refused. `istota_plan` is the only application-settings input; an assert before the first change refuses `istota_plan_secrets` or a prune flag without it. No apply task notifies the restart handler: `istota-stack apply` restarts once from the result document, and a refusal is reported from that document's error codes. When user settings follow, the config apply passes `--no-restart`, which records the restart in `.restart-owed` rather than taking it, and the user settings apply takes it with its own, so a play changing both restarts once (#741); a second health wait follows that apply. The record is a file so that a play failing in between leaves the restart to the next apply: any apply without the flag takes an owed restart, except `--check`, a dry run, a partial apply or one whose exit contradicts its result, and a successful `restart_for_config` clears it, as does finding the stack down. A stopped stack owes nothing, since it starts on the config as written. Nothing before the user settings needs the restart: `check-image` and a rebuild read `config.toml` from disk, and the user settings apply is a one-shot container. Two consequences: a config the entrypoint refuses is now found by the second health wait, after the user settings are written, rather than by the first; and a play that also rebuilds the image still restarts twice (the update's recreate, then the owed restart), as it did before. The ensure loops are gone. It renders no unit and builds nothing, and it refuses a VM with no verified checkout, leaving the first verification to `cloud-init.yaml`. Three rules it holds. It writes nothing below `config/` or `secrets/` as root: those go through `istota-stack put-files`, which drops to 10001 (`setpriv`) before it opens a file and replaces a link rather than following it, with the values as JSON on stdin. It provisions when `provision.sh --digest` (host.env, rclone.conf, `.env`'s `COMPOSE_PROFILES`, the checkout's commit) differs from `.provisioned`, which only a successful `provision.sh` run writes, so a play that dies partway still provisions on the next. And after the apply it runs `istota-stack check-image` and rebuilds the deployed tag on exit 2, because a build reads `config.toml` to decide whether Claude Code goes in and the first update runs before the config exists. No secret is on an argv (only the envelope's path is), and `tests/test_management_role.py` requires `no_log` on every task whose arguments carry one. Its contract is name lists, so `tests/test_management_role.py` reads them from both sides: secrets against `SECRET_NAMES`, `host.env` keys against `provision.sh`'s documented header and every `host_env`/`env_get "$HOST_ENV"` lookup, the `.env` keys and their per-mode values against `stack_env_values` and `nginx_publish`, and the verbs against `istota-stack`'s dispatch. A new `host.env` key goes in `provision.sh`'s header and the role's `istota_host_env` together.

**`istota-stack` is the VM's one command** (`update`, `rollback`, `setup` and `setup --web`, `setup-code`, `setup-cancel`, `apply`, `put-files`, `config-apply`, `import-bare-metal`, `localize-workspace`, `up`/`down` for `istota-stack.service`, `exec`, `compose`). It runs the checkout's own compose file at `/srv/app/istota/src/docker/docker-compose.yml`, so the compose file, the seccomp and AppArmor profiles and the images always come from the same tag, and passes the VM's own paths (`ISTOTA_SECRETS_DIR`, `ISTOTA_CONFIG_DIR`, `ISTOTA_DATA_DIR`, `ISTOTA_MOUNT_DIR`, `ISTOTA_HOST_ENV`, `CERTS_DIR`, `ACME_WEBROOT`) in the environment, which outranks `.env`. It also sets `ISTOTA_LOG_DRIVER=journald`, which every service's `logging: *logging` reads, so container output reaches the host journal with `CONTAINER_NAME` (#712); the compose default is `json-file` because Docker Desktop has no journald and refuses to start a container on that driver. The devbox services keep their own rotated `json-file`. The daemon and web run `istota:${ISTOTA_TAG}`, the other images are `istota-<name>:${ISTOTA_TAG}`, all built on the VM; nothing is pulled from or pushed to a registry. **The daemon's compose service is `daemon`**, so containers read `istota-daemon-1`, `istota-web-1`; no service sets `container_name` but the browser, so a second compose project on the host stays possible. Releases before the rename called it `istota` and built `istota-istota:<tag>`: `update`'s `up -d --remove-orphans` removes the old `istota-istota-1`, the state is not keyed by the service and carries over, `rollback` tags a pre-rename `istota-istota:<tag>` as `istota:<tag>` before its schema check, and `main_service` reads the checked-out compose file so `exec`, `setup` and `apply` name whichever service that release has.

- **`update <tag>` is release integrity (parity row 13).** It refuses a name that is not a tag, a lightweight tag, a tag object without an SSH signature, one whose own `tag` header differs from the ref (a downgrade by moving refs), and a signature `git verify-tag` does not accept against `allowed_signers`. The git calls set `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1` and switch OpenPGP and X.509 verification off, so nothing the operator's own keyring trusts counts. A failed build puts the checkout back; `.env` (`ISTOTA_TAG`, `ISTOTA_PREVIOUS_TAG`) is written only after a good build, then `up -d`. The previous tag's images are kept, older `istota` and `istota-*` images (`istota-istota` included) removed. Before building, after success, and through an EXIT trap on failure, update prunes dangling images with `com.docker.compose.project=istota` and unused default-builder cache toward 2 GB (`docker builder prune --all --force --keep-storage 2GB`). Core and devbox builds explicitly use that default builder; its cache is shared, so other builds may lose cache too, but their images and volumes stay. Exit cleanup reads the retained pair from `.env`, so a failed build keeps both old deployment tags and discards incomplete candidate tags. Cleanup warnings preserve the update result. The success path cleans before `exec`-based reprovisioning and clears the trap. Unlabeled dangling images are untouched. `tests/test_stack_build_cleanup_docker.py` proves reclamation in a disposable Docker daemon, including same-tag rebuilds and starting the previous image after cleanup. Witness `tests/test_istota_stack.py`, controls `scripts/test-stack-negative-control.sh`. **Only releases are signed**: `update --unsigned <tag>` installs any tag, annotated or lightweight, without the signature checks, for that run only. A branch or a bare commit is still refused, since rollback needs a name that stays put. `.env` marks such a tag (`ISTOTA_TAG_UNSIGNED`, carried to `ISTOTA_PREVIOUS_TAG_UNSIGNED`), and `rollback` returns to a marked tag without verifying it; an unmarked previous tag is verified as a release. An unsigned tag needs no `allowed_signers` at all. **`update --unsigned latest` follows main without tags**: it fetches `origin/main`, deploys its tip and records it as `main-<first 12 hex>`, which names that commit for good, so `rollback` and the per-name image tags work as for a tag. A `main-<hex>` name resolves only to a commit that is an ancestor of `origin/main`, so it is no route to an arbitrary commit, and `latest` without `--unsigned` is refused. A deployment tracking main is updated with that command after each merge; nothing is tagged for it. **`update` with no tag** fetches as usual, takes `newest_release_tag` of the checkout's tags (the highest `vX.Y.Z` by number) and exits 0 without building when `.env` already names it with `ISTOTA_TAG_UNSIGNED` empty; otherwise it is `update <tag>`. A newest tag that fails verification is refused with 65, never replaced by an older one. `update --unsigned` with no tag stays a usage error. `TestUpdateToTheNewestRelease` holds it. The cloud-init bootstrap has no such path: a first provision is always from a verified release.
- **The rest of an update is run by the release's own `istota-stack`.** The installed script fetches, resolves and verifies the tag and checks it out; `hand_update_to_release` then execs the checkout's `host/istota-stack update-from-checkout <tag> <unsigned> <before> <commit>` under the same `$BASH`, with `ISTOTA_STACK_UPDATE_HANDOFF=1` and the lock held through descriptor 9, and that script builds, renders the devbox file, writes `.env`, starts the stack and provisions. Before it, every step after the checkout ran the previous release's code, so a change to any of them reached a host only on the update after: on zorg the old script rendered the devbox file without `--state-dir`, the new compose file mounted no such volume, the start failed, provision never ran, and the next update ran the old script again. `update-from-checkout` refuses without the variable and the inherited lock, and on a checkout that is not the verified commit. A checkout script without the `ISTOTA_STACK_UPDATE_HANDOFF` marker (an older release) is finished by the running script, as before. A start that fails still provisions the host (`provision.sh` installs the release's script) and then fails the update; `stack_up` re-renders a non-empty devbox file before every start, so the file always matches the script starting the stack. `TestTheReleasesOwnScriptBringsTheStackUp`, `TestAnUpdateReprovisionsTheHost` and `TestTheStateDirectory` hold all three. The installed script is still the one that runs the handoff, so a host whose installed script predates it takes one update, or a hand-run `provision.sh`, to get it.

After the switch it reprovisions the host by `update`'s rule (below), from the checkout it returned to (ISSUE-710). It also warns, naming the files, about every secret file the outgoing compose file declared, the older one does not, and that holds a value: the file is kept, but the older release exports nothing from it (ISSUE-768). `update` to an older tag warns the same way, from the running script before the handoff, since the older release's script has no such check.

Installs from before the directory kept the state in the volume `istota_istota_data`; the one-time copy that moved the two that existed was removed once both had moved, so a VM still on the volume needs the copy done by hand.

## Host memory headroom

Robustness spec, Track A. `provision.sh` installs `systemd-zram-generator`, writes `/etc/systemd/zram-generator.conf` and starts **`dev-zram0.swap`**: compressed in-RAM swap, zstd, `swap-priority=100`, `zram-size = ram / 2`. With no swap the kernel cannot evict anonymous pages, and tmpfs/shmem is swap-backed, so cold shmem became unreclaimable and the host thrashed. zram rather than a disk swapfile because the disk was already saturated. `ZRAM_ENABLED=0` in `host.env` skips it, so an operator with other swap is not fought; it does **not** tear down a device an earlier run created.

**Two units, and the wrong one is a no-op.** `systemd-zram-setup@.service` is a static template from the package: it creates `/dev/zram0`, sets `disksize`/`comp_algorithm` and `mkswap`s, and never calls `swapon`. `dev-zram0.swap` is synthesised by the *generator* and activates swap; its `Requires=`/`After=` pull in the setup service, never the reverse. The generated unit has no `[Install]`, so there is nothing to enable: persistence comes from the generator recreating the `swap.target.wants` symlink on every reload and boot, which is why the script runs `daemon-reload` before it starts the swap unit.

**Geometry changes need stop, rebuild, start, in that order.** A live zram0 keeps its size and algorithm until torn down. Restarting *only* the setup service is worse than nothing: `Requires=` propagates the stop to `dev-zram0.swap` and nothing propagates the start back, so swap goes to zero until reboot.

**Sizing.** `zram-size` is the *uncompressed* logical capacity. `ram / 2` on a 7.9 GB box is a ~4 GB device costing ~1.3 GB of RAM at 3:1. 4 GB is kept deliberately: it covers the 4.6 GB of cold shmem that killed the host, and the incompressible worst case commits only 4 GB of 7.9.

`provision.sh` also caps the journal (`SystemMaxUse=500M`) and bounds auditd's logs. The stack sets no unit-level memory limit: the per-task cgroups under the daemon's delegated subtree (sandbox.md) are the limit that matters.

## The local VM's host folder

`STORAGE=host-folder` is the local VM's workspace (the local-VM spec): a folder on the Mac that Lima shares in with virtiofs at `/srv/mount/host-folder`, bound at `/mnt/shared` like the rclone mount, with `workspace_path` and `workspace_mount_path` both `/mnt/shared` and no Nextcloud URL (`istota setup --storage host-folder`, kept on a re-run without the flag). `mount_dir_for_storage` is the directory rule, carried by both `provision.sh` and `istota-stack` and held equal by `tests/test_host_units.py`. `provision.sh` writes `istota-stack.service.d/host-folder.conf` (`RequiresMountsFor=`) and never creates, chmods or chowns the folder, and neither does `istota-stack setup`: a guest chmod reaches the Mac. Apple's virtiofs reports every entry as owned by whichever guest uid asks, so uid 10001 writes there with no uid layer, and the root phase's ownership walk never leaves `/data`. A folder that went away still reads as a virtiofs mount (Lima recreates a missing one empty), so `.istota-workspace` at its root is the only signal: the entrypoint refuses without it, `runtime.mount_liveness` fails, and `db_backup` neither snapshots nor copies the config there. Row L1's witness is `tests/vm/test_host_folder.py`, control `no-workspace-marker`. A lost VM comes back from the folder: `istota-stack restore` (VM verb, key on stdin, stack down) runs `istota migrate restore-workspace` in a one-shot container, and the Mac's `istota-stack restore` wraps it with `destroy` and `create --no-setup`. `update`, `setup` and `apply` copy `.env` and `host.env` into the folder's `Backups/config/<date>/` for it (`copy_stack_env_out`; `.claude/rules/maintenance.md`).

## The local VM: the Mac's istota-stack

The local run shape (the local-VM spec): a Lima VM on an Apple silicon Mac running the stack unchanged, created and controlled by `host/mac/istota-stack` (bash 3.2-safe; `tests/test_mac_istota_stack.py` runs it under `/bin/bash` with `limactl`, `security`, `lsof`, `open`, `uname`, `sysctl` and `df` as recording stubs). User docs: `docs/getting-started/local-install.md`; the trust model: `docs/deployment/security.md`, "The local VM".

- **One command name, forwarding.** The Mac script handles `create`, `start`, `stop`, `status`, `open`, `shell`, `autostart`, `allow-host-port`/`deny-host-port`, `setup`, `update`, `destroy`, `restore`, `import-standalone`, and `exec`s everything else as `limactl shell --workdir / $INSTANCE sudo istota-stack "$@"`, exit status passed through. `apply` and `import-bare-metal` take a Mac path, which goes through the VM's `stage` (a fresh root-only, or with `--daemon` uid 10001's, directory under `/srv/app/istota/staging/`) and `unstage` after. `host/mac/istota` is `istota-stack exec istota`, so it reaches `istota-drop` (row L4; control `mac-shim-without-drop`). `INSTANCE` is `istota`, `ISTOTA_LIMA_INSTANCE` overrides it, in the default `LIMA_HOME`.
- **Lima facts `create` is built on, measured (Stage 1, 5).** `cpus`, `memory` and port numbers cannot be template params (Lima parses them as numbers before expanding), so `create` passes `--cpus`/`--memory`/`--disk` and one `--set` for `.portForwards[0]`. A new VM's size comes from `size_new_vm`: the size given, else the recorded one (`CPUS`, `MEMORY`, `DISK`, so `restore` makes the same size), else an answer on a terminal, else this Mac's defaults. Those are half of `hw.ncpu` (2 to 8), a quarter of `hw.memsize` (4 to 16 GiB) and a quarter of `df`'s free space under `LIMA_HOME` (40 to 100 GiB), or the template's 4/4/40 when `sysctl` cannot be read. `create_settings` refuses more CPUs than the Mac has, or memory that leaves it under 2 GiB, before anything changes. The size is fixed at create, because both setups, terminal and web, run inside the VM. A mount location can be a param, but cannot be empty, so the template names both mounts and a release-mode `create` drops the checkout's in the same `--set` (`del(.mounts[] | select(.mountPoint == "/mnt/istota-repo"))`); `--set` cannot touch `base:`. `autostart on|off` is `limactl autostart enable|disable`, a LaunchAgent effective at the next login. Lima's DNS is the gateway, `192.168.5.2`; nothing answers at `.3`.
- **`create`** refuses before any `limactl` call: not Darwin arm64 (78), a folder in iCloud/CloudStorage, under `~/Documents|Desktop|Downloads`, `~/.istota`, `/`, the home, or containing or inside `~/.lima`/`~/.ssh` (links resolved, compared lowercased), then `limactl` < 2.0 (69), a held port (78, names the holder via `lsof`), a non-empty unmarked folder without `--adopt`. Then the folder and `.istota-workspace`, `limactl create`/`start`, `istota-stack host-env STORAGE=host-folder INGRESS=local HOST_LOOPBACK_BLOCK=1 HOST_GATEWAY_ADDR=192.168.5.2 LOCAL_FORWARD_PORT=<port>` (a VM verb, since `put-files` reaches only 10001's files and `host.env` is root's; this call writes unconditionally), `update`, then the setup: by default `web_setup` (below), after which `check-image`, `provision.sh` and `enable --now` are skipped because the VM's `setup --web` did all three, and `create` checks `systemctl is-active istota-stack` instead; with `--terminal-setup` the wizard (`setup --storage host-folder --ingress local --hostname localhost:<port>`), then `check-image` and the rebuild, `provision.sh`, `enable --now`. Then the script refresh, the key escrow and the enrolment link (which says "already has a password" after a browser setup). The skip applies only to a web setup that returned 0 in this run: a probe showing `config=1` at the start is an earlier run's, whose later steps may not have happened, so those run. An abandoned web setup fails `create` with its status and the probe still says `config=0`, so a re-run mints a new code. `--terminal-setup` is per run, not recorded; `install.sh --local --terminal-setup` passes it to `create` (kept out of `FORWARD_ARGS`, which `run_server` refuses). Release mode takes `--tag` and `--signing-key`, both optional: with no tag given or recorded (`TAG`, else a signed `DEPLOYED_TAG`) `create_settings` runs `git ls-remote --tags --refs` against `REPO_URL` (`ISTOTA_REPO_URL`, passed to the template as its param only when set) and takes `newest_release_tag` of it, and with no key it takes `DEFAULT_SIGNING_KEY`. `install.sh --local` resolves the tag the same way before `create` and passes `--signing-key` only when given one, so a key the Mac recorded wins over the default. Each step is skipped when one probe (`VM_PROBE`: tag, unsigned, config present, first admin) shows its effect, so a re-run resumes. `--no-setup` stops after provision; `restore` and `import-standalone` use it. `create`'s arguments, the public signing key included, are kept in `${XDG_CONFIG_HOME:-~/.config}/istota-stack/<instance>.env`, a directory of its own: the first version kept them in `~/.config/istota/<instance>.env`, which for the default instance is the standalone install's `istota.env`, and `create` replaced it, master key and all. That old path is still read, only when it holds nothing but `create`'s keys, and is never written. The state also records the deployed tag (`DEPLOYED_TAG`, `DEPLOYED_UNSIGNED`, read back through `VM_PROBE` after `create` and every `update`): `TAG` is only the signed release a new VM bootstraps from, and a new VM made by a later `create` or `restore` installs the deployed tag, since the VM's `update` has no schema check and an older image meets `SchemaTooNew`. On a VM that has a tag deployed, `create` updates only to a `--tag` given on that run. `restore` checks `create`'s options (source, signing key, port form, template) through `create_settings` and `require_new_vm_inputs` before the delete. `tests/test_mac_istota_stack.py` sets no `XDG_CONFIG_HOME`, so the two share `~/.config` as they do on a Mac.
- **`LOCAL_FORWARD_PORT` is the port Lima forwards** (#749), which only the Mac knows. Setup reads it from the staged host.env for its hostname default and port rule, and `setup --web --local` publishes on it. `write_forward_port` reads the VM's value with the lockless `host-env LOCAL_FORWARD_PORT` and writes only when it differs, because a write takes the stack lock and would wait up to 600 s behind a running `setup --web`; the Mac's `setup` calls it first (fixing VMs made before the key), and `restore` and `import-standalone` call it after installing a backup's `host.env`, which may predate the key or name an old port. `provision.sh`'s header documents it and the management role's `istota_host_env` carries it empty, per the host.env rule.
- **The Mac's `setup` and `web_setup`.** `setup` without `--web` writes the port and forwards. `setup --web [--force]` is `web_setup`: `require_running`, the port, then `limactl shell ... sudo istota-stack setup --web --local "$@"` as a **background job with stdin kept (`<&0`) and a `wait` loop**, output tee'd to a temp file. With a terminal on stdin limactl still gets a pty, so Ctrl-C reaches the VM; the job-plus-`wait` lets the INT/TERM trap (`cancel_web_setup`, which calls the VM's `setup-cancel`) run at once rather than after the run ends, and also means limactl ignores SIGINT locally in the no-pty case, where the trap is the only path. When stdout is a terminal a watcher reads the temp file (not `setup-code`, whose lock a stale run can hold) for the first `^ *http://localhost:N/istota/setup#code=` line, CRs stripped, then polls `/istota/api/setup/state` with `curl` until `phase` is `locked`, and only then `open`s it, so it never opens the old stack's page, which would drop the code. Its 120 s limit (`ISTOTA_SETUP_PAGE_WAIT`) starts at the address line, since backup, snapshot and stop come first. A `--local` the caller passes is dropped, since it adds its own. It returns the VM's status.
- **`status` names a port mismatch.** `VM_PROBE` adds `publish=` (the last `NGINX_PUBLISH` line of `.env`). When nothing listens on the Mac port and the probe's host port differs from the state's `PORT`, `status` says nginx publishes on the other port and names `setup --web --force` rather than blaming Lima's forward.
- **The Mac scripts follow the verified tag.** After `create`'s update and every successful `update`, `refresh_scripts` copies `host/mac/{istota-stack,istota}` and `host/lima/istota.yaml` out of the VM's checkout through a temp file and a rename, only when an install exists in `BIN_DIR` (`ISTOTA_MAC_BIN_DIR`, default `~/.local/bin`). The test is that file's existence alone, so a run from a checkout on a Mac with an install replaces the installed scripts with the checkout's.
- **Key escrow is `security -i`, read back.** The command line `add-generic-password -s istota.local -a secret-key-<instance> -w <key>` goes on `security -i`'s stdin, never an argv (asserted across every stub call). `security add-generic-password -w` with no value reads a pipe only without a controlling TTY, asks twice, and stores an empty item with exit 0 on a short read, hence the read-back. A different key already in the item stops `create` (78): it decrypts an earlier VM's snapshots. `destroy` refuses without the item unless `--force`, and, while the VM runs, when the item is not the VM's `/data/.secret_key` (read through `istota-stack exec`, compared in the shell, on no argv) or that key cannot be read; `restore` makes the same comparison before it deletes a running VM. `destroy --purge` skips those checks, since it deletes the key with the folder, and also removes the Keychain item, the folder and the state file, the state file last so a partial run is re-runnable, and with no instance left. The folder is only the state's own `WORKSPACE`, never `workspace_or_default`'s `~/Istota`, and `purge_folder_refusal` fails closed: it must print `may-delete`, and keeps the folder when the path is not already its own `resolve_dir` (a link at the leaf, a trailing slash, a link in a parent), lacks the marker, fails `refuse_location`, or overlaps a `WORKSPACE` in another state file, in either the current directory or the old `~/.config/istota/` (there only files `is_state_file` accepts). A kept folder keeps the Keychain item, which its snapshots need. An `OLD_STATE_FILE` is named and left, never removed (controls `scripts/test-stack-negative-control.sh mac-purge`).
- **The loopback block's DNS exception.** `HOST_LOOPBACK_BLOCK=1` drops forwarded traffic to `HOST_GATEWAY_ADDR` from any source in `DOCKER-USER`, with udp/tcp 53 and the `HOST_LOOPBACK_ALLOW` ports returned first, and `! -s` the devbox subnet on the returns (row L2, control `host-loopback-unblocked`). Without the port-53 return a default-bridge container (a `docker build` step) cannot resolve; compose services resolve through Docker's embedded resolver, from the VM's namespace.
- **What crosses from the Mac is the template's mount list** (row L3, control `default-mounts-in-template`): `base:` is `template:_images/debian-13`, never `template:debian-13`, which merges in `_default/mounts`, the whole home. The template names three mounts (the checkout, the workspace, and `RELEASE_DIR` read-only at `/mnt/istota-release`), and every create drops the ones its source does not share, since Lima refuses a mount with no location: a release drops the checkout and the releases, a checkout the releases, an appliance the checkout. The vm tier's `lima.py` drops the releases mount in both of its creates.
- **Appliance mode** (the Mac app spec, Stage 5): `create --appliance <releases>/<tag>` makes the VM from an unpacked release with no network. Before anything is unpacked, `require_new_vm_inputs` needs `zstd` (69) and `verify_appliance` checks `images-<tag>.json` with the Mac's own `ssh-keygen -Y verify -n istota-images` against the signing key the VM will trust, then that it names this tag and an `appliance_sha256` equal to the `.raw.zst`'s SHA-256 (65 on any of them; a missing file is 78). The VM checks the same manifest again for the images, but nothing else can check the disk it boots from. The disk is unpacked sparse (`zstd -d --sparse`) into `${LIMA_HOME}/_istota-appliance/`, given to Lima with `--set '.images = [{location, arch}]'` (a `--set` runs after the bases are merged, so it replaces Debian's downloads, which Lima would otherwise try after a failed local image; measured) and removed after `limactl create` copies it. Lima grows a raw disk to `--disk` and refuses to shrink one ("disk shrinking is not supported", Lima 2.2.1, measured), so `raise_disk_to_image` raises a smaller `--disk` to the image's size. The params are `IMAGE` (which turns appliance mode on in the template's provision) and `RELEASE_DIR`, the directory above the release, refused when it is `/`, the home or a parent of it, or holds `~/.lima` or `~/.ssh`, or overlaps the workspace. The template's provision then skips `apt-get` and the clone, fetches the tag from `/mnt/istota-release/<tag>/istota-<tag>.bundle` into the disk's checkout, verifies it with the tag-check copy and runs its `provision.sh`. `host-env` adds `ISTOTA_DESKTOP_APP=1`, the update is `update <tag> --bundle /mnt/istota-release/<tag>/istota-<tag>.bundle --images /mnt/istota-release/<tag>`, and the state records `APPLIANCE`, so a re-run, `restore` and `import-standalone` (which take `--appliance` too) make the same kind of VM; a signed `DEPLOYED_TAG` newer than the release directory's is refused (78). `update --appliance DIR` installs a later release from the same releases directory and records it. On such a VM a config that needs Claude Code gets `local-layers`, not a rebuild: the Mac's `rebuild_if_lacking`, and the VM's `build_what_setup_needs` (which also builds the Chrome layer for a browser profile), both report a failed layer and go on with the stack on the release's image. `config-apply` takes the same route through `layers_for_what_config_needs`, and refuses the request with nothing written when the layer still leaves the image lacking. Every `up` on such a VM (`stack_up`) passes `--no-build` and leaves out a service whose image is missing, since compose would otherwise build the whole browser image from source, a Chrome download that fails offline with `.env` already on the new tag; `run_local_layers` brings the stack up again once the Chrome layer exists and the browser is an active service. `--web-setup-in-app` prints `ISTOTA_SETUP_URL=<url>` once the setup page answers `locked` and opens nothing, terminal or not. The app runs the CLI with its own `XDG_CONFIG_HOME`, which already moves the state file. Row L3's appliance witness and row M11's (the first launch, to a healthy daemon, with every new outbound packet of the VM's own counted), their controls, and the builder of a release directory (`scripts/build-appliance.sh`, `scripts/release-artifacts.py`: the tag's own template, provision, `host/appliance-generalize.sh` and `scripts/sign-images-manifest.sh` in a LIMA_HOME of its own, Lima's user set to `build`, row M7's content check) live in the Mac app's repository, istota-mac. It reads every one of those istota files from the signed tag it builds, so they stay here and ship with the release.
- **Restore** is described under "The local VM's host folder" above. **`import-standalone`** stages `sqlite3 .backup` copies, the config, admins and transcripts, sends `istota.env` on stdin (every credential, not only the master key; an unknown name is refused), runs `istota migrate import-standalone` in the VM before copying the files so a refusal leaves the folder untouched, and never changes `~/.istota`; `.claude/rules/maintenance.md` has the module.
- **Owed manual runs.** A release-mode boot against a real signed GitHub release (none is SSH-signed yet), `install.sh --local` on a clean account, `security -i` against a real login Keychain, autostart across a logout, and the guest clock after a real 30-minute sleep (Lima's guest agent steps the clock from the host; measured with the clock set back, not across a sleep).

## The Mac app

The Mac app is its own project, istota-mac (a Tauri 2 shell over the Mac CLI; user docs and trust notes there, istota's half in `docs/deployment/security.md`, "The Mac app"). It pins an istota release in its `ISTOTA_VERSION`, bundles that tag's `host/mac/istota-stack`, `host/mac/istota` and `host/lima/istota.yaml`, and builds nothing from a live istota checkout. What it relies on stays here, because a release carries it and `istota-stack` verifies it: the Mac CLI's appliance mode, `update --bundle` / `--images`, `trust-signer`, `local-layers`, `local_code`, `istota setup --desktop-app`, `host/appliance-generalize.sh` and `scripts/sign-images-manifest.sh`.

- **The contract is two scripts' usage text.** istota-mac's contract test holds the app's command table (every Mac CLI verb and option it passes, the `istota` commands it runs through `exec`, the exit codes it maps) to `host/mac/istota-stack`'s and `host/istota-stack`'s usage, `EX_*` codes and `EXIT_REFUSED_TAG` at the pinned tag, and to `istota`'s own parser. Renaming or dropping a verb, option or exit code there breaks an app that pins a release with it. Keep released verbs and options working, and run that test against the change (`ISTOTA_REF`) before it is released.
- **What istota-mac loads from a tag**: `tests/vm/lima.py` (the vm-tier harness, for the appliance mode), `tests/support/parity.py` (the registry its own rows are held to, and `WITNESSED_IN_ISTOTA_MAC`), `host/release-signing-key.pub`, `src/istota/db.py`'s `SCHEMA_VERSION` line (the builder's `sed` reads it) and `web/src/lib/styles/tokens.css`. Treat their names and shapes as part of the contract too.
- **A moved or imported install becomes the app's.** The Mac CLI's `restore` and `import-standalone`, when the state records `APPLIANCE`, run the VM's `setup --desktop-app` after the restore or import and before the start (`become_the_apps`). That is `istota setup --desktop-app` in `cmd_setup`'s staging: `setup_wizard.adopt_desktop_app` adds `ISTOTA_DESKTOP_APP=1` to host.env, sets `.env`'s `ISTOTA_WEB_INSECURE_COOKIES` by `web_insecure_cookies` (the rule `stack_env_values` uses), and adds `local_code` to `[web] auth` through `apply.plan_config` (validated by loading, a backup kept). Everything else in the three files is kept, which a `setup --force` re-run would not do. A config that cannot take the codes (`none`, a hostname that is not `localhost:<port>`), or an install where `istota web login-code` with no `--user` would be refused (no database, not exactly one user with a profile, that user with no web identity; `auth.local_login_user`), is left alone with the reason printed; a non-`local` ingress or no config is a refusal, which the Mac reports as a WARNING and carries on, since the install still signs in its own way. The VM's `restore` also keeps this VM's `ISTOTA_DESKTOP_APP` over the backup's host.env, as it keeps the tag lines, because its `build_what_setup_needs` reads it first. A non-appliance restore or import is unchanged.
- **`workspace_restore` refuses a snapshot newer than its schema**, which is what holds a move from a newer command-line install when the app's release manifest is from before its `schema_version` field; the app's own check reads that field first.
- **Parity rows** M6, M7, M9 and M11 are witnessed in istota-mac (`tests/support/parity.py`'s `WITNESSED_IN_ISTOTA_MAC`), with their negative controls; L3's appliance half is too.

## Nextcloud mount

The mount is optional under Nextcloud. `istota setup` asks where the workspace lives once a URL is given (`--workspace mount|local`, default `mount`): `local` writes `workspace_path = "/data/workspace"`, no `workspace_mount_path`, `auto_share_bot_dir = false` and `STORAGE=local`, so `provision.sh` installs no rclone and Talk and the `nextcloud` skill still use the URL. `host.env`'s `STORAGE` means the rclone mount, not Nextcloud; the management role picks local with `istota_storage: local` and no `workspace_mount_path` in its plan.

**Moving a mounted install to local storage is `istota-stack localize-workspace`, offline.** It runs four `istota workspace` verbs as uid 10001 in one-shot containers, so root reads and writes nothing under `config/` or the mount: `localize-config --check` and `localize --check` first, which refuse a config `istota apply` wrote (the plan would undo the edit; that VM moves by its plan after `--copy-only`) and a non-empty destination without `--resume` before anything stops (#722); then `compose stop` of `daemon`, `web` and `whatsapp-baileys` (the room-relocation set) and `localize --scheduler-stopped`; then, on exit 0 or an accepted 2, `localize-config` with the config directory open, `moved-note` (skipped by `--no-note`, never run under `--copy-only`, a failure only a warning), `STORAGE=local` in `host.env` (`file_set`, `env_set`'s writer generalised), `provision.sh` (which waits up to 120 s, `wait_for_mount_uploads`, until no cache entry of the mount's remote is marked `Dirty`, then stops the mount; with a `dav_prefix` `RCLONE_REMOTE` is an alias and rclone keys the cache by its target, so `mount_cache_name` reads that from `rclone.conf`; without it the note stayed in the cache, #739, control `localize-stops-mount-at-once`), `cmd_up`, and `workspace reindex --forget-root /mnt/shared` through `stack_exec`. Any other exit stops with the stack down and the config untouched, which is the "re-run with `--resume`, or `up` to return to the mount" state. The copy uses the daemon service's own `/mnt/shared` bind, which is read-write, because `MOVED.md` is written there; the copier itself opens the source read-only. Rollback is `config.toml.pre-localize` plus `STORAGE=nextcloud`, `provision.sh`, `moved-note --remove`, `up` and `reindex --forget-root /data/workspace`. `tests/test_istota_stack.py::TestLocalizeWorkspace` holds the order; the copy, config edit and index cleanup are `maintenance.md`'s; `tests/vm/test_localize.py` is the vm-tier move, control `localize-without-config`. Operator doc: `docs/deployment/moving-to-a-local-workspace.md`.

In full Nextcloud integration the VM mounts the bot's Nextcloud files at `/srv/mount/nextcloud/content` with rclone (`mount-nextcloud.service`, installed by `provision.sh`), and compose binds it into the daemon at `/mnt/shared` (`rslave`). "The config directory is a host bind" above covers the unit's ordering and the pinned rclone.

## Native web login

`[web] auth` in `config.toml`, defaulting to `["nextcloud"]` even with no Nextcloud URL; `istota setup` asks. The nginx template has a no-access-log exact location for `/istota/auth/set-password`, and the web launcher disables uvicorn's access log. The sign-in forms are read with no session, so the app reads each through `read_bounded_body` at `_AUTH_FORM_BODY_LIMIT` (16 KiB) before parsing it, and nginx caps `/istota/login/email` and `/istota/auth/` at 32k rather than the upload cap (ISSUE-777); `tests/test_web_auth_deployment.py` holds every POST on `auth_router` to a capped location above the app's limit. Every request under `/istota/api/` that may carry a body (any method but GET, HEAD and OPTIONS, or one declaring a length) needs a live session before the app reads it: `webui.app._ApiBodyAuthGuard`, pure ASGI inside the session middleware, answers 401 through `_require_api_auth`, since FastAPI parses a declared body parameter before any dependency runs (ISSUE-783). The three `DEVICE_TOKEN_ROUTES` (`POST /workspace/notes`, `POST /chat/voice`, `DELETE /devices/self`) are the exception for a request carrying `Authorization: Bearer`: the guard checks that bearer as a device token, and only it, before the body, which is the check the route's `require_session_or_device` makes again. `tests/test_web_auth_routes.py` fails on a body parameter outside that prefix and on a write route under it with no session dependency, `account/password` and the device token routes being the ones that authenticate themselves. nginx buffers requests by default, so on the stack it still takes an anonymous API body up to the upload cap before the app refuses it. An outer proxy needs the same protection. The public launchers reject no-auth even when the backend binds loopback; only direct local `istota serve` may set the required in-process marker. `local_code` (the Mac app's login codes, `.claude/rules/web-ui.md`) is refused by `load_config` unless `[site] hostname` is `localhost:<port>` (not `127.0.0.1:<port>`: the app opens `localhost`, and the origin check compares the page's name with the hostname), and by the entrypoint's preflight under any `INGRESS` but `local` or unset; `web` waits on `daemon` being healthy, so that refusal keeps both down (row M1). Setup writes `["local_code", "email"]` when the staged host.env has `ISTOTA_DESKTOP_APP=1` and the ingress is `local` (`ContainerAnswers.desktop_app`, read and never written, like the forwarded port).

## Leaving the bare-metal shape

- **`retire-bare-metal --namespace NS [--dry-run]` removes what the old Ansible role installed**, after a migration: its units, crons, scripts, sysctl, journald, tmpfiles and module-load files, `/etc/NS`, `/var/lib/NS`, the service user and its home (only when that home is `/srv/app/NS`), its `NS-`-named containers, images and `NS-`/`NS_` volumes and networks, the host nginx site for `DOMAIN`, and the ufw rule commented `Docker containers (NS)`. It refuses `istota` as a namespace, while `istota-stack.service` is not active, and while any of the four app units is enabled or running. It never touches `mount-nextcloud.service` or the zram config, which the stack took over under the same names. `ISTOTA_RETIRE_ROOT` prefixes every path for `tests/test_retire_bare_metal.py`.

- **An update or a rollback reprovisions the host when its inputs changed.** `provision.sh` installs `istota-stack` itself, the units and the host scripts, so an update that never ran it left them at whatever tag last provisioned (zorg's first `retire-bare-metal` was not there). After a successful switch, `update` compares `src/host/provision.sh --digest` with `.provisioned` and, when they differ (a new release changes the digest through the checkout's commit), runs that `provision.sh` as its last step, by `exec`, because provision replaces the very file bash is reading the update from. A failed provision fails the update with the stack already on the new tag. The update itself runs the previous release's `istota-stack`, so `provision.sh` ends by running the newly installed `istota-stack up` when it replaced a different `istota-stack` and `istota-stack.service` is active: whatever the new script's `compose()` passes (the journald driver, #712) reaches the containers on the deploy that ships it. That alone recreated daemon and web twice whenever the two `compose()` functions differed, so `update` and `rollback` bring the stack up with the checkout's own script (`release_stack_up`), passing `ISTOTA_STACK_LOCK_INHERITED=1`: the child's `up` skips the lock when `flock -n 9` succeeds on the descriptor it inherited, and takes it as usual otherwise. A checkout script without that marker (an older release) would wait on the held lock, so the running script's `stack_up` is used for it, and provision's later `up` finds nothing to change. The steps that run compose without `compose.devbox.yml` set `COMPOSE_IGNORE_ORPHANS`, since the running devbox containers would otherwise draw an orphan warning on every call. Only then, because the management role provisions before its apply, and an `up` there would start the stack on a `host.env` the config does not match yet (the entrypoint refuses a `[site] hostname` that is not `DOMAIN`). A failed `up` there is a warning, since the previous script's `up` already ran. A release with no `host/provision.sh` updates as before. `rollback` ends with the same `reprovision_if_changed`, so the host's scripts and units follow the tag it returns to rather than staying at the newer one. That comparison is sound only because `provision.sh` removes `.provisioned` before it acts: a run that died after installing the newer checkout's files used to leave the older release's digest, which a rollback to that release then read as provisioned. The vm tier's update case asserts it (`TestARollbackToTheRelease::test_a_rollback_returns_the_hosts_istota_stack`, control `rollback-without-reprovision`).
