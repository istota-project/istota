# Deployment

**`istota doctor` first, on any host, before anything else.** It runs the whole check registry against the loaded config and reports each result as `ok` / `warn` / `fail` / `skip`, with a remedy on everything not `ok`; it exits 1 on any `FAIL`, 0 otherwise, and never raises. `--json` gives a machine-readable payload whose statuses are **lowercase** (the text renderer uppercases them; a consumer filtering on `"FAIL"` matches nothing, a defect this repo has shipped once). `--scope image` answers only what a bare `docker run` can, `--scope deployment` only what needs a real install; `--only <prefix>` narrows, `--deep` opts into the checks that spawn a namespace. The same run happens at daemon start-up, silent unless something is wrong, and `check_doctor` sweeps hourly, alerting each admin's `alerts_channel` on a transition into `FAIL`. A tokenless or disabled developer skill makes the `developer.*` checks `SKIP`, so "no FAIL" is not evidence the forge chain is healthy; check that the forge checks did not skip.

**The role has a tier that runs it, and it is the only thing here that does** (ISSUE-439). `scripts/test-deploy.sh` boots a Debian 13 container with systemd as PID 1 and drives the real `deploy/install.sh --headless` inside it, so `ansible-playbook` actually executes. The `tests/test_ansible_*.py` files parse the role's YAML one task at a time and cannot see an ordering (the first end-to-end run found `~/.claude` chowned to a user created later in the play, and a `defaults/main.yml` switch `settings.toml` could not reach). Discretionary and `-n0`, about three minutes; `scripts/test-deploy-negative-control.sh` keeps it able to fail. It converges with rclone, zram, Talk and the web UI off and covers no reboot ordering and no real FUSE mount; `tests/deploy/conftest.py` states each concession. **Run it when you touch `deploy/`**: the static tests cannot see an ordering, a unit systemd refuses, or a render the loader rejects.

**The supported upgrade span is `scripts/upgrade-floor`**, one hand-edited line naming the oldest release an upgrade to current main is expected to work from. `scripts/test-upgrade.sh --from-floor --shape volume` holds it: it captures that release's `config.toml` (by running that release's own `entrypoint.sh` against a two-endpoint Nextcloud stub) and its schema, boots the current image over both, and requires no `FAIL` plus a `developer.forge_config_drift` `WARN`. Bump the floor deliberately, when a migration stops reaching that far or the span stops being worth the run, and never to make a red run green without reading why. The unqualified `scripts/test-upgrade.sh` uses the merge-base with the default branch, the span the auto-update cron crosses.

**Migrations run before the units that read the new schema are restarted, and only deployment ordering says so.** `db.init_db` is the only framework migration runner and nothing on a long-running process's startup path calls it (not `get_db`, the scheduler, `web_app` or `serve`), so a process whose code names a missing column fails on its first task read (`_TASK_COLUMNS` is the SELECT list and `sqlite3.Row` raises `IndexError`). `istota-update.sh.j2` migrates before its `systemctl restart` lines, and `istota update` shells out to a freshly installed `istota init` rather than calling `db.init_db` in a process holding the old schema module. `tests/test_migration_before_restart.py` pins both. Docker is **not** closed: `entrypoint.sh` writes the config-ready flag the web container waits on before it runs `istota init`, so the web process can serve against an unmigrated database for the rest of that script. Pre-existing and left alone (`webui/app.py` documents the same window for `task_usage`); remember it when adding a column to a shipped table.

**Room identity relocation is an offline deployment step.** The role invokes `scripts/relocate-rooms.sh`, which holds the existing update flock across every stop, the migration, and restoration. The cron invokes the same wrapper with `--lock-held` because it already owns that flock. Every other role start/restart of those writers, including legacy migration restoration, web-only updates and handlers, takes the same lock so a later play task cannot reopen a writer during cron migration. After stopping every present scheduler/web/webhooks unit, the wrapper repairs ownership of the framework database and any remaining SQLite sidecars inside the same lock. A missing database or failed ownership change aborts. It runs `istota init --relocate-rooms --scheduler-stopped` in a waited transient systemd unit as the daemon user with its `secrets.env`, and restores previously running units in an EXIT trap; stop failures abort, and only exit 1 with the exact `refusal: live_tasks` line is tolerated. `--scheduler-stopped` runs the scheduler's own startup orphan recovery first: `WorkerPool.shutdown()` joins for 10 seconds and exits with an in-flight task still `running`, and with the scheduler stopped that row is an orphan, so without it every deploy that landed mid-task deferred (ISSUE-690). Only a caller that has stopped the scheduler may pass it, and nothing checks that: an `istota task -x` or `istota run` holds a `running` row without the daemon flock, and its row would be requeued and migrated under it. The database half consults the task table only while a legacy room is pending, the `repos_relocate` rule. Pending confirmations and every other refusal fail explicitly. The CLI runs schema initialization, database relocation, then the mount sweep, stopping at the first nonzero result. Standalone updates refuse a running scheduler before changing code and invoke the fresh CLI. Docker requires the explicit offline maintenance window in `docs/deployment/docker.md`; ordinary boot still cannot coordinate its sibling writers. The retained-volume upgrade test seeds a legacy room, tasks, transcript and directory, invokes this shipped command, and checks minted identity, unchanged native binding, preserved history and an idempotent sweep. Keep the temporary either-name storage reader until production reports zero outstanding; mapping and forwarding remain permanent.

## The auto-update cron

**It builds the frontend, and knows what it last finished** (ISSUE-428). `web/build` is gitignored, so the reset brings `web/` sources and not the artifact. The cron diffs `web/` between the deployed marker and the target and builds when they differ, running `npm ci` only when `web/package-lock.json` changed or `node_modules` is absent; the role does both unconditionally, right for a play and wasteful on a two-minute cron. **The build runs before the migrations and the restarts**, so a failed build leaves the previous deployment intact. The repo-wide `chown` runs before dependencies, so the build is chowned again afterwards, as the role does. Two `git diff` calls rather than one piped through `grep -q`, because the writer gets SIGPIPE'd when grep exits early and `pipefail` turns that into a failed run.

`git reset --hard` lands before anything that can fail, so testing whether the *checkout* moved let a failed run leave HEAD at the target and every later run exit 0 on a half-applied deploy. `/var/lib/{ns}/last-deployed-sha` records the sha a run got all the way through, written last, through a temp file and a `mv` in both writers (a redirection creates the target first, so a failing `git rev-parse` would leave a zero-byte marker no sha can equal). An empty marker reads as missing (`-s`, not `-f`). **The web diff is taken from that marker, never from `CURRENT`**: on a retry the previous reset has landed, so `CURRENT` is `TARGET`, a build gated on that diff would be skipped, and the run would record itself complete. A marker naming a commit the checkout no longer has (a re-clone, a history rewrite) builds rather than aborting, since `git diff` against a missing object would end every run before the migrations. A missing `npm` is logged and skipped rather than fatal, or a host that can never build would wedge the pipeline; `web.build_current` reports the bundle left behind.

**The role writes the marker too**, after `meta: flush_handlers`, or every play would be followed by a redundant cron redeploy, and **never under `istota_web_only`**. The clone task has no `when:`, so a web-only run advances HEAD while `uv sync`, the schema migration and the scheduler start are gated off; recording that as complete would make the cron's early exit fire for ever, leaving the scheduler on old code against an unmigrated database. That guard also keeps the flush ordering true, since `Force handlers to run now` is itself `when: not istota_web_only`. A **missing** marker is seeded rather than acted on: it is the state of a host the play just deployed, and reading it as stale would restart every unit on every host once for nothing. So deleting the marker does **not** force a rebuild (it is re-seeded from HEAD); the supported force is the play.

**Only one build runs against the checkout at a time, through two mechanisms.** The cron serializes against itself: `exec 200>"$LOCK"` then `flock -n 200`, taken before the `cd`, fetch, reset and build, and held for the whole process. Later ticks in a burst exit silently at the lock, and the first tick after the build deploys whatever the tip is, skipping intermediate commits. It is tested now; the rig used to stub `flock` to `exit 0`.

The cron and the **play** serialize through the same lock. The play's three mutating commands (`uv sync`, `npm ci`, `npm run build`) run under `flock -w {{ istota_update_lock_wait }}` on `/tmp/{ns}-update.lock`; without it a play's `npm ci`, which wipes `node_modules`, could run under the cron's `npm run build`, and both wrote the marker unordered. **`-w` on the play and `-n` on the cron** is the asymmetry to keep: an operator wants the deploy and can wait, while the cron's next tick is two minutes away. Exceeding the wait fails the play, which is the right loud outcome. The lock is released between the play's tasks, so a cron tick can run *between* two of them, sequentially and never concurrently; no lock survives Ansible's per-task process boundary. The lock stays in world-writable `/tmp`: a local user can pre-create and hold it, but changing the path means one upgrade window in which old and new scripts hold *different* locks and can both build, the failure this exists to prevent.

**The bundle names the commit it came from.** SvelteKit emits `_app/version.json`, and `web/svelte.config.js` stamps `ISTOTA_BUILD_SHA` into it in place of the build timestamp, so `doctor`'s `web.build_current` can ask whether the served bundle is current (`web.static` only asks whether `index.html` exists and is non-empty). **The question is whether `web/` moved, not whether HEAD did**: the cron rebuilds only on a commit touching `web/`, so the stamp trails HEAD nearly always, and an equality test would warn on every deploy. It runs `git diff --quiet <stamped> HEAD -- web/`, which needs git and is therefore **probe-gated**, answering `SKIP` without one; `probe` is True on the boot run, the hourly sweep, `istota doctor`, `!check` and the admin pane, and False only on `config.CONFIG_LOAD_CHECKS`, which this is not in. Only the role and the cron stamp a commit; a Docker image, a wheel install and a developer's own `npm run build` carry a timestamp and are **skipped**, as is a stamp the checkout cannot resolve. A mismatch is a **WARN**, since the next tick clears it.

## Ansible

Role at `deploy/ansible/` (symlinked from the operator's `ansible-server` checkout). When adding config fields, update `defaults/main.yml` + `templates/config.toml.j2`. The role runs `files/validate_config.py` against the rendered TOML before any handler can restart the scheduler, so structural bugs fail the play instead of the running daemon. Three systemd units (`istota-scheduler`, `istota-web`, `istota-webhooks`) read `ISTOTA_ADMINS_FILE` and `ISTOTA_SECRET_KEY` from the same EnvironmentFile.

**gh and glab come from the vendors' release `.deb`s**, sha256-verified per architecture and extracted with `dpkg-deb -x` into `/usr/local/bin`, not from the Debian archive, which ships versions far behind what both images pin. The version and digests are named in three files (this role, `docker/istota/Dockerfile`, `docker/devbox/Dockerfile`), because nothing shares a literal across an Ansible role and two Docker builds; `tests/test_ansible_forge_cli_install.py` holds them equal, so bump them together. There is deliberately **no** version floor for these two: any floor true of the verbs the skill uses is also cleared by the archive versions, so it caught nothing. The cost: nothing stops the pins being edited *down*, since lowering all three together satisfies the parity test. gitleaks keeps one (`istota_developer_gitleaks_min_version`, 8.19), because below it `gitleaks git` does not exist, the pre-commit hook cannot run, and every unattended agent commit is refused. That floor catches gitleaks missing from PATH and the pin edited down, not an apt 8.16 shadowing ours, which cannot happen since `/usr/local/bin` precedes `/usr/bin` on Debian's PATH. Unlike the image these stay **on** PATH, ahead of `/usr/bin`: an apt-installed `gh` from an older run may still be present, so moving ours off PATH buys nothing and breaks `gh` for an operator; the role therefore does not remove that package. After install the role runs both binaries through PATH and requires the pinned version back, because the install ends in a `copy`, which succeeds whatever the bytes are.

**Default Talk rooms on both targets.** `general` / `logs` / `alerts` are provisioned per user by whichever target is in play, both as group rooms (`roomType=2`, invite-only), since `#logs` carries the verbose execution log and `#alerts` carries confirmations and security alerts. Both run `istota nextcloud provision-rooms`: Docker from `entrypoint.sh` for the first admin, Ansible per inventory user (the command is `src/istota/rooms/provision.py`), gated on `istota_provision_talk_rooms` + `istota_talk_enabled` and run *after* `istota user ensure`, so an inventory-pinned `log_channel` / `alerts_channel` is already in the row. A channel room whose column is set is not created, and a column is seeded only for a room that run made usable, so a redeploy cannot refill a channel the user cleared (the ISSUE-102 shape).

- **Matched by remembered token first, by display name only on a first provision** (ISSUE-342). The name belongs to the user; renaming `general` to `#general` (the web UI propagates it to Talk) used to make every deploy mint a second room. The token goes in the reserved `_provisioned_rooms` `istota_kv` namespace. `general` was the reliable victim because `pending_channel_rooms` drops `logs` and `alerts` once their profile columns hold a token, and `general` has no column. Reusing a remembered room is never `seedable`, so the cleared-channel rule holds.
- **A failed invite leaves a bot-only room**, which the next run adopts and retries rather than duplicating. On the remembered-token arm that retry is gated on the recorded outcome (ISSUE-408), because a user who leaves their own `general` leaves the identical state and was dragged back on every deploy. The record carries `invite_failed` beside the token; only a recorded failure is retried. The name-matching arm is unchanged. A pre-ISSUE-408 record has no outcome and reads as "no failure", so a stranded pre-upgrade room prints `user not a member`; clearing its `_provisioned_rooms` key puts it back on the name arm. A run that observed nothing (an empty participant read, treated as a failed read) carries the previous outcome forward, or one transient Talk error would disable the retry permanently.
- Docker runs the same command now, from the entrypoint, for the first admin; the bash room provisioning (with its `CHANNEL.md` seed and `#alerts` intro, which the CLI never did, ISSUE-115) is gone.

## Docker

`docker/docker-compose.yml` brings up nginx (the only published listener, in the ingress mode `INGRESS` in host.env names), istota and web (a multi-stage Dockerfile builds the SvelteKit frontend; separate scheduler / web / webhooks services). It ships no Nextcloud (the one-deployment-shape spec's Stage 4): storage is local (`/data/workspace`) unless `[nextcloud] url` is set, and then the workspace is the VM's rclone mount bound at `/mnt/shared` (`rslave`). The old bundled services live on only as the full test tier's fixture, `testbed/compose/nextcloud.yml`, with `provision-nc.sh` beside it; `docs/deployment/moving-the-bundled-nextcloud.md` is the upgrade path. The image installs `bubblewrap` + `tmux`, plus `gh` and `glab` from pinned release `.deb`s, sha256-verified per architecture and extracted to `/usr/local/lib/istota_forge/`, off PATH so the policy wrapper is what a task reaches; `[developer] gh_bin_path` / `glab_bin_path` override the location.

**The config is an input, written once** (the one-deployment-shape spec's Stage 3). `istota setup`, run inside the image as uid 10001 (`istota-stack setup` on the VM; by hand `ISTOTA_CONFIG_READ_ONLY=false docker compose run --rm --no-deps --entrypoint istota-drop istota istota setup --vm-dir /vm`), writes `/data/config/config.toml`, `/data/config/admins` and `/data/.secret_key` (0600, never replaced). With `--vm-dir` it also updates the stack's `.env` (keeping every line it does not own) and `host.env`, and writes one file per credential under `secrets/`, 0400. The entrypoint reads the config and never writes it; nothing renders it from the environment, and `render-config.sh`, `ISTOTA_CONFIG_RENDER`, `config.toml.prev`, `.api-provisioned` and the `.config-current` readiness flag are gone. An existing install's rendered `config.toml` is kept as the operator's file (`tests/image/test_upgrade.py::TestTheNewEntrypointKeepsARenderedConfig`). `docker/istota/config-diff.py` stays in the image as a one-time comparison tool. The container half of the wizard and its tests are `setup_wizard.run_container_setup` and `tests/test_setup_container.py`; the standalone half is unchanged.

**Credentials are compose secret files**, never `environment:`. `docker-compose.yml` declares `setup_wizard.SECRET_NAMES` (held equal by a test), each a file under `${ISTOTA_SECRETS_DIR:-./secrets}`, and every service built from the image mounts them all. Compose refuses to start a service whose secret file is missing, so the wizard writes every one, empty when unused, and a stack directory needs them present before the first `docker compose run`. `istota-drop` execs `istota-secrets` after the drop, which exports each non-empty `/run/secrets/<name>` as the uppercase variable (`istota_nextcloud_app_password` becomes `ISTOTA_NEXTCLOUD_APP_PASSWORD`, an existing `load_config` override) and refuses with exit 78 on a file uid 10001 cannot read. So the daemon, `web`, `webhooks`, the healthcheck and an operator's CLI call all see the same credentials, and `docker inspect` sees none (parity row 12, `tests/image/test_secrets_contract.py`, control `scripts/test-image-negative-control.sh secrets`). Compose does not apply a secret's uid or mode outside Swarm; the 0400 and uid 10001 come from the writer.

**The entrypoint** (`docker/istota/entrypoint.sh`, under 250 lines) refuses with 78 when there is no config, resolves the master key (`ISTOTA_SECRET_KEY` from a secret, else `/data/.secret_key`, else a new one; an empty file is a refusal) and the web-only token key, runs `istota init`, ensures the first id in the admins file only when `user_profiles` is empty, runs `istota nextcloud provision-rooms` for that admin when Talk and Nextcloud are configured (best-effort), writes Claude Code's credentials file from `CLAUDE_CODE_OAUTH_TOKEN`, and execs the scheduler from the venv. `web` and `webhooks` depend on `istota` being healthy, which closes the window in which `web` served an unmigrated database.

The image has no `USER` directive, and the daemon does not run as root. The `istota` service starts in a short root phase (`docker/istota/root-phase.sh`): it refuses a cgroup2 mount not rooted at `/`, remounts the container's own cgroup read-write and delegates it to uid 10001 (`ISTOTA_TASK_CGROUP_ROOT`), hands `/data` to 10001 once (`/data/.ownership-10001`), checks that bwrap can build a namespace as 10001 (exit 78 with the compose lines to add if not), and execs `istota-drop`, which empties every capability set. `docker compose exec` does not inherit the drop, so every exec path (the healthcheck, the testbed, an operator's CLI call) goes through `istota-drop`; `web` and `webhooks` drop through it too. The run contract on the service is in `docker-compose.yml` with its reasoning, and `tests/test_container_security_profiles.py` holds both profiles to the Docker defaults they were derived from. The stack `.env` carries stack-level settings only (`COMPOSE_PROFILES`, `DOMAIN`, `ISTOTA_SECRETS_DIR`, `NGINX_PUBLISH` / `NGINX_PUBLISH_TLS`, `ISTOTA_WEB_INSECURE_COOKIES`).

**The entrypoint's preflight refuses three configs before it writes anything** (exit 78): one naming `http://nextcloud` when no such host resolves (an install that ran the bundled Nextcloud); full Nextcloud integration whose workspace is not on a `fuse.rclone` mount (parity row 9's container half; `ISTOTA_TESTBED_SHARED_VOLUME_WORKSPACE=1` is the full tier's concession, set only by its fixture, which narrows it to "a mount point of its own"); and, in `direct` or `proxied` ingress, a `[site] hostname` that is not the stack's `DOMAIN`. `istota` and `nginx` both read `host.env` through `env_file` (`required: false`, so a stack without one is `local`).

**nginx** renders its configuration at start from `docker/nginx/` through `istota-ingress.sh` (mounted into the stock image's `/docker-entrypoint.d/`): the mode's server blocks (`listen-local.conf`, `listen-proxied.conf`, `listen-direct.conf` with `direct-http.conf` and `tls.conf`) around the one location template, `istota.conf.template`, which includes `root-locations.conf` (`/` to the web UI, 404 for the rest). In `direct` with no certificate yet only the port-80 server is rendered. `tests/image/test_nginx_ingress.py` runs `nginx -t` on every mode with both root variants; doctor's `web.tls` is the runtime check for `direct`.

## The dedicated VM: host/ and istota-stack

The one deployment shape's host half (the one-deployment-shape spec, Stage 6). `host/provision.sh` turns a fresh Debian 13 machine into one install, idempotently, porting the role's host tasks with the role's values (Docker Engine from Docker's repository, the userns sysctl, zram, the journald cap, the auditd bound) plus what the stack needs: `userland-proxy: false` in `daemon.json` (nginx must see the client's address for the proxied allow list), a host user at uid 10001, the `/srv/istota` layout, `allowed_signers` from `RELEASE_SIGNING_KEY`, the AppArmor profile, and every `host/` unit. Units read `/srv/istota/host.env` through `EnvironmentFile`, so nothing in `host/` is a template. `tests/test_host_units.py` holds what can be held without a VM; running the script is Stage 7's vm tier. `host/lima/istota.yaml` provisions from a read-only mount of a Mac checkout; `host/cloud-init.yaml` verifies the release tag before running anything from it.

**`istota-stack` is the VM's one command** (`update`, `rollback`, `setup`, `apply`, `up`/`down` for `istota-stack.service`, `exec`, `compose`). It runs the checkout's own compose file at `/srv/istota/src/docker/docker-compose.yml`, so the compose file, the seccomp and AppArmor profiles and the images always come from the same tag, and passes the VM's own paths (`ISTOTA_SECRETS_DIR`, `ISTOTA_CONFIG_DIR`, `ISTOTA_MOUNT_DIR`, `ISTOTA_HOST_ENV`, `CERTS_DIR`, `ACME_WEBROOT`) in the environment, which outranks `.env`. Images are `istota-<name>:${ISTOTA_TAG}`, built on the VM; nothing is pulled from or pushed to a registry.

- **`update <tag>` is release integrity (parity row 13).** It refuses a name that is not a tag, a lightweight tag, a tag object without an SSH signature, one whose own `tag` header differs from the ref (a downgrade by moving refs), and a signature `git verify-tag` does not accept against `allowed_signers`. The git calls set `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1` and switch OpenPGP and X.509 verification off, so nothing the operator's own keyring trusts counts. A failed build puts the checkout back; `.env` (`ISTOTA_TAG`, `ISTOTA_PREVIOUS_TAG`) is written only after a good build, then `up -d`. The previous tag's images are kept, older `istota-*` removed. Witness `tests/test_istota_stack.py`, controls `scripts/test-stack-negative-control.sh`.
- **`rollback`** asks the previous image `istota init --check-schema` first and leaves `.env` alone when it answers 3 (see the schema stamp below).
- **`setup`** runs the wizard as uid 10001 with `ISTOTA_CONFIG_READ_ONLY=false`, in a staging `--vm-dir` it owns, then takes staging back (root, 0700) and installs `.env` and `host.env` with `install_staged`, which opens each `O_NOFOLLOW` and refuses anything but a plain file, so a link planted there cannot copy what root reads into `.env`; it pre-creates every secret file compose declares and copies an upgraded Docker install's `config.toml` and `admins` out of the state volume once.
- **Root acts on no file uid 10001 can write.** `config/` and the setup staging directory are 10001's, and so is anything a VM process running as 10001 (the rclone mount) touches. The devbox compose file is therefore rendered to `/srv/istota/compose.devbox.yml`, beside `.env`, and `compose` refuses it unless it is a regular file owned by the caller and writable by it alone (`require_own_file`); a copy left in `config/` by an older release is removed at the next render.
- **`apply <plan>`** runs `istota apply` in a one-shot container with the config directory open, and restarts the stack on exit 2 only (not under `--dry-run`).
- **`exec`, and the VM's `istota` wrapper (`host/istota`, which is `istota-stack exec istota`), go through `istota-drop`.** A `docker compose exec` starts as uid 0 with the cap_add set. `ISTOTA_STACK_EXEC` replaces only the `compose exec istota` prefix, for the image tier's row 5 witness (`tests/image/test_stack_wrapper.py`).

**The config directory is a host bind**, `/srv/istota/config` at `/data/config`, read-only for istota, web and webhooks (`ISTOTA_CONFIG_READ_ONLY`, default true); only `setup` and `apply` open it. In full Nextcloud integration `provision.sh` installs `mount-nextcloud.service` (rclone as uid 10001, from an `rclone.conf` the operator places) and a drop-in making `istota-stack.service` require it. In `direct` ingress with `acme`, certbot runs on the host (`host/istota-certbot`, a twice-daily timer, a deploy hook restarting nginx), and `istota-stack up` starts the first issuance. The proxied listener's `DOCKER-USER` rule lives in the egress unit, matched on conntrack's original destination.

**The schema stamp.** `db.init_db` writes `db.SCHEMA_VERSION` as `PRAGMA user_version` and refuses, before anything writes to the file, a database stamped higher (`db.SchemaTooNew`); `istota init` exits 3 with one `REFUSE` line, and `init --check-schema` answers read-only. Raise `SCHEMA_VERSION` in the commit that adds a migration an older release cannot run against. The upgrade tier's `TestAnOlderImageRefusesANewerSchema` holds the boot; its control is `scripts/test-stack-negative-control.sh rollback`.

## Host memory headroom

Robustness spec, Track A; `tags: [swap]`. The role installs `systemd-zram-generator`, renders `/etc/systemd/zram-generator.conf` from `zram-generator.conf.j2`, and starts **`dev-zram0.swap`**: compressed in-RAM swap, zstd, `swap-priority=100`. With no swap the kernel cannot evict anonymous pages, and tmpfs/shmem is swap-backed, so cold shmem became unreclaimable and the host thrashed. zram rather than a disk swapfile because the disk was already saturated.

**Two units, and the wrong one ships a no-op.** `systemd-zram-setup@.service` is a static template from the package: it creates `/dev/zram0`, sets `disksize`/`comp_algorithm` and `mkswap`s, and never calls `swapon`. `dev-zram0.swap` is synthesised by the *generator* into `/run` and activates swap; its `Requires=`/`After=` pull in the setup service, never the reverse. No `enabled:` on the task: the generated unit has no `[Install]`, so `systemctl is-enabled` answers `static` and Ansible reports success doing nothing; persistence comes from the generator recreating the `swap.target.wants` symlink on every reload and boot. **A `daemon_reload` must re-run the generators before the start task**, or a first install has no unit. Swap is live at the end of the play, and a mandatory `Verify zram swap is actually active` task asserts it against `/proc/swaps`.

**Geometry changes need stop, rebuild, start, in that order.** A live zram0 keeps its size and algorithm until torn down. Restarting *only* the setup service is worse than nothing: `Requires=` propagates the stop to `dev-zram0.swap` and nothing propagates the start back, so swap goes to zero until reboot. The rebuild is skipped when zram0 holds more than 64 MB, since `swapoff` faults every page back into RAM; a skip is surfaced by its own `debug` task, because config and device then disagree permanently and the next run will not retry.

**Sizing.** `zram-size` is the *uncompressed* logical capacity. `ram / 2` on a 7.9 GB box is a ~4 GB device costing ~1.3 GB of RAM at 3:1, not the spec's "10-12 GB effective" (that would need `ram * 1.5`). 4 GB is kept deliberately: it covers the 4.6 GB of cold shmem that killed the host, and the incompressible worst case commits only 4 GB of 7.9. The three values in `zram-generator.conf.j2` are **not nullable**: an empty value there is rejected, unlike the unit directives.

`istota_zram_enabled: false` makes every task a no-op so an operator with other swap is not fought; it does **not** tear down a device the role created earlier. An optional disk swapfile (`istota_swapfile_enabled`, default false) sits below zram at `pri=10` with `nofail`; `mkswap` is gated on a `blkid` signature probe, and the fstab entry is written only *after* `swapon` succeeds, so an interrupted run cannot leave a boot-time reference to an unformatted file.

**Unit resource limits.** `MemoryHigh` on all three units (`5G` scheduler, `1G` web/webhooks): soft throttling, never `MemoryMax`, because killing the daemon takes everything down and istota's own footprint (~1.2 GB) was never the problem. The scheduler figure covers the **whole cgroup**, every `claude` subprocess and child included, which is why the spec's 3G is too low: `memory.high` applies an allocation-time sleep penalty to every process in the cgroup, dispatch loop included, so a low figure reads as "everything slow, nothing logged". `host_pressure` reads the unit's `memory.events` counters into its breadcrumb line, which is where a throttle shows. `CPUWeight=50` on the scheduler only, below systemd's default 100 so other units win under contention; no `CPUQuota`, since PSI showed cores waiting on memory, not oversubscribed. `Delegate=memory pids cpu` **plus `DelegateSubgroup=supervisor`** and explicit `MemoryAccounting=yes` on the scheduler: cgroup v2 forbids a non-root cgroup from both holding processes and enabling controllers for children (`EBUSY`), and `Type=simple` puts the daemon in the unit cgroup, so without the subgroup a `task-<id>/` cgroup would have no `memory.max` and A6's fail-open rule would hide it. `ProtectControlGroups` and `ProtectKernelTunables` must stay unset or delegation is silently defeated; `ProtectSystem=strict` is fine, since it leaves `/sys` writable. An empty string on any of the three variables omits the directive. Covered by `tests/test_ansible_memory_limits.py`.

## Clone credential

ISSUE-258. `istota_repo_clone_token` never enters a URL. The bare token goes to `/etc/{{ istota_namespace }}/clone-token` at `0600 root:root`; `git-credential-istota.sh.j2` renders to `/usr/local/bin/{{ istota_namespace }}-git-credential`, registered as `credential.https://<repo host>.helper` at **system** scope. The clone uses the bare `istota_repo_url`. Interpolating the token into the URL made git persist it as `remote.origin.url` and expand it into `git-remote-https`' argv on every cron fetch.

**Not `store --file=`.** `git-credential-store` implements `erase`, which git calls on any 401, truncating the file: one expired or rotated token would leave the cron fetch failing silently (`MAILTO=""`) until Ansible re-ran. It also rewrites its file on successful auth, so an unrelated root git operation could swap the deploy credential, and Ansible's copy would not be idempotent. The helper answers `get` and ignores every other verb, and reads the token from a file, so rotation is one write. Host scoping keeps it from being consulted for anything else. System scope because `/etc/gitconfig` is read under any user and `HOME`; the neighbouring `safe.directory` task is at `global` scope and the cron does read that, so `global` would also work and `system` is the more robust of two.

**Only https remotes are in scope, and the guards match a password, not an `@`.** `git@host:path` and `https://oauth2@host/…` contain `@` and no secret; matching `@` would rewrite the remote every run. The remediation and the assert both test `urlsplit('password')`. `_istota_repo_host` comes from `urlsplit('netloc')` split on `@`, not `urlsplit('hostname')`, because `hostname` lowercases and git matches config subsections by exact string. A `remote set-url` ahead of the clone remediates hosts provisioned under the old shape (gated on a replacement credential being available, so a run without the vault cannot strip the only working one), and an `assert` after it fails the play if the remote carries a userinfo password. Neither prints the value; both read-back tasks carry `no_log`, since on an unremediated host their stdout is the token. Both use `check_mode: false` and `| default()` guards, since `command` is skipped under `--check`. Clearing `istota_repo_clone_token` (or using an ssh remote) removes the token file, helper and git-config entry. Covered by `tests/test_ansible_clone_credential.py`, which executes the rendered helper to hold the `erase` property.

## The devbox half of the role

`deploy/ansible/templates/docker-compose.devbox.yml.j2` is the bare-metal devbox definition, rendered per entry in `istota_devbox_users`; the stack renders its own with `istota devbox compose-file` (`devbox.md`), and both go to one shape when Stage 9 deletes the role. Two halves. The service's own shape is ungated for **every** devbox, because the image's `CMD` is the supervisor and a template saying `sleep infinity` would make the image's build-time smoke test a lie. The two mounts and the `environment:` block are gated on `istota_developer_enabled` and a non-empty `istota_developer_repos_dir`, inside the `istota_devbox_enabled` gate the file already sits behind. `istota_developer_container_backend` is retired; every `when:` that tested it also carried `istota_devbox_enabled`.

The ungated half:

- `command` is a supervisor (`istota-exec-run`), not `sleep infinity`, with `init: true` for reaping. `restart: unless-stopped` restarts the *container*, so nothing restarted the server after a dockerd restart or container OOM, and `sleep` as PID 1 never calls `wait()`.
- `init: true` covers zombies only. A backgrounded build outliving its server is running, not a zombie (ISSUE-322). What covers it is `run_reaper` in `istota-exec-serve`: a child holding the read end of a pipe the kernel closes however the server dies, SIGKILL included.
- `cap_add: [NET_RAW]` and the 1 GiB `/workspace` tmpfs are gone.
- `DEV_UID` / `DEV_GID` build args carry the daemon's own uid and gid, from a `getent passwd` lookup with an assert, so both sides of the shared mount have one numeric identity; the image defaults them to 10001, the istota image's daemon uid.
- `cap_add` and `command` were removed from `tests/test_devbox_deployment_shape.py::TestTheAnsibleServiceKeepsItsContainment`'s `REQUIRED` list, with reasons in the relinquished-keys block under it. `networks: ["devbox-net"]` stays required: a container on the project default network sits outside `istota_devbox_network_subnet`, where every `DOCKER-USER` rule the role installs is scoped.

**Two mounts, one socket directory.** The container binds `{repos_dir}/{user_id}` and `{exec_socket_dir}/{user_id}`, nothing else. The package cache is derived at `{repos_dir}/{user_id}/.package-caches`, inside the first mount; one mount covering cache and venv is the only shape where uv hardlinks a wheel rather than copying, since `link(2)` compares mounts. `doctor`'s `uv_cache` result checks that the derived directory is visible in the container. Each mount is at the same absolute path on both sides, so a working directory needs no translation. The per-user socket subdirectory is created by the play *and* declared in `istota-exec.tmpfiles.j2`, because Docker auto-creates a missing bind source as `root:root` and systemd-tmpfiles runs at boot where the play does not. It is 0770, since the container creates the socket as the daemon's uid. Only the per-user subdirectory is ever mounted: the parent holds every user's socket, which is arbitrary command execution against another user's repositories.

**The home volume's ownership is the host's job.** Docker seeds a named volume from the image only while it is empty, so a `/home/dev` created before `DEV_UID` / `DEV_GID` existed keeps uid 1000 for good. The container cannot repair itself: `istota-exec-run`'s `chown` reaches root through `sudo`, and `no-new-privileges` (daemon-wide in `/etc/docker/daemon.json` on at least one deployment) makes sudo refuse. So the role reads each volume's ownership through a throwaway root container (`:ro`, `--network none`, `docker volume inspect` first so a fresh install is not handed an empty volume ahead of its seed) and chowns only one that disagrees. A standing guard, since the divergence recurs whenever the daemon's uid changes. The in-container path asks whether root is reachable *before* trying, so a `chown -R` that died half-way and one that could never run report differently.

The layout migration is `python -m istota.maintenance.repos_relocate`, run after the code is in place and before the units restart; it assigns every namespace to the single configured admin and refuses where there are none or several, since nothing on disk records who owns a clone.

**The Docker-API proxy is retired and the role tears it down.** `istota-docker-proxy@.service.j2`, `istota-docker-proxy.tmpfiles.j2` and every `api_proxy` variable are deleted; a retirement block enumerates surviving per-user instance units, stops, disables and removes them, and removes `/var/run/{{ istota_namespace }}-docker` with its stale sockets. The path is written out rather than interpolated, because the variable that named it is gone. `tests/test_ansible_config_template.py` sweeps the role for the retired key names, so none appears even in a comment. `tests/test_ansible_docker_proxy_retirement.py` holds two fixes: the unit listing passes `--plain` (without it `awk '{print $1}'` returned systemd's status glyph for exactly the failed and not-found units being retired, and `failed_when: false` swallowed the failure), and the block calls `reset-failed` so no `not-found / failed (226/NAMESPACE)` entry is left behind.

## Native web login

`ISTOTA_WEB_AUTH` on both Docker services and `istota_web_auth` in Ansible, defaulting to `["nextcloud"]` even with no Nextcloud URL. Docker renders `[web]` unconditionally and reuses the entrypoint's persisted session secret; only OAuth fields depend on provisioning. Both nginx templates have no-access-log exact locations for the set-password and sign-in-link paths, and both web uvicorn launchers disable access logs. An outer proxy needs the same protection. The public launchers reject no-auth even when the backend binds loopback; only direct local `istota serve` may set the required in-process marker.
