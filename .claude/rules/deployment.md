# Deployment

**`istota doctor` first, on any host, before anything else.** It runs the whole check registry against the loaded config and reports each result as `ok` / `warn` / `fail` / `skip`, with a remedy on everything not `ok`; it exits 1 on any `FAIL`, 0 otherwise, and never raises. `--json` gives a machine-readable payload whose statuses are **lowercase** (the text renderer uppercases them; a consumer filtering on `"FAIL"` matches nothing, a defect this repo has shipped once). `--scope image` answers only what a bare `docker run` can, `--scope deployment` only what needs a real install; `--only <prefix>` narrows, `--deep` opts into the checks that spawn a namespace. The same run happens at daemon start-up, silent unless something is wrong, and `check_doctor` sweeps hourly, alerting each admin's `alerts_channel` on a transition into `FAIL`. A tokenless or disabled developer skill makes the `developer.*` checks `SKIP`, so "no FAIL" is not evidence the forge chain is healthy; check that the forge checks did not skip.

**The supported upgrade span is `scripts/upgrade-floor`**, one hand-edited line naming the oldest release an upgrade to current main is expected to work from. `scripts/test-upgrade.sh --from-floor --shape volume` holds it: it captures that release's `config.toml` (by running that release's own `entrypoint.sh` against a two-endpoint Nextcloud stub) and its schema, boots the current image over both, and requires no `FAIL` plus a `developer.forge_config_drift` `WARN`. Bump the floor deliberately, when a migration stops reaching that far or the span stops being worth the run, and never to make a red run green without reading why. The unqualified `scripts/test-upgrade.sh` is the same run; its old near anchor (the merge-base, the `code` shape) went with the bare-metal auto-update cron.

**Migrations run before anything reads the new schema, and only ordering says so.** `db.init_db` is the only framework migration runner and nothing on a long-running process's startup path calls it (not `get_db`, the scheduler, `webui.app` or `serve`), so a process whose code names a missing column fails on its first task read (`_TASK_COLUMNS` is the SELECT list and `sqlite3.Row` raises `IndexError`). On the stack the daemon's entrypoint runs `istota init` before it execs the scheduler, and `web` waits for `daemon` to be healthy, so neither serves an unmigrated database. `istota update` (standalone) shells out to a freshly installed `istota init` rather than calling `db.init_db` in a process holding the old schema module. A rollback across a migration is refused by the schema stamp (below). Remember the ordering when adding a column to a shipped table.

**Room identity relocation is an offline step, and nothing on the stack runs it for you.** `istota init --relocate-rooms --scheduler-stopped` runs schema initialization, the database relocation, then the mount sweep, stopping at the first nonzero result. `--scheduler-stopped` runs the scheduler's own startup orphan recovery first: `WorkerPool.shutdown()` joins for 10 seconds and exits with an in-flight task still `running`, and with the scheduler stopped that row is an orphan, so without it every relocation that landed mid-task deferred (ISSUE-690). Only a caller that has stopped the scheduler may pass it, and nothing checks that: an `istota task -x` or `istota run` holds a `running` row without the daemon flock, and its row would be requeued and migrated under it. The database half consults the task table only while a legacy room is pending, the `repos_relocate` rule. Pending confirmations and every other refusal fail explicitly; only exit 1 with the exact `refusal: live_tasks` line is a retry. On the stack the window is the procedure in `docs/deployment/docker.md` (stop `daemon` and `web`, the two room writers, plus `whatsapp-baileys`, whose in-memory hold drops inbound messages after 240 s; run the command in a one-shot `compose run --no-deps` container; `istota-stack up`). The external Nextcloud and the rclone mount stay up: the sweep moves `Channels/` over DAV and refuses when either is unavailable. `istota-stack down` would also work but stops `signaling`, which a registered HPB makes every Talk user on that Nextcloud depend on; standalone updates refuse a running scheduler before changing code and invoke the fresh CLI. The retained-volume upgrade test seeds a legacy room, tasks, transcript and directory, invokes this command, and checks minted identity, unchanged native binding, preserved history and an idempotent sweep. Keep the temporary either-name storage reader until production reports zero outstanding; mapping and forwarding remain permanent.

**The bundle names the commit it came from, when its builder says so.** SvelteKit emits `_app/version.json`, and `web/svelte.config.js` stamps `ISTOTA_BUILD_SHA` into it in place of the build timestamp, so `doctor`'s `web.build_current` can ask whether the served bundle is current (`web.static` only asks whether `index.html` exists and is non-empty). The question is whether `web/` moved since the stamp, not whether HEAD did, so the check runs a `diff --quiet <stamped> HEAD -- web/` through git. It needs git and is therefore **probe-gated**, answering `SKIP` without one. The image build sets no `ISTOTA_BUILD_SHA`, so a stack's bundle carries a timestamp and the check is **skipped** there, as it is for a wheel install and a developer's own `npm run build`; a stamp the checkout cannot resolve skips too. A mismatch is a **WARN**. On the stack the bundle is built into the same image as the code, so it cannot trail it.

**gh and glab come from the vendors' release `.deb`s**, sha256-verified per architecture and extracted rather than installed, not from the Debian archive, which ships versions far behind the pins. The version and digests are named in `docker/istota/Dockerfile` and `docker/devbox/Dockerfile`; `tests/test_docker_forge_clis.py::TestTheTwoImagesAgreeOnVersions` holds them equal, so bump them together. There is deliberately **no** version floor for these two: any floor true of the verbs the skill uses is also cleared by the archive versions, so it caught nothing. The cost: nothing stops the pins being edited *down* together.

**Default Talk rooms.** `general` / `logs` / `alerts` are provisioned per user by `istota nextcloud provision-rooms` (`src/istota/rooms/provision.py`), as group rooms (`roomType=2`, invite-only), since `#logs` carries the verbose execution log and `#alerts` carries confirmations and security alerts. The entrypoint runs it for the first admin when Talk and Nextcloud are configured; for anyone else it is run through the VM's `istota` wrapper after `istota user ensure`, so a pinned `log_channel` / `alerts_channel` is already in the row. A channel room whose column is set is not created, and a column is seeded only for a room that run made usable, so a rerun cannot refill a channel the user cleared (the ISSUE-102 shape).

- **Matched by remembered token first, by display name only on a first provision** (ISSUE-342). The name belongs to the user; renaming `general` to `#general` (the web UI propagates it to Talk) used to make every run mint a second room. The token goes in the reserved `_provisioned_rooms` `istota_kv` namespace. `general` was the reliable victim because `pending_channel_rooms` drops `logs` and `alerts` once their profile columns hold a token, and `general` has no column. Reusing a remembered room is never `seedable`, so the cleared-channel rule holds.
- **A failed invite leaves a bot-only room**, which the next run adopts and retries rather than duplicating. On the remembered-token arm that retry is gated on the recorded outcome (ISSUE-408), because a user who leaves their own `general` leaves the identical state and was dragged back on every run. The record carries `invite_failed` beside the token; only a recorded failure is retried. The name-matching arm is unchanged. A pre-ISSUE-408 record has no outcome and reads as "no failure", so a stranded pre-upgrade room prints `user not a member`; clearing its `_provisioned_rooms` key puts it back on the name arm. A run that observed nothing (an empty participant read, treated as a failed read) carries the previous outcome forward, or one transient Talk error would disable the retry permanently.
- The bash room provisioning the old entrypoint did (with its `CHANNEL.md` seed and `#alerts` intro, which the CLI never did, ISSUE-115) is gone.

## Docker

`docker/docker-compose.yml` brings up nginx (the only published listener, in the ingress mode `INGRESS` in host.env names), daemon and web (a multi-stage Dockerfile builds the SvelteKit frontend; separate daemon and web services, the web process also serving the webhook receiver's routes (`webui/stack_app.py`)). It ships no Nextcloud (the one-deployment-shape spec's Stage 4): storage is local (`/data/workspace`) unless `[nextcloud] url` is set, and then the workspace is the VM's rclone mount bound at `/mnt/shared` (`rslave`). The old bundled services live on only as the full test tier's fixture, `testbed/compose/nextcloud.yml`, with `provision-nc.sh` beside it; `docs/deployment/moving-the-bundled-nextcloud.md` is the upgrade path. The image installs `bubblewrap` + `tmux`, plus `gh` and `glab` from pinned release `.deb`s, sha256-verified per architecture and extracted to `/usr/local/lib/istota_forge/`, off PATH so the policy wrapper is what a task reaches; `[developer] gh_bin_path` / `glab_bin_path` override the location.

**The config is an input, written once** (the one-deployment-shape spec's Stage 3). `istota setup`, run inside the image as uid 10001 (`istota-stack setup` on the VM; by hand `ISTOTA_CONFIG_READ_ONLY=false docker compose run --rm --no-deps --entrypoint istota-drop daemon istota setup --vm-dir /vm`), writes `/data/config/config.toml`, `/data/config/admins` and `/data/.secret_key` (0600, never replaced). With `--vm-dir` it also updates the stack's `.env` (keeping every line it does not own) and `host.env`, and writes one file per credential under `secrets/`, 0400. The entrypoint reads the config and never writes it; nothing renders it from the environment, and `render-config.sh`, `ISTOTA_CONFIG_RENDER`, `config.toml.prev`, `.api-provisioned` and the `.config-current` readiness flag are gone. An existing install's rendered `config.toml` is kept as the operator's file (`tests/image/test_upgrade.py::TestTheNewEntrypointKeepsARenderedConfig`). `docker/istota/config-diff.py` stays in the image as a one-time comparison tool. The container half of the wizard and its tests are `setup_wizard.run_container_setup` and `tests/test_setup_container.py`; the standalone half is unchanged.

**Credentials are compose secret files**, never `environment:`. `docker-compose.yml` declares `setup_wizard.SECRET_NAMES` (held equal by a test), each a file under `${ISTOTA_SECRETS_DIR:-./secrets}`, and every service built from the image mounts them all. Compose refuses to start a service whose secret file is missing, so the wizard writes every one, empty when unused, and a stack directory needs them present before the first `docker compose run`. `istota-drop` execs `istota-secrets` after the drop, which exports each non-empty `/run/secrets/<name>` as the uppercase variable (`istota_nextcloud_app_password` becomes `ISTOTA_NEXTCLOUD_APP_PASSWORD`, an existing `load_config` override) and refuses with exit 78 on a file uid 10001 cannot read. So the daemon, `web`, the healthcheck and an operator's CLI call all see the same credentials, and `docker inspect` sees none (parity row 12, `tests/image/test_secrets_contract.py`, control `scripts/test-image-negative-control.sh secrets`). Compose does not apply a secret's uid or mode outside Swarm; the 0400 and uid 10001 come from the writer.

**The entrypoint** (`docker/istota/entrypoint.sh`, under 250 lines) refuses with 78 when there is no config, resolves the master key (`ISTOTA_SECRET_KEY` from a secret, else `/data/.secret_key`, else a new one; an empty file is a refusal) and the web-only token key, runs `istota init`, ensures the first id in the admins file only when `user_profiles` is empty, runs `istota nextcloud provision-rooms` for that admin when Talk and Nextcloud are configured (best-effort), writes Claude Code's credentials file from `CLAUDE_CODE_OAUTH_TOKEN`, and execs the scheduler from the venv. `web` depends on `daemon` being healthy, which closes the window in which `web` served an unmigrated database.

The image has no `USER` directive, and the daemon does not run as root. The `daemon` service starts in a short root phase (`docker/istota/root-phase.sh`): it refuses a cgroup2 mount not rooted at `/` and a cgroup namespace that is not its own (its `/proc/self/cgroup` must read `0::/`, which `cgroup: host` does not), remounts the container's own cgroup read-write and delegates it to uid 10001 (`ISTOTA_TASK_CGROUP_ROOT`), re-execs itself through `setpriv --bounding-set=-sys_admin` with an `--after-remount` flag so it cannot loop (logging `CapBnd` and refusing with 77 if bit 21 is still set), hands `/data` to 10001 once (`/data/.ownership-10001`), checks that bwrap can build a namespace as 10001 (exit 78 with the compose lines to add if not), and execs `istota-drop`, which empties every capability set. `CAP_SYS_ADMIN` is held for the remount alone and never while uid 0 walks the tree 10001 wrote: with it, a bug in the walk could mount a fresh procfs and reach the sysctls AppArmor denies only at their literal paths (the profile refuses a bind or move out of `/proc` and `/sys`, but not a fresh procfs, which bwrap needs; parity row 20; smoke witness `TestTheRootPhaseWalksDataWithoutSysAdmin`, control `Dockerfile.no-sys-admin-drop`). `docker compose exec` does not inherit the drop, so every exec path (the healthcheck, the testbed, an operator's CLI call) goes through `istota-drop`; `web` has no root phase: its entrypoint is `istota-drop` itself, with `cap_drop: [ALL]`, only `SETUID`, `SETGID` and `SETPCAP` (what the drop needs), `no-new-privileges`, `read_only` with a `/tmp` tmpfs, and `ISTOTA_CONFIG_PATH` in place of the old `/app/config` link. The session cookie is `Secure` unless `ISTOTA_WEB_INSECURE_COOKIES=1`, which compose defaults to 0 and the wizard writes as 0 for every ingress, `local` included (browsers treat `http://localhost` as a secure context); the testbed sets 1 because its httpx client does not. The run contract on the service is in `docker-compose.yml` with its reasoning, and `tests/test_container_security_profiles.py` holds both profiles to the Docker defaults they were derived from. The stack `.env` carries stack-level settings only (`COMPOSE_PROFILES`, `DOMAIN`, `ISTOTA_SECRETS_DIR`, `NGINX_PUBLISH` / `NGINX_PUBLISH_TLS`, `ISTOTA_WEB_INSECURE_COOKIES`).

**The entrypoint's preflight refuses four configs before it writes anything** (exit 78): one naming `http://nextcloud` when no such host resolves (an install that ran the bundled Nextcloud); a workspace that is not on the mount the host provides, which is `fuse.rclone` in full Nextcloud integration and otherwise whatever `ISTOTA_WORKSPACE_FSTYPE` names (parity row 9's container half; `ISTOTA_TESTBED_SHARED_VOLUME_WORKSPACE=1` is the full tier's concession, set only by its fixture, which narrows it to "a mount point of its own"); a host folder (`ISTOTA_WORKSPACE_MARKER_REQUIRED=1`) without `.istota-workspace` at its root, or a config with no `workspace_mount_path` to use it (row L1); and, in `direct` or `proxied` ingress, a `[site] hostname` that is not the stack's `DOMAIN`. The two variables come from `istota-stack`, by host.env's `STORAGE` (`nextcloud` gives `fuse.rclone`, `host-folder` gives `virtiofs` and the marker), and compose passes both to daemon and web; a stack started any other way sets neither and keeps the rclone rule alone. A `workspace_mount_path` with no type named and no Nextcloud URL is refused too, because a bind of a plain host directory is a mount point as well: that is host.env saying `STORAGE=local` beside a host folder's config, the state in which the vm tier once had a daemon write a workspace into the rclone mount's empty mount point. Doctor's `runtime.mount_liveness` and `db_backup`'s guard apply the same rule (`lib/workspace_marker.undeclared_mount`); a developer's own mount names its type in `ISTOTA_WORKSPACE_FSTYPE`. `daemon` and `nginx` both read `host.env` through `env_file` (`required: false`, so a stack without one is `local`).

**nginx** renders its configuration at start from `docker/nginx/` through `istota-ingress.sh` (mounted into the stock image's `/docker-entrypoint.d/`): the mode's server blocks (`listen-local.conf`, `listen-proxied.conf`, `listen-direct.conf` with `direct-http.conf` and `tls.conf`) around the one location template, `istota.conf.template`, which includes `root-locations.conf` (`/` to the web UI, 404 for the rest). In `direct` with no certificate yet only the port-80 server is rendered. `tests/image/test_nginx_ingress.py` runs `nginx -t` on every mode with both root variants; doctor's `web.tls` is the runtime check for `direct`.

## The dedicated VM: host/ and istota-stack

The one deployment shape's host half (the one-deployment-shape spec, Stage 6). `host/provision.sh` turns a fresh Debian 13 machine into one install, idempotently (Docker Engine from Docker's repository, the userns sysctl, zram, the journald cap, the auditd bound) plus what the stack needs: `userland-proxy: false` in `daemon.json` (nginx must see the client's address for the proxied allow list), a host user at uid 10001, the `/srv/app/istota` layout, the Nextcloud mount point outside it at `/srv/mount/nextcloud/content` (the bare-metal installs' path; `ISTOTA_MOUNT_DIR` overrides it for the tests), `allowed_signers` from `RELEASE_SIGNING_KEY`, the AppArmor profile, and every `host/` unit. Units read `/srv/app/istota/host.env` through `EnvironmentFile`, so nothing in `host/` is a template. `tests/test_host_units.py` holds what can be held without a VM; running the script is Stage 7's vm tier. `host/lima/istota.yaml` provisions from a verified release tag (`ISTOTA_TAG`, `RELEASE_SIGNING_KEY`, carrying the third byte-equal copy of the tag check) or from a read-only mount of a Mac checkout (`ISTOTA_REPO`); its two mounts, the checkout and the `WORKSPACE` folder, are all that may cross from the Mac (row L3), and a VM that uses one drops the other at create with `--set`, since Lima refuses an empty mount location. `host/cloud-init.yaml` verifies the release tag before running anything from it.

**`ansible/` is the optional management role for an estate-managed VM** (the one-deployment-shape spec, Stage 8a; it replaced the bare-metal role that lived in `deploy/ansible/`). It writes `host.env`, the `.env` keys `istota setup` owns, one secrets file per `SECRET_NAMES` entry, `rclone.conf`, `config/admins` and an `istota apply` plan from variables, then calls `provision.sh`, `istota-stack update` (in `istota_update_mode: release`, only when `istota_release` differs from `ISTOTA_TAG`; in `latest`, `update --unsigned latest` only when `istota-stack latest-tag`, a read-only `ls-remote`, names a different `main-<hex>`, since an update always rebuilds; `istota_update_force` runs it regardless, and `--tags istota_update` runs only the update, its checks and the health wait; `latest` needs no signing key, and the post-apply rebuild passes `--unsigned` for a tag `.env` marks unsigned) and `istota-stack apply` (`--dry-run` under `--check`), and runs the ensure loops through the VM's `istota` wrapper. It renders no unit and builds nothing, and it refuses a VM with no verified checkout, leaving the first verification to `cloud-init.yaml`. Three rules it holds. It writes nothing below `config/` or `secrets/` as root: those go through `istota-stack put-files`, which drops to 10001 (`setpriv`) before it opens a file and replaces a link rather than following it, with the values as JSON on stdin. It provisions when `provision.sh --digest` (host.env, rclone.conf, `.env`'s `COMPOSE_PROFILES`, the checkout's commit) differs from `.provisioned`, which only a successful `provision.sh` run writes, so a play that dies partway still provisions on the next. And after the apply it runs `istota-stack check-image` and rebuilds the deployed tag on exit 2, because a build reads `config.toml` to decide whether Claude Code goes in and the first update runs before the config exists. No secret is on an argv (`istota secret ensure --value-stdin`), and `tests/test_management_role.py` requires `no_log` on every task whose arguments carry one. Its contract is name lists, so `tests/test_management_role.py` reads them from both sides: secrets against `SECRET_NAMES`, `host.env` keys against `provision.sh`'s documented header and every `host_env`/`env_get "$HOST_ENV"` lookup, the `.env` keys and their per-mode values against `stack_env_values` and `nginx_publish`, and the verbs against `istota-stack`'s dispatch. A new `host.env` key goes in `provision.sh`'s header and the role's `istota_host_env` together.

**`istota-stack` is the VM's one command** (`update`, `rollback`, `setup` and `setup --web`, `setup-code`, `apply`, `import-bare-metal`, `up`/`down` for `istota-stack.service`, `exec`, `compose`). It runs the checkout's own compose file at `/srv/app/istota/src/docker/docker-compose.yml`, so the compose file, the seccomp and AppArmor profiles and the images always come from the same tag, and passes the VM's own paths (`ISTOTA_SECRETS_DIR`, `ISTOTA_CONFIG_DIR`, `ISTOTA_MOUNT_DIR`, `ISTOTA_HOST_ENV`, `CERTS_DIR`, `ACME_WEBROOT`) in the environment, which outranks `.env`. It also sets `ISTOTA_LOG_DRIVER=journald`, which every service's `logging: *logging` reads, so container output reaches the host journal with `CONTAINER_NAME` (#712); the compose default is `json-file` because Docker Desktop has no journald and refuses to start a container on that driver. The devbox services keep their own rotated `json-file`. The daemon and web run `istota:${ISTOTA_TAG}`, the other images are `istota-<name>:${ISTOTA_TAG}`, all built on the VM; nothing is pulled from or pushed to a registry. **The daemon's compose service is `daemon`**, so containers read `istota-daemon-1`, `istota-web-1`; no service sets `container_name` but the browser, so a second compose project on the host stays possible. Releases before the rename called it `istota` and built `istota-istota:<tag>`: `update`'s `up -d --remove-orphans` removes the old `istota-istota-1`, the state volume `istota_data` is keyed by its own name and carries over, `rollback` tags a pre-rename `istota-istota:<tag>` as `istota:<tag>` before its schema check, and `main_service` reads the checked-out compose file so `exec`, `setup` and `apply` name whichever service that release has.

- **`update <tag>` is release integrity (parity row 13).** It refuses a name that is not a tag, a lightweight tag, a tag object without an SSH signature, one whose own `tag` header differs from the ref (a downgrade by moving refs), and a signature `git verify-tag` does not accept against `allowed_signers`. The git calls set `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1` and switch OpenPGP and X.509 verification off, so nothing the operator's own keyring trusts counts. A failed build puts the checkout back; `.env` (`ISTOTA_TAG`, `ISTOTA_PREVIOUS_TAG`) is written only after a good build, then `up -d`. The previous tag's images are kept, older `istota` and `istota-*` images (`istota-istota` included) removed. Witness `tests/test_istota_stack.py`, controls `scripts/test-stack-negative-control.sh`. **Only releases are signed**: `update --unsigned <tag>` installs any tag, annotated or lightweight, without the signature checks, for that run only. A branch or a bare commit is still refused, since rollback needs a name that stays put. `.env` marks such a tag (`ISTOTA_TAG_UNSIGNED`, carried to `ISTOTA_PREVIOUS_TAG_UNSIGNED`), and `rollback` returns to a marked tag without verifying it; an unmarked previous tag is verified as a release. An unsigned tag needs no `allowed_signers` at all. **`update --unsigned latest` follows main without tags**: it fetches `origin/main`, deploys its tip and records it as `main-<first 12 hex>`, which names that commit for good, so `rollback` and the per-name image tags work as for a tag. A `main-<hex>` name resolves only to a commit that is an ancestor of `origin/main`, so it is no route to an arbitrary commit, and `latest` without `--unsigned` is refused. A deployment tracking main is updated with that command after each merge; nothing is tagged for it. The cloud-init bootstrap has no such path: a first provision is always from a verified release.
- **`rollback`** asks the previous image `istota init --check-schema` first and leaves `.env` alone when it answers 3 (see the schema stamp below). After the switch it reprovisions the host by `update`'s rule (below), from the checkout it returned to (ISSUE-710).
- **`setup`** runs the wizard as uid 10001 with `ISTOTA_CONFIG_READ_ONLY=false`, in a staging `--vm-dir` it owns, then takes staging back (root, 0700) and installs `.env` and `host.env` with `install_staged`, which opens each `O_NOFOLLOW` and refuses anything but a plain file, so a link planted there cannot copy what root reads into `.env`; it pre-creates every secret file compose declares and copies an upgraded Docker install's `config.toml` and `admins` out of the state volume once. It installs a staged `rclone.conf` too (0600, `install_staged`), which the wizard now writes for full Nextcloud integration, with `RCLONE_REMOTE` in `host.env`. A `--force` re-run with Nextcloud therefore replaces a hand-written `rclone.conf` and remote name with its own pair.
- **`setup --web [--local]`** (`cmd_setup_web`) is the browser first run, the default (`docs/deployment/docker.md`, "First-run setup"; the server is `.claude/rules/install.md`'s). It refuses a configured stack, takes `flock` on `.setup/lock` (fd 8, through python3; a second run is refused), and mints into root's `.setup/` (0700): the setup code (100 bits as four groups of five Crockford characters), and unless `--local` a two-day P-256 self-signed certificate, CN `istota-setup`, with the primary address (`ip route get`, IPv6 bracketed when there is no IPv4 route) and `DOMAIN` as SANs, then the printed instructions. Everything it prints comes from those files, never from staging. Staging gets 0400 copies of the code and the pair, is handed to 10001, and the server runs in the foreground through `oneshot -p <publish>:<8443|8080>`, publish `ISTOTA_SETUP_PUBLISH` (default `0.0.0.0:443`, or `127.0.0.1:8080` with `--local`). The `daemon` network is not `internal:`, so no separate compose service was needed. Afterwards root takes staging back and requires a plain `setup-done`: without it nothing is installed, files the server wrote in `config/` are named for removal, and the run exits with the server's code (3 means timed out, 4 means fifty wrong codes, 0 becomes 1). With it: `install_setup_staging`, `ISTOTA_TAG`, the devbox render, `build_what_setup_needs` (the full build when `image_lacks_what_config_needs` says Claude Code, else `compose build` of only the `missing_service_images`, which follow the new `COMPOSE_PROFILES`, so the browser on a fresh machine), `provision.sh` as a child when `provision_outdated` (the predicate half of `reprovision_if_changed`), then `systemctl enable --now istota-stack`, and `exit 0` because provision may have replaced the script being read. It holds its lock, and whatever the caller holds, for the whole server run, up to an idle hour.
- **`setup-code`** prints `.setup/instructions` only while someone holds the setup lock, so a killed run's leftovers read as "no setup in progress".
- **`istota-setup.service`** is `istota-stack setup --web` as a `Type=exec` unit with `TimeoutStartSec=infinity` and `ConditionPathExists=!/srv/app/istota/config/config.toml`, installed by `provision.sh` and never enabled (no `[Install]`). `host/cloud-init.yaml`'s bootstrap runs `istota-stack update "$TAG"`, `systemctl start istota-setup.service`, then retries `istota-stack setup-code` for five minutes to put the instructions on the console. `istota-stack up` without a config names both ways in. `install.sh --server` still runs the terminal setup.
- **Root acts on no file uid 10001 can write.** `config/`, `secrets/` and the setup staging directory are 10001's, and so is anything a VM process running as 10001 (the rclone mount) touches. The devbox compose file is therefore rendered to `/srv/app/istota/compose.devbox.yml`, beside `.env`, and `compose` refuses it unless it is a regular file owned by the caller and writable by it alone (`require_own_file`); a copy left in `config/` by an older release is removed at the next render.
- **`apply <plan>`** runs `istota apply` in a one-shot container with the config directory open, and restarts the stack on exit 2 only (not under `--dry-run`).
- **A profile turned off stops its service.** Compose counts a service whose profile is no longer active as defined, so neither `down` nor `up --remove-orphans` removes its container; the browser kept running after `COMPOSE_PROFILES` dropped it. Every `up` in `istota-stack` (`stack_up`) removes the project's non-one-off containers whose service `compose config --services` no longer lists.
- **`exec`, and the VM's `istota` wrapper (`host/istota`, which is `istota-stack exec istota`, the `istota` CLI in the `daemon` service), go through `istota-drop`.** A `docker compose exec` starts as uid 0 with the cap_add set. `ISTOTA_STACK_EXEC` replaces only the `compose exec daemon` prefix, for the image tier's row 5 witness (`tests/image/test_stack_wrapper.py`).

**The config directory is a host bind**, `/srv/app/istota/config` at `/data/config`, read-only for daemon and web (`ISTOTA_CONFIG_READ_ONLY`, default true); only `setup`, `apply` and `import-bare-metal` open it. `update` creates any secret file the new tag's compose file declares and setup never made, before `.env` names the tag, since compose refuses to start a service whose secret file is missing. `import-bare-metal` refuses while any container of the stack is running: the import replaces the database and the master key, and the scheduler's singleton lock is in a `/tmp` the one-shot container does not share. In full Nextcloud integration `provision.sh` installs `mount-nextcloud.service` (rclone as uid 10001, from the `rclone.conf` setup writes, or the management role, or the operator) and a drop-in making `istota-stack.service` require it. rclone itself comes from rclone.org's pinned, SHA-256-verified `.deb` and is held, never Debian's package: Debian links it against a 2016 `bazil.org/fuse` that turns every plain errno into `EIO`, so xattr calls on workspace files fail and `shutil.copy2` out of the mount breaks (#694). A mount whose process runs a binary other than `/usr/bin/rclone` (the one dpkg replaced) is restarted, read off the process so a re-run after an interrupted one still does it. In `direct` ingress with `acme`, certbot runs on the host (`host/istota-certbot`, a twice-daily timer, a deploy hook restarting nginx), and `istota-stack up` starts the first issuance. The proxied listener's `DOCKER-USER` rule lives in the egress unit, matched on conntrack's original destination.

**The schema stamp.** `db.init_db` writes `db.SCHEMA_VERSION` as `PRAGMA user_version` and refuses, before anything writes to the file, a database stamped higher (`db.SchemaTooNew`); `istota init` exits 3 with one `REFUSE` line, and `init --check-schema` answers read-only. Raise `SCHEMA_VERSION` in the commit that adds a migration an older release cannot run against. The upgrade tier's `TestAnOlderImageRefusesANewerSchema` holds the boot; its control is `scripts/test-stack-negative-control.sh rollback`.

## Host memory headroom

Robustness spec, Track A. `provision.sh` installs `systemd-zram-generator`, writes `/etc/systemd/zram-generator.conf` and starts **`dev-zram0.swap`**: compressed in-RAM swap, zstd, `swap-priority=100`, `zram-size = ram / 2`. With no swap the kernel cannot evict anonymous pages, and tmpfs/shmem is swap-backed, so cold shmem became unreclaimable and the host thrashed. zram rather than a disk swapfile because the disk was already saturated. `ZRAM_ENABLED=0` in `host.env` skips it, so an operator with other swap is not fought; it does **not** tear down a device an earlier run created.

**Two units, and the wrong one is a no-op.** `systemd-zram-setup@.service` is a static template from the package: it creates `/dev/zram0`, sets `disksize`/`comp_algorithm` and `mkswap`s, and never calls `swapon`. `dev-zram0.swap` is synthesised by the *generator* and activates swap; its `Requires=`/`After=` pull in the setup service, never the reverse. The generated unit has no `[Install]`, so there is nothing to enable: persistence comes from the generator recreating the `swap.target.wants` symlink on every reload and boot, which is why the script runs `daemon-reload` before it starts the swap unit.

**Geometry changes need stop, rebuild, start, in that order.** A live zram0 keeps its size and algorithm until torn down. Restarting *only* the setup service is worse than nothing: `Requires=` propagates the stop to `dev-zram0.swap` and nothing propagates the start back, so swap goes to zero until reboot.

**Sizing.** `zram-size` is the *uncompressed* logical capacity. `ram / 2` on a 7.9 GB box is a ~4 GB device costing ~1.3 GB of RAM at 3:1. 4 GB is kept deliberately: it covers the 4.6 GB of cold shmem that killed the host, and the incompressible worst case commits only 4 GB of 7.9.

`provision.sh` also caps the journal (`SystemMaxUse=500M`) and bounds auditd's logs. The stack sets no unit-level memory limit: the per-task cgroups under the daemon's delegated subtree (sandbox.md) are the limit that matters.

## The local VM's host folder

`STORAGE=host-folder` is the local VM's workspace (the local-VM spec): a folder on the Mac that Lima shares in with virtiofs at `/srv/mount/host-folder`, bound at `/mnt/shared` like the rclone mount, with `workspace_path` and `workspace_mount_path` both `/mnt/shared` and no Nextcloud URL (`istota setup --storage host-folder`, kept on a re-run without the flag). `mount_dir_for_storage` is the directory rule, carried by both `provision.sh` and `istota-stack` and held equal by `tests/test_host_units.py`. `provision.sh` writes `istota-stack.service.d/host-folder.conf` (`RequiresMountsFor=`) and never creates, chmods or chowns the folder, and neither does `istota-stack setup`: a guest chmod reaches the Mac. Apple's virtiofs reports every entry as owned by whichever guest uid asks, so uid 10001 writes there with no uid layer, and the root phase's ownership walk never leaves `/data`. A folder that went away still reads as a virtiofs mount (Lima recreates a missing one empty), so `.istota-workspace` at its root is the only signal: the entrypoint refuses without it, `runtime.mount_liveness` fails, and `db_backup` neither snapshots nor copies the config there. Row L1's witness is `tests/vm/test_host_folder.py`, control `no-workspace-marker`. A lost VM comes back from the folder: `istota-stack restore` (VM verb, key on stdin, stack down) runs `istota migrate restore-workspace` in a one-shot container, and the Mac's `istota-stack restore` wraps it with `destroy` and `create --no-setup`. `update`, `setup` and `apply` copy `.env` and `host.env` into the folder's `Backups/config/<date>/` for it (`copy_stack_env_out`; `.claude/rules/maintenance.md`).

## The local VM: the Mac's istota-stack

The local run shape (the local-VM spec): a Lima VM on an Apple silicon Mac running the stack unchanged, created and controlled by `host/mac/istota-stack` (bash 3.2-safe; `tests/test_mac_istota_stack.py` runs it under `/bin/bash` with `limactl`, `security`, `lsof`, `open` and `uname` as recording stubs). User docs: `docs/getting-started/local-install.md`; the trust model: `docs/deployment/security.md`, "The local VM".

- **One command name, forwarding.** The Mac script handles `create`, `start`, `stop`, `status`, `open`, `shell`, `autostart`, `allow-host-port`/`deny-host-port`, `update`, `destroy`, `restore`, `import-standalone`, and `exec`s everything else as `limactl shell --workdir / $INSTANCE sudo istota-stack "$@"`, exit status passed through. `apply` and `import-bare-metal` take a Mac path, which goes through the VM's `stage` (a fresh root-only, or with `--daemon` uid 10001's, directory under `/srv/app/istota/staging/`) and `unstage` after. `host/mac/istota` is `istota-stack exec istota`, so it reaches `istota-drop` (row L4; control `mac-shim-without-drop`). `INSTANCE` is `istota`, `ISTOTA_LIMA_INSTANCE` overrides it, in the default `LIMA_HOME`.
- **Lima facts `create` is built on, measured (Stage 1, 5).** `cpus`, `memory` and port numbers cannot be template params (Lima parses them as numbers before expanding), so `create` passes `--cpus`/`--memory` and one `--set` for `.portForwards[0]`. A mount location can be a param, but cannot be empty, so the template names both mounts and a release-mode `create` drops the checkout's in the same `--set` (`del(.mounts[] | select(.mountPoint == "/mnt/istota-repo"))`); `--set` cannot touch `base:`. `autostart on|off` is `limactl autostart enable|disable`, a LaunchAgent effective at the next login. Lima's DNS is the gateway, `192.168.5.2`; nothing answers at `.3`.
- **`create`** refuses before any `limactl` call: not Darwin arm64 (78), a folder in iCloud/CloudStorage, under `~/Documents|Desktop|Downloads`, `~/.istota`, `/`, the home, or containing or inside `~/.lima`/`~/.ssh` (links resolved, compared lowercased), then `limactl` < 2.0 (69), a held port (78, names the holder via `lsof`), a non-empty unmarked folder without `--adopt`. Then the folder and `.istota-workspace`, `limactl create`/`start`, `istota-stack host-env STORAGE=host-folder INGRESS=local HOST_LOOPBACK_BLOCK=1 HOST_GATEWAY_ADDR=192.168.5.2` (a VM verb, since `put-files` reaches only 10001's files and `host.env` is root's), `update`, the terminal `setup --storage host-folder --ingress local --hostname localhost:<port>`, `check-image` and the rebuild, `provision.sh`, `enable --now`, the script refresh, the key escrow and the enrolment link. Release mode needs `--tag` and `--signing-key`; `install.sh --local` requires both too. Each step is skipped when one probe (`VM_PROBE`: tag, unsigned, config present, first admin) shows its effect, so a re-run resumes. `--no-setup` stops after provision; `restore` and `import-standalone` use it, and `setup --web --local` after it is the browser first run (the web setup keeps `host-folder` from `host.env`; its page publishes on the VM's 8080, so only with the default port). `create`'s arguments, the public signing key included, are kept in `${XDG_CONFIG_HOME:-~/.config}/istota/<instance>.env`.
- **The Mac scripts follow the verified tag.** After `create`'s update and every successful `update`, `refresh_scripts` copies `host/mac/{istota-stack,istota}` and `host/lima/istota.yaml` out of the VM's checkout through a temp file and a rename, only when an install exists in `~/.local/bin`; run from a checkout it refreshes nothing.
- **Key escrow is `security -i`, read back.** The command line `add-generic-password -s istota.local -a secret-key-<instance> -w <key>` goes on `security -i`'s stdin, never an argv (asserted across every stub call). `security add-generic-password -w` with no value reads a pipe only without a controlling TTY, asks twice, and stores an empty item with exit 0 on a short read, hence the read-back. A different key already in the item stops `create` (78): it decrypts an earlier VM's snapshots. `destroy` refuses without the item unless `--force`.
- **The loopback block's DNS exception.** `HOST_LOOPBACK_BLOCK=1` drops forwarded traffic to `HOST_GATEWAY_ADDR` from any source in `DOCKER-USER`, with udp/tcp 53 and the `HOST_LOOPBACK_ALLOW` ports returned first, and `! -s` the devbox subnet on the returns (row L2, control `host-loopback-unblocked`). Without the port-53 return a default-bridge container (a `docker build` step) cannot resolve; compose services resolve through Docker's embedded resolver, from the VM's namespace.
- **What crosses from the Mac is the template's mount list** (row L3, control `default-mounts-in-template`): `base:` is `template:_images/debian-13`, never `template:debian-13`, which merges in `_default/mounts`, the whole home.
- **Restore** is described under "The local VM's host folder" above. **`import-standalone`** stages `sqlite3 .backup` copies, the config, admins and transcripts, sends `istota.env` on stdin (every credential, not only the master key; an unknown name is refused), runs `istota migrate import-standalone` in the VM before copying the files so a refusal leaves the folder untouched, and never changes `~/.istota`; `.claude/rules/maintenance.md` has the module.
- **Owed manual runs.** A release-mode boot against a real signed GitHub release (none is SSH-signed yet), `install.sh --local` on a clean account, `security -i` against a real login Keychain, autostart across a logout, and the guest clock after a real 30-minute sleep (Lima's guest agent steps the clock from the host; measured with the clock set back, not across a sleep).

`[web] auth` in `config.toml`, defaulting to `["nextcloud"]` even with no Nextcloud URL; `istota setup` asks. ## Leaving the bare-metal shape

- **`retire-bare-metal --namespace NS [--dry-run]` removes what the old Ansible role installed**, after a migration: its units, crons, scripts, sysctl, journald, tmpfiles and module-load files, `/etc/NS`, `/var/lib/NS`, the service user and its home (only when that home is `/srv/app/NS`), its `NS-`-named containers, images and `NS-`/`NS_` volumes and networks, the host nginx site for `DOMAIN`, and the ufw rule commented `Docker containers (NS)`. It refuses `istota` as a namespace, while `istota-stack.service` is not active, and while any of the four app units is enabled or running. It never touches `mount-nextcloud.service` or the zram config, which the stack took over under the same names. `ISTOTA_RETIRE_ROOT` prefixes every path for `tests/test_retire_bare_metal.py`.

- **An update or a rollback reprovisions the host when its inputs changed.** `provision.sh` installs `istota-stack` itself, the units and the host scripts, so an update that never ran it left them at whatever tag last provisioned (zorg's first `retire-bare-metal` was not there). After a successful switch, `update` compares `src/host/provision.sh --digest` with `.provisioned` and, when they differ (a new release changes the digest through the checkout's commit), runs that `provision.sh` as its last step, by `exec`, because provision replaces the very file bash is reading the update from. A failed provision fails the update with the stack already on the new tag. The update itself runs the previous release's `istota-stack`, so `provision.sh` ends by running the newly installed `istota-stack up` when it replaced a different `istota-stack` and `istota-stack.service` is active: whatever the new script's `compose()` passes (the journald driver, #712) reaches the containers on the deploy that ships it. Only then, because the management role provisions before its apply, and an `up` there would start the stack on a `host.env` the config does not match yet (the entrypoint refuses a `[site] hostname` that is not `DOMAIN`). A failed `up` there is a warning, since the previous script's `up` already ran. A release with no `host/provision.sh` updates as before. `rollback` ends with the same `reprovision_if_changed`, so the host's scripts and units follow the tag it returns to rather than staying at the newer one. That comparison is sound only because `provision.sh` removes `.provisioned` before it acts: a run that died after installing the newer checkout's files used to leave the older release's digest, which a rollback to that release then read as provisioned. The vm tier's update case asserts it (`TestARollbackToTheRelease::test_a_rollback_returns_the_hosts_istota_stack`, control `rollback-without-reprovision`).
