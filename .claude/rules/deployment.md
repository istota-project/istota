# Deployment

**`istota doctor` first, on any host, before anything else.** It runs the whole check registry against the loaded config and reports each result as `ok` / `warn` / `fail` / `skip` with a remedy on everything that is not `ok`; it exits 1 on any `FAIL` and 0 otherwise, and it never raises. `--json` for a machine-readable payload (statuses are **lowercase** there — the text renderer uppercases them for display, and a consumer filtering on `"FAIL"` matches nothing, which is a defect this repo has already shipped once). `--scope image` answers only what a bare `docker run` can answer, `--scope deployment` only what needs a real install; `--only <prefix>` narrows, `--deep` opts into the checks that spawn a namespace. The same run happens at daemon start-up with no output unless something is wrong, and `check_doctor` sweeps hourly, alerting each admin's `alerts_channel` on a transition into `FAIL`. A tokenless or disabled developer skill makes the `developer.*` checks `SKIP` rather than fail — so "no FAIL" on its own is not evidence the forge chain is healthy; check that the forge checks did not skip.

**The supported upgrade span is `scripts/upgrade-floor`** — one hand-edited line naming the oldest release an upgrade to current main is expected to work from, currently about a month back. `scripts/test-upgrade.sh --from-floor --shape volume` is what holds it: it captures that release's `config.toml` (by running that release's own `entrypoint.sh` against a two-endpoint Nextcloud stub) and its schema, boots the current image over both, and requires no `FAIL` plus a `developer.forge_config_drift` `WARN`. Bump the floor deliberately — when a migration stops reaching that far, or when the span stops being worth the run — and never to make a red run green without reading why it went red. The unqualified `scripts/test-upgrade.sh` uses the merge-base with the default branch instead, which is the span the auto-update cron crosses.

**Ansible**: role at `deploy/ansible/` (symlinked from the operator's `ansible-server` checkout). When adding config fields, update `defaults/main.yml` + `templates/config.toml.j2`. The role runs `files/validate_config.py` against the rendered TOML before any handler can restart the scheduler — structural bugs fail the play instead of the running daemon. Three systemd units (`istota-scheduler`, `istota-web`, `istota-webhooks`) all read `ISTOTA_ADMINS_FILE` and `ISTOTA_SECRET_KEY` from the same EnvironmentFile. The developer skill's `gh` and `glab` come from the vendors' release `.deb`s, sha256-verified per architecture and extracted with `dpkg-deb -x` into `/usr/local/bin`. Not from the Debian archive, which ships gh 2.46 and glab 1.53 on trixie — 50 and 60 releases behind what both images pin. The version and the digests are named in three files — this role, `docker/istota/Dockerfile` and `docker/devbox/Dockerfile` — because nothing can share a literal across an Ansible role and two Docker builds; `tests/test_ansible_forge_cli_install.py` holds the three equal, so bump them together. There is deliberately **no** version floor for these two: any floor low enough to be true of the verbs the skill uses is also cleared by the archive versions it would be meant to catch, so it caught nothing and was a third place to edit. gitleaks keeps one (`istota_developer_gitleaks_min_version`, 8.19) because below it `gitleaks git` does not exist, the pre-commit hook cannot run at all, and every unattended agent commit on the host is refused. What that floor reaches is gitleaks missing from PATH altogether and the pin being edited down — **not** an apt 8.16 shadowing ours, which cannot happen, since `/usr/local/bin` precedes `/usr/bin` on Debian's default PATH. The consequence of dropping the forge floors, stated rather than implied: nothing now stops the gh/glab pins being edited *down*, because the parity test is satisfied by lowering all three files together. Unlike the image these stay **on** PATH, ahead of `/usr/bin`: an apt-installed `gh` from an older run of this role may still be present and name-resolvable, so moving ours out of the way would buy the off-PATH property for nobody and break `gh` for an operator on the box — which is also why the role does not remove that package. After the install the role runs both binaries through PATH and requires the pinned version back: the install block ends in a `copy`, which succeeds whatever the bytes are, so without that a truncated extraction installs green and then reinstalls identically on every play.

**Default Talk rooms on both targets**: `#general` / `#logs` / `#alerts` are provisioned per user by whichever target is in play, and both use group rooms (`roomType=2`, invite-only) — `#logs` carries the verbose execution log and `#alerts` carries confirmations and security alerts, so a public room would be joinable by anyone holding the token. Docker does it in `entrypoint.sh` (before `config.toml` exists, so it can't call the CLI); Ansible does it through `istota nextcloud provision-rooms` (`src/istota/provision_rooms.py`), gated on `istota_provision_talk_rooms` + `istota_talk_enabled` and run *after* `istota user ensure` so an inventory-pinned `log_channel` / `alerts_channel` is already in the row — a channel room whose column is already set is not created at all, and a column is seeded only for a room that run actually made usable, so a redeploy can't refill a channel the user cleared in the web UI (the ISSUE-102 shape). A failed invite leaves a bot-only room, which the next run adopts and retries rather than minting a duplicate. **Not** at parity: the entrypoint also seeds `Channels/{general}/CHANNEL.md` and posts an intro message to `#alerts`; the Ansible path does neither (ISSUE-115).

**Docker**: `docker/docker-compose.yml` brings up nginx (single host port, reverse-proxies `/` → Nextcloud and `/istota/` → web service) + nextcloud + postgres + redis + istota (multi-stage Dockerfile builds the SvelteKit frontend; separate scheduler / web / webhooks services). The image installs `bubblewrap` + `tmux`, plus the developer skill's `gh` and `glab` (pinned release `.deb`s, sha256-verified per architecture, extracted to `/usr/local/lib/istota_forge/` — off PATH, so nothing resolves the real binary by name and the policy wrapper is what a task reaches; `ISTOTA_DEVELOPER_GH_BIN_PATH` / `_GLAB_BIN_PATH` override the location). `config.toml` is rendered by `docker/istota/render-config.sh`, a sibling of the entrypoint that the entrypoint *executes* (never sources — it runs `set -euo pipefail`, so a sourced render would abort the boot on any unset variable it read). The entrypoint keeps the file-exists guard and the three post-guard backfill passes that repair an existing config on an upgrade; the render itself takes its inputs as exported variables and is independently runnable, which is what lets `tests/test_render_config.py` and the image tier produce a config with no Nextcloud to provision against. It renders to a `.partial` sibling and `mv`s it into place, so a failure part-way through cannot leave a truncated file that the file-exists guard then accepts as complete forever. The four operator-typed credentials are escaped for TOML before interpolation — a `"` in a password used to terminate the string early and corrupt the file while the render still exited 0. The render writes `gh_bin_path` / `glab_bin_path` into `[developer]`, but only on a first boot with a fresh volume, so `_resolve_real_bin` also probes that directory for containers upgraded past an older `config.toml`. It defaults `sandbox_enabled = true` and `skill_proxy_enabled = true` (overridable via `ISTOTA_SECURITY_SANDBOX_ENABLED` / `ISTOTA_SECURITY_SKILL_PROXY_ENABLED`); the network proxy is off (`[security.network] enabled = false`) since the container's own network is the boundary. The container runs as **root** (no `USER` directive), so the CLI brains' `--dangerously-skip-permissions` is accepted via `IS_SANDBOX=1`, which `ClaudeCodeBrain`/`TmuxClaudeBrain` set automatically when running as root; bwrap doesn't `--clearenv`, so it propagates into the sandboxed `claude`. The entrypoint auto-provisions `#general`, `#logs`, `#alerts` group rooms (`roomType=2`; lookups are scoped by `USER_NAME` participation, so identically-named rooms across users on a shared NC don't collide), registers an OAuth2 client in NC via inline PHP, generates `LOCATION_INGEST_TOKEN` + `ISTOTA_SECRET_KEY` (persisted to `/data/.secret_key`), and seeds workspace files. Modules default on (`ISTOTA_*_ENABLED=true`). Key env: `CLAUDE_CODE_OAUTH_TOKEN`, `ADMIN_PASSWORD`, `USER_NAME`/`USER_PASSWORD`, `BOT_PASSWORD`, `POSTGRES_PASSWORD`, `DOMAIN`, `ISTOTA_WEB_INSECURE_COOKIES` (toggle for plaintext localhost).

**Host memory headroom** (robustness spec, Track A; `tags: [swap]`): the role installs `systemd-zram-generator`, renders `/etc/systemd/zram-generator.conf` from `zram-generator.conf.j2`, and starts **`dev-zram0.swap`** — a compressed in-RAM swap device, zstd, `swap-priority=100`. The box previously ran with `Total swap = 0`, which is what turned a memory shortfall into a thrash-to-death: with no swap the kernel cannot evict anonymous pages, and tmpfs/shmem is swap-backed by design, so cold shmem becomes permanently unreclaimable and the page cache absorbs the whole shortfall. zram rather than a disk swapfile because the disk was already the saturated resource.

**Two units, and picking the wrong one ships a no-op.** `systemd-zram-setup@.service` is a *static template shipped by the package*: it creates `/dev/zram0`, sets `disksize`/`comp_algorithm` and `mkswap`s it, and never calls `swapon`. `dev-zram0.swap` is what the *generator* synthesises into `/run`, and it is the unit that activates swap; its `Requires=`/`After=` point at the setup service, so starting the swap unit pulls the setup service in and never the reverse. Target the setup service and the play is fully green on a host with no swap. No `enabled:` on the task either — the generated unit has no `[Install]`, so `systemctl is-enabled` answers `static` and Ansible records success without doing anything; persistence comes from the generator re-creating the `swap.target.wants` symlink on every reload and boot. **A `daemon_reload` must re-run the generators before the start task**, or there is no unit yet on a first install. Swap is live at the end of the play — no reboot needed — and a mandatory `Verify zram swap is actually active` task asserts that against `/proc/swaps`, because a swap change whose only evidence is a green play is how the first draft of this block shipped a no-op.

**Geometry changes need a stop/rebuild/start, in that order.** A live zram0 keeps its size and algorithm until torn down. Restarting *only* the setup service is worse than doing nothing: `Requires=` propagates the stop to `dev-zram0.swap` and nothing propagates the start back, so a size change on a running host silently takes swap to zero until reboot. The rebuild is skipped when zram0 holds more than 64 MB — `swapoff` faults every page back into RAM, which is the failure the whole track exists to prevent — and a skip is surfaced by its own `debug` task, since the config and the device then disagree permanently (the next run sees no config change and never retries).

**Sizing**: `zram-size` is the device's *uncompressed* logical capacity; compression happens beneath it. `ram / 2` on a 7.9 GB box is a ~4 GB swap device costing ~1.3 GB of real RAM at 3:1 — not the "10-12 GB effective" the spec claims, which would need `ram * 1.5`. 4 GB is kept deliberately: it covers the 4.6 GB of cold shmem that killed the host, and the incompressible worst case commits only 4 GB of 7.9. The three values in `zram-generator.conf.j2` are **not nullable** — unlike the unit directives, an empty value there is rejected rather than omitted.

`istota_zram_enabled: false` makes every task a no-op so an operator who arranged swap another way is not fought with — it does **not** tear down a device the role previously created. An optional second-tier disk swapfile (`istota_swapfile_enabled`, default false) sits below zram at `pri=10`, with `nofail`; `mkswap` is gated on a `blkid` signature probe rather than on "did this run create the file", and the fstab entry is written only *after* `swapon` succeeds, so an interrupted run cannot leave a boot-time reference to an unformatted file.

**Unit resource limits**: `MemoryHigh` on all three units (`5G` scheduler, `1G` web/webhooks) — soft throttling, never `MemoryMax`, because killing the daemon takes everything down and istota's own footprint was never the problem (~1.2 GB). The scheduler figure covers the **whole cgroup**, including every `claude` subprocess and its children, which is why the spec's 3G is too low: at two foreground workers with a task running a test suite the cgroup clears 3 GB on its own, and `memory.high` responds with an allocation-time sleep penalty applied to every process in it — including the dispatch loop — so the symptom would be "everything slow, nothing logged", indistinguishable from the hang being fixed. Nothing reads `memory.events` yet, so a throttle is currently invisible; Stage 3 should have `host_pressure` surface the `high` counter. `CPUWeight=50` on the scheduler only, below systemd's default of 100 so every other unit wins under contention; no `CPUQuota`, since PSI showed the cores idle-waiting on memory rather than oversubscribed. `Delegate=memory pids cpu` **plus `DelegateSubgroup=supervisor`** and explicit `MemoryAccounting=yes` on the scheduler: `Delegate=` alone is not enough, because cgroup v2 forbids a non-root cgroup from both holding processes and enabling controllers for its children (`EBUSY`), and `Type=simple` puts the daemon directly in the unit cgroup — Stage 5 would create `task-<id>/` and find no `memory.max` in it, which A6's fail-open rule would swallow. `ProtectControlGroups` and `ProtectKernelTunables` must stay unset or delegation is silently defeated; `ProtectSystem=strict` is fine alongside, since strict leaves `/sys` writable. An empty string on any of the three variables omits the directive rather than emitting one systemd would reject. Rendering and task shape are covered by `tests/test_ansible_memory_limits.py`.

**Clone credential** (ISSUE-258): `istota_repo_clone_token` never enters a URL. The bare token goes to `/etc/{{ istota_namespace }}/clone-token` at `0600 root:root`; `git-credential-istota.sh.j2` renders to `/usr/local/bin/{{ istota_namespace }}-git-credential`, and `credential.https://<repo host>.helper` is registered at **system** scope to point at it. The clone then uses the bare `istota_repo_url`. The old shape interpolated the token into the clone URL, so git persisted it as `remote.origin.url` and expanded it into `git-remote-https`' argv on every fetch — every two minutes, under the auto-update cron.

**Not `store --file=`, which is the obvious choice and the wrong one.** `git-credential-store` implements `erase`, and git calls `erase` on any 401, truncating the file: one expired, revoked or freshly-rotated token would leave the cron fetch failing silently (`MAILTO=""`, output to a log) until someone re-ran Ansible. It also rewrites its file on a successful auth, so an unrelated root git operation against the same host could swap the deploy credential, and Ansible's copy of that file would not be idempotent. The helper answers `get` and ignores every other verb, which removes all three. It reads the token from a file rather than embedding it, so rotation is one file write. Host scoping is per-host so the helper is never consulted for anything else; **system** scope because `/etc/gitconfig` is read whichever user and whatever `HOME` the fetch runs under — note the neighbouring `safe.directory` task is at `global` scope and the cron fetch does read it, so `global` would work too; `system` is the more robust of two working options, not a fix for a broken one.

**Only https remotes are in scope, and the guards match a password rather than an `@`.** An scp-style `git@host:path` legitimately contains `@` and carries no secret, as does `https://oauth2@host/…`; matching `@` would rewrite the remote on every run and fail the play forever. Both the remediation and the assert test `urlsplit('password')` instead. `_istota_repo_host` comes from `urlsplit('netloc')` split on `@`, not `urlsplit('hostname')` — `hostname` lowercases, and git matches config subsections by exact string, so an uppercase host would yield a key git can never match. Two tasks keep the defect from returning: a `remote set-url` ahead of the clone that remediates hosts provisioned under the old shape (gated on a replacement credential being available, so a run without the vault cannot strip the only working one), and an `assert` after it that fails the play if the remote carries a userinfo password. Neither prints the value, and both read-back tasks carry `no_log` because on an unremediated host their stdout *is* the token. Both use `check_mode: false` and `| default()` guards, since `command` is skipped under `--check` and would otherwise raise on a missing attribute. Clearing `istota_repo_clone_token` (or pointing at an ssh remote) removes the token file, the helper and the git-config entry rather than orphaning them. Covered by `tests/test_ansible_clone_credential.py`, which executes the rendered helper to hold the `erase` property down.

**The devbox half of the role.** `deploy/ansible/templates/docker-compose.devbox.yml.j2` is the only devbox definition in the tree, rendered once per entry in `istota_devbox_users`. Read it in two halves: the service's own shape changed for **every** devbox, gated on nothing, because the image's own `CMD` is the supervisor and a template still saying `sleep infinity` would make that image's build-time smoke test a lie; the two mounts and the `environment:` block below are gated on `istota_developer_enabled` and a non-empty `istota_developer_repos_dir`, inside the `istota_devbox_enabled` gate the whole file already sits behind. `istota_developer_container_backend` is retired: every `when:` that tested it already carried `istota_devbox_enabled` as its other conjunct, so the collapse took nothing away. In the ungated half: `command` is a supervisor (`istota-exec-run`) rather than `sleep infinity`, with `init: true` for reaping — `restart: unless-stopped` restarts the *container*, so nothing used to restart the server after a dockerd restart or a container OOM, and `sleep` as PID 1 never calls `wait()`. `init: true` covers **zombies** and only zombies: a backgrounded build that outlives its server is running, not a zombie, and tini calls `wait()` on it exactly never, so the supervisor's restart used to leave every command the dead server was running alive and invisible (ISSUE-322). What covers that is inside the server rather than in the deployment: `run_reaper` in `istota-exec-serve` is a child holding the read end of a pipe the kernel closes however the server dies, including SIGKILL, which the `finally` that normally kills the groups cannot survive. `cap_add: [NET_RAW]` and the 1 GiB `/workspace` tmpfs are gone. `DEV_UID` / `DEV_GID` are build args carrying the daemon's own uid and gid, from a `getent passwd` lookup with an assert behind it, so the two sides of the shared mount have one numeric identity; the image defaults them to 1000, so a build with no args reproduces the old container exactly. Both `cap_add` and `command` came out of `tests/test_devbox_deployment_shape.py::TestTheAnsibleServiceKeepsItsContainment`'s `REQUIRED` list, each with its reason recorded in the relinquished-keys block directly under that list — the durable record the class asks for; `networks: ["devbox-net"]` stays in it and the design depends on that, since a container on the project default network sits outside `istota_devbox_network_subnet` where every `DOCKER-USER` rule the role installs is scoped to a subnet no container uses.

**Two mounts, one socket directory, and one migration.** Under `backend: devbox` the container binds `{repos_dir}/{user_id}` and `{exec_socket_dir}/{user_id}`, and nothing else. It was three: the package cache had a mount of its own while `security.sandbox_cache_dir` was a configured root, and the cache is derived at `{repos_dir}/{user_id}/.package-caches` now, inside the first mount. That is the arrangement rather than a simplification — one mount covering cache and venv is the only shape where uv hardlinks a wheel instead of copying it, since `link(2)` compares mounts rather than devices. `doctor`'s `uv_cache` result checks that the derived directory is visible in the container, not that a key is set. Each mount is at the identical absolute path on both sides, so a working directory needs no translation. The per-user socket subdirectory is created by the play *and* declared in `istota-exec.tmpfiles.j2`, because Docker auto-creates a missing bind source as `root:root` and systemd-tmpfiles runs at boot where the play does not. It is 0770 rather than 0750: the container creates the socket in there as the daemon's uid. Only the per-user subdirectory is ever mounted — the parent holds every user's socket, and that is arbitrary command execution against another user's repositories. **The home volume's ownership is the host's job, and that is not a preference.** Docker seeds a named volume from the image only while the volume is empty, so a `/home/dev` created before `DEV_UID` / `DEV_GID` existed keeps uid 1000 while every rebuilt container's `dev` is the daemon's uid, and nothing re-seeds it. The container cannot repair itself: `istota-exec-run` carries a `chown` that reaches root through `sudo`, and `no-new-privileges` — daemon-wide in `/etc/docker/daemon.json` on at least one deployment — makes sudo refuse whatever the image's sudoers grant says. So the role reads each volume's ownership through a throwaway root container (`:ro`, `--network none`, and `docker volume inspect` first so a fresh install is not handed an empty volume ahead of its seed) and chowns only one that disagrees. A standing guard rather than a migration: the same divergence appears any time the daemon's uid changes. The in-container path now asks whether root is reachable *before* attempting anything, so a `chown -R` that died half-way and one that could never run keep the different words they need.

The layout migration is `python -m istota.repos_relocate`, which the role runs after the code is in place and before the units restart; it assigns every namespace to the single configured admin and refuses where there are none or several, since nothing on disk records who owns a clone.

**The Docker-API proxy is retired and the role tears it down.** `istota-docker-proxy@.service.j2`, `istota-docker-proxy.tmpfiles.j2` and every `api_proxy` variable are deleted; a retirement block enumerates any surviving per-user instance units, stops, disables and removes them, and removes `/var/run/{{ istota_namespace }}-docker` with the stale socket inodes in it. The path is written out rather than interpolated, because the variable that named it is gone and this is the last thing in the role that knows where those sockets were. `tests/test_ansible_config_template.py` sweeps the whole role for the retired key names, which is why none appears even in a comment. Two defects in that block are fixed and held by `tests/test_ansible_docker_proxy_retirement.py`: the unit listing lacked `--plain`, so `awk '{print $1}'` returned systemd's status glyph instead of the unit name — for failed and not-found units only, which is exactly the set the block exists to retire, so the stop ran against a unit named `●`, failed, and was swallowed by its own `failed_when: false`; and nothing ever called `reset-failed`, so a host kept a `not-found / failed (226/NAMESPACE)` entry with nothing left that could clear it. Both observed on a live deployment.
