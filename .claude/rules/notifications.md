# Notifications: the inbox behind the bell

`notifications/delivery.py` is delivery (Talk / email / ntfy). The three below are the durable open set of what is waiting on a user.

## notifications/store.py

The `notifications` table: the durable open set of what is waiting on a user, behind the bell. The write and the send are **two calls** — most producers raise from inside an open write transaction, and a second connection opened there waits the full 30s busy timeout on the lock the caller holds, raises, and is swallowed by the never-raises contract (the same hazard `run_cleanup_checks` buffers its expiry notices for). So a producer calls `write_notification` on its own connection, buffers the `RaiseResult`, and calls `deliver_pending` after its `with` block; `raise_notification` is for a caller that demonstrably holds no lock. The upsert is a read-modify-write, not `ON CONFLICT DO UPDATE`: the branch depends on the row's state *before* the write and SQLite exposes no way to see that from an upsert — insert and reopen deliver, a bump does not (that dedup is what a chat channel structurally cannot do). `last_delivered_at` records only a *successful* send, since `send_notification` returns False with no destination configured and suppressing a redelivery on a send that reached nobody is the failure the inbox exists to fix. `resolve_by_object` takes `user_id` first-class and required — panel ids come from the per-user health DB where every user has a panel `12`. `mark_seen` takes `(id, updated_at)` pairs so a row bumped between the client's fetch and its POST is stamped but not closed. `list_open` runs a liveness pass over the *whole* open set (the oldest rows are the ones with dead objects, and a render-bounded sweep never reaches them), enforces the URL allowlist at runtime on every view, and counts survivors rather than re-querying. Never raises

## What an alert push may carry (#638)

**A push on the `alert` purpose is a title plus text a producer fixed or the system composed, never conversation.** The alert route is often a room (the alerts channel, mirrored into its web transcript), and a room gets notices about the conversation, not the conversation. The full text belongs in the bell, which only the authenticated user reads. The one exception is the model's own deferred alerts (`task:{id}:{type}`), which are deliberate alerts and already flattened and bounded. Per producer:

- **A scheduler park** stores `confirmation.park_title(task_id)` and `PARK_BODY`, or `PARK_BELL_BODY` when the question is in no room, and never the answer. The bell does not read the body: `ConfirmationResolver` renders the question from the live task's `confirmation_prompt`, the phone branch included. It does render the stored title, for the gate's row as for the park's, so the bell names an item as its push did (#663); recomputing it from the task gave an email-origin park the gate's held-mail label. The owed re-push after the question's own delivery failed goes through `confirmation.owed_push`, whose `PARK_UNDELIVERED_BODY` does not send the user back to where the delivery just failed; it is owed only when a private room that pushes (Talk or WhatsApp) failed its send, since a web-only private room's row is its delivery and the park pushes `PARK_BODY` at once (#661). The email gate's row is unchanged, since its title and body are the gate's own composed text.
- **The three undelivered-result fallbacks in `process_one_task`** (the Talk post, the email reply, the emailed request that failed) set two values: `failure_alert` is the record and goes into the `undelivered:` row, and `failure_alert_push` comes from `task_alert.undelivered_push`. An `undelivered:` row's body is capped at `MAX_UNDELIVERED_BODY_CHARS` rather than the usual 1,000, on write and on read, because it is the only copy of a whole answer that reached nobody. It is still `flatten_body`'s rendering, so code fences, link brackets and blank lines do not survive; the push therefore says "a copy", not "the full text".
- **A private note with no private room** (`rooms.private_replies._bell_note`) keeps the note in its row and pushes the title and `PRIVATE_NOTE_POINTER`, through `_common.pushing_only`, which replaces a `RaiseResult`'s push text and leaves the row alone.

**A row that is the user's copy stays until dismissed.** `task_alert` closes on being seen and on the 14-day alert sweep, which would take the copy the pointer names after one panel open. A resolver may name `kept_until_dismissed` dedup-key prefixes; `task_alert` names `undelivered:` and `private-note:`, `store.mark_seen` and `sweep_expired_alerts` skip them (the sweep with `substr`, not `LIKE`), and the view's `status_note` says Dismiss is what clears it. The read is `sources.kept_until_dismissed`, so the store stays source-agnostic.

No generic check can tell whether a string is "the answer", so each producer has a test that drives its real path and asserts the answer is absent from what `send_notification` was handed: `test_private_channel_push.TestThePark`, `test_talk_result_undelivered`, `test_email_self_reply_residue` and `test_private_replies.TestTheBellFallback`. A new alert producer that has somebody's words to carry follows the same split and gets the same test.

## notifications/sources.py

The resolver seam: `NotificationRow`/`NotificationView`/`NotificationAction`, the registry, and `SAFE_PATH_RE`. A resolver returning `None` means the object is gone — that single value is the whole anti-staleness story, so an item answered over Talk can never render stale. Resolvers are a backstop, not the primary close path. `auto_resolve_on_seen` splits object-backed rows (something closes them) from fire-and-forget ones (nothing will, so seeing them closes them). Runs in the **web process**: no heavy module-scope imports, registration explicit rather than by import side effect. Imports nothing from the package

## notifications/resolvers/

One module per notification source: its `SOURCE` id, its `dedup_key` spelling, the `write` / `resolve_for_*` producer helpers and the resolver, all in one file so the three cannot drift — the key is load-bearing (`UNIQUE (user_id, source, dedup_key)` is what the backfill claims idempotency from). Ten ship today. Seven are **object-backed** (`auto_resolve_on_seen = False`), so something outside the table closes them: `confirmation` (a task in `pending_confirmation`), `outbound_draft` (a held reply, with Send, Discard and an Open LINK to `/chat/r/<room>/t/<task>`, the room being the one holding the task's email note (`private_replies.note_room_for_task`) else the draft's own `room_token`, and no Open with neither or with no task), `cron_job` (a scheduled job the scheduler switched off after N consecutive failures), `connected_service` (a stored credential that stopped working — Garmin, the user-scoped Nextcloud OAuth pair) `health_panel` (a bloodwork panel left in `draft` after OCR) `relay_question` (a relay question waiting on its recipient, open while the relay is `waiting` or `uncertain`) and `job_failure` (a scheduled job or briefing that failed for good, ISSUE-632: keyed `task:<id>` on the failed task, closed when a newer run of the same job exists or the job is gone, with a Run now action posting to `/chat/tasks/{id}/retry`; written and delivered from `process_one_task`'s terminal-failure branch, never for a `_module.*` job or when the same failure raised `cron_job`, and its body carries no error text, since the push follows alert routing and the scheduler keeps that error out of the job's room). Three are **fire-and-forget**: `message_relay`, the asker's body-free relay notice, `admin_profile_change` (an admin changed another user's email addresses, SMS or WhatsApp number or login email; the body names the fields and the acting admin and never a value, the key is built from the fixed field names, and the admin user routes write it in their own transaction and `deliver_pending` after the commit), and `task_alert` (all `auto_resolve_on_seen = True`). `task_alert` is the one where the delivery rule below bites hardest: it carries the five one-shot alerts that used to be a push and nothing behind it — a deferred alert the model wrote inside the sandbox, a mail-throttle notice, an expired confirmation, the DMARC canary's verdict, and a task result that reached nobody — and three of those five producers keep their own send entirely. A sixth writes and never delivers: the room migration's partial (`maintenance.room_relocate.record_outcome`, ISSUE-588), raised from the deploy's offline window with every service stopped, fanned out through `admin_readers` and closed by the next clean run. Another producer is `private-note:<reference>`, a private reply for a shared-room member with no private room to take it (`rooms.private_replies`). For an email thread's note the reference is the task id alone (`private_replies._bell_reference`), so every path announcing one note shares one `private-note:<task>` row and a retry pushes once: no private room, a Talk or WhatsApp push that reached nobody, and a web-only private room, where `send_private` writes the row and delivers it with `room_free=True` (ntfy and email only), since the note is already in a room. A Talk or WhatsApp private room gets the post and no row. That push covers kind `pass_on` only; a whisper to a web-only room is still unannounced. Open rows written before this keep their old `<task>-pass-on` key. Its resolver **never returns `None` on any path**, because `None` means "the object is gone" and `list_open` marks those `stale`; a row with no object behind it would then close a notice the user has not read, silently and for good, since nothing raises it a second time. Every axis its `dedup_key` is built from is bounded (`_slug`), since `alert_type` comes from the model's JSON and `verdict` from a parsed mail header, and an unbounded axis means one durable row per attacker-chosen value, each firing a push. Bodies take `flatten_body`, which strips **less** than the title's `flatten`: the label rule deletes `* _ ~` and every newline, and in a body that is corruption — `rm -rf ~/Documents` would be delivered as a different command. **Each resolver's close predicate is the thing that actually ends the condition, which is not always the obvious column** — `cron_job` watches `auto_disabled_at`, not `enabled`, because `sync_cron_jobs_to_db` treats CRON.md as authoritative for `enabled` and runs every tick, so a file-defined job is switched back on within a tick of being auto-disabled; the same sync leaves the state columns alone. **And that source has two close predicates, because one column means two different things depending on the row.** A `_module.*` job closes on a success since `row.updated_at` (`last_success_at`, whose one writer is `reset_scheduled_job_failures`), never on `auto_disabled_at`: `_sync_module_jobs` has a rescue arm that clears that column — along with `consecutive_failures` and `last_error` — on an hourly cooldown whether or not anything was fixed, so on a module row it is a retry rather than a repair and says nothing about the condition. Reading it as a close is what made the source unsafe for these rows and got the whole prefix excluded from it: raised on the suspend, marked stale by the rescue, then *reopened* by the next suspension — and a reopen delivers. The exclusion was the wrong half to fix, because `_sync_module_jobs` also seeds every module row `skip_log_channel = 1`, so a job failing on every run reached neither the inbox nor the log channel and left nothing behind but `scheduled_jobs.last_error` (ISSUE-391). With the predicate corrected the row stays open across the loop and later suspensions *bump* it, which does not deliver — one push per outage. The module branch also renders the **stored** `row.title` / `row.body` rather than recomputing from the live job, since by the time most panel reads land the rescue has wiped the failure count and the error the row exists to carry. A module job failing for an actionable reason still raises its own more specific source in parallel (a dead Garmin credential raises `connected_service`). **A confirmation's push is room-free when its question is already in a room** (#625, email on rooms stage 5). `confirmation.write(in_room=True)` returns its `RaiseResult` with `room_free=True`, and `deliver_pending` hands such a result to `send_notification(only_surfaces=store.ROOM_FREE_SURFACES)`, which cuts the resolved destinations to ntfy and email; an empty cut sends nothing and the row stands undelivered. A question in the private room, the web room it was asked in or the Talk room would land in a second room on a Talk, web, SMS or WhatsApp leg; SMS and WhatsApp are out because each records a push in its phone room. **Two producers pass `in_room=False`, because their question is in no room** and a cut to ntfy and email would reach nobody who routes alerts to Talk: the scheduler's private park when `private_park.dest is None` (the bell row is the only place the question is), and the email gate, whose row is pushed only by `_deliver_confirmation_prompts`' fallback after its own prompt reached nobody. **A third case recomputes it: the owed push after a failed post** (#635). A room-free row withheld at the park because a Talk, SMS or WhatsApp post was going to carry the question is re-delivered by `process_one_task`'s owed-debt arm when that post fails, and there the question is in a room only if `db.task_shown_in_room` says the web view renders the parked task (or a private park wrote its row); otherwise the arm clears `room_free` before `deliver_pending`. An unregistered Talk conversation, a phone thread and an email mirror with no stored turn show it nowhere. The arm also sets `RaiseResult.skip_surfaces` to the SMS or WhatsApp leg that failed or came back unknown, which `deliver_pending` passes to `send_notification(skip_surfaces=)`: a ledger never resends an ambiguous send, and a push there would be one under a new key. The flag stays on `RaiseResult`, one way to ask. The flag is in memory only and set by the source, not by each producer, so a new park cannot forget it. **Delivery is per producer, not per source.** `connected_service` delivers because the wiped credential takes the sync job with it and nothing will notice again; `health_panel` writes and never delivers, because the producer is the upload handler and the user is on the review screen it just returned them to. `relay_question` is split by destination kind rather than by producer: a room question is written and delivered with `deliver_pending` after the transaction that moved the relay to `waiting`, while a WhatsApp or SMS question is written and not delivered, since the message on the phone is already the push. Its stored body is fixed text naming how to answer and never the question, because a push follows the recipient's alert routing, which can reach a shared room; the resolver shows the question, fenced, in the authenticated bell only. Its one action links to `/chat/r/<room token>`, a server redirect on the web app, because the chat's own deep link carries a query string, which `SAFE_PATH_RE` and the client's `isSafeActionPath` refuse, and widening both was decided against (#624); a token the allowlist refuses falls back to `/chat`. **A relay-held confirmation has no Confirm where a private room shows its preview** (#624): for a task with `whatsapp_confirmation_request_id` (a relay question, a `room post`, a guest proposal) the resolver renders a title by kind (`confirmations.describe_title`), the destination's label and the preview's first two lines fenced as `APPROVAL PREVIEW`, and the actions Open (a LINK to `/chat/r/<room>/t/<task>`, the first of `private_replies.preview_rooms`) and Discard. The confirm route refuses such a task without the room showing its preview, so a Confirm here would only approve a post nobody had seen. **With no preview room the bell shows the whole preview, fenced, and a Confirm** (#633) whose endpoint carries the preview's digest (`bell_confirm_endpoint`) and which is `detail_only`: `NotificationAction.detail_only` keeps it out of the list row, so it is offered only beside the body it approves. The stored title and body stay fixed text. **A source can have several producers and the row does not say which** — the confirmation row is written by both the inbound email gate and the scheduler's mid-run park, with identical `source_type`, so anything the resolver renders has to be right for both: it reads `tasks.confirmation_prompt`, which is the gate's own composed message in one case and the model's question in the other, and never `tasks.prompt`, which for a gated email *is* the withheld body. Each resolver coerces `object_id` with `int()` before interpolating it into an API path and re-checks that the object it found belongs to the row's user — the id is a value on the row, not something the query scoped. `connected_service` keys on a service *name* rather than an integer, so an explicit allowlist stands in for the coercion. `health_panel` is the cross-user trap the store's `user_id` argument exists for: panel ids come from the per-user health module DB, so the row goes against `ctx.framework_db_path` (never `ctx.db_path`) and the resolver opens the module for `row.user_id` rather than for whoever is reading. Registered explicitly by `notifications.sources._register_all`, each import guarded so one broken module costs its own source and not the registry
