# SMS

SMS is one provider-neutral, user-routable push surface with Twilio and Telnyx adapters. It is never a room member or view, writes no `messages` row, and uses the stable `sms-<user hash>` conversation token plus task history for context. A bare `sms` destination resolves the user's current binding immediately before send. A descriptor carrying a phone number is never sent to — the binding wins and the number is ignored with a warning — so the route grammar cannot become a way to send to an arbitrary number. A destination whose user has no binding is kept rather than dropped, and records `unconfigured` with a task alert: dropping it empties the plan, which discards the answer and makes an SMS-origin confirmation complete instead of parking.

The phone binding is an identity credential. Exact E.164 lookup decides which user an authenticated inbound event may act as. It can create tasks, dispatch commands, and answer that user's pending SMS confirmations. Unknown senders create no task and are not retained. Changing or clearing the binding revokes delivery to the old number.

Provider adapters own signature verification, provider payloads, account or profile checks, acknowledgements, send calls, exception classification, and status mapping. Common code sees only `SmsProviderEvent`, `SmsSendRequest`, `SmsSendResult`, and public error codes. A complete inactive adapter may authenticate late delivery callbacks, but its inbound messages create no task.

Outbound work is ledger-backed and one-send. The caller supplies a stable logical id, the row claims one provider before the network call, and a timeout or other ambiguous outcome becomes `unknown` with no retry or provider failover. The renderer sends one provider message within the configured GSM-7 or UCS-2 segment budget. Provider acceptance is not handset delivery.

`logical_key` is UNIQUE across the whole `sent_sms` table and nothing deletes from it, so a claim is permanent and two messages that share a key are one send. Three namespaces produce one: `task-result:<task id>` for a task's final answer, `confirmation:<notification id>` and `confirmation-task:<task id>` for the question that parked it, and `notification:<uuid>` for a raise with no task. **A confirmation prompt must never be able to reach the `task-result:` key**, which is what the scheduler's ungated fallback at the park is for: derived only from the notification row, it fell through whenever `write_notification` returned `None`, the prompt settled the answer's key, and the answer the user had just approved was refused for good (ISSUE-489). The fallback has a namespace of its own because a task id and a notification id are independent small integers — sharing the `confirmation:` prefix let one task's fallback key permanently swallow another task's prompt. `sent_whatsapp` is the same table under the same rule.

**Still open: a task that parks twice.** The notification row is keyed `task:<id>`, so a re-park reuses its id and therefore its ledger key, and the second question is refused as a duplicate claim. The refusal reports the *settled row's own* status rather than a failure, and in the ordinary case that status is in `REACHED_PROVIDER`, so neither `sms_undelivered` nor the owed-notification arm pays the debt and the task waits on an answer to a question nobody saw. Do not read that as "always `accepted`": the reported value is whatever the first send left on the row, and on the WhatsApp twin a delivery callback arriving between the two parks can make it a terminal failure instead (ISSUE-490). Silent either way, and that is the defect — not the particular value. Pre-existing, and the same shape on both surfaces. Fixing it means making the key vary per park, which `tasks.attempt_count` cannot do (`confirm_task` requeues without bumping it); the candidates are the notification's `occurrences` counter, which `RaiseResult` does not currently carry, or a digest of the prompt.

**A status callback can arrive before the id it names**, because the provider mints that id in its reply to the send and `_set_outcome` writes it a statement later. Such a callback matches no row; discarding it is harmless for `queued` and `sent`, which a later status supersedes, and silently wrong for `failed` — the row keeps whatever the provider said at accept time, no alert is raised, and the surface reports a delivery that failed. It is held in `sms_parked_status` and replayed by `_settle_and_drain` once the id lands. The WhatsApp twin is `whatsapp_parked_status`; this is the same fix on the live surface, and the two differ only where the ledgers do.

**The delivery branch takes `BEGIN IMMEDIATE`, but only where a park is possible, and that pair of facts is the change to notice.** It previously ran under no explicit transaction, which was harmless while it only read a row and updated it, and stopped being harmless the moment the lookup could be followed by a park: unless the write lock is held across both, the outcome write can commit the id in between, leaving a parked row nothing will ever drain and a `failed` lost exactly as before. Removing the line turns `test_a_status_racing_the_id_write_is_never_lost` red every run, on the row's status rather than on a lock error.

Taking it unconditionally was the first version and costs too much to keep: a provider sends three or four statuses per message, all but the first find their row, and those used to complete on one `SELECT` in autocommit with no write lock at all. The route calls `handle_provider_event` synchronously on the event loop with a 30s busy timeout, and under `istota serve` that router is mounted on the web app — so a lock held across the daemon's other writers is a stalled receiver and a stalled web UI, not a slow query. `delivery_may_park` is the unlocked pre-read that keeps the common callbacks off the lock; the authoritative read is `apply_delivery_event`'s own, which happens under it, so a row appearing in between is simply found and applied. The inbound branch takes its own `BEGIN IMMEDIATE` for the analogous reason, and the two cannot collide because the delivery branch returns first.

**The replay is a second transaction, after the outcome commits.** Sharing one reads better and is wrong: `db.get_db` commits only on a clean exit, so a raise out of any replay — a notification write, an opt-out insert, a parked table a half-upgraded host has not created yet — would unwind the `provider_message_id` write with it, and a message the provider accepted whose id was never recorded can never be matched by a later status. The replay is also never allowed to raise past `_settle_and_drain`.

The replay goes back through `apply_delivery_event` rather than writing the row, which keeps the one-send contract — the ladder refuses a row already in `_TERMINAL_STATUSES`, so a `failed` drained ahead of a `delivered` parked after it closes the row and the `delivered` is a duplicate — and is also what performs the **opt-out** a parked status may carry. That last one is why a direct write is not merely less tidy: `opted_out` is a request that was made, and dropping it keeps texting somebody who asked to stop. `_set_outcome` now carries the same terminal set as a `WHERE` clause, which the write had always needed and not only since parking: several paths write an outcome, and a replayed status can have taken the row terminal in between.

**Parking is bounded twice and needs both bounds.** A status is parked only while a send *on that provider* sits between its claim and its settle — `status = 'pending'` with a claim stamped and no id. The provider scope is available here and not on the WhatsApp twin, because the event names its provider and the ledger key is the pair. That gate alone is not enough, since a send killed between those two points leaves an in-flight row nothing clears, so a row past the window is pruned whenever the table is touched — on an attempted park, *before* its gate, and on a drain. Behind the gate the only thing clearing the table would be a successful park, which is exactly the deployment that has gone quiet keeping its rows for good. A pruned row is a status istota held and could not place, so the count is logged as a warning.

**The parked row stores the provider's id as given, where the WhatsApp table keys on a fingerprint.** Deliberate rather than overlooked: this module logs `provider_message_id` in full on every transition, so a fingerprint here would reduce nothing while the log lines beside it print the value. Whether the SMS surface should mask ids the way the WhatsApp one does is a wider question than this table. What the id does get is a **bound**: `MAX_PROVIDER_MESSAGE_ID`, the inbound branch's own 255 lifted to one spelling both branches read, because an unbounded provider-chosen string on a uniquely-indexed column is the axis `write_delivery_failure` hashes its dedup key to avoid. An empty id is refused for a plainer reason — it can match no row, since the column is NULL on an unsettled one rather than empty.

**WhatsApp is the authoritative copy.** It was fixed first and the SMS version is a port. Four things genuinely differ — the key, the provider-scoped gate, the alert shape and the fingerprint — so the two are not consolidated; `transport/_alerts.py` is the counter-example that was worth sharing, where the copies differed only in a surface name. `tests/test_delivery_parking_parity.py` is what holds the set of moving parts in step, and states the divergences.

**Two residuals, both shared with the WhatsApp twin and neither closed here.** A drain that fails is not retried: `_settle_and_drain` swallows the exception so the id write survives, and nothing drains that row again, so a parked `failed` can still be lost. It is no longer lost *silently* — `_prune_parked_statuses` counts expiring rows whose id now matches a `sent_sms` row and logs those as `sms.delivery.parked_lost`, apart from the foreign traffic it logs as `parked_expired` — but a sweeper that replays matchable rows is the real fix and belongs to both surfaces at once. And nothing reaps a stale claim: a daemon killed between the claim and the settle leaves a `pending` row with a claim and no id for the life of the deployment, which holds the park gate open for that provider. Those rows are invisible to every surface today, so a reaper is independently worth having.

STOP and START state is stored by phone number in `sms_opt_outs`, outside the provider namespace. Switching providers preserves user bindings, routes, conversation history, opt-outs, and common ledger rows. Keep the old complete provider block until its outstanding callbacks settle if later delivery state matters.

The webhook receiver mounts `/webhooks/sms/twilio` and `/webhooks/sms/telnyx`. Docker and Ansible run one receiver for location, active SMS, complete callback-only provider configuration, or WhatsApp. The combined `istota serve` process includes each configured surface's router on its web port, and no other — location, SMS and WhatsApp are three independent gates over one mount. Provider setup and operating steps are in `docs/features/sms.md`.
