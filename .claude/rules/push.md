# Native iOS push

`push/dispatch.py` is the only automatic APNs sender, and `push/delivery.py:send_prepared` is the only caller of `apns.send`. The dispatcher adds delivery to the inbox and chat without changing transport routing; `istota push test --user U` is the manual diagnostic. `write_notification` sets `push_pending` on insert and reopen, inside the producer's transaction, and leaves it alone on occurrence bumps. Neither the web request nor `deliver_pending` calls APNs.

The scheduler's `push-dispatch` interval gate uses the existing `_spawn_background_check` seam beside heartbeats. Only one sweep can run at a time; the gate skips overlapping ticks, and the dispatcher also refuses overlapping direct calls. A slow device must not hold up task dispatch. The interval comes from `config.push.dispatch_interval_seconds`, captured when the gate table is built. Zero disables the gate. Missing HTTP/2 support, a disabled deployment or a missing key file produces one warning per process and leaves pending work alone.

Each sweep reads one bounded pending-notification batch and one delayed message ceiling. For each user it computes one badge, sends inbox alerts, groups chat candidates into one alert per room, then sends a quiet badge update if no alert carried that number and the stored device badge differs. `push/preferences.py:push_badge_count` is the only badge calculation, shared by dispatch, the diagnostic CLI and `/notifications/count`. It counts enabled inbox sources and unread messages in rooms whose effective mode is alerts or badge. Category IDs come from `notifications.sources.all_resolvers`; labels live once in `notification_categories`, with a readable fallback. Missing category keys are enabled. Disabled sources are still acknowledged so enabling them does not replay alerts. The bell and ordinary unread counters remain unfiltered; `/notifications/count` adds `push_badge` separately. Badge query errors propagate, so a failed query cannot announce zero. Results update each device through `devices.record_result`; failed alerts are acknowledged without a retry, and a later badge-only push repairs the count. Every APNs request expires immediately rather than queuing a backlog with Apple. APNs acceptance is not delivery confirmation: an offline phone can miss a badge update, and an unchanged total is not retried. Opening the app reasserts the current count; recovery without opening the app needs a separate retry or expiry policy.

No write transaction spans network I/O. Notification flags clear after attempts, guarded by the sampled `updated_at` and `occurrences` so a concurrent reopen is not erased. A concurrent refresh can therefore leave one additional alert pending. A process killed after a successful send but before its acknowledgement can repeat that alert; there is no atomic transaction across SQLite and APNs. Chat watermarks also advance only after the user pass. Failures for one user are contained.

`web_chat_rooms.push_notifications` belongs to the recipient's handle, like colour. An explicit override wins even when `push_chat_alerts` is off. Both unread queries join that handle, retain membership/archive/dismissal/hidden-email predicates and never advance read cursors. The room PATCH requires current membership as well as handle ownership for preference writes; a non-host can edit their own setting. The chat query must still run when the account default is off. Suppressed chat advances the sender watermark, so enabling alerts later does not replay it.

The chat ceiling is the highest message ID old enough for `chat_delay_seconds`; the watermark advances to that ceiling, never to the highest scanned ID. Otherwise a message inside its quiet delay is skipped forever. `db.unread_rooms_since` shares the unread aggregate's membership, read cursor, archive, dismissal and hidden-email-room predicates. A recent room with no web handle gets one through `db.ensure_web_chat_handle` before sending, without advancing its read cursor. Room handles belong to the recipient, including shared rooms. Candidates older than `max_age_seconds` advance the watermark without banners. A user's first registration seeds its watermark at the current message maximum.

`(token, environment)` is unique. Registration moves an existing token to the current user and resets its delivery state. Before each send the sweep checks that the captured registration still belongs to that user. Results carry the registration's `created_at` so a late response cannot modify a newer registration. A token move during an APNs request cannot retract that in-flight request. Registration timestamps advance even if two registrations share the same millisecond. Never log a full token or a credential.

Registration stores the validated auth method and credential epoch, never a cookie. `webui.auth.validate_session_credential` is shared with the session gate; `devices.registration_authorized` rechecks it before each send and refuses legacy metadata-less enrollments. A disabled method/account, changed epoch or unavailable email/local-code identity/profile refuses delivery. Nextcloud retains its existing session authorization rules. Local no-auth enrollment is restricted to the configured local user while that mode remains enabled. Cookie expiry alone does not revoke persistent enrollment: there is no server session registry, and a fixed expiry would disagree with rolling cookies. Explicit logout deletes rows bound in SQLite to the existing login session ID; ordinary concurrent responses cannot overwrite this binding. Another account or a later login that re-registers the token replaces that binding, so an older login cannot remove it. Authenticated legacy cookies without a login ID must sign in again before enrolling. Local no-auth mode has no login to revoke and uses device removal instead. Revocation after the final check can still race an in-flight APNs request.

The generic iOS shell (0.12.0 and later) sends `connection_binding`, a lowercase UUID its native code generated for the connection, and `connection_generation`, a positive integer no larger than 2^53 - 1, with each registration. Both or neither; older binaries send neither. They are stored on the row, and `delivery._for_device` adds them to that device's `istota` routing object, so the app can refuse a tap that belongs to a connection it has since left. A room or notification ID alone is not unique across servers. A registration without them clears an earlier binding. Badge-only updates carry no routing and no binding: iOS applies a badge, and displays an alert, before any app code runs, so the binding protects opening, not display. The device list never returns the binding. The app records the returned registration ID natively so a later disconnect can call the existing DELETE.

The provider token uses ES256. `cryptography` returns a DER signature; JWS requires the raw 64-byte `r || s` form. Keep the generated-key verification in `test_push_apns.py`. Provider tokens last 50 minutes in the cache and cannot be minted more often than every 20 minutes, including an expiry rejection. APNs uses HTTP/2 and the host selected by each device's environment. A wrong environment invalidates a device; deployment credential errors do not.

A chat preview's body is first flattened from Markdown to plain text (`lib/markdown_plain.to_plain_text`), before the cut, so markup cannot spend its length; an inbox notification body is not, since the web inbox shows it as text. Alert text strips controls, collapses whitespace and caps titles and bodies at 80 and 180 characters. The serialized payload is bounded to 4096 UTF-8 bytes; oversize alerts lose their body, then shorten the title. An envelope that cannot fit is refused. `push_preview = false` uses a generic notification title or a room label and an empty body, while retaining navigation data. Links use the inbox's existing safe-path predicate. Under `content = "legacy"` Apple can read these payloads; they are not end-to-end encrypted. Private delivery is below. These native previews are separate from routed alert messages, whose more restrictive conversation-text rule remains in `notifications.md`.

Badge-only updates are alert-type APNs pushes at priority 5, collapse ID `badge`, with only `aps.badge`. They use neither sound nor `content-available` and require no background notification mode. Alert pushes use priority 10 and carry the same badge; chat uses `room:<token>` for both collapse ID and thread ID.

## The delivery seam and the content modes

The dispatcher and `istota push test` describe each alert once, as a `delivery.LogicalPush` (raw title and body, badge, legacy `thread`, collapse `group`, target), and `build_delivery(config, device, logical, now=, signing_key=)` turns it into a `PreparedPush`: the exact APNs bytes, collapse ID, priority, kind, badge and event ID. `apns.send` takes those bytes as they are, so what was measured is what is sent; its own 4096-byte check stays. The test command goes through the same two functions so it cannot drift from dispatch. All of a user's payloads are built before any is sent.

The mode per device is `devices.device_content(config.push.content, device, sender_key_id)`, the same rule the device list shows; `delivery.effective_content` calls it and restates nothing. `legacy` is the installation default and is the old helpers (`_alert_payload`, `_for_device`, `_fit_payload`, `_sanitize`), moved into `delivery.py` unchanged; `tests/golden/push/legacy_wire.json` is a full legacy sweep's wire output from before the move and `tests/test_push_delivery.py` holds every byte and header to it. Under `private`, a device with an encrypted enrollment whose `sender_key_id` is the current key gets `envelope.seal`; every other device gets the generic alert (bot name, fixed body, badge, no routing, no `mutable-content`, no collapse ID). A device enrolled under an older key is sent generic content and its row is not cleared, so the card can say it needs to enroll again. Badge-only updates are identical in every mode.

**A private installation never sends plaintext.** There is no fallback: `build_delivery` refuses any alert on a private deployment without a signing key, and the dispatcher reads the key once per sweep (`_signing_key`), warns once per process when it cannot, and returns before taking pending work, so notifications stay pending and watermarks do not move. A sealed payload that cannot be built raises `DeliveryError`: a bad stored device key records `private_payload`, an envelope over 4096 bytes `payload_too_large`, through `devices.record_refusal`, which leaves the enrollment columns alone. The log line names the device ID and the exception class, never a title, body, header, envelope, key or generation. A legacy envelope that cannot fit still raises `ValueError` and aborts the user before anything is sent, as it always has.

Sealing uses the dispatcher's `now` (`iat = int(now)`, `exp = iat + 300`), a fresh `mid` per device per alert, the title and body sanitized and capped here before `seal`, `_sanitize(bot_name, 80)` as the outer title, and the target with `connection_binding` and `connection_generation` added as `_for_device` adds them, or `{"kind": "inbox"}` for a target-less alert. Notification alerts have no collapse group in either mode, so their envelope's `collapse` and `group` are null; chat alerts collapse on the HMAC of `room:<token>` per binding.

The wire format is `docs/reference/private-push-v1.md`, and `tests/fixtures/private_push_v1/vectors.json` is the contract the iOS app and the relay test against. A change to the envelope, the page or the vectors is a change for both other repositories, and `tests/test_push_envelope.py` re-opens every vector so a regenerated file that no longer opens fails here.
