# Sharing with Istota

Open protocols beside the bot-account share (`.claude/rules/web-ui.md`, "The Nextcloud connection card"), which stays: an ICS feed a user subscribes Istota to, Istota's own calendar (invitations or a feed), and Open Cloud Mesh folder shares. User docs: `docs/features/sharing.md`. The design is the open-protocol-sharing spec; its `## Decisions` section holds the rejected alternatives.

## Shared sources

`sharing/sources.py` is the `shared_sources` store: one row per ICS feed (`ics_feed`) or OCM share (`ocm_share`), keyed `UNIQUE (user_id, kind, remote_key)` (a feed's key is the SHA-256 of its normalized URL, a share's `<sender host>|<providerId>`). Every function takes the owner's `user_id` in the statement, so another user's id reads as absent. The two cross-user reads are named for their one caller each: `due_sources` (the poller) and `shares_for_provider` (`receive_notification`, which matches the secret afterwards).

States: `pending` (an offer), `active`, `error` (reachable, last use failed), `declined`, `revoked`. A feed starts `active`, an offer `pending`; `_TRANSITIONS` is the whole lifecycle and anything else raises. **A move into `declined` or `revoked` deletes every secret in the same transaction** (`_remove_secrets`): the `shared_source` secrets `<id>` and `<id>:reoffer`, the `ocm_share_<id>` local credential and the feed's `shared_feed_cache` row. The row itself stays, so a repeat of the same resource is recognized: a removed feed added again reactivates, a revoked share offered again becomes `pending`, a declined one stays declined.

**Where the secret lives follows who reads it.** A feed URL, and an OCM secret held while pending or re-offered, are `secrets` rows under service `shared_source`, read with `get_secret(touch=False)`; daemon-owned like `mail_account`, so not in `credentials/schema.py`. An accepted share's secret is a local credential `ocm_share_<id>` bound to `https://<sender host>`, because a skill reads it (the web process reads it too, for its owner only: "The Files page" below), and the private credential channel, the snapshot, the fetch budget, the broker grant and `vault_isolation_refusal` already enforce everything such a read needs. It shows in Settings > Credentials, the KeePass export and the backups, which was accepted. `ocm_share_` is in `credentials/local._RESERVED_PREFIXES`; only `sharing/ocm.py` passes `system_prefix="ocm_share_"`, so the user's edit form can change the grant and delete it, never the value or site.

**Reach is ISSUE-576's, with no per-source room policy.** `sources_for_task(conn, task, *, kind, skill_index)` is the one task-side listing: nothing when the kind's scope (`calendar` for feeds, `shares` for shares, `KIND_SCOPE`) is withheld or the skill is not in the index. The system-half lines (`Other calendars ...`, `Shared folders ...`, ids and hosts only, through `executor._one_line`) are left out under `rooms.scopes.ambient_memory_off`, which is also true in any group-owned room; the host's own turn in an email thread room keeps them. Third-party names never reach the system half.

`user_profiles.delete_profile` calls `sources.delete_for_user` and `events.delete_for_user` on its own connection, so a deleted account leaves no row, secret, credential, cache, event, invitation or feed token.

## Fetching

Every daemon-side fetch to a host a user or a remote server chose goes through `sandbox/guarded_http.guarded_send` (`.claude/rules/sandbox.md`) with `[sharing] private_hosts` (exact names, `config._warn_malformed_private_hosts`). Failures become one fixed code in `last_reason` (`host_refused`, `too_large`, `redirect_refused`, `connection_failed`, `timeout`, `http_<status>`, `not_a_calendar`, `share_revoked`, `secret_missing`, `secret_unreadable`); response text, a URL's path or query and any secret never reach a log, a row or an exception.

## ICS feeds

`sharing/ics.py`. Added only in the web UI (`POST /settings/sharing/feeds`, body parsed by hand, since a 422 would echo the URL): one guarded fetch (`max_redirects=3`, `ics_max_bytes`), `icalendar` validation, then row, secret and cache in one transaction, capped by `ics_max_feeds_per_user` before the fetch and again under the write lock. No task verb adds one, because the URL would sit in tool-call arguments and transcripts. The `sharing-ics-poll` gate looks every minute for rows whose `next_poll_at` has come; each feed is polled every `ics_poll_interval` with conditional GET, backed off by `feeds/poller._backoff_interval` and `_rate_limit_interval`, and keeps its last good cache through failures. With no master key the poll does nothing, so a key outage cannot revoke every feed. Tasks read `shared_feed_cache`, never the network (the calendar skill, `.claude/rules/skills.md`). Feeds deliberately stay out of `executor.discover_calendars_for_task`, whose result gates the bot account's CalDAV credential (ISSUE-673).

## Istota's calendar and its delivery

`sharing/events.py`: `istota_events` rows (UTC, single events, UID `<uuid4>@<site host>`) written only by the deferred op file `task_<id>_istota_events.json` (`scheduler_deferred._process_deferred_istota_events`, `.claude/rules/scheduler.md`), user from the task, at most `[sharing] events_per_task` entries applied whatever the file says. `user_profiles.calendar_delivery` is `invite` (default) or `feed`, never both, since both shows each event twice; `[email] enabled = false` forces `feed`.

The feed is `GET /istota/calendar/<token>.ics` (`sharing/feed_routes.py`): no session, the token stored as its SHA-256 digest (`calendar_feed_tokens`, one live per user), 404 for an unknown one, an ETag, and `lib/rate_limit.SlidingWindow` at 120 an hour per token and 600 per client address (a hosted calendar service polls many users from one address). nginx's `location ^~ /istota/calendar/` has `access_log off`, because the path is the token.

Invitations (`sharing/itip.py`): one mail per UID per apply, through `mail/outbound_policy.recipients_require_hold` and `skills/email.send_email(..., calendar=(method, ics))`, the one daemon send path, sent after the apply's commit with no lock held. There is no retry: a failure records `invite_status = 'send_failed'` and a fixed-text `task_alert`; a user with no address gets `no_address` and one alert. Inbound, `Email.calendar_parts` carries every `text/calendar` or `application/ics` part (4 parts, 256 KiB each). A `METHOD:REPLY` for one of our UIDs is always consumed (`routing_method="itip_reply"`, no task) and applied only when `_answer_refusal` passes, the authenticated From is the owner's and the single ATTENDEE matches; without `[email] authserv_id` none is ever applied. A `REQUEST`/`CANCEL` admitted unheld, DMARC-passing and from its ORGANIZER is recorded in `received_invitations`, keyed on the authenticated sender; nothing is ever sent back.

## OCM receiving

`sharing/ocm.py` and `sharing/ocm_routes.py`, served on `[site] hostname` at the root (`/ocm-provider[/]`, `/.well-known/ocm`, `/ocm/shares`, `/ocm/notifications`). The router is always included and answers a plain 404 per request while `[sharing.ocm] enabled` is off; nginx always routes the paths. `load_config` refuses OCM when the site host is `[nextcloud] url`'s. These are the web app's only fully unauthenticated routes, so the order in `receive_share` is fixed and each step writes nothing on refusal: body shape (400), rate limits before any outbound request or user lookup (429), sender verification by its discovery document and, where it publishes a `publicKey`, a draft-cavage signature (403), the WebDAV base from the verified discovery document only and the master key (503), then the recipient (one 404 body for an unknown host and an unknown user), then the store. Every refusal that holds for any recipient runs before the recipient, so a malformed offer cannot test an address without storing an offer the user would see. The offer's `ownerDisplayName` and `sharedByDisplayName` are kept in `extras` beside `owner` and `shared_by` for the card and the Files index, and never reach a prompt. Istota publishes no key and signs nothing: Nextcloud 31 stores a host's key on the first signed request and refuses unsigned ones from it afterwards, so signing is a one-way switch a later change must make for every request at once.

**A sender learns little about a recipient (#891).** The 201's `recipientDisplayName` echoes the local part of `shareWith` as the sender wrote it, never a profile's name or the stored spelling; OCM makes the field optional and Nextcloud 31 does not read it. A refusal that depends on the recipient (`_RecipientRefused`: unknown, or `too_many_pending`) is answered honestly `RECIPIENT_REFUSALS_PER_DAY` times per sending host and per client address, and `RECIPIENT_REFUSALS_PER_DAY_TOTAL` times across the install, so a mistyped address still fails at the sender with Nextcloud's "could not find". Past that, the same offer gets the 201 and stores nothing, with an INFO log. It answers 201 rather than 429 because an offer with room always stores: an unsigned sender can claim any host, and a 429 would let it stop that host's shares for a day, where this costs only typo feedback. The exception is a real recipient whose inbox is full past the budget: that offer is lost and the sender believes it arrived, so the recipient gets a fixed-text bell row (`TURNED_AWAY_KEY`). A dropped offer is held in memory (`_remember_dropped`: provider id and a digest of the secret, bounded), so `receive_notification` answers it as it would a stored offer, discovery fetch included; a `SHARE_UNSHARED` forgets it as it would revoke a row. Strings a JSON escape can make unencodable are refused at the parser, because the failure would otherwise land after the recipient and answer for them. What remains: 5 guesses a day per host and address and 50 across the install (hosts and IPv6 addresses are cheap to rotate, so 50 is the bound that holds); in-memory limits and dropped-offer records a restart clears; a first stored offer is tens of milliseconds slower than a dropped one (scrypt and the write), though that hit also puts an offer in front of the user. `extras.sender_signed` records whether the offer was signed; the card, the accept dialog and the bell's detail line say so, and none claims a signature proves the person. An offer stored before this has no value and shows neither.

**A repeat offer replaces nothing unless it was signed.** From a sender publishing no key (Nextcloud 30), a repeat for a pending or live share is answered 201 and changes nothing, because anyone holding a secret that host accepts, such as their own public link, could otherwise swap in a folder of their choosing and the accept-time PROPFIND would pass. From a signing sender, a repeat for a pending share replaces its held secret, and one for an `active` share never touches the live credential: the new secret is held under `<id>:reoffer` and `extras.reoffer_pending` is set until the user accepts it. A first offer from an unsigned sender has the same weakness and is the user's call to accept; the bell and card name the sending host. The bell row (`notifications/resolvers/shared_source.py`, dedup key `pending-offers`, one per user, object-backed on waiting offers, with `offers-turned-away` beside it for the full-inbox case above) has fixed text with no sender word (#638), handed to the daemon with `hand_to_daemon` because the web process may not send (ISSUE-702).

**Expected noise for operators**: after any answer but 201, Nextcloud retries on the legacy `/ocs-provider/` and `/ocs/v2.php/cloud/shares` with the secret in the form body; those stay 404 with no location, and the access log records only the path. A Nextcloud caches a discovery result 24 h after a success and 5 min after a failure.

## Accept, decline, remove, notifications

`accept` refuses under `vault_isolation_refusal` before any request, PROPFINDs the root with the held secret (the proof that the verified host accepts it; 401/403/404 leave it pending), reads `oc:permissions` (`C`, `K` or `W` is write; the offer's permission field is a placeholder), re-reads the row and secret under the write lock (`offer_changed` if a repeat replaced either), then creates or updates the local credential and sets `active` in one transaction, and posts `SHARE_ACCEPTED` after the commit. `decline` posts `SHARE_DECLINED`, which makes Nextcloud delete the share; declining a re-offer posts nothing, since that would delete the live share. `remove` revokes and posts `SHARE_DECLINED`. `expire_pending` declines pending rows `pending_days` after their last offer and posts nothing. The bell offers a `detail_only` Accept only when exactly one offer waits, never Decline, since a bell action cannot ask for confirmation.

`POST /ocm/notifications` acts only on a constant-time secret match against the share's stored secret, then the same rate limits and sender verification: `SHARE_UNSHARED` revokes, `RESHARE_CHANGE_PERMISSION` re-reads `oc:permissions`, anything else is 501. Nextcloud sends no notification on a permission change, which is why the `shares` skill re-reads permissions on every invocation (`.claude/rules/skills.md`).

## The Files page (#849)

An `active` or `error` share is a `share:<id>` place (`workspace/places.py`): no root, `browsable` true, `remote: {host, access, kind}` in the places payload (`kind` is `extras.root_kind`, null until the root has been read). The sidebar does not list share places: the bot's section has one index, **From other servers** (`view=shares`, shown when `places.share_index_shown`: OCM receiving with a site hostname, or any share), which renders `components/sharing/FolderShares.svelte` over `GET /settings/sharing`'s `ocm` payload, the component the Settings card uses too, so Accept, Decline and Remove have one implementation. It is the section's last entry, and there the component takes `layout="index"`: ruled record rows like the other indexes, the address help as the copy field's description, and no `share:<id>` line, which the Settings card keeps. A folder row opens the place; a file row opens the viewer on the share's root. `share:<id>` stays the id the skill and the prompt use. The bell's Review link is `/files/shares`, a server redirect to `/istota/files?view=shares` (`SAFE_PATH_RE` takes no query). `/me`'s `features.files` gates the Files link and is true wherever offers can arrive or a share exists; `features.workspace` keeps meaning a workspace or a Drive connection, since the group overview's files card reads it. With no place but shares, the page opens on the index, and the bot section leaves out the entries that live in My files.

**The web process reads the secret** for the signed-in owner's own request, from the local credential (`ocm.share_secret`), as `accept` and `remove` already did, and sends it only to the verified WebDAV base through `guarded_http` with `[sharing] private_hosts`. The credential's grant bounds tasks and does not apply to its owner here. A daemon round trip per folder click was rejected: it adds a queue and seconds to every listing to keep the secret out of a process that already held it. With no master key the routes answer 503 and revoke nothing; a credential row that is gone revokes the share (`secret_missing`), as the skill does.

`webui/share_files.py` serves `/workspace/list?place=share:<id>`, `/workspace/share/preview` and `/workspace/share/file`. Every request starts with `sharing.ocm_files.check_root`, the depth-0 PROPFIND the skill makes, which records access and `root_kind` and revokes on a 401 or 404 (410 `share_revoked`); other failures record `error` and answer 502 with the guard's code. The path rules, the href reduction and the row updates are `sharing/ocm_files.py`, shared with the skill, so the two readers cannot drift. A listing returns direct children only, with `share_path` per entry; a file share lists its one file named by the share, at `share_path` `""`. A download streams through `guarded_http.guarded_stream` under the skill's 64 MB `MAX_TRANSFER_BYTES` (refused before a byte when the listing or the answer declares more, cut off otherwise), forwards one byte range, and is served by `workspace_routes._file_response`, the Nextcloud file route's policy: `attachment` unless the head sniffs as a raster, `nosniff`, sandbox CSP, never the sharer's `Content-Type`. Names come back as JSON strings the page renders as text, and the viewer renders a share's documents with `untrusted` as it does Nextcloud's.

Reach is `skill` in a private room and on a member's turn when `shares` is advertised, `none` for a guest or an unasked task. Not built: writes from the Files page (upload, new folder, delete), pins naming a share (`workspace_pins.provider` is `CHECK`ed to `workspace` and `drive`, so it needs a table rebuild), and the dev mock's share file routes.

## Known gaps

- A held re-offer of an active share never expires: `expire_pending` covers pending rows, and `reoffer_pending` carries no timestamp. It waits until the user accepts or declines it.
- No bell row or push when a remote `SHARE_UNSHARED` or the `shares` skill revokes a share; the card shows it gone on the next load. The resolver is object-backed on waiting offers and would close such a row at once, so it needs resolver behaviour of its own.
- An `error` share has no backoff: there is no poller for shares, so the next invocation retries; `error_count` still counts.
- A share's `ls` path (`share:<id>:<path>`) carries the sharer's file name unfenced, since the model passes it back.
- No provider-captured iTIP REPLY fixtures; the tests use ones built from RFC 6047 and RFC 5546.
