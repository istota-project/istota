# Memory system

## Memory System

- `USER.md` — auto-loaded, optional nightly op-based curation. Runtime writes go through the `memory` skill CLI (`istota-skill memory append|add-heading|remove|replace|remove-heading|remove-subheading|show|headings|skills`) — never `echo >>`. `remove`/`replace` reach bullets anywhere in a section (top region **and** `### subsections`); `replace` rewrites in place; `remove-heading` drops a whole `## ` section and `remove-subheading` one `### ` subsection of it — between them the only way to remove a heading line, or the prose and numbered items `remove` cannot reach; a `remove` that empties a subsection takes its heading too, the same rule that deletes an emptied overlay file; `append --subheading` targets a subsection. The CLI shares the curation `apply_ops` engine, takes a per-file flock (anchor under the per-user deferred dir, not on the Nextcloud mount, so flock stays reliable and the config dir stays clean), and writes a `source="runtime"` audit entry per call.
- `CHANNEL.md` — loaded with `conversation_token`. Same CLI with `--channel TOKEN` (token must match `ISTOTA_CONVERSATION_TOKEN`). Channel writes are not audited (no per-channel audit infrastructure yet) and do not update the stored USER.md fingerprint; the audit/curation pipeline is USER.md-only.
- `config/skills/<skill-name>.md` — per-skill user overlays. Same CLI with `--skill NAME` on `append`/`remove`/`replace`/`remove-subheading`/`show`, plus `istota-skill memory skills` for the inventory (one row per file: skill, bytes, lines, first line, and whether it `binds`). Same flock, atomic write and `source="runtime"` audit entry as USER.md; overlay writes **are** audited, unlike channel writes. The document is flat — no `## ` sections — so `apply_ops` cannot drive it: `curation/overlay.py` parses the whole file as one synthetic `Section` and reuses `ops.py`'s region helpers, which were promoted from private for exactly that (`insert_bullet_in_region`, `find_unique_bullet`, `normalize_to_bullet`, `validate_appendable_line`). Consequences of flatness at the CLI: `--heading` names a `### ` subsection rather than a `## ` section, `append --subheading` is refused as a second spelling of the same target (the flag is on no other sub-parser, so on `remove`/`replace`/`show` it is argparse's exit-2 usage dump rather than an envelope), and `add-heading`/`remove-heading`/`headings` are refused outright. Omitting `--heading` is deliberately not one meaning but two — `_region` returns the top region for an `append`, `_match_region` returns None for `remove`/`replace` and `find_unique_bullet` reads that as the whole document. Collapsing them would either put every append at the end of the file or stop a bare `remove` reaching a bullet inside a subsection, which is what USER.md's `remove` already does. `--skill` and `--channel` are mutually exclusive. An unknown name is refused on every verb that accepts a skill target — including the read-only `show`, because the skill index is the whole of what bounds a caller-supplied path component. (The three heading verbs refuse `--skill` in `_refuse_skill` before `_resolve_target` runs, so they answer `heading_ops_not_valid_with_skill` and never consult the index.) By contrast a denylisted name (`sensitive_actions`, `untrusted_input`) is refused only on the verbs that put text in, since `show`/`remove` add nothing. `append` creates the file, a `remove` that empties it deletes it, and each write re-indexes (outside the lock — a cold sentence-transformers load inside a per-write flock is not a place to pay it). The loading rules and the ordering guarantees live in `.claude/rules/skills.md`; the user-facing page is `docs/configuration/per-user.md`.
- `memories/YYYY-MM-DD.md` — last N days auto-loaded (`auto_load_dated_days`).
- Knowledge graph (`knowledge_facts`) — temporal subject/predicate/object triples, freeform predicates, fuzzy dedup (predicate-equality gated), audited. Sandboxed runtime writes via `istota-skill memory_search add-fact|invalidate|delete-fact` are deferred as `task_<id>_kg_ops.json` and applied by the scheduler post-task.
- Classification gate in `memory/skill.md`: temporal events and stable factual claims → KG; behavioral instructions → USER.md; skill-scoped behavioral rules → that skill's overlay; reusable task procedures → playbooks (sleep-cycle-generated in v1). The USER.md/overlay branch is decided by one test — "would it be *wrong* to ignore this rule on a task where the skill was not loaded? If yes → USER.md; if it is merely irrelevant there → skill overlay" — because a rule in an overlay only reaches the prompt when its skill is selected, and selection is heuristic. That inverts for prohibitions: the task that most needs "never write to the base notes folder" is the one that never recognized itself as a notes task.
- Learned playbooks (`playbooks.enabled`, off by default) — per-user markdown task procedures distilled by the sleep cycle from successful multi-step tasks, stored under the user's bot `playbooks/` dir, indexed into `memory_chunks` as `source_type="playbook"`, and recalled by relevance into a "## Learned Playbooks" prompt section. Markdown-only, never executed; excluded from briefings. Lifecycle (ISSUE-174): the extraction prompt distils the _verified_ command from the trace's per-tool `raw` field (the literal Bash invocation, captured by all three brains) rather than a paraphrase, and writes a thin router instead of re-narrating a single-script task; a `pinned: true` file survives re-derivation (kept on disk, re-indexed so the correction reaches recall); retention (`retention_days`, default 90) prunes on **last-use** mtime (stamped on recall), deletes the pruned file's chunks, never prunes a pinned file, and grandfathers existing files on first upgrade. See `.claude/rules/scheduler.md` (generation) + `.claude/rules/executor.md` (recall).
- The nightly curation prompt carries a skill-overlay inventory — names and line counts only, never bodies — so the curator does not re-add to USER.md a rule that moved into an overlay a week ago. It states in the prompt that the bodies are deliberately withheld, that the ops cannot edit those files, and that the list is grounds not to *add* a rule and never grounds to *remove* one; the curator holds destructive `remove`/`remove_heading` ops and would otherwise have a topic list with nothing to check against. `sleep_cycle._load_skill_overlay_inventory` derives one candidate path per known skill rather than listing the model-writable directory.
- Nightly curator self-heals: bypass-write detection (the `last_seen` fingerprint), sha256 re-read after the LLM call, agents-header migration, Phase-A lint pass logs date-stamped USER.md bullets without migrating them.
- **Curation state lives in the KV store, not beside USER.md.** The audit trail is one `istota_kv` row per write event in `_memory_audit` (key `<ts>-<NNN>`, so several entries in one second cannot upsert over each other — a nightly run emits up to three); `last_seen` and `lint_seen` are single blobs in `_memory_curation`. One row per entry rather than one growing array is what keeps an append O(1). Every namespace starting with `_` is refused by `skills/kv` **and** by `scheduler_deferred`'s applier, and hidden from `kv namespaces` — the predicate is `kv_namespaces.is_reserved_namespace`, a stdlib-only leaf so the skill subprocess needn't import `istota.db`. Both enforcement points are needed: the skill covers a host-side CLI call, the applier covers a sandboxed task, whose `kv set` never reaches the skill's check because the sandbox has no database and the op is replayed from JSON afterwards. This is defence in depth, not the boundary — the boundary is that the framework DB is bound into no sandbox at any path. The three files this replaced (`USER.md.audit.jsonl`, `USER.md.last_seen.json`, `USER.md.lint_seen.json`) sat under `{mount}/Users/{user_id}`, which `build_bwrap_cmd` binds read-write, so a task could wipe its own audit trail or forge the fingerprint. `migrate_user_md_sidecars` imports and removes them from `process_user_sleep_cycle`, **before** its early returns (a user with no interactions leaves within a few lines) and **outside** the `curate_user_memory` gate (that flag is off by default, but the runtime CLI wrote the sidecars regardless). The import is all-or-nothing per file — `_with_conn` wraps the whole `with db.get_db(...)`, and `get_db` commits only on a clean return, so a failure partway leaves nothing committed and the file survives for the next pass rather than being half-imported and duplicated. `curation/lint.py` is now pure: `filter_unseen_candidates` takes the seen dict and returns the updated one, and the caller stores it.
- **Every host-side read and write of `{bot_dir}/config/` goes through one pair of helpers, and neither is optional** (ISSUE-339). `storage.resolve_user_config_dir` is `resolve_user_skill_overlays_dir` one level up — `contained_overlay_dir` against `{mount}/Users/{uid}`, returning the **resolved** path — and `storage.read_user_config_file` is `read_overlay_bytes` behind it. That directory is bound read-write into the user's own sandbox while the daemon reads it unsandboxed, so the two failure modes the overlay path was built against apply unchanged: a symlink resolves in the daemon's larger view and its content becomes prompt text, and a FIFO blocks `open(2)` before the `BrainRequest` exists, where no task timeout reaches it. The readers are `read_user_memory_v2` (USER.md), `load_persona` (PERSONA.md), `cron_loader.load_cron_jobs` (CRON.md), `heartbeat.load_heartbeat_config` (HEARTBEAT.md), `heartbeat`'s task-deadline check (TASKS.md), the memory CLI's `_read_text` and the curator's re-read; the writers are the seeding block, the `examples/` refresh, `_write_cron_md` and the curator. **A reader that joins the mount itself is the bug.** The blast radius is not uniform and that is worth knowing: USER.md and PERSONA.md wedge *prompt assembly*, so one `mkfifo` stopped every later task for that user, while CRON.md and HEARTBEAT.md are read on the **scheduler's own tick**, so one there stopped scheduled work for everyone.
- **`None` means could-not-read and `""` means not-there**, and collapsing them is how the curator came to destroy the file it curates. `current = read_user_memory_v2(...) or ""` made an unreadable USER.md an *empty document*; the post-LLM sha guard then compared a refusal against a refusal, matched by construction, and the ops were serialized over a healthy file — a 1.26 MB USER.md reduced to 456 bytes with the run reporting success, reachable by a task padding its own memory past the read cap. `read_regular_file` is the tri-state leaf for a caller that already holds a resolved path, and the curator uses it for **both** reads: `read_user_config_file` re-resolves `config/`, so using it for the post-LLM re-read would compare whatever the directory points at *now* against a write going to the path resolved minutes earlier, and an in-tree link swap during the brain call is permitted and model-reachable.
- The writers are `storage.create_file_if_absent` (`O_CREAT | O_EXCL | O_NOFOLLOW`, which is what `if not path.exists(): write_text(...)` should always have been — `exists()` follows a link, so a **dangling** one read as absent and the seed landed at the far end of it; it `lstat`s on `EEXIST` because `O_EXCL | O_NOFOLLOW` reports a symlink as `EEXIST` rather than `ELOOP`, so a planted inode would otherwise be refused correctly and reported by nothing) and `storage.write_regular_file` (`O_NOFOLLOW` plus `S_ISREG` to *probe*, then a staging file and `os.replace`). The staging is not tidiness: truncating the target and writing into it means an ENOSPC or a FUSE fault returns False — which every caller reads as "nothing was written" — with the file already emptied.
- **Ancestor containment is the caller's** and the leaf guard covers only the last component. In `ensure_user_directories_v2` the check must run **before the migrations**, not beside the writes: `_migrate_workspace_to_bot_dir` derives `base / bot_dir / "config"` itself and `mkdir`s it, so a check placed after it refused correctly, returned False, and had already created a directory outside the tree. `{mount}/Channels/{token}` gets the same treatment against `{mount}/Channels` (a room belongs to no one user, so the user root is the wrong ceiling) — `validate_conversation_token` bounds the *name*, which is not the question of where it resolves.
- Memory recall (BM25 + vector) — opt-in via `auto_recall`.
- Briefings exclude all personal memory.
- Subsystem lives under `src/istota/memory/`; `memory/sleep_cycle.py` orchestrates.

## Sleep Cycle

Nightly extraction goes through the configured Brain (no streaming, no sandbox). Per-feature model overrides via `[sleep_cycle]` and `[channel_sleep_cycle]`. Writes dated memory files with `ref:TASK_ID`, inserts KG facts, optionally curates `USER.md` op-by-op. **Degraded-brain skip (ISSUE-181):** the sleep cycle calls the primary brain _directly_ (not the executor's fallback-wrapped path), so it consults the shared availability breaker (`brain/_fallback.primary_brain_unavailable`) before each call and feeds its own failures back (`report_brain_result`). When the primary is in a `usage_limit`/`not_found` state the whole pass is skipped — no per-user/channel extraction, no curation, no playbook distillation — and the first failure opens the breaker so the remaining channels skip in-pass (stops the N-identical-errors pattern). One operator alert fires on the closed→open transition; the breaker cooldown gates the next scheduled run so it doesn't re-attempt every cycle while the primary stays down. Shared-block synthesis follows the same policy (keeps last-known-good content; structured blocks still generate — no brain call). See `.claude/rules/brain.md` "Direct-caller availability" + the posture registry (`brain/_postures.py`).
