# Memory system

## Memory System

- `USER.md` — auto-loaded, optional nightly op-based curation. Runtime writes go through the `memory` skill CLI (`istota-skill memory append|add-heading|remove|replace|remove-heading|remove-subheading|show|headings`) — never `echo >>`. `remove`/`replace` reach bullets anywhere in a section (top region **and** `### subsections`); `replace` rewrites in place; `remove-heading` drops a whole `## ` section and `remove-subheading` one `### ` subsection of it — between them the only way to remove a heading line, or the prose and numbered items `remove` cannot reach; a `remove` that empties a subsection takes its heading too; `append --subheading` targets a subsection. The CLI shares the curation `apply_ops` engine, takes a per-file flock (anchor under the per-user deferred dir, not on the Nextcloud mount, so flock stays reliable and the config dir stays clean), and writes a `source="runtime"` audit entry per call.
- `CHANNEL.md` — loaded with `conversation_token`. Same CLI with `--channel TOKEN` (token must match `ISTOTA_CONVERSATION_TOKEN`). Channel writes are not audited (no per-channel audit infrastructure yet) and do not update the stored USER.md fingerprint; the audit/curation pipeline is USER.md-only.
- `GROUP.md` — `{mount}/Groups/<group_id>/GROUP.md`, one group's prose store; `group_kv` is the same group's machine state. The operator-facing version is `docs/features/groups.md`. **Which groups a task carries is one answer, `room_scopes.task_group_ids(conn, task)`**: the user's current groups off a room and on the user's own SMS/WhatsApp 1:1 (the token is *derived* from `user_id`, never prefix-matched), in a room only the groups whose current members cover `room_policy.room_readers` (members plus present principals), and nothing on a guest turn, a stored `mixed` turn, with any guest or `others` row present, or with no recorded readers. **A room linked to a group (`rooms.group_id`, Stage 27) carries that group alone**: the link filters the candidates *before* the coverage check and never replaces it, so a linked room whose readers the group does not cover loads nothing rather than falling back to the other covering groups. The link is written only past `room_policy.group_link_refusal` (`settings_refusal`'s authority plus current membership of a live group, one refusal string for every reason), which `!room group` and `PUT /chat/rooms/{id}/group` both ask; it has no foreign key and is re-checked per turn. A shared room's `CHANNEL.md` is fenced in the prompt (`executor.CHANNEL_MEMORY_LABEL`, D24) on the room card's predicate, `executor._channel_memory_is_shared`; a private room's is not. `executor._resolve_task_groups` wraps it for connection handling and returns `[]` on any error; that one list feeds the `## Group memory` block, the `Groups/<id>` read-write binds (`build_mount_plan(group_ids=)`), and `ISTOTA_TASK_GROUPS` in the proxy's base env, never the model's. `exclude_memory` skills empty it. **One gate for both stores, `skills/_group_access.group_access_denied`** (multiplayer D21): `kv --group` and `memory --group` both call it, and it requires `ISTOTA_USER_ID` to be a current member *and* the id to be in `ISTOTA_TASK_GROUPS` (absent means none), refuses an `ISTOTA_DB_PATH` naming no file rather than letting `get_db` create one (#570), and answers every reason with the one string `group_refusal` builds, so neither CLI is an existence oracle. The deferred kv apply re-derives the set from the task row, because the op file is model-written. `_group_md_path` runs the gate *before* containment, and containment is `skills/_loader.contained_group_dir` (equality with `realpath(Groups)/<id>`), which `storage._contained_group_dir` delegates to, so the daemon's read and the CLI's write share one rule. **Fenced** (multiplayer D22/D24): the prompt block, `memory show --group` and every `kv --group` value read go through `frame_untrusted`, `GROUP.md` under `_group_access.GROUP_MEMORY_LABEL`; keys, namespace and heading names stay bare. **Audited into the group, not the writer**: `memory.curation.audit.write_group_audit_log` writes every group op, applied or rejected, to `group_kv` under the reserved `_memory_audit` namespace (same `<ts>-NNN` key as the user trail via the shared `_next_key`, `written_by` the writer, entry carrying `group_id`, `user_id`, `task_id`, `op`, `outcome`), because the file has several authors; a refused caller leaves no entry, and a group write touches neither USER.md's trail nor `last_seen`. Read it with `istota group kv-list <id> _memory_audit`. **The lock anchor is the default one, not the per-user deferred dir**: two members have different deferred dirs, so a per-user anchor would let their read-modify-writes interleave and lose one, which is the weakness `CHANNEL.md` still has. That default is the system temp dir, and under `PrivateTmp=true` it is per systemd *unit*, not per host — correct today only because every `GROUP.md` writer is the memory CLI spawned by the scheduler unit. A writer in another unit (a web editor, say) needs a shared local anchor such as one under `db_path.parent`. **No automatic writer** (groups spec D4): neither sleep cycle reads or writes a group store, and `tests/test_group_no_auto_writer.py` pins it — rewrite it if a v2 writer lands, never delete it. Size: read with `USER_CONFIG_READ_CAP_BYTES`, a `group_memory_large` WARNING past 32 KiB, counted toward `max_memory_chars` but never cut — so one member's task can grow every member's prompt, an accepted residual (multiplayer D23).
- `config/skills/<skill-name>.md` — per-skill user overlays. **No CLI write path, by decision** (ISSUE-343). The `memory` CLI used to carry the same bullet ops under `--skill`, and the fit was wrong: five of the six live overlays are pure bullet lists, but the sixth is the `developer` workflow ISSUE-337 deliberately put there — twelve numbered stages, prose and fenced blocks — of which the ops reached about 20%. `remove` popped a bullet and re-parented the fenced block that belonged to it; a bare `append` landed above the file's own first heading, outside every stage; prose and fences were unwritable by construction, since `validate_appendable_line` refuses a newline (correctly — the check stops `--line "note\n### Injected"`). Rather than adding a whole-file verb beside the bullet ops, the verbs went and `curation/overlay.py` with them. Nothing was preserved by keeping them: `read_audit_entries` had no caller anywhere in the repo, so the audit trail those writes fed was write-only, and `_update_last_seen` deliberately declined to stamp after an overlay write (stamping USER.md's key from an overlay write would mask a real out-of-band edit to USER.md) with nothing taking its place, so there was no bypass detection either. **The loader is the enforcement point and it is total**: `_demote_overlay_headings` demotes a stray `## `, and `inspect_overlay` derives `binds` from unknown-skill, denylist, disabled-skill, over-cap, not-UTF-8 and empty-effective-body in the loader's own order. A hand edit cannot corrupt a prompt; it can only produce a file that does not bind, and two read-only surfaces say so by name and with a reason. **What the loader does not cover is the standing instruction, and that did widen.** "Nothing was preserved by keeping the verbs" is true of the audit trail and false of the rule the model was reading: `skill.md` used to say never to direct-edit an overlay, and now says to. The capability was always there — `{mount}/Users/<uid>` is bound read-write into the sandbox — but the ops vocabulary was an incidental bound on it (one bullet, no newlines, denylist on write), and it is gone. What still holds is the half that matters for a prompt-injection case: the load-time denylist keeps `sensitive_actions` and `untrusted_input` unreachable, and `_demote_overlay_headings` keeps a `## ` from escaping the injected block. What is now unobserved is that an overlay's *content* changed at all — no audit row, no fingerprint, and the nightly curator sees names and line counts, never bodies. A content fingerprint on `doctor`'s `config.skill_overlays` or on the curation inventory is the obvious way to close that and is not done here. That is the reframing the change rests on — **verify-after-write beats refuse-at-write here, because binding is a property of the file rather than of the write**: one `skills overlays` run catches a `develper.md` typo, an over-cap file, a denylisted slot and a frontmatter-only file, where the write-time refusal only ever caught the first. The read side lives on the *skills* CLI now, not here: `istota-skill skills overlay <name>` prints one whole (no `### ` filter — that existed to place a bullet, and there are no bullet ops) and `istota-skill skills overlays` is the inventory (one row per file: skill, bytes, lines, first line, `binds`, `reason`). Both resolve the directory through `storage.open_user_skill_overlays` and read through the descriptor it returns, so containment is the same `open_overlay_dir` walk the loader and the search reindex make rather than this CLI's own second copy of the rule. The relaxation that stood here is **reversed** (ISSUE-344): the old `_check_overlay_dir` refused *any* symlink at the `skills/` leaf because it created and owned that directory, and containment alone allowed a link that stayed inside the user's own tree, which is what the loader allowed and therefore what the prompt reflected. Both now refuse it, and for a different reason than ownership — a resolved-path comparison is only true until something moves, and every component under `{mount}/Users/{uid}` is model-writable, so a link that stays inside the tree cannot be told from one that has just been repointed. The loader and the read verbs still agree; what they agree on is stricter. Indexing moved with it: `memory/search.py::reindex_skill_overlays` on a scheduler tick (`scheduler.check_skill_overlay_reindex`, `scheduler.skill_overlay_reindex_interval`, 6h). It went into `process_user_sleep_cycle` first, above that function's early returns so a quiet day still got a pass — and review found the gate one level up: `check_sleep_cycles` returns before calling it at all when `sleep_cycle.enabled` is false, and again when the primary brain's breaker is open. `memory_search.enabled` and `sleep_cycle.enabled` are independent settings, so that left search-on/sleep-cycle-off indexing no overlay at all, where index-on-write had. A pass that makes no model call has no business behind a brain breaker, so it sits beside the worktree reap and the cache sweep instead, on its own connection — the sleep cycle holds one write transaction per half and `index_file` re-embeds every binding overlay unconditionally. Loading rules and ordering guarantees are in `.claude/rules/skills.md`; the user-facing page is `docs/configuration/per-user.md`.
- `memories/YYYY-MM-DD.md` — last N days auto-loaded (`auto_load_dated_days`).
- Knowledge graph (`knowledge_facts`) — temporal subject/predicate/object triples, freeform predicates, fuzzy dedup (predicate-equality gated), audited. Sandboxed runtime writes via `istota-skill memory_search add-fact|invalidate|delete-fact` are deferred as `task_<id>_kg_ops.json` and applied by the scheduler post-task.
- Classification gate in `memory/skill.md`: temporal events and stable factual claims → KG; behavioral instructions → USER.md; skill-scoped behavioral rules → that skill's overlay, edited as a file rather than through this CLI; reusable task procedures → playbooks (sleep-cycle-generated in v1); group facts → `memory append --group` / `kv set --group`, a fourth branch that states it is not the default and that nothing is promoted from USER.md or the knowledge graph without a member asking. The USER.md/overlay branch is decided by one test — "would it be *wrong* to ignore this rule on a task where the skill was not loaded? If yes → USER.md; if it is merely irrelevant there → skill overlay" — because a rule in an overlay only reaches the prompt when its skill is selected, and selection is heuristic. That inverts for prohibitions: the task that most needs "never write to the base notes folder" is the one that never recognized itself as a notes task.
- Learned playbooks (`playbooks.enabled`, off by default) — per-user markdown task procedures distilled by the sleep cycle from successful multi-step tasks, stored under the user's bot `playbooks/` dir, indexed into `memory_chunks` as `source_type="playbook"`, and recalled by relevance into a "## Learned Playbooks" prompt section. Markdown-only, never executed; excluded from briefings. Lifecycle (ISSUE-174): the extraction prompt distils the _verified_ command from the trace's per-tool `raw` field (the literal Bash invocation, captured by all three brains) rather than a paraphrase, and writes a thin router instead of re-narrating a single-script task; a `pinned: true` file survives re-derivation (kept on disk, re-indexed so the correction reaches recall); retention (`retention_days`, default 90) prunes on **last-use** mtime (stamped on recall), deletes the pruned file's chunks, never prunes a pinned file, and grandfathers existing files on first upgrade. See `.claude/rules/scheduler.md` (generation) + `.claude/rules/executor.md` (recall).
- The nightly curation prompt carries a skill-overlay inventory — names and line counts only, never bodies — so the curator does not re-add to USER.md a rule that moved into an overlay a week ago. It states in the prompt that the bodies are deliberately withheld, that the ops cannot edit those files, and that the list is grounds not to *add* a rule and never grounds to *remove* one; the curator holds destructive `remove`/`remove_heading` ops and would otherwise have a topic list with nothing to check against. `sleep_cycle._load_skill_overlay_inventory` derives one candidate path per known skill rather than listing the model-writable directory.
- Nightly curator self-heals: bypass-write detection (the `last_seen` fingerprint), sha256 re-read after the LLM call, agents-header migration, Phase-A lint pass logs date-stamped USER.md bullets without migrating them.
- **Curation state lives in the KV store, not beside USER.md.** The audit trail is one `istota_kv` row per write event in `_memory_audit` (key `<ts>-<NNN>`, so several entries in one second cannot upsert over each other — a nightly run emits up to three); `last_seen` and `lint_seen` are single blobs in `_memory_curation`. One row per entry rather than one growing array is what keeps an append O(1). Every namespace starting with `_` is refused by `skills/kv` **and** by `scheduler_deferred`'s applier, and hidden from `kv namespaces` — the predicate is `kv_namespaces.is_reserved_namespace`, a stdlib-only leaf so the skill subprocess needn't import `istota.db`. Both enforcement points are needed: the skill covers a host-side CLI call, the applier covers a sandboxed task, whose `kv set` never reaches the skill's check because the sandbox has no database and the op is replayed from JSON afterwards. This is defence in depth, not the boundary — the boundary is that the framework DB is bound into no sandbox at any path. The three files this replaced (`USER.md.audit.jsonl`, `USER.md.last_seen.json`, `USER.md.lint_seen.json`) sat under `{mount}/Users/{user_id}`, which `build_bwrap_cmd` binds read-write, so a task could wipe its own audit trail or forge the fingerprint. `migrate_user_md_sidecars` imports and removes them from `process_user_sleep_cycle`, **before** its early returns (a user with no interactions leaves within a few lines) and **outside** the `curate_user_memory` gate (that flag is off by default, but the runtime CLI wrote the sidecars regardless). The import is all-or-nothing per file — `_with_conn` wraps the whole `with db.get_db(...)`, and `get_db` commits only on a clean return, so a failure partway leaves nothing committed and the file survives for the next pass rather than being half-imported and duplicated. `curation/lint.py` is now pure: `filter_unseen_candidates` takes the seen dict and returns the updated one, and the caller stores it.
- **Every host-side read and write of `{bot_dir}/config/` goes through one pair of helpers, and neither is optional** (ISSUE-339). `storage.resolve_user_config_dir` is `resolve_user_skill_overlays_dir` one level up — `contained_overlay_dir` against `{mount}/Users/{uid}`, returning the **resolved** path — and `storage.read_user_config_file` is `read_overlay_bytes` behind it. That directory is bound read-write into the user's own sandbox while the daemon reads it unsandboxed, so the two failure modes the overlay path was built against apply unchanged: a symlink resolves in the daemon's larger view and its content becomes prompt text, and a FIFO blocks `open(2)` before the `BrainRequest` exists, where no task timeout reaches it. The readers are `read_user_memory_v2` (USER.md), `load_persona` (PERSONA.md), `cron_loader.load_cron_jobs` (CRON.md), `heartbeat.load_heartbeat_config` (HEARTBEAT.md), `heartbeat`'s task-deadline check (TASKS.md), the memory CLI's `_read_text` and the curator's re-read; the writers are the seeding block, the `examples/` refresh, `_write_cron_md` and the curator. **A reader that joins the mount itself is the bug.** The blast radius is not uniform and that is worth knowing: USER.md and PERSONA.md wedge *prompt assembly*, so one `mkfifo` stopped every later task for that user, while CRON.md and HEARTBEAT.md are read on the **scheduler's own tick**, so one there stopped scheduled work for everyone.
- **`None` means could-not-read and `""` means not-there**, and collapsing them is how the curator came to destroy the file it curates. `current = read_user_memory_v2(...) or ""` made an unreadable USER.md an *empty document*; the post-LLM sha guard then compared a refusal against a refusal, matched by construction, and the ops were serialized over a healthy file — a 1.26 MB USER.md reduced to 456 bytes with the run reporting success, reachable by a task padding its own memory past the read cap. `read_regular_file` is the tri-state leaf for a caller that already holds a resolved path, and the curator uses it for **both** reads: `read_user_config_file` re-resolves `config/`, so using it for the post-LLM re-read would compare whatever the directory points at *now* against a write going to the path resolved minutes earlier, and an in-tree link swap during the brain call is permitted and model-reachable.
- The writers are `storage.create_file_if_absent` (`O_CREAT | O_EXCL | O_NOFOLLOW`, which is what `if not path.exists(): write_text(...)` should always have been — `exists()` follows a link, so a **dangling** one read as absent and the seed landed at the far end of it; it `lstat`s on `EEXIST` because `O_EXCL | O_NOFOLLOW` reports a symlink as `EEXIST` rather than `ELOOP`, so a planted inode would otherwise be refused correctly and reported by nothing) and `storage.write_regular_file` (`O_NOFOLLOW` plus `S_ISREG` to *probe*, then a staging file and `os.replace`). The staging is not tidiness: truncating the target and writing into it means an ENOSPC or a FUSE fault returns False — which every caller reads as "nothing was written" — with the file already emptied.
- **Ancestor containment is the caller's** and the leaf guard covers only the last component. In `ensure_user_directories_v2` the check must run **before the migrations**, not beside the writes: `_migrate_workspace_to_bot_dir` derives `base / bot_dir / "config"` itself and `mkdir`s it, so a check placed after it refused correctly, returned False, and had already created a directory outside the tree. `{mount}/Channels/{token}` gets the same treatment against `{mount}/Channels` (a room belongs to no one user, so the user root is the wrong ceiling) — `validate_conversation_token` bounds the *name*, which is not the question of where it resolves.
- Memory recall (BM25 + vector) — opt-in via `auto_recall`.
- Briefings exclude all personal memory.
- Subsystem lives under `src/istota/memory/`; `memory/sleep_cycle.py` orchestrates.

## Sleep Cycle

Nightly extraction goes through the configured Brain (no streaming, no sandbox). Per-feature model overrides via `[sleep_cycle]` and `[channel_sleep_cycle]`. Writes dated memory files with `ref:TASK_ID`, inserts KG facts, optionally curates `USER.md` op-by-op. **Degraded-brain skip (ISSUE-181):** the sleep cycle calls the primary brain _directly_ (not the executor's fallback-wrapped path), so it consults the shared availability breaker (`brain/_fallback.primary_brain_unavailable`) before each call and feeds its own failures back (`report_brain_result`). When the primary is in a `usage_limit`/`not_found` state the whole pass is skipped — no per-user/channel extraction, no curation, no playbook distillation — and the first failure opens the breaker so the remaining channels skip in-pass (stops the N-identical-errors pattern). One operator alert fires on the closed→open transition; the breaker cooldown gates the next scheduled run so it doesn't re-attempt every cycle while the primary stays down. Shared-block synthesis follows the same policy (keeps last-known-good content; structured blocks still generate — no brain call). See `.claude/rules/brain.md` "Direct-caller availability" + the posture registry (`brain/_postures.py`).
