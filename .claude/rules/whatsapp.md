# WhatsApp

One WhatsApp number reached through one of two adapters, behind a provider seam that mirrors the SMS one. `baileys` is the default: a paired WhatsApp Web session held by a Node sidecar, free and unmetered, with no service window, no template and no Meta business account. `whatsapp_cloud` is Meta's hosted Cloud API, direct rather than through a BSP, and is the sanctioned path — metered, window-bound, and configured against a verified account. `config.whatsapp.provider` picks one and a deployment runs one; there is no failover between them.

The surface is the same either way. It is a user-routable push surface, text only, and outside the room model: no `messages` row, no room membership, no Talk or web view. Context comes from the stable `whatsapp-<user hash>` conversation token and task history, and that token is a pure function of `user_id`, so it survives every number, username, send-id and adapter change. A bare `whatsapp` destination resolves the user's current binding immediately before the send; `whatsapp:<anything>` is refused, so routing cannot become an arbitrary-contact send API. `all` and `both` are unchanged, deliberately — the rule was written about a metered surface and stands without the metering, because the surface is external either way.

Almost every hard constraint this file used to state is a fact about the Cloud API rather than about WhatsApp. The 24-hour window, approved templates, the monthly attempt cap, `quota_month`, the pricing ladder, the billing circuit breaker, the signed webhook and the 1,024-character interactive body are all Cloud's. What is common to both adapters is the one-send ledger, the parked-status machinery, delivery-state monotonicity, identity resolution and opt-out.

## The seam

`transport/whatsapp/providers/` mirrors `transport/sms/providers/` in shape and deliberately not in code: the two surfaces have different identities, different ledger keys and different delivery vocabularies, so what is shared is the arrangement. `WhatsAppProviderAdapter` is a frozen record of `name`, `caps`, `send`, and the pair `parse_webhook` / `verify_signature`, which are `None` together for an adapter that receives over a transport of its own. `make_provider_registry` importlib-loads `providers.<name>.build_adapter`, keeps the active adapter plus any fully-configured one as callback-only, and refuses three contract faults at build: an adapter answering to another name, a half-declared webhook pair, and a synchronous `send`. The last is a ledger property rather than tidiness — a synchronous `send` fails inside the claim-to-settle region, where the backstop settles `unknown` for a message nobody sent. A fault on the *active* adapter raises; on a non-active one that adapter is dropped and logged at ERROR, so a programming error in a provider nobody selected is not a whole-surface outage.

**The build gate departs from the SMS one in one place.** SMS gates both the active and the callback-only role on the provider's config block being populated and complete, which works because every SMS provider's credentials are in the config file. Baileys declares no credential fields at all — its credential is a paired session on disk — so a populated-block test reads False for it for ever, and gating the active role on it would leave a Baileys deployment with no adapter and every send recorded `unconfigured`. So the active provider is built whenever nothing it declares is missing, and a non-active one only when its block is populated as well.

`WhatsAppProviderCaps` is what the gate order reads instead of branching on a name: `metered`, `has_service_window`, `supports_templates`, `delivery_receipts`, `address_field`, `service_body_limit`, `interactive_body_limit`. It takes **no defaults**, so a third adapter answers every question rather than inheriting whichever answers happened to suit the first two — which also makes widening it a deliberate seam change, and is why the last three arrived with both adapters answering them in the same diff. `delivery_receipts` is declared ahead of its reader and nothing reads it: the parked-status table, the status ladder and the failure alert are unconditional, so declaring it False disables none of them. Read it as a description, not a switch.

**Nothing was physically moved behind the seam, and the property that holds is narrower than "the Meta code lives in the adapter".** `client.py` was already the PyWa boundary and `webhook.py` was already Cloud-only, so what was missing was the binding rather than the separation; relocating either buys a large diff, an import-path change in every test that names them, and no boundary that was not already there. `_observe_pricing`, `quota_month`, `render_template_parameter` and Meta's two character caps are still in `outbound.py`. What is checkable is that **`outbound.py` imports no provider module at run time**, held by a drift guard, and that every gate reads `adapter.caps`. The drift guard's one carve-out is that the word `pywa` may appear in a comment saying what that module refuses to do.

`transport/whatsapp/identity.py` is the only module that branches on the provider by name, because an identity is genuinely per adapter rather than a capability the gate order can read.

## Identity is the adapter-native identity, not the number

Cloud's identity is the BSUID; Baileys' is the JID, `<number>@s.whatsapp.net`. `whatsapp_user_bindings` carries both, plus a nullable `provider` saying which adapter established this row's identity. The migration adds two columns and one partial unique index on `jid` — the index is not optional, because each of these columns decides which user an authenticated event may act as, so two rows holding one value is a principal takeover. There is no backfill: a NULL `provider` reads as `whatsapp_cloud`, which is what every row written before the split is.

The binding lives in its own table rather than a `user_profiles` column because the inbound path has to read and write it inside the same transaction as the dedup claim and the task creation. A `db_path`-taking store would open a second connection under an open write transaction, wait out the 30s busy timeout and raise — the hazard `.claude/rules/notifications.md` documents.

Resolution order is the same five rules in both arms. The adapter-native identity is matched against the bindings; failing that, a valid E.164 number — Meta's `wa_id`, or the number embedded in the JID — is matched against one bootstrap number whose identity column *for this adapter* is still empty, which latches it atomically. **A bootstrap number matching a user whose stored identity for that adapter differs is refused and alerted, never taken** — that is a recycled line, and reading it as the same principal is the takeover this table exists to prevent. An unknown sender creates no task, leaves no retained identifier and gets a one-way fingerprint in the log. `webhook.py` delegates to `identity.py`, and so does the Baileys bridge's inbound worker.

Three properties hold the two adapters apart, and each is the takeover guard one adapter over. An event from one adapter resolves only through that adapter's column, so a stale identity of the wrong kind is never read. A JID whose number matches a row already carrying a *different* JID is refused and alerted exactly as a recycled BSUID is, under its own dedup namespace so the second alarm is not swallowed as a bump. And a latch onto a row belonging to the other adapter discards the derived state described below.

**The bootstrap refusal is per adapter, which means an adapter switch does let a phone number alone re-establish a principal** on a row whose identity for the new adapter is unset. Refusing that is not available: on a genuine migration every row is in exactly that state, so a refusal locks out the whole deployment, and nothing on the row separates it from a recycled number. The number is the operator's own assertion that it belongs to this user, which is what licenses the latch — so the latch happens and a deduplicated `whatsapp-cross-adapter` alert says a principal was re-established from a number, threaded into the accepted result so it is pushed rather than only filed.

**There are two discards with two different triggers, and collapsing them is a defect in either direction.**

A **holder** change — a new bootstrap number, a cleared identity — discards everything learned about the previous holder, `opted_out_at` included: it belonged to that holder, and leaving it strands the new one opted out with no verb to clear it. `last_user_message_at` matters most there, since it is the sole input to Meta's window and carrying it across would authorize a free-form send to somebody who never wrote in. `set_whatsapp_binding` and `reset_whatsapp_identity` own that discard.

An **adapter** change — a latch onto a row whose identity belongs to the other adapter — discards `last_user_message_at` and, on the Baileys side, `send_id`, and **keeps `opted_out_at`**. The holder has not changed there, only the adapter has, so clearing the opt-out silently revokes a STOP and resumes messaging somebody who asked to be left alone, where keeping it merely withholds until they send START. That discard is provider-compared and so is a no-op on every pre-split row, which is what leaves the Cloud path as it was.

`last_user_message_at` is Meta's window and only a Cloud-authenticated message writes it. A Baileys message opens no conversation Meta knows about, so stamping it would authorize a free-form send after a switch back to Cloud — where no latch fires, because the BSUID is still there, and so no discard would catch it. `send_id` is likewise Meta's opaque destination and is not written on the Baileys path; the destination there is the JID. An identity reset (`istota user ensure --reset-whatsapp-identity`) clears **both** adapters' identities and the provider stamp, which is wider than the spec's "for that adapter" and is deliberate: the verb takes no adapter argument, it is a statement that the learned identity on this row is wrong, and a half-reset leaves the other adapter resolving the previous holder the moment the deployment switches back.

An inbound message whose provenance is not the active provider is refused as `inactive_provider` before any identity lookup, which is the SMS rule ("a complete inactive adapter may authenticate late delivery callbacks, but its inbound messages create no task") on this surface. The refusal is deliberately non-durable — it returns before the dedup claim, because claiming a message id under a user id that no identity resolution produced would be worse. Delivery events bypass the gate entirely, for the reason the SMS rule keeps them: a status has to settle its ledger row whether or not the adapter that sent the message is still the active one.

`touch_whatsapp_binding` writes the uniquely-indexed `send_id` **conditionally**, in SQL with a correlated `EXISTS`. Unconditional, a BSUID sitting stale in another user's `send_id` raised `IntegrityError` out of the batch, the route answered 503, and Meta redelivered into the same deterministic failure for ever with no disposition row, no task and no alert. The rest of the touch lands including the service window, the helper returns False and the caller alerts. Deliberately not the latch path's fail-closed: the sender is legitimate, and refusing their every message over a row that is not theirs is a denial of service. A Baileys touch passes no send id and no window, so it raises no spurious alert.

## Outbound: one send, one row, no resend

Common to both adapters. `sent_whatsapp` claims a `logical_key` and commits **before** the network call, which is the whole no-resend guarantee: from that instant every later call reads the row as settled and returns. So the claimed region is wrapped whole, catching `BaseException` (both callers run where shutdown delivers `CancelledError`, on the one path where the send may already be on the wire), and split at the send — a pre-send failure settles `failed`, since it is provably a message that never left, and `unknown` is the one state an operator can never resolve.

**The adapter's whole job is one bit**, and each adapter draws the line in its own vocabulary. For Cloud it is the status code: a 4xx means Meta read the request, applied a documented rule and refused it, so nothing was queued, while a 5xx is Meta failing while handling a request it may already have accepted. PyWa's `is_transient` is deliberately not consulted — it answers whether retrying later might work, not whether this attempt was applied. For Baileys the line is `writer.write` on the socket, and `definite` is read off the `send_result` line rather than derived. **No failure reason is ever built from an exception on either adapter**: Meta's prose, PyWa's exception text and an httpx repr all carry the request URL, which carries the recipient and the token's path segment, and a Baileys error carries the destination JID and, on a Boom error, the whole request. The reason comes from a fixed table and only a numeric code is taken off the exception.

The gate order is by whose decision each is — transport, binding, opt-out, billing circuit, window, budget — and **three of the six skip themselves where the caps say the precondition cannot arise**. The billing circuit and the budget need `metered`, the window needs `has_service_window`, and the closed-window fall-through to a template needs `supports_templates`. Under Baileys the order is transport, binding, opt-out, and nothing after. Opt-out outranks the window deliberately: reporting a closed window about somebody who asked not to be messaged is an alert nobody should be woken by.

The destination is the adapter's own binding column, named by `caps.address_field`. `identity.address_for_binding` holds the two spellings, beside the JID parser they have to agree with, because a destination built by one rule and an identity parsed by another means a user enrolled by number can be messaged and never recognised when they answer.

**A confirmation prompt is an interactive message and Meta caps that body at 1,024 characters, not 4,096.** Rendered at the text limit, Meta refused every question past a quarter of the budget and the task parked until it expired. The scheduler sizes the body rather than the renderer, and asks `render_whatsapp` for the budget rather than repeating the arithmetic: cut at the renderer's boundary, the truncation took the `Task #N. Reply YES or NO.` sentence with it, which is the address `!confirm <id>` and a typed YES resolve at. That cliff is Meta's, so the budget is the adapter's answer rather than a constant: `service_body_limit` and `interactive_body_limit` are caps fields and `outbound.confirmation_body_budget` folds them with the template-parameter cap, so the scheduler asks one question instead of spelling out three Cloud facts. Baileys has no interactive object, its two budgets are equal, and a stale `[whatsapp.cloud]` template block does not narrow them because `supports_templates` is False.

`_TERMINAL_FOR_STATUS` and `_NO_RESEND` are two sets: the first says which rows a status callback may not move, the second which rows no send path may re-attempt, and they differ on the four states meaning the message was taken.

Monotonicity compares the canonical status rank alone. `sent_whatsapp` has no event-time column, and over a total order of four statuses the rank answers what a timestamp would. **Pricing observation sits outside that ladder on purpose**: reading it only on an applied transition would throw the evidence away in exactly the out-of-order case the ladder exists for, and a billable `failed` row is the loudest evidence there is. `billable` is never downgraded from true by a later false; the other three pricing fields take the latest non-NULL observation. Only Cloud produces pricing at all — a Baileys receipt carries none — so the ladder is common and its pricing arm is fed by one adapter.

**A status can arrive before the id it names**, on both adapters and for the same reason: Meta mints that id in its reply to the send, Baileys mints it in `send_result`, and `_settle` writes it a statement later. Such a status matches no row; discarding it is harmless for `sent`, `delivered` and `read`, which a later status supersedes, and silently wrong for `failed` — the row stays `accepted` for good, no alert is raised, and the surface reports a delivery that failed (ISSUE-490). It is held in `whatsapp_parked_status` and replayed by `_settle_async` once the id lands.

**The replay is a second transaction, after the settle commits, and the obvious shape is the wrong one.** Draining inside `_settle`'s own transaction reads better and was written first: it makes the ordering a property of one function instead of resting on a lock another module takes. It is wrong because `db.get_db` commits only on a clean exit, so any raise out of a replay — a notification write, the admin file `_write_billing_alerts` reads, a parked table `init_db` has not created yet — unwinds the `meta_message_id` write with it. That loses the id of a message that was accepted, no later status can match the row again, and the escape wrapper then settles it `unknown`: strictly worse than the defect. The replay is also never allowed to raise past `_settle_async`.

Nothing between the two transactions can lose a status, and that is the one property the lock argument still carries. A status is parked only under `handle_whatsapp_batch`'s `BEGIN IMMEDIATE`, which holds the write lock across its own row lookup and the park, and the settle's UPDATE needs that same lock — so a batch either commits its park before the settle, and the drain finds it, or does its lookup after, and finds the row. `test_a_status_racing_the_id_write_is_never_lost` drives two real threads at it; with the batch's `BEGIN IMMEDIATE` weakened to a deferred `BEGIN` it goes red every run.

The replay goes back through `apply_delivery_event` rather than writing the row directly, which is what keeps the one-send contract: the ladder refuses a row already in `_TERMINAL_FOR_STATUS`, so a `failed` drained ahead of a `delivered` parked after it closes the row and the `delivered` is a duplicate. `_settle`'s own UPDATE carries that set as a `WHERE` clause for the same reason, which is a rule the write had always needed and not only since parking: `deliver_whatsapp`'s escape wrapper settles `unknown` on any escape, and a cancellation arriving after an earlier settle committed would otherwise overwrite a settled row with the one state an operator can never resolve.

**The parked row keys on the message fingerprint, never the id.** The in-flight test is deployment-wide and cannot tell one of our ids from another application's on the same number, so a raw id would persist an identifier naming somebody else's private conversation — the thing every log line in the transport fingerprints to avoid. The drain fingerprints the id it already holds and matches on that, so nothing is lost.

**Parking is bounded twice and needs both bounds.** A status is parked only while some send sits between its claim and its settle — `status = 'pending'` with a claim stamped and no id — so a status for a message this deployment never sent is discarded exactly as before. That gate alone is not enough, because a send killed between those two points leaves an in-flight row nothing clears, and while one exists every unmatched status parks; so a row past `PARKED_STATUS_WINDOW` is pruned whenever the table is touched — on an attempted park, *before* its gate, and on a drain. Behind the gate the only thing clearing the table would be a successful park, which is exactly the deployment that has gone quiet keeping its rows for good. A pruned row is a status istota held and could not place, so the count is logged as a warning.

**The park is guarded and falls through to the discard.** That branch used to be a log line and a return, so it could not fail; it now writes, and `handle_whatsapp_batch` turns any exception into a 503 the whole batch rolls back into and Meta retries against. A park that cannot happen must cost the status, never the batch.

**The SMS ledger has the same race and is not fixed here.** `sms.outbound.apply_delivery_event` matches on `provider_message_id`, which `_persist_outcome_or_unknown` writes only after the adapter returns, so a `failed` callback that overtakes it is discarded the same way. It is a different table with a composite key, on a surface that is live, and a shared holding table would have to be generalized over the key and the in-flight predicate — its own change.

## The Cloud adapter

Everything in this section is reachable only under `provider = "whatsapp_cloud"`.

### The signed webhook

`GET`/`POST` at the fixed `/webhooks/whatsapp`. Three phases, and the order is the module's design: **authenticate then read** (bounds, content type, configured secret, HMAC over the exact raw bytes, decode — a 403 arriving as a 400 has told the caller the body was read); **normalize the whole batch before `BEGIN IMMEDIATE`**, so a malformed element cannot leave the first message applied behind a 200 nobody will retry; **one transaction for the batch**, with any database failure rolling back to a 503 Meta retries.

`client.verify_signature` adds three guards in front of PyWa's validator, and the load-bearing one is refusing an absent app secret: `webhook_updates_validator` takes the secret as a plain `str` and computes an HMAC under `b''`, so with none configured it does not fail to validate — it validates against a key every reader of this repository knows. The route refuses to serve besides.

An oversized body answers **413**, not the 400 the spec's design section wrote, matching the sibling SMS route through the same shared bounded-body reader. The GET handshake bounds `hub.challenge` to ASCII digits and refuses anything else with 400, which is stricter than "echo it as plain text" — the value is echoed verbatim from a route that answers before anything authenticates it.

The normalizer reads `pricing.billable` and never derives it, where PyWa's own `Pricing.from_dict` infers it from `type == "regular"` when the field is absent. A guess is what opens, or fails to open, the billing circuit. Messages are paired with contacts by sender id, never positionally: PyWa takes `contacts[0]` for every message in a value, which is fine while a value holds one of each and is a principal takeover when it does not.

### Cost controls

Two, and neither is called a guarantee. **The monthly cap is reserved by the claim, in the claim's own `BEGIN IMMEDIATE`** — the count and the row that increments it are one write transaction, so the last free slot cannot be read as free twice (measured: a deferred `BEGIN` turns the two-thread test red every run). `quota_month` is stamped on every row including blocked ones, but only a *claimed* row counts, so a `window_closed` or `budget_exhausted` row consumes nothing while a `failed` or `unknown` one consumes its slot and is never reclaimed.

**`monthly_service_attempt_limit` bounds service attempts and bounds template attempts by nothing.** Implemented as named. The consequence is inverted and worth knowing before enabling paid mode: with the cap spent, an open window is refused while a closed one still bills a template. Templates are reachable only under `allow_paid`, and `doctor.whatsapp.billing` reports the template count beside the service count so the volume is visible. A `monthly_template_attempt_limit` is the real fix and is a spec change.

**The circuit breaker is persistent and deployment-wide.** In `free_guard` the first authenticated status carrying `billable = true` sets `whatsapp_runtime.billing_blocked_at` and blocks every later send. The message that revealed the charge may already be billable; what the breaker buys is that the next one is not. Its alert is not `write_delivery_failure` — that one is about a message that reached nobody, this is a message that arrived and was charged for — and it goes to each admin as well as the recipient, since a deployment-wide block landing in one non-admin's inbox is not an operator notice. `template_available` re-checks `billing_policy == "allow_paid"` rather than resting on `load_config`'s refusal: one validator standing between a free-biased deployment and a paid message is one place for the rule to be edited out of.

`doctor.whatsapp.billing` SKIPs under a non-metered adapter. It reported a circuit state, a spend, a cap and a calendar month, none of which governs a send Baileys makes.

### What a switch away from Cloud costs

`whatsapp_webhooks_enabled(config)` is `enabled` plus the **active** provider being one with an HTTP callback at all (`WHATSAPP_WEBHOOK_PROVIDERS`), and the asymmetry with `sms_webhooks_enabled` is the point. SMS keeps a complete inactive provider's routes so a late delivery callback still authenticates across a switch; WhatsApp does not. Both handlers answer 404 on the same predicate the mount reads, so after a flip to Baileys, Meta's retries reach nothing and eventually stop. **The cost is stated rather than hidden: messages still in Meta's retry queue are lost, and an outstanding `sent_whatsapp` row keeps whatever state it had.** Where a Cloud message does reach `handle_whatsapp_batch` on a Baileys deployment — a receiver holding an older config, say — the provenance gate drops it as `inactive_provider` with no task.

It is deliberately **not** `WhatsAppProviderRegistry.callback_only_names()`, which does list every built adapter and is an answer about credentials a switched-away deployment still holds; reading it as the mount would restore the SMS rule this surface does not follow.

Four places read the same predicate — that function, `serve._maybe_mount_webhooks`, the role's `Resolve webhook receiver need`, and the compose profile — and three of them express the provider half. Both generators render `provider` when the operator names one, and the role's condition **refuses `baileys`** rather than requiring `whatsapp_cloud`: an unnamed provider is resolved from the Meta values by `_migrate_whatsapp_flat`, and reproducing that rule in Jinja would be a second copy going stale against `config.py` with nothing to say so. So the ambiguous case provisions a receiver nothing may call rather than risk dropping one a Cloud deployment needs. The fourth cannot express it at all — a compose profile is a static name — so it is split per adapter instead: `whatsapp` starts the receiver and `whatsapp-baileys` starts the sidecar. The residual is that nothing stops a stack selecting both, which costs a receiver whose handlers 404 and is inert.

**Two things nginx has to do that the application cannot, and one the proxy cannot do either.** The verify token arrives as a *query value* on the GET handshake and nginx decides what to log before the route runs, so `/webhooks/whatsapp` gets `access_log off` in both shipped configurations; a `log_format` naming `$uri` would keep the line but is only valid at http level, and both templates are one server block inside a generated `conf.d`. **Uvicorn's default access formatter renders `get_path_with_query_string(scope)`**, so silencing the front end alone leaves the token in the container log and the journal — measured against a live server, not read off the source. `serve.build_uvicorn_server` had always passed `access_log=False`, so the combined process was the only shape holding the property the docs claimed; both standalone receivers now run `--no-access-log` and a test pins all three. And the route-specific `client_max_body_size 512k` sits above istota's own 256 KiB cap so an oversized POST is answered by the application rather than by nginx with an HTML page Meta retries against.

## The Baileys adapter

A WhatsApp Web session, the mechanism mautrix-whatsapp and similar bridges use. It emulates a client WhatsApp does not sanction outside the Business API, so it carries account-ban risk, it breaks when the Web protocol changes until the library catches up, and the device unlinks after long inactivity. That trade is the operator's to make, which is why Cloud stays and why `docs/features/whatsapp.md` states it where an operator meets it.

### The sidecar and the wire

Baileys is TypeScript with no Python port, so the adapter is a Node subprocess: `docker/whatsapp-baileys/`, its own image rather than a stage in istota's. Decided on size — the library pulls in libsignal, protobufjs and a Node runtime, and `[whatsapp] enabled` is false by default, so folding it in charges a few hundred megabytes to every deployment for a surface most do not run.

**The daemon listens and the sidecar dials**, `devbox_proxy`'s arrangement: the listener's lifetime is the daemon's, so a sidecar restart reconnects to a socket that never went away, and the daemon creates the inode and therefore owns its mode. One JSON object per line over `AF_UNIX`, capped at 256 KiB on *both* ends, with a `hello` frame carrying a protocol version the bridge refuses on mismatch rather than reading an older shape's fields out of a newer frame. **There is no HMAC and none is faked** — the trust boundary is the socket itself, 0600 from the instant the inode exists rather than narrowed to it, with no network peer, which is why this adapter's `verify_signature` is `None` and nothing on this path calls it.

The wire format cannot be byte-pinned the way `docker/devbox/lib/` is, because the other end is Python. `tests/test_whatsapp_sidecar_vendoring.py` pins it behaviourally instead, on the precedent `.claude/rules/devbox.md` records for `istota_devbox_client.py`: it lists the directory's entries and requires each to be classified, pins the wire constants and every per-message field name by driving the sidecar's own object literals through the daemon's normalizers, and **executes** the sidecar's pure functions through `node`, which is possible because `loadBaileys` is lazy so the module imports with no dependency tree. The control-flow properties are source assertions in a class whose docstring says it catches a deletion and not a subtle change. A real connection needs a real WhatsApp account and is in no automated tier.

### The session directory is a full-account credential

Whoever holds it can send and read as the paired number, with no second factor and no revocation short of unlinking the device. It is 0700 whether it was just created or already existed — `mkdir(mode=…)` applies only to a directory the call creates, so the mode is asserted on an `O_NOFOLLOW` descriptor every time — and that same descriptor is what refuses one belonging to another uid, which a mode check alone cannot see: a directory already at 0700 skips the `fchmod` and with it the `EPERM` that would have been the only signal, so a planted one would be adopted in silence. The sidecar is spawned under `umask 0o077` so its own files land 0600, with **its stdio discarded** — inherited, a chatty Baileys logger writes JIDs and message bodies into the daemon's own journal, where this module's never-log rule does not reach, and `PIPE` with no reader blocks the child once the buffer fills. The sidecar writes `sidecar.log` inside the 0700 directory instead, at a level the operator can raise, taking a fixed message and a small bag of bounded labels rather than an arbitrary object.

The directory is bound into no sandbox at any path, and neither its contents nor a `qr` payload is ever logged, a QR being the pairing credential itself. The sidecar's environment is an **allowlist** (`PATH`, `HOME`, the locale pair, `TZ`, `NODE_ENV`, plus the socket and session paths) rather than `os.environ` minus a pattern list, so a credential name nobody thought to filter is excluded by construction.

### The bridge

**Nothing about the one-send contract changes, and the definite line is `writer.write`.** Above it — no sidecar connected, a session in a permanent fatal state, a request that would not encode — the message provably never entered the socket and the row settles `failed`; from `write` onwards the bytes may be in the kernel buffer whatever `drain` then says, so a timeout, a dropped link and an unreadable answer all settle `unknown`. The catch-all reads a mark set at the write rather than assuming a side of it: a fixed ambiguous answer spends `unknown` on a message that never left, and a fixed definite one is the same mistake waiting for a refactor to move a post-write failure onto that path. Both waits are bounded and for different reasons — the answer by `SEND_TIMEOUT_SECONDS`, and `drain()` by its own smaller bound, because it is held across the write lock and a sidecar that connects and stops reading never lets it return; unbounded, one such peer holds the lock for ever and every later send queues behind it, leaving rows claimed and unsettled and the parked-status gate open deployment-wide. The writer is adopted only after the `hello` passes, so no `send` can be handed to a peer whose version is unknown. A send is matched to its answer by a request id rather than by order, since one long-lived connection multiplexes.

**The read loop dispatches and never works**, which is a deadlock rather than a tidiness rule: handling an inbound message can end in a reply, and a reply awaits a `send_result` only that loop can deliver. So inbound events go to a bounded queue drained by **one** worker — serial, because order within a conversation is meaning — and a full queue *drops* loudly rather than blocking the reader, since back-pressure there is the deadlock. The worker calls `handle_whatsapp_batch(..., provider="baileys")`, the same entry point Meta's signed webhook calls and inside the same `BEGIN IMMEDIATE`, so dedup, identity, the claim row and task creation are common code. The whole `with db.get_db(...)` block is one `asyncio.to_thread` callable: a connection must not hop threads, and that block opens and commits the transaction.

A malformed line is logged, counted and dropped — a message this side cannot read is not one it can attribute, and attributing one to a guessed sender is a principal takeover rather than a lost message. A *database* failure is retried in place and in order, because the webhook answers 503 and lets Meta redeliver and nothing redelivers over a socket. **The retry is bounded and then the event is dropped with a count**, which is a deviation from the spec's "parked and retried rather than dropping" and is stated as one: the worker is serial, so an unbounded retry starves every message behind it and the queue's own overflow then drops the *newer* ones, trading a loud loss of the message that cannot be written for a silent loss of the ones that could. `failed_events` is what `doctor` reads.

**A permanent `fatal` ends the respawn loop rather than slowing it.** A logged-out session comes back only from a re-pair, so respawning burns a process every few seconds and changes nothing; the running sidecar is stopped rather than left re-reporting the same fatal, and sends refuse *definitely* until it resolves. Only a `ready` clears the latch, so a transient fatal arriving afterwards cannot reopen the send gate against a dead session. `sidecar_argv=()` is a first-class mode rather than a test affordance: on both deployment shapes the sidecar runs as a unit or a compose service of its own, so the bridge listens and supervises nothing.

**An unlinked device is said out loud on both surfaces.** The bridge calls its owner back once per *transition* into a permanent fatal — not once per reconnect, since a logged-out sidecar reports the same fatal each time it comes back — and `baileys_runtime` writes an admin-addressed row and pushes it off the WhatsApp surface, the way the billing circuit's alert does. The sidecar's own words never reach the body; the reason goes through `task_alert._slug`. `doctor.whatsapp.baileys_bridge` is the other half and is what still answers a week later, with the re-pair remedy on its FAIL arm. `whatsapp.baileys_session` reports the credential's permissions and **surveys rather than repairs** — a diagnostic that narrowed a wide file was a second writer of a full-account credential's mode, attributed to no process, and its WARN self-cleared so the hourly sweep could observe an exposure exactly once. The bridge still narrows on its own start path.

**The bridge starts from the scheduler's boot, not from `serve.py`, and that is a deviation from the spec's affected-files list.** `serve.py` names the webhook-mount decision point, which runs in the web process — and on the Ansible shape the web app and the scheduler are separate units, so a sidecar started there would run in the one process that never sends. The loop matters more than the process: every send reaches `deliver_whatsapp` through `run_coro` on the persistent runtime loop, and the bridge's asyncio primitives bind to whichever loop first awaits them, so a bridge started anywhere else is awaited across loops from inside the claim-to-settle region. `transport/whatsapp/baileys_runtime.py` starts it beside the Talk signaling supervisor; `istota serve` inherits one through its own scheduler thread. `whatsapp.baileys_bridge` therefore answers only in a process holding a bridge and SKIPs elsewhere, so `istota doctor` from a shell cannot settle it — the authoritative surfaces are the boot run, the hourly sweep, `!check` and the admin Health pane. Its `library_version` arm runs *before* that skip, since it compares a config string against a file.

### Pairing

`istota whatsapp pair` starts a sidecar of its own, renders the QR and waits for `ready`. It refuses while a daemon is running, by connecting to the socket rather than testing for the inode, since an inode outliving its process is ordinary: two Baileys clients on one auth state corrupt it, so the session directory is a single-writer resource and a running bridge is already its writer. That refusal is also what makes permanent-fatal recovery work — stop the daemon, pair, start it again — which is the remedy the supervisor's log line names.

The QR is drawn in-process by `segno`, at error level `l` and two rows per character, which puts a 217-byte payload in 31 lines by 61 columns. It shelled out to `qrencode` and printed the raw payload where that package was absent, which let the host's package list decide whether a pairing could be completed — on the host where an operator is least able to install something, at the moment they need it. A pure-Python renderer with no dependencies of its own was the cheaper answer, and it is also the stronger handling of the credential: the payload now reaches no argv, no pipe and no other process, and on a successful draw it is not printed at all. The fallback that prints it survives only for a draw that fails, because this runs on the bridge's read loop through a callback where a raise is swallowed with no `exc_info`.

The daemon finds the Node program through `[whatsapp.baileys] sidecar_command` and nothing else. An in-tree fallback existed and was removed: the Ansible shape installs from a checkout, so `docker/whatsapp-baileys/index.js` is present and `node` is usually on PATH, and the daemon would have spawned a second sidecar beside the systemd unit's — the corruption the pair refusal exists to prevent, arranged by a convenience. The fallback lives in `in_tree_sidecar_argv`, whose one caller is `pair`, where a developer's checkout is the case it serves; it also requires `node_modules/@whiskeysockets/baileys` beside the program, so a checkout with no `npm ci` is not named as an argv at all.

## Config, credentials and deployment

Structural validity fails the load (`whatsapp_structural_config_errors`); **credential presence does not** (`whatsapp_credential_errors`, reported by doctor, refused at use). Failing the load on a missing secret repeats ISSUE-058: under `istota_use_environment_file` the Ansible role renders the three Cloud credentials empty on purpose and delivers them through `secrets.env`, which the role's own `command:`/`script:` tasks cannot read. Both halves are per provider: only the active adapter's structural arm runs, and the credential report names the active adapter's own fields — which matters because the unconditional Cloud form refused every Baileys send for want of a token that adapter does not use, and doctor's partial-credential arm FAILs, so a stale `secrets.env` entry would have alerted every admin about an adapter nothing runs. `graph_api_version` accepts `v25` and `v25.0`, since PyWa 4.4 pins Graph `25.0` and a `v<integer>` rule would refuse every real version string. `business_phone_number` stays top-level and is adapter-independent: required when enabled under Cloud, because a Meta account is configured by hand, and format-checked-if-set under Baileys, because a paired session carries its own number. It still earns its place there — it is what `identity.address_for_binding` renders into a JID for a user enrolled by number who has not yet written in, the only way to message somebody first on this adapter.

**Meta's settings live in `[whatsapp.cloud]`, and the pre-adapter flat spelling still loads.** `_migrate_whatsapp_flat` runs as a pre-walk step in `config.py` rather than as a `config_mapper` hook, and the spec's affected-files line naming `config_mapper.py` is the imprecise half. Two reasons, and the second is mechanical: `config_mapper` states that anything migrating a legacy key stays hand-written in `istota.config`, and `apply_section` consults a hook *before* it recurses into a nested dataclass, so a hook keyed on `whatsapp` would replace the walk for that whole section and lose the unknown-key report and every nested coercion. A `Hook` also returns one field's value, and this migration has to set a *sibling* key — `provider` — decided from the values, which that signature cannot express. Naming it `normalize_legacy_document` is what lets the loader and the two generator drift guards share one answer.

**The provider signal is read off the resolved `cloud` table, not off where the keys were written.** A block carrying a `waba_id`, a `phone_number_id` or one of the three credentials selects `whatsapp_cloud` when no `provider` key is present; an empty one takes the `baileys` default. Reading the signal off the flat keys alone was a defect produced by the deprecation note itself: following "move them under `[whatsapp.cloud]`" removed the last flat key, dropped the signal, and converted a Cloud deployment into a Baileys one in silence — `whatsapp_webhooks_enabled` False, no config errors, doctor OK. It cannot misfire the other way, because a deployment wanting Baileys with a populated Cloud block writes `provider` explicitly and an explicit value is never overridden.

The transport registers on `config.whatsapp.enabled` alone, not "enabled and locally valid": structural validity is already raised at load and gating on credentials would repeat ISSUE-058 again. Local validity is enforced per send by the outbound gate (recording `unconfigured`) and per user by `is_whatsapp_configured`, which applies the gates still true in an hour — transport, binding, opt-out, and under a metered adapter the billing circuit and the cap — and deliberately **not** the service window, which reopens on the user's next message and whose absence would make the heartbeat skip an alert outright rather than record `window_closed` off-surface.

Both generators write the nested shape and render `provider` **only when the operator names one**, which is the whole compatibility story: absent is not either default, so a value written at either one breaks the other case. Writing `baileys` by default takes Meta's callback away from every existing Cloud deployment at the upgrade, silently; writing `whatsapp_cloud` by default makes a fresh install ignore the product default. An empty value is refused outright on both shapes, because an unrecognised provider fails `load_config` in every istota process whether or not the block is enabled — the scheduler, the web app, the webhook receiver and every host-side skill CLI spawn alike.

**The sidecar runs as a unit of its own on Ansible and a service of its own on compose, and the daemon spawns nothing by default.** `[whatsapp.baileys] sidecar_command` stays empty on both, which is the `sidecar_argv=()` shape: systemd restarts a unit that exited on a logged-out session where the in-process supervisor deliberately does not, so a re-pair recovers without touching the scheduler. The role refuses a unit and a `sidecar_command` together — that pairing is the two-clients corruption arranged by configuration, and neither process can detect the other. The unit and the compose service both pass `ISTOTA_BAILEYS_SOCKET` and `ISTOTA_BAILEYS_SESSION_DIR`; the sidecar exits 2 with no log destination when either is absent, and both literals are compared by test against the product's own `default_session_dir` / `default_socket_path` for that shape, since a drift there is a sidecar dialling a socket nobody is listening on with no error on either side.

**Three things about the unit are decisions rather than defaults.** `Wants=`, never `Requires=`, so a scheduler restart does not drop the paired session. `RestartSec=30`, because the steady state of a de-paired session is start-log-exit until somebody scans a code, and the only place it writes is a rotated file inside the 0700 credential directory. And `ReadWritePaths` is narrowed to the data directory rather than `istota_home` as the sibling units have it — those run istota's own code, this one runs a third-party dependency tree while holding a full WhatsApp account. The compose side cannot be narrowed without a second volume.

**Both update paths carry the sidecar, and that is not bookkeeping.** The unit runs a Node program out of the checkout, so it holds stale code the way the Python units do, and on the reference host the two-minute auto-update cron *is* the deploy path — ISSUE-428's class on a second non-Python artifact. Its dependencies are the worse half: a cron-delivered lockfile bump leaves `node_modules` matching the old one, the running process survives on modules it has already required, and the failure surfaces at the next unrelated restart, days after the commit that caused it. Both paths diff the sidecar's directory between the deployed marker and the target, reinstall when the lockfile moved or `node_modules` is absent, and restart unconditionally; the install stops the unit first and takes the role's update lock, because `npm ci` deletes `node_modules` before installing and `Restart=always` turns any crash in that window into an exit loop against a half-populated tree.

Docker, Ansible and `istota serve` all run one webhook receiver for location, SMS and WhatsApp together. Setup for both adapters, the operating modes and the operational commands are in `docs/features/whatsapp.md`.

## Residuals

Recorded rather than closed, and each is a decision somebody may want to revisit.

- **The session directory has no advisory lock.** `istota whatsapp pair` detects a running *bridge*, by connecting to the daemon's socket, and not a sidecar somebody else's systemd unit is running — so on the external-unit shape a pair can start a second Baileys client against one session directory, which is the auth-state corruption every other guard here exists to prevent. Every remedy names both processes and the role refuses the one configuration that arranges two clients by inventory alone. The real guard is a lock inside the session directory taken by whichever process opens it, which needs a lock on the Node side.
- **The bridge's graceful `shutdown` frame is unreachable on the daemon's own shutdown path.** `AsyncRuntime._shutdown` cancels every pending task before it runs the cleanup hooks, so the connection handler's `finally` has already dropped the writer by the time `stop()` asks. A spawned sidecar is SIGTERM'd instead, which works, and the external shape is correctly not told at all. `istota whatsapp pair` is the one caller that reaches the frame.
- **Nothing reaps a stale claim**, on either push surface. A send cancelled at shutdown can leave `sent_whatsapp` `pending` with a claim and no id, which is unresolvable and holds the parked-status gate open deployment-wide; the window is real, since the shutdown budget is about five seconds against a 30s SQLite busy timeout. The reaper is owed by SMS and WhatsApp together.
- **Pairing is not reachable from inside the compose stack.** `istota whatsapp pair` spawns a sidecar of its own and the istota image ships neither the program nor its dependencies, so a session is paired from a checkout with node and the directory moved into the volume. The fix is a listen-only mode for the command — the daemon listens, the compose sidecar dials in and supplies the QR, with the live-socket refusal unchanged.
- **The pinned Baileys version is the one the advisory names as fixed.** The sidecar shipped pinned to 6.7.18, which `npm audit` reports as critical: GHSA-qvv5-jq5g-4cgg, message-upsert and hist-sync spoofing from a crafted `protocolMessage`, on exactly the inbound path the bridge feeds into `handle_whatsapp_batch`. The pin is 6.7.24, where the tree audits clean. The bump also drops the eslint config Baileys 6.7.18 declared under `dependencies`, taking the install from 207 packages to 92. Nothing in any tier connects to WhatsApp, so the version is verified by build and by the API names `index.js` uses being present, and not by a session.
- **The sidecar image is in no test tier.** It was built and exercised by hand when it landed, and the `deploy` tier converges with WhatsApp off, so the systemd unit is executed by nothing either. Every assertion about both is a parse.
- **A mid-migration flip loses Meta's outstanding traffic**, as "What a switch away from Cloud costs" states above.
- **A LID contact whose phone number WhatsApp withholds cannot use this surface at all.** WhatsApp addresses an ordinary one-to-one chat by LID, a durable per-contact id carrying no number, and the daemon's whole Baileys identity story is the phone JID — `normalize_jid` accepts `@s.whatsapp.net` alone, `jid_number` takes the E.164 out of it for the bootstrap comparison, and `address_for_binding` renders that same spelling back as a destination. The sidecar's `chatAddress` bridges the two by forwarding the `senderPn` the server stamps beside the LID, so the ordinary case resolves; a message arriving with a LID and no usable `senderPn` is dropped with a named reason and can neither enroll nor resolve. Closing it means making the LID a first-class identity column with its own bootstrap story, which is what the `@lid` refusal in `JID_USER_DOMAIN`'s docstring is holding the place for.
- **The reply direction is exercised by nothing.** `sent_whatsapp` had no rows at all when the inbound break was found, so `address_for_binding` -> phone JID -> Baileys `sendMessage` has never run on this adapter, and whether a send to the phone JID lands in a chat WhatsApp is addressing by LID is a fact to observe rather than assume.
