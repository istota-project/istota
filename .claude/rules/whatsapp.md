# WhatsApp

One business phone number through Meta's hosted Cloud API, direct rather than through a BSP. A user-routable push surface, text only, and outside the room model: no `messages` row, no room membership, no Talk or web view. Context comes from the stable `whatsapp-<user hash>` conversation token and task history, and that token is a pure function of `user_id` so it survives every number, username and send-id change. A bare `whatsapp` destination resolves the user's current binding immediately before the send; `whatsapp:<anything>` is refused, so routing cannot become an arbitrary-contact send API. `all` and `both` are unchanged, deliberately — a metered external surface is selected explicitly or not at all.

## Identity is the BSUID, not the number

**One adapter later, that heading is half the rule: identity is the *adapter-native* identity, not the number.** The whatsapp-baileys-adapter spec put a provider seam under this surface, and identity is the one thing on it that is genuinely per adapter — everything else the split touches is a capability the gate order reads off `WhatsAppProviderCaps`. Cloud's identity is the BSUID; Baileys' is the JID, `<number>@s.whatsapp.net`. `whatsapp_user_bindings` carries both plus a nullable `provider` saying which one this row's identity belongs to, added by a column-only migration with no backfill — a NULL reads as `whatsapp_cloud`, which is what every row written before the split is. `transport/whatsapp/identity.py` is the one module that branches on the provider by name; the five rules and their order are identical in both arms, and `webhook.py` delegates to it.

Three properties hold the two apart, and each is the takeover guard one adapter over. An event from one adapter resolves only through that adapter's column, so a stale identity of the wrong kind is never read. A JID whose number matches a row already carrying a *different* JID is refused and alerted, exactly as the recycled BSUID is, under its own dedup namespace so the second alarm is not swallowed as a bump. And a latch onto a row belonging to the other adapter discards `last_user_message_at` and, on the Baileys side, `send_id` — the rule below applied to the case a second identity created, where a row lacking *this* adapter's identity can still carry a full history. That discard is provider-compared and so is a no-op on every pre-split row, which is what leaves the Cloud path as it was.

**`opted_out_at` is outside that discard, and it is the one field where discarding would be the unsafe direction.** The spec is explicit that an adapter switch preserves opt-outs — the SMS property restated — and it is right against the reading that the column names a previous holder: on a migration the holder has not changed, only the adapter has. Clearing it silently revokes a STOP and resumes messaging somebody who asked to be left alone, where keeping it merely withholds until they send START. Where the holder genuinely did change, the discard lives in `set_whatsapp_binding` and the refusal in the resolver's bootstrap arm, which are the paths that know.

The bootstrap arm's refusal is per adapter, which means an adapter switch does let a phone number alone re-establish a principal on a row whose identity of *this* adapter is unset. Refusing that is not available: on a genuine migration every row is in exactly that state, so a refusal locks out the whole deployment, and nothing on the row separates it from a recycled number. The number is the operator's own assertion that it belongs to this user, which is what licenses the latch — so the latch happens and a deduplicated alert says a principal was re-established from a number, rather than the decision being made silently either way.

`last_user_message_at` is Meta's window and only a Cloud-authenticated message writes it. A Baileys message opens no conversation Meta knows about, so stamping it would authorize a free-form send after a switch back to Cloud — where no latch fires, because the BSUID is still there, and so no discard would catch it. `send_id` is likewise Meta's opaque destination and is not written on the Baileys path; the destination there is the JID. An identity reset (`istota user ensure --reset-whatsapp-identity`) clears **both** adapters' identities and the provider stamp, since the verb takes no adapter argument and a half-reset leaves the other adapter resolving the previous holder.

An inbound message whose provenance is not the active provider is refused as `inactive_provider` before any identity lookup, which is the SMS rule ("a complete inactive adapter may authenticate late delivery callbacks, but its inbound messages create no task") on this surface. Delivery events bypass that gate, for the reason the SMS rule keeps them: a status callback has to settle its ledger row whether or not the adapter that sent the message is still the active one.

The binding lives in `whatsapp_user_bindings`, its own table rather than a `user_profiles` column, because the webhook has to read and write it inside the same transaction as the dedup claim and the task creation. A `db_path`-taking store would open a second connection under an open write transaction, wait out the 30s busy timeout and raise — the hazard `.claude/rules/notifications.md` documents.

Resolution order: a non-empty BSUID matched against the bindings; failing that, a valid `wa_id` in E.164 form matched against one bootstrap number whose BSUID is still empty, which latches the BSUID and the send id atomically. **A bootstrap number matching a user whose stored BSUID differs is refused and alerted, never taken** — that is a recycled line, and reading it as the same principal is the takeover this table exists to prevent. An unknown sender gets a 200, no task, no retained identifier and a one-way fingerprint in the log.

**Any change to the identity discards everything learned about the previous holder**, `last_user_message_at` above all: it is the sole input to the 24-hour service window, so carrying it across would authorise a free-form send to somebody who never wrote in. `opted_out_at` goes with it, because it belonged to the previous holder and leaving it strands the new one opted out with no verb to clear it. `set_whatsapp_binding` and `reset_whatsapp_identity` discard the same set.

`touch_whatsapp_binding` writes the uniquely-indexed `send_id` **conditionally**, in SQL with a correlated `EXISTS`. Unconditional, a BSUID sitting stale in another user's `send_id` raised `IntegrityError` out of the batch, the route answered 503, and Meta redelivered into the same deterministic failure for ever with no disposition row, no task and no alert. The rest of the touch lands including the service window, the helper returns False and the caller alerts. Deliberately not the latch path's fail-closed: the sender is legitimate, and refusing their every message over a row that is not theirs is a denial of service.

## The webhook

`GET`/`POST` at the fixed `/webhooks/whatsapp`. Three phases, and the order is the module's design: **authenticate then read** (bounds, content type, configured secret, HMAC over the exact raw bytes, decode — a 403 arriving as a 400 has told the caller the body was read); **normalize the whole batch before `BEGIN IMMEDIATE`**, so a malformed element cannot leave the first message applied behind a 200 nobody will retry; **one transaction for the batch**, with any database failure rolling back to a 503 Meta retries.

`client.verify_signature` adds three guards in front of PyWa's validator, and the load-bearing one is refusing an absent app secret: `webhook_updates_validator` takes the secret as a plain `str` and computes an HMAC under `b''`, so with none configured it does not fail to validate — it validates against a key every reader of this repository knows. The route refuses to serve besides.

An oversized body answers **413**, not the 400 the spec's design section wrote, matching the sibling SMS route through the same shared bounded-body reader. The GET handshake bounds `hub.challenge` to ASCII digits and refuses anything else with 400, which is stricter than "echo it as plain text" — the value is echoed verbatim from a route that answers before anything authenticates it.

The normalizer reads `pricing.billable` and never derives it, where PyWa's own `Pricing.from_dict` infers it from `type == "regular"` when the field is absent. A guess is what opens, or fails to open, the billing circuit. Messages are paired with contacts by sender id, never positionally: PyWa takes `contacts[0]` for every message in a value, which is fine while a value holds one of each and is a principal takeover when it does not.

## Outbound: one send, one row, no resend

`sent_whatsapp` claims a `logical_key` and commits **before** the network call, which is the whole no-resend guarantee: from that instant every later call reads the row as settled and returns. So the claimed region is wrapped whole, catching `BaseException` (both callers run where shutdown delivers `CancelledError`, on the one path where the send may already be on the wire), and split at the send — a pre-send failure settles `failed`, since it is provably a message that never left, and `unknown` is the one state an operator can never resolve.

The adapter's whole job is one bit, and **4xx is the line**. A client error means Meta read the request, applied a documented rule and refused it, so nothing was queued; a 5xx is Meta failing while handling a request it may already have accepted. PyWa's `is_transient` is deliberately not consulted — it answers whether retrying later might work, not whether this attempt was applied. No failure reason is ever built from an exception: Meta's prose, PyWa's exception text and an httpx repr all carry the request URL, which carries the recipient and the token's path segment, so the reason comes from a fixed table and only the numeric code is taken off the exception.

The gate order is by whose decision each is: transport, binding, opt-out, billing circuit, window, budget. Opt-out outranks the window deliberately — reporting a closed window about somebody who asked not to be messaged is an alert nobody should be woken by. `_TERMINAL_FOR_STATUS` and `_NO_RESEND` are two sets: the first says which rows a status callback may not move, the second which rows no send path may re-attempt, and they differ on the four states meaning Meta took the message.

**A confirmation prompt is an interactive message and Meta caps that body at 1,024 characters, not 4,096.** Rendered at the text limit, Meta refused every question past a quarter of the budget and the task parked until it expired. The scheduler sizes the body rather than the renderer, and asks `render_whatsapp` for the budget rather than repeating the arithmetic: cut at the renderer's boundary, the truncation took the `Task #N. Reply YES or NO.` sentence with it, which is the address `!confirm <id>` and a typed YES resolve at. With a template configured it sizes to the *smaller* of the interactive and template-parameter budgets, because the window is not known where the sizing happens.

Monotonicity compares the canonical status rank alone. `sent_whatsapp` has no event-time column, and over a total order of four statuses the rank answers what a timestamp would. **Pricing observation sits outside that ladder on purpose**: reading it only on an applied transition would throw the evidence away in exactly the out-of-order case the ladder exists for, and a billable `failed` row is the loudest evidence there is. `billable` is never downgraded from true by a later false; the other three pricing fields take the latest non-NULL observation.

**A status can arrive before the id it names**, because Meta mints that id in its reply to the send and `_settle` writes it a statement later. Such a status matches no row; discarding it is harmless for `sent`, `delivered` and `read`, which a later status supersedes, and silently wrong for `failed` — the row stays `accepted` for good, no alert is raised, and the surface reports a delivery that failed (ISSUE-490). It is held in `whatsapp_parked_status` and replayed by `_settle_async` once the id lands.

**The replay is a second transaction, after the settle commits, and the obvious shape is the wrong one.** Draining inside `_settle`'s own transaction reads better and was written first: it makes the ordering a property of one function instead of resting on a lock another module takes. It is wrong because `db.get_db` commits only on a clean exit, so any raise out of a replay — a notification write, the admin file `_write_billing_alerts` reads, a parked table `init_db` has not created yet — unwinds the `meta_message_id` write with it. That loses the id of a message Meta accepted, no later status can match the row again, and the escape wrapper then settles it `unknown`: strictly worse than the defect. The replay is also never allowed to raise past `_settle_async`.

Nothing between the two transactions can lose a status, and that is the one property the lock argument still carries. A status is parked only under `handle_whatsapp_batch`'s `BEGIN IMMEDIATE`, which holds the write lock across its own row lookup and the park, and the settle's UPDATE needs that same lock — so a batch either commits its park before the settle, and the drain finds it, or does its lookup after, and finds the row. `test_a_status_racing_the_id_write_is_never_lost` drives two real threads at it; with the batch's `BEGIN IMMEDIATE` weakened to a deferred `BEGIN` it goes red every run.

The replay goes back through `apply_delivery_event` rather than writing the row directly, which is what keeps the one-send contract: the ladder refuses a row already in `_TERMINAL_FOR_STATUS`, so a `failed` drained ahead of a `delivered` parked after it closes the row and the `delivered` is a duplicate. `_settle`'s own UPDATE carries that set as a `WHERE` clause for the same reason, which is a rule the write had always needed and not only since parking: `deliver_whatsapp`'s escape wrapper settles `unknown` on any escape, and a cancellation arriving after an earlier settle committed would otherwise overwrite a settled row with the one state an operator can never resolve.

**The parked row keys on the message fingerprint, never the id.** The in-flight test is deployment-wide and cannot tell one of our ids from another application's on the same number, so a raw id would persist an identifier naming somebody else's private conversation — the thing every log line in the transport fingerprints to avoid. The drain fingerprints the id it already holds and matches on that, so nothing is lost.

**Parking is bounded twice and needs both bounds.** A status is parked only while some send sits between its claim and its settle — `status = 'pending'` with a claim stamped and no id — so a status for a message this deployment never sent is discarded exactly as before. That gate alone is not enough, because a send killed between those two points leaves an in-flight row nothing clears, and while one exists every unmatched status parks; so a row past `PARKED_STATUS_WINDOW` is pruned whenever the table is touched — on an attempted park, *before* its gate, and on a drain. Behind the gate the only thing clearing the table would be a successful park, which is exactly the deployment that has gone quiet keeping its rows for good. A pruned row is a status istota held and could not place, so the count is logged as a warning: it is what the old unknown-id warning said, moved to where it is still reached.

**The park is guarded and falls through to the discard.** That branch used to be a log line and a return, so it could not fail; it now writes, and `handle_whatsapp_batch` turns any exception into a 503 the whole batch rolls back into and Meta retries against. A park that cannot happen must cost the status, never the batch.

**The SMS ledger has the same race and is not fixed here.** `sms.outbound.apply_delivery_event` matches on `provider_message_id`, which `_persist_outcome_or_unknown` writes only after the adapter returns, so a `failed` callback that overtakes it is discarded the same way. It is a different table with a composite key, on a surface that is live, and a shared holding table would have to be generalized over the key and the in-flight predicate — its own change.

## Cost controls

Two, and neither is called a guarantee. **The monthly cap is reserved by the claim, in the claim's own `BEGIN IMMEDIATE`** — the count and the row that increments it are one write transaction, so the last free slot cannot be read as free twice (measured: a deferred `BEGIN` turns the two-thread test red every run). `quota_month` is stamped on every row including blocked ones, but only a *claimed* row counts, so a `window_closed` or `budget_exhausted` row consumes nothing while a `failed` or `unknown` one consumes its slot and is never reclaimed.

**`monthly_service_attempt_limit` bounds service attempts and bounds template attempts by nothing.** Implemented as named. The consequence is inverted and worth knowing before enabling paid mode: with the cap spent, an open window is refused while a closed one still bills a template. Templates are reachable only under `allow_paid`, and `doctor.whatsapp.billing` reports the template count beside the service count so the volume is visible. A `monthly_template_attempt_limit` is the real fix and is a spec change.

**The circuit breaker is persistent and deployment-wide.** In `free_guard` the first authenticated status carrying `billable = true` sets `whatsapp_runtime.billing_blocked_at` and blocks every later send. The message that revealed the charge may already be billable; what the breaker buys is that the next one is not. Its alert is not `write_delivery_failure` — that one is about a message that reached nobody, this is a message that arrived and was charged for — and it goes to each admin as well as the recipient, since a deployment-wide block landing in one non-admin's inbox is not an operator notice. `template_available` re-checks `billing_policy == "allow_paid"` rather than resting on `load_config`'s refusal: one validator standing between a free-biased deployment and a paid message is one place for the rule to be edited out of.

## Config, credentials and deployment

Structural validity fails the load (`whatsapp_structural_config_errors`); **credential presence does not** (`whatsapp_credential_errors`, reported by doctor, refused at use). Failing the load on a missing secret repeats ISSUE-058: under `istota_use_environment_file` the Ansible role renders the three empty on purpose and delivers them through `secrets.env`, which the role's own `command:`/`script:` tasks cannot read. `graph_api_version` accepts `v25` and `v25.0`, since PyWa 4.4 pins Graph `25.0` and a `v<integer>` rule would refuse every real version string.

Everything in this file above that line is the Cloud adapter, and its settings now live in `[whatsapp.cloud]` rather than flat on `[whatsapp]`; `provider` defaults to `baileys`, and a pre-adapter flat block carrying a Meta id or credential still resolves to `whatsapp_cloud` so an existing deployment is unchanged. Both halves of the validation are per-provider: only the active adapter's structural arm runs, and the credential report names the active adapter's own fields. `.claude/rules/config.md` has the rules; the rewrite of this file for the seam is the Baileys spec's last stage.

The transport registers on `config.whatsapp.enabled` alone, not "enabled and locally valid": structural validity is already raised at load and gating on credentials would repeat ISSUE-058 again. Local validity is enforced per send by the outbound gate (recording `unconfigured`) and per user by `is_whatsapp_configured`, which applies the four gates still true in an hour — transport, binding, opt-out, billing circuit — plus the cap, and deliberately **not** the service window, which reopens on the user's next message and whose absence would make the heartbeat skip an alert outright rather than record `window_closed` off-surface.

`whatsapp_webhooks_enabled(config)` is `enabled` plus the **active** provider being one with an HTTP callback at all (`WHATSAPP_WEBHOOK_PROVIDERS`), and the asymmetry with `sms_webhooks_enabled` is the point: SMS keeps a complete inactive provider's routes so a late delivery callback still authenticates across a switch, while WhatsApp has one account and both handlers refuse every request while the block is off. It is deliberately **not** `WhatsAppProviderRegistry.callback_only_names()`, which does list every built adapter and is an answer about credentials a switched-away deployment still holds — reading it as the mount would restore the SMS rule this surface does not follow. Four places read the same predicate — that function, `serve._maybe_mount_webhooks`, the role's `Resolve webhook receiver need`, and the `whatsapp` compose profile — and today only the first two can express the provider half, since neither deployment generator renders `provider`; all four agree by unreachability until that lands.

**Two things nginx has to do that the application cannot, and one the proxy cannot do either.** The verify token arrives as a *query value* on the GET handshake and nginx decides what to log before the route runs, so `/webhooks/whatsapp` gets `access_log off` in both shipped configurations; a `log_format` naming `$uri` would keep the line but is only valid at http level, and both templates are one server block inside a generated `conf.d`. **Uvicorn's default access formatter renders `get_path_with_query_string(scope)`**, so silencing the front end alone leaves the token in the container log and the journal — measured against a live server, not read off the source. `serve.build_uvicorn_server` had always passed `access_log=False`, so the combined process was the only shape holding the property the docs claimed; both standalone receivers now run `--no-access-log` and a test pins all three. And the route-specific `client_max_body_size 512k` sits above istota's own 256 KiB cap so an oversized POST is answered by the application rather than by nginx with an HTML page Meta retries against.

Docker, Ansible and `istota serve` all run one receiver for location, SMS and WhatsApp together. Setup, the three operating modes and the operational commands are in `docs/features/whatsapp.md`.

## The Baileys sidecar, so far

Interim, like the paragraphs above it: the seam's second adapter does not exist yet, so nothing here is reachable from a shipped deployment and the full rewrite is still the spec's last stage. What exists is the transport under it — `baileys_protocol.py`, the wire format, and `baileys_bridge.py`, the daemon side of a Node subprocess the daemon owns.

**The daemon listens and the sidecar dials**, `devbox_proxy`'s arrangement: the listener's lifetime is the daemon's, so a sidecar restart reconnects to a socket that never went away, and the daemon creates the inode and therefore owns its mode. One JSON object per line, capped at 256 KiB on *both* ends, with a `hello` frame carrying a protocol version the bridge refuses on mismatch rather than reading an older shape's fields out of a newer frame. **There is no HMAC and none is faked** — the trust boundary is the socket itself, `AF_UNIX`, 0600 from the instant the inode exists rather than narrowed to it, with no network peer, which is why the Baileys adapter's `verify_signature` is `None` and nothing on this path calls it.

**The session directory is a full-account credential.** Whoever holds it can send and read as the paired number, with no second factor and no revocation short of unlinking the device. It is 0700 whether it was just created or already existed — `mkdir(mode=…)` applies only to a directory the call creates, so the mode is asserted on an `O_NOFOLLOW` descriptor every time — and that same descriptor is what refuses one belonging to another uid, which a mode check alone cannot see: a directory already at 0700 skips the `fchmod` and with it the `EPERM` that would have been the only signal, so a planted one would be adopted in silence. The sidecar is spawned under `umask 0o077` so its own files land 0600, with **its stdio discarded** — inherited, a chatty Baileys logger writes JIDs and message bodies into the daemon's own journal, where this module's never-log rule does not reach, and `PIPE` with no reader blocks the child once the buffer fills; the sidecar owning a log destination inside the 0700 directory is the Node program's job. The directory is bound into no sandbox at any path, and neither its contents nor a `qr` payload is ever logged, a QR being the pairing credential itself. The sidecar's environment is an **allowlist** (`PATH`, `HOME`, the locale pair, `TZ`, `NODE_ENV`, plus the socket and session paths) rather than `os.environ` minus a pattern list, so a credential name nobody thought to filter is excluded by construction.

**Nothing about the one-send contract changes, and the definite line is `writer.write`.** Above it — no sidecar connected, a session in a permanent fatal state, a request that would not encode — the message provably never entered the socket and the row settles `failed`; from `write` onwards the bytes may be in the kernel buffer whatever `drain` then says, so a timeout, a dropped link and an unreadable answer all settle `unknown`. `definite` is read off the `send_result` line and never derived, and no failure reason is ever built from the sidecar's own words: Baileys' errors carry the destination JID and, on a Boom error, the whole request, so the reason comes from a fixed table exactly as it does for Meta's prose. A send is matched to its answer by a request id rather than by order, since one long-lived connection multiplexes.

**The read loop dispatches and never works**, which is a deadlock rather than a tidiness rule: handling an inbound message can end in a reply, and a reply awaits a `send_result` only that loop can deliver. So inbound events go to a bounded queue drained by **one** worker — serial, because order within a conversation is meaning — and a full queue *drops* loudly rather than blocking the reader, since back-pressure there is the deadlock. The worker calls `handle_whatsapp_batch(..., provider="baileys")`, the same entry point Meta's signed webhook calls and inside the same `BEGIN IMMEDIATE`, so dedup, identity, the claim row and task creation are common code. The whole `with db.get_db(...)` block is one `asyncio.to_thread` callable: a connection must not hop threads, and that block opens and commits the transaction. A malformed line is logged, counted and dropped — a message this side cannot read is not one it can attribute, and attributing one to a guessed sender is a principal takeover rather than a lost message — while a *database* failure is retried in place and in order, because the webhook answers 503 and lets Meta redeliver and nothing redelivers over a socket. **The retry is bounded and then the event is dropped with a count**, which is a deviation from the spec's "parked and retried rather than dropping" and is stated as one: the worker is serial, so an unbounded retry starves every message behind it and the queue's own overflow then drops the *newer* ones — trading a loud loss of the message that cannot be written for a silent loss of the ones that could. `failed_events` is what `doctor` reads.

**The definite line is `writer.write` and the catch-all reads a mark rather than assuming a side of it.** Every exception that can reach `send`'s handler today is above that statement, so a fixed ambiguous answer there spends `unknown` on a message that never left — and a fixed definite one is the same mistake waiting for a refactor to move a post-write failure onto the path. Both waits are bounded and for different reasons: the answer by `SEND_TIMEOUT_SECONDS`, and `drain()` by its own smaller bound, because it is held across the write lock and a sidecar that connects and stops reading never lets it return — unbounded, one such peer holds the lock for ever and every later send queues behind it, leaving rows claimed and unsettled and the parked-status gate open deployment-wide. The writer is adopted only after the `hello` passes, so no `send` can be handed to a peer whose version is unknown.

**A permanent `fatal` ends the respawn loop rather than slowing it.** A logged-out session comes back only from a re-pair, so respawning burns a process every few seconds and changes nothing; the running sidecar is stopped rather than left re-reporting the same fatal, and sends refuse *definitely* until it resolves. `sidecar_argv=()` is a first-class mode, not a test affordance: the Ansible shape runs the sidecar as its own systemd unit, so the bridge listens and supervises nothing.
