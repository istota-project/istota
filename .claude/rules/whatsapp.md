# WhatsApp

One WhatsApp number reached through one of two adapters, behind a provider seam that mirrors the SMS one. `baileys` is the default: a paired WhatsApp Web session held by a Node sidecar, free and unmetered, with no service window, no template and no Meta business account. `whatsapp_cloud` is Meta's hosted Cloud API, direct rather than through a BSP, and is the sanctioned path — metered, window-bound, and configured against a verified account. `config.whatsapp.provider` picks one and a deployment runs one; there is no failover between them.

The surface is the same either way. It is a user-routable push surface, outside the room model: no `messages` row, no room membership, no Talk or web view. Inbound it takes text and one media type, images; outbound it sends text alone, since `Transport.deliver` carries `text: str` and there is no outbound-attachment concept on any surface. Context comes from the stable `whatsapp-<user hash>` conversation token and task history, and that token is a pure function of `user_id`, so it survives every number, username, send-id and adapter change. A bare `whatsapp` destination resolves the user's current binding immediately before the send; `whatsapp:<anything>` is refused, so routing cannot become an arbitrary-contact send API. `all` and `both` are unchanged, deliberately — the rule was written about a metered surface and stands without the metering, because the surface is external either way.

Almost every hard constraint this file used to state is a fact about the Cloud API rather than about WhatsApp. The 24-hour window, approved templates, the monthly attempt cap, `quota_month`, the pricing ladder, the billing circuit breaker, the signed webhook and the 1,024-character interactive body are all Cloud's. What is common to both adapters is the one-send ledger, the parked-status machinery, delivery-state monotonicity, identity resolution, opt-out, and the inbound-image staging below.

## The seam

`transport/whatsapp/providers/` mirrors `transport/sms/providers/` in shape and deliberately not in code: the two surfaces have different identities, different ledger keys and different delivery vocabularies, so what is shared is the arrangement. `WhatsAppProviderAdapter` is a frozen record of `name`, `caps`, `send`, and the pair `parse_webhook` / `verify_signature`, which are `None` together for an adapter that receives over a transport of its own. `make_provider_registry` importlib-loads `providers.<name>.build_adapter`, keeps the active adapter plus any fully-configured one as callback-only, and refuses three contract faults at build: an adapter answering to another name, a half-declared webhook pair, and a synchronous `send`. The last is a ledger property rather than tidiness — a synchronous `send` fails inside the claim-to-settle region, where the backstop settles `unknown` for a message nobody sent. A fault on the *active* adapter raises; on a non-active one that adapter is dropped and logged at ERROR, so a programming error in a provider nobody selected is not a whole-surface outage.

**The build gate departs from the SMS one in one place.** SMS gates both the active and the callback-only role on the provider's config block being populated and complete, which works because every SMS provider's credentials are in the config file. Baileys declares no credential fields at all — its credential is a paired session on disk — so a populated-block test reads False for it for ever, and gating the active role on it would leave a Baileys deployment with no adapter and every send recorded `unconfigured`. So the active provider is built whenever nothing it declares is missing, and a non-active one only when its block is populated as well.

`WhatsAppProviderCaps` is what the gate order reads instead of branching on a name: `metered`, `has_service_window`, `supports_templates`, `delivery_receipts`, `address_field`, `service_body_limit`, `interactive_body_limit`. It takes **no defaults**, so a third adapter answers every question rather than inheriting whichever answers happened to suit the first two — which also makes widening it a deliberate seam change, and is why the last three arrived with both adapters answering them in the same diff. `delivery_receipts` is declared ahead of its reader and nothing reads it: the parked-status table, the status ladder and the failure alert are unconditional, so declaring it False disables none of them. Read it as a description, not a switch.

**Nothing was physically moved behind the seam, and the property that holds is narrower than "the Meta code lives in the adapter".** `client.py` was already the PyWa boundary and `webhook.py` was already Cloud-only, so what was missing was the binding rather than the separation; relocating either buys a large diff, an import-path change in every test that names them, and no boundary that was not already there. `_observe_pricing`, `quota_month`, `render_template_parameter` and Meta's two character caps are still in `outbound.py`. What is checkable is that **`outbound.py` imports no provider module at run time**, held by a drift guard, and that every gate reads `adapter.caps`. The drift guard's one carve-out is that the word `pywa` may appear in a comment saying what that module refuses to do.

`transport/whatsapp/identity.py` is the only module that branches on the provider by name, because an identity is genuinely per adapter rather than a capability the gate order can read.

## Identity is the adapter-native identity, not the number

Cloud's identity is the BSUID; Baileys' is the JID, `<number>@s.whatsapp.net`. `whatsapp_user_bindings` carries both, plus a nullable `provider` saying which adapter established this row's identity. The migration adds two columns and one partial unique index on `jid` — the index is not optional, because each of these columns decides which user an authenticated event may act as, so two rows holding one value is a principal takeover. There is no backfill: a NULL `provider` reads as `whatsapp_cloud`, which is what every row written before the split is.

The binding lives in its own table rather than a `user_profiles` column because the inbound path has to read and write it inside the same transaction as the dedup claim and the task creation. A `db_path`-taking store would open a second connection under an open write transaction, wait out the 30s busy timeout and raise — the hazard `.claude/rules/notifications.md` documents.

Resolution order is the same five rules in both arms. The adapter-native identity is matched against the bindings; failing that, a valid E.164 number — Meta's `wa_id`, or the number embedded in the JID — is matched against one bootstrap number whose identity column *for this adapter* is still empty, which latches it atomically. **A bootstrap number matching a user whose stored identity for that adapter differs is refused and alerted, never taken** — that is a recycled line, and reading it as the same principal is the takeover this table exists to prevent. An unknown sender creates no task, leaves no retained identifier and gets a one-way fingerprint in the log. `webhook.py` delegates to `identity.py`, and so does the Baileys bridge's inbound worker.

Three properties hold the two adapters apart, and each is the takeover guard one adapter over. An event from one adapter resolves only through that adapter's column, so a stale identity of the wrong kind is never read. A JID whose number matches a row already carrying a *different* JID is refused and alerted exactly as a recycled BSUID is, under its own dedup namespace so the second alarm is not swallowed as a bump. And a latch onto a row belonging to the other adapter discards the derived state described below.

**The bootstrap refusal is per adapter, which means an adapter switch does let a phone number alone re-establish a principal** on a row whose identity for the new adapter is unset. Refusing that is not available: on a genuine migration every row is in exactly that state, so a refusal locks out the whole deployment, and nothing on the row separates it from a recycled number. The number is the operator's own assertion that it belongs to this user, which is what licenses the latch — so the latch happens and a deduplicated `whatsapp-cross-adapter` alert says a principal was re-established from a number, threaded into the accepted result so it is pushed rather than only filed.

**There are two discards with two different triggers, and collapsing them is a defect in either direction.**

A **holder** change — a new bootstrap number, a cleared identity — discards everything learned about the previous holder, `opted_out_at` included: it belonged to that holder, and leaving it strands the new one opted out with no verb to clear it. `last_user_message_at` matters most there, since it is the sole input to Meta's window and carrying it across would authorize a free-form send to somebody who never wrote in. `set_whatsapp_binding` and `reset_whatsapp_identity` own that discard.

An **adapter** change — a latch onto a row whose identity belongs to the other adapter — discards `last_user_message_at` and, on the Baileys side, `send_id`, and **keeps `opted_out_at`**. The holder has not changed there, only the adapter has, so clearing the opt-out silently revokes a STOP and resumes messaging somebody who asked to be left alone, where keeping it merely withholds until they send START. That discard is provider-compared and so is a no-op on every pre-split row, which is what leaves the Cloud path as it was.

`last_user_message_at` is Meta's window and only a Cloud-authenticated message writes it. A Baileys message opens no conversation Meta knows about, so stamping it would authorize a free-form send after a switch back to Cloud — where no latch fires, because the BSUID is still there, and so no discard would catch it. `send_id` is likewise Meta's opaque destination and is not written on the Baileys path; the destination there is the JID. An identity reset (`istota user ensure --reset-whatsapp-identity`) clears **both** adapters' identities and the provider stamp, which is wider than the spec's "for that adapter" and is deliberate: the verb takes no adapter argument, it is a statement that the learned identity on this row is wrong, and a half-reset leaves the other adapter resolving the previous holder the moment the deployment switches back.

An inbound message whose provenance is not the active provider is refused as `inactive_provider` before any identity lookup, which is the SMS rule ("a complete inactive adapter may authenticate late delivery callbacks, but its inbound messages create no task") on this surface. The refusal is deliberately non-durable — it returns before the dedup claim, because claiming a message id under a user id that no identity resolution produced would be worse. Delivery events bypass the gate entirely, for the reason the SMS rule keeps them: a status has to settle its ledger row whether or not the adapter that sent the message is still the active one.

`touch_whatsapp_binding` writes the uniquely-indexed `send_id` **conditionally**, in SQL with a correlated `EXISTS`. Unconditional, a BSUID sitting stale in another user's `send_id` raised `IntegrityError` out of the batch, the route answered 503, and Meta redelivered into the same deterministic failure for ever with no disposition row, no task and no alert. The rest of the touch lands including the service window, the helper returns False and the caller alerts. Deliberately not the latch path's fail-closed: the sender is legitimate, and refusing their every message over a row that is not theirs is a denial of service. A Baileys touch passes no send id and no window, so it raises no spurious alert.

## Outbound: one send, one row, no resend

Common to both adapters. `sent_whatsapp` claims a `logical_key` and commits **before** the network call, which is the whole no-resend guarantee: from that instant every later call reads the row as settled and returns. So the claimed region is wrapped whole, catching `BaseException` (both callers run where shutdown delivers `CancelledError`, on the one path where the send may already be on the wire), and split at the send — a pre-send failure settles `failed`, since it is provably a message that never left, and `unknown` is the one state an operator can never resolve.

**The adapter's whole job is one bit**, and each adapter draws the line in its own vocabulary. For Cloud it is the status code: a 4xx means Meta read the request, applied a documented rule and refused it, so nothing was queued, while a 5xx is Meta failing while handling a request it may already have accepted. PyWa's `is_transient` is deliberately not consulted — it answers whether retrying later might work, not whether this attempt was applied. For Baileys the line is `writer.write` on the socket, and `definite` is read off the `send_result` line rather than derived. **No failure reason is ever built from an exception on either adapter**: Meta's prose, PyWa's exception text and an httpx repr all carry the request URL, which carries the recipient and the token's path segment, and a Baileys error carries the destination JID and, on a Boom error, the whole request. The reason comes from a fixed table and only a numeric code is taken off the exception.

The gate order is by whose decision each is — transport, binding, opt-out, billing circuit, window, budget — and **three of the six skip themselves where the caps say the precondition cannot arise**. The billing circuit and the budget need `metered`, the window needs `has_service_window`, and the closed-window fall-through to a template needs `supports_templates`. Under Baileys the order is transport, binding, opt-out, and nothing after. Opt-out outranks the window deliberately: reporting a closed window about somebody who asked not to be messaged is an alert nobody should be woken by.

The destination is the adapter's own binding column, named by `caps.address_field`. `identity.address_for_binding` holds the two spellings, beside the JID parser they have to agree with, because a destination built by one rule and an identity parsed by another means a user enrolled by number can be messaged and never recognised when they answer.

**A confirmation prompt is an interactive message and Meta caps that body at 1,024 characters, not 4,096.** Rendered at the text limit, Meta refused every question past a quarter of the budget and the task parked until it expired. The scheduler sizes the body rather than the renderer, and asks `render_whatsapp` for the budget rather than repeating the arithmetic: cut at the renderer's boundary, the truncation took the `Task #N. Reply YES or NO.` sentence with it, which is the address `!confirm <id>` and a typed YES resolve at. That cliff is Meta's, so the budget is the adapter's answer rather than a constant: `service_body_limit` and `interactive_body_limit` are caps fields and `outbound.confirmation_body_budget` folds them with the template-parameter cap, so the scheduler asks one question instead of spelling out three Cloud facts. Baileys has no interactive object, its two budgets are equal, and a stale `[whatsapp.cloud]` template block does not narrow them because `supports_templates` is False.

`_TERMINAL_FOR_STATUS` and `_NO_RESEND` are two sets: the first says which rows a status callback may not move, the second which rows no send path may re-attempt, and they differ on the four states meaning the message was taken.

Monotonicity compares the canonical status rank alone. `sent_whatsapp` has no event-time column, and over a total order of four statuses the rank answers what a timestamp would. **Pricing observation sits outside that ladder on purpose**: reading it only on an applied transition would throw the evidence away in exactly the out-of-order case the ladder exists for, and a billable `failed` row is the loudest evidence there is. `billable` is never downgraded from true by a later false; the other three pricing fields take the latest non-NULL observation. Only Cloud produces pricing at all — a Baileys receipt carries none — so the ladder is common and its pricing arm is fed by one adapter.

**A status can arrive before the id it names**, on both adapters and for the same reason: Meta mints that id in its reply to the send, Baileys mints it in `send_result`, and `_settle` writes it a statement later. Such a status matches no row; discarding it is harmless for `sent`, `delivered` and `read`, which a later status supersedes, and silently wrong for `failed` — the row stays `accepted` for good, no alert is raised, and the surface reports a delivery that failed (ISSUE-490). It is held in `whatsapp_parked_status` and replayed by `_settle_async` once the id lands.

**The replay is a second transaction, after the settle commits, and the obvious shape is the wrong one.** Draining inside `_settle`'s own transaction reads better and was written first: it makes the ordering a property of one function instead of resting on a lock another module takes. It is wrong because `db.get_db` commits only on a clean exit, so any raise out of a replay — a notification write, the admin file `_write_billing_alerts` reads, a parked table `init_db` has not created yet — unwinds the `meta_message_id` write with it. That loses the id of a message that was accepted, no later status can match the row again, and the escape wrapper then settles it `unknown`: strictly worse than the defect. The replay is also never allowed to raise past `_settle_async`.

Nothing between the two transactions can lose a status, and that is the one property the lock argument still carries. A status is parked only under `handle_whatsapp_batch`'s `BEGIN IMMEDIATE`, which holds the write lock across its own row lookup and the park, and the settle's UPDATE needs that same lock — so a batch either commits its park before the settle, and the drain finds it, or does its lookup after, and finds the row. `test_a_status_racing_the_id_write_is_never_lost` drives two real threads at it; with the batch's `BEGIN IMMEDIATE` weakened to a deferred `BEGIN` it goes red every run.

The replay goes back through `apply_delivery_event` rather than writing the row directly, which is what keeps the one-send contract: the ladder refuses a row already in `_TERMINAL_FOR_STATUS`, so a `failed` drained ahead of a `delivered` parked after it closes the row and the `delivered` is a duplicate. `_settle`'s own UPDATE carries that set as a `WHERE` clause for the same reason, which is a rule the write had always needed and not only since parking: `deliver_whatsapp`'s escape wrapper settles `unknown` on any escape, and a cancellation arriving after an earlier settle committed would otherwise overwrite a settled row with the one state an operator can never resolve.

**The parked row keys on the message fingerprint, never the id.** The in-flight test is deployment-wide and cannot tell one of our ids from another application's on the same number, so a raw id would persist an identifier naming somebody else's private conversation — the thing every log line in the transport fingerprints to avoid. The drain fingerprints the id it already holds and matches on that, so nothing is lost.

**Parking is bounded twice and needs both bounds.** A status is parked only while some send sits between its claim and its settle — `status = 'pending'` with a claim stamped and no id — so a status for a message this deployment never sent is discarded exactly as before. That gate alone is not enough, because a send killed between those two points leaves an in-flight row nothing clears, and while one exists every unmatched status parks; so a row past `PARKED_STATUS_WINDOW` is pruned whenever the table is touched — on an attempted park, *before* its gate, and on a drain. Behind the gate the only thing clearing the table would be a successful park, which is exactly the deployment that has gone quiet keeping its rows for good. A pruned row is a status istota held and could not place, so the count is logged as a warning.

**The park is guarded and falls through to the discard.** That branch used to be a log line and a return, so it could not fail; it now writes, and `handle_whatsapp_batch` turns any exception into a 503 the whole batch rolls back into and Meta retries against. A park that cannot happen must cost the status, never the batch.

**The SMS ledger has the same race and is not fixed here.** `sms.outbound.apply_delivery_event` matches on `provider_message_id`, which `_persist_outcome_or_unknown` writes only after the adapter returns, so a `failed` callback that overtakes it is discarded the same way. It is a different table with a composite key, on a surface that is live, and a shared holding table would have to be generalized over the key and the in-flight predicate — its own change.

## Inbound images

A photograph sent to the number becomes a task whose `attachments` list names it, so `image_attachments.prepare_image_attachments` renders the pixels and the OCR block into the prompt exactly as it does for a Talk attachment. Nothing in that pipeline is new and nothing in it is surface-aware; the whole of this work is getting the bytes onto a path in `task.attachments`. A caption rides `InboundWhatsAppEvent.text`, so it is ordinary user-typed text and every gate in `_dispatch_inbound` applies to it unchanged — `STOP` as a caption opts out, `!usage` as a caption dispatches the command, a caption that parses as a confirmation answer answers the parked confirmation. An uncaptioned image gets `MEDIA_ONLY_PROMPT`, a fixed sentence, so the prompt is not empty and the turn reads correctly in task history. Audio, video, documents, stickers and location keep the reply they had.

**The whole difficulty is one ordering constraint, and everything in `media.py` is shaped by it.** Both inbound paths funnel into `handle_whatsapp_batch`, which opens `BEGIN IMMEDIATE` and holds the write lock across the dedup claim, identity resolution, the binding latch and task creation. Fetching media is a network round trip, and a round trip under that lock is the hazard `.claude/rules/notifications.md` names and the one the SMS delivery branch's `delivery_may_park` pre-read exists to avoid: a second connection waits out its 30s busy timeout against the lock the caller holds, and under `istota serve` that router is on the web app's event loop, so it stalls the receiver and the web UI together. So **the bytes land on disk before the transaction opens, and the transaction sees only a path**. `tests/test_whatsapp_media_precheck.py::TestNothingStagesUnderTheWriteLock` drives a second thread holding `BEGIN IMMEDIATE` while the route stages, and asserts on elapsed time rather than on nothing having raised — moving the fetch inside the transaction turns it red at thirty seconds against a two-second bound.

**The two adapters differ only in who fetches and when.** The sidecar downloads on the Baileys path because it already holds the decryption keys; the daemon downloads in the webhook route on the Cloud path because Meta's media endpoint needs the access token. From `media.precheck` onwards it is one code path. That pre-check is common rather than Cloud's, which is the part that reads like tidiness and is not: `stage_to_attachment` copies into *a user's* inbox, so it needs a `user_id`, and the authoritative one does not exist until the transaction, which is after the copy. Cloud needed the pre-check anyway to keep a stranger's media off the wire; Baileys needs it because the file is already on disk with nowhere to go. It reads the opt-out column too, so an opted-out sender's photograph is never copied while the text path stays unchanged and `START` typed as a caption still works.

**It is a pre-filter and not a boundary**, and being allowed to be stale has one consequence handled rather than accepted: a binding can change between the pre-check and the authoritative resolution, and by then the file is in the inbox of whoever the pre-check named. So the pre-check's answer rides `WhatsAppInboundMedia.attached_for_user` and is compared against the authoritative one inside the transaction; a mismatch drops the media, takes the media-failed path, and reports the already-copied file at warning, since nothing can un-copy it. The window is milliseconds and the case is rare, which is why it needs a rule rather than a reader's assumption.

**Bounds are owned by whoever can enforce them.** The per-file cap is the fetcher's: the sidecar aborts past it and sends an error marker rather than a path, and on Cloud the daemon enforces it twice — once against `MediaURL.file_size`, which Meta reports before a byte moves, and once during the stream, because a declared size is a claim. The staging ceiling and the orphan sweep are the daemon's, because only the daemon knows the whole directory and which files were consumed. The sweep runs whenever the directory is touched, `outbound._prune_parked_statuses`' arrangement, rather than on a gate of its own: a gate is a new interval, a new config key and a new thing to be wrong about for a directory whose steady state is empty. A swept orphan is logged at warning, because a staged file istota fetched and could not place is a message somebody sent that nobody answered.

**What an image is here is asked of the bytes, never of a name.** `image_sniff` grew a second predicate rather than a wider first one: `sniff_decodable` answers what the image pipeline can decode, `sniff_raster` still answers what `/chat/files` will serve inline on the app's own origin, and each caller asks the one it means. Widening the first in place would have changed a different subsystem silently, on a browser-support argument that is still correct — so a HEIC in a workspace is still served as an attachment there, deliberately. The HEIF arm is a **major-brand allowlist and never a bare `ftyp` test**: MP4, 3GP and QuickTime are the same ISO-BMFF container, so matching `ftyp` alone types a video as an image and spends a Pillow decode on it. `stage_to_attachment` names the inbox copy from its own sniff, always — the staged file's extension is advisory and the sidecar's declared mimetype is carried for a log line — because `prepare_image_attachments` screens by suffix and an image whose suffix is wrong is skipped downstream with no notice, which is the worst failure available here.

### The staging directory

`{db_path.parent}/whatsapp-media`, 0700, files 0600, written `O_NOFOLLOW` and `O_EXCL` under a daemon-chosen name. There is no operator override and none is planned: the directory is a property of the surface rather than of one adapter, so an override would be `[whatsapp] media_dir` rather than a Baileys key. The location mirrors `default_session_dir` exactly, and it has to, for three independent reasons:

1. **The sidecar must be able to write it.** The Ansible unit runs under `ProtectSystem=strict` with `ReadWritePaths={istota_home}/data`, and that write path is narrower than its siblings' on purpose, because this unit runs a third-party dependency tree while holding a full WhatsApp account. So a dotted sibling under `temp_dir` — where `.control` and the pairing relay live — is unwritable, and widening the unit to reach it would hand the sidecar every user's task temp directory. It is the write path that refuses it and **not** `PrivateTmp=true`, which is also on the unit and is doing a different job: the role renders `temp_dir` as `{istota_home}/tmp`, and a private `/tmp` says nothing about a path that is not under `/tmp`.
2. **Compose already shares it.** The `whatsapp-baileys` service mounts `istota_data:/data` and `render-config.sh` writes `db_path = "/data/db/istota.db"`, so both containers see the same inodes with no new volume.
3. **It is inside the database mask.** `build_bwrap_cmd` masks `db_path.parent` with an empty read-only tmpfs after every other mount, so on the Ansible and compose shapes the directory is bound into no sandbox at any path.

`ISTOTA_BAILEYS_MEDIA_DIR` is a third variable beside the socket and the session directory, named in the daemon's spawn allowlist, the unit template and the compose service. **It is an override rather than a requirement, and that is ISSUE-508's correction to how it shipped.** It was the third variable the sidecar exited 2 without, and that took the whole WhatsApp surface down — text included — on the deploy that introduced it: the two-minute update cron ships `docker/whatsapp-baileys/` and restarts the unit but cannot re-render `istota-whatsapp-baileys.service.j2`, so the new program met a unit that predated the variable, exited 2 on every start, and `Restart=always` turned that into a loop whose journal was empty, because `log` writes inside the session directory and swallows its own failure. The update script's own guard against exactly this shipped in the same merge and lives in a Jinja template, so the copy on the host predated it too — a guard delivered by a deploy protects the next deploy, not the one delivering it. `index.js`'s `deriveMediaDir` answers it instead: `media.default_media_dir` is `{db_path.parent}/whatsapp-media` and `baileys_bridge.default_session_dir`'s own default is `{db_path.parent}/whatsapp-baileys-session`, so the session path the sidecar already holds names the media path outright. The rule that remains is not "never require a variable" but **do not require one whose value is already determined by another variable in the same process** — which is why the socket and the session directory keep the requirement: neither has a sibling to derive from, and a wrong guess at either is worse than a refusal. Sibling and never child, even though the session directory is the one path the sidecar holds outright: it carries a full-account credential, `harden_session_files` narrows everything in it to 0600, and `dir_holds_a_session` counts any file it does not recognise, so a staged photo in there would make a media-only directory read as a paired session and break `restore-session`'s newest-good rule. The derivation covers the unset case only, so on every **shipped** shape a configured `[whatsapp.baileys] session_dir` — an arm `default_session_dir` has and `default_media_dir` deliberately does not — cannot make the two disagree: both deployment literals and `_child_env` name the media directory explicitly. **Sibling-never-child is enforced in `deriveMediaDir` rather than asserted**, which is the review's correction and not the first draft: `path.dirname` alone does not give it, since `/a/b/.` has dirname `/a/b` and *is* `/a/b`, `/a/b/..` does the same one level up, and a session directory already named `whatsapp-media` derives to itself — all three were demonstrated by running the program. So the path is resolved first, a relative value and the filesystem root are refused outright, and a derived path equal to or inside the session directory is refused. An empty answer becomes a refusal in `main()` with its own reason, which is reachable by a hand-edited unit and by nothing else. The cron guard **reports and no longer refuses**: it could never fire for the next genuinely-mandatory variable, since a unit carrying `ISTOTA_BAILEYS_MEDIA_DIR` passes its grep whatever else it lacks, and its `elif` sat ahead of both the restart and the start arms — so on a stale-unit host a lockfile-touching commit hit the install arm that stops the unit for `npm ci` and was then declined a start, taking WhatsApp down until a full play on exactly the class of host this fix exists for. A guard against a loop that can no longer happen must not be able to cause an outage that can. Both deployment literals stay, and both are still compared by test against `media.default_media_dir` for that shape — but what they pin has changed: each is now also driven through the sidecar's own `deriveMediaDir` and required to equal it, so the literal is the fixed point that catches a drift in the derivation rather than the thing the program cannot start without. A drift is still a sidecar writing where the daemon never reads, with no error on either side; an absence is now nothing at all. `tests/test_whatsapp_deployment.py` also parses `ReadWritePaths=` out of the rendered unit and asserts the derived directory falls inside it, so reason 1 is verified rather than assumed and a later narrowing of either fails there.

**A second directory exists and is not this one.** Where the WebDAV copy fails, `stage_to_attachment` falls back to the local path that `transport/email/inbound.py` already falls back to — and puts it under `{temp_dir}/whatsapp-media/` rather than leaving it where it was staged, because this module's own sweep would delete it 600 seconds later while a task can sit well past that behind queue pressure, the retry ladder or a parked confirmation, and because the staging directory is inside the tmpfs `build_bwrap_cmd` masks, so a path there is unreadable from inside the task's own sandbox. `cleanup_old_temp_files` owns that one on its `retention_days` window. `doctor.whatsapp.media_staging` does not look at it, deliberately: it is a task attachment for as long as the task needs it, so a file standing in it is not the loss a standing orphan in the staging directory is.

**The standalone residual is stated rather than hidden.** `setup_wizard` puts `db_path`, `workspace_path` and `temp_dir` in one directory, where `_mask_dir` refuses outright — so there the staging directory sits inside `workspace_path` and a `user_resources` row naming the workspace root reaches it. It is the residual `default_pairing_relay_path` already carries, and milder: a staged file is one user's own photograph, lives for the few hundred milliseconds between the write and the inbox copy, and carries no credential.

`doctor.whatsapp.media_staging` reports the directory's mode, its owner, and how many staged files are past the orphan window with the age of the oldest. It is gated on `[whatsapp] enabled` alone and **not** on the provider, since both adapters stage and a Cloud deployment is the one fetching attacker-supplied bytes from inside Meta's own webhook request. An absent directory is `OK` rather than the WARN its session-directory sibling gives, because nothing creates this until the first image arrives. Survey only, never repair, and that rule bites harder here than on either neighbour: the repair available on this directory is `prune_media_dir`, which deletes, so a check that swept would clear the orphans it is reporting and the confirming run would say the directory was clean. It opens nothing, the contents being other people's photographs.

## The Cloud adapter

Everything in this section is reachable only under `provider = "whatsapp_cloud"`.

### The signed webhook

`GET`/`POST` at the fixed `/webhooks/whatsapp`. Three phases, and the order is the module's design: **authenticate then read** (bounds, content type, configured secret, HMAC over the exact raw bytes, decode — a 403 arriving as a 400 has told the caller the body was read); **normalize the whole batch before `BEGIN IMMEDIATE`**, so a malformed element cannot leave the first message applied behind a 200 nobody will retry; **one transaction for the batch**, with any database failure rolling back to a 503 Meta retries.

`client.verify_signature` adds three guards in front of PyWa's validator, and the load-bearing one is refusing an absent app secret: `webhook_updates_validator` takes the secret as a plain `str` and computes an HMAC under `b''`, so with none configured it does not fail to validate — it validates against a key every reader of this repository knows. The route refuses to serve besides.

An oversized body answers **413**, not the 400 the spec's design section wrote, matching the sibling SMS route through the same shared bounded-body reader. The GET handshake bounds `hub.challenge` to ASCII digits and refuses anything else with 400, which is stricter than "echo it as plain text" — the value is echoed verbatim from a route that answers before anything authenticates it.

The normalizer reads `pricing.billable` and never derives it, where PyWa's own `Pricing.from_dict` infers it from `type == "regular"` when the field is absent. A guess is what opens, or fails to open, the billing circuit. Messages are paired with contacts by sender id, never positionally: PyWa takes `contacts[0]` for every message in a value, which is fine while a value holds one of each and is a principal takeover when it does not.

### Cost controls

Two, and neither is called a guarantee. **The monthly cap is reserved by the claim, in the claim's own `BEGIN IMMEDIATE`** — the count and the row that increments it are one write transaction, so the last free slot cannot be read as free twice (measured: a deferred `BEGIN` turns the two-thread test red every run). `quota_month` is stamped on every row including blocked ones, but only a *claimed* row counts, so a `window_closed` or `budget_exhausted` row consumes nothing while a `failed` or `unknown` one consumes its slot and is never reclaimed.

**`monthly_service_attempt_limit` bounds service attempts and bounds template attempts by nothing.** Implemented as named. The consequence is inverted and worth knowing before enabling paid mode: with the cap spent, an open window is refused while a closed one still bills a template. Templates are reachable only under `allow_paid`, and `doctor.whatsapp.billing` reports the template count beside the service count so the volume is visible. A `monthly_template_attempt_limit` is the real fix and is a spec change.

**The circuit breaker is persistent and deployment-wide.** In `free_guard` the first authenticated status carrying `billable = true` sets `whatsapp_runtime.billing_blocked_at` and blocks every later send. The message that revealed the charge may already be billable; what the breaker buys is that the next one is not. Its alert is not `write_delivery_failure` — that one is about a message that reached nobody, this is a message that arrived and was charged for — and it goes to each admin as well as the recipient, since a deployment-wide block landing in one non-admin's inbox is not an operator notice. `template_available` re-checks `billing_policy == "allow_paid"` rather than resting on `load_config`'s refusal: one validator standing between a free-biased deployment and a paid message is one place for the rule to be edited out of.

`doctor.whatsapp.billing` SKIPs under a non-metered adapter. It reported a circuit state, a spend, a cap and a calendar month, none of which governs a send Baileys makes.

### What a switch away from Cloud costs

`whatsapp_webhooks_enabled(config)` is `enabled` plus the **active** provider being one with an HTTP callback at all (`WHATSAPP_WEBHOOK_PROVIDERS`), and the asymmetry with `sms_webhooks_enabled` is the point. SMS keeps a complete inactive provider's routes so a late delivery callback still authenticates across a switch; WhatsApp does not. Both handlers answer 404 on the same predicate the mount reads, so after a flip to Baileys, Meta's retries reach nothing and eventually stop. **The cost is stated rather than hidden: messages still in Meta's retry queue are lost, and an outstanding `sent_whatsapp` row keeps whatever state it had.** Where a Cloud message does reach `handle_whatsapp_batch` on a Baileys deployment — a receiver holding an older config, say — the provenance gate drops it as `inactive_provider` with no task.

It is deliberately **not** `WhatsAppProviderRegistry.callback_only_names()`, which does list every built adapter and is an answer about credentials a switched-away deployment still holds; reading it as the mount would restore the SMS rule this surface does not follow.

Four places read the same predicate — that function, `serve._maybe_mount_webhooks`, the role's `Resolve webhook receiver need`, and the compose profile — and three of them express the provider half. Both generators render `provider` when the operator names one, and the role's condition **refuses `baileys`** rather than requiring `whatsapp_cloud`: an unnamed provider is resolved from the Meta values by `_migrate_whatsapp_flat`, and reproducing that rule in Jinja would be a second copy going stale against `config.py` with nothing to say so. So the ambiguous case provisions a receiver nothing may call rather than risk dropping one a Cloud deployment needs. The fourth cannot express it at all — a compose profile is a static name — so it is split per adapter instead: `whatsapp` starts the receiver and `whatsapp-baileys` starts the sidecar. The residual is that nothing stops a stack selecting both, which costs a receiver whose handlers 404 and is inert.

**Two things nginx has to do that the application cannot, and one the proxy cannot do either.** The verify token arrives as a *query value* on the GET handshake and nginx decides what to log before the route runs, so `/webhooks/whatsapp` gets `access_log off` in both shipped configurations; a `log_format` naming `$uri` would keep the line but is only valid at http level, and both templates are one server block inside a generated `conf.d`. **Uvicorn's default access formatter renders `get_path_with_query_string(scope)`**, so silencing the front end alone leaves the token in the container log and the journal — measured against a live server, not read off the source. `serve.build_uvicorn_server` had always passed `access_log=False`, so the combined process was the only shape holding the property the docs claimed; both standalone receivers now run `--no-access-log` and a test pins all three. And the route-specific `client_max_body_size 512k` sits above istota's own 256 KiB cap so an oversized POST is answered by the application rather than by nginx with an HTML page Meta retries against.

## The Baileys adapter

A WhatsApp Web session, the mechanism mautrix-whatsapp and similar bridges use. It emulates a client WhatsApp does not sanction outside the Business API, so it carries account-ban risk, it breaks when the Web protocol changes until the library catches up, and the device unlinks after long inactivity. That trade is the operator's to make, which is why Cloud stays and why `docs/features/whatsapp.md` states it where an operator meets it.

### The sidecar and the wire

Baileys is TypeScript with no Python port, so the adapter is a Node subprocess: `docker/whatsapp-baileys/`, its own image rather than a stage in istota's. Decided on size — the library pulls in libsignal, protobufjs and a Node runtime, and `[whatsapp] enabled` is false by default, so folding it in charges a few hundred megabytes to every deployment for a surface most do not run.

**The daemon listens and the sidecar dials**, `devbox_proxy`'s arrangement: the listener's lifetime is the daemon's, so a sidecar restart reconnects to a socket that never went away, and the daemon creates the inode and therefore owns its mode. One JSON object per line over `AF_UNIX`, capped at 256 KiB on *both* ends, with a `hello` frame carrying a protocol version the bridge refuses on mismatch rather than reading an older shape's fields out of a newer frame. **There is no HMAC and none is faked** — the trust boundary is the socket itself, 0600 from the instant the inode exists rather than narrowed to it, with no network peer, which is why this adapter's `verify_signature` is `None` and nothing on this path calls it.

The wire format cannot be byte-pinned the way `docker/devbox/lib/` is, because the other end is Python. `tests/test_whatsapp_sidecar_vendoring.py` pins it behaviourally instead, on the precedent `.claude/rules/devbox.md` records for `istota_devbox_client.py`: it lists the directory's entries and requires each to be classified, pins the wire constants and every per-message field name by driving the sidecar's own object literals through the daemon's normalizers, and **executes** the sidecar's pure functions through `node`, which is possible because `loadBaileys` is lazy so the module imports with no dependency tree. The control-flow properties are source assertions in a class whose docstring says it catches a deletion and not a subtle change. A real connection needs a real WhatsApp account and is in no automated tier.

### The session directory is a full-account credential

Whoever holds it can send and read as the paired number, with no second factor and no revocation short of unlinking the device. It is 0700 whether it was just created or already existed — `mkdir(mode=…)` applies only to a directory the call creates, so the mode is asserted on an `O_NOFOLLOW` descriptor every time — and that same descriptor is what refuses one belonging to another uid, which a mode check alone cannot see: a directory already at 0700 skips the `fchmod` and with it the `EPERM` that would have been the only signal, so a planted one would be adopted in silence. The sidecar sets `umask 0o077` **on itself**, as its first statement, so its own files land 0600 — the daemon's spawn passes the same umask and reaches only the `istota serve` shape, while systemd's default `UMask` is 0022 and a compose service cannot express one at all, so both deployment shapes wrote every post-pairing key file 0644 until the program took it over; `harden_session_files` runs once at bridge start and narrows what is there rather than what a live session writes next, which is why `doctor` kept reporting the exposure back. The unit carries `UMask=0077` too, as the half an operator reading it can see. The sidecar also runs with **its stdio discarded** — inherited, a chatty Baileys logger writes JIDs and message bodies into the daemon's own journal, where this module's never-log rule does not reach, and `PIPE` with no reader blocks the child once the buffer fills. The sidecar writes `sidecar.log` inside the 0700 directory instead, at a level the operator can raise, taking a fixed message and a small bag of bounded labels rather than an arbitrary object.

The directory is bound into no sandbox at any path, and neither its contents nor a `qr` payload is ever logged, a QR being the pairing credential itself. The sidecar's environment is an **allowlist** (`PATH`, `HOME`, the locale pair, `TZ`, `NODE_ENV`, plus the socket and session paths) rather than `os.environ` minus a pattern list, so a credential name nobody thought to filter is excluded by construction.

### The bridge

**Nothing about the one-send contract changes, and the definite line is `writer.write`.** Above it — no sidecar connected, a session in a permanent fatal state, a request that would not encode — the message provably never entered the socket and the row settles `failed`; from `write` onwards the bytes may be in the kernel buffer whatever `drain` then says, so a timeout, a dropped link and an unreadable answer all settle `unknown`. The catch-all reads a mark set at the write rather than assuming a side of it: a fixed ambiguous answer spends `unknown` on a message that never left, and a fixed definite one is the same mistake waiting for a refactor to move a post-write failure onto that path. Both waits are bounded and for different reasons — the answer by `SEND_TIMEOUT_SECONDS`, and `drain()` by its own smaller bound, because it is held across the write lock and a sidecar that connects and stops reading never lets it return; unbounded, one such peer holds the lock for ever and every later send queues behind it, leaving rows claimed and unsettled and the parked-status gate open deployment-wide. The writer is adopted only after the `hello` passes, so no `send` can be handed to a peer whose version is unknown. A send is matched to its answer by a request id rather than by order, since one long-lived connection multiplexes.

**The read loop dispatches and never works**, which is a deadlock rather than a tidiness rule: handling an inbound message can end in a reply, and a reply awaits a `send_result` only that loop can deliver. So inbound events go to a bounded queue drained by **one** worker — serial, because order within a conversation is meaning — and a full queue *drops* loudly rather than blocking the reader, since back-pressure there is the deadlock. The worker calls `handle_whatsapp_batch(..., provider="baileys")`, the same entry point Meta's signed webhook calls and inside the same `BEGIN IMMEDIATE`, so dedup, identity, the claim row and task creation are common code. The whole `with db.get_db(...)` block is one `asyncio.to_thread` callable: a connection must not hop threads, and that block opens and commits the transaction.

A malformed line is logged, counted and dropped — a message this side cannot read is not one it can attribute, and attributing one to a guessed sender is a principal takeover rather than a lost message. A *database* failure is retried in place and in order, because the webhook answers 503 and lets Meta redeliver and nothing redelivers over a socket. **The retry is bounded and then the event is dropped with a count**, which is a deviation from the spec's "parked and retried rather than dropping" and is stated as one: the worker is serial, so an unbounded retry starves every message behind it and the queue's own overflow then drops the *newer* ones, trading a loud loss of the message that cannot be written for a silent loss of the ones that could. `failed_events` is what `doctor` reads.

**A permanent `fatal` ends the respawn loop rather than slowing it.** A logged-out session comes back only from a re-pair, so respawning burns a process every few seconds and changes nothing; the running sidecar is stopped rather than left re-reporting the same fatal, and sends refuse *definitely* until it resolves. Only a `ready` clears the latch, so a transient fatal arriving afterwards cannot reopen the send gate against a dead session. `sidecar_argv=()` is a first-class mode rather than a test affordance: on both deployment shapes the sidecar runs as a unit or a compose service of its own, so the bridge listens and supervises nothing.

**An unlinked device is said out loud on both surfaces.** The bridge calls its owner back once per *transition* into a permanent fatal — not once per reconnect, since a logged-out sidecar reports the same fatal each time it comes back — and `baileys_runtime` writes an admin-addressed row and pushes it off the WhatsApp surface, the way the billing circuit's alert does. The sidecar's own words never reach the body; the reason goes through `task_alert._slug`. `doctor.whatsapp.baileys_bridge` is the other half and is what still answers a week later, with the re-pair remedy on its FAIL arm. `whatsapp.baileys_session` reports the credential's permissions and **surveys rather than repairs** — a diagnostic that narrowed a wide file was a second writer of a full-account credential's mode, attributed to no process, and its WARN self-cleared so the hourly sweep could observe an exposure exactly once. The bridge still narrows on its own start path.

**The bridge starts from the scheduler's boot, not from `serve.py`, and that is a deviation from the spec's affected-files list.** `serve.py` names the webhook-mount decision point, which runs in the web process — and on the Ansible shape the web app and the scheduler are separate units, so a sidecar started there would run in the one process that never sends. The loop matters more than the process: every send reaches `deliver_whatsapp` through `run_coro` on the persistent runtime loop, and the bridge's asyncio primitives bind to whichever loop first awaits them, so a bridge started anywhere else is awaited across loops from inside the claim-to-settle region. `transport/whatsapp/baileys_runtime.py` starts it beside the Talk signaling supervisor; `istota serve` inherits one through its own scheduler thread. `whatsapp.baileys_bridge` therefore answers only in a process holding a bridge and SKIPs elsewhere, so `istota doctor` from a shell cannot settle it — the authoritative surfaces are the boot run, the hourly sweep, `!check` and the admin Health pane. Its `library_version` arm runs *before* that skip, since it compares a config string against a file.

### Pairing

**`istota whatsapp pair` has two modes and the live socket selects between them rather than refusing.** With no bridge listening it is unchanged: it starts a sidecar of its own, renders the QR and waits for `ready`, which is the first-ever pair on a developer checkout and how a compose deployment's session directory is seeded. With a bridge listening it **attaches** — it writes the durable pairing request the daemon's own poll services and follows the relay file, drawing each code, spawning nothing and touching no session directory. Same request a web admin writes, so a window either of them opens is visible to the other. The probe is still a connect to the socket rather than a test for the inode, since an inode outliving its process is ordinary.

The reason behind the old refusal is unchanged and is what the two modes are arranged around: two Baileys clients on one auth state corrupt it, so the session directory is a single-writer resource and a running bridge is already its writer. Attach mode is safe because it is not a second writer — the bridge performs the destructive half on evidence the CLI does not have. And the refusal's other job, permanent-fatal recovery on the spawned shape, is now `resume()`'s: stop the daemon, pair, start it again still works and is no longer the only route.

**The selector reaches one of the two shapes, and the gap is the same one the advisory-lock residual names.** The daemon owns the listener, so with the daemon stopped the socket is gone and the probe is silent — while a sidecar run as its own systemd unit or compose service is still running and still holding the directory. Own-sidecar mode therefore names the sidecar as well as the daemon before it spawns anything, as do the doctor and alert remedies.

**`--reset` is the half of that recovery which was missing, and the state it covers is the one nothing could get out of** (ISSUE-496). A `logged_out` session leaves `creds.json` naming a device WhatsApp has unlinked, and `useMultiFileAuthState` reads it as a registered account and attempts a login rather than emitting a QR — so the one thing that could resolve the state is the one thing that cannot happen while the file is there. Under systemd that is `Restart=always` at `RestartSec=30` for as long as it takes somebody to notice, and `pair` met the same wall, printing `Remove <session dir> and try again` rather than performing it. What an operator was left with was composing an `rm -rf` against a full-account credential directory, as root, on a host where WhatsApp was already down.

**The move is the easy part and the guards are the change**, and the primitive is `BaileysBridge.reset_session` rather than a few lines in the CLI. That placement is the issue's own later ruling: a CLI that moves a directory it can only *believe* is unheld makes the live-socket refusal load-bearing and arranges the whole flow around eviction, where the bridge can move one whose writer it supervised and watched exit. Four refusals stand in front of the waits, each raising `SessionResetRefused` with the directory untouched — no permanent fatal (a live session is never reset), no `sidecar_argv` (the bridge supervises nothing on the Ansible and compose shapes, so it can establish nothing about the unit's own sidecar and `Restart=always` means it is coming back whatever was observed), the bridge stopping, and a second call.

**Then the child goes before the directory does, and three more refusals stand between the waits and the rename.** The permanent fatal has already ended the supervisor loop, which reaps on its way out, so `reset_session` awaits that task rather than racing it, shielded so a timeout does not cancel a reap in flight. **A supervisor that outlived the wait is a refusal, and the process check cannot stand in for it** — `_await_child_or_fatal` sets `self._process = None` itself on the exit arm, so an abandoned loop sleeping out its backoff presents no process at all. That arm is taken whenever the child's exit and the fatal complete in one iteration of the event loop, since `exited.done()` is tested first, and the loop then sleeps its backoff *before* re-reading the latch — longer than the settle wait from the fifth consecutive fast crash. Falling through would clear the latch and create a second supervisor while the first slept; it wakes, reads the cleared latch, and spawns a sidecar into the directory the new one is already pairing into. Two Baileys clients on one auth state, arranged by the very method meant to prevent it; both reviewers found it independently.

**Neither wait is bounded from the inside, and the bounds are this caller's rather than the callees'.** `_reap_process`'s last phase is `kill()` and then an unbounded `wait()`, which is right for `stop()` and would hang `istota whatsapp pair --reset` for ever here — so the refusal it is supposed to produce would be unreachable rather than merely slow. And both gates are **re-read after the waits**, since everything from there to the rename is synchronous: a `ready` dispatched during them clears the latch, and renaming on the strength of the stale answer moves the directory of a session that has just come back. The link is closed explicitly after all of it, because `_on_connect` refuses a second connection while a writer is live and a stale one would have the respawned sidecar counted as a rejected connection with nothing saying why.

**A failure after the rename is its own outcome, not a refusal.** `ensure_session_dir` raises rather than degrading, by its own docstring, and by then the credential has moved — so an unguarded raise leaves the reset half-applied while the caller reports that the session could not be moved aside, which is the opposite of what happened. The directory is renamed back and the original raised, which returns the bridge to the state every refusal leaves it in; where even the restore fails, `SessionResetIncomplete` carries `moved_to` so the CLI can print the one thing that has to reach a human, which is the path the only copy of their credential is now at. Its own exception type because a refusal and this ask opposite things of whoever catches them: one means nothing happened and a retry is safe.

**One reset per bridge, structurally.** ISSUE-497 established that a sidecar restart drops and rebuilds a link WhatsApp watches for churn, and that the cost is invisible from our side because the credential is on disk rather than in the process. A second fatal after a reset is a *fresh* directory that also failed, which another move cannot fix, and retrying it is that defect one level up — so the bound is `_reset_used` on the primitive rather than a convention in whoever calls it. The CLI tracks its own flag beside it and gives the operator a fresh scan deadline after the move, since the one that just expired was spent waiting for a session that could never open.

**Timestamped sibling, never a fixed name and never a delete.** A sibling because the move has to be one `rename(2)` inside one directory — copy-then-delete has a window where the credential exists twice and a crash where it exists nowhere — and timestamped so the second logout of a deployment's life does not overwrite the record of the first. The stamp is one second wide, so the destination name is settled by probing with `os.path.lexists` rather than by trusting the clock: what stands there is the only copy of what was in the session directory. **The probe is the whole of that guarantee**, since there is no `RENAME_NOREPLACE` behind it — a directory created at the chosen name in the window is still taken, though only an empty one, since a non-empty one fails `ENOTEMPTY`. Bounded at `_RESET_NAME_ATTEMPTS`, matching `session/session_log.py`'s solution to the identical problem, because an unbounded walk is a hang wherever a stat answers wrongly. `tests/test_whatsapp_baileys_bridge.py::TestTheSessionReset` freezes the clock for the collision case, and it had to — written against the real one it passed with the probing loop deleted, because the second that elapsed between arranging the collision and performing the reset gave the two different stamps.

**`istota whatsapp restore-session` is the inverse, and it is what a host already stranded runs** (ISSUE-504). `restore_session_archive` parks whatever stands at the live name using the same `archive_destination` the reset does, then renames the archive into place; a failure between the two puts the park back, and one that cannot even do that raises `SessionResetIncomplete` carrying the path the only copy is now at. The archive is put through `ensure_session_dir` **before** anything moves — `--date` takes any stamped sibling and the operator docs say these exist, so a hand-copied 0755 one would otherwise become the live directory at 0755; validating it first gives the same guarantee as validating the live name afterwards, since `rename(2)` carries the inode, and costs no second unwind. A live directory holding a session is parked and nothing is deleted, so a restore aimed at the wrong stamp is undone by running the command again against the parked one; one holding only `sidecar.log` — which is every ordinary recovery — is removed instead, because parking it files a permanent stamped archive `doctor` reports for ever beside the real credentials with nothing to tell them apart. It also clears the pairing row, since leaving a non-terminal one open has the next tick adopt it, arm a window over the session just restored and latch the send gate against a session that works. "Newest" means the newest archive `dir_holds_a_session` answers True for, which is `db_restore`'s newest-*good* rule applied literally — a failed re-pair is exactly when an archive of a log-only directory is lying around beside a real one. `--date` names a stamp and `--list` prints them with that same predicate's answer beside each, so a listing cannot offer a stamp the restore would then refuse. The refusals are `reset_session`'s: a bridge answering the socket is a live writer, so that is a refusal naming the daemon and the sidecar. **The sidecar half is printed on every path rather than only in the prompt**, because the probe sees the daemon alone and the daemon is stopped by the time anybody runs this — so a unit-run sidecar is exactly the writer nothing here can detect, and the ordinary recovery path prompts for nothing and would otherwise warn about nothing. Displacing a live session additionally collects the typed unlink phrase — `_whatsapp_confirm_unlink` now takes its prose from the caller, since two verbs displace a working session and each has to say what it is about to do while the challenge itself stays one string. The ordinary recovery runs against the empty directory a failed re-pair left, where there is nothing to displace and no prompt at all.

**Every refusal in that class is asserted with a `match=`.** There are seven raise sites now and the gates are ordered, so a bare `pytest.raises(SessionResetRefused)` passes whenever *any* of them fires — which is what a reordering would silently rely on. The supervisor-survivor case also nulls `_process` before it runs: leaving the real process in place makes the liveness check fire instead, and the case then passes without the guard it exists for. Its control turned that from a pass into `DID NOT RAISE`.

Three remedies that named a command which provably does nothing in this state now name the flag: `doctor`'s `whatsapp.baileys_bridge` FAIL arm, the unlink alert body in `baileys_runtime`, and the supervisor's own `not_respawning` log lines. The `whatsapp.baileys_session` permission remedies keep `chmod` as the fix, because they fire on a different condition and a reset is gated on a permanent fatal and would refuse them — what they no longer say is "re-pair with `istota whatsapp pair`", since on a host with a bridge running that command attaches and the unforced request is refused. They name Admin, Connections and `--reset` as the re-pair routes instead.

**`--reset` reaches the destructive half in either mode, and what it asks for differs because what it costs differs.** In own-sidecar mode `reset_session` acts only on a session that has reported a permanent fault, so there is nothing working to disconnect and the flag is the whole confirmation. In attach mode it writes `pairing_force`, which is what lets the daemon disconnect a session that *is* working — so it collects the same typed phrase the web's destructive control does, read through `sys.stdin.isatty()` with no bypass flag and with the phrase itself asserted against the Svelte source rather than restated. A bare `pair` needs no confirmation and is the short route once the session has reported itself unlinked.

The QR is drawn in-process by `segno`, at error level `l` and two rows per character, which puts a 217-byte payload in 31 lines by 61 columns. It shelled out to `qrencode` and printed the raw payload where that package was absent, which let the host's package list decide whether a pairing could be completed — on the host where an operator is least able to install something, at the moment they need it. A pure-Python renderer with no dependencies of its own was the cheaper answer, and it is also the stronger handling of the credential: the payload now reaches no argv, no pipe and no other process, and on a successful draw it is not printed at all. The fallback that prints it survives only for a draw that fails, because this runs on the bridge's read loop through a callback where a raise is swallowed with no `exc_info`.

The daemon finds the Node program through `[whatsapp.baileys] sidecar_command` and nothing else. An in-tree fallback existed and was removed: the Ansible shape installs from a checkout, so `docker/whatsapp-baileys/index.js` is present and `node` is usually on PATH, and the daemon would have spawned a second sidecar beside the systemd unit's — the corruption the pair refusal exists to prevent, arranged by a convenience. The fallback lives in `in_tree_sidecar_argv`, whose one caller is `pair`, where a developer's checkout is the case it serves; it also requires `node_modules/@whiskeysockets/baileys` beside the program, so a checkout with no `npm ci` is not named as an argv at all.

### Re-pairing through the running bridge

This is the daemon-driven recycle the residuals used to call designed and unbuilt, and the operator-facing half of it is under "Re-pairing" in `docs/features/whatsapp.md`. An admin writes a request from Admin, Connections; the scheduler's poll hands it to the bridge; the bridge sends the connected sidecar a `shutdown` frame, moves the session directory aside after the drop that frame caused, and opens a TTL-bounded window in which `_handle_qr` relays the code instead of discarding it. Nothing spawns a second sidecar and nothing needs a privilege the daemon lacks.

**Two channels, because the trigger and the payload have opposite storage requirements.** The request and its state go in `whatsapp_runtime`, the existing singleton row: transactional, durable across a scheduler restart, and already open in both processes — the `task_steers` arrangement, where the web writes a row and the process owning the work polls it. The code goes in a 0600 file and **never** in the database, because `db_backup` snapshots the framework database into a dated directory on the Nextcloud mount, so a code live at snapshot time would be captured in a durable replicated backup of a full-account credential. `default_pairing_relay_path` puts it beside `db_path`, except on the standalone install where `db_path.parent`, `workspace_path` and the state root are one directory — there it resolves to the per-user temp root, and Stage 4's route-side check refuses a window outright where the resolved path would still sit inside a sandbox-bound root, since the answer needs `build_bwrap_cmd`'s bind list and a `transport/whatsapp` module cannot import the executor without a cycle.

**The frame is the evidence, and that is the whole design rather than a step in it.** There is no way to ask whether something holds the session directory — that is what an advisory lock would buy and this deployment has none — so the sequence *causes* the answer instead of observing one. A passive flow that waited for the logged-out loop's own restart gap was written first and is wrong: `connected == False` is a fact about the daemon's Unix socket, and `index.js` calls `session.start()` without waiting for the link while retrying the link on its own timer, so a freshly started sidecar reaches `useMultiFileAuthState` and binds `saveCreds` to that path while `connected` still reads false. Renaming there leaves the survivor writing the old dead credential into the freshly created directory: no code, an orphaned archive, and a window that waits out its TTL. ISSUE-496 shipped the same conclusion as `reset_session`'s `not self._sidecar_argv` refusal, which a waiting flow would have had to argue past.

**One restart, spent at the write.** A sidecar slow past `SIDECAR_STOP_TIMEOUT` still exits, so an abort there has already cost a reconnect — the outcome message names the spent restart rather than reporting a clean no-op, and the directory is untouched, because moving it out from under a live writer is the corruption this area exists to prevent. The one abort that really costs nothing is `sidecar_absent`: no sidecar connected inside `SIDECAR_RETURN_TIMEOUT`, no frame sent, nothing moved. That timeout is `restart_interval_seconds + 30.0` and is additive rather than a multiple because only one term scales — a whole restart interval can elapse before boot begins, and the boot itself is the same few seconds whatever the interval.

**One mechanism, two confirmations.** `force` selects no mechanism: the frame is sent either way and it means "I accept disconnecting a session that is working", so a bridge with no latched permanent fault is refused without it. The web route requires `confirm_disconnect` on top of it, and neither flag is ever defaulted server-side — with `force` false and the session live the route answers 409 rather than quietly setting it, because a server-side fallback is how a confirmed action becomes an unconfirmed one. The carrier is the seventh column, `pairing_force`: the route collects the confirmation and the *poll* is what calls `repair_session`, so with nothing on the row the poll could only ever call it unforced and the whole forced half would be dead on the web surface. Deriving `force` from the bridge's live state was considered and refused — a request written while a fatal was latched and serviced after the session recovered would disconnect a working link.

**`_move_session_aside` is `reset_session`'s core, extracted, and both callers reach it through their own evidence.** That sequence — `_reset_destination`, the `os.rename`, `ensure_session_dir` plus `harden_session_files`, and the rollback that restores the archive or raises `SessionResetIncomplete` carrying `moved_to` — went through two reviewers and ten negative controls, and a second copy of a credential-moving path is the most expensive kind of duplication. `reset_session`'s evidence is awaiting and reaping the child it supervised; `repair_session`'s is the drop its frame caused. **On the spawned shape `repair_session` delegates to `reset_session` rather than using the frame**, because `_supervise` returns its respawn delay to `RESPAWN_BASE_SECONDS` for any child that ran a while, so the sidecar just asked to exit is back about a second later — into the directory the rename is about to move, with the drop to observe, schedule and act on inside that second. The cost is that the forced case is unavailable there, which is the developer checkout `istota whatsapp pair` already owns, and it is said in the message rather than left as a silent refusal. `_reset_used` stays once-per-bridge for the CLI and `RESET_COOLDOWN` is the daemon's instrument for the same rule: a once-per-bridge flag on a bridge that lives as long as the daemon would mean one web re-pair per daemon restart on a surface whose whole purpose is recovery.

**Clearing the fatal latch has a consequence in the outbound ledger, and the arm that pays for it is wider than the window on both sides.** `_send`'s only session gate was `fatal_is_permanent`, so with the latch cleared and no session paired a send reaches `writer.write`, the write mark is set, and the answer either never comes or comes back as a link failure — both of which settle **`unknown`**, the one state an operator can never resolve, on a `logical_key` nothing deletes. Gating on the open window alone leaves two gaps that produce exactly that row: under `force` the latch is absent *by construction* before the window opens, so the wait for a sidecar plus the stop timeout is ungated; and an unscanned window closes at its TTL leaving the latch clear against a directory the sequence has just emptied, so every later send is ungated for the life of the process. The gate is therefore three-state — `_repairing`, or a window is open, or `_session_unpaired` — and a `ready` is what clears the third. Its test asserts the `sent_whatsapp` row settles `failed`, not that a refusal happened: the row is the thing that cannot be repaired afterwards.

**The latch dies with its process and the unpaired directory does not, which is the fourth producer and the reason it is no longer called `_unpaired_by_repair`** (ISSUE-506). Three producers set it because *this* process emptied the directory or inherited a window from one that did — `repair_session`, `reset_session`, `adopt_pairing_window`. The fourth is `start()`: a window that expired with nobody scanning leaves the directory unpaired, adoption cannot reach the row because it is terminal by then, and a restart hands the new bridge a clear latch against it — so every send for the life of the *deployment* settles `unknown`, which is where a per-process fix stops. A host that has never paired is the same state with no re-pair behind it, and **the sidecar's own `not_connected` guard does not answer it**: `open_()` assigns `this.sock` from `makeWASocket` and the connection opens later, so the guard passes and every path past it is ambiguous — `sendMessage` throwing goes through `sendFailureReason` with `definite: false`, a reply with no message id is `internal` and non-definite, and a hang is ended by the daemon at `send_timeout` with the write mark already set. All three settle `unknown`, so one gate covers both states.

**What `start()` reads is `session_is_registered`, not `dir_holds_a_session`, and mistaking the two would have left the fix inert on the shape it is for.** That predicate answers "is there anything here worth archiving", counts any file it does not recognise, and fails toward True — all correct for its four callers, every one of which is about not destroying a credential. In exactly the two states above the sidecar is a unit of its own and is *up*, looping on a fresh code every twenty seconds against this directory with `saveCreds` bound to `creds.update`, so a Baileys release is free to leave noise keys, prekeys or an unregistered `creds.json` behind — each a file, none a session anybody can send from. `session_is_registered` reads the registration field out of `creds.json` instead and fails toward **not registered**, because here the answers are not symmetric: a wrong True means no refusal, no `ready` ever, and permanent `unknown` rows, while a wrong False refuses sends until the first `ready`, which after a daemon restart is the next link the sidecar dials. That asymmetry is also what licenses reading a field out of a library this repository does not ship — a future Baileys that stops writing both fields costs seconds of refusal on one boot, and one that writes either early costs the pre-ISSUE-506 behaviour rather than something worse. A `ready` clears this producer exactly as it clears the other three, so a first-ever pairing sends the moment the code lands.

**Scope, because this producer is much wider than the other three.** They each follow a deliberate destructive act, so the span is bounded by a re-pair somebody is performing; this one fires on every boot of an unpaired host and is bounded only by when the operator scans. `failed` is in `_NO_RESEND`, so every WhatsApp-routed message produced in that window is permanently unsendable under its own `logical_key` — not worse than the `unknown` it replaces, since both are permanent and this one at least alerts and is legible, but a real widening of how often the refusal fires. Having `is_whatsapp_configured` report False while the latch is set, so routing falls to another surface rather than burning the key, is the obvious follow-on and is a design change rather than part of this fix. `BridgeStatus.session_unpaired` is what makes the state visible: `_send` answers `REASON_SESSION_FATAL` for this *and* for a logged-out session, so the reason string cannot tell them apart, and `doctor.whatsapp.baileys_bridge`'s not-ready arm reads the field to say which of the two an operator has — one wants a pairing, the other wants patience, and offering both remedies is how somebody archives a working credential.

Its three send tests assert the `sent_whatsapp` row rather than the refusal, and each has a control: removing the `start()` read turns the two empty-directory cases red, and putting `dir_holds_a_session` back turns the pre-pair-auth-state case red on its own. The fixture reorder is part of the fix rather than fallout: two `running`/`bridge` fixtures wrote `creds.json` *after* `start()`, so every send case in both files was a bridge in one state answering as though it were in another.

**The poll is every tick, inline, and claims in SQL.** One `IntervalGate` beside `avatar-import` with `fixed_interval=0` and **none** of `background`, `overlap_expected` or `one_shot`. Every tick because `_tick_interval_gates` runs once per outer loop and `_dispatch_sleep` then consumes a whole `poll_interval`, so any non-zero interval is serviced at that cadence regardless; `0` also bypasses the clock, which matters because `now` is wall-clock and a recovery surface must not be switchable off by a backwards NTP step. Not `background`, because `_spawn_background_check` creates a thread per spawn and an every-tick background gate is some 17,000 threads a day to perform one indexed read that finds nothing. Not `one_shot`, which would have `istota run` poll in a process holding no bridge. The gate reads and claims the row to `servicing` in one `BEGIN IMMEDIATE`, then hands off with `async_runtime.spawn_task` — the bridge's asyncio primitives are bound to the runtime loop, so a task on that loop is the native shape and a worker thread calling `run_coro` would be a thread that exists only to wait. `spawn` raises `RuntimeError` when the runtime is stopping, so the poll reverts the claim rather than stranding the row.

**Durable expiry is what stops a scheduler restart bricking pairing for good, and its predicate has two arms that must not be collapsed.** The window and its watchdog live in bridge memory while the request lives in the row, so a restart mid-window leaves the new bridge with no window (QRs discarded again), nothing that will ever close the row, a relay file whose `window_id` still matches, and `request_whatsapp_pairing` guarded on there being no open window — every later request 409s for ever. The **deadline** arm applies to every non-terminal state including `requested` and `servicing`: past `pairing_expires_at`, stamp `expired`. The **orphan** arm applies only to the states that imply a window was opened, and only in a process holding the bridge. The obvious single-sentence form ("any non-terminal row with no in-memory window behind it") kills the request it is meant to service, because `request_whatsapp_pairing` writes `requested` and the window is not opened until the last step — such a row satisfies "no window behind it" by construction, so a poll running that predicate first would stamp it `expired` and then find nothing pending, inside one invocation and with no race involved. The two closures are different outcomes and must not share a message: a deadline is `expired` (nobody scanned, which the confirmation covered), an orphan is `failed` naming the process restart and the archived path, because the credential is already moved aside and somebody has to be told which of two directories to trust. On the reference deployment the two-minute update cron restarts the units on every commit, so a 300s window meets one fairly often; a re-pair from that state re-opens a window against the already-emptied directory rather than archiving a second time, which `dir_holds_a_session` decides on auth state rather than on emptiness — the sidecar writes `sidecar.log` and `logout-backoff.json` into that directory on every boot, so an emptiness test answers True for a directory holding only logs.

**Since ISSUE-504 the orphan arm is the fallback rather than the routine answer, and the routine answer is adoption.** Closing the row was right about the row and wrong about the credential, which by then is already at a timestamped sibling — so a restart during a window took a working deployment to unpaired, on any commit landing in those 300 seconds, and the recovery was an operator composing `mv` against a full-account credential as root. What makes the fix cheap is that the sidecar is its own unit with no `PartOf=` on the scheduler: it survives, sits against the emptied directory and keeps offering a fresh QR every twenty seconds. Nothing about the pairing was lost — only this daemon's record that somebody was waiting for a code — so the new bridge reconstructs the window from the row instead.

`adopt_pairing_window` is that reconstruction and it **writes nothing**: the row already carries the window id, the deadline, the requester and, in `pairing_message`, the archive path that says the re-pair was destructive. It converts the durable wall-clock deadline to the loop's monotonic one rather than restating it, so the watchdog fires on the row's own instant and the bound the issue requires is kept rather than extended. `opened_at` is taken as *now*, because its one reader is the `sidecar_absent` demotion, which asks whether a code has reached **this** process. It shares `_arm_pairing_window` with `open_pairing_window`, so the install-before-the-first-await rule and the re-read of both gates afterwards have one implementation. **`qr_seq` is seeded from the row and that is a correctness fix rather than bookkeeping**: `_dispatch`'s `ready` branch reads it to tell a real pairing from a link blip re-announcing a working session, so a window adopted at zero closes the exact sequence adoption exists for — a code relayed, the user scans, the scheduler dies before the `ready` — as `failed`, writes that to the durable row and alerts every admin to re-pair, a remedy which archives the credential just paired. The evidence is the row's own `awaiting_scan`, and the test is that state rather than "anything but `awaiting_sidecar`", since `sidecar_absent` is a demotion of a window that never got a code either. Four refusals, all meaning nothing was touched: a window already open, the bridge stopping, a deadline already passed, and — its own, and a send-ledger guard rather than tidiness — a session that is already `ready`, since a `ready` clears `_session_unpaired` and nothing re-sends one until the link reconnects, so arming a window over an open session would set that latch with nothing left to lift it and refuse every later send for the life of the process. Three of those four converge through an arm that already exists within a tick or two; the `ready` one converges through nothing until the deadline arm fires, so until then each tick spawns a coroutine that refuses on sight — bounded by the row's TTL, one scheduled no-op per poll, and left that way because the alternative is recording a row whose session came up on its own as a failure.

It does set the latch on every path it takes, because that is state the dead process held and this one does not: without it `_send` reaches `writer.write` against the emptied directory and the ledger settles `unknown` on a UNIQUE `logical_key` nothing deletes. The window arm of the send gate covers the span while the window is installed; the latch covers the tail after it expires.

**The arm order in `_expire_stale_pairing` is load-bearing and adoption sits sixth.** After the missing-id arm, the deadline arm (which is what still bounds everything), the no-bridge-or-not-a-window-state arm, the matching-live-window arm, and the `last_pairing_outcome` arm — that last one specifically, because a `paired` close this process performed presents as `pairing_window is None` exactly as a dead process does, and adopting ahead of it would re-arm a window over a session that had just come up. Seventh is the close, now reached in two cases only: a row whose deadline this cannot parse, where a window could not be bounded and an armed relay would hold a published credential until the process stopped, and a `spawn_task` the runtime refused, which means the daemon is stopping. No retry bookkeeping is added, because every other refusal converges through an arm that already exists within a tick or two. The decision is returned out of the `BEGIN IMMEDIATE` and acted on after it, the way the claim already is, since `adopt_pairing_window` is a coroutine on the runtime loop while the transaction runs on the dispatch thread; the refused-spawn close then takes its own transaction rather than holding a write lock across a spawn.

Recovery latency is one scheduler tick to adopt plus up to the sidecar's twenty-second QR cadence to a visible code. That is the number saying the operator's scan survives the restart, rather than only the row.

**The web half puts no payload in a JSON body and no code in a JS string.** Five routes plus the connections index, all admin-gated, the mutating ones behind the origin check. The SSE stream carries `state`, `qr_seq`, `expires_at` and `message`, polls at 1 Hz off the loop, and sleeps through `web_shutdown.sleep_unless_shutdown` like the three generators already there. `qr.svg` renders the code server-side with `segno` under `Cache-Control: no-store`, and a `seq` mismatch is a **cache-buster rather than a refusal** — the client can legitimately be one rotation behind and a 409 there would blank the code for somebody mid-scan, so the sequence actually drawn is reported in `X-Pairing-Qr-Seq`; the parameter is typed `str | None` so `?seq=abc` is not a 422 reaching the same refusal by another status code. `pairing_enabled = false` 404s those five and **the index deliberately stays 200**, since the card has to be able to say the session is working and that re-pairing is switched off here; it gates the routes and nothing else, because the CLI's attach mode writes the same row and gating the poll would disable `istota whatsapp pair` on the shape whose operator is already at a terminal. The card offers the one-click control where the fault is latched *and* where the link is unreadable from this process, which on the split Ansible deployment is every page load — safe because the unforced start carries no confirmation for the bridge to honour, so the refusal comes back as `session_live` on the row and the card renders it.

**Doctor has three arms on this and each answers a question the others cannot.** `whatsapp.baileys_bridge` reports an open window ahead of its `connected` and `ready` checks, because mid-window a disconnected unpaired sidecar is what the sequence asked for and those remedies are wrong for it, and `sidecar_absent` is a WARN naming the unit and the update log. `whatsapp.pairing_relay` reports the relay file's mode, owner and age — it `lstat`s and never opens, and a file older than one configured window is residue rather than a code, which is the shape `stop()` can leave behind when its cleanup task is cancelled mid-unlink. And `whatsapp.baileys_session` walks the archives as well as the live directory: coverage would otherwise have dropped from "the one credential on disk" to "one of N" the moment this flow shipped. `session_archives` is the enumerator and lives in this module beside the writer that names them, sharing `ARCHIVE_STAMP_FORMAT` with `_reset_destination`, so a diagnostic cannot end up looking for a shape nothing writes; the walk itself is `du.first_level_dirs`' rather than a fourth copy of it. Each archive is asked the same three questions the live directory is — its own mode, its owner, and whether anything in it is wider than 0600 — since a remedy naming more than the check verified is the gap that made this pass necessary one level up. Survey only, never `harden`: on a directory nothing is writing there is no start path that would narrow it again, and a check that repairs is a check that cannot report.

## Config, credentials and deployment

Structural validity fails the load (`whatsapp_structural_config_errors`); **credential presence does not** (`whatsapp_credential_errors`, reported by doctor, refused at use). Failing the load on a missing secret repeats ISSUE-058: under `istota_use_environment_file` the Ansible role renders the three Cloud credentials empty on purpose and delivers them through `secrets.env`, which the role's own `command:`/`script:` tasks cannot read. Both halves are per provider: only the active adapter's structural arm runs, and the credential report names the active adapter's own fields — which matters because the unconditional Cloud form refused every Baileys send for want of a token that adapter does not use, and doctor's partial-credential arm FAILs, so a stale `secrets.env` entry would have alerted every admin about an adapter nothing runs. `graph_api_version` accepts `v25` and `v25.0`, since PyWa 4.4 pins Graph `25.0` and a `v<integer>` rule would refuse every real version string. `business_phone_number` stays top-level and is adapter-independent: required when enabled under Cloud, because a Meta account is configured by hand, and format-checked-if-set under Baileys, because a paired session carries its own number. It still earns its place there — it is what `identity.address_for_binding` renders into a JID for a user enrolled by number who has not yet written in, the only way to message somebody first on this adapter.

**Meta's settings live in `[whatsapp.cloud]`, and the pre-adapter flat spelling still loads.** `_migrate_whatsapp_flat` runs as a pre-walk step in `config.py` rather than as a `config_mapper` hook, and the spec's affected-files line naming `config_mapper.py` is the imprecise half. Two reasons, and the second is mechanical: `config_mapper` states that anything migrating a legacy key stays hand-written in `istota.config`, and `apply_section` consults a hook *before* it recurses into a nested dataclass, so a hook keyed on `whatsapp` would replace the walk for that whole section and lose the unknown-key report and every nested coercion. A `Hook` also returns one field's value, and this migration has to set a *sibling* key — `provider` — decided from the values, which that signature cannot express. Naming it `normalize_legacy_document` is what lets the loader and the two generator drift guards share one answer.

**The provider signal is read off the resolved `cloud` table, not off where the keys were written.** A block carrying a `waba_id`, a `phone_number_id` or one of the three credentials selects `whatsapp_cloud` when no `provider` key is present; an empty one takes the `baileys` default. Reading the signal off the flat keys alone was a defect produced by the deprecation note itself: following "move them under `[whatsapp.cloud]`" removed the last flat key, dropped the signal, and converted a Cloud deployment into a Baileys one in silence — `whatsapp_webhooks_enabled` False, no config errors, doctor OK. It cannot misfire the other way, because a deployment wanting Baileys with a populated Cloud block writes `provider` explicitly and an explicit value is never overridden.

The transport registers on `config.whatsapp.enabled` alone, not "enabled and locally valid": structural validity is already raised at load and gating on credentials would repeat ISSUE-058 again. Local validity is enforced per send by the outbound gate (recording `unconfigured`) and per user by `is_whatsapp_configured`, which applies the gates still true in an hour — transport, binding, opt-out, and under a metered adapter the billing circuit and the cap — and deliberately **not** the service window, which reopens on the user's next message and whose absence would make the heartbeat skip an alert outright rather than record `window_closed` off-surface.

Both generators write the nested shape and render `provider` **only when the operator names one**, which is the whole compatibility story: absent is not either default, so a value written at either one breaks the other case. Writing `baileys` by default takes Meta's callback away from every existing Cloud deployment at the upgrade, silently; writing `whatsapp_cloud` by default makes a fresh install ignore the product default. An empty value is refused outright on both shapes, because an unrecognised provider fails `load_config` in every istota process whether or not the block is enabled — the scheduler, the web app, the webhook receiver and every host-side skill CLI spawn alike.

**The sidecar runs as a unit of its own on Ansible and a service of its own on compose, and the daemon spawns nothing by default.** `[whatsapp.baileys] sidecar_command` stays empty on both, which is the `sidecar_argv=()` shape: systemd restarts a unit that exited on a logged-out session where the in-process supervisor deliberately does not, so a re-pair recovers without touching the scheduler. The role refuses a unit and a `sidecar_command` together — that pairing is the two-clients corruption arranged by configuration, and neither process can detect the other. The unit and the compose service both pass `ISTOTA_BAILEYS_SOCKET` and `ISTOTA_BAILEYS_SESSION_DIR`; the sidecar exits 2 with no log destination when either is absent, and both literals are compared by test against the product's own `default_session_dir` / `default_socket_path` for that shape, since a drift there is a sidecar dialling a socket nobody is listening on with no error on either side.

**Three things about the unit are decisions rather than defaults.** `Wants=`, never `Requires=`, so a scheduler restart does not drop the paired session. `RestartSec={{ istota_whatsapp_baileys_restart_sec }}`, 30 by default, because the steady state of a de-paired session is start-log-exit until somebody scans a code — and **the same variable renders `restart_interval_seconds` in `config.toml`**, which is the only way the unit's real cadence and the daemon's declaration of it cannot drift, and the only place it writes is a file inside the 0700 credential directory — an *unrotated* one, which is the half of that sentence to keep in view, since ISSUE-498's wait made a de-paired sidecar a long-lived writer to it rather than a process that exited in 500ms. And `ReadWritePaths` is narrowed to the data directory rather than `istota_home` as the sibling units have it — those run istota's own code, this one runs a third-party dependency tree while holding a full WhatsApp account. The compose side cannot be narrowed without a second volume.

**That interval is not the bound on how often a de-paired session logs in, and treating it as one is what ISSUE-498 was.** Each of those cycles is a real websocket and a real authentication attempt against a number WhatsApp has already unlinked once — about 2,400 a day on the unit, converging to roughly 1,400 under Docker's own capped backoff, indefinitely on both. `MAX_START_FAILURES` does not reach it: that gates `reportStartFailure`, which covers a session that could not be *constructed*, and the `loggedOut` branch exits upstream of the counter without touching it. The spawned shape was the only one already right, because `BaileysBridge._supervise` ends its loop on a permanent fatal — and it is the shape that is off by default. This is the same vendor model the file already records for delivery ACKs: anomalous client behaviour carries ban risk, and a permanent 401 retry loop against an account that has just been unlinked is anomalous client behaviour.

**The bound is in the program, and it has to be — neither supervisor can tell an unlinked device from a crash**, and both must keep restarting promptly for the second, so a longer `RestartSec` buys the fix by slowing down every other failure. The sidecar waits before exiting instead, on a ladder indexed by the length of the run: no wait on the first logout, then 30s, 5m, 15m, 30m, an hour, clamped. Those are *sleeps* rather than effective intervals, and the supervisor's own number is deliberately not written down in `index.js` — a copy of `RestartSec` there would be right for one shipped shape and wrong for the other. A floor of 500ms is folded into the same function, which is the pre-existing delay that lets the `fatal` frame leave the socket before the process goes, so the first logout of a run keeps the same 500ms wait it always had.

**The run is a file because every cycle is a different process**, so nothing in memory survives one: `logout-backoff.json` beside `sidecar.log`, 0600, holding a count and two timestamps. It is written *before* the wait, since a `systemctl restart` partway through a half-hour one would otherwise reset the ladder to its first rung and make the loop unbounded again through the operator's own intervention. A `connection === 'open'` deletes it, which is the existing `startFailures = 0` rule one level out. **Every arm degrades toward the short wait, never the long one**, because a wait this machinery lengthens by mistake is a working session held down, which is the opposite of what it is for: an unparseable count and a negative or non-numeric one resolve to run 1, and so does a missing file, which is the healthy first logout of a run.

**That argument is about the read, and where the state cannot reach disk at all it inverts** (ISSUE-501). Then the short wait is not a cautious guess but a permanent one: every cycle reads nothing, computes `0 + 1` and waits the 500ms frame flush, so the ladder never advances and the deployment is back to roughly 2,880 logins a day against an account WhatsApp has already unlinked — the condition ISSUE-498 exists to bound, reintroduced by the failure modes most likely to be permanent. `recordLogout` marks such a run `unrecorded` and `logoutWaitMs` floors it at `LOGOUT_UNKNOWN_RUN`, the ladder's third rung, taking that to about 290 a day. Guessing is licensed here and nowhere else because the guess cannot hold a working session down: a session that opens deletes the file, and a re-pair ends the wait through the credential watch within one poll — including the `--reset` remedy, which moves the whole directory and so changes the stamp even where the directory itself is what cannot be written.

**The mark is a union of two conditions and each covers a shape the other leaves unbounded**, which is where this departs from the shape ISSUE-501 suggested. That entry proposed discriminating the read errno, `ENOENT` being genuinely nought runs and `EACCES`/`EISDIR`/`EIO` being unknowable, and acting where the read was unknowable *and* the write then failed. Measured against the entry's own repro list, that conjunction covers one of three: a read-only directory with no file reads a perfectly ordinary `ENOENT` and is pinned at the floor anyway because the *write* is what cannot land, and an unreadable file in a writable directory is rewritten to `count: 1` on every cycle for ever while satisfying only the read half. So the mark is set when the state did not reach disk **or** the read failed for anything but `ENOENT`. A read that succeeds and fails to *parse* is not unknown — the bytes were reachable, so the file is one this program can replace, and the next cycle reads the count it just wrote.

**A failed write does not shorten the rung it read, and that is why the floor is a `Math.max` rather than a branch.** `recordLogout` is read-modify-write and returns the incremented run whether or not the write lands, so five recorded logouts and an unwritable file still waits the five-logout rung — the run really is five long, and collapsing to 500ms there would make the ladder vanish exactly when the disk filled, while collapsing to the fallback would cut an hour to five minutes at the run length where the wait matters most. What the failure costs is the *next* process's increment.

**And the condition is reported rather than only acted on.** Its only other signal is the `warn` line `recordLogout` writes, and `log()` appends to `sidecar.log` *inside* the directory that cannot be written, so on the most likely trigger it goes nowhere at all. The sidecar therefore sends a **second** `fatal` carrying `run_unrecorded`, which the bridge latches on `BridgeStatus.fatal_run_unrecorded` and `doctor.whatsapp.baileys_bridge` names on its existing unlink arm. A second frame rather than a field on the first, because the first one's position is load-bearing: it has to leave before any filesystem work, which on a hung mount blocks indefinitely, and the daemon must not learn its WhatsApp is down only once that returns. The healthy path still sends exactly one frame, and the once-per-outage alert has already fired on it, so nobody is paged twice. `announceReady` carries the marker on the re-announced verdict too, since the daemon's latch is in memory and a scheduler restarting inside the wait would otherwise re-learn the logout and not that the backoff behind it is running on a guess. `first_at` is carried rather than restamped so a later reader can say how long the session has been unlinked; nothing reads it yet, and `doctor` reporting a duration is the obvious second reader.

**And the wait watches `creds.json` rather than only counting down**, which is what keeps a re-pair prompt. Nothing in the re-pair flow restarts this unit — `istota whatsapp pair` spawns a sidecar of its own against the same directory — so a plain sleep would leave a session re-paired at minute two of an hour-long wait sitting out the remaining fifty-eight. A changed stamp (mtime and size, never the contents) is exactly the evidence that the next login is not the doomed one, so the wait ends there. Removal counts as a change too, since moving the directory aside is the documented remedy and is ISSUE-496's `--reset` primitive; that is why an absent credential and an unconfigured session directory are distinct strings rather than one constant.

**The baseline for that comparison is taken at the first poll rather than when the wait is scheduled, and getting this wrong is the whole defect wearing a label.** `saveCreds` is an async write, so one started by the login that has just failed can land *after* `scheduleLogoutExit` is called — and against a baseline captured before it lands, our own write reads as a re-pair. The wait would then end at the first poll on every rung of every cycle, capping the effective interval at the supervisor's own while `logout-backoff.json`'s count kept climbing and looked like a working backoff: `.claude/rules/testbed.md`'s "success indistinguishable from a no-op", in the one place nothing executes. Seeding later costs a blind window of one `CREDENTIAL_POLL_MS`, and the cost is sharper than "noticed an interval later": a credential replaced before the first tick is adopted *as* the baseline, so it is never noticed and the rung runs to its full length. Rungs 1 and 2 have no watch at all, since `min(delayMs, poll)` makes their single tick also their exit. Both reviewers established that by executing the loop rather than reading it, which is also why the control below asserts the *full* elapsed wait rather than an early exit one interval late. Two guards stand in front of the same hazard, since neither reaches the other's case: `creds.update` is now bound behind the `mine()` guard its three siblings always had, which stops a *new* write, and the socket is nulled in the logged-out branch, which is what makes `mine()` false. `tests/test_whatsapp_sidecar_vendoring.py::TestTheLoggedOutBackoff` drives the loop rather than reading it — a top-level function taking its own exit callback and poll interval, which is what makes that possible at all — and `test_a_write_landing_before_the_first_poll_does_not_end_the_wait` is the control: seeding at schedule time turns it red and leaves its two neighbours green.

**Three smaller properties the wait needs and did not have, each a consequence of the process now living up to an hour where it lived 500ms.** The logged-out branch is **one-shot**, because `if (this.stopping) return;` sits below it and `mine()` still passes for the socket that just closed — a repeated close carrying the same status would re-enter, and one duplicate event would cost a rung permanently on the evidence of a single unlink. The **socket is dropped**, not merely left closed, because `send`'s `if (!this.sock)` guard is the only thing that answers a send with a definite `not_connected`; left in place, a send during the wait reaches a dead socket and settles the ledger `unknown`, the one state an operator cannot resolve. And the **daemon link keeps reconnecting** through the wait, gated on `loggedOut` rather than on `stopping` so a deliberate shutdown still does not, with `announceReady` re-sending the fatal instead of a `ready`: the bridge's permanent-fatal latch is in memory and only that frame sets it, so a scheduler restarting inside the wait would otherwise leave `doctor` and the admin alert saying "no sidecar connected" rather than "logged out, re-pair" for the rest of the rung. On the spawned shape the bridge now asks for a graceful shutdown before reaping, since `_reap_process` would otherwise spend its whole `SHUTDOWN_GRACE_SECONDS` and then SIGTERM a process that answers the frame in milliseconds.

**Both update paths carry the sidecar, and that is not bookkeeping.** The unit runs a Node program out of the checkout, so it holds stale code the way the Python units do, and on the reference host the two-minute auto-update cron *is* the deploy path — ISSUE-428's class on a second non-Python artifact. Its dependencies are the worse half: a cron-delivered lockfile bump leaves `node_modules` matching the old one, the running process survives on modules it has already required, and the failure surfaces at the next unrelated restart, days after the commit that caused it. Both paths diff the sidecar's directory between the deployed marker and the target and reinstall when the lockfile moved or `node_modules` is absent; the install stops the unit first and takes the role's update lock, because `npm ci` deletes `node_modules` before installing and `Restart=always` turns any crash in that window into an exit loop against a half-populated tree. **Neither restarts unconditionally, and the two paths reach the same guarantee from opposite directions** (ISSUE-497). The cron restarts only when that diff is non-empty and otherwise `start`s, because this unit holds a WhatsApp Web session and a restart drops and rebuilds a link WhatsApp watches for churn — free from our side, since the credential is on disk rather than in the process, which is what made the original unconditional, and not free from theirs. The play restarts from the checkout task, which lists this unit beside every other long-running service running out of the tree: its own handler fires only from the dependency install and the unit template, both deployment changes rather than source ones, so an `index.js`-only commit reached it through neither and left the unit on the copy it loaded at start — the ISSUE-294 shape the checkout task's comment already names, on a service added after it was written. That gap was invisible while the cron restarted on every tick, since the next tick of any kind healed it; gating the cron is what exposed it, and the two had to be fixed together.

Docker, Ansible and `istota serve` all run one webhook receiver for location, SMS and WhatsApp together. Setup for both adapters, the operating modes and the operational commands are in `docs/features/whatsapp.md`.

## Residuals

Recorded rather than closed, and each is a decision somebody may want to revisit.

- **A session directory the sidecar can never write bounds the backoff at one rung rather than climbing it.** ISSUE-501 took this from "switched off" to a fixed five-minute floor, which is a bound rather than a cure: a run that cannot be recorded cannot advance, so such a deployment sits on `LOGOUT_UNKNOWN_RUN` for as long as the condition lasts instead of reaching the hourly rung an ordinary outage reaches. Roughly 290 logins a day rather than 2,880, and rather than the ~24 the top rung would give. Closing it properly means the run surviving a process that exits by some route other than that file, which is the thing the file exists for; an in-memory count helps only a supervisor that does not restart the process, which is neither shipped shape. The condition is now reported — `doctor.whatsapp.baileys_bridge` names it on the unlink arm, off the `run_unrecorded` frame — so it is no longer a state whose only signal is a warning written into the directory that cannot be written.
- **The wait widens the window in which two Baileys clients can hold one auth state.** The pairing residual below is unchanged in kind, but not in exposure: a de-paired sidecar used to be a process alive for a couple of seconds in every thirty, and is now alive essentially continuously. What bounds the risk is that the waiting process has already dropped its socket and its `creds.update` handler is behind a `mine()` guard, so there is nothing left in it that writes the **auth state**. It does still write the directory: `link.onClose` now reconnects through the wait, so a daemon that is down — the documented re-pair state — costs two `sidecar.log` lines every two seconds, roughly 300 KB across an hour-long rung, appended to a file nothing rotates. That is the bound to state, since it shares a filesystem with the state file and so walks toward the never-writable residual above. The proper close is still the advisory lock the next residual names, which is cheaper to justify now that the process has a documented long-lived state.
- **`writeFileSync` on the state file follows a symlink, and its `mode` applies only to a file it creates.** Recorded as a decision rather than an oversight: the target is inside the 0700 directory and is trust-identical to the `sidecar.log` append beside it, which has the same shape and predates it. Tighten both together or neither, so the two do not drift.
- **The session directory has no advisory lock.** `istota whatsapp pair` detects a running *bridge*, by connecting to the daemon's socket, and not a sidecar somebody else's systemd unit is running — so on the external-unit shape a pair can start a second Baileys client against one session directory, which is the auth-state corruption every other guard here exists to prevent. Every remedy names both processes and the role refuses the one configuration that arranges two clients by inventory alone. The real guard is a lock inside the session directory taken by whichever process opens it, which needs a lock on the Node side. **`--reset` inherits this exactly and widens nothing**: it sits behind the same refusal and moves a directory only after the sidecar *it* supervised has exited, so on the external-unit shape the undetected second client is the one that was already there. **`repair_session` inherits it in a sharper form**, and the frame does not close it: the drop is evidence about the *adopted* peer, so a second sidecar whose connection `_on_connect` rejected is a live Baileys client this process sees only as a counter, and the rename would proceed under it. Gating on `rejected_connections` was considered and refused — a stray connect attempt would then refuse a legitimate re-pair — and `doctor`'s refused-connection WARN is what reports the condition instead, carried into the pairing arm's own detail and remedy for the span in which that arm shadows it, which is exactly the span in which the rename happens.
- **The daemon-driven recycle is built, and three pieces of it are not.** "Re-pairing through the running bridge" above is the flow the constraints recorded on ISSUE-496 described, including the one about the relay being a 0600 file rather than `istota_kv`. What did not arrive with it: a cooperative check inside `repair_session`, so between the poll's claim and the outcome there is no way to stop a sequence in flight and the cancel refuses a `servicing` row honestly rather than pretending; a reclaim for a `servicing` row whose claimant is demonstrably gone, which needs a pid or a runtime start stamp on the row and is meanwhile covered by the slower deadline arm; and the recycle becoming a casual "restart sidecar" control or growing a retry loop, which remains the thing not to build.
- **A third `istota whatsapp pair` reads the second one's socket as a daemon's and writes a request nothing services.** Own-sidecar mode holds the bridge socket while it runs, so a `pair` started beside it takes the live-socket branch, enters attach mode and writes a durable `requested` row — and the process holding that socket runs no poll, so nothing picks it up. Bounded twice: the deadline arm clears such a row on the first tick of any scheduler, and the 30-second message now names the other explanation ("no bridge has picked this up") rather than only the scheduler being down. A CLI cancel verb was considered and declined, because it needs a second copy of `web_app._cancel_pairing_request`'s semantics — which refuse a `servicing` row so the archive path still reaches the operator — and the shape it would guard is one terminal running two pairings at once.
- **An archive nothing can list reads as a host that has never re-paired.** `session_archives` walks the state root through `du.first_level_dirs`, so `x` without `r` on that directory returns nothing while `whatsapp.baileys_session`'s live arms answer normally off a plain `lstat` — the archive pass then reports no archives rather than reporting that it could not look. Distinguishing the two needs a second return channel for a corner where the directory is the daemon's own, which is why it is stated instead. The pass is also a fixed cost on every run of a check that fires at boot, hourly, behind `!check` and on every admin Health pane render: one listing of the state root plus one per archive, growing with the re-pair count because nothing deletes an archive by design.
- **`qr_seq` can lead the relay file by a moment, and that is why a test waits on the file.** `_handle_qr` stamps `window.state` and bumps `qr_seq` synchronously on the read loop while the relay write is queued to a worker thread, so the status — and therefore the SSE frame built from it — can announce a sequence before the file holds that payload. Benign on the surface: the client's `qr.svg?seq=N` fetch finds the previous code or none, and the next one-second poll resolves it. The consequence is for whoever writes the next test here, since the two are not atomic and waiting on the state is what made one flaky.
- **The bridge's graceful `shutdown` frame is unreachable on the daemon's own shutdown path.** `AsyncRuntime._shutdown` cancels every pending task before it runs the cleanup hooks, so the connection handler's `finally` has already dropped the writer by the time `stop()` asks. A spawned sidecar is SIGTERM'd instead, which works, and the external shape is correctly not told at all. `istota whatsapp pair` is the one caller that reaches the frame.
- **Nothing reaps a stale claim**, on either push surface. A send cancelled at shutdown can leave `sent_whatsapp` `pending` with a claim and no id, which is unresolvable and holds the parked-status gate open deployment-wide; the window is real, since the shutdown budget is about five seconds against a 30s SQLite busy timeout. The reaper is owed by SMS and WhatsApp together.
- **A failing `npm ci` leaves the sidecar stopped for as long as it keeps failing.** The cron's install arm stops the unit and then runs `npm ci` with no `|| true` under `set -euo pipefail`, so a persistent failure — an unreachable registry, a corrupt lockfile — aborts the script before either restart arm and before `record_deployed`. The marker never advances, so the next tick recomputes the same non-empty diff, stops an already-stopped unit and dies at the same line: WhatsApp is down indefinitely with the reason only in the update log. Pre-existing rather than introduced by ISSUE-497 — the old unconditional restart sat at the end and was equally unreachable — and left alone there because reviving the unit means either moving the revival above the failure surface or making the install non-fatal, and `set -e` in a root deploy script is not a thing to loosen as a side effect of a different fix. Two smaller relatives of the same shape: a failure *after* the restart arm holds the marker back too, so a sidecar-touching commit that trips it restarts the live session on every tick until somebody intervenes; and `systemctl start` mid-`RestartSec` backoff is unmeasured — under `Type=simple` a start job succeeds as soon as exec succeeds, so it should be a no-op, but nothing in any tier executes this unit, and a non-zero return there would kill the script under `set -e`.
- **A scheduler restart during a pairing window no longer strands the credential, and the residuals it leaves are different ones.** Adoption covers the window; what it does not cover is a deadline the row carries in a form this cannot parse, and a daemon stopping between the decision and the spawn — both of which fall to the close, and both of which now name `restore-session` in the message they write. Nothing sweeps an archive, by design, so a deployment that re-paired several times before this landed holds several credentials and `whatsapp.baileys_session` reports each.
- **A refused adoption leaves the previous process's relay file until the deadline arm fires.** `_spawn_pairing_adopt` reports whether the *spawn* was scheduled, not what the coroutine then decided, so the poll returns and nothing republishes or unlinks; `_close_orphaned_pairing` does not sweep it either, since the row is non-terminal and in a window state. Bounded by the row's TTL, 300s by default, on a 0600 file whose code WhatsApp has already rotated several times over — so it is a stale credential rather than a live one. Closing it means the poll reading the coroutine's result, which means awaiting it on the dispatch thread, which is the stall the hand-off exists to avoid.
- **An unpaired host burns a `logical_key` per message until somebody scans.** The `start()` producer above refuses sends definitely, and `failed` is terminal in `_NO_RESEND`, so a task result or admin alert produced during a pre-pairing window that may last days is permanently unsendable under its own key. Better than the `unknown` it replaced — legible, alerted, and named by `doctor` — but the routing question behind it is open: `is_whatsapp_configured` still reports True while the latch is set, so nothing falls back to another surface. Closing it means the latch reaching that predicate, which changes where traffic goes rather than how a send settles.
- **`session_is_registered` reads a field out of a library this repository does not ship**, so which spelling says "paired" is an assumption rather than a verified fact — nothing in any tier connects to WhatsApp, and `node_modules` is not in the tree. Both misreadings are bounded (see the paragraph above), and the boundary it does pin — an unregistered `creds.json` and a stray key file both reading as unpaired — is a test with its own control. What would settle the spelling is one `ls` of a live session directory mid-pairing, or a grep of an installed Baileys 7 for the `creds.update` emissions reachable before `pair-success`.
- **`_status.ready` is weaker than "the session is up", so `adopt_pairing_window`'s fourth refusal has a gap.** `_handle_fatal` clears `ready` on a *transient* fatal without dropping the daemon link, and the sidecar re-announces only on a link reconnect — so once cleared that way, no further `ready` arrives while the link stands. Adoption in that window passes the guard, sets `_session_unpaired`, and nothing lifts it: every send then settles `failed` on a `UNIQUE logical_key` nothing deletes. The preconditions are compound (a stale window-state row still open at the moment of a transient fatal) and the shape is unmeasured; it is recorded rather than fixed because the fix means changing what lifts the latch, and "a transient fatal clears `ready` and sends carry on" is a decision already shipped on the live path.
- **A *first* pairing is not reachable from inside the compose stack, and a re-pair now is.** `istota whatsapp pair` in own-sidecar mode spawns a sidecar and the istota image ships neither the program nor its dependencies, so a first session is still paired from a checkout with node and the directory moved into the volume. Attach mode is the listen-only mode this residual asked for and it closes the other half: the frame works wherever a sidecar is connected and depends on no supervisor cadence, so a compose deployment with a paired session re-pairs from Admin, Connections or from `istota whatsapp pair` inside the container.
- **The pin is Baileys `7.0.0-rc14`, a prerelease, and that is a decision rather than drift.** WhatsApp addresses an ordinary one-to-one chat by LID, and 6.7.x has no PN-to-LID mapping at all: a send addressed to the phone JID establishes a session in the phone-number namespace that a LID-migrated recipient cannot use, so every reply arrives as "Waiting for this message" and every retry is fresh in the wrong namespace. 7.x is where that is implemented — `signalRepository.lidMapping`, and a device resolution that calls `storeLIDPNMappings` then `assertSessions(lids, true)` "to align identity addressing" — and the work has no 6.x backport. npm's own tags say the rest: `latest` is the 7.0.0 prerelease and `legacy` is 6.7.24. The tree audits clean, so the GHSA-qvv5-jq5g-4cgg spoofing advisory that forced the 6.7.18 to 6.7.24 bump is covered too, and 7.x additionally stops sending delivery ACKs, which the maintainers removed because WhatsApp was banning accounts for them.
- **The version string is pinned exactly, and a range is refused for a sharper reason than usual.** `6.17.16` was published on 2025-03-04, *before* 6.7.18, and outranks every real 6.7.x by semver — so `^6` resolves to a build seventeen months older than the pin, and the `legacy` tag exists to name 6.7.24 past it. The guard accepts a prerelease suffix and still refuses a range.
- **Baileys 7 is ESM-only and the sidecar stays CommonJS.** `loadBaileys` is an `await import(...)` rather than a `require`, which keeps the two properties converting the file to ESM would have cost: `module.exports` is what lets the default suite load the program with **no `node_modules` present** and execute its pure functions, and the specifier still resolves at session open rather than at module load. It also needs Node 20, whose `preinstall` script enforces it — prod is on 22 and the image is `node:20-trixie-slim`.
- **Nothing in any tier connects to WhatsApp**, so the version is verified by build, by `npm audit`, and by the API names `index.js` uses resolving through a real dynamic import — not by a session.
- **The sidecar image is in no test tier.** It was built and exercised by hand when it landed, and the `deploy` tier converges with WhatsApp off, so the systemd unit is executed by nothing either. Every assertion about both is a parse.
- **`istota_update_only` and `istota_web_only` together still start the sidecar unguarded.** ISSUE-494 put a `stat` + `assert` on `/usr/bin/node` at the top of the Baileys block, ahead of every task that deploys or starts the unit — including the update-only restart loop, which names this unit and runs much later. Both new tasks carry `not istota_web_only`, and that loop carries only `istota_update_only and (item.enabled | bool)`, so setting both flags skips the guard and still reaches the start. Not fixed there because the loop's gate is wrong for four units rather than for this one — it restarts the scheduler under `istota_web_only` too, which contradicts what web-only means — so correcting it is its own change with its own blast radius. `tests/test_ansible_whatsapp_baileys_node.py` asserts the ordering and says in its docstring that this combination is outside what it claims.
- **A hand-written unit that moves the session directory and omits `ISTOTA_BAILEYS_MEDIA_DIR` stages where the daemon never reads.** The derivation answers `dirname(session)/whatsapp-media` while the daemon joins the staged name onto its own `_media_dir`, which is `{db_path.parent}/whatsapp-media` and has no override — so every inbound image takes `MEDIA_NOT_PLACED` and the files accumulate in a directory `prune_media_dir` never sweeps. Not silent: one `whatsapp.baileys.media_unreadable` warning per image. Unreachable before ISSUE-508 only because the sidecar exited 2 instead, so it is a residual the fix creates rather than one it leaves; it is bounded by there being no shipped shape that produces it, and closing it means the sidecar learning `db_path`, which it deliberately does not know.
- **A mid-migration flip loses Meta's outstanding traffic**, as "What a switch away from Cloud costs" states above.
- **A LID contact whose phone number WhatsApp withholds cannot use this surface at all.** WhatsApp addresses an ordinary one-to-one chat by LID, a durable per-contact id carrying no number, and the daemon's whole Baileys identity story is the phone JID — `normalize_jid` accepts `@s.whatsapp.net` alone, `jid_number` takes the E.164 out of it for the bootstrap comparison, and `address_for_binding` renders that same spelling back as a destination. The sidecar's `chatAddress` bridges the two by forwarding the `senderPn` the server stamps beside the LID, so the ordinary case resolves; a message arriving with a LID and no usable `senderPn` is dropped with a named reason and can neither enroll nor resolve. Closing it means making the LID a first-class identity column with its own bootstrap story, which is what the `@lid` refusal in `JID_USER_DOMAIN`'s docstring is holding the place for.
- **A retry arriving after a sidecar restart cannot be served.** Signal encryption is per device and per session, and a message the far side cannot decrypt is answered with a retry receipt — for which Baileys delegates the one thing only the caller has, the body, to `getMessage`, whose default is `async () => undefined`. The sidecar passed no hook at all, so `sendMessagesAgain` logged "message not available", relayed nothing, and the recipient sat on "Waiting for this message" for ever. `rememberSent` / `recallSent` back the hook with the last 256 sent bodies, **in memory and nowhere else** — the session directory holds a full-account credential rather than a transcript, and a plaintext message store beside it is a worse trade than a missable retry. So a restart empties the cache and a retry for anything sent before it goes unanswered. Much rarer under Baileys 7, which addresses the right session first time and so seldom provokes a retry at all, but the cache is what answers one when it comes. `makeCacheableSignalKeyStore` wraps the key store for the neighbouring race, where a key written and immediately re-read off disk misses and provokes a PreKey handshake that was not needed.
- **A message WhatsApp never manages to redeliver is lost silently.** A linked device that cannot decrypt a stanza is handed a `CIPHERTEXT` stub with no content; Baileys emits it through `messages.upsert` and asks WhatsApp to resend the *same message id*. The sidecar withholds the stub rather than forwarding it, because forwarding claims that id in `processed_whatsapp` and every retry behind it — the ones carrying the decrypted text — is then refused as a duplicate (measured: one claim at `unsupported_type`, three duplicates, nothing delivered). The cost of withholding is that a stanza whose retries all fail leaves nothing but a `inbound withheld until it decrypts` line in `sidecar.log`. That is the safe direction, but it is still a loss with no surface. Closing it means the daemon distinguishing "not yet arrived" from "arrived and unreadable" in the claim itself, rather than the sidecar deciding by omission.
- **The reply direction is exercised by no test.** `sent_whatsapp` had no rows at all when the inbound break was found, so `address_for_binding` -> phone JID -> Baileys `sendMessage` had never run on this adapter. It has now been driven by hand on the reference deployment under Baileys 7 and it works first-attempt: send to `read` in about a second, with no retry request behind it, where 6.7.x took 3m37s and 7m13s on the two sends before the upgrade and often never arrived at all. The daemon still addresses the phone JID; the translation to the LID session is Baileys'. That is a handful of observations, not coverage — nothing in any tier can reach it without a real account.
- **The staging ceiling has no enforcement point on the Baileys path.** `MEDIA_STAGING_CEILING_BYTES` is consulted by the Cloud route, which decides whether to fetch; the daemon structurally cannot refuse a fetch the sidecar has already made, so on Baileys the ceiling governs nothing and the sidecar deliberately does not prune. A sidecar-side ceiling was rejected rather than overlooked: it is a second delete-and-measure authority over a directory of user photographs, written in a language the daemon's tests cannot reach, and two such authorities racing each other over the same files is worse than the bound it buys. What bounds that path instead is the per-file cap times the inbound queue depth, since the daemon unlinks every staged file it consumes *and* every one it drops. The spec's `## Who owns which bound` is what governs here, over its own Behaviour row.
- **A batch that does not commit is re-staged on the provider's retry, and each attempt leaves its own inbox copy.** Staging runs in front of the transaction, so `precheck`'s claimed-id read is rolled back with the batch it could not close, and the inbox name carries `staged_name`'s random half — so the copies accumulate in the sender's own inbox rather than colliding. Reachable by a deterministic in-transaction failure and by a fetch and upload that outlast the provider's callback tolerance. It affects **both adapters** for one reason, which is why it is not a Cloud patch: the fix is a stable per-message inbox name, and that is a Stage 1 rule whose random half exists to keep two media parts of one message apart. Neither case is silent — the copies land in the sender's own inbox and `_report_stranded_media` names the stranded one — and `stage_cloud_media`'s docstring carries it in full beside `precheck`'s.
- **The consume tail now exists in both adapters**, at `baileys_bridge.stage_inbound_media` step 2 and `providers/whatsapp_cloud._stage_one`: sniff, then `stage_to_attachment`, with the three outcomes each adapter answers in its own words. Extraction into `media.py` is a stated follow-up rather than debt found later. What is duplicated is the arrangement and not the rules — the suffix re-derivation, the inbox naming, never-raise and discard-at-the-decision each still live once.
- **PyWa logs a Graph error body and the media URL at DEBUG on the Cloud fetch path.** `pywa.api.GraphAPIAsync._request` logs `res.text` and `stream_media_bytes` logs the URL, which is the one thing every rule on this path keeps out of a log line: a media URL carries the recipient's identifiers and the token's path segment. Not fixed, because it is a dependency's logger below the default level, and silencing it means either a `logging_setup` entry for `pywa.api` or a wrapper around a library call. Worth the `logging_setup` line if anybody ever runs this surface at DEBUG.
- **The Cloud staging step resolves an identity ahead of `handle_whatsapp_batch`'s inactive-provider gate**, as the Baileys one does. Narrower here, since `whatsapp_webhooks_enabled` already gates the route on the active provider being Cloud, so what reaches it is not an inactive adapter's traffic in the first place.
- **The staging ceiling is asked with the per-file cap rather than with the declared size**, so it refuses a fetch whenever the directory could not hold a full-size file rather than whenever it could not hold this one. Conservative in the safe direction and visible only on a directory already near its ceiling, which is a directory whose sweep is already failing.
- **The Cloud download's whole-transfer deadline is a bound against a hang, not a budget.** `_MEDIA_FETCH_DEADLINE_SECONDS` (60s) exists because `httpx.Timeout` is per operation, so a trickling peer could otherwise hold open the request Meta is waiting on, and `max_bytes` cannot close it — a peer that sends nothing never reaches a byte cap. What a callback may actually cost is Meta's tolerance, which Meta publishes no number for; the spec's one open question is answered by design rather than by measurement, and what would force the background-staging fallback is an operator observing redelivered image callbacks or the receiver's own latency on image batches.
- **Whether a HEIC ever reaches an `imageMessage` at all is unsettled, and it is the one manual check the work leaves behind.** WhatsApp transcodes an ordinary photo send, so an `imageMessage` — and a Cloud `image` — is usually JPEG on the wire, and the path that preserves the original file is *send as document*, which is out of scope. So the shipped HEIC support may be real, tested and unreachable through the message types admitted here. It was built anyway: it costs one brand allowlist, it is the difference between a silent refusal and a working photograph on any client or WhatsApp version that does not transcode, and finding out later would otherwise mean revisiting the sniff. The check is cheap — send one iPhone photograph to the reference deployment's number and read the sidecar's `messageShape` line beside the sniffed type in the staging log. What the generated test fixture pins is that the allowlist matches what `pillow-heif` in this tree produces, not what a device produces; nobody here has inspected a photograph off a phone. If a device file lands outside the eight brands the sniff answers `None` and the sender gets the unsupported reply, which is the safe direction and a visible one.
- **`doctor.whatsapp.media_staging`'s census is unbounded in entry count**, and it runs at boot, on the hourly sweep, behind `!check` and on every admin Health pane render: one `iterdir` plus one `lstat` per entry, with no cap. The steady state is an empty directory and `staging_bytes` and `prune_media_dir` use the same unbounded idiom, so it is consistent with the module rather than a new risk — but the Baileys residual above is exactly the shape that would fill the directory, since nothing prunes it there while the daemon is down. Capping the loop and saying "N or more" is the fix if it is ever wanted.
- **Nothing in any tier connects to WhatsApp, so the inbound media path is covered the way the send path is and no better.** The sidecar's download is pinned by parse and by its pure functions executed through `node`; the Cloud fetch is pinned against a stubbed transport; the common half is driven directly. None of it is exercised against a real account by anything automated. The Baileys leg has been driven by hand on the reference deployment; the Cloud leg has not.
