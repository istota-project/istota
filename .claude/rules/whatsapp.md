# WhatsApp

One business phone number through Meta's hosted Cloud API, direct rather than through a BSP. A user-routable push surface, text only, and outside the room model: no `messages` row, no room membership, no Talk or web view. Context comes from the stable `whatsapp-<user hash>` conversation token and task history, and that token is a pure function of `user_id` so it survives every number, username and send-id change. A bare `whatsapp` destination resolves the user's current binding immediately before the send; `whatsapp:<anything>` is refused, so routing cannot become an arbitrary-contact send API. `all` and `both` are unchanged, deliberately — a metered external surface is selected explicitly or not at all.

## Identity is the BSUID, not the number

The binding lives in `whatsapp_user_bindings`, its own table rather than a `user_profiles` column, because the webhook has to read and write it inside the same transaction as the dedup claim and the task creation. A `db_path`-taking store would open a second connection under an open write transaction, wait out the 30s busy timeout and raise — the hazard `.claude/rules/notifications.md` documents.

Resolution order: a non-empty BSUID matched against the bindings; failing that, a valid `wa_id` in E.164 form matched against one bootstrap number whose BSUID is still empty, which latches the BSUID and the send id atomically. **A bootstrap number matching a user whose stored BSUID differs is refused and alerted, never taken** — that is a recycled line, and reading it as the same principal is the takeover this table exists to prevent. An unknown sender gets a 200, no task, no retained identifier and a one-way fingerprint in the log.

**Any change to the identity discards everything learned about the previous holder**, `last_user_message_at` above all: it is the sole input to the 24-hour service window, so carrying it across would authorise a free-form send to somebody who never wrote in. `opted_out_at` goes with it, because it belonged to the previous holder and leaving it strands the new one opted out with no verb to clear it. `set_whatsapp_binding` and `reset_whatsapp_identity` discard the same set.

`touch_whatsapp_binding` writes the uniquely-indexed `send_id` **conditionally**, in SQL with a correlated `EXISTS`. Unconditional, a BSUID sitting stale in another user's `send_id` raised `IntegrityError` out of the batch, the route answered 503, and Meta redelivered into the same deterministic failure for ever with no disposition row, no task and no alert. The rest of the touch lands including the service window, the helper returns False and the caller alerts. Deliberately not the latch path's fail-closed: the sender is legitimate, and refusing their every message over a row that is not theirs is a denial of service.

## The webhook

`GET`/`POST` at the fixed `/webhooks/whatsapp`. Three phases, and the order is the module's design: **authenticate then read** (bounds, content type, configured secret, HMAC over the exact raw bytes, decode — a 403 arriving as a 400 has told the caller the body was read); **normalize the whole batch before `BEGIN IMMEDIATE`**, so a malformed element cannot leave the first message applied behind a 200 nobody will retry; **one transaction for the batch**, with any database failure rolling back to a 503 Meta retries.

`client.verify_signature` adds three guards in front of PyWa's validator, and the load-bearing one is refusing an absent app secret: `webhook_updates_validator` takes the secret as a plain `str` and computes an HMAC under `b''`, so with none configured it does not fail to validate — it validates against a key every reader of this repository knows. The route refuses to serve besides.

An oversized body answers **413**, not the 400 the spec's design section wrote, matching the sibling SMS route through the same shared bounded-body reader. The GET handshake bounds `hub.challenge` to ASCII digits and refuses anything else with 400, which is stricter than "echo it as plain text" — the value is echoed verbatim from a route that answers before anything authenticates it.

The normalizer reads `pricing.billable` and never derives it, where PyWa's own `Pricing.from_dict` infers it from `type == "regular"` when the field is absent. A guess is what opens, or fails to open, the billing circuit. Messages are paired with contacts by sender id, never positionally: PyWa takes `contacts[0]` for every message in a value, which is fine while a value holds one of each and is a principal takeover when it does not.

## Outbound: one send, one row, no resend

`sent_whatsapp` claims a `logical_key` and commits **before** the network call, which is the whole no-resend guarantee: from that instant every later call reads the row as settled and returns. So the claimed region is wrapped whole, catching `BaseException` (both callers run where shutdown delivers `CancelledError`, on the one path where the send may already be on the wire), and split at the send — a pre-send failure settles `failed`, since it is provably a message that never left, and `unknown` is the one state an operator can never resolve.

The adapter's whole job is one bit, and **4xx is the line**. A client error means Meta read the request, applied a documented rule and refused it, so nothing was queued; a 5xx is Meta failing while handling a request it may already have accepted. PyWa's `is_transient` is deliberately not consulted — it answers whether retrying later might work, not whether this attempt was applied. No failure reason is ever built from an exception: Meta's prose, PyWa's exception text and an httpx repr all carry the request URL, which carries the recipient and the token's path segment, so the reason comes from a fixed table and only the numeric code is taken off the exception.

The gate order is by whose decision each is: transport, binding, opt-out, billing circuit, window, budget. Opt-out outranks the window deliberately — reporting a closed window about somebody who asked not to be messaged is an alert nobody should be woken by. `_TERMINAL_FOR_STATUS` and `_NO_RESEND` are two sets: the first says which rows a status callback may not move, the second which rows no send path may re-attempt, and they differ on the four states meaning Meta took the message.

**A confirmation prompt is an interactive message and Meta caps that body at 1,024 characters, not 4,096.** Rendered at the text limit, Meta refused every question past a quarter of the budget and the task parked until it expired. The scheduler sizes the body rather than the renderer, and asks `render_whatsapp` for the budget rather than repeating the arithmetic: cut at the renderer's boundary, the truncation took the `Task #N. Reply YES or NO.` sentence with it, which is the address `!confirm <id>` and a typed YES resolve at. With a template configured it sizes to the *smaller* of the interactive and template-parameter budgets, because the window is not known where the sizing happens.

Monotonicity compares the canonical status rank alone. `sent_whatsapp` has no event-time column, and over a total order of four statuses the rank answers what a timestamp would. **Pricing observation sits outside that ladder on purpose**: reading it only on an applied transition would throw the evidence away in exactly the out-of-order case the ladder exists for, and a billable `failed` row is the loudest evidence there is. `billable` is never downgraded from true by a later false; the other three pricing fields take the latest non-NULL observation.

## Cost controls

Two, and neither is called a guarantee. **The monthly cap is reserved by the claim, in the claim's own `BEGIN IMMEDIATE`** — the count and the row that increments it are one write transaction, so the last free slot cannot be read as free twice (measured: a deferred `BEGIN` turns the two-thread test red every run). `quota_month` is stamped on every row including blocked ones, but only a *claimed* row counts, so a `window_closed` or `budget_exhausted` row consumes nothing while a `failed` or `unknown` one consumes its slot and is never reclaimed.

**`monthly_service_attempt_limit` bounds service attempts and bounds template attempts by nothing.** Implemented as named. The consequence is inverted and worth knowing before enabling paid mode: with the cap spent, an open window is refused while a closed one still bills a template. Templates are reachable only under `allow_paid`, and `doctor.whatsapp.billing` reports the template count beside the service count so the volume is visible. A `monthly_template_attempt_limit` is the real fix and is a spec change.

**The circuit breaker is persistent and deployment-wide.** In `free_guard` the first authenticated status carrying `billable = true` sets `whatsapp_runtime.billing_blocked_at` and blocks every later send. The message that revealed the charge may already be billable; what the breaker buys is that the next one is not. Its alert is not `write_delivery_failure` — that one is about a message that reached nobody, this is a message that arrived and was charged for — and it goes to each admin as well as the recipient, since a deployment-wide block landing in one non-admin's inbox is not an operator notice. `template_available` re-checks `billing_policy == "allow_paid"` rather than resting on `load_config`'s refusal: one validator standing between a free-biased deployment and a paid message is one place for the rule to be edited out of.

## Config, credentials and deployment

Structural validity fails the load (`whatsapp_structural_config_errors`); **credential presence does not** (`whatsapp_credential_errors`, reported by doctor, refused at use). Failing the load on a missing secret repeats ISSUE-058: under `istota_use_environment_file` the Ansible role renders the three empty on purpose and delivers them through `secrets.env`, which the role's own `command:`/`script:` tasks cannot read. `graph_api_version` accepts `v25` and `v25.0`, since PyWa 4.4 pins Graph `25.0` and a `v<integer>` rule would refuse every real version string.

The transport registers on `config.whatsapp.enabled` alone, not "enabled and locally valid": structural validity is already raised at load and gating on credentials would repeat ISSUE-058 again. Local validity is enforced per send by the outbound gate (recording `unconfigured`) and per user by `is_whatsapp_configured`, which applies the four gates still true in an hour — transport, binding, opt-out, billing circuit — plus the cap, and deliberately **not** the service window, which reopens on the user's next message and whose absence would make the heartbeat skip an alert outright rather than record `window_closed` off-surface.

`whatsapp_webhooks_enabled(config)` is `enabled` and nothing else, and the asymmetry with `sms_webhooks_enabled` is the point: SMS keeps a complete inactive provider's routes so a late delivery callback still authenticates across a switch, while WhatsApp has one account and both handlers refuse every request while the block is off. Four places read the same predicate — that function, `serve._maybe_mount_webhooks`, the role's `Resolve webhook receiver need`, and the `whatsapp` compose profile.

**Two things nginx has to do that the application cannot, and one the proxy cannot do either.** The verify token arrives as a *query value* on the GET handshake and nginx decides what to log before the route runs, so `/webhooks/whatsapp` gets `access_log off` in both shipped configurations; a `log_format` naming `$uri` would keep the line but is only valid at http level, and both templates are one server block inside a generated `conf.d`. **Uvicorn's default access formatter renders `get_path_with_query_string(scope)`**, so silencing the front end alone leaves the token in the container log and the journal — measured against a live server, not read off the source. `serve.build_uvicorn_server` had always passed `access_log=False`, so the combined process was the only shape holding the property the docs claimed; both standalone receivers now run `--no-access-log` and a test pins all three. And the route-specific `client_max_body_size 512k` sits above istota's own 256 KiB cap so an oversized POST is answered by the application rather than by nginx with an HTML page Meta retries against.

Docker, Ansible and `istota serve` all run one receiver for location, SMS and WhatsApp together. Setup, the three operating modes and the operational commands are in `docs/features/whatsapp.md`.
