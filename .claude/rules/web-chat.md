# Web chat surface

The in-app chat surface in the web UI. Inbound/outbound plumbing is in
`.claude/rules/transport.md` (`WebTransport`); this file is the surface itself —
rooms, the composer, drafts, send durability, message actions, and the live
room-event stream.

## Overview

An always-on in-app chat surface in the web UI (full-page console at `/chat`, "Chat" nav tab before Feeds). Rooms are per-user channel tokens in `web_chat_rooms` (each gets its own `CHANNEL.md` + sleep-cycle handling); a sent message becomes a `source_type="web"` task (interactive: loads context + `CHANNEL.md` + `guidelines/web.md`) with `output_target="web"`, which routes as a stream surface (no Talk/email push — the result and progress live in `task_events`, tailed by the existing `/api/chat/tasks/{id}/stream` SSE endpoint). Endpoints under `/api/chat/*` in `web_app.py`: rooms CRUD (incl. `DELETE /chat/rooms/{id}` — a hard, token-scoped cascade across `task_events`/`tasks`/`web_chat_messages`/`channel_sleep_cycle_state` via `db.delete_web_chat_room`, guarded by `count_active_web_tasks` → 409 when a task is in flight, plus best-effort `Channels/<token>/` removal; channel `memory_chunks` are a documented residual), message send/history, **`DELETE /chat/messages/{message_id}`** (see below), task confirm/cancel, attachment upload, and **`GET /chat/files?path=`** — the authenticated file handover. Web chat has no outbound attachment channel, so a file a task produces had no way to reach the user and the only answer was minting a _public_ Nextcloud link to hand someone a file they already own; this serves it inside the session instead (`_resolve_chat_file`), leaving link shares for giving a file to someone else. Confinement is two independent checks: the lexical one reuses the skill CLI's `resolve_scoped_path` (one rule for browser and model) and a `realpath` pass catches a symlink _inside_ the workspace pointing out. No admin bypass — `is_admin=False` always, since this is the most directly reachable read path on the web app. Always `Content-Disposition: attachment` + `nosniff` (the workspace holds user-authored HTML/SVG, which inline would execute on the app's own origin against the session cookie). An rclone deployment has no local workspace → 503 naming the share-link alternative. The model is told to use it by `config/guidelines/web.md`'s "Handing over a file" section — the surface guideline, not the skill, because the trigger is "a task produced a file" and `nextcloud` is a menu skill the model would never reach for on that prompt. Per-room UI: a kebab → `RoomSettings.svelte` modal renames a room (token invariant), sets its **standing model/effort default** (see below), copies its token (for a `web:<token>` route), and hard-deletes it behind a GitHub-style type-the-name confirm. **Per-room model default**: a room carries an optional `model`/`effort` on the shared `rooms` registry (canonical values, so the default is surface-independent — a Talk message and a web message in the same room resolve the same default). `transport.ingest.record_inbound` fills a task's model/effort from the room default when the message carried no inline `!model` override (the inline prefix wins as a unit — effort follows model, so an explicit model choice keeps its alias's own effort). Precedence: inline `!model` > room default > `config.model`. Settable on both surfaces via the `!room` command (`!room` shows current, `!room model <alias>` / `!room effort <level>`, `default` clears) and in the web room-settings modal (model + effort dropdowns fed by `GET /chat/commands`'s alias table; the PATCH validates against the brain's known models + effort levels and writes `db.set_room_model_effort`). Room-global by design — in a shared room one participant's setting applies to every sender. Deep link `/chat?room=<token>` selects a room on load (`selectRoomByToken`), silently falling back for an unknown/foreign token; the optional `&task=<id>` extension jumps to a specific turn after selecting the room (`jumpToTask` → pages up to 5 older history pages to locate it, scrolls the `data-cid`-anchored row into view with a ~2s highlight pulse). **`!search` result cards**: `cmd_search` returns a structured `command_data` payload (`kind="search_results"`) alongside its plain-text body via `CommandContext.result_data` → `dispatch` → the web POST; the store renders `SearchResults.svelte` (conversation cards carry a "Jump to reply" button = `jumpToTask`; memory cards show source + preview) instead of markdown, falling back to markdown for any other/absent `data`. Talk ignores `data` and keeps the text body + deep links. The read path (`commands._search_memory`) searches the `channel:{token}` namespace + all memory source types and classifies each hit on an `is_memory` axis (conversation rows room-scoped, recovering the room from the `messages` store via `db.get_message_room_for_task` past `tasks` retention); `cmd_search` runs a strict prefix pass, scope-filters, then retries once in OR mode only if the _scoped_ result is empty (forgiveness keyed on scoped emptiness, not global BM25 emptiness). The executor recall path + skill CLI keep strict AND (no prefix / no OR fallback) via unchanged `memory.search.search` defaults. `!commands` (and the `!model <alias>` prefix) work identically across surfaces — `commands.dispatch(... surface=...)` runs the handler over a `CommandContext` and delivers via the resolved transport on a push surface (Talk) or returns the text inline on a stream surface (web → `inline_result`); per-user rate limit counts `source_type='web'` rows in `tasks`. **Command autocomplete**: typing `!` in the composer opens a live-filtered dropdown of available commands (arrow-nav, Tab/Enter to accept, Escape to dismiss); `!model ` completes model aliases via the same mechanism. Built as a reusable prefix-autocomplete primitive in `web/src/lib/components/chat/autocomplete/` (a trigger-agnostic engine + per-trigger `CompletionProvider`s — `commandProvider`, `modelAliasProvider`) fed by one cached `GET /chat/commands` endpoint (`{commands, model_aliases}` serialized from `commands.COMMANDS` + the active brain's `list_aliases()`); adding a new trigger is a new provider, not a composer change. **Composer**: one bordered pill (`Composer.svelte`) holding `+` (file picker), the field, and mic + send on the right; once the text wraps, the field takes the full width and the controls drop below it (a CSS `order` swap on a `multiline` class). Two non-obvious invariants. (1) **Wrap detection is measured at the single-row width, never the field's current width** — wrapping moves the controls out of the field's row, which widens the field, which can un-wrap the text, which flips it back; measuring the live width makes the decision depend on its own output and the field alternates one/two rows on consecutive keystrokes. `wrapsAtSingleRowWidth` pins the _wrapper's_ inline `flex-basis` for the measurement (the field is a flex item with `flex: 1`, so its own `width` is ignored for sizing), and height sizing is a separate pass after `await tick()` so it measures the width the field ends up with. `<svelte:window onresize>` re-evaluates, since the wrap point moves with the container. (2) **Control sizing is `em`-relative with `font: inherit` on the buttons** — a `<button>` does not inherit font, so without it the `em` sizes resolve against the UA's ~13px and the controls stay fixed while the text-size preference scales the type around them. Voice messages: `useRecorder.svelte.ts` wraps `getUserMedia` + `MediaRecorder` (webm/opus on Chrome/Firefox, `audio/mp4` named `.m4a` on iOS) and hands the result to the ordinary attachment upload — `executor._pre_transcribe_attachments` transcribes any audio attachment into the prompt, so this needs no dedicated endpoint (needs the `whisper` extra; `webm` is in `attachment_extensions`). The mic hides itself when `navigator.mediaDevices` is absent, which is what makes it disappear outside a secure context rather than failing on tap. Stored attachment names lead with a sanitized stem (`_attachment_stem`, `[A-Za-z0-9._-]` only, `Path.stem` drops any directory component) plus a random suffix, so the inbox is browsable without trusting a client-supplied filename. **Attachment chips are persisted, not just optimistic**: a turn's chip labels live on the canonical `messages` row (`messages.attachments`, JSON display names, written by `record_inbound` via `transport.display_attachment_names`) and are emitted on every user-row history/stream payload. They used to exist only in the composer's in-memory file list, so leaving a room and coming back silently dropped the record that a file was part of the turn. The names are duplicated off `tasks.attachments` (paths) deliberately — retention GCs the task row, while the transcript has to keep showing the file; a turn predating the column falls back to basenames of the joined task paths. The client supplies the display names (`attachment_names` on the send, positional, discarded wholesale on a count mismatch) because the _stored_ filename carries the collision suffix above — a basename-derived chip would read `note-a1b2c3d4.txt` where the live one read `note.txt`. Every other surface (Talk) falls back to the basename, which is also what gives a Talk-attached file a chip in web chat. **A chip is also a link to the file it names** (ISSUE-206), pointed at the same session-scoped `GET /chat/files?path=` handover described above — the user opening a file they already own, so nothing becomes public. A minted Nextcloud share link is the wrong tool here for the same reason it's the right one for handing a file to someone else. The link needs a _workspace_ path (`/Users/<uid>/…`) while the attachment is stored as a host path, so `transport.ingest.workspace_attachment_paths` translates once at ingest and the result rides the message row as `messages.attachment_paths` — a JSON array positional against `attachments`, stored beside the names for the same reason they are (the host paths live only on the `tasks` row retention deletes, so deriving at read time would make every link rot after a few days). A `null` entry means "not servable" and renders the inert chip it always was: a Talk attachment lives under `/Talk`, and a mountless (rclone) deployment has no local workspace at all. The read path re-scopes to **the caller's own** workspace rather than trusting the stored value, because rooms are shared — a co-member sees the chip but `/chat/files` would refuse them the file, and offering a link that 403s is worse than offering none. `POST /chat/attachments` returns `workspace_path` alongside the host `path` so the composer's optimistic chip is a working link immediately; without it the just-sent chip would stay inert for the whole session, since the optimistic row is deduped against the streamed echo rather than replaced by it. **Attachment intake.** Five entry points through one `upload()` sink in `Composer.svelte`: the `+` menu's three native rows (photo library, camera, document picker — shell 0.3.0), the plain file input off-shell, paste, drop, and the voice recorder. The server publishes its own limits at `GET /chat/config` (`max_attachment_mb`, `attachment_extensions`) and the composer pre-checks against them, **fail-open** — `limits` stays null until the config lands, so an unreachable endpoint never becomes a client-side refusal and the server's 413 is the backstop. The app default is 25 MB but the Ansible role deploys **100** and renders nginx's `client_max_body_size` from the same variable; splitting them means nginx answers its own HTML error page, which the client cannot parse (`uploadFromShell` tolerates that shape deliberately). `heic` is in the accepted set because that is what an iPhone photo is — the gallery picker usually re-encodes to JPEG, but a HEIC dragged off a Mac was being refused on extension. A native-picked file need not enter the page at all: with `IstotaUploader` present the shell posts it straight from disk with URLSession (absolute URL, `file` field), and otherwise the file is read in 3 MiB windows into a `File` backed by the WebKit blob store rather than the JS heap — which is what made the client-side ceiling removable. The temp copy is deleted on every path. A send with **no text** is accepted when attachments are present; `_describe_attachment_only_message` stores a descriptor as the prompt ("Voice message (see attached audio)." for an all-audio turn) so the transcript, the LLM context and the Talk mirror all read something. Relatedly, `_pre_transcribe_attachments` now **appends** a transcript rather than replacing the prompt — text typed alongside a voice memo used to be discarded. **Drafts** (ISSUE-205): unsent composer text survives leaving the room and leaving the page, held client-side in `localStorage` (`stores/drafts.ts`, one map under `chat.drafts`) rather than round-tripped through the server — a draft belongs to the machine it is being typed on, and publishing text the user has not decided to send is the one thing a draft is not. The page hands the composer a `draftKey`; without one the field behaves exactly as it did. The key is `<user>:room:<token>`, and both halves earn their place: the **token** rather than the room id because `web_chat_rooms.id` is `INTEGER PRIMARY KEY` **without** `AUTOINCREMENT`, so SQLite hands a freed rowid straight back out and a deleted room's draft would be inherited by whichever room takes its id next; and the **user** in front of it because a shared Talk room has one token across every member, so on a browser profile two people take turns using, a bare token would hand one person's half-written message to the other. The composer is mounted once and never keyed on the room, so before this a draft did not merely vanish on a tab switch — it also followed you into the next room; `switchDraft` writes the outgoing room's text down before restoring the incoming one's, which closes both halves at once, and clears the attachment chips on the way (they are not drafted, an uploaded file being server-side already, but re-picking one costs a tap while posting it to the wrong room does not undo). Writes are debounced (`DRAFT_SAVE_DEBOUNCE_MS`) with an immediate flush on every departure the component can see: a key change, unmount, `pagehide` (a reload or a close — the event a WKWebView delivers where `unload` is not) and `visibilitychange` → hidden, which is the **only** callback a backgrounded iOS app gets before the page may be discarded; without that one the exposure is 400ms of _idle_ rather than of typing, since continuous typing never reaches a debounce. **Two null-key cases that look identical from the prop and want opposite treatment.** Text typed before the room list answers is carried into whichever room lands, since there is no earlier room to attribute it to — but a stored draft always outranks it, or one keystroke during that window would destroy the draft the user came back for. A key going null _later_ means the room was deleted, archived or removed by another client, all of which leave the view on `room` with the composer mounted; there the field is cleared, because carrying that text is exactly the leak. The carry is therefore gated on a one-shot "has ever had a key" flag, not on the previous key being null. Bounded by a 30-day TTL (checked on read as well as on write, so an expired draft is never restored) and a 50-entry cap, because a room that is deleted or never revisited would otherwise leave its draft behind forever and nothing else collects it; writing an unchanged draft is a no-op so that merely _visiting_ a room neither re-serializes the map nor pushes its age out.

**Send lifecycle on the user's own row** (ISSUE-200). The composer appends the user turn and an assistant placeholder optimistically, then POSTs — so a message had exactly one appearance whether or not it ever reached the backend. Worse, the one failure that was handled (an HTTP error response) was written into the *assistant* placeholder, which made "your message never left" present as "the assistant errored replying", and the failure the issue actually reports took a path with no handling at all: `fetch` **rejects** rather than resolving when the backend is unreachable, so the throw escaped an un-awaited caller, `status` was never reset off `'sending'`, and the composer stayed locked in Stop mode until reload. The ack itself already existed — the endpoint returns `{task_id, status: "pending", …}` — and is unchanged; this is entirely client-side. `sendChatMessage` now **classifies instead of throwing** (`SendFailure` = `unreachable | timeout | auth | rate_limit | rejected`, plus a `SEND_TIMEOUT_MS` bound `fetch` has none of), the row carries a `sendState` lifecycle, and `failSend` **removes** the assistant placeholder rather than repurposing it — the turn produced no assistant message. Absence of `sendState` is the settled state, deliberately with no `'sent'` member: every row rebuilt from history is settled by construction, and the ack's visible form is the pending mark clearing rather than a receipt we have no read-receipt semantics to back. Four non-obvious constraints. **Retry reuses the failed row's `cid`**, because `appendStreamedRow` dedups on `(role, task_id)` — stamping the retry's new id onto the existing row is what folds the canonical echo into it, where appending a fresh row would leave the failed one behind and show two bubbles for one message. It therefore needs the original `ChatAttachment[]` stashed on the row (`sendPayload`): the rendered row holds display names and *workspace* paths, not the host paths the POST body takes. **Retry is gated on an idle status** (and its button disabled while busy) because `runTurn` is not re-entrant — it drains the `pendingSend` echo buffer on entry and silently resets `cancelRequested`. `send` was gated by the composer's `busy`; Retry was the first entry that wasn't. **A send the server accepted but never got to report** — a client timeout, a socket dropped after the request was processed — leaves a row marked failed whose task is really running; `appendStreamedRow` reconciles that by **adopting** an echo whose `(role, text)` matches a failed, task-less row instead of appending it, matched on the body precisely so a send the server rewrote (an attachment-only descriptor, a stripped `!model` prefix) falls through to the old duplicate rather than claiming a wrong row. That heuristic is now the fallback rather than the mechanism (see `client_msg_id` below), and is what still covers rows created before the key existed. **`failSend` only sets `'idle'` when its turn's room is still on screen**: switching rooms isn't gated on `busy`, so a send failing after a switch would otherwise unlock the composer over a room with a live stream. Retry is withheld where it cannot succeed — an expired session, and any other 4xx that is a verdict on the request (409 archived, 400 over-cap, 413) — mirroring the server's own transient/permanent split. Per `web/AGENTS.md`, a *classified* send failure is **in-band** and raises no `notify()`; the two `notifyError` calls on the send path are last-resort catches for a rejection that escaped the store's own handling, where a notice beats silence. An offline outbox is deliberately out of scope and belongs to ISSUE-202, whose queue plugs into this same `sendState` union.

**Making a failed send durable** (chat-send-durability-fixes spec). ISSUE-200 made a failed send *visible* without making it *durable*: the `sendState: 'failed'` row was the only copy of the user's text, and three paths destroyed it — the room stream's own reconnect recovery, an ordinary page reload, and the composer dropping the draft the instant Send was pressed. A network outage triggers the first two at once, and it is the same outage that produced the failure, so the user watched their message be reported as unsent and then vanish. Four corrections, three of them client-side.

`messages` is a projection of server history — `loadHistory` and `loadViewPage` both `messages.set` a list built wholly from the response — and a failed send is the one row with no server copy, identifiable without ambiguity (`sendState === 'failed'` and no `msgId`, which every server row carries). Those rows are held in a room-keyed **`strandedSends`** map while off screen, put away by `stopActive` (the single "this transcript is about to be replaced" hook, which every clear path already calls) and taken back out by `carryClientOnlyRows` on the next rebuild, re-appended at the tail because that is where they were: a failed send is always the newest thing in its room from the client's point of view. Carried into **All**, which spans every room, and not into Unread or Starred, which are filtered panes a client-only row is not a member of — those leave the held rows alone, so the room's own transcript still gets them back. A deleted or hidden room drops its entry; the row was only ever going to be re-sent into that room.

**The draft is the second copy, and is dropped on the ack rather than on submit.** Nothing in the store survives a reload, so the stored draft is what restores the text into the composer when the row itself is gone — a downgrade from Retry to a re-send with no retyping, and the accepted outcome until ISSUE-202. The signal is **`sendSettled`** on the session — a counter *and the room it acked* — bumped by `settleSend` (which already runs at the moment the POST acks, ahead of everything downstream that can throw) and watched by the composer through a prop; the page translates the room into a draft key, because the composer owns the key's shape and passing a callback *into* it for it to call itself would be circular. `submit` writes the submitted text under the key rather than merely leaving it — a fast submit beats the debounce and would otherwise store nothing, or a stale prefix — and `flushDraft` holds it through the unsettled window, since every departure (a room switch, unmount, `pagehide`, `visibilitychange`) flushes an emptied field and would drop exactly the draft this exists to keep.

**Three constraints on that, each of which was a proven defect first.** The unsettled sends are a **map keyed by draft key**, not one slot, and the ack carries an identity: two sends can be open at once (leaving a room resets `status` to `'idle'`, which un-gates the composer), and with a bare counter the first ack dropped the second room's draft while its own POST was still open — destroying the only copy of it, which is the exact failure this whole section exists to prevent, reintroduced in a second place. `switchDraft` **refuses to restore a message still awaiting its ack**, even though it is stored under that key: putting it back in the field shows an already-sent message as unsent text, one Enter from being sent twice, and the ack then reads it as newly typed and declines to clear it, so it stays there for good. And the drop is withheld when something *has* been typed since — emptiness is a sufficient test for the on-screen room only because of the rule before it.

**`client_msg_id` moves retry identity to the server** — one nullable column on `messages`, a partial unique index on `(room_token, client_msg_id)`, and an empty string coerced to `NULL` on the way in, following `location_pings.client_id` (an empty string is a valid unique key and would collapse a room's whole history onto its first send). The client mints one per message (`crypto.randomUUID`, absent when the page is not a secure context, in which case the endpoint behaves exactly as it did before the field existed) and **reuses it on every retry**; `record_inbound` checks it after resolving the room and before creating anything, so a repeat resolves to the first turn and no second task, message row or Talk mirror exists (`_mirror_web_turn_as_user` reads the stamp it left as its own guard). The body-match adoption above stays as the fallback, because it is a heuristic that already fails on any send the server rewrites, and because rows predating the key have none. ISSUE-202's outbox needs the key regardless.

Three properties of that key are load-bearing and none is obvious. The lookup **returns the sender rather than filtering on it**: a room is shared and the key is arbitrary client-supplied text, so filtering would make a co-member's reused key miss and then collide on the room-scoped index, while ignoring the sender hands them a task `_authorize_task_access` will refuse them — instead the send **gives the key up** and proceeds without idempotency, which it is an optimization rather than a requirement. The endpoint **rejects an over-long key rather than truncating** it, since truncation changes the identity and two keys sharing a 64-char prefix would silently resolve to one another. And the replay deliberately **does not filter on task status**, though the spec's wording said non-terminal: a late replay would then find nothing, create a task, and take a `UNIQUE` violation on the insert. **A `!command` is the documented gap** — it runs inside the request and returns before the key is ever consulted, so a timed-out `!steer` or `!retry` cannot be re-POSTed safely; the client withholds Retry for any `!`-prefixed body rather than guessing which commands repeat cleanly.

Two pieces of per-room state were also not scoped to their room. An **upload in flight across a room switch** put its chip in the new room, and sending from there posted the file to the wrong one: `upload()` is async and appends with no notion of where it started, while `switchDraft` clears the list synchronously and cannot see a promise. A monotonic **`uploadEpoch`**, captured on entry and compared before each write, drops a stale result — including the counter decrement, since the switch has already reset it to 0 and a stale decrement would drive it negative and leave the composer reporting an upload forever. The file does reach the server and is orphaned there, the same outcome as closing the tab mid-upload. And the module-level **`pendingSend` echo buffer** survived a room switch that reset `status` to `'idle'`, defeating both gates the drain rested on (`send`'s `busy`, `retrySend`'s idle status): a second send then released the first's frames before its task id was stamped, showing two bubbles for one message. `runTurn` now holds its own buffer and drains only that one, and `stopActive` **abandons** the slot rather than draining it — those frames are for a room the user has left, whose transcript `loadHistory` rebuilds from the server on the way back in. The drain on the way *in* is a safety net rather than a step, and only because the third way into an overlapping same-room turn was closed with it: `Cmd/Ctrl+Enter` called `submit` without consulting the send/stop mode, so holding it started a second turn in a room that already had one. The chord now does nothing while the button is in Stop mode, rather than being repurposed as Stop.

**Per-turn message actions** (ISSUE-210). One action row under each message body — copy, star, delete, left to right in ascending consequence — revealed on hover or on tap, keeping its layout box either way so revealing it never reflows the transcript. Copy takes `messageCopyText`: the turn's prose groups only, tool traces excluded, as **markdown source** rather than rendered HTML (which is why a fenced code block needs no copy button of its own). It is withheld mid-stream, because half an answer is not an answer; the star is not, because it marks the row rather than the text. **Delete is `DELETE /chat/messages/{message_id}` → `db.delete_message`** and it is _room-wide_, not per-user: the `messages` row is gone for every member, and authorization is membership (`db.is_room_member`), not authorship — the opposite of stars, which are per-user in `message_stars`. Unknown id and non-member both return **404**, deliberately indistinguishable so neither becomes an id oracle for the other (the same rule the star endpoint follows); a turn whose task is still in flight returns **409**, because the scheduler writes the assistant row at completion and the delete would silently undo itself. It is a hard delete, not a tombstone: every read path would have to learn to filter a tombstone, and the row would still occupy its slot in the `(room_token, role, task_id)` unique index, so re-running the turn would collide with a message the user believes they removed. It touches `messages` and `message_stars` only — never `task_events` or `tasks` (unlike a room delete) — and leaves `room_read_state` alone, since a read cursor is a high-water mark rather than a reference. **The `message_deletions` ledger exists because the room stream has a second cursor.** That stream tails `messages.id > cursor`, and a vanished row can carry nothing, so deletions get their own monotonic `message_deletions.id`; the `message_deleted` frame therefore carries no SSE `id:` (that cursor belongs to the message tail) and instead rides its cursor _inside_ the payload, which the client passes back as `since_deletion_id` on both `/chat/stream` and `/chat/events` — without it a reconnect after a delete silently resurrects the message. Like the message tail, the deletion cursor advances to the max id **scanned**, not the last one sent, or a client sitting behind someone else's invisible deletions never catches up and the O(1) gate stops short-circuiting. Rows are pruned after a fixed 30 days in `run_cleanup_checks` (`_MESSAGE_DELETION_RETENTION_DAYS`, deliberately not a config knob — the row is tiny and nothing about it is worth tuning). Propagation into a bound Talk room is best-effort and fire-and-forget, trying the user's own OAuth token first and the bot's second, because Talk lets only the author or a moderator delete and a mirrored user turn is authored by the _user_ while a reply is authored by the bot — so a 403 is the ordinary "not yours", not an error. A Talk failure never fails the web delete, which has already committed. Client-side the removal is **pessimistic**, unlike `toggleStar`: a row removed and then restored would reappear mid-transcript after the user watched it go.

**App shell and caching.** There is no service worker: static responses carry two cache classes — hashed `_app/immutable/` assets immutable for a year, everything else (the HTML shell, `version.json`, the manifest, icons) `no-cache` and revalidating. Sending neither let an installed home-screen app pin the shell indefinitely and then request hashed chunks the server had deleted. A new build is surfaced rather than forced: SvelteKit's version poll drives a toast with a Reload button (a tap, because a reload discards a half-typed message), re-checked on `visibilitychange` since the poll timer is throttled in a background tab and stopped in a suspended PWA. The web unit passes `--timeout-graceful-shutdown` for a related reason — `GET /chat/stream` is session-lived and exits only on client disconnect, which server shutdown does not trigger, so a restart with any browser tab open used to sit out the full stop timeout and die on SIGKILL. Docker's web service has no equivalent flag.

Knobs under `[web.chat]`. Frontend engine in `web/src/lib/stores/chat.ts` (SSE with polling fallback) + widgets in `web/src/lib/components/chat/`. **Body render model**: an assistant turn is an ordered list of `text`/`tool`/`thinking` segments (`segments.ts`); `renderGroups` reduces it to interleaved render groups — substantial prose blocks (trimmed length ≥ `SUBSTANTIAL_TEXT_CHARS`, mirrors the backend gate) render as prominent markdown in true order, consecutive tools coalesce into one `ActivityTrace` chip, short lead-in narration + reasoning are dropped, and the trailing text is always the answer. This keeps a meaty intermediate block (analysis the model wrote, then acted on) visible as its own prose block instead of vanishing when the next tool settles it — the live stream and a reloaded-from-`execution_trace` turn build the same groups. Not a Talk replacement — an in-app companion. Web chat is also a _delivery_ surface (ISSUE-121): alerts, the verbose execution log, and notifications routed to `web` are appended to a room as unsolicited system messages (distinct from task-backed turns, written into the canonical `messages` store as `role='system'` rows) and merged into room history by time. See `WebTransport` in the Transport abstraction section. **Unread indicators**: the sidebar bolds a room name and shows a count chip for rooms with unseen messages. Counts are server-computed in the `/chat/rooms` payload (`db.count_unread_messages` — `messages` past the per-user/per-surface `room_read_state` cursor, excluding `role='user'` so your own/Talk-mirrored turns don't ring your own room); `db.initialize_room_read_state` seeds a freshly-surfaced room's cursor to its current max so a backlog doesn't read as unread. Opening a room (or `POST /chat/rooms/{id}/read` → `_chat_mark_room_read`) advances the cursor to the room's newest message; the client persists on open / stream-append / stream-settle / `visibilitychange` (visibility-gated). The active room is held at 0.

**Live room-event stream** (`live-web-chat-room-stream` spec). The per-task SSE stream only ever covered a task the client itself started; everything else — a Talk-originated turn, a routed alert, an unread badge, a rename — rode `setInterval`. `GET /chat/stream` is a sibling of `chat_task_stream` that tails the canonical `messages` store instead of `task_events`, carrying **every room the user is a member of over one session-lived connection**. The seam between the two: the room stream is the "something happened" bus, the task stream stays the "here is the token-level detail" bus — a streamed `user` row whose task is still unsettled makes the client open a task stream for it, which is `pickUpNewInFlightTasks` made event-driven (and fixes the `pending_confirmation` skip, since the persisted `confirmation` event now replays). Cursor is `messages.id` alone — one monotonic integer over user turns, assistant turns and system rows — which is what closes the fast-turn hole _structurally_: a Talk turn that starts and finishes inside 200ms still writes two rows and both are tailed, so timing stops mattering. The producers are in a different process from the web server (separate systemd units / containers), so the web tier polls SQLite exactly as `events.py` prescribes; the change is _where_ the polling lives — server-side at ~1s as an indexed `id > :cursor` scan behind an O(1) `MAX(id)` gate, pushing deltas, instead of client-side at 5s refetching a 50-row page per open room. `db.list_room_events_since` shares SQL fragments with `db.list_messages_across_rooms` so the visibility predicate (membership minus dismissals minus archived) cannot fork, and rows are emitted in the **same shape the history endpoints emit** (`_cross_room_message_dict`) so `buildHistoryMessage` builds a streamed row and a reloaded row identically. Frame kinds: `message` (carries `id:`), `gap` (carries `id:`), `room` (metadata delta — rename / model / effort / added / removed; **no** `id:`), `message_deleted` (**no** `id:` — see below), and a `: ping` keepalive (**no** `id:`) — auxiliary frames must omit `id:` or EventSource's resume cursor lands in the wrong place. The **gap threshold** is split because neither side can see the other's variable: the server decides on _cost_ (`room_stream_max_batch` rows AND `room_stream_max_bytes` — a joined assistant row carries `execution_trace`, so row count alone measures the wrong thing), the client on _age_ (~60s of silence on reconnect or after a hidden tab, since a star toggled elsewhere or a Talk-synced read cursor is state the stream doesn't carry). Both converge on one recovery routine: reload rooms + the open room, then adopt the cursor — which is the server's max id **scanned**, not the last one sent, or the truncated rows are stranded. Frames landing during that reload are buffered and re-applied. The notif poller is gone; the rooms poll is demoted to a 30s metadata reconciler and **kept only because `GET /chat/rooms` drives the Talk→web read-state pull**. Aggregate views (All / Unread) and background-room previews are fed from the same frames. Knobs under `[web.chat] room_stream_*`; `GET /chat/events` is the polling-fallback snapshot; `_admin_chat_section` reports live connection count (the metric that would justify the deferred shared per-user broker).
