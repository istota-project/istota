# Web chat surface

The in-app chat surface in the web UI. Inbound/outbound plumbing is in
`.claude/rules/transport.md` (`WebTransport`); this file is the surface itself —
rooms, the composer, drafts, send durability, message actions, and the live
room-event stream.

## Overview

An always-on in-app chat surface in the web UI (full-page console at `/chat`, "Chat" nav tab before Feeds). Rooms are per-user channel tokens in `web_chat_rooms` (each gets its own `CHANNEL.md` + sleep-cycle handling); a sent message becomes a `source_type="web"` task (interactive: loads context + `CHANNEL.md` + `guidelines/web.md`) with `output_target="web"`, which routes as a stream surface (no Talk/email push — the result and progress live in `task_events`, tailed by the existing `/api/chat/tasks/{id}/stream` SSE endpoint). Endpoints under `/api/chat/*` in `web_app.py`: rooms CRUD (incl. `DELETE /chat/rooms/{id}` — a hard, token-scoped cascade across `task_events`/`tasks`/`web_chat_messages`/`channel_sleep_cycle_state` via `db.delete_web_chat_room`, guarded by `count_active_web_tasks` → 409 when a task is in flight, plus best-effort `Channels/<token>/` removal; channel `memory_chunks` are a documented residual), message send/history, **`DELETE /chat/messages/{message_id}`** (see below), task confirm/cancel, attachment upload, and **`GET /chat/files?path=`** — the authenticated file handover. Web chat has no outbound attachment channel, so a file a task produces had no way to reach the user and the only answer was minting a _public_ Nextcloud link to hand someone a file they already own; this serves it inside the session instead (`_resolve_chat_file`), leaving link shares for giving a file to someone else. Confinement is two independent checks: the lexical one reuses the skill CLI's `resolve_scoped_path` (one rule for browser and model) and a `realpath` pass catches a symlink _inside_ the workspace pointing out. No admin bypass — `is_admin=False` always, since this is the most directly reachable read path on the web app. Always `Content-Disposition: attachment` + `nosniff` (the workspace holds user-authored HTML/SVG, which inline would execute on the app's own origin against the session cookie). An rclone deployment has no local workspace → 503 naming the share-link alternative. The model is told to use it by `config/guidelines/web.md`'s "Handing over a file" section — the surface guideline, not the skill, because the trigger is "a task produced a file" and `nextcloud` is a menu skill the model would never reach for on that prompt. Per-room UI: a kebab → `RoomSettings.svelte` modal renames a room (token invariant), sets its **standing model/effort default** (see below), copies its token (for a `web:<token>` route), and hard-deletes it behind a GitHub-style type-the-name confirm. **Per-room model default**: a room carries an optional `model`/`effort` on the shared `rooms` registry (canonical values, so the default is surface-independent — a Talk message and a web message in the same room resolve the same default). `transport.ingest.record_inbound` fills a task's model/effort from the room default when the message carried no inline `!model` override (the inline prefix wins as a unit — effort follows model, so an explicit model choice keeps its alias's own effort). Precedence: inline `!model` > room default > `config.model`. Settable on both surfaces via the `!room` command (`!room` shows current, `!room model <alias>` / `!room effort <level>`, `default` clears) and in the web room-settings modal (model + effort dropdowns fed by `GET /chat/commands`'s alias table; the PATCH validates against the brain's known models + effort levels and writes `db.set_room_model_effort`). Room-global by design — in a shared room one participant's setting applies to every sender. Deep link `/chat?room=<token>` selects a room on load (`selectRoomByToken`), silently falling back for an unknown/foreign token; the optional `&task=<id>` extension jumps to a specific turn after selecting the room (`jumpToTask` → pages up to 5 older history pages to locate it, scrolls the `data-cid`-anchored row into view with a ~2s highlight pulse). **`!search` result cards**: `cmd_search` returns a structured `command_data` payload (`kind="search_results"`) alongside its plain-text body via `CommandContext.result_data` → `dispatch` → the web POST; the store renders `SearchResults.svelte` (conversation cards carry a "Jump to reply" button = `jumpToTask`; memory cards show source + preview) instead of markdown, falling back to markdown for any other/absent `data`. Talk ignores `data` and keeps the text body + deep links. The read path (`commands._search_memory`) searches the `channel:{token}` namespace + all memory source types and classifies each hit on an `is_memory` axis (conversation rows room-scoped, recovering the room from the `messages` store via `db.get_message_room_for_task` past `tasks` retention); `cmd_search` runs a strict prefix pass, scope-filters, then retries once in OR mode only if the _scoped_ result is empty (forgiveness keyed on scoped emptiness, not global BM25 emptiness). The executor recall path + skill CLI keep strict AND (no prefix / no OR fallback) via unchanged `memory.search.search` defaults. `!commands` (and the `!model <alias>` prefix) work identically across surfaces — `commands.dispatch(... surface=...)` runs the handler over a `CommandContext` and delivers via the resolved transport on a push surface (Talk) or returns the text inline on a stream surface (web → `inline_result`); per-user rate limit counts `source_type='web'` rows in `tasks`. **Command autocomplete**: typing `!` in the composer opens a live-filtered dropdown of available commands (arrow-nav, Tab/Enter to accept, Escape to dismiss); `!model ` completes model aliases via the same mechanism. Built as a reusable prefix-autocomplete primitive in `web/src/lib/components/chat/autocomplete/` (a trigger-agnostic engine + per-trigger `CompletionProvider`s — `commandProvider`, `modelAliasProvider`) fed by one cached `GET /chat/commands` endpoint (`{commands, model_aliases}` serialized from `commands.COMMANDS` + the active brain's `list_aliases()`); adding a new trigger is a new provider, not a composer change. **Composer**: one bordered pill (`Composer.svelte`) holding `+` (file picker), the field, and mic + send on the right; once the text wraps, the field takes the full width and the controls drop below it (a CSS `order` swap on a `multiline` class). **The send key is a bare Enter, and Shift+Enter writes the newline** — nearly every message is one line, so the unmodified key belongs to the common case; `Cmd/Ctrl+Enter` is kept as an alias rather than removed, since it was the send key long enough to be in people's hands. It is **gated on a hardware keyboard** (`usesSoftKeyboard()`, the same `pointer: coarse` primitive the post-send blur reads): on a phone there is no cheap Shift and the send button is already under the thumb, which is also why `enterkeyhint` stays `enter` — a soft keyboard is the only thing that reads the label, and it must not promise "send" where the key writes a newline. It sits **after** the autocomplete's own `onKeydown`, so a bare Enter accepts the highlighted completion while the popover is open and sends on the next press; the chord alone is checked ahead of the popover, being unambiguous. Making Enter the send key is what forced the popover to **decline a modified Enter** (`useAutocomplete.onKeydown`), which it used to swallow along with the plain one: Shift+Enter is now the field's only newline, so eating it left no way to break a line while a popover happened to be open.

**Two rules hold the send key together, and both were defects in the first cut of it.** Every keyboard path asks `wouldSend()` *before* consuming the key, so a key that cannot send falls through to the browser and writes its newline rather than being eaten — the send key going dead is the one failure the user has no way to read, and `preventDefault()` ahead of the gate produced exactly that during a running turn. `wouldSend()` collects four refusals: the `showStop` mode gate (a second send into a room that already has a turn shares one echo buffer, whose drain releases the first turn's frames before its task id exists), an **active recording** (the send button is deliberately swapped out for Discard/Finish and the field sits under an opaque overlay, so a key that sent would post text the user cannot see and strand the memo in the next message — a hole straight through a control that was removed on purpose), an **upload still in flight** (the file is part of this message; sending without it leaves the chip in the composer for whatever is typed next, which reads as the file having been sent), and `canSend`. The send button reads the same predicate, so the two cannot disagree about whether the message is ready.

**The mode gate has one exemption, and it is a `!command` (ISSUE-300).** A command is answered inside the request and comes back carrying no task id, so it never enters `runTurn` — and `runTurn`, not the server's task count, is what the gate protects: one non-re-entrant entry point holding `status`, the `pendingSend` echo slot and the pending-cancel flag. Refusing commands left `!steer`, built for exactly the mid-turn case, untypeable on the one surface where the stream is being watched. Note that "no task id" describes the *response*, not the server: `!retry`, `!resume` and `!confirm` each leave a task queued and still answer inline. Those turns arrive over the room stream and are adopted by `pickUpStreamedTask` exactly as a Talk turn landing mid-stream is, with the backend's per-channel gate serializing them — so they need nothing from this path, and the client deliberately does not try to claim them. What distinguishes a command from ordinary text is `isKnownCommand` (autocomplete `providers.ts`, off the same cached `GET /chat/commands` catalogue). The catalogue is the *only* evidence available client-side, which is the real reason an unregistered `!word` is refused — not that the server would make a task of it, since `dispatch` answers an unknown name inline too. Model aliases are deliberately not excluded from the set: the prefix resolved ahead of dispatch is the literal `!model <alias>`, not `!<alias>`, so an alias shadows nothing and filtering on one would only refuse a genuine command sharing a name with a role alias. `!model …` is refused on its own terms — no command is registered under `model`. Before the catalogue lands the answer is no, which leaves the gate exactly as it was. The store applies the same rule at the seam that owns the invariant rather than trusting the composer: `send` routes a mid-turn command to **`sendInlineCommand`**, which writes no `status`, claims no `pendingSend` slot, does not reset `cancelRequested`, and withholds Retry for the reason `sendTurn` already does. An attachment disqualifies a command on both sides, since a file belongs to a task.

**Two things that exemption breaks if they are not handled, both found in review.** A command may write a **durable `messages` row** — `cmd_steer` records the note as a `task_id IS NULL` user row, the same shape a confirmation answer takes — and that row echoes back over the room stream carrying no task id, so `msg_id` is the only dedup key `appendStreamedRow` has. `cmd_steer` therefore returns `{kind: 'steer_recorded', user_msg_id, body}` on `result_data` and `applyInlineResult` stamps it, exactly as `confirmation_answered` already did; `body` rides along because the stored row holds the note alone while the client drew the whole `!steer <note>` line, and adopting it is what keeps the live transcript and a reloaded one identical. Unstamped, the steer renders twice live and once after reload. This was unreachable before: with the room idle `cmd_steer` refuses and writes nothing, so the branch was dead on this surface.

And **two sends can now be open in one room**, which the draft machinery was not built for. `unsettledSends` is keyed by draft key — one entry per room — on the reasoning that the `showStop` gate allowed one open send per room and a second could only be another room's. A command sent while an ordinary message is still pre-ack breaks that: it would overwrite the map entry and the stored draft, and its own ack would then clear the draft belonging to the message still in flight, which for a send that goes on to fail is the only copy that survives a reload. Two halves close it. `submit` writes the *held* text back rather than its own when an unsettled send already owns the slot — a command is not a draft worth restoring. And `settleSend` splits: `sendInlineCommand` calls `settleSendRow`, clearing its own row's marks without bumping `sendSettled`, since only a drafted send may signal an ack the composer will act on.

Two smaller consequences worth knowing. The button **reverts to Send over a command** rather than staying in Stop, which costs the tap-to-cancel affordance in that state — `!stop` being a command itself is what makes that tolerable — and the mode flips *back* the instant `submit` empties the field, so a second deliberate tap past `MODE_FLIP_GUARD_MS` lands on Stop and cancels the turn. And the hidden aliases in `_COMMAND_ALIASES` (`!yes`, `!inject`, …) are not in `COMMANDS`, so `GET /chat/commands` does not serialize them and they stay refused mid-turn — including `!inject`, which is `!steer`'s own alias.

**The IME guard is two mechanisms, because the event alone cannot answer the question.** `isImeComposing` (`$lib/platform/input`, shared with the room-name field on the chat page, which has the same hazard) tests `isComposing` and the legacy `keyCode === 229`; on top of it the composer keeps a `compositionend` timestamp and treats an Enter within `IME_COMMIT_GRACE_MS` as the input method's, because WebKit can dispatch `compositionend` *before* the keydown that confirmed the candidate, which then carries neither mark. The check is hoisted to the top of `onKeydown` rather than repeated per branch: the popover navigates on the arrow keys an IME uses for its candidate list, so it is a precondition of the whole handler. Two further non-obvious invariants. (1) **Wrap detection is measured at the single-row width, never the field's current width** — wrapping moves the controls out of the field's row, which widens the field, which can un-wrap the text, which flips it back; measuring the live width makes the decision depend on its own output and the field alternates one/two rows on consecutive keystrokes. `wrapsAtSingleRowWidth` pins the _wrapper's_ inline `flex-basis` for the measurement (the field is a flex item with `flex: 1`, so its own `width` is ignored for sizing), and height sizing is a separate pass after `await tick()` so it measures the width the field ends up with. `<svelte:window onresize>` re-evaluates, since the wrap point moves with the container. (2) **Control sizing is `em`-relative with `font: inherit` on the buttons** — a `<button>` does not inherit font, so without it the `em` sizes resolve against the UA's ~13px and the controls stay fixed while the text-size preference scales the type around them. Voice messages: `useRecorder.svelte.ts` wraps `getUserMedia` + `MediaRecorder` (webm/opus on Chrome/Firefox, `audio/mp4` named `.m4a` on iOS) and hands the result to the ordinary attachment upload — `executor._pre_transcribe_attachments` transcribes any audio attachment into the prompt, so this needs no dedicated endpoint (needs the `whisper` extra; `webm` is in `attachment_extensions`). The mic hides itself when `navigator.mediaDevices` is absent, which is what makes it disappear outside a secure context rather than failing on tap. Stored attachment names lead with a sanitized stem (`_attachment_stem`, `[A-Za-z0-9._-]` only, `Path.stem` drops any directory component) plus a random suffix, so the inbox is browsable without trusting a client-supplied filename. **Attachment chips are persisted, not just optimistic**: a turn's chip labels live on the canonical `messages` row (`messages.attachments`, JSON display names, written by `record_inbound` via `transport.display_attachment_names`) and are emitted on every user-row history/stream payload. They used to exist only in the composer's in-memory file list, so leaving a room and coming back silently dropped the record that a file was part of the turn. The names are duplicated off `tasks.attachments` (paths) deliberately — retention GCs the task row, while the transcript has to keep showing the file; a turn predating the column falls back to basenames of the joined task paths. The client supplies the display names (`attachment_names` on the send, positional, discarded wholesale on a count mismatch) because the _stored_ filename carries the collision suffix above — a basename-derived chip would read `note-a1b2c3d4.txt` where the live one read `note.txt`. Every other surface (Talk) falls back to the basename, which is also what gives a Talk-attached file a chip in web chat. **A chip is also a link to the file it names** (ISSUE-206), pointed at the same session-scoped `GET /chat/files?path=` handover described above — the user opening a file they already own, so nothing becomes public. A minted Nextcloud share link is the wrong tool here for the same reason it's the right one for handing a file to someone else. The link needs a _workspace_ path (`/Users/<uid>/…`) while the attachment is stored as a host path, so `transport.ingest.workspace_attachment_paths` translates once at ingest and the result rides the message row as `messages.attachment_paths` — a JSON array positional against `attachments`, stored beside the names for the same reason they are (the host paths live only on the `tasks` row retention deletes, so deriving at read time would make every link rot after a few days). A `null` entry means "not servable" and renders the inert chip it always was: a Talk attachment lives under `/Talk`, and a mountless (rclone) deployment has no local workspace at all. The read path re-scopes to **the caller's own** workspace rather than trusting the stored value, because rooms are shared — a co-member sees the chip but `/chat/files` would refuse them the file, and offering a link that 403s is worse than offering none. `POST /chat/attachments` returns `workspace_path` alongside the host `path` so the composer's optimistic chip is a working link immediately; without it the just-sent chip would stay inert for the whole session, since the optimistic row is deduped against the streamed echo rather than replaced by it. **Attachment intake.** Five entry points through one `upload()` sink in `Composer.svelte`: the `+` menu's three native rows (photo library, camera, document picker — shell 0.3.0), the plain file input off-shell, paste, drop, and the voice recorder. The server publishes its own limits at `GET /chat/config` (`max_attachment_mb`, `attachment_extensions`) and the composer pre-checks against them, **fail-open** — `limits` stays null until the config lands, so an unreachable endpoint never becomes a client-side refusal and the server's 413 is the backstop. The app default is 25 MB but the Ansible role deploys **100** and renders nginx's `client_max_body_size` from the same variable; splitting them means nginx answers its own HTML error page, which the client cannot parse (`uploadFromShell` tolerates that shape deliberately). `heic` is in the accepted set because that is what an iPhone photo is — the gallery picker usually re-encodes to JPEG, but a HEIC dragged off a Mac was being refused on extension. A native-picked file need not enter the page at all: with `IstotaUploader` present the shell posts it straight from disk with URLSession (absolute URL, `file` field), and otherwise the file is read in 3 MiB windows into a `File` backed by the WebKit blob store rather than the JS heap — which is what made the client-side ceiling removable. The temp copy is deleted on every path. A send with **no text** is accepted when attachments are present; `_describe_attachment_only_message` stores a descriptor as the prompt ("Voice message (see attached audio)." for an all-audio turn) so the transcript, the LLM context and the Talk mirror all read something. Relatedly, `_pre_transcribe_attachments` now **appends** a transcript rather than replacing the prompt — text typed alongside a voice memo used to be discarded. **Drafts** (ISSUE-205): unsent composer text survives leaving the room and leaving the page, held client-side in `localStorage` (`stores/drafts.ts`, one map under `chat.drafts`) rather than round-tripped through the server — a draft belongs to the machine it is being typed on, and publishing text the user has not decided to send is the one thing a draft is not. The page hands the composer a `draftKey`; without one the field behaves exactly as it did. The key is `<user>:room:<token>`, and both halves earn their place: the **token** rather than the room id because `web_chat_rooms.id` is `INTEGER PRIMARY KEY` **without** `AUTOINCREMENT`, so SQLite hands a freed rowid straight back out and a deleted room's draft would be inherited by whichever room takes its id next; and the **user** in front of it because a shared Talk room has one token across every member, so on a browser profile two people take turns using, a bare token would hand one person's half-written message to the other. The composer is mounted once and never keyed on the room, so before this a draft did not merely vanish on a tab switch — it also followed you into the next room; `switchDraft` writes the outgoing room's text down before restoring the incoming one's, which closes both halves at once, and clears the attachment chips on the way (they are not drafted, an uploaded file being server-side already, but re-picking one costs a tap while posting it to the wrong room does not undo). Writes are debounced (`DRAFT_SAVE_DEBOUNCE_MS`) with an immediate flush on every departure the component can see: a key change, unmount, `pagehide` (a reload or a close — the event a WKWebView delivers where `unload` is not) and `visibilitychange` → hidden, which is the **only** callback a backgrounded iOS app gets before the page may be discarded; without that one the exposure is 400ms of _idle_ rather than of typing, since continuous typing never reaches a debounce. **Two null-key cases that look identical from the prop and want opposite treatment.** Text typed before the room list answers is carried into whichever room lands, since there is no earlier room to attribute it to — but a stored draft always outranks it, or one keystroke during that window would destroy the draft the user came back for. A key going null _later_ means the room was deleted, archived or removed by another client, all of which leave the view on `room` with the composer mounted; there the field is cleared, because carrying that text is exactly the leak. The carry is therefore gated on a one-shot "has ever had a key" flag, not on the previous key being null. Bounded by a 30-day TTL (checked on read as well as on write, so an expired draft is never restored) and a 50-entry cap, because a room that is deleted or never revisited would otherwise leave its draft behind forever and nothing else collects it; writing an unchanged draft is a no-op so that merely _visiting_ a room neither re-serializes the map nor pushes its age out. **Two further bounds exist for a different reason — size rather than collection** (ISSUE-216). Because every draft shares one storage entry, every write serializes the whole map, so one entry large enough to exceed the origin's quota made the write fail for _every_ room at once — and `persisted.ts` swallows that, so nothing was saved and nothing was reported, which is right for a preference and wrong here. A paste is the ordinary way past it. So one draft is capped (`MAX_DRAFT_CHARS`, 64 KB, kept deliberately above the server's own `max_prompt_chars` so truncation can only reach text that could not have been sent) and the map as a whole is capped (`MAX_DRAFTS_CHARS`, 256 KB, counted in characters of draft text rather than in the code units the escaped payload costs). The per-draft cap is applied **on read as well as on write**, so a map written before the caps existed is healed on first read rather than carried back into a write at full size; the whole-map cap is applied in `prune`, where the map is assembled, and evicts oldest-first like the entry cap. `prune` takes the key currently being written and moves it to the front, because two writes in the same millisecond tie and a tie resolves to insertion order — so without it the entry a caller just wrote could be the one evicted, the single outcome no caller can work around. **`writeDraft` returns what was actually stored, and a caller holding its own copy must keep that rather than what it passed**: the composer records the submitted text to recognise it again when the send acks (`settleDraft`) and to refuse restoring it mid-flight (`switchDraft`), and comparing a full-length copy against a clamped stored one makes both tests miss — which leaves the draft behind for good and puts an already-sent message back in the field as unsent text. Neither cap makes a refusal impossible: the quota belongs to the origin, and a refusal originating anywhere else is still silent.

**Send lifecycle on the user's own row** (ISSUE-200). The composer used to append the user turn and an assistant placeholder optimistically and then POST — so a message had exactly one appearance whether or not it ever reached the backend. Worse, the one failure that was handled (an HTTP error response) was written into the *assistant* placeholder, which made "your message never left" present as "the assistant errored replying", and the failure the issue actually reports took a path with no handling at all: `fetch` **rejects** rather than resolving when the backend is unreachable, so the throw escaped an un-awaited caller, `status` was never reset off `'sending'`, and the composer stayed locked in Stop mode until reload. The ack itself already existed — the endpoint returns `{task_id, status: "pending", …}` — and is unchanged; this is entirely client-side. `sendChatMessage` now **classifies instead of throwing** (`SendFailure` = `unreachable | timeout | auth | rate_limit | rejected`, plus a `SEND_TIMEOUT_MS` bound `fetch` has none of), the row carries a `sendState` lifecycle, and `failSend` **removes** the assistant placeholder rather than repurposing it — the turn produced no assistant message. Absence of `sendState` is the settled state, deliberately with no `'sent'` member: every row rebuilt from history is settled by construction, and the ack's visible form is the pending mark clearing rather than a receipt we have no read-receipt semantics to back. Four non-obvious constraints. **Retry reuses the failed row's `cid`**, because `appendStreamedRow` dedups on `(role, task_id)` — stamping the retry's new id onto the existing row is what folds the canonical echo into it, where appending a fresh row would leave the failed one behind and show two bubbles for one message. It therefore needs the original `ChatAttachment[]` stashed on the row (`sendPayload`): the rendered row holds display names and *workspace* paths, not the host paths the POST body takes. **Retry is gated on an idle status** (and its button disabled while busy) because `runTurn` is not re-entrant — it drains the `pendingSend` echo buffer on entry and silently resets `cancelRequested`. `send` was gated by the composer's `busy`; Retry was the first entry that wasn't. **A send the server accepted but never got to report** — a client timeout, a socket dropped after the request was processed — leaves a row marked failed whose task is really running; `appendStreamedRow` reconciles that by **adopting** an echo whose `(role, text)` matches a failed, task-less row instead of appending it, matched on the body precisely so a send the server rewrote (an attachment-only descriptor, a stripped `!model` prefix) falls through to the old duplicate rather than claiming a wrong row. That heuristic is now the fallback rather than the mechanism (see `client_msg_id` below), and is what still covers rows created before the key existed. **`failSend` only sets `'idle'` when its turn's room is still on screen**: switching rooms isn't gated on `busy`, so a send failing after a switch would otherwise unlock the composer over a room with a live stream. Retry is withheld where it cannot succeed — an expired session, and any other 4xx that is a verdict on the request (409 archived, 400 over-cap, 413) — mirroring the server's own transient/permanent split. Per `web/AGENTS.md`, a *classified* send failure is **in-band** and raises no `notify()`; the two `notifyError` calls on the send path are last-resort catches for a rejection that escaped the store's own handling, where a notice beats silence. An offline outbox is deliberately out of scope and belongs to ISSUE-202, whose queue plugs into this same `sendState` union.

**One progress indicator per turn, handed over at the ack.** The grace-gated pending mark and the assistant placeholder's ack verb are the same claim at two phases of one turn, and both used to render: the placeholder was appended before the POST went out, so any send outliving the 400ms grace showed `Sending…` on the user row and `Sleuthing…` below it simultaneously — with the assistant one asserting the model was working on a message that had not reached the server. A `!command` made it deterministic rather than occasional, since it runs *inside* the request (`res.task_id == null`) and holds the POST open for the whole command; `!search` over a memory corpus is seconds of it. `runTurn` therefore no longer appends the placeholder — `sendTurn` does, immediately after `settleSend`, so the mark clears as the placeholder arrives. Pre-ack the user row owns the indicator, post-ack the assistant row does, and the order never reverses. Two consequences. There is a sub-grace window with **no** indicator on a fast send, which is deliberate: the user's own bubble has just appeared, and the alternative (the placeholder appearing first and the mark then opening above it) is the row-to-row hop this replaced. And the append is **guarded on the room**, because it now runs after an await while `messages` is rebuilt per room — unguarded it would drop this turn's spinner into whichever transcript is on screen. The guard's failure mode is the one a room switch already produced: `updateMsg`/`enqueueStream` no-op against an absent cid, exactly as they did when the switch wiped the placeholder out from under a send in flight.

**Making a failed send durable** (chat-send-durability-fixes spec). ISSUE-200 made a failed send *visible* without making it *durable*: the `sendState: 'failed'` row was the only copy of the user's text, and three paths destroyed it — the room stream's own reconnect recovery, an ordinary page reload, and the composer dropping the draft the instant Send was pressed. A network outage triggers the first two at once, and it is the same outage that produced the failure, so the user watched their message be reported as unsent and then vanish. Four corrections, three of them client-side.

`messages` is a projection of server history — `loadHistory` and `loadViewPage` both `messages.set` a list built wholly from the response — and a failed send is the one row with no server copy, identifiable without ambiguity (`sendState === 'failed'` and no `msgId`, which every server row carries). Those rows are held in a room-keyed **`strandedSends`** map while off screen, put away by `stopActive` (the single "this transcript is about to be replaced" hook, which every clear path already calls) and taken back out by `carryClientOnlyRows` on the next rebuild, re-appended at the tail because that is where they were: a failed send is always the newest thing in its room from the client's point of view. Carried into **All**, which spans every room, and not into Unread or Starred, which are filtered panes a client-only row is not a member of — those leave the held rows alone, so the room's own transcript still gets them back. A deleted or hidden room drops its entry; the row was only ever going to be re-sent into that room.

**The draft is the second copy, and is dropped on the ack rather than on submit.** Nothing in the store survives a reload, so the stored draft is what restores the text into the composer when the row itself is gone — a downgrade from Retry to a re-send with no retyping, and the accepted outcome until ISSUE-202. The signal is **`sendSettled`** on the session — a counter *and the room it acked* — bumped by `settleSend` (which already runs at the moment the POST acks, ahead of everything downstream that can throw) and watched by the composer through a prop; the page translates the room into a draft key, because the composer owns the key's shape and passing a callback *into* it for it to call itself would be circular. `submit` writes the submitted text under the key rather than merely leaving it — a fast submit beats the debounce and would otherwise store nothing, or a stale prefix — and `flushDraft` holds it through the unsettled window, since every departure (a room switch, unmount, `pagehide`, `visibilitychange`) flushes an emptied field and would drop exactly the draft this exists to keep.

**Three constraints on that, each of which was a proven defect first.** The unsettled sends are a **map keyed by draft key**, not one slot, and the ack carries an identity: two sends can be open at once (leaving a room resets `status` to `'idle'`, which un-gates the composer), and with a bare counter the first ack dropped the second room's draft while its own POST was still open — destroying the only copy of it, which is the exact failure this whole section exists to prevent, reintroduced in a second place. `switchDraft` **refuses to restore a message still awaiting its ack**, even though it is stored under that key: putting it back in the field shows an already-sent message as unsent text, one Enter from being sent twice, and the ack then reads it as newly typed and declines to clear it, so it stays there for good. And the drop is withheld when something *has* been typed since — emptiness is a sufficient test for the on-screen room only because of the rule before it.

**`client_msg_id` moves retry identity to the server** — one nullable column on `messages`, a partial unique index on `(room_token, client_msg_id)`, and an empty string coerced to `NULL` on the way in, following `location_pings.client_id` (an empty string is a valid unique key and would collapse a room's whole history onto its first send). The client mints one per message (`crypto.randomUUID`, absent when the page is not a secure context, in which case the endpoint behaves exactly as it did before the field existed) and **reuses it on every retry**; `record_inbound` checks it after resolving the room and before creating anything, so a repeat resolves to the first turn and no second task, message row or Talk mirror exists (`_mirror_web_turn_as_user` reads the stamp it left as its own guard). The body-match adoption above stays as the fallback, because it is a heuristic that already fails on any send the server rewrites, and because rows predating the key have none. ISSUE-202's outbox needs the key regardless.

Three properties of that key are load-bearing and none is obvious. The lookup **returns the sender rather than filtering on it**: a room is shared and the key is arbitrary client-supplied text, so filtering would make a co-member's reused key miss and then collide on the room-scoped index, while ignoring the sender hands them a task `_authorize_task_access` will refuse them — instead the send **gives the key up** and proceeds without idempotency, which it is an optimization rather than a requirement. The endpoint **rejects an over-long key rather than truncating** it, since truncation changes the identity and two keys sharing a 64-char prefix would silently resolve to one another. And the replay deliberately **does not filter on task status**, though the spec's wording said non-terminal: a late replay would then find nothing, create a task, and take a `UNIQUE` violation on the insert. **A `!command` is the documented gap** — it runs inside the request and returns before the key is ever consulted, so a timed-out `!steer` or `!retry` cannot be re-POSTed safely; the client withholds Retry for any `!`-prefixed body rather than guessing which commands repeat cleanly.

Two pieces of per-room state were also not scoped to their room. An **upload in flight across a room switch** put its chip in the new room, and sending from there posted the file to the wrong one: `upload()` is async and appends with no notion of where it started, while `switchDraft` clears the list synchronously and cannot see a promise. A monotonic **`uploadEpoch`**, captured on entry and compared before each write, drops a stale result — including the counter decrement, since the switch has already reset it to 0 and a stale decrement would drive it negative and leave the composer reporting an upload forever. The file does reach the server and is orphaned there, the same outcome as closing the tab mid-upload. And the module-level **`pendingSend` echo buffer** survived a room switch that reset `status` to `'idle'`, defeating both gates the drain rested on (`send`'s `busy`, `retrySend`'s idle status): a second send then released the first's frames before its task id was stamped, showing two bubbles for one message. `runTurn` now holds its own buffer and drains only that one, and `stopActive` **abandons** the slot rather than draining it — those frames are for a room the user has left, whose transcript `loadHistory` rebuilds from the server on the way back in. The drain on the way *in* is a safety net rather than a step, and only because the third way into an overlapping same-room turn was closed with it: `Cmd/Ctrl+Enter` called `submit` without consulting the send/stop mode, so holding it started a second turn in a room that already had one. A key that sends now does nothing while the button is in Stop mode, rather than being repurposed as Stop — a rule the bare Enter inherited when it became a send key, which is what keeps holding *it* down from reopening the same hole.

**Per-turn message actions** (ISSUE-210). One action row under each message body — copy, star, delete, left to right in ascending consequence — revealed on hover or on tap, keeping its layout box either way so revealing it never reflows the transcript. Copy takes `messageCopyText`: the turn's prose groups only, tool traces excluded, as **markdown source** rather than rendered HTML (which is why a fenced code block needs no copy button of its own). It is withheld mid-stream, because half an answer is not an answer; the star is not, because it marks the row rather than the text. **Delete is `DELETE /chat/messages/{message_id}` → `db.delete_message`** and it is _room-wide_, not per-user: the `messages` row is gone for every member, and authorization is membership (`db.is_room_member`), not authorship — the opposite of stars, which are per-user in `message_stars`. Unknown id and non-member both return **404**, deliberately indistinguishable so neither becomes an id oracle for the other (the same rule the star endpoint follows); a turn whose task is still in flight returns **409**, because the scheduler writes the assistant row at completion and the delete would silently undo itself. It is a hard delete, not a tombstone: every read path would have to learn to filter a tombstone, and the row would still occupy its slot in the `(room_token, role, task_id)` unique index, so re-running the turn would collide with a message the user believes they removed. It touches `messages` and `message_stars` only — never `task_events` or `tasks` (unlike a room delete) — and leaves `room_read_state` alone, since a read cursor is a high-water mark rather than a reference. **The `message_deletions` ledger exists because the room stream has a second cursor.** That stream tails `messages.id > cursor`, and a vanished row can carry nothing, so deletions get their own monotonic `message_deletions.id`; the `message_deleted` frame therefore carries no SSE `id:` (that cursor belongs to the message tail) and instead rides its cursor _inside_ the payload, which the client passes back as `since_deletion_id` on both `/chat/stream` and `/chat/events` — without it a reconnect after a delete silently resurrects the message. Like the message tail, the deletion cursor advances to the max id **scanned**, not the last one sent, or a client sitting behind someone else's invisible deletions never catches up and the O(1) gate stops short-circuiting. Rows are pruned after a fixed 30 days in `run_cleanup_checks` (`_MESSAGE_DELETION_RETENTION_DAYS`, deliberately not a config knob — the row is tiny and nothing about it is worth tuning). Propagation into a bound Talk room is best-effort and fire-and-forget, trying the user's own OAuth token first and the bot's second, because Talk lets only the author or a moderator delete and a mirrored user turn is authored by the _user_ while a reply is authored by the bot — so a 403 is the ordinary "not yours", not an error. A Talk failure never fails the web delete, which has already committed. Client-side the removal is **pessimistic**, unlike `toggleStar`: a row removed and then restored would reappear mid-transcript after the user watched it go.

**A `role='system'` row carries the same action row a turn does**, inside its content column and under its card. It was withheld for a while on the reading that a notice is not a turn — no author, nothing on the other side of it — but the server already supports every one of the four on a system row, and the argument was really about where the row sat: before the system branch took the gutter + content columns, the card began at the row's own edge and the action row under it lined up with nothing. Copy takes the markdown body a `!command` wrote, which is the whole reason a notice renders as markdown; `DELETE /chat/messages/{id}` has always accepted a system row's id; and a reply cites it through `db.get_reply_target`, which reads any `messages` row, with `_ensure_reply_parent_in_history` already naming a `role='system'` parent as one of the three cases that correctly fall through to the snapshot alone. Replying to an alert to ask what caused it is the ordinary thing to want. The one carve-out that stands on its own is **search results** (`!message.searchResults`): that row renders cards rather than markdown, so there is no source worth copying. The gating is otherwise the derived values unchanged, so a system row and a turn cannot disagree about what a durable id buys.

The row's **placement inside `.content`** is load-bearing rather than incidental — `.cmd-row` is a two-column flex row, so a third child would sit beside the card instead of under it. `.cmd-output` also shares one uniform `var(--space-2)` padding with `.external` and `DraftCard`, the other two filled blocks a content column holds: they stack under one another in the same column and their text has to start at one inset.

**Reply to a message.** A reply is an identified parent plus a rendered citation plus a prompt frame, and the three have to agree. The parent is addressed by canonical **`messages.id`** — the same id star and delete use — carried on the send as `reply_to_msg_id` and stored on two nullable columns: `tasks.reply_to_message_id` for the executor, and `messages.reply_to_message_id` so the transcript can still render the turn as a reply after retention deletes the task row. That duplication has its precedent in the same table (`messages.attachments` exists for the same reason), and there is deliberately **no foreign key** on the self-reference: keeping a dangling id is what lets a reply to a hard-deleted message say so instead of silently becoming an ordinary message.

**The namespace split is the whole reason this is a new column** rather than a reuse of `reply_to_talk_id`. That one resolves through `talk_message_id`/`talk_response_id`, and in a Talk-bound room — which is most of them, since web rooms promote and Talk rooms surface in web — canonical ids and Talk ids are both small integers in the *same* room. A canonical id stored there resolves to whichever Talk turn happens to share the number, the executor injects that turn as the message being replied to, and nothing at any layer notices. So `record_inbound` takes `reply_to_canonical_id` alongside the existing surface-native `reply_to_message_id`, and the parameter whose name matches the column is not the one that writes it — a collision worth stating so nobody helpfully merges them. `_ensure_reply_parent_in_history` resolves the canonical id first (through `db.get_reply_parent_task_by_message_id`) and falls back to the Talk lookup, so a task carrying both — a Talk reply whose canonical id was derived from it — takes the more precise of the two.

**The parent snapshot is derived server-side, never sent by the client.** The POST carries the id and nothing else; the server reads `messages.body` and caps it at the same 1000 characters Talk uses. A client-supplied quote would be text the model reads as an authoritative record of what it previously said, forgeable by anyone who can call the endpoint, and there is no reason to accept one for a row we hold. A parent in another room or an unknown id **refuses with 404**, indistinguishable, and creates no task — the same rule star and delete already set so no endpoint becomes an id oracle for another. Refusing rather than dropping the citation is the deliberate call: a reply body routinely depends on its referent ("yes, do that"), so a reply delivered without it is not the message the user wrote and produces a confidently wrong answer instead of a visible failure.

**Two prompt mechanisms, doing different jobs.** `build_prompt` renders the snapshot as a blockquote in the **request** section, unconditionally — the user's message is a response *to* that text, and `## Conversation context` is an ordered record where "this specific one" is not an entry. That frame replaced the old `(In reply to: …)` context fallbacks, which fired only when history came back empty and so vanished exactly when the marker was most needed; keeping both quoted the same 1000 characters twice. Separately, `_ensure_reply_parent_in_history` force-includes the parent's *whole* turn and marks it must-survive-triage, which is what saves a 5000-character parent from its own snapshot. Three cases fall through to the snapshot alone, all correctly: a `role='system'` row (no task), a turn retention deleted, and a turn that failed, was cancelled or is still running.

**Reading and rendering.** Every message dict gains an optional `reply_to` (`{msg_id, role, excerpt, deleted}`, or `{msg_id, deleted: true}`), emitted by all three producers — the per-room spine, the cross-room dict the aggregate panes and the live stream share, and the dev mock — because a reply that renders as a reply in one view and not another is worse than one that renders in neither. The parent is joined live (`LEFT JOIN messages p ON p.id = m.reply_to_message_id`, a primary-key lookup) rather than snapshotted, which is safe because nothing in the stack edits `messages.body`; a NULL join against a non-NULL id *is* the deleted case. The excerpt is capped at 200 characters — a **display** bound distinct from the prompt snapshot, and the composer's staged chip is capped at the same number so the chip and the reloaded quote cannot diverge for the life of a session. `buildHistoryMessage` is the single place the field becomes a row property, which is what keeps history, the aggregate panes and the stream in agreement.

**The refusal carve-out.** A 404 on a send that carried a citation classifies as its own `SendFailure` (`reply_target_gone`) — on the *intent* rather than on the error sentence, which is prose — and takes a recovery no other failure takes: the optimistic row is removed and the text and attachments go back to the composer. That contradicts the rule ISSUE-200 set, that a failed send never repopulates the box. The carve-out is narrow and earns itself: this is a synchronous pre-flight rejection of the citation rather than of the message, the offered Retry cannot work (it would re-POST the same dead parent), and no time has passed in which anything else could have been typed. Leaving a permanently un-retryable failed row is the strictly worse reading of the same rule.

**Talk in both directions.** A web reply into a Talk-bound room posts as a real Talk reply, using the parent's own Talk id out of the `external_ids` ledger (`db.get_message_external_id`, the value-returning sibling of the yes/no check); a parent that never reached Talk degrades to a plain post rather than being withheld. Inbound, `record_inbound` maps a Talk parent id back to a canonical id (`db.find_message_by_external_id`) and fills the canonical column too, so a Talk-origin reply renders as a reply in web. That lookup is **room-scoped** — a Talk message id is per-conversation — and it scans the room's stamped rows, since `external_ids` is a JSON blob; the same shape `message_has_external_id` and `room_max_talk_synced_message_id` already use, bounded by the room and run once per inbound reply.

**Client-side details worth keeping.** The Reply button is fourth in the turn action row (copy, star, reply, delete — ascending consequence, delete terminal), gated on a durable `msgId` like star and delete, and additionally withheld in the aggregate panes, which have no composer for a staged reply to go to. The touch overlays tile at the button *pitch* rather than at a flat 44px, so a fourth button needs no change to the formula. Escape clears the composer chip only **after** the autocomplete popover has declined it — the popover owns that key, and a chip taking it first would dismiss the citation while the user was closing a menu. A staged reply is part of the unsent message, so it rides in the draft as an optional `replyTo` (no storage migration: an absent optional field reads back absent), and an emptied field drops both — a citation is not itself a message. A `!command` clears the chip on send, since it returns from inside the request with no task for a citation to attach to. `MessageReply.deleted` is optional and truthy-tested: the composer stages without asserting a state only the server knows.

**App shell and caching.** There is no service worker: static responses carry two cache classes — hashed `_app/immutable/` assets immutable for a year, everything else (the HTML shell, `version.json`, the manifest, icons) `no-cache` and revalidating. Sending neither let an installed home-screen app pin the shell indefinitely and then request hashed chunks the server had deleted. A new build is surfaced rather than forced: SvelteKit's version poll drives a toast with a Reload button (a tap, because a reload discards a half-typed message), re-checked on `visibilitychange` since the poll timer is throttled in a background tab and stopped in a suspended PWA. The web unit passes `--timeout-graceful-shutdown` for a related reason — `GET /chat/stream` is session-lived and exits only on client disconnect, which server shutdown does not trigger, so a restart with any browser tab open used to sit out the full stop timeout and die on SIGKILL. Docker's web service has no equivalent flag.

Knobs under `[web.chat]`. Frontend engine in `web/src/lib/stores/chat.ts` (SSE with polling fallback) + widgets in `web/src/lib/components/chat/`. **Body render model**: an assistant turn is an ordered list of `text`/`tool`/`thinking`/`notice` segments (`segments.ts`) — `notice` is an out-of-band statement about the *run* rather than its content (today only a `brain_fallback`, ISSUE-278), rendered as its own warn-tinted `.banner warn` group in true segment order, never coalesced into a chip, and excluded from `messageCopyText` alongside the tool trace. It is deliberately not counted as content by the streaming cue in `Message.svelte`: a notice is a static sentence and the fallback run after it is the long part of the wait, so the pulsing dot and ack verb stay up under a turn whose only groups are notices. It is also **live-only** — the `task_events` row survives pruning and an SSE resume, but `_trace_segments` / `historySegments` rebuild a finished turn from `execution_trace`, which carries no notice, so a reload shows the answer without it; `renderGroups` reduces it to interleaved render groups — substantial prose blocks (trimmed length ≥ `SUBSTANTIAL_TEXT_CHARS`, mirrors the backend gate) render as prominent markdown in true order, consecutive tools coalesce into one `ActivityTrace` chip, short lead-in narration + reasoning are dropped, and the trailing text is always the answer. This keeps a meaty intermediate block (analysis the model wrote, then acted on) visible as its own prose block instead of vanishing when the next tool settles it — the live stream and a reloaded-from-`execution_trace` turn build the same groups. Not a Talk replacement — an in-app companion. Web chat is also a _delivery_ surface (ISSUE-121): alerts, the verbose execution log, and notifications routed to `web` are appended to a room as unsolicited system messages (distinct from task-backed turns, written into the canonical `messages` store as `role='system'` rows) and merged into room history by time. See `WebTransport` in the Transport abstraction section. **Unread indicators**: the sidebar bolds a room name and shows a count chip for rooms with unseen messages. Counts are server-computed in the `/chat/rooms` payload (`db.count_unread_messages` — `messages` past the per-user/per-surface `room_read_state` cursor, excluding `role='user'` so your own/Talk-mirrored turns don't ring your own room); `db.initialize_room_read_state` seeds a freshly-surfaced room's cursor to its current max so a backlog doesn't read as unread. Opening a room (or `POST /chat/rooms/{id}/read` → `_chat_mark_room_read`) advances the cursor to the room's newest message; the client persists on open / stream-append / stream-settle / `visibilitychange` (visibility-gated). The active room is held at 0.

**Pending confirmations are a banner, not a card in a room** (ISSUE-241). The in-room `ConfirmationCard` covers a turn the user started here; it cannot cover the one they did not. An inbound email held by the untrusted-sender gate has its transcript mirror deliberately withheld (`suppress_transcript_mirror`) until the answer, so there is no row to hang a card on. That withheld row is also what keeps it out of the room history query: `_AUX_ROOM_SCOPE` admits an email task only through a mirrored `role='user'` row, and admitting a held one would publish `tasks.prompt`, which for a gated email is exactly the untrusted body the gate exists to hold back. (Since ISSUE-247 the exchange *does* have a room — resolved from the routing — so the withheld mirror is the whole of the argument; the old "its token belongs to no room" half no longer holds.) `GET /chat/confirmations` is the API equivalent of `handle_confirmation_reply`'s Path C: every `pending_confirmation` task owned by the caller, oldest first, carrying the bot-composed prompt plus the sender / subject / routing method off `processed_emails` and no message body. `PendingConfirmations.svelte` renders one card each above the transcript, in every view — an aggregate pane is still where the user is looking — and Confirm / Discard hit the existing `/chat/tasks/{id}/confirm` and `/cancel`. Every field on the card is attacker-supplied text rendered into a text node. Three things about the wiring: the banner is **seeded on entry** as well as polled with the 30s rooms reconciler, since a gate parked before the tab opened has no stream frame to arrive on; removal is **pessimistic** (a card that vanished and came back would read as the question being asked twice) but the row is **kept on a failed answer**, because the card is the only place that question is visible here; and a failed *poll* raises no notice, being nothing the user did. Answering is also reachable without the banner at all — `!confirm <task-id>` works from the composer on any surface.

**A held outbound draft is a card under its own turn, and the opposite call from the banner above.** `DraftCard.svelte` renders one held email — the recipients, the subject and the **whole** drafted body, as a text node under `white-space: pre-wrap`, never markdown. That is the single promise the feature makes: approving sends exactly the bytes that were read, so a card that abbreviated or re-rendered would break it. It goes **inline under the assistant row** whose task composed it, which is where the drafted text and the "this task also created a calendar event" summary read together — keyed on the assistant row alone, since a turn's user and assistant rows share one task id and keying on the id would draw every card twice. Everything else falls to a list above the transcript beside `PendingConfirmations`: a task with no room (a cron job mailing an external address), a turn paged out of view, a turn whose task row retention deleted. The fallback is what makes the placement safe — no draft can be hidden by failing to find a home. The actions summary is **read-only**: reversing a calendar write needs a per-task ledger of reversible operations, which `actions_taken` (rendered strings, not structured ops) cannot back and which is its own feature.

Three states the card must be able to show, and none of them existed in the Stage 5 payload. A row stuck in **`sending`** — the process died between the claim and the finalize — was filtered out by every `status='pending'` producer, so the one state that needs "check your Sent folder" was the one state invisible on the whole web surface; `outbound_drafts.open_for_user` carries `pending` and `sending` both, and the card offers *no* action on it, since nobody can know whether the mail went out and one of the actions would send it twice. A row whose stored JSON does not parse is reported as an **id in `DraftListing.unreadable`** rather than raising: strictness is right inside `release` (sending to a recipient set we cannot read is exactly the thing to refuse) and wrong in a listing, where one bad row 500'd `GET /chat/drafts` and emptied the stream frame for the other nine. It is named rather than dropped, because held mail that silently disappears is mail the user never hears about — and it stays discardable, which is why ownership checks and `discard` now read through `outbound_drafts.identity` (the two plain columns, parsing nothing). Approving one still refuses. And the drafts frame is **byte-budgeted** (`_DRAFT_FRAME_MAX_BYTES`), unlike the message tail's per-row cost: a body is capped only by the 200k PATCH ceiling, the whole set rides *every* frame, and every open connection pays — so past the budget a draft rides as a stub carrying id, room and status, and the card fetches the full row from `GET /chat/drafts`, which is deliberately not budgeted. The first draft always rides whole, or the budget could make the frame useless exactly when it matters.

Client-side, **a 409 is read against the action, never on its own** — the same status means opposite things to Send and to Discard, and getting that wrong is how a refusal comes to look like a success. "Already discarded elsewhere" *settles* a discard (the card goes, silently, since that is what was asked for) and *refuses* a send (the card goes, but with a notice saying nothing was sent — dropping it quietly would give the user who pressed Send exactly the feedback a successful send gives). `sending` keeps the card on either action and says the mail is in motion. `sent_unrecorded` never offers a retry. Two supporting rules make that readable: **every route that can 409 carries `state`** — the discard route did not at first, and the client's default of `gone` turned "we don't know" into the drop-it-silently branch — and a missing `state` now stays `undefined` and keeps the card, so a future route that forgets fails safe.

**The optimistic removal is held down only where the server accepted the answer.** `_drafts_snapshot` runs on a worker thread on the room-check tick, so a read taken a moment before `release` committed its claim arrives *after* the answer and puts the card back with a live Send button on mail already going out. A short window (`ANSWERED_SUPPRESS_MS`) filters those ids out of an incoming snapshot. It is deliberately **not** applied on a refusal: there the row may still be held, and suppressing would hide answerable mail for the window's whole length — so those paths drop the card and let the re-read be the authority, which puts it back if it is still there.

The set is **seeded on entry** for a reason the confirmations banner does not have: the frame is a *diff* against a baseline seeded `[]`, so an instance whose set has not changed since the connection opened pushes no frame at all. `recoverStream` refreshes it too, metadata-only recoveries included — a backgrounded tab is exactly where an approval given on the phone would otherwise leave a card up for a message already sent. `refreshDrafts` **coalesces concurrent callers onto one request**, because a frame that stubs K drafts makes K cards each ask for the full row against an endpoint that is deliberately un-budgeted; without it the frame's byte budget is "saved" by fetching every body K times.

**The two placements are a prop, not two components** (`placement: 'turn' | 'banner'`), and `banner` is a different **shape** rather than a shorter one. The reader arrived at the inline card by scrolling to it and the body is what they came for, so `turn` is the full card: the fields grid, the body at a 700-character preview, the actions list. The banner is chrome nobody asked for, pinned above the transcript beside `PendingConfirmations` and competing with the transcript for the top of the pane, so `compact` is four rows — the head, recipients and subject folded onto one line, one clipped line of body, and the buttons — expanding to the full card in place and back.

**Shortening the preview was tried first and was not enough**, which is the part worth keeping. At 180 characters a body carrying a blank line still rendered as two paragraphs, because the block is `white-space: pre-wrap` and honours the break; the fields grid still spent a row each on To and Subject; and the actions list and button row were rows of their own. Two held drafts still took most of the pane (360px, scrolling, with the buttons clipped below the fold). The compact card is 145px. So the peek **collapses whitespace** (`body.replace(/\s+/g, ' ')`) — it is a label for the held message, not the message — and clips in **CSS** rather than at a character count, since the card's width varies with the pane and a count that fits at one width is wrong at another. That is also what keeps a stack of drafts off `.loose-drafts`' `max-height: 40vh`, which otherwise turns the list into a scroller at the top of the pane.

Compact hides **detail, not decisions**: Send, Edit and Discard are all on the compact card, because answering without opening anything is the point of it. `editing` is excluded from `compact` — the textarea is the full-height writing surface the card exists to offer, and there is no compact way to write a reply — and the `unreadable` / `truncated` / `sending` branches are checked ahead of it, since none carries a body to peek at and a stuck row's card is a "check your Sent folder" notice rather than a decision. Truncating is a **reading** decision and never an abbreviation of what is sent: `Send` and `Edit` both operate on the full stored `body`, never on `shownBody` or `peek`, and the body is a text node that is never re-rendered — so the feature's promise is about transformation, not about how much is on screen at once. The component's docstring used to say a card that abbreviated would break the promise, which its own `PREVIEW_CHARS` had already contradicted.

**The `--chat-body-max` cap travels with the slot, not the card.** Inline the card is one block in a turn's content column and has to stop where the prose body above it stops, so the cap is written in `Message.svelte` on `.content > :global(.draft-card)` — beside the top spacing, which is scoped there for exactly the same reason. On the component it also applied in the banner, where the card is pane chrome sitting beside a `PendingConfirmations` card that spans the pane: the draft stopped **134px** short of the confirmation directly above it (900px against a 1034px card in a 1060px pane), at the one width the two most obviously want to agree on. `.pending-card` sets no `max-width` and never did; both banners take `.pending`/`.loose-drafts`' shared `var(--space-2) var(--space-3)` inset and now come out identical. Pinned in `DraftCard.svelte.test.ts` against the **source**, not a computed style: jsdom does not apply a Svelte component's own `<style>`, so `getComputedStyle(card).maxWidth` reads `none` whether the rule is there or not — vacuous in the one direction that matters. Note also that the existing "no margin on `.draft-card`" assertion regexes the raw file, comments included, so prose inside that rule must avoid the word.

Two things about the stub path that were defects first. The card's "I need the full row" latch **resets when the row stops being truncated** rather than being once-per-instance: the frame is diffed against the server's own baseline, which the client's refetch does not touch, so the same draft is stubbed again on the next frame that changes anything — and a permanent latch left the card on "Loading…" forever with no way to answer the mail. And `_draft_stub` carries **`task_id`**, the field that actually places the card; without it a stub moved its own card out of its turn into the fallback list and back as the full row landed, which destroys and recreates the component and throws away a correction being typed.

**A turn that arrived from outside the room says so, and the reader decides how much of it to read.** The inbound mirror writes an external contact's mail as a canonical `role='user'` row, and `origin_surface` — which has always been on the row — was dropped on the way out: a stranger's message rendered as an ordinary user bubble with an unfamiliar name in it, full body, no provenance, no collapse. Both SQL fragments now select it (`db._CROSS_ROOM_COLUMNS` and `web_app._SPINE_COLUMNS`, deliberately both, since they exist as shared pieces precisely so the room tail and the history query cannot disagree), and `_user_row_display` — the one builder both producers go through — publishes `origin`. `subject` rides along from the same place, because the wrapper the display body strips is where it lives and a collapsed turn shows it in place of the body; a prompt that parses to an **empty** body publishes an empty `text` rather than the wrapper, or an attachment-only mail previews as `<email_metadata>` and expands to an instruction addressed to the model. The subject is capped (`_SUBJECT_MAX_CHARS`) for the reason the reply excerpt is truncated in SQL: it is an attacker-supplied header of no fixed length, and this dict rides the byte-budgeted room-event stream.

**`origin` needs two conditions and the second is the one that is easy to miss.** The surface must be outside `ROOM_SURFACES` (`talk`/`web`), *and* the row must carry an `author_label`. Surface alone was the first cut and it was wrong in the mirror image of the case it was protecting: a user mailing their own plus-address writes an `origin_surface='email'` row that is nonetheless their own words, so the reader got the stranger's treatment applied to themselves — "External email" over their own message, collapsed. `transport.ingest.resolve_author` already draws exactly this line, setting `author_label` **iff** the envelope sender is not one of the user's own addresses, and it is safe to gate on because it is never absent for a genuine outsider: an unclassifiable sender falls back to `UNATTRIBUTED_SENDER` rather than to nothing. Absence of `origin` therefore means "from inside this conversation" for a colleague's Talk turn and for your own forwarded mail alike. Client-side the *label* is derived rather than hardcoded (`External email` / `External message`): the server's contract is the surface predicate, which resolves to email today only because `TRANSCRIPT_SURFACE_FILTER` limits user rows to web/talk/email, and nothing enforces that coupling across the two files.

**The wrapper the display body strips has to be the wrapper the poller wrote (ISSUE-274).** `email_support.parse_email_prompt` is what turns a stored email turn into something a human reads, and returning `None` means "render verbatim" at its one call site. It anchored the closing tags at column 0; the builder in `transport/email/inbound.py` is an f-string nested eight levels deep, so it emitted `\n        </email_metadata>`. The parser therefore matched nothing on every real prompt it was ever handed, and the transcript showed the user the wrapper tags, the untrusted-input guard and the trailing instruction addressed to the model — in a bubble labelled with their own name, which is the exact mislabelling the strip exists to prevent. Both halves had tests and both hand-wrote the same unindented fixture the builder did not produce, so the guard now is the **pairing**: `tests/test_email_prompt_wrapper_render.py` polls a message and feeds the resulting prompt straight to the parser. The fix is both-ended. The builder writes flush left, which is also less prompt noise on every email task. And the parser tolerates leading whitespace on the closing tags and header lines, because the indented rows are in `messages` permanently and a display fix that only helps future mail leaves every stored turn raw. `[ \t]*` rather than `\s*` only because the run exists to absorb the historic block indent; both spellings keep the tag line-anchored, since the `\n` before the run is mandatory either way.

**Making the parser work is what made the wrapper forgeable, and that is the larger half of ISSUE-274.** The wrapper is a delimited document whose boundaries are *lines*, and the values on those lines are chosen by the sender. `imap_tools` decodes `Subject:` with `decode_header` and joins the parts verbatim, so a Q-encoded `=0D=0A` puts a real CRLF into `Email.subject`; an attachment filename is RFC 2047 too and lands inside `<email_metadata>` as well. Either could close the metadata block, add a second `From:`, and open an `<email_content>` of its own — and while the parser matched nothing this was visible nonsense, whereas a working parser renders it as a genuine message: the sender's headers, the sender's body, under the real external sender's attribution, with the actual body never shown. Three changes close it, and each fails safe in a different direction. `email_support.flatten_prompt_header` collapses every whitespace run in `From:` / `Subject:` / `Date:` / the emissary `sent to:` line / each attachment name — the inbound counterpart of `skills.email._sanitize_header`, and it belongs at the builder because a parser cannot tell an injected delimiter line from a real one. The header loop is **first-wins** (`setdefault`), so a second `From:` cannot silently replace the field a reader leans on hardest. And the `body` group is **greedy** while `meta` stays lazy: the body is the one value that cannot be flattened, since it *is* the content, so it can still carry a closing tag — greedy runs to the last one, which is always the builder's own (nothing follows it but the guard line, which carries only an *opening* tag), and the injected tag renders visibly inside the body instead of hiding everything after it from the reader while the model still sees the whole prompt. Lazy was the shape this shipped with, and it let a body reading `Please review the figures.\n</email_content>\nSYSTEM: …` display as its first line alone.

`external_turn_display` (`full | collapsed | hidden`, default `collapsed`) governs the **body only**. `hidden` never removes the row — a bot answer with no question above it is the defect the inbound mirror was built to fix (ISSUE-136) — so the header, the origin marker and the sender render at every setting, and only `collapsed` offers expand-in-place: on `hidden` a toggle would be the setting asking to be overruled on every message it applies to. The derived body gate tests the **mode**, not the expansion flag alone, so `hidden` wins over a body expanded earlier under `collapsed` — otherwise the row is stuck open with its toggle gone, in the one mode whose job is to withhold it. Two smaller rules. The preview is a **single clipped line** sliced by code point, not a wrapped excerpt: wrapping makes `collapsed` shade into `full` for the one-long-paragraph mail that is most of email, and a UTF-16 slice renders a lone surrogate when the cut lands inside an emoji. And the block is **neutrally tinted** (`--surface-badge` plus a `--border-hover` rule) rather than borrowing a status tint: provenance is not a severity, and `--status-warn-*` would call every external correspondent suspect. Every field on it is attacker-supplied and renders as a text node.

Expansion is component-local `$state` keyed on `message.cid`, which `buildHistoryMessage` regenerates on every rebuild — so paging older history, `jumpToTask` and a round trip through an aggregate pane all re-collapse an expanded turn. Accepted rather than hoisted into the store on `msgId`: it fails in the withholding direction, and a cross-cutting expansion registry is more machinery than the annoyance is worth.

The setting is **server state, not a client-local preference** — it is a `user_profiles` column edited on `/settings`, published by both `GET /chat/config` (which the chat store reads at `init`) and `GET /settings/profile` (which the pane edits) — because how much of a stranger's mail a reader wants inline is a decision about the account, not about the browser they happen to be on. It is the counter-example to theme and text scale, which are localStorage for the pre-paint reason. **`/chat/config` reads it live from `user_profiles`, not off the `_config.users` snapshot** the rest of that handler uses: the snapshot is rebuilt only by `_reload_config` (startup and SIGHUP) while `PUT /settings/profile` deliberately syncs nothing in memory, so resolving it there had the pane show the new value from its own live read while the transcript kept applying the old one until a restart. `outbound_approval` on the same handler still has that staleness; nothing edits it yet, and closing it means moving `effective_policy` off the snapshot too. The PUT **rejects an unrecognized value** rather than folding it onto the default, since a stored string the code ignores would leave the pane rendering a selection nobody made; the client normalizes anyway (`stores/externalTurns.ts`) for the hand-edited row the route never saw. That normalizer sits beside the store rather than on `$lib/api` for a reason worth not rediscovering: eleven store test files `vi.mock('$lib/api', …)` wholesale, so a *function* exported from there is `undefined` in every one of them — the type is erased and can stay.

**A bare "yes" answers from the composer too, and the exchange is durable** (ISSUE-243). The Talk poller had intercepted a confirmation reply before task creation since it was written; web had no equivalent, so "yes" fell through to `_chat_create_web_task` — which room-scoped-cancels pending confirmations on a new message, so a same-room gate was **cancelled by its own approval**, and a cross-room email gate got a task whose prompt was the word "yes" while the question kept ticking toward its timeout. The parse, the three-path lookup and the ack text now live in `confirmations.py` (`parse_answer` / `resolve` / `apply_answer` / `ambiguity_listing`) with the approve/decline verbs, so the Talk poller, the web POST and `!confirm` cannot drift.

**Falling through is required, not a fallback.** "yes" is an ordinary reply to a question the bot asked in prose, so `parse_answer` matching must not by itself suppress task creation — only `resolve` finding a parked question may, which is why `_chat_answer_confirmation` returns `None` rather than a string when nothing is pending. The match is **exact against fixed word lists** (surrounding whitespace stripped, case folded, and deliberately nothing more — collapsing *internal* whitespace would make `"do  it"` an answer, and every widening here widens the set of ordinary messages swallowed as an authorization decision) rather than a prefix test: a message that merely starts with "no" is a message, and swallowing it loses it. The intercept is also skipped for an **attachment-bearing** send — the file is the message whatever the caption says.

**The ordering is not cosmetic.** It sits after the `!command` block and *before* `_chat_create_web_task`, because an answer that reached that helper would cancel the question it is answering. Same reason the Talk poller orders its own check ahead of `ingest_message`.

**The exchange is written to `messages`, unlike every other inline result.** `confirmations.record_exchange` stores the answer as a `role='user'` row and the ack as `role='system'`, both with `task_id=NULL` — the `!steer` shape, since the `(room, role, task_id)` unique index reserves the per-task user slot for the original prompt and LLM-context reconstruction joins on `task_id`, so a NULL row is display-only and never re-paired as a phantom turn. A confirmation is an authorization decision and "did I approve that untrusted email?" deserves an answer after a refresh, which the `!command` inline-only precedent does not give. Existence-only like every other room write, so a synthetic email-thread token no-ops rather than minting a room. `!confirm` records through the same helper, and so does the Talk poller — which is what puts a Talk-given answer in the web view of that room. **The reverse does not hold**: a web answer writes `messages` rows and posts nothing to Talk, and unlike an ordinary web send it never reaches `_chat_create_web_task`, so neither `_mirror_web_turn_as_user` nor the `output_target="room"` mirror leg runs either. Answering in web leaves the Talk view showing the question alone. That asymmetry is inherited (Talk renders from Nextcloud, not from the canonical store) rather than introduced here, and closing it means giving the answer a real Talk post.

**Three things deliberately record nothing**, because none of them decides anything: a usage error, the ambiguity listing, and an answer given on a surface the transcript does not render. The ambiguity listing is the one worth naming — it is also the only branch that *consumes no question*, and the intercept returns before `_chat_create_web_task` where the rate limit lives, so recording it would let a client loop append transcript rows without bound. `_TRANSCRIPT_SURFACES` covers the third: `TRANSCRIPT_SURFACE_FILTER` renders a `role='user'` row only for `web`/`talk`/`email` while every `role='system'` row renders, so a `cli` or `repl` `!confirm` would leave a visible ack above an invisible question.

**The send response carries both `messages.id`s, and the client must stamp them.** `command_data` is `{kind: 'confirmation_answered', user_msg_id, system_msg_id}`; the store writes them onto the optimistic user row and the placeholder-turned-system row. `appendStreamedRow` drops a frame whose `msg_id` is already on screen, and that is the *only* guard available here — neither row carries a task id, so the `(role, task_id)` path cannot fire. Without the stamp the room stream's own echo appends a second copy of both halves. It also makes the two rows starrable and deletable without a reload. `cmd_confirm` returns the same payload on `CommandResult.data` for exactly this reason. The client additionally calls `refreshConfirmations()` on that kind, so the banner clears with the answer instead of at the next 30s tick — an answer that works while the card lingers reads as the answer not having taken.

**A retried answer replays; it must not re-resolve.** A send the server accepted but never got to report is re-POSTed with the same `client_msg_id`, and `_is_own_replay` cannot see this exchange — `db.find_send_by_client_msg_id` inner-joins `tasks`, and these rows carry no task id, so the row consumes the `(room_token, client_msg_id)` unique index while being invisible to the lookup that exists to resolve a retry. `db.find_confirmation_exchange` is the NULL-tolerant sibling, consulted before anything else in `_chat_answer_confirmation`, returning the stored ids and ack. Both failure modes it closes were found in review and one is an authorization defect: with no gate parked the retry fell through to `_chat_create_web_task` and took an `IntegrityError` on the index (a 500), and with a *second* gate parked in the meantime `resolve` found that one open and **approved a question the user never answered**.

**Path B is resolved to the canonical token before the lookup**, not only before the transcript write. A task parks under the canonical token, so on a promoted room an unresolved Talk token misses Path B and falls to Path C — which with a second question open answers neither and posts the listing instead.

**Path A works on web because the mirror below stamps the Talk id.** A web reply cites a canonical `messages.id`; `get_pending_confirmation_by_response_id` matches `tasks.talk_response_id`. The mirrored prompt row carries `external_ids={"talk": …}`, so `db.get_message_external_id` walks the citation back and an explicit reply to one of several open prompts picks that one instead of hitting the ambiguity listing. The citation is checked against **this room** first, so the endpoint does not become an id oracle for another's. No second id column was invented for it.

**A Talk-delivered notification is mirrored into that room's transcript** (ISSUE-242). `notifications._dispatch` treated `talk` and `web` as unrelated destinations: the `web` leg writes a `role='system'` row into `messages`, the `talk` leg posted to Nextcloud and wrote nothing — same token, same room, one surface got the message. Everything going through a *task* already crossed over (`scheduler._store_room_turn`, ISSUE-176's producer half); non-task posts — alerts, heartbeat notices, reminders, and the inbound-email confirmation prompt — never were. For the prompt that is silent mail loss, since the task auto-cancels at `confirmation_timeout_minutes`.

`_mirror_talk_to_room` writes a `role='system'` row after a successful Talk delivery. `role='system'` is what the `web` leg already writes, so it renders identically, rides the live room stream and counts toward unread — no new render path; `origin_surface='talk'` is provenance only, since `list_system_messages` filters on `role` alone. The gate is **room existence, not surface config** — the same rule `_store_room_turn` uses — and the token is resolved through `db.resolve_room_token` first so a promoted web room is not missed. `_dispatch` resolves a bare `talk` destination's token itself rather than leaving that to `_send_talk`, because the mirror needs the token the post actually landed on. Best-effort throughout: the Talk post has already happened, so a failed transcript row must not report the notification as undelivered. Not idempotent across a retried notification — nothing retries one today; if that changes, dedup on `external_ids.talk`.

**The double-write guard compares canonical rooms, not raw tokens.** A route naming both legs of one room must produce one row, and neither raw value is the room: a bare `web` leaf carries no channel and lands on `default_web_room_token`, while a promoted room's Talk token differs from its own. Both sides are resolved before comparing.

**The short lock wait on the mirror's connection is load-bearing.** This opens a *second* connection to a database a caller may already hold a write transaction on — the hazard the `web` leg has always had, and the reason `_deliver_dmarc_alerts`, `_deliver_confirmation_prompts` and `run_cleanup_checks`' buffered notices are structured the way they are. Making the `talk` leg a writer extends that hazard to **every** remaining `send_notification` call site, and those reached from inside a transaction are not all worth restructuring — the nightly sleep cycle holds one write transaction for a whole pass and notifies from deep inside it. At the default 30s wait such a caller stalls for 30s per notification, on the dispatch thread, where six of them trip `loop_stall_alert_seconds`. `_MIRROR_LOCK_WAIT_MS` (250ms) turns the worst case into a *dropped mirror* instead, which is the right trade: the notification itself has already reached Talk, and the confirmation prompt — the one case where the mirror matters — is delivered outside any transaction. `run_cleanup_checks`' ancient-pending notice was moved out of its transaction with this change, joining the expiry notice that was already buffered for the same reason.

Why the aux gap-fill could not have covered the confirmation case: a gated task's transcript mirror is withheld, so it has no `role='user'` row — and `_AUX_ROOM_SCOPE` reaches an email task only through that row. Widening it to admit gated rows would publish `tasks.prompt`, the attacker-supplied text the gate exists to hold back. The fix belongs on the delivery side, and it generalizes past confirmations.

The direct `client.send_message` calls in `transport/talk/inbound.py` bypass `_dispatch` and so are not covered by the mirror — but the confirmation acks among them are now recorded through `record_exchange` instead, which reaches the same transcript. The `!model` usage error at `:541` stays Talk-only on purpose: it is a reply to something the user typed *in Talk*, so the reader is by definition looking at Talk.

**A failed or cancelled turn is gap-filled from `tasks`, and bands by its message, not by its task row.** `messages` is the transcript spine, but a turn that never produced an assistant row has nothing there to render its error bubble from, so `_chat_room_messages` runs an auxiliary query over `tasks` scoped to failed/cancelled and merges it into the page. Banding that fill on `tasks.created_at` was wrong: `record_inbound` writes the task row and then the user message row, both defaulting to second-granularity `datetime('now')`, so a turn straddling a clock second is stamped up to a second before the spine row it belongs to. The page floor `t1` is the oldest spine row, so the excluded turn was exactly the page's oldest — and since a first load fetches `limit*2` spine rows, any room shorter than one page had its error bubble missing on **every** load, not intermittently. The aux-filled bubble also sorted above its own question, the transcript's final sort being on `created_at`. `_AUX_TURN_TS` coalesces the turn's user spine row `created_at` with the task's own stamp and is the banding, cursor and rendered key for aux rows; a spineless legacy turn falls back to the task stamp. Only the timestamp is coalesced, not the `id` tiebreaker, so a turn tying the page floor second but sorting below it by id can still split across two pages — the pre-existing limit of a timestamp-only band. The `COALESCE` is not sargable and gives up the range bound `idx_tasks_user_created` gave the raw column (0.003 ms → 3.3 ms per probe over 10k tasks, linear, twice per page load), so every bound carries a redundant sargable companion on the raw column (`_AUX_TS_ABOVE` / `_AUX_TS_BELOW`) with an hour of slack. The companion is only ever *looser* than the exact test it accompanies, which is what makes it safe; the slack absorbs a backwards clock step. `backfill_room_messages_from_talk_cache` is the one writer that stamps a user row far from its task, and it recovers completed turns only, so it can never meet a band scoped to failed/cancelled.

**Sidebar order is latest activity, newest first.** The sort key is `last_activity` — the `created_at` of the room's newest `messages` row, falling back to the room's own creation time so a room nobody has spoken in still has one and a freshly created room lands near the top rather than at the bottom. It is computed in `db.list_member_rooms` as `(SELECT created_at … ORDER BY id DESC LIMIT 1)` rather than a `MAX(created_at)`: the ids carry the same order and `idx_messages_room (room_token, id)` makes that one index seek per room instead of a scan over the room's whole history. `_chat_list_rooms` emits it through `_iso_utc`, the same normalization a message row's `created_at` gets, precisely so a streamed row's stamp can be written straight onto the room client-side. The frontend renders `$rooms` in store order, so the store's order *is* the screen's; `stores/roomOrder.ts` holds the two pure operations (`sortRoomsByActivity`, `touchRoomActivity`) and `applyRoomEvent` touches on every frame — the single funnel every message passes through, which is what keeps the order live for a Talk turn, a routed alert and the user's own send alike. Three constraints. The **stamp never moves backwards** (gap recovery and the reconnect replay both redeliver older rows, and a demotion there would drop the room the user just spoke in). The **30s rooms poll now re-sorts**, reversing its long-standing "no reorder" rule — that reconciliation is what recovers the order after a sleeping tab or a dropped stream, and it takes the newer of the two stamps so a response built before it was awaited can't undo a frame that landed in between. And the **`room` metadata frame carries no `last_activity`** for the same reason it carries no unread count — it is diffed per stream tick, so including a per-message field would turn every turn into a `room` frame; a room *appearing* in that frame is stamped client-side with now (its appearance is the activity), and the poll settles it. Two responses that omit the key are merged rather than adopted for the same reason: the room PATCH (a rename is not activity) and the create POST, which is why `_chat_create_room` stamps its own reply server-side.

**Live room-event stream** (`live-web-chat-room-stream` spec). The per-task SSE stream only ever covered a task the client itself started; everything else — a Talk-originated turn, a routed alert, an unread badge, a rename — rode `setInterval`. `GET /chat/stream` is a sibling of `chat_task_stream` that tails the canonical `messages` store instead of `task_events`, carrying **every room the user is a member of over one session-lived connection**. The seam between the two: the room stream is the "something happened" bus, the task stream stays the "here is the token-level detail" bus — a streamed `user` row whose task is still unsettled makes the client open a task stream for it, which is `pickUpNewInFlightTasks` made event-driven (and fixes the `pending_confirmation` skip, since the persisted `confirmation` event now replays). Cursor is `messages.id` alone — one monotonic integer over user turns, assistant turns and system rows — which is what closes the fast-turn hole _structurally_: a Talk turn that starts and finishes inside 200ms still writes two rows and both are tailed, so timing stops mattering. The producers are in a different process from the web server (separate systemd units / containers), so the web tier polls SQLite exactly as `events.py` prescribes; the change is _where_ the polling lives — server-side at ~1s as an indexed `id > :cursor` scan behind an O(1) `MAX(id)` gate, pushing deltas, instead of client-side at 5s refetching a 50-row page per open room. `db.list_room_events_since` shares SQL fragments with `db.list_messages_across_rooms` so the visibility predicate (membership minus dismissals minus archived) cannot fork, and rows are emitted in the **same shape the history endpoints emit** (`_cross_room_message_dict`) so `buildHistoryMessage` builds a streamed row and a reloaded row identically. Frame kinds: `message` (carries `id:`), `gap` (carries `id:`), `room` (metadata delta — rename / model / effort / added / removed; **no** `id:`), `message_deleted` (**no** `id:` — see below), and a `: ping` keepalive (**no** `id:`) — auxiliary frames must omit `id:` or EventSource's resume cursor lands in the wrong place. The **gap threshold** is split because neither side can see the other's variable: the server decides on _cost_ (`room_stream_max_batch` rows AND `room_stream_max_bytes` — a joined assistant row carries `execution_trace`, so row count alone measures the wrong thing), the client on _age_ (~60s of silence on reconnect or after a hidden tab, since a star toggled elsewhere or a Talk-synced read cursor is state the stream doesn't carry). Both converge on one recovery routine: reload rooms + the open room, then adopt the cursor — which is the server's max id **scanned**, not the last one sent, or the truncated rows are stranded. Frames landing during that reload are buffered and re-applied. The notif poller is gone; the rooms poll is demoted to a 30s metadata reconciler and **kept only because `GET /chat/rooms` drives the Talk→web read-state pull**. Aggregate views (All / Unread) and background-room previews are fed from the same frames. Knobs under `[web.chat] room_stream_*`; `GET /chat/events` is the polling-fallback snapshot; `_admin_chat_section` reports live connection count (the metric that would justify the deferred shared per-user broker).
