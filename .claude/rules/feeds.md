# Feeds module

## Feeds

Native RSS/Atom/Tumblr/Are.na (`src/istota/feeds/`), per-user SQLite, no Miniflux. **Are.na runs on the v3 API**: `content`/`description` arrive as `{markdown, html, plain}`, so real HTML is rendered instead of v2's HTML-escaped markdown, and `image.src` is already the original. Block ids are identical across v2 and v3, so `guid` stayed stable and the switch re-inserted nothing. Six block types have typed builders (`Text`, `Image`, `Link`, `Embed`, `Attachment`, `Channel`) over a generic fallback, so a type Are.na adds later still renders; a builder that raises degrades to the safe generic rather than failing the poll, and `_ensure_renderable` guarantees no blank card. An `Embed` sets `feed_entries.embed_url` and an `Attachment` sets `file_url` — the provider's own `embed.html` iframe is deliberately discarded rather than allowing `<iframe>` through the shared sanitizer, so the web side resolves a player URL from a **host allowlist** (YouTube / `youtube-nocookie` / Vimeo, ids re-validated) and both the card and the reader use the same three helpers. **Inline `<video>` is allowed but bounded.** The tag was always through the sanitizer; what it now keeps is `loop` and `muted` alongside `src`/`controls`/`poster`/`preload`/`playsinline`. `autoplay` stays out — a grid of cards all playing on scroll is not the same request as playing one — and so do `width`/`height`, since a stored width is what made a clip run off the side of a card; both surfaces bound video with CSS the way they already bounded `<img>`. Stripping `autoplay` alone would have stored a tag nothing could start (a GIF-as-mp4 is authored as an autoplaying muted loop with _no_ controls, precisely so it doesn't look like a player), so `_ensure_video_controls` runs as a post-pass on both sanitize branches and injects `controls` when absent — after sanitisation, so it only ever sees tags the allowlist already passed and escaped `&lt;video&gt;` in prose stays text. The reader's Images toggle hides inline video along with pictures: it already hid the embed hero, so leaving a clip drawn made the chip mean "some of the media". **A direct media attachment is a third field, not a variant of the two above** (ISSUE-356): `feed_entries.media_url` / `media_type` (schema v7) carry a file the reader plays itself with a native `<video>`/`<audio>` — a Mastodon video attachment, a podcast enclosure — where `embed_url` means "a provider page we can rebuild a player for" and `file_url` means "open this elsewhere". It exists because the poller's `media:content` loop gated on nothing at all where the `<enclosure>` loop beside it gated on `image/`, and Mastodon ships a video *only* as `media:content`, so an mp4 landed in `image_urls` and the reader painted `<img src="….mp4">` — a hero that never decodes over a lightbox that opens on nothing. `_classify_attachment` is now the one place either element is read: three pieces of evidence — MIME type, then `medium`, then the extension (`models.media_type_for_url`) — consulted in order and **falling through** rather than short-circuiting. Falling through is the load-bearing part: an attachment typed `application/octet-stream` (a common CDN default) or carrying an MRSS `medium` of `document` still gets the later questions asked of it, and short-circuiting to a drop there costs a hero the old loop kept, since that loop took every `media:content` URL whatever its type said. The `untyped` argument is what an attachment no evidence classified falls back to, and it preserves the two elements' *different* historical defaults — a `media:content` stays an image, an `<enclosure>` is still dropped. The v7 migration also lifts the mp4s already sitting in `image_urls`, because additive alone would fix nothing an existing reader sees: `insert_entries` matches on `(feed_id, guid)` and holds `image_urls` with `COALESCE(?, image_urls)`, so a re-poll emitting an empty image list leaves the broken URL exactly where it is. It applies `is_http_url` before promoting anything — those rows predate any scheme check and `media_type_for_url` reads the path, so `javascript:x.mp4` parses as a video, and the poller's own refusal is the only other guard on that value. It rebuilds `entry_images` for the rows it touched, since a lifted video left in that index would go on suppressing later posts through the image dedupe; **the other side of that is deliberate** — a clip is now outside repeat-image suppression entirely, so a boost wave of one video renders a player per entry, where suppression exists to stop the same *picture* filling a screen and a player nobody pressed is not that. Only the first playable attachment is kept, matching the poller; the migration counts and logs the rest rather than dropping them silently. The frontend half is `inlineMedia` in `web/src/lib/feeds/embed.ts`, sitting beside `playerUrl` for the same reason — the return value goes straight into a `src`, so the URL is re-parsed and anything not http(s) is refused. It returns `kind` and the URL and deliberately no MIME type: the elements are single-source and take their format from the response's `Content-Type`, so a `type` hint would have no consumer and a field nothing reads is a field that drifts. `kind` comes from the stored type first and the extension only as a fallback, and `.ogg` is in neither language's table though `.oga` and `.ogv` are — Ogg is a container and `video/ogg` is registered, so guessing audio would put a Theora video in an `<audio>` and lose the picture silently, which is worse than offering no player. The two extension tables are hand-mirrored across languages and held equal by `tests/test_feeds_media_parity.py`, on the `usage_render.py` ↔ `usageFormat.ts` precedent; without it a key added on one side fails nowhere, because the TS side reads the stored `media_type` and never consults its own table until a feed ships an untyped attachment. Both surfaces size the player the way they already size inline `<video>` in body copy — `max-width: 100%` with a height cap, never a `width`/`height` attribute. A **lone** still that came with the clip becomes the `poster`; several stay a gallery rendered under the player, since consuming the first would leave the rest drawn by nothing, and a still that is itself a playable URL is refused as a poster so a downgrade's re-filed mp4 cannot come back through the `<img>`-shaped hole. **A poll refreshes an entry it already holds** rather than discarding it, so a provider fix reaches entries already on file; user state (`status`, `starred`, `starred_at`) and `fetched_at` are never overwritten, and a field is only overwritten by a non-empty value, so a sparser re-fetch cannot blank a title. The "N new" count still means newly inserted. **Repeat-image suppression** (`image_dedupe.py`) is a display-time decision, never a row mutation: an image is suppressed on the older of two entries carrying the same identity key within a look-back window (`feeds_settings.image_dedupe_window_days`, default 14, `0` = off, distinct from unset), so the newest carrier always keeps the tile and re-surfacing after the window renders again. The key is `netloc + path` with query/CDN signature ignored, plus a Tumblr rule dropping the shard and `/sWxH/` size segment. Scoped to the slice the reader is showing (feed / category / starred), deliberately **not** by read state.

**Rate limiting** (`poller.py`, ISSUE-347) is four parts and only works as a set. The pacing key is the **host**, not the source type: every Are.na channel is one request to `api.are.na` and every Tumblr blog one to `api.tumblr.com`, so one minimum-gap rule covers both providers and any future one, while RSS — dozens of distinct origins — pays nothing for it. Two feeds that genuinely share an RSS origin are paced too, which is correct for the same reason. It lives in `poll_due_feeds` rather than inside a provider so it is written once. A **429 is not an error**: `FeedRateLimited` (same shape as `health/garmin.py`'s `GarminRateLimited`, the in-repo precedent) carries the parsed `Retry-After` out of the provider, `poll_feed` turns it into `FetchResult.rate_limited` rather than `error`, and `_persist_poll` writes `error_count` and `last_error` back **unchanged** — the 429 says nothing about whether a previous real failure is fixed, and not incrementing is also what stops a throttle carrying a doubled interval forward once it clears. **A 429 never schedules sooner than a success would**, and that invariant is what fixes the floor: `_rate_limit_interval` floors at the same quantity the success path uses (`max(poll_interval_minutes, DEFAULT_POLL_INTERVAL_MINUTES)`) plus `DEFAULT_RATE_LIMIT_BACKOFF_MINUTES` on top, capped at `MAX_RATE_LIMIT_BACKOFF_MINUTES`. Flooring at the raw `poll_interval_minutes` — the first cut — let a 429 come back *sooner* than a healthy poll on any feed configured under 30 minutes, adding pressure to the host that had just turned us away; the settings page bounds that value at neither end, so it is reachable. `Retry-After` therefore only ever extends, which is the direction the generic doubling would have missed, and waiting longer than asked is always compliant. Every `next_poll_at` is **jittered**, on the success path as well as the two failure paths, because a set that burst together otherwise reschedules to the same instant and re-forms every round. `run-scheduled` caps its burst by default, draining a larger backlog over consecutive ticks (the due list is oldest-first), and a **second cap bounds the sleeping itself** (`DEFAULT_MAX_PACING_SECONDS`): the poll is a background skill task and `user_max_background_workers` defaults to 1, so 50 same-host channels at a 2s gap would hold that one slot for ~98s of every 5-minute tick with every other background job for that user queued behind it. On exhaustion the run stops rather than un-pacing itself, leaving the rest due for the next tick. **A throttle is recorded, just not as an error**: `feeds.last_throttled_at` (schema v6) is where it shows, cleared by the next successful fetch so the column means "throttled now" rather than "throttled once", and the rate-limited path writes `last_fetched_at` back unchanged because nothing was fetched. `errors` and `throttled` are separate counters on the poll run's own output, and a wholly throttled run exits non-zero — without that it reported `status: ok, errors: 0`, indistinguishable from a clean poll that found nothing. **The known gap is that none of this spans users**: the poll is a per-user skill subprocess, so two users' polls are two processes reaching one host from one IP with no shared budget. Within-process pacing is the large win since the observed bursts are one user's channel set, but nothing here bounds the cross-user case.
