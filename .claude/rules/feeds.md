# Feeds module

## Feeds

Native RSS/Atom/Tumblr/Are.na (`src/istota/feeds/`), per-user SQLite, no Miniflux. **Are.na runs on the v3 API**: `content`/`description` arrive as `{markdown, html, plain}`, so real HTML is rendered instead of v2's HTML-escaped markdown, and `image.src` is already the original. Block ids are identical across v2 and v3, so `guid` stayed stable and the switch re-inserted nothing. Six block types have typed builders (`Text`, `Image`, `Link`, `Embed`, `Attachment`, `Channel`) over a generic fallback, so a type Are.na adds later still renders; a builder that raises degrades to the safe generic rather than failing the poll, and `_ensure_renderable` guarantees no blank card. An `Embed` sets `feed_entries.embed_url` and an `Attachment` sets `file_url` — the provider's own `embed.html` iframe is deliberately discarded rather than allowing `<iframe>` through the shared sanitizer, so the web side resolves a player URL from a **host allowlist** (YouTube / `youtube-nocookie` / Vimeo, ids re-validated) and both the card and the reader use the same three helpers. **Inline `<video>` is allowed but bounded.** The tag was always through the sanitizer; what it now keeps is `loop` and `muted` alongside `src`/`controls`/`poster`/`preload`/`playsinline`. `autoplay` stays out — a grid of cards all playing on scroll is not the same request as playing one — and so do `width`/`height`, since a stored width is what made a clip run off the side of a card; both surfaces bound video with CSS the way they already bounded `<img>`. Stripping `autoplay` alone would have stored a tag nothing could start (a GIF-as-mp4 is authored as an autoplaying muted loop with _no_ controls, precisely so it doesn't look like a player), so `_ensure_video_controls` runs as a post-pass on both sanitize branches and injects `controls` when absent — after sanitisation, so it only ever sees tags the allowlist already passed and escaped `&lt;video&gt;` in prose stays text. The reader's Images toggle hides inline video along with pictures: it already hid the embed hero, so leaving a clip drawn made the chip mean "some of the media". **A direct media attachment is a third field, not a variant of the two above** (ISSUE-356): `feed_entries.media_url` / `media_type` (schema v7) carry a file the reader plays itself with a native `<video>`/`<audio>` — a Mastodon video attachment, a podcast enclosure — where `embed_url` means "a provider page we can rebuild a player for" and `file_url` means "open this elsewhere". It exists because the poller's `media:content` loop gated on nothing at all where the `<enclosure>` loop beside it gated on `image/`, and Mastodon ships a video *only* as `media:content`, so an mp4 landed in `image_urls` and the reader painted `<img src="….mp4">` — a hero that never decodes over a lightbox that opens on nothing. `_classify_attachment` is now the one place either element is read: three pieces of evidence — MIME type, then `medium`, then the extension (`models.media_type_for_url`) — consulted in order and **falling through** rather than short-circuiting. Falling through is the load-bearing part: an attachment typed `application/octet-stream` (a common CDN default) or carrying an MRSS `medium` of `document` still gets the later questions asked of it, and short-circuiting to a drop there costs a hero the old loop kept, since that loop took every `media:content` URL whatever its type said. The `untyped` argument is what an attachment no evidence classified falls back to, and it preserves the two elements' *different* historical defaults — a `media:content` stays an image, an `<enclosure>` is still dropped. The v7 migration also lifts the mp4s already sitting in `image_urls`, because additive alone would fix nothing an existing reader sees: `insert_entries` matches on `(feed_id, guid)` and holds `image_urls` with `COALESCE(?, image_urls)`, so a re-poll emitting an empty image list leaves the broken URL exactly where it is. It applies `is_http_url` before promoting anything — those rows predate any scheme check and `media_type_for_url` reads the path, so `javascript:x.mp4` parses as a video, and the poller's own refusal is the only other guard on that value. It rebuilds `entry_images` for the rows it touched, since a lifted video left in that index would go on suppressing later posts through the image dedupe; **the other side of that is deliberate** — a clip is now outside repeat-image suppression entirely, so a boost wave of one video renders a player per entry, where suppression exists to stop the same *picture* filling a screen and a player nobody pressed is not that. Only the first playable attachment is kept, matching the poller; the migration counts and logs the rest rather than dropping them silently. The frontend half is `inlineMedia` in `web/src/lib/feeds/embed.ts`, sitting beside `playerUrl` for the same reason — the return value goes straight into a `src`, so the URL is re-parsed and anything not http(s) is refused. It returns `kind` and the URL and deliberately no MIME type: the elements are single-source and take their format from the response's `Content-Type`, so a `type` hint would have no consumer and a field nothing reads is a field that drifts. `kind` comes from the stored type first and the extension only as a fallback, and `.ogg` is in neither language's table though `.oga` and `.ogv` are — Ogg is a container and `video/ogg` is registered, so guessing audio would put a Theora video in an `<audio>` and lose the picture silently, which is worse than offering no player. The two extension tables are hand-mirrored across languages and held equal by `tests/test_feeds_media_parity.py`, on the `usage_render.py` ↔ `usageFormat.ts` precedent; without it a key added on one side fails nowhere, because the TS side reads the stored `media_type` and never consults its own table until a feed ships an untyped attachment. Both surfaces size the player the way they already size inline `<video>` in body copy — `max-width: 100%` with a height cap, never a `width`/`height` attribute. A **lone** still that came with the clip becomes the `poster`; several stay a gallery rendered under the player, since consuming the first would leave the rest drawn by nothing, and a still that is itself a playable URL is refused as a poster so a downgrade's re-filed mp4 cannot come back through the `<img>`-shaped hole. **A poll refreshes an entry it already holds** rather than discarding it, so a provider fix reaches entries already on file; user state (`status`, `starred`, `starred_at`) and `fetched_at` are never overwritten, and a field is only overwritten by a non-empty value, so a sparser re-fetch cannot blank a title. The "N new" count still means newly inserted. **Repeat-image suppression** (`image_dedupe.py`) is a display-time decision, never a row mutation: an image is suppressed on the older of two entries carrying the same identity key within a look-back window (`feeds_settings.image_dedupe_window_days`, default 14, `0` = off, distinct from unset), so the newest carrier always keeps the tile and re-surfacing after the window renders again. The key is `netloc + path` with query/CDN signature ignored, plus a Tumblr rule dropping the shard and `/sWxH/` size segment. Scoped to the slice the reader is showing (feed / category / starred), deliberately **not** by read state.

**Rate limiting** (`poller.py`, ISSUE-347) is four parts and only works as a set. The pacing key is the **host**, not the source type: every Are.na channel is one request to `api.are.na` and every Tumblr blog one to `api.tumblr.com`, so one minimum-gap rule covers both providers and any future one, while RSS — dozens of distinct origins — pays nothing for it. Two feeds that genuinely share an RSS origin are paced too, which is correct for the same reason. It lives in `poll_due_feeds` rather than inside a provider so it is written once. A **429 is not an error**: `FeedRateLimited` (same shape as `health/garmin.py`'s `GarminRateLimited`, the in-repo precedent) carries the parsed `Retry-After` out of the provider, `poll_feed` turns it into `FetchResult.rate_limited` rather than `error`, and `_persist_poll` writes `error_count` and `last_error` back **unchanged** — the 429 says nothing about whether a previous real failure is fixed, and not incrementing is also what stops a throttle carrying a doubled interval forward once it clears. **A 429 never schedules sooner than a success would**, and that invariant is what fixes the floor: `_rate_limit_interval` floors at the same quantity the success path uses (`max(poll_interval_minutes, DEFAULT_POLL_INTERVAL_MINUTES)`) plus `DEFAULT_RATE_LIMIT_BACKOFF_MINUTES` on top, capped at `MAX_RATE_LIMIT_BACKOFF_MINUTES`. Flooring at the raw `poll_interval_minutes` — the first cut — let a 429 come back *sooner* than a healthy poll on any feed configured under 30 minutes, adding pressure to the host that had just turned us away; the settings page bounds that value at neither end, so it is reachable. `Retry-After` therefore only ever extends, which is the direction the generic doubling would have missed, and waiting longer than asked is always compliant. Every `next_poll_at` is **jittered**, on the success path as well as the two failure paths, because a set that burst together otherwise reschedules to the same instant and re-forms every round. `run-scheduled` caps its burst by default, draining a larger backlog over consecutive ticks (the due list is oldest-first), and a **second cap bounds the sleeping itself** (`DEFAULT_MAX_PACING_SECONDS`): the poll is a background skill task and `user_max_background_workers` defaults to 1, so 50 same-host channels at a 2s gap would hold that one slot for ~98s of every 5-minute tick with every other background job for that user queued behind it. On exhaustion the run stops rather than un-pacing itself, leaving the rest due for the next tick. **A throttle is recorded, just not as an error**: `feeds.last_throttled_at` (schema v6) is where it shows, cleared by the next successful fetch so the column means "throttled now" rather than "throttled once", and the rate-limited path writes `last_fetched_at` back unchanged because nothing was fetched. `errors` and `throttled` are separate counters on the poll run's own output, and a wholly throttled run exits non-zero — without that it reported `status: ok, errors: 0`, indistinguishable from a clean poll that found nothing. **The known gap is that none of this spans users**: the poll is a per-user skill subprocess, so two users' polls are two processes reaching one host from one IP with no shared budget. Within-process pacing is the large win since the observed bursts are one user's channel set, but nothing here bounds the cross-user case.

**Entry retention** (`retention.py`, ISSUE-388, schema v8) bounds two tables that used to grow until a feed was removed outright: `feed_entries` kept every entry ever fetched and `entry_images` grew alongside it, on a database `db_backup.py` copies to the mount in several dated snapshots. **The clock is `fetched_at` — when the entry entered this reader — and never `published_at`.** `published_at` describes the item rather than our copy of it: an Are.na block created in 2019 and added to a channel today arrives with a 2019 date and would be purged on the day it appeared, and the field is nullable and, on plenty of RSS feeds, wrong. `fetched_at` is neither, and `insert_entries` has always refused to overwrite it on refresh, so the field this needs already existed and was already stable. There are **two passes and they protect different things**, which is why the skill doc refuses to describe them as one rule. **Age** deletes a row that is unstarred, read or removed, past the cutoff, and not in the feed's most recent response; unread is exempt absolutely, which is where "don't throw away what I haven't read" belongs. **Count** trims each feed to `max_entries_per_feed` ranked by `fetched_at DESC, id ASC`, reading no status at all — so on a feed at its ceiling an old unread row can go ahead of a newer read one. That cost is stated rather than designed away: an earlier draft did keep unread ahead of read here, and because admission ranks by source order the two orderings disagreed, so a feed near its maximum had in-response read rows trimmed and re-admitted as unread on the next poll. Defaults are 90 days and 5000 entries, stored per user in `schema_meta` under `feeds_settings.entry_retention_days` and `feeds_settings.max_entries_per_feed`, `0` disabling either independently. A negative stored value resolves to the default at the point of use rather than being used, since a negative window puts the cutoff in the future and deletes the whole reader on one bad number.

**The age pass closes churn with "was it in the most recent response", not with a completeness test**, and that single clause is why pagination needs no handling and no provider gets a branch in a deletion path. A row is deletable only where its `last_seen_at` is older than its feed's `last_items_seen_at`, so we never delete what the feed has just handed us and the feed therefore cannot hand it back — by construction, rather than by inference about what the source still holds. Classic readers never needed it: an ordinary RSS feed drops an entry within weeks, so by the time any sane clock expires re-import is theoretical. Are.na is archive-shaped, a block stays in its channel indefinitely, and a read block deleted by age while the channel still serves it comes back as unread with a fresh `fetched_at`, every retention period, forever. `feeds.last_items_seen_at` advances to the poll timestamp when, and only when, the response yielded at least one identifiable item, and that is the whole trust rule — there is no `membership_complete`, no truncation predicate and no `document_rank`; Stage 1 of the spec shipped all three and Stage 2 removed them. A 304, a 429, an HTTP error, an exception and an HTML error page that `feedparser` parses into zero entries all leave the marker where it was, so every stored entry keeps `last_seen_at == last_items_seen_at` and stays protected. The HTML error page is what forced the rule's shape: served at HTTP 200 it parses with `bozo` **False**, so any completeness test would have made a whole feed's history age-eligible on one proxy error, where `len(items) > 0` cannot. The cost is that a feed which has genuinely gone empty never advances its marker again and is bounded by the maximum alone, which is the safe direction and far cheaper than the `version`/`bozo`/expat reasoning it replaced. A feed migrated to v8 that never fetches successfully again keeps everything, since the marker starts null and the age rule requires a non-null one.

**Admission is the other half of the maximum, and the two ends must agree or they take turns on every poll.** `plan_admission` caps one response at the same `unstarred_budget` the count pass enforces, in source-response order, dropping items with no guid and later copies of a duplicated one; without it a response larger than the maximum has its tail inserted, trimmed by the next prune and re-inserted by the poll after that. Source order rather than a re-sort, because RSS has no trustworthy sequence for missing or malformed publication dates and re-sorting would substitute a guess. The tie-break decides more than it looks like it does: every entry of one poll carries that poll's single `fetched_at`, so a whole batch ties and `id ASC` alone picks the survivors, and since `insert_entries` writes in source order against an ascending rowid the head of the response holds the lowest id — which is what admission keeps. `id DESC` kept the tail and deleted the head, so the count pass deleted precisely what the next response would hand back (`4f2995bb`). What admission must not do is decide what was *observed*: an item past the budget was still returned, so `mark_entries_seen` stamps its `last_seen_at` anyway, or the age pass deletes it, that frees budget, and the next response re-admits it as unread. The budget is `max(max_entries_per_feed - starred_count, min(50, max_entries_per_feed))`, and the floor under it is not tidiness — without it a feed whose stars reach the maximum gets a budget of zero permanently: every unstarred row deleted, unread and in-response alike, nothing admitted ever again, and only `protected_excess_entries` hinting at it. `MIN_ENTRIES_PER_FEED = 50` is a constant with no knob, because it is a safety floor rather than a preference and the quantity a user has an opinion about is the ceiling, which is already exposed; where the ceiling is set below it the ceiling wins, since an explicit instruction to store twenty entries must not be overridden by a default that says fifty. The age pass applies that floor against **every** stored row for the feed rather than only the deletable ones, so a feed holding fifty unread rows has plenty of history and does lose its old read ones. The count pass honours no floor on rows at all: a feed over its maximum is by definition not empty, and honouring one there would make a maximum below fifty unenforceable. Stars can leave a feed above its maximum and so can that budget floor; `protected_excess_entries` is the plain difference and distinguishes neither, because the alternative is guessing that a starred row is safe to delete.

Schema v8 adds `feed_entries.last_seen_at`, `feeds.last_items_seen_at`, `feeds.poll_claimed_until` and two partial indexes over the unstarred rows. The migration stamps every existing entry with one shared `last_seen_at` (`fetched_at` is deliberately untouched — it is the retention clock, and rewriting it would reset every entry's age to the upgrade date), leaves both feed columns null, clears `etag`/`last_modified` and makes every feed due, and opens a 90-day no-deletion period in `feeds_internal.entry_prune_not_before`. Clearing the validators is not tidying up: a stored ETag answers the first post-upgrade poll with a 304, which carries no entry list and so can never advance the marker. The grace row is internal and reaches no API — a user who could edit it could turn a safety period into an immediate delete — and `prune_feeds` reads it before either pass, because the count pass has no age predicate of its own and an observation stamp alone could not have stopped it deleting pre-upgrade rows on the day the feature shipped. It is cleared inside the same transaction both passes ran in, and only where a limit was actually enabled, so spending the safety period on a run that could delete nothing does not leave a user who switches retention on afterwards with no grace at all; a malformed value is a hard error that retains everything. The migration also creates `schema_meta` rather than assuming it, since `_read_schema_version` returns 1 for a database predating that table and `init_db` runs the whole migration chain before `SCHEMA_SQL` — without that the oldest databases stopped opening at all.

**Poll claims** (`poll_claimed_until`, `POLL_CLAIM_SECONDS = 300`) serialize polls of one feed across processes, so an older response cannot stamp observation state on top of a newer one. `feeds_due_for_poll` excludes a claimed feed and `claim_feed_for_poll` restates the same two predicates as one conditional update committed before the fetch, because the interval between that SELECT and the request is where a manual poll and the scheduled one actually collide. Deliberately not a database lock: nothing may hold a SQLite write transaction across 30 seconds of network I/O, and the price of that is a lease an unexpected exit leaves behind for at most five minutes. The claim is taken after any pacing sleep and after the pacing budget check, so a feed nobody went on to fetch is never held; a refusal is an ordinary skip, and every handled outcome releases it. Both the claim and the observation marker are ISO strings compared lexically, so `poll_due_feeds` converts a caller's clock to UTC once at the top and refuses a naive one: a naive stamp sorts below every `+00:00` string in the same column, which would have a poll write entries whose `last_seen_at` reads as older than the marker it wrote in the same transaction — its own entries, age-deletable.

The prune runs daily as `_module.feeds.prune` at `17 3 * * *` and by hand as `feeds prune [--dry-run]`: one connection, one write transaction, both passes, one commit. A dry run executes the same statements and rolls them back, so its counts come from the real algorithm rather than a second implementation of it. It bounds a feed's *stored* total, not each response — polling runs every five minutes and the prune once a day, so a source emitting fresh guids every poll sits over its maximum until the next prune restores it. Image rows leave only through `ON DELETE CASCADE` and are counted either side of the two entry passes rather than deleted directly, because `_plan_image_suppression` queries owners relative to timestamps on the page being rendered: a retained page from any date still needs its index rows from that date, so there is no correct global wall-clock cutoff for that table and no index on `entry_images.seen_ts`. **No `VACUUM`, by decision.** A vacuum rewrites the database, needs stronger locking than row deletes, and would contend with `db_backup.py`'s online backup, and enabling `auto_vacuum` on an existing file requires one anyway. Freed pages stay on SQLite's freelist and are reused by later writes, so this stops high-water growth rather than reversing it — the file does not shrink and a backup snapshot may keep its prior size. `reusable_pages` and `page_size` report that state without claiming space went back to the filesystem, and a PRAGMA that cannot be read logs at debug and returns zero, since a diagnostic must never turn a committed deletion into a failure.

Saving the feeds settings clears `etag` and `last_modified` on every feed when the **effective** maximum changes, since a new maximum only takes effect through a response carrying items and a conditional request answered 304 carries none, so a raised limit would otherwise sit unused until the feed happened to publish. It clears `next_poll_at` only where the feed is neither throttled nor in error backoff (`last_throttled_at IS NULL AND error_count = 0`): ISSUE-347's stated invariant is that a 429 never schedules sooner than a success would, and a settings save is user-triggered and repeatable, so clearing the standoff there hands the user a way to stampede a host that has just turned us away, one save at a time. A held-back feed keeps its backoff and picks the new budget up at its own next poll, which is late rather than wrong. `_migrate_v7_to_v8` clears the schedule unconditionally and is right to, because it runs once per upgrade rather than once per click. An age-window change resets nothing, since it deletes on a stored clock and inserts nothing.
