# Relay questions between users

A task asks another user of the same installation a question; the recipient's explicit reply returns unchanged to the asker's private conversation. The question travels to a room (web plus its Talk mirror), WhatsApp or SMS; the answer returns to a web, Talk, WhatsApp or SMS origin. The operator-facing version is `docs/features/relay.md`. WhatsApp self-sends share the request table and are in `.claude/rules/whatsapp.md`.

## Who owns what

- `relay/destinations.py`: where a question goes. `resolve_destination`, the three per-kind resolvers (`_room`, `_whatsapp`, `_sms`), `check_room` for re-resolution at admission, `render_question` / `fit_question` for the wording, and `relay_delivery_options` for the settings page. `KINDS` is derived from `user_profiles.RELAY_DELIVERY_VALUES`, so the PUT's enum and the resolver's kinds are one tuple.
- `relay/requests.py`: durable intent, approval and admission for every relay question, despite the name. `hold_question`, `park_question`, `approve_request`, the clean-turn rule, `admit_request`, `drain_requests`, `_finish_request`. The table is still `whatsapp_skill_requests`; a rename was rejected as churn with no behaviour change.
- `relay/relays.py`: blocks, frozen private origins, `deliver_question` (the room arm is here; WhatsApp and SMS go through their ledgers), answer acceptance per surface, `create_recipient_task`, `recipient_context`, returns, expiry and notices.
- `notifications/resolvers/relay_question.py` (recipient side) and `message_relay.py` (asker side). See `.claude/rules/notifications.md`.
- `skills/relay/`: the task-facing CLI. It persists intent under the proxy's trusted user and task identity and never sends. `skills/whatsapp/` keeps only self-sends.

## Asking and the destination

Asking is open by default within one installation (ISSUE-566). The recipient's only control is a directional `!relay block`, with no admin bypass. Refusal order in `hold_question` is fixed: `unknown_user`, then the block (`recipient_unavailable`, the one code that hides its cause), then the origin checks, then the destination. The block is checked before the destination so a blocked asker learns nothing about where the recipient could have been reached. Every other code names what failed, since hiding who exists inside one installation protects nothing the admin UI does not already show.

Resolution order: the recipient's `user_profiles.relay_delivery` if set and usable, else the asker's `--via` if given, else the default room. **An unusable preference falls to the default room, never to `--via`.** The recipient chose, and a fallback to the asker's choice overrides them in exactly the case they set it for. An unusable `--via` is refused with that kind's code rather than silently rerouted. An unknown stored preference counts as none.

A room qualifies when `db.default_web_room` names one whose only member is the recipient and which is not archived; its Talk ref is captured. That check is `db.is_private_room_of`, shared with the private-reply resolver (`rooms.private_replies.private_room_for`), so the two cannot disagree about what a private room is. A room with an SMS or WhatsApp binding never qualifies, a pinned `default_room` included (`db.room_has_phone_binding`): a phone room is read-only in web, so a question there could only be answered by a send the server refuses. **No room is ever created for a relay**, which is the rooms-are-user-created rule; the refusal is `recipient_has_no_private_room`. The live Talk participant check is not run at hold time: the daemon runs it before the preview and again at release, so a third call from the skill subprocess added nothing (ISSUE-567).

`relay list` and `relay status` run the live Talk audience check from the skill subprocess. It authenticates with the app password the relay manifest declares `sensitive`, so the proxy injects it into that skill alone and the subprocess's `load_config` picks it up through the `ISTOTA_NEXTCLOUD_APP_PASSWORD` override (ISSUE-568). The subprocess used to hold no credential on a deployment with `istota_use_environment_file`, and every Talk-bound call was refused. A fetch failure is `audience_unavailable` in the skill, apart from a wrong audience (`unsupported_origin`). The local participant store ISSUE-567 proposed was not built: with the credential present it would only trade a live check for a stale one on this path.

The destination is frozen into the request (`provider`, `binding_fingerprint`) and into `relay.relays.destination`, JSON holding kind, room token, Talk ref and a human label, never a phone number. Fingerprints: a room is `text_hash(json([room_token, talk_ref]))`, WhatsApp the existing binding fingerprint, SMS `text_hash(number)`. A question is rendered once at hold time and never shortened: a rendering that would not arrive whole is `invalid_rendering`.

## Approval, and the clean turn (ISSUE-565)

A held question parks through `park_question`, and `tasks.whatsapp_confirmation_request_id` plus the stored preview digest bind the approval to one request; `confirmed_at` alone grants nothing. Confirmation delivery uses the validated private origin, never output overrides, log subscribers or a content-bearing fallback. Phone preview references include the request id, so successive questions in one task each get their own approval message.

A question skips approval (`approval = 'clean_turn'`) when, inside `hold_question`'s own write transaction and after the reservation and caps have run: the task's source type is web, Talk, WhatsApp or SMS (`_CLEAN_TURN_SURFACES`, the four whose `tasks.prompt` is the sender's own text, checked per producer in stage 7); the task is not a confirmed re-run (no `confirmed_at`, empty `confirmation_prompt`), because a re-run counts from zero while its prompt carries the previous attempt's output as "Execute the action you proposed"; `tasks.attempt_tool_calls == 1` and `attempt_first_tool_relay == 1`; and `tasks.prompt` names the recipient by user id or display name, whole-word and case-insensitive. Attachment basenames are cut from the prompt first, since a web send with no text stores a stand-in listing them. Names under two characters never match, since an article would. Everything else is held and later records `approval = 'user'`.

**The first-call flag is a strict parse, not the progress label.** `agent.events._lone_relay_ask` answers it from the raw tool input: Bash, one simple command whose argv starts `istota-skill relay ask`, no `;`, `&`, `|`, redirects, substitutions, parameter expansion, globs, newlines or assignment prefixes outside quotes, and no `$` or backtick inside double quotes. Single-quoted text is literal. Each brain computes it where it builds the `ToolUseEvent` (Claude Code's frame parser, both tmux paths, NativeBrain's `tool_execution_start`) and carries it as `ToolUseEvent.lone_relay_ask`; the adapter counts on that field alone. `_private_relay_tool` stays loose, because it decides what to hide and over-matching there costs nothing; used for authorization it let `q=$(curl …); istota-skill relay ask bob "$q"` or a bare `echo relay ask` count as a clean first call, and let a grep for `relay ask` stand in for a real ask whose own count had not landed. Never key the rule on `description`.

**The count is two dedicated columns, not `tool_start` events**, which are gated on `event_log_enabled` and `progress_show_tool_use`; a security decision cannot depend on a display setting. `TaskStreamAdapter.on_event` writes them for every `ToolUseEvent` before any display gating. All three brains reach it: NativeBrain awaits the emit before it runs the tool, and Claude Code writes when it reads the `assistant` frame, which can race the tool itself. **Every race fails closed**: an uncounted ask reads zero and is held. `db.record_attempt_tool_call` floors at the adapter's own running total (`MAX(old + 1, calls_seen)`) rather than incrementing or assigning, because a lost write under pure increment makes a relay ask look first, and a reclaimed task's stale worker under pure assignment can lower the count; this form only raises it. `reset_attempt_tool_calls` runs in `process_one_task`, in the same transaction as the move to `running`, so it cannot fail alone and leave the previous attempt's count. A caller with no event writer (REPL, CLI, non-scheduler callers) writes no count, so it is always held. The adapter writes only when `config.db_path` exists.

A clean-turn release does what `approve_request` does (queue, `approved_at`, `approved_digest = preview_digest`, deadlines) and skips `park_question`, `present_question` and the posted preview. The preview is still built and stored for the audit trail. Only the preview post is skipped: the asker's live Talk audience check still runs, because `deliver_question` calls `verify_private_audience` on the frozen origin for every queued question before it sends, whichever way it was released. The skill answers `queued` with `approval: "clean_turn"`; `!relay show` and the skill's `status` both show which way a question was released.

## Delivery

`drain_requests` hands every relay row to `relay.relays.deliver_question`, and `admit_request` decides the destination kind from `relay.relays.surface` and refuses a mismatch with the caller's surface.

**A participant list that cannot be fetched is not a wrong audience.** `verify_private_audience` raises `AudienceUnavailable` when `get_participants` fails (a Nextcloud 5xx, a timeout), a `RequestError` subclass with the same `unsupported_origin` code so callers answering a person refuse as before. `deliver_question` catches it ahead of `RequestError`, for the asker-origin check and the room destination check alike: nothing is claimed yet, so the request stays `queued` and the next drain retries it through `_pending_requests`. Past `queue_deadline` it closes `queue_expired`, as an expired queue does in `admit_request`. Only a list that was fetched and is wrong closes the relay (`unsupported_origin` for the asker, `destination_not_private` for the room). `deliver_returns` has the same shape and still records a fetch failure as `blocked`.

**Room.** Re-resolve through `check_room`; any resolution failure or fingerprint mismatch closes the relay `failed` with `destination_changed`, with no retarget. Then the live audience check in the daemon (`destination_not_private` when the room is shared; a fetch failure waits, as above). Then, in one transaction with admission, `db.add_message(..., delivery_reference="relay-question:<id>")`, which returns the existing row on a retry, so a retry cannot duplicate. Then the Talk post with the same reference; its id goes to `question_talk_id` and to the canonical row's `external_ids` as `{"talk": id}`, the shape `notifications.delivery.mirror_talk_to_room` writes, so a web reply and a Talk reply resolve to one relay. A Talk failure does not fail the relay: the web row is the question and stays answerable. The request stays `sending` across the post; recovery is `_pending_requests`' stale-claim arm, which reads back by reference and never re-posts. Not routed through `notifications.delivery.send_notification`, which takes no `delivery_reference`.

**WhatsApp.** Unchanged: the request-backed ledger admission checks consent, deadline, provider, binding fingerprint and approved renderings in its write transaction, and the destination comes from the same binding object the fingerprint was checked against. Questions debit the recipient's ledger with `task_id=None`, so the asker's task never appears in the recipient's alerts.

**SMS.** `deliver_sms(..., relay_question_id=)`, beside `relay_return_id`. Admission runs twice: a read-only `admit_request(status='check')` before the ledger insert to size the exact stored body, then `status='pending'` inside the claim transaction, taken `BEGIN IMMEDIATE`, so the request moves to `sending` with the claim or not at all. The number sent to is the one the second admission matched against the frozen hash. A provider switch does not fail admission, following the SMS rule that bindings survive it; the number hash is the check. A second admission failing after the insert leaves an unclaimed `pending` `sent_sms` row under `relay-question:<id>`: it opens no park gate, and the relay is closed so nothing sends under that key. Receipts reach `reconcile_question_delivery` through `apply_delivery_event`, so a failed SMS receipt closes a waiting relay.

Ledger outcomes map alike on both phone surfaces: accepted is `waiting`, unknown is `uncertain` and is never resent, a definite failure closes the relay. An exact-id answer is still accepted for an uncertain question until expiry. No network call runs under a writer lock.

## The recipient notification

**Neither Talk post enters later Talk history.** `context.build_talk_context` skips a message whose reference starts `relay-question:` or `relay-return:`, and the private-reply references `private-whisper:`, `private-confirmation:` and `private-proposal:` for the same reason: each was written by a task reading somebody else's words, and a reply to one reaches its task framed as the linked room's context. As a bot turn the question would reach the recipient's later tasks as another user's text read unframed in the daemon's voice; it already reaches the answering task framed, through `recipient_context`. The web history path needs no rule: it pairs `messages` user and assistant rows by task id, and relay rows are `role='system'` with no task.

`relay_question` is written in the same transaction that moves the relay to `waiting` or `uncertain`, and resolved by `resolve_by_object` on every close (answered, expired, failed, cancelled, blocked). A room question pushes with `deliver_pending` after that transaction; a phone question writes and does not push. The stored body is fixed text and never the question. Its action links to `/chat` only: the deep link `/chat?room=<token>&task=<id>` carries a query string that `SAFE_PATH_RE` and the client's `isSafeActionPath` refuse, and widening both allowlists was decided against. Details in `.claude/rules/notifications.md`.

## Answers

`accept_reply(conn, config, *, actor_user_id, relay_id, surface, inbound_id, text)` holds the common checks (state, expiry, block, emptiness, `_answer_fits`); `_destination_current` holds the per-surface one: provider and binding fingerprint for WhatsApp, the number hash for SMS, membership for a room. A room answer checks membership and not a live Talk call, because the reply was authored inside the room and the live check already ran at delivery. `inbound_id` is namespaced (`web:<messages.id>`, `talk:<id>`, `sms:<provider>:<id>`, the WhatsApp provider id), so `inbound_answer_id` stays unique across surfaces. The first accepted answer wins.

**A relay reply is checked before a confirmation reply on every surface**, so a quoted `yes` answers the relay and never approves a parked task. On web the intercept sits after the `!command` block and before the confirmation intercept; the spec's line reference put it after the confirmation intercept, which contradicts its own precedence rule. On Talk it sits after the parent capture and before `handle_confirmation_reply`. On both, a `!`-prefixed reply to a question is dispatched as a command, since the Talk poller dispatches commands before it captures a parent. A relay reply still cancels parked confirmations in that room under the ordinary new-message rule (a parked foreground task would otherwise hold the room under the claim gate); it never approves one.

The web and Talk intercepts create the recipient's ordinary task through `record_inbound` / `ingest_message` in the same `BEGIN IMMEDIATE` as the acceptance, linked by `recipient_task_id`, with `recipient_context` framing the question and outcome as untrusted content in the user half. `executor.build_prompt` injects it for web, Talk, WhatsApp and SMS. A rejected answer still creates the ordinary task with the rejection notice as context. `create_recipient_task` returns `None` for a Talk or web echo drop instead of raising, so one echo cannot roll back a whole poll batch for ever; WhatsApp still raises. Web and Talk store the raw text, whitespace included.

`!relay reply` in a room (`commands._relay_reply_in_room`) answers only a room relay and only from its destination room, so an answer cannot arrive through a surface the question never went to. It records the answer and returns the notice without creating a task. `parse_command` strips the arguments, so a command answer loses leading and trailing whitespace; everything after the one separator after the id is kept.

On WhatsApp, matching runs after dedup and STOP/START/HELP, before bare confirmation or generic command parsing; both adapters' quote ids and `!relay reply` require the bound recipient, and media captions never authorize forwarding. Unknown quotes during a send persist as bounded candidates, then settle into exactly one ordinary task on correlation or timeout without re-entering confirmation parsing. On SMS the intercept runs after STOP/START, the MMS refusal and the empty check, before `confirmations.parse_answer` and `!` dispatch; since `parse_answer` never matches a `!relay reply` text, the precedence that matters there is over command dispatch, where `cmd_relay` would refuse a non-room reply. SMS has no quote field. `parse_reply_command` is shared by the WhatsApp and SMS matchers.

## Returns

Web returns write the canonical message with a unique `delivery_reference` and settle in one transaction. Talk uses reference and readback; WhatsApp and SMS use their ledgers with an opt-in exact-body path. Returns never summarize, strip markdown, truncate, split or use a Cloud template. Origin privacy is revalidated before delivery; blocked and uncertain returns keep the answer for 30 days and raise a body-free `message_relay` notice. Recovery reads receipts or readback rather than resending. Bounded polls expire unanswered relays, reconcile late receipts and clear expired content while keeping identity and hash tombstones.

## Progress events

`agent/events._private_relay_tool` matches `relay ask` and the old `whatsapp ask`, so a stale instruction still cannot put a question into a trace. The shared renderer suppresses those arguments and model-authored descriptions before Claude Code, tmux and native events reach traces or progress subscribers, and the stream adapter suppresses the tool's output, whose JSON carries the preview. A shared log destination sees only the fixed "Private relay request" label. Talk origin verification reuses the transport's configured bot actor identities and requires exactly the asker and one bot participant.

## Schema

`db._migrate_message_relays_surfaces` rebuilds `message_relays` for the `room` / `whatsapp` / `sms` surface CHECK and the `destination`, `question_message_id`, `question_talk_id` and `approval` columns. The four columns are `ALTER`-added before the rebuild is attempted, so a refused rebuild leaves a table `schema.sql`'s new index can still be built on, and the next boot retries. The rename needs `PRAGMA legacy_alter_table=ON`, because the `whatsapp_request_task_deleted` trigger on `tasks` names `message_relays` and the modern rename refuses while that table is absent. `foreign_keys` is off for the rebuild, `foreign_key_check` refuses the commit on any violation, and the previous `foreign_keys` value is restored. `approval` is backfilled as `user` where `approved_at` is set, so a relay cancelled or expired while held records none. The migration keeps its own DDL copy, held equal to `schema.sql` by the fresh-versus-upgraded parity test in `tests/test_whatsapp_requests.py`. **It is a migration, so the upgrade tier (`scripts/test-upgrade.sh`) against a pre-rebuild database is owed before a release.**

## The same table carries private-reply requests

Multiplayer D16 put the shared-room hold on this machinery rather than a second table, so `whatsapp_skill_requests` has two more kinds, `side_whisper` and `room_post`, plus `origin` and `destination` columns, because those kinds have no `message_relays` row to keep them on. `db._migrate_skill_request_room_kinds` rebuilds the `kind` CHECK by the procedure above (foreign keys off, `legacy_alter_table` on, `foreign_key_check` before commit); the two columns are added first, so a refused rebuild still leaves every column the code reads and only a row of a new kind is refused. It is part of the upgrade-tier run owed before merge. `side_whisper` is a historical name, kept when side rooms were retired (ISSUE-608) because renaming it is a second CHECK rebuild for no change in behaviour; a whisper's destination is now `{"kind": "private_reply", "about", "user"}`, resolved to a private room at claim time, and `db._migrate_private_replies` deleted the requests bound for a side room. The verbs are in the `room` skill (`shared_room: safe`), not `relay`, and they are `rooms/private_replies.py`'s; the rules are in `.claude/rules/transport.md` ("Multiplayer rooms", its "Private replies" paragraph) and `docs/features/shared-rooms.md`.

Reused unchanged or widened in place: `_store_request`, `_validate_input`, the write transaction, the preview digest, `park_question`, `associate_confirmation`, `approve_request`, `_queue_question`, `_clean_turn`, `held_question`, `present_question`, `close_task_questions` and `drain_requests`. **Not reused**: `admit_request` and `_deliver_room_question`, which are relay-shaped (`message_relays` state, a recipient other than the asker, surface ledgers). `rooms.private_replies._claim` is the room-kind admission instead, re-checking the approval digest, parent membership and the frozen parent fingerprint (`relay.destinations.destination_fingerprint`) in the claim transaction. One held request per task is kept, since the task parks on one confirmation.

**The `room post` clean turn takes whole units.** The relay rule's recipient test is replaced by "the text is the member's own words": the whole prompt, one whole line, or one whole double-quoted span. A substring was accepted first and let a fragment that reversed its meaning skip approval. `agent.events._lone_relay_ask` accepts `istota-skill room post` so the first-call flag counts it, and `_private_relay_tool` hides both room verbs from progress traces, since a shared room's trace is read by everyone. Approval provenance (`user` or `clean_turn`) is returned to the skill and not persisted, since only `message_relays` has an `approval` column.

**Guest proposals** (D2, `guest_reply = held`) are `room_post` requests keyed `guest-reply-<task>`, destination the parent room, origin the host's private room from `private_room_for` (`{"surface": "notifications"}` when there is none, so the bell carries it). The preview is put to the host through the scheduler's privately routed park, and `present_question`'s body says to reply in the private chat or approve from notifications. The preview names the guest, quotes up to 500 characters of their words and carries the exact answer; approving completes the task with the approved text rather than re-running it, and the drain delivers the post. **No email thread** (email on rooms stage 4, which removed D20): `_post_destination` refuses an email-bound room with `email_thread`, so neither a guest proposal nor a `room post` carries a mail; mail awaiting approval is a draft. `relay.destinations.destination_fingerprint` includes a WhatsApp or email ref only when present, so stored relay fingerprints are unchanged, and the room migration still re-verifies the email refs stored before.

A stale `sending` room request is recovered by marking it sent, never by re-posting its Talk half.
