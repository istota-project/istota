# The container's setup

`istota setup` writes the stack's config, inside the istota image. The terminal wizard comes first, then the validator it shares with the web setup, then the setup server itself.

The standalone install (`install.sh --standalone`, its half of `setup_wizard.py`, `istota update` and `updater.py`) was removed in the release after the one that shipped `istota-stack import-standalone`. Outside the image, with no `--vm-dir`, `setup_wizard.setup_shape` raises `NOT_IN_THE_IMAGE`, which names `install.sh --local` and `import-standalone`, before anything is written; `install.sh --standalone` refuses with the same pointers. `istota serve` and `[web] auth = "none"` stay, for development on a checkout. The importer (`maintenance/standalone_import.py`, `.claude/rules/maintenance.md`) reads the old layout from constants of its own and imports nothing that was deleted.

## setup_wizard.py

`istota setup` inside the image (`ISTOTA_SETUP_SHAPE=container`, or `--shape container`, or `--vm-dir`) is the one deployment shape's wizard, replacing `docker/init.sh` and the per-boot `render-config.sh`. It runs as uid 10001 (`docker compose run --rm --no-deps --entrypoint istota-drop daemon istota setup --vm-dir /vm`) and writes `/data/config/config.toml` (0600, from `container_config_document` through `lib/toml_write`, only what the answers decide plus the container layout; every other key is left to the dataclass default), `/data/config/admins` (created and never modified: an existing file is left byte for byte alone even when it does not name the user, and a line says what to add, since appending would widen an allowlist the operator manages) and `/data/.secret_key` (created only if absent; an existing unusable file is a refusal, never a replacement). With `--vm-dir` it also writes `secrets/<name>` for every `SECRET_NAMES` entry (0400, empty when unused, because compose refuses a missing secret file) and merges its own keys into the stack's `.env` and `host.env`, keeping every other line. Without `--vm-dir` a credential with a config key is written into the 0600 config instead, and the two Claude Code credentials, which have none, are not written. A `--yes` run takes credentials from the environment under the names the daemon reads (`ISTOTA_NEXTCLOUD_APP_PASSWORD`, `ANTHROPIC_API_KEY`, …), never from argv. A re-run needs `--force` and keeps the web session key, and an empty answer for any credential keeps the existing non-empty file rather than emptying it, since a `--yes` re-run without a variable in its environment was not asked to delete that credential; removing one is deleting the file by hand. It refuses proxied ingress without an upstream address or with a wildcard listener.

**A re-run starts from the stack's files (#749).** `prior_answers(data_dir, vm_dir)` is the inverse of `container_config_document`, `host_env_values`, `stack_env_values` and `container_secret_values`, field by field, with `container_config_document` authoritative: `config.toml` through tomllib (storage is derived from `workspace_mount_path` and `[nextcloud] url`, not host.env's `STORAGE`), host.env's ingress keys, `.env`'s `COMPOSE_PROFILES`, and the secret files through `_read_secret_file`. The user is the one id with both a line in the admins file and a `[users.<id>]` block (`prior_user_ids`; `load_admin_users` is an unordered set, so "the first admin" is no rule); zero or several and the terminal asks as on a first run. A value setup cannot write back (a `brain.kind` other than `claude_code` or `native`, a profile outside the known set) is refused by name before any question, since a silent default would change a working install. A config that does not parse raises `PriorConfigUnreadable`; the terminal falls back to first-run defaults, the web re-run refuses. `collect_container_answers(..., prior=)` begins from a copy of the prior, so every default and every `--yes` fallback is the current value and an unasked question keeps it; flags still win. The kept user's per-user fields (display name, timezone, email, module toggles) are shown and not asked: the `user_profiles` row wins over `[users.X]` at load, and `ensure_profile` never overwrites it. `current_storage` stays the first-run fallback (a host folder kept without `--storage`). Both setup one-shots in `istota-stack` pass `-e ISTOTA_SECRETS_DIR=/nonexistent`, so `istota-secrets` exports nothing: the stored files would otherwise outrank a value passed with `-e` and hide the prior, and a credential prompt says "(Enter keeps the current one)". `write_container_setup(..., backup=RERUN_CONFIG_BACKUPS)` writes the config through `apply.write_config_with_backup` (`config.toml.bak.<stamp>`, newest ten). `tests/test_setup_container.py`'s identity table writes each first-run answer set, re-runs with `--yes --force` and with Enter at every prompt, and requires every written file byte-identical; that, not `prior(write(a)) == a`, is what holds the inverse, because the writer normalises fields.

**The forwarded port.** `forwarded_port(vm_dir)` reads `LOCAL_FORWARD_PORT` from the staged host.env, which only the Mac writes (0 when absent or not a plain port; a leading zero is refused here and in the shell alike). `ContainerAnswers.forwarded_port` is read, never asked, and written nowhere. With it set, the hostname default is `localhost:<port>`, and `validate_container_answers` refuses a `local` ingress whose `local_publish_port` differs ("This VM's port forward is N; use localhost:N."); the web wording is produced in `_web_message`. A portless hostname reads as 8080, so port 80 defaults to `localhost:80`, not bare `localhost`. Tests: `tests/test_setup_container.py`; the image tier runs it in the built image (`tests/image/test_istota_image.py::TestGroupCTheWrittenConfig`).

**What the container half also writes.** With full Nextcloud integration, `write_container_setup` stages `rclone.conf` in the `--vm-dir` (0600): one WebDAV remote named `nextcloud` at `<nextcloud_url>/remote.php/dav/files/<username>/`, or, when `dav_prefix` names the workspace's folder in the bot's files, an alias named `nextcloud` for that folder over a `nextcloud-root` WebDAV remote at that URL, so the mount serves the same tree every DAV call addresses. Rendered by `lib/rclone_conf.render_webdav_remote` with the app password through `lib/rclone_conf.obscure` (rclone's published scheme, AES-256-CTR under rclone's fixed key, so the image needs no rclone). The obscuring is salted and `provision.sh --digest` hashes the file, so a re-run goes through `rclone_conf.webdav_remote_for`, which keeps the previous file byte for byte when it is the rendering of the same answers under its own obscured password; `istota-stack`'s `new_staging` copies the installed `rclone.conf` into staging so the wizard has it to compare (#720). `host_env_values` writes `RCLONE_REMOTE=nextcloud`, empty otherwise, and `istota-stack setup` installs the file with `install_staged`. Obscuring is not encryption; the file's mode and owner are the protection, as for the secret file holding the same password. `maintenance/role_vars` renders and obscures through the same module, so the management role and setup cannot write different remotes. The interactive browser question defaults to yes; a `--yes` run without `--profile browser` still leaves it off, which keeps `tests/test_testbed_config.py`'s base config and any operator script unchanged.

## The shared validator, and the two front ends

The terminal wizard and the web setup (`istota setup --web`, below) produce one `ContainerAnswers` and go through one validator and one writer, per the install-onboarding-refresh finding that front ends with their own rules drift.

- **The sender check (ISSUE-746).** With email on, both front ends ask for the receiving mail server's authserv-id and explain what it is and where to find it (`AUTHSERV_ID_EXPLANATION` on the terminal, `StepConnections.svelte` on the web, `--authserv-id` for `--yes`). A value writes `authserv_id` and `confirm_sender_match = "verify"`; blank writes neither, so `off` stays the dataclass default. The validator refuses a value with whitespace or a delimiter through `config.authserv_id_is_one_token`, the loader's own rule.
- `validate_container_answers(a) -> list[FieldError]` holds every refusal `collect_container_answers` used to raise inline (proxied ingress without an upstream or with a wildcard listener, direct ingress with a self-signed certificate, the native brain without a model or key, signaling without Talk, an unknown profile). The terminal raises `SetupError` with the first error's message, so its wording is unchanged; the web returns them all as `{field, message}`. `tests/test_setup_container.py` drives each refusal through both.
- `answers_from_payload(payload, base=None)` maps the web draft onto `ContainerAnswers`, starting from a copy of `base` when given (a field absent from the payload keeps the base value), and `payload_from_answers(a)` is its inverse over `WEB_SETUP_FIELDS`, which seeds a re-run's draft. The profile check is "not offered by the web setup and not in `base.profiles`", so a re-run keeps `signaling`, `whatsapp-baileys` and `location`. Under non-proxied ingress it clears the proxied fields, under local storage the Nextcloud URL, and under Nextcloud the host folder, whatever the base had. Only `WEB_SETUP_FIELDS` are accepted, and an unknown key or a wrong type raises `PayloadError` (carrying the answers it could build, so the validator still runs over the rest). A missing or `null` key takes what a `--yes` run gives it, so both front ends agree on what an unasked question means. It reads the storage choice, not the presence of a URL, so Nextcloud fields left in a draft after switching back to local storage are not written. Under Nextcloud it reads `workspace` as the terminal's `--workspace` does: `mount` unless told `local`, and `local` turns `auto_share_bot_dir` off (#727).
- `write_container_setup(a, data_dir=, vm_dir=, out=)` is the write sequence after the answers, shared by `run_container_setup` and the web Finish, `config/managed.json` (every resource unmanaged, source `setup`) included. The two paths write byte-identical files for the same answers, which `tests/test_setup_container.py` and `tests/test_setup_web.py` hold.
- `DEFAULT_ANTHROPIC_MODEL`, `DEFAULT_OPENROUTER_BASE_URL` and `DEFAULT_OPENROUTER_MODEL` sit beside `DEFAULT_ANTHROPIC_BASE_URL`, one default each for both front ends.

The web setup adds rules of its own in `webui/setup_app.draft_errors`, because it also creates the first login: an email is required; the password goes through `auth.password_policy_error` with the dataclass-default policy; a username takes `auth.valid_new_user_id` with local storage, and with Nextcloud, where it is the user's Nextcloud id, `user_scope.is_scopable_user_id` and no leading `#` (the admins file reads that as a comment; `istota user ensure` itself checks nothing); direct and proxied ingress need a real hostname, since `answers_from_payload` reads a missing one as `localhost`; a subscription needs its token, since a first setup has no file to keep (`_subscription_errors` passes when the re-run's base already holds a Claude token or an Anthropic key). The terminal keeps accepting what it always has. In a re-run (`draft_errors` on a re-run state) the email, password and new-username rules are skipped, since a terminal-made id may fail `valid_new_user_id` and cannot be changed, and `_rerun_username_errors` requires the draft's `user_id` to be the existing user. Every place the server turns a draft into answers goes through `_answers_for(state, draft)`, which passes `base=state.prior` and the forwarded port, so `draft_errors`, the check route and Finish see the same answers. The shared validator's operator wording (option names, environment variables) is replaced by `_WEB_MESSAGES` for the page, field by field; the terminal's messages are untouched.

## The setup server: webui/setup_app.py

`istota setup --web [--force] --vm-dir /vm [--local]` runs a one-shot FastAPI app as uid 10001 in a `compose run` of the daemon image, before any config exists or, with `--force`, over one. It does not import `webui/app.py`, which loads config at import. It serves the built bundle under `/istota/` (the cache rule moved into `webui/static_dir.py`, which both apps use), redirects `/` and `/istota/` to `/istota/setup`, answers the setup API under `/istota/api/setup/`, and 404s everything else, `/istota/api/me` included. Without `--force` it refuses before binding when `/data/config/config.toml` exists (`_ALREADY_SET_UP`, which names `setup --web --force`); it always refuses without `--vm-dir`. `istota-stack setup --web` is the only intended caller (`.claude/rules/deployment.md`). The normal web app answers `GET /istota/api/setup/state` with `{phase: "configured"}` and nothing else of the API, so the page shows "already set up" there.

**Re-run mode (#750).** `--web --force` is `create_setup_app(rerun=True)`, which requires a config and refuses to start, naming the reason, when it does not parse ("fix it, or re-run in the terminal"), when `prior_user_ids` is not exactly one id (the ids are named), or when `prior_answers` refuses a value. `SetupState` carries `rerun`, `prior`, `existing_user` and `stored_credentials`, and the draft is seeded with `payload_from_answers(prior)`, credentials as their real values: no route returns them (`_redacted_draft`), and they pass the "needs its token" rules and are written back unchanged. `GET /state` adds `rerun` for anyone and `user_id` only with the session, since the route is unauthenticated and public on a server for up to an hour. The re-run's steps are `RERUN_SETUP_STEPS`, `SETUP_STEPS` without `RERUN_SKIPPED_STEPS = ("account",)`, a one-line literal the client's `setupDraft.test.ts` reads to hold its own list equal. **A stored credential follows its host** (`_CREDENTIAL_HOSTS`): when the draft changes `nextcloud_url`, `imap_host` or `caldav_url`, `_drop_moved_credentials` drops the matching seeded credential, and `_moved_credential_errors` requires it again, because `write_container_setup`'s keep-on-empty rule would otherwise send the old secret to the new host. Only a credential still holding its seeded value is dropped. The OAuth pair is not a draft field: another Nextcloud clears it in `_answers_for`, turning Nextcloud login off. Finish in a re-run writes with `backup=10`, skips `db.init_db` and the profile, identity and password step, writes the marker, and answers without `email`.

**The rollback snapshot.** `istota setup --snapshot DIR --vm-dir /vm` (uid 10001, `snapshot_for_rerun`) copies `config.toml`, `managed.json` and every file under `/vm/secrets` into a new directory (0700, files 0600), refusing links and an existing directory, which may be the only copy of an unfinished setup. `--restore DIR` (`restore_rerun_snapshot`) writes them back, config files through `apply.write_private` and secrets through `_write_secret_file`, removes any secret or config file the snapshot does not have, and removes the snapshot. Root acts on nothing under `config/` or `secrets/`, so `istota-stack setup --web --force` runs both as one-shots (`.claude/rules/deployment.md`). `tests/test_setup_container.py::TestTheRerunSnapshot`.

Its security properties, each held by `tests/test_setup_web.py` and the image tier's `tests/image/test_web_setup.py`:

- **The setup code is the boundary.** Root mints it and hands it over as the file `/vm/setup-code`, never an environment variable or argv. The printed address carries it in the URL fragment, which a browser never sends, and the page posts it once and clears it. Comparison is `hmac.compare_digest` on the normalized form (case, hyphens and spaces ignored, Crockford's O, I and L folded). Twenty Crockford characters hold 100 bits.
- **One session per process.** A right code is spent on use and sets `istota_setup` (32 random bytes, `HttpOnly`, `SameSite=Strict`, `Path=/istota`, `Secure` unless `--local`). A second unlock, even with the right code, gets the same 403 body as a wrong one. Five failures per client address per minute are 429; after fifty in total no unlock is accepted until a new run.
- **Requests.** Every state-changing route needs the session and an `Origin` (or `Referer`) whose host is the request's own `Host`, through `webui/request_guards.origin_refusal`, the leaf `webui/app.py`'s `_verify_origin` now calls with `[site] hostname` instead. Bodies are read by hand through `request_guards.read_bounded_body` under 64 KiB and never declared as pydantic parameters, so a refusal cannot echo a submitted credential. An unknown draft key is refused without being echoed.
- **Nothing reaches disk or a log before Finish.** The draft is in process memory; `GET /draft` returns a credential as `{set: true}`, and a credential sent as `null` keeps the stored value. uvicorn's access log is off and the request log names the path without its query. An hour with no request drops the session and the draft and exits 3.
- **Connection checks** (`webui/setup_checks.py`) build a throwaway `Config` from exactly what would be written, through `config.config_from_document` (extracted from `load_config` without env overrides or DB overlays), and call the client istota already uses: `llm.make_provider` and a one-shot completion for the model, `nextcloud/capabilities` and `nextcloud/_http.dav_request` and `shares.search_sharees` line by line for Nextcloud (the sign-in line is `capabilities.sign_in`, the classifier doctor's `nextcloud.connection` shares, mapped onto setup's own messages), the email skill's extracted `imap_session` plus SMTP `EHLO`/`STARTTLS`/`AUTH` for mail, a CalDAV `PROPFIND`, a DNS comparison for the address. Each has a 10-second deadline, answers plain messages with no exception text, logs a redacted reason, writes nothing, and the route allows twenty a minute. A Claude subscription has no live check. `OpenAICompatibleProvider.scrub` removes the key from a provider's error body before it becomes a logged message, which the Finish log-sentinel test found.
- **Finish** validates everything, then runs `write_container_setup`, `db.init_db`, `user_profiles.ensure_profile` (seeded from the `[users.<id>]` block just written, as the entrypoint seeds it), `auth.upsert_identity` and `auth.set_password`, then writes `/vm/setup-done` (0400, `O_EXCL|O_NOFOLLOW`), the marker `istota-stack` reads to tell a finished run from one that died after writing config. A failed step is a 500 naming it and the server stays up; every step is safe to repeat, and a retry under a different username than an earlier attempt wrote is refused, since the admins file is only ever created. The draft is cleared and the response is sent before the server asks uvicorn to exit 0.
