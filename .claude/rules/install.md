# The standalone install, and the container's setup

The local single-user shape: what the wizard writes and what the updater does with it. The container half of the same wizard follows, then the validator it shares with the web setup and the setup server itself.

## setup_wizard.py

Interactive first-run installer (`istota setup`) for the local single-user shape. Two of the things it writes are boundaries rather than config. `ISTOTA_SECRET_KEY` is generated into `istota.env` and **carried forward on a `--force` re-run**, on the same rule Docker's `entrypoint.sh` applies to `/data/.secret_key`: every credential in the secrets table is Fernet-encrypted under it, so regenerating orphans the lot with no way back, and a re-run is a config rewrite rather than a key rotation. `ISTOTA_WEB_TOKEN_KEY` is carried with it and is the one to notice, because the wizard never *writes* one: `webui/tokens.py` derives a second, independent Fernet from it for the `web_user_tokens` rows, so it is only ever present because an operator added it and the wholesale rewrite would delete a key with no recovery — carried forward, never generated, since that storage mode is opt-in. `ISTOTA_WEB_SESSION_SECRET_KEY` rides along for consistency, its loss being only invalidated cookies. **Two precedence rules decide *which* value is kept, and each is a way to write the wrong key into the file while looking correct**: the environment outranks the file, because `serve.load_env_file` is non-clobbering and an exported value is therefore the one actually in use (preserving the file's would write a value the daemon ignores, and the install would switch keys silently the day the export went away — the operator is told when the two differ, by name); and within the file the *first* line for a name wins, since `load_env_file` skips a name already in `os.environ`, so a duplicated `ISTOTA_SECRET_KEY` — precisely the shape an operator produces by appending the line a remedy told them to add to a file that already had one — must not be read as the later, dead one. Only a value meeting `credentials.store._MIN_KEY_LEN` is preserved, which is safe because nothing below the floor can have encrypted anything, and pinning a blank or truncated line would make the guard the bug. The env file is created `0600` through `os.open` rather than written and then chmod'd; the `fchmod` on the descriptor is the half that is easy to drop, since `O_CREAT`'s mode applies **only** to a file the call creates and the re-run is the one path where it pre-exists — so without it a hand-made 0644 `istota.env` is refilled with the master key at its original mode and narrowed afterwards, which is the same window on the only shape that has it. And it writes `{config_dir}/admins` naming the local user, pointed at by `ISTOTA_ADMINS_FILE` in the env file — an empty allowlist reads as "everyone" to `Config.is_admin` and as "nobody" to `is_shared_kv_writer`, so a standalone install with no file could not write a shared briefing block; the exemption in `is_shared_kv_writer` is the backstop for installs made before this, not the primary route. **It only ever creates**: an existing file is left byte for byte alone even when it does not name the user, and a line is printed instead, because the path is `config_path.parent / "admins"` with nothing asserting the standalone shape — `istota setup -c /etc/istota/config.toml --force` would otherwise append the wizard's user to exactly the file `load_admin_users` defaults to, a widening that survives the operator restoring `config.toml` from a backup. Membership is asked of `load_admin_users` rather than re-parsed, so the writer and the reader cannot drift on what a line means

## updater.py

`istota update` — self-update for the standalone install: reads install.json provenance, git fetch/reset the recorded checkout (stable channel = latest release tag, main channel = branch tip), `uv tool install --reinstall`, fresh-code migrations. Refuses on the server shape and while the scheduler/serve process holds its lock. Stop separate web and webhook processes too. The fresh CLI runs `init --relocate-rooms` before the operator restarts the local server; room or workspace refusals fail the update and leave it retryable.

## setup_wizard.py, the container half

`istota setup` inside the image (`ISTOTA_SETUP_SHAPE=container`, or `--shape container`, or `--vm-dir`) is the one deployment shape's wizard, replacing `docker/init.sh` and the per-boot `render-config.sh`. It runs as uid 10001 (`docker compose run --rm --no-deps --entrypoint istota-drop daemon istota setup --vm-dir /vm`) and writes `/data/config/config.toml` (0600, from `container_config_document` through `lib/toml_write`, only what the answers decide plus the container layout; every other key is left to the dataclass default), `/data/config/admins` (created, never modified, as above) and `/data/.secret_key` (created only if absent; an existing unusable file is a refusal, never a replacement). With `--vm-dir` it also writes `secrets/<name>` for every `SECRET_NAMES` entry (0400, empty when unused, because compose refuses a missing secret file) and merges its own keys into the stack's `.env` and `host.env`, keeping every other line. Without `--vm-dir` a credential with a config key is written into the 0600 config instead, and the two Claude Code credentials, which have none, are not written. A `--yes` run takes credentials from the environment under the names the daemon reads (`ISTOTA_NEXTCLOUD_APP_PASSWORD`, `ANTHROPIC_API_KEY`, …), never from argv. A re-run needs `--force` and keeps the web session key, and an empty answer for any credential keeps the existing non-empty file rather than emptying it, since a `--yes` re-run without a variable in its environment was not asked to delete that credential; removing one is deleting the file by hand. It refuses proxied ingress without an upstream address or with a wildcard listener. Tests: `tests/test_setup_container.py`; the image tier runs it in the built image (`tests/image/test_istota_image.py::TestGroupCTheWrittenConfig`).

**What the container half also writes.** With full Nextcloud integration, `write_container_setup` stages `rclone.conf` in the `--vm-dir` (0600): one WebDAV remote named `nextcloud` at `<nextcloud_url>/remote.php/dav/files/<username>/`, rendered by `lib/rclone_conf.render_webdav_remote` with the app password through `lib/rclone_conf.obscure` (rclone's published scheme, AES-256-CTR under rclone's fixed key, so the image needs no rclone). The obscuring is salted and `provision.sh --digest` hashes the file, so a re-run goes through `rclone_conf.webdav_remote_for`, which keeps the previous file byte for byte when it is the rendering of the same answers under its own obscured password; `istota-stack`'s `new_staging` copies the installed `rclone.conf` into staging so the wizard has it to compare (#720). `host_env_values` writes `RCLONE_REMOTE=nextcloud`, empty otherwise, and `istota-stack setup` installs the file with `install_staged`. Obscuring is not encryption; the file's mode and owner are the protection, as for the secret file holding the same password. `maintenance/role_vars` renders and obscures through the same module, so the management role and setup cannot write different remotes. The interactive browser question defaults to yes; a `--yes` run without `--profile browser` still leaves it off, which keeps `tests/test_testbed_config.py`'s base config and any operator script unchanged.

## The shared validator, and the two front ends

The terminal wizard and the web setup (`istota setup --web`, below) produce one `ContainerAnswers` and go through one validator and one writer, per the install-onboarding-refresh finding that front ends with their own rules drift.

- `validate_container_answers(a) -> list[FieldError]` holds every refusal `collect_container_answers` used to raise inline (proxied ingress without an upstream or with a wildcard listener, direct ingress with a self-signed certificate, the native brain without a model or key, signaling without Talk, an unknown profile). The terminal raises `SetupError` with the first error's message, so its wording is unchanged; the web returns them all as `{field, message}`. `tests/test_setup_container.py` drives each refusal through both.
- `answers_from_payload(payload)` maps the web draft onto `ContainerAnswers`. Only `WEB_SETUP_FIELDS` are accepted, and an unknown key or a wrong type raises `PayloadError` (carrying the answers it could build, so the validator still runs over the rest). A missing or `null` key takes what a `--yes` run gives it, so both front ends agree on what an unasked question means. It reads the storage choice, not the presence of a URL, so Nextcloud fields left in a draft after switching back to local storage are not written.
- `write_container_setup(a, data_dir=, vm_dir=, out=)` is the write sequence after the answers, shared by `run_container_setup` and the web Finish. The two paths write byte-identical files for the same answers, which `tests/test_setup_container.py` and `tests/test_setup_web.py` hold.
- `DEFAULT_ANTHROPIC_MODEL`, `DEFAULT_OPENROUTER_BASE_URL` and `DEFAULT_OPENROUTER_MODEL` sit beside `DEFAULT_ANTHROPIC_BASE_URL`, one default each for both front ends.

The web setup adds rules of its own in `webui/setup_app.draft_errors`, because it also creates the first login: an email is required; the password goes through `auth.password_policy_error` with the dataclass-default policy; a username takes `auth.valid_new_user_id` with local storage, and with Nextcloud, where it is the user's Nextcloud id, `user_scope.is_scopable_user_id` and no leading `#` (the admins file reads that as a comment; `istota user ensure` itself checks nothing); direct and proxied ingress need a real hostname, since `answers_from_payload` reads a missing one as `localhost`; a subscription needs its token, since a first setup has no file to keep. The terminal keeps accepting what it always has. The shared validator's operator wording (option names, environment variables) is replaced by `_WEB_MESSAGES` for the page, field by field; the terminal's messages are untouched.

## The setup server: webui/setup_app.py

`istota setup --web --vm-dir /vm [--local]` runs a one-shot FastAPI app as uid 10001 in a `compose run` of the daemon image, before any config exists. It does not import `webui/app.py`, which loads config at import. It serves the built bundle under `/istota/` (the cache rule moved into `webui/static_dir.py`, which both apps use), redirects `/` and `/istota/` to `/istota/setup`, answers the setup API under `/istota/api/setup/`, and 404s everything else, `/istota/api/me` included. It refuses before binding when `/data/config/config.toml` exists, with `--force`, without `--vm-dir`, or with `--shape standalone`. `istota-stack setup --web` is the only intended caller (`.claude/rules/deployment.md`). The normal web app answers `GET /istota/api/setup/state` with `{phase: "configured"}` and nothing else of the API, so the page shows "already set up" there.

Its security properties, each held by `tests/test_setup_web.py` and the image tier's `tests/image/test_web_setup.py`:

- **The setup code is the boundary.** Root mints it and hands it over as the file `/vm/setup-code`, never an environment variable or argv. The printed address carries it in the URL fragment, which a browser never sends, and the page posts it once and clears it. Comparison is `hmac.compare_digest` on the normalized form (case, hyphens and spaces ignored, Crockford's O, I and L folded). Twenty Crockford characters hold 100 bits.
- **One session per process.** A right code is spent on use and sets `istota_setup` (32 random bytes, `HttpOnly`, `SameSite=Strict`, `Path=/istota`, `Secure` unless `--local`). A second unlock, even with the right code, gets the same 403 body as a wrong one. Five failures per client address per minute are 429; after fifty in total no unlock is accepted until a new run.
- **Requests.** Every state-changing route needs the session and an `Origin` (or `Referer`) whose host is the request's own `Host`, through `webui/request_guards.origin_refusal`, the leaf `webui/app.py`'s `_verify_origin` now calls with `[site] hostname` instead. Bodies are read by hand through `request_guards.read_bounded_body` under 64 KiB and never declared as pydantic parameters, so a refusal cannot echo a submitted credential. An unknown draft key is refused without being echoed.
- **Nothing reaches disk or a log before Finish.** The draft is in process memory; `GET /draft` returns a credential as `{set: true}`, and a credential sent as `null` keeps the stored value. uvicorn's access log is off and the request log names the path without its query. An hour with no request drops the session and the draft and exits 3.
- **Connection checks** (`webui/setup_checks.py`) build a throwaway `Config` from exactly what would be written, through `config.config_from_document` (extracted from `load_config` without env overrides or DB overlays), and call the client istota already uses: `llm.make_provider` and a one-shot completion for the model, `nextcloud/capabilities` and `nextcloud/_http.dav_request` and `shares.search_sharees` line by line for Nextcloud, the email skill's extracted `imap_session` plus SMTP `EHLO`/`STARTTLS`/`AUTH` for mail, a CalDAV `PROPFIND`, a DNS comparison for the address. Each has a 10-second deadline, answers plain messages with no exception text, logs a redacted reason, writes nothing, and the route allows twenty a minute. A Claude subscription has no live check. `OpenAICompatibleProvider.scrub` removes the key from a provider's error body before it becomes a logged message, which the Finish log-sentinel test found.
- **Finish** validates everything, then runs `write_container_setup`, `db.init_db`, `user_profiles.ensure_profile` (seeded from the `[users.<id>]` block just written, as the entrypoint seeds it), `auth.upsert_identity` and `auth.set_password`, then writes `/vm/setup-done` (0400, `O_EXCL|O_NOFOLLOW`), the marker `istota-stack` reads to tell a finished run from one that died after writing config. A failed step is a 500 naming it and the server stays up; every step is safe to repeat, and a retry under a different username than an earlier attempt wrote is refused, since the admins file is only ever created. The draft is cleared and the response is sent before the server asks uvicorn to exit 0.
