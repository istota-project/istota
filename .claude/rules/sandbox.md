# Sandbox, task runtime and process boundaries

The boundaries a task runs inside and the modules that build them. `executor.md` owns `execute_task()`; this file owns the environment it hands over. The devbox bullet is in `devbox.md`.

## Security posture

**Multi-user vaults need a sandbox.** With more than one configured user (vault or not), vaults require `effective_sandboxing` or `[security] allow_unsandboxed_multi_user_vaults = true` (default false). `credentials.names.vault_isolation_refusal` gates import/export, task credential loading and proxy writes; it withholds cached credentials without deleting rows. Doctor fails and the settings card refuses; with the opt-in doctor still warns (same-uid exposure). Restart services and stop tasks after changing the policy or adding users. Manifest-injected credentials are unaffected.

- **Sandbox** (`bwrap`): per-user filesystem isolation. Linux + bubblewrap is the only supported deployment.
- **Every brain's tools run in the sandbox, one namespace per attempt.** `NativeBrain` spawns `istota.sandbox.tool_server` per attempt via `build_bwrap_cmd(..., profile=NATIVE)` (`BrainRequest.tool_server_wrap`), places it in the task cgroup from `preexec_fn` and reports its pid via `req.on_pid`; the daemon holds proxies (`session/tools/remote.py`). On `claude_code` the CLI spawns the same wrapped process through `sandbox/tool_launcher.py`, which reports its pid down a FIFO; the harness authorizes it only when it descends from the CLI, and it inherits the task cgroup from the CLI (`brain.md`, "The CLI tool harness"). The `claude` CLI itself runs outside the sandbox with its machine-acting built-ins denied (`brain.md`, "The tool server"). `SandboxProfile` has one member, `NATIVE`, for this release: `CLAUDE` and its binds (`~/.local/bin`, `~/.local/share/claude`, `~/.local/state/claude`, the `~/.claude` tmpfs, `.credentials.json`, `settings.json`, `projects`, `debug`, `todos`, the system-prompt file) went with the in-sandbox CLI, and `build_mount_plan` / `build_bwrap_cmd` / `build_daemon_sandbox` lost `cli_auth_mode`. Before ISSUE-389 file tools ran on daemon threads behind `executor.native_fs_roots` and `Bash` built a namespace per call with the CLI's runtime block. The roots are still enforced: the error-message layer, and the only confinement on unsandboxed shapes. Transport is an inherited socketpair for native and the CLI's stdio for `claude_code` (nothing listens, no peer to authenticate); `close_fds` keeps the socketpair from Bash children, and the `--mcp` front end moves the stdio stream off fds 0 and 1. No enable flag, deliberately (it would keep two tool paths); `build_bwrap_cmd` returns the command unchanged where bwrap is unavailable. Rollback is a revert.
- **No databases in the sandbox.** `build_bwrap_cmd` ends by masking `db_path.parent` and `module_db_root()` with an empty read-only tmpfs, last so no earlier bind shows through, with `--remount-ro` and `--disable-userns` (plus required `--unshare-user`) where supported: a writable mask lets `sqlite3` create a zero-byte file that reads as corruption, and a tmpfs can be unmounted from a nested userns. So keep `sandbox_ro_paths` narrow; the mask does not make a broad entry safe. Nothing binds the framework DB (`sandbox_admin_db_write` retired), `sandbox_ro_paths` defaults to `[]`, `native_fs_roots` matches. Host-side skill CLIs scoped by `ISTOTA_USER_ID` are the per-user boundary; masks are defence in depth.
- **Session logs are unbound: an absence, not a guard.** Native transcripts (assembled prompt, `USER.md`) go to `{db_path.parent}/logs/{user_id}/` (`/data/db/logs` on Docker), bound nowhere, in no `native_fs_roots` root. Kept out by `security.sandbox_ro_paths` defaulting to `[]` (its old `/srv/app` default exposed every DB) and, where `workspace_path` equals `db_path.parent`, no `user_resources` row naming it. The mask backs this on the stack, whose run contract lets bwrap run; it does not where nothing is sandboxed (`native_fs_confinement_active` gates on `effective_sandboxing`), and `_mask_dir` refuses where the database sits in the workspace. `doctor`'s `runtime.session_log_dir` asks `executor.mask_shadowed_by`, reporting availability (`executor.effective_sandboxing`, not `sandbox_enabled`, ISSUE-381) then placement; under `probe=False` it uses `effective_sandboxing_if_known` and reports unestablished. Never `user_temp_dir`. Tasks read transcripts via `istota-skill tasks transcript`.
- **One admin's repos are not in another's sandbox.** `build_bwrap_cmd` binds `{repos_dir}/{user_id}` (holding `{namespace}/{project}.git`), never the root; `native_fs_roots` matches; `DEVELOPER_REPOS_DIR` comes only from developer `setup_env`; `sandbox.host_paths.resolve_under_repos` scopes `--worktree`. The cache is derived at `{repos_dir}/{user_id}/.package-caches` (same mount as a venv for `link(2)`; retired the ISSUE-319 sibling masks). **Gated on `sandbox_cache_is_derived`, the repos bind's condition including `is_admin`; a boundary** (ISSUE-320): the later repos bind buries a symlink swapped in between check and `mount`. Non-admins get the fallback root or none; no separate cache write root in `native_fs_roots`. `maintenance/repos_relocate.py` moves old trees.
- **Config dir out of the sandbox.** Prompt-text files and `config.toml` live in `config/`, never bound, `config/system-prompt.md` included: `NativeBrain` reads it in the daemon, and the CLI, which opens it via `--system-prompt-file`, runs outside the sandbox. `executor._sandbox_bind_targets` still lists `~/.local`, `~/.claude` and that file, though nothing binds them, because the daemon runs the CLI from them and a `sandbox_cache_dir` at or above one would hand the model write access to the binary or the token.
- **Network proxy**: `--unshare-net` + CONNECT proxy on a Unix socket, `host:port` allowlist (`executor._build_network_allowlist`: PyPI under `allow_pypi`, `extra_hosts`, then skill-gated hosts). **The name is not the check** (ISSUE-883): every upstream connect, raw or brokered (`intercept._requests` through `network_proxy.checked_connection`), resolves once through `net_guard.checked_addresses` and connects to the checked address; a non-public answer is a 403 unless the name is one the operator wrote (`executor._network_private_hosts`: `extra_hosts` and the configured forge and Nextcloud URL hosts), so only the built-in defaults must resolve public. `[security.network] private_hosts` is retired: parsed, warned about, never read, since requiring a second listing of a host the operator already allowlisted guarded nothing. A raw tunnel answers 200, then `read_client_hello` must find one SNI equal to the CONNECT host (none only for an IP literal) before a byte goes upstream; otherwise it closes. Residual: HTTP `Host` inside the TLS is unseen, so domain fronting through an allowed shared front still works; ECH is refused. No Anthropic host: nothing in the sandbox calls a model, so `api.anthropic.com:443` and `mcp-proxy.anthropic.com:443` left the defaults and the `anthropic` provider's base-URL host is not added under "api_key"; a task that needs one names it in `extra_hosts`. TLS interception only for credential-bound hosts in the task snapshot, when the broker is enabled.
- **Skill proxy.** Strips secret env vars; CLI calls go through a Unix socket injecting credentials server-side, decoupled from skill selection. Required wherever the sandbox is (`istota-skill` refuses under `ISTOTA_SANDBOXED`). DB paths (`ISTOTA_DB_PATH`, manifest `proxy_only`) go to the proxy only. Requests: `credential` (manifest lookup for git and forge helpers), `vault_list` / `vault_credential` / `vault_entry` (map from `task_env`, capped by `vault_fetch_limit_per_task`, which counts distinct credentials: a `(channel, type, name)` already served in full this attempt is free, anything not yet served is charged every time, absent or refused; keyed by channel so a value a skill got privately is not free to the model; ISSUE-743). `sandbox/credential_shim.py` goes to `{user_temp_dir}/.istota/istota-credential` (0700) on the model's PATH only, never `proxy_base_env`'s; `.istota` is re-bound read-only after the workspace (like `.developer`). The shim is a convenience, not a gate. **The socket gates which task asks** (ISSUE-550): 0600 stops other uids, not other tasks. The proxy serves only kernel-reported peers descending from pids its task registered: the brain child via `on_pid` (to `authorize_pid` first) and spawned skills (`sandbox.peer_process.reporting_pid`, revoked on exit), pinned to start time against pid cycling. Narrows rather than closes cross-task access on unsandboxed multi-user hosts; `security.proxy_peer_check` warns. Env nonce rejected (same uid reads env). A brain skipping `on_pid` gets every skill call refused.
- **Host paths in skill CLIs.** A model-chosen host path is an arbitrary read or write unless scoped. **The disposition sits on the argument** (ISSUE-447): `skills/_hostpath.host_path` stamps it; `skills/_cli.parse_and_resolve` resolves before dispatch and writes back; refusal is `reason: host_path_refused`. Modes by where bytes end up: `READ` (deferred dir, own workspace, own channel, the task's attachment copies under `ISTOTA_ATTACHMENTS_DIR`, mirroring binds); `WRITE` (minus read-only roots); `EGRESS` (workspace and deferred dir, for content mailed, indexed, uploaded or persisted); `REPO`, `REMOTE`, `NOT_A_PATH` resolve nothing. Never the mount whole; no directory is created at parse. `open_resolved` walks every component of the validated absolute name from the filesystem root without following links, then checks the opened leaf is regular. Readers retain that descriptor; `write_resolved` creates parents through directory descriptors and checks the leaf before truncation. Consumers that only accept pathnames use `stage_resolved`, a private copy removed after the call. Feeds exports return bytes to the facade for a confined write. Deferred health sources use the same open at replay.
- **Coverage.** `tests/test_skill_host_paths_coverage.py` builds every parser (`build_parser`, Click `build_cli`) and requires each path-shaped argument to have a stamp or registry record (`UNSCOPED` is gone). `tests/test_skill_host_paths_refusals.py` drives each resolving stamp for refusal and acceptance. **`google_workspace` is bounded by an argv scan, a weaker claim**: `gws` cannot be walked, so `scan_argv` classifies tokens (absolute, `~`, `..`, existing relative, `=` split, short-flag tail, leading `@`) and resolves them under the read rule (`drive +upload` takes a Talk attachment). An admitted file is copied through `open_resolved` into launcher-owned staging and made read-only; directories are refused. The workspace is used only to interpret relative inputs. Execution uses a private non-writable cwd, so a not-yet-existing relative token cannot write into the workspace. Local output files are unsupported. `skill_file_env` gives the proxy, scheduled skill runner and direct skill client the same staging lifetime, including cleanup after exec or timeout.
- **Nothing narrows what the daemon itself may read**; argument scoping is the only layer. Cut: a systemd read allowlist (leaves `{istota_home}` and the mount readable) and a bwrap `SandboxProfile.SKILL` (needs a conditional DB mask, `config/` bound, an ISSUE-390 carve-out, a per-skill table).
- **No Docker API in the sandbox.** No socket bound, no `DOCKER_HOST`; a `docker` binary fails at connect. The per-user `/var/run/docker.sock` proxy is retired (`docker exec` through it lost exit status, forcing the exec transport).
- **The web container reaches every live browser's display, and nothing else in the browser container.** The `browser-console` volume (`/run/istota-browser-console`) is mounted in `browser` and `web` only, never the daemon, so no task sandbox can see it; `tests/test_browser_console_exposure.py` holds that. Each x11vnc listens there on `<console_socket_name(user)>` (`lib/browser_console.py`, vendored to `docker/browser/lib/` by `scripts/sync-devbox-lib.sh`), mode 0660, group 10001, in a 2710 directory the web uid can traverse and not list. The web container stays off the browser network (ISSUE-699), so it has no route to the browser API on 9223. It can still drive every signed-in Chrome over VNC, unauthenticated where `VNC_PASSWORD` is unset: the admin console's step-up gates the admin's request, not the process, so code execution in the web process now reaches the browsers. Accepted, since that process already holds the stack's credentials and every admin session. The console also trusts the browser container's `browser` user, which owns the directory and writes every socket: a compromised browser container could map one user's socket name to another display or to a fake RFB server, and `connect_no_follow` refuses only a symlink or a non-socket at the leaf. Accepted, since that container already holds every user's profile. Loopback 6080 (websockify and noVNC) is the break-glass path.
- **Native WebFetch** (`session/tools/web_fetch.py`): daemon netns, outside the CONNECT allowlist, credential-free (`trust_env=False`), SSRF-hardened (each resolved IP checked per hop and pinned, GET/text only, caps, untrusted delimiter). **Every brain**: a `claude_code` task gets it through the harness's second MCP server, `istota_web` (`HarnessSpec.web_fetch`, `brain/_web_fetch_mcp.py`: unwrapped, the CLI's env cleared, never reported to the proxies), and the CLI's own WebFetch is denied, which widened CLI-brain egress from the CONNECT allowlist to any public host. **Every user** (ISSUE-449): the `[brain.native.web_fetch]` egress policy bounds all alike; `admin_only = true` restores the gate (read by `build_allowed_tools`, not mapped onto `WebFetchPolicy`). `require_url_provenance` as non-admin default rejected: its corpus is the user half, so WebSearch-then-read fails. See `brain.md`.
- **Deferred DB**: sandboxed tasks write JSON to temp; the scheduler applies it after success. Identity (`user_id`, `conversation_token`) from the task, never the JSON. Subtasks admin-only, capped by `max_subtasks_per_task`, `max_subtask_depth`, `max_subtask_prompt_chars`.

### The credential store

`credentials/store.py` is the only live store. `names.py` owns slugging, password generation and the multi-user isolation gate. `kdbx_import.py` parses an upload and applies selected entries; `kdbx_export.py` is the sole KeePass writer and saves only to memory. Generated credentials stay in the table. `vault_retire.py` keeps one final reader and the legacy storage path resolver for one release; it imports without deletion, leaves the file unchanged, deletes the stored passphrase and old KV state, and records a retirement marker. Database startup converts leftover source values only after this marker, so startup cannot erase the ownership information the final import needs.

History is limited to `vault_entries`, ten versions per field and the configured age. Audit records names, actors and bounded metadata, never values. Web exports, recovery reveals, recipient changes, restores and purges require an emailed code tied to the native identity, action and session. The optional age backup includes credentials only, excludes connected-service secrets and wallet cards, and writes ciphertext to the user's exports folder. Keep the server secret key outside database backups.

## Shared rooms and groups in the mount plan

A turn runs with its sender's reach (ISSUE-576). `rooms.scopes.withheld_for_task(conn, task)` is the one derivation: every scope on a guest's turn, every scope on a task in a shared room no member asked there (no origin surface, as for a subtask, CLI or heartbeat task), nothing otherwise, a member's turn with a guest present included. **Nothing in an email thread room** (`rooms.scopes.is_email_thread_room`, a binding with `surface='email'` on the canonical token, asked first): the thread is the host's correspondence, so a correspondent's admitted mail runs as the host at full reach with ambient memory loaded (`ambient_memory_off` answers False ahead of the roster and audience), bounded by the untrusted-sender gate and the outbound gate rather than a scope rail (email on rooms, section 2a). `record_inbound` skips the guest branch there, so such a task has no `guest_participant_id`. The stored-author arm that used to withhold an outside correspondent's turn is gone; `written_by_someone_else` stays for `private_replies.my_notes_room` and the skill proxy's `mail_account` channel (`not_owner_turn`). A read error on that check withholds every scope. **A member's own schedule counts as their turn** (ISSUE-594): a `scheduled` task whose `scheduled_job_id` names a job row owned by the task's user, or a `briefing` task with a `briefing_name`, in a room that user is a current member of, withholds nothing (`rooms.scopes._members_own_schedule`). The job lives in the user's workspace and names the room as where its answer is read, which is the consent a live turn carries. Under bwrap a guest's turn and a restricted task cannot write that file; on an unconfined shape a guest's tools can, which `security.room_scope_confinement` names, though such a job could already be aimed at the host's private room at full reach. Membership is a `room_members` row plus, where the user has any principal participant row, a present one, because Talk records a departure only as `left_at`. A job row owned by someone else, an owner who left the room, or a scheduled task flagged `is_group_chat` still withholds every scope. A read error on the second case withholds everything. Read by `effective_disabled_skills`, the proxy's `cli_skills`, `derive_authorized_skills` and identity env (`reach_index`), setup-env hooks (env dropped), and the mount plan. A member's turn in a shared room loses only ambient memory, in prompt assembly (`.claude/rules/prompts.md`). Per-room grants, `!room share` and `[rooms] shared_room_data_policy` are gone; `room_data_grants` is dropped by migration. Rules: `transport.md` ("Multiplayer rooms"), `docs/features/shared-rooms.md`.

What a restricted task gets:

- **No workspace without `files`**: `{mount}/Users/{user_id}` and per-resource mounts unbound. Without `developer`, repos and cache go too, dropped in `resolve_sandbox_cache_dir` so bind and `UV_CACHE_DIR` agree (ISSUE-320).
- **Own temp dir**: `{temp}/{user}/emissary-task-<id>` for a guest, `room-task-<id>` otherwise, also `ISTOTA_DEFERRED_DIR`, since a guest-planted op file in the persistent per-user dir would replay at the host's authority. `executor.task_deferred_dir` reads the choice from disk (restriction can change before drain); all deferred and `email_output` readers use it. A symlink there fails the task by return.
- **No Talk bind, for any task** (ISSUE-880, below).
- **`ISTOTA_WITHHELD_SCOPES`** is in the proxy base env only. `env_host_roots` drops the workspace without `files`; `sandbox.host_paths.memory_refusal` refuses memory dirs; the `skills` guard unions it with `withheld_for_task` over `ISTOTA_TASK_ID`; nextcloud `_scoped` refuses file and share verbs without `files`, and memory paths without `memory`, after collapsing a leading `//`. Without `memory`, `files list --depth` and `files search` drop entries inside memory dirs. Residual: `share list` (`--subfiles` or no path) and `files trash list` still show them.
- **Talk writes check the live roster**: `nextcloud talk send`, `share-file`, `rename`, `describe`, `invite`, `leave`, `delete` refuse unless participants are caller plus bot; posting into the task's own room is exempt, changing a shared room never; `invite` takes only the caller; an unfetchable roster refuses. Unchecked outside a task.
- **Vault withheld whenever anything is**: `vault_credentials={}`, `vault_write_limit=0`, no prompt line. Calendar discovery skipped without `calendar`.
- **`Groups/<id>`**: each group in `rooms.scopes.task_group_ids` bound read-write as `nextcloud_group_dir` after the channel bind, sorted, de-duplicated, via `sandbox.user_scope.scoped_user_dir`. `Groups/` never bound. Empty for a guest turn, stored-mixed turn, any guest/agent/unmapped participant, no recorded readers, or readers the members do not cover; `rooms.group_id` narrows. `project_fs_roots` carries it. `ISTOTA_TASK_GROUPS` (proxy env only) gates kv/memory `--group` (`skills/_group_access`, whole-id); deferred kv re-derives from the task row.

**Without bwrap none of this confines**: Docker, macOS and a config with the sandbox off strip prompt, skills, allowlist and env, but tools can still read the workspace; `security.room_scope_confinement` warns. Witness: `tests/smoke/test_sandbox_shared_room.py` with a private-room control; the default suite reads argv only. The memory masks, the bot-directory self-bind and `IDENTITY_GUARD` (Stage 28) were removed with the grants: they fired only for `files` granted without `memory`, which no turn can be any more.

## No task reaches the flat Talk folder

On the Nextcloud mount `{mount}/Talk` is the bot account's `Talk/`, flat, holding the attachments of every conversation the bot is in. No sandbox binds it and no host-path root names it (ISSUE-880); before, every unrestricted task had it read-only, so any user's task could list and read another room's files. `executor.stage_attachments` copies the task's own attachments, Talk files and the nc-data fallback, into `{control_dir}/room-attachments` (`O_EXCL | O_NOFOLLOW`, from an fd opened by `sandbox.attachment_source`), and `task.attachments` names the copies in memory only; with `files` withheld it also copies inbox files under `Users/<uid>`. The control dir is bound read-only, so the copies are readable and not writable. Skill CLIs get the directory as `ISTOTA_ATTACHMENTS_DIR`, a `READ` root that `WRITE` and `EGRESS` drop (`workspace_roots(attachments_dir=)`, `env_host_roots(attachments=)`). The audio path copies a staged file into the deferred dir as before (`extra`). Each copy is capped at `[talk] attachment_max_mb`, the local workspace fetch's cap, since `temp_dir` is tmpfs on the stack; an over-cap file stays named and unread, and an inbox copy for a restricted task is not capped. Residuals: a file named only in older conversation history, never sent to this task, is no longer readable, and giving one back needs a lookup through room membership, which is not built; and an admin's task can still reach `/Talk` through the `nextcloud` skill's WebDAV verbs, since `nextcloud/_http.resolve_scoped_path` leaves an admin unscoped on the bot's account.

## Group web access and managed writes

`groups.policy` checks current membership on member web reads and writes, independent of owner management authority. An admin outside a group may inspect metadata and membership through admin routes but gets no notebook or viewer bypass. `workspace.places.list_places` and `webui.chat_files.servable_roots` derive current memberships on each request, so removal or archive removes listing, preview and download access on the next request. Membership grants no access to another member's personal files, memory or credentials. The task audience gate above stays unchanged; a running task can retain an admitted snapshot or bind after removal.

Web notebook saves and the host-side memory CLI lock the same resolved file under `{db_path.parent}/locks/group-memory`, from trusted host configuration. That anchor is outside sandbox mounts and must be shared with writable permissions across the daemon and web services. Managed saves preserve explicit read refusals and recheck membership under the lock before replacement. Admitted task directories remain writable, so direct filesystem edits can bypass this managed lock and audit trail. There is no automatic group writer.


## sandbox/confined.py

**User-controlled file access goes through `confined`, anchored at a daemon-composed root, by fd, never by name** (ISSUE-779). #775, #776 and #782 were one defect: a path checked, then used again by name, so a task that can write the tree swaps a component for a link in between. The anchor is a root the daemon builds from its own config (`Config.workspace_root(user_id)`, the mount, a temp dir), never a path from user data or a resolved descendant, because the walk follows a link at its anchor. `open_dir` walks every component below it `O_NOFOLLOW`; `open_regular_at` / `open_regular` open the leaf `O_NOFOLLOW | O_NONBLOCK` with `S_ISREG` on the fd; `open_or_create_dirs` is the writing walk; `parts_below` turns a daemon-spelled path into components by spelling; `valid_part` is the one component rule. Then read, `fstat`, `scandir`, `rename` and `unlink` through the fd with `dir_fd`. Serving over HTTP is `webui.fd_response.fd_file_response`, kept in the web package because it needs Starlette while this module is stdlib-only. The old names re-export (`skills._loader.open_overlay_dir`, `attachment_source.open_regular_at`, `workspace.writes.open_or_create_dirs`), and tests patch them there, so callers that reach them through those modules keep working. `skills._loader.contained_overlay_dir` is resolve-then-compare and is not part of it.

`tests/test_confined_file_access.py` is the tripwire: `FileResponse` anywhere in `src/` fails, and so does a function that both resolves a path and tests containment (`is_relative_to`, `commonpath`, `relative_to`, `.parents`, `path_under_roots`, `is_within`, `startswith`, or `==` / `in` against the resolved value) unless it is on `RESOLVE_THEN_COMPARE_ALLOWED`. That list holds the functions that existed when the guard landed; a stale entry fails, and `ALLOWLIST_CEILING` caps its size, so lower the ceiling as entries come off. The scan is per function: a resolve in one function and a compare in its caller passes. It reads files off disk, so `scripts/qt` does not select it.

## sandbox/task_env.py

`build_task_runtime`: the model env, the credential split (clean / proxy-only / credential), the `SkillProxy` and `NetworkProxy`, and the read-only bind list, as a `TaskRuntime`. **Context managers are built here, entered by the caller**: they must span primary, reroute and fallback, so the `ExitStack` stays in `execute_task` around `run_with_failover`.

Load-bearing orderings: `proxy_base_env` is snapshotted before `ISTOTA_SANDBOXED` is set (skills run host-side); proxy-only split runs first, credential split on the residue (a var declared both ways stays proxy-only); `HOOK_PATH_PREPEND_KEY` is consumed after the snapshot (task-temp on host PATH is code execution); ISSUE-410 top-ups run after both splits.

**ISSUE-410 top-ups**, split by whether an uninterested CLI can be harmed. Trust stores only add a CA: `skill_cli_tls_env` puts `SKILL_CLI_TLS_VARS` (with `CURL_CA_BUNDLE`, as `sandbox.forge_cli._CARRY_EXACT`) in the shared snapshot. Proxy URLs redirect traffic (even loopback, e.g. `browse` via httpx `trust_env=True`) and can carry userinfo, so `skill_model_reachability` routes `SKILL_MODEL_REACHABILITY_VARS` (the proxy triple) through the per-skill map and `_PROXY_LOOKUP_BLOCKED` gains them. Gap-fillers, never overrides (`credential_env` keeps `sensitive` names out); `derive_credential_set` is index-wide, so one `sensitive` `SSL_CERT_FILE` removes it for all. Open: `feeds` egress proxy. Inside `skill_proxy_enabled` only.

The network-proxy gate asks `config.security.sandbox_enabled` (asked for), the sandboxed marker `effective_sandboxing` (got); they differ on Linux without bwrap, so do not unify. `executor` is imported at function scope (cycle; keeps `monkeypatch.setattr(executor, "_bwrap_available", …)` working).

## sandbox/confined_command.py

`run_confined_command`: a CRON `command:` row or a HEARTBEAT `shell-command` check, run where a task's Bash call would (ISSUE-886). Both files are model-writable, so the command has the authority of whatever last edited the file. It takes `build_task_runtime` with no skill selected, which is a turn's reach (authorization follows credentials, the proxy runs any CLI), enters both proxies, wraps `shell_argv` with `build_bwrap_cmd(profile=NATIVE)`, places the child in a task cgroup from `preexec_fn`, and reports its pid through `executor._record_worker_pid`, which authorizes it with both proxies and sets `worker_pid`. Withheld scopes come from `_task_withheld_scopes`, so a job in a shared room gets what `rooms.scopes` says. A runtime that cannot be built is a failed run, never a run outside the namespace. Without bwrap the command runs unwrapped but with the same env split: on those shapes it is as unconfined as a task's Bash. `doctor` already warns there.

**No privileged job, deliberately.** The audit's other remedy, an approved host job bound to immutable content, is not built: nothing shipped needs one, and a host job belongs in a system timer, outside anything the model can write. A heartbeat check has no task row: it runs under a negative id from `heartbeat._shell_check_ids` and `make_daemon_control_dir`, so `_owners_own_turn` and the credential snapshot find no row and refuse. ## sandbox/tool_server.py

`python -m istota.sandbox.tool_server --fd N`, one per **task attempt** on either brain, via `build_bwrap_cmd(..., profile=NATIVE)`, placed in the cgroup from `preexec_fn`. Builds one `ToolEnv` from `hello` and binds the six core tools (`build_default_tools`) (ISSUE-389). Holds no image library (see `lib/image_sniff.py`) and must not import `istota.skills` (`tests/test_tool_server_env.py::TestTheServerDoesNotImportTheSkillsPackage`; why `sandbox/git_hardening.py`, `sandbox/forge_bin.py`, `lib/untrusted.py` live outside `skills/`).

- **Wraps nothing**: nested bwrap under `--unshare-user --disable-userns` fails, so `ToolEnv` lost the field.
- **Places nothing**: membership is inherited at fork; `cgroup.procs` is unbound.
- **Every call goes through one `ToolDispatcher`** (`build_dispatcher`, #862): the hello's `tools` subset (absent = all six, `[]` = none), argument preparation, the readers-writer lock (Bash, Write, Edit alone; Read, Grep, Glob together) and the hello's `text_cap`. Native's `request_hello` sends `tools` as its grant narrowed to the six and no cap; the loop prepares arguments too, which is safe because preparation is idempotent on its own output (`tests/test_tool_server.py`).
- **A second front end, `--mcp --hello PATH`** (#862): MCP over stdio through `mcp_stdio.serve_stdio`, the hello read once from a 0600 file in the control dir (`O_NOFOLLOW`, regular file), the calls through the same dispatcher. An optional `gate` FIFO in the hello holds every `tools/call` until one byte arrives, read once; `initialize`, `tools/list` and `ping` are never held. The MCP stream is moved off fds 0 and 1 at start, which become /dev/null and stderr, so a Bash child cannot read or write the CLI's stream. `tests/test_tool_server_mcp.py`.
- **Merges `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY` from its own env** into `subprocess_env`, since the wrapper `exec env`s them onto this process and the frame env came from the bridge-less daemon. `NO_PROXY` is deliberately empty, so the merge tests presence; the wrapper wins collisions (the loopback bridge is the only reachable proxy).

Nothing raises past `main` (sends `fatal`); frame contents are never logged.

## sandbox/tool_launcher.py

`python -I -m istota.sandbox.tool_launcher --report FIFO --env-file PATH -- ARGV...`, the command the `claude` CLI runs as its MCP server (#862). In order: `os.environ.clear()`; report its pid down the FIFO (`O_WRONLY | O_NONBLOCK | O_NOFOLLOW`, `S_ISFIFO` by `fstat`); read the env file (`O_NOFOLLOW`, regular, a JSON object of strings) and unlink it; `execve` with that env. The pid survives the exec, so the daemon authorizes the tool server and never the CLI. The report comes before the env file so a respawned launcher still reports and is refused. `ARGV[0]` must be absolute; nothing searches `PATH`. Every refusal, an exec failure included, exits 2 before running anything, with one line on stderr and no values. The child's env is the file's because `execve` is passed it explicitly; the clear covers only the launcher's own life before the exec. stdlib-only, imports nothing from the package. `tests/test_tool_launcher.py`.

## sandbox/tool_server_protocol.py

stdlib-only, one `ProtocolError`. 4-byte big-endian length plus UTF-8 JSON; `MAX_FRAME_BYTES` (32 MiB) enforced on both ends. `hello` carries two optional fields, `tools` and `text_cap`, with no version change. Messages: `hello` / `call` / `abort` / `shutdown` down, `ready` / `update` / `result` / `fatal` up. `ToolResult.details` does not cross (only `agent/loop.py` reads it); content blocks are plain dicts. `FrameDecoder.close()` raises on leftover bytes: a missing result is a broken server, not an unmade call.

## sandbox/cgroup.py

A cgroup v2 group per task (A6): `<unit cgroup>/task-<id>-<attempt>/` with `memory.max`, `pids.max`, `cpu.max`. A sibling of the daemon's `supervisor/` leaf (v2 forbids controllers under a process-holding cgroup). `resolve_root` takes the last `.service`/`.scope` (the first is `user@N.service`). **In the container** it first takes `ISTOTA_TASK_CGROUP_ROOT`, the private namespace's root the entrypoint's root phase remounted and delegated to uid 10001, but only when `declared_root_problem` finds it a cgroup2 directory on a mount rooted at `/`, in a cgroup namespace of the container's own (this process's `0::` path is `/`, the `supervisor` leaf or a `task-*` cgroup), with a writable `cgroup.subtree_control`: a bind of the host's `/sys/fs/cgroup` reads `/../..`, and `cgroup: host` reads `/` with the process at the VM's path for the container (`/system.slice/docker-<id>.scope/…`); both are writable once remounted, probe clean, and are the VM's whole tree. The root phase refuses both before writing anything, the second by requiring its own cgroup to read `0::/`. The mount lookup is `lib/mountinfo.covering_mount`, shared with the entrypoint's rclone preflight. `doctor`'s `security.task_cgroups` FAILs on a declared root with a problem or a failed `probe()`, WARNs where nothing declares one (a host unit without `Delegate=`, the web container), and SKIPs off Linux and in a task. A successful `memory.max` write is the delegation proof, so startup calls `probe()`, not `resolve_root`. Placement is `preexec_fn` since bwrap forks during setup (ISSUE-285): parent opens `cgroup.procs`, child writes `0`, `verify_placement` reads back. `place()` is the after-the-fact backstop for a pid a brain reports without having spawned it through a `preexec_fn`. `destroy` writes `cgroup.kill` on `EBUSY` (5.14+); `read_events` names an OOM kill before `rmdir`. Fails open without `Delegate=`, said at startup. stdlib-only, never raises.

## sandbox/bind_launcher.py

**A linked resource is bound from a descriptor, never by name** (ISSUE-881). Anyone who can write the resource's tree can swap a name: the owner of another home a resource points into, or a concurrent task when an operator-written resource sits under a `Channels/<token>` or `Groups/<id>` it can write. `Mount.walk_root` marks these entries. `render_bwrap_argv` touches no name for them: it emits `--ro-bind-fd <fd> DEST` or `--bind-fd <fd> DEST` and wraps the command as `python -I -m istota.sandbox.bind_launcher --binds JSON -- /abs/bwrap ...`. A task with no such resource keeps a bare `bwrap` and its argv is unchanged. The launcher pairs each `{root, parts}` in order with a placeholder before bwrap's `--`, walks from the daemon-composed root with `confined.open_dir`, opens the leaf `O_PATH | O_NOFOLLOW`, requires a directory or a regular file, and execs bwrap holding the fd. bwrap turns the fd into a name through `/proc/self/fd`, mounts that, compares the mount's device and inode against the fd, and dies with "Race detected binding fd" before running anything on a mismatch.

It is a process because the `claude` CLI spawns the command on that brain and hands a child no descriptor of ours; `tool_launcher` execs it like any other command, and the pid survives both execs. **A resource that fails the walk loses its bind and the task runs**, since failing the namespace would let a task in one home stop another user's tasks through a name they share. The price is that a swap landing in bwrap's own window fails that one attempt, which the owner of the tree can cause on purpose. bwrap's path is absolute, from the daemon's `PATH` (`executor._bwrap_fd_bind_binary`), because the launcher runs with the task's env. A bwrap without the flag (older than Debian 13's) loses every linked resource with an ERROR rather than falling back to a bind by name. `tests/linux/test_resource_bind_identity.py` races a swap of the leaf and of a parent against the real mount builder, with a control that runs the same race against a bind by name and requires the canary to appear. `tests/smoke/test_sandbox_in_stack.py::TestALinkedResourceBindsByDescriptor` runs it unprivileged under the shipped seccomp profile. Docker Desktop ignores AppArmor, so the `istota` profile was checked by hand in enforce mode on the test VM: the fd bind passes. Its `deny mount ... /proc/**` rule does not read on this, since bwrap names a source under `/oldroot`. `doctor`'s `security.linked_resource_binds` warns on a bwrap without the flag. `project_fs_roots` still resolves the source by name. Under the sandbox those roots are the error-message layer, so a swap changes a message and a symlink loop there fails that one attempt. **Any spawn with a task's env makes a bare name absolute first** (`shell_exec.on_daemon_path`, used by the native spawn and the CLI harness): given a bare `bwrap`, `subprocess` searches the task's `PATH`, which starts under the model-writable temp dir.

## sandbox/guarded_http.py

The HTTP half beside `net_guard`'s address rule, for daemon-side fetches to a host a user or a remote server chose. `pinned_request` builds a request against a checked address with the `Host` header and TLS SNI on the name, so DNS cannot answer differently between check and connect; the caller's headers never replace `Host`, nor `Authorization` when `auth` is given. `new_client` is the client both skill clients used to build by hand: `trust_env=False`, no automatic redirects, the trust store still reading `SSL_CERT_FILE`. The `wordpress` and `servarr` clients build their requests with `pinned_request` and keep their own send loops, because both refuse redirects and carry retry and `outcome_unknown` rules of their own; their unchanged tests are the check on the extraction.

`guarded_send` is the whole path for callers with no such rules (the shared-source fetchers and the RSS poller): a required `deadline_seconds` bounding the whole call (hops and body included, checked after every chunk), because httpx's timeouts are per read and a server dripping one byte inside each would hold a web worker thread for hours; plain `http` only to a host on `private_hosts` unless the caller passes `allow_plain_http` (the RSS poller alone: the user chose the scheme, and the request carries nothing the daemon adds), a non-public address only for a listed host either way, each checked address in turn on a refused connection, the body read to `max_bytes`, and no redirect unless `max_redirects` allows. Each hop is checked from scratch; a hop may reach a non-public address only when its host is listed **and** is the original request's host, so a public feed cannot bounce the daemon onto an internal one, and a hop to another origin drops `auth` and any `Authorization` header for the rest of the chain. A 303, or a 301/302 to a method other than GET or HEAD, becomes a GET with no body. Every refusal is a `GuardRefused` with one of `host_refused`, `too_large`, `redirect_refused`, `connection_failed`, `timeout`, and its text is that code alone: a feed URL and a share secret are bearer credentials, so neither the URL's path or query nor any response text reaches an exception. The answer comes back with its body decoded and the wire headers (`Content-Encoding`, `Content-Length`, `Transfer-Encoding`) dropped. `session/tools/web_fetch.py` is not converted (async, tool-server leaf, its own policy). Nor is the heartbeat `url-health` check, deliberately: it is admin-only (ISSUE-596), and the check exists to probe internal services the guard would refuse. It is the one thing HEARTBEAT.md still does from the daemon's network: an injected admin task can read a status code from an internal address, and nothing else (ISSUE-886). The RSS poller is converted (#838, `feeds/poller._guarded_get`, `[feeds] private_hosts`). Tests: `tests/test_guarded_http.py`, loopback servers named in `private_hosts`, plus httpx's mock transport for the rules that need a public name.

## sandbox/shell_exec.py

`shell_argv(command)` with `pipefail`, for callers trusting exit status: native Bash, CRON `command:` rows (auto-disable), heartbeat `shell-command` (cf. ISSUE-307). `bash` is named, not probed; fallback `/bin/sh -c`, logged once. An interpreter swap: bash sources `$BASH_ENV` (refused by `executor.build_clean_env`).

**`pipefail_env()`** (ISSUE-321) returns `{"SHELLOPTS": "pipefail"}`, applied last by `executor.build_clean_env`, for the Claude Code CLI's own `bash -c` that `shell_argv` cannot reach. `SHELLOPTS` cannot source a file (`pipefail:$(touch /tmp/x)` is rejected). `_SHELL_STARTUP_ENV_VARS` (`BASH_ENV`, `SHELLOPTS`, `BASHOPTS`) are filtered from `build_clean_env`'s passthrough first. Inherited, so nested bash gets it; dash does not. Cron and heartbeat take it from `build_clean_env` like a task, since ISSUE-886. `is_sigpipe_failure`: a SIGPIPE-killed cron row is failed, not retried (retry re-runs the producer). `SIGPIPE_EXIT` / `SIGPIPE_NOTE` annotate 141. A non-final stage exiting non-zero to report (`grep -c x f | wc -l` returns 1) has no marker; documented. stdlib-only, never raises.

## sandbox/peer_process.py

Peer identity on a Unix socket and descent from roots (ISSUE-550). `peer_pid`: `SO_PEERCRED` (translates `--unshare-pid` pids) or `LOCAL_PEERPID`. `parent_pid`: `/proc/<pid>/stat` after the last `)`, or `proc_pidinfo(PROC_PIDTBSDINFO)`. `start_time`: field 22, or `pbi_start_tvsec`/`pbi_start_tvusec`. `descends_from` takes `{pid: start}`, needs both to match, refuses on unreadable links and at pid 1. `reporting_pid` is a `preexec_fn` sending the child pid down a close-on-exec pipe, reader joined on exit; runs after `sandbox.cgroup.placement`. `split_pid_lines` is the one `pid\n` parser, shared with the tool harness's FIFO reader; it drops anything but a positive decimal, so a report never reads as the reap report 0. Other platforms answer `None`, so all are refused (`security.proxy_peer_check` FAIL). `PeerRoots` serves both proxies; the network proxy checks before reading CONNECT, and brain children are registered with both even with the skill proxy off. No roots, no access; per connection, so an admitted tunnel lasts until closed. stdlib-only, never raises.

## sandbox/process_group.py

`kill_process_group(pid, sig)`: signal the group, or only the process when it leads none (a non-leader shares the daemon's group). The streaming CLI child leads a group; `ClaudeCodeBrain`'s non-streaming child does not. Used by ClaudeCodeBrain's streaming kill paths, scheduler and native-bash timeouts, through `signal_task_worker` by `!stop`, the web cancel endpoint and a group removal, and directly by the attempt's own `scheduler._task_cancel_watch`. Never raises (called from a `threading.Timer`).

`signal_task_worker(pid, sig)` signals a recorded `worker_pid` only in the process that runs the scheduler (ISSUE-701): `run_daemon` calls `own_task_pids(True)` once it holds the daemon lock and clears it before releasing, which covers the daemon and `istota serve`. Anywhere else (the web container, with its own PID namespace where uvicorn is PID 1) it returns `"elsewhere"` and the cancel rests on `cancel_requested`. The worker's process acts on it: `scheduler._task_cancel_watch`, entered with `_task_heartbeat` around every attempt, polls every `_CANCEL_POLL_SECONDS` (2s) and SIGTERMs the running row's `worker_pid` once through `kill_process_group` (ISSUE-812). It skips the daemon-lock guard because the pid is its own process's child, which also covers `istota run`. Every brain clears the row once it has reaped its child, through the same `on_pid` callback that set it, called with 0 (`sandbox.peer_process.report_child_reaped`, ISSUE-823): ClaudeCodeBrain after `process.wait()` on the streaming path, and on the non-streaming path from `reporting_pid`'s reader at EOF (`report_reap=True`), on the thread that sent the spawn report so it cannot overtake it, and NativeBrain from the tool server's `aclose` once the process has a return code. The executor's `_record_worker_pid` writes NULL for 0 and authorizes and places nothing, since placing pid 0 would move the daemon into the task cgroup. The watch still pins each pid to `peer_process.start_time` when it first sees it, which covers the moment between a reap and the clear. Before it, `ClaudeCodeBrain` saw the flag only on the CLI's next event (non-streaming: at exit). The REPL's inline tasks never reach `running` and are not watched.

## Credential grant snapshots

A scoped selected import grants new host-bound entries once unless tagged `istota:nogrant`. Unscoped and generated imports stay ungranted. `_credential_grants` records decisions so revocation and narrowed access survive re-import. Task-created credentials receive the creating conversation grant and extend that task's snapshot.

Reserved KV `_credential_grants`: `granted_existing` (one-time upgrade action: the settings button, and `build_task_runtime` on the first task with the broker on, between `sync_forge_bindings` and `ensure_credential_grants`, so an install turning the broker on keeps its bound entries usable), `revision:<name>` (kept after deletion so a recreated grant cannot revive an old snapshot; policy edits advance it), `allow_http:<name>` (explicit, default off; HTTP bindings keep `http://`), `auto:<name>` (the first-sight marker above). `_credential_fields` maps imported fields to their vault entry (from the vault parser, not suffixes). Deleting a vault credential deletes its grant and room rows in one transaction; task retention and room deletion delete task grant rows explicitly (no FK cascades).

## Credential broker CA

Grants allow every HTTP method; legacy `credential_grants.methods` is kept for compatibility, neither exposed nor enforced. Exact host and port, auth-header restrictions, the HTTP override and live revocation still apply.

`credentials/broker/ca.py`: CA under `{db_path.parent}/credential-broker` (`0700`, atomic `0600` P-256 key plus ten-year cert, cross-process lock). Corrupt or insecure records fail closed; delete `ca-key.pem` and restart to rotate. Setup rejects a location under any sandbox bind, masked or not. Leaves: exact SANs, 24 hours, bounded cache, loaded via a temp private file removed at once. HTTP/1.1 only; SNI must equal Host; upstream verified with the daemon trust context.

`build_task_runtime` writes system roots plus the CA into the read-only control dir. `TaskRuntime.sandbox_env` reaches only `sandbox_plan`'s `exec env` wrapper (never task, proxy or daemon env); the tool server passes it to Bash via `merge_proxy_env`. Node gets the CA as an extra root; others use the bundle. Broker off: nothing created. No effective sandbox: no broker trust, and setup warns.

`credentials/broker/intercept.py` intercepts only snapshot-bound hosts (others stay raw TLS); absolute-form HTTP gets the same checks for allowlisted snapshot destinations. The HTTP override never downgrades HTTPS. Per request the h11 loop checks grants, replaces placeholders only in allowed auth headers (Basic decoded first), and refuses them in URLs or the body prefix. Headers and a response body at any size are scrubbed when the request carried a value (#888): up to `scan_max_bytes` buffered, past it `_relay_scrubbed`, holding back the longest value's length minus one so a value split across reads is seen, at the cost of that many bytes of lag on a live stream. `_echo_forms` is what gets matched; a transformed, partial or mid-blob echo, and one on a later request with no value, still pass. Encoded bodies, encoded authenticated responses, trailers and upgrades are refused. Audit never holds values. On by default (config.md); legacy fetch paths remain for the broker-off shapes.

## Private skill credential channel

Each skill invocation gets a socketpair via `ISTOTA_CRED_FD` / `pass_fds`, never the model; the skills package marks it close-on-exec before loading skill code. `_credref` resolves at parse time over a per-name duplicate. The proxy accepts only credential reads there, sets provenance itself, and charges the attempt budget. With the broker on it checks the grant (room scope, `allow_scheduled`, revision), refusing `credential_not_granted` or `credential_changed`; a grant read error refuses. Names created this attempt by `vault_create` are exempt (`_created_names`, in memory) for create-then-fill, since the snapshot was frozen before the create's conversation grant; later tasks use that grant. Public reads follow the reveal policy, not grants. Values come from the live lookup.

Both ends are closed and the reader joined on success, timeout or spawn failure. An invalid fd refuses without falling back; callers with no fd use the public socket, under the reveal policy.

### Connected mail accounts on the channel

A second per-row, non-vault type beside `wallet_card`: `{"type": "mail_account", "account_id": N, "purpose": "read" | "send"}`, asked by the email CLI through `credential_shim.fetch_mail_account` once it has resolved `--account <slug>` to a row itself (`mail.accounts.get_account`, scoped by `ISTOTA_USER_ID`). `SkillProxy._serve_mail_account` answers for `self.user_id` and `self.task_id`; the request contributes only the id and the purpose. Refusals, in order, a closed set: `skill_not_permitted` (the invoking skill is not `email`; `_credential_channel` carries the skill name the proxy spawned), `account_not_found` (a malformed id, or `mail.accounts.resolve_for_daemon` finding no enabled row for this user: one answer for both, so ids cannot be probed), `invalid_credential_request`, `account_channel_unavailable` (no config, user or task), `mail_accounts_disabled`, `not_owner_turn`, `permission_denied` (`send` on a `read` account, or `[mail_accounts] allow_send` off), `password_missing` (absent, or undecryptable without the master key). The public socket answers `account_channel_unavailable` to the type and serves nothing; so does a `skill:` job, which spawns the CLI with no proxy and no fd. A `command:` job's CLI goes through the proxy like a task's.

**The turn check is the channel's alone.** `not_owner_turn` fires when the task's row, or any ancestor's on the `parent_task_id` chain (`skill_proxy._owners_own_turn`), is not this user's, has a `guest_participant_id`, or `rooms.scopes.written_by_someone_else` finds its stored turn written by someone else; a missing ancestor, a cycle or a chain past 64 is refused too. A subtask has the host's user id and the room's token but no `messages` row, so a check of its own row alone passed a correspondent's turn. On an email thread room a correspondent's admitted mail runs as the host at full reach (above), so without this a prompt-injection mail could read the host's other mailboxes. An email task with no stored row (an approved held mail no room admitted) is read from its `processed_emails` sender and counts as someone else's unless that is one of the user's own addresses (ISSUE-874); the proxy, the deferred KV replay and the `kv` and `briefings_config` CLIs (`skills/_turn_access.calling_turn_passes`) pass the config's addresses, and with no config the check falls back to `db.own_addresses_without_config`, which can only under-trust. A `!retry` copy of an email task has no ledger row and leaves the decision to its parent on the chain. `resolve_for_daemon` applies every other refusal and is what `drafts.release`, the briefing source (`imap:<id>`) and the connection test call; they run daemon-side with no turn to check.

The answer is `{"imap": {...}, "smtp": {...} | null}`, with `smtp` only for `send`, so a `read` account's SMTP password never leaves the daemon. The CLI boxes each password in `_credref.SecretValue` (the shim is copied standalone into the sandbox and cannot import it). Not charged against the vault fetch budget: it is not a vault entry. Every serve and refusal logs `task_id`, `account_id`, `purpose` and the reason, never a host, username or password; an unexpected error answers `mail_account_error` and logs the exception type only. The passwords are `secrets` rows under `service='mail_account'`, keys `{id}.imap_password` / `{id}.smtp_password`, outside `CONNECTED_SERVICE_SCHEMA`, so `istota secret` and the generic secret routes cannot write them and no manifest, `credential_env` or `istota-credential env` lookup reaches them (`tests/test_skill_proxy_mail_account.py` builds a runtime for a user with two accounts and checks none of their values is in `credential_env`, `base_env` or the lookup allowlist). Connections go through `mail/connect.py`: verified TLS, the resolved address checked against `net_guard` unless the host is in `[mail_accounts] private_hosts`, and the socket connected to the checked address.

## Public credential reveal enforcement

`SkillProxy._serve_vault_credential` (and `_serve_vault_entry`, per member, refusing the entry if any member is unrevealable) charges the budget and checks presence before reading live `credential_bindings.revealable`; under enforcement permission and value are read in one transaction. Only the private dispatcher sets `trusted_skill=True`; public `mode` or trust claims carry no authority. Unmarked public reads log `credential_reveal action=would_refuse reason=credential_brokered` at WARNING, or return `credential_brokered` with `[security.credential_broker] enforce_reveal = true`. Predicate `CredentialBrokerConfig.reveal_enforced` also needs `enabled` (no placeholders otherwise, so every git and forge read would fail; `load_config` warns). Missing metadata means no reveal; names via `label_for_display`, values never logged.

Covers `get`, both `run` forms, raw socket clients, and the public manifest `credential` branch (manifest vars and forge tokens have no reveal marker). Host-side injection and the private fd are unaffected; `list`, `placeholder`, `new` unchanged. On by default with the broker; `enforce_reveal = false` returns to audit mode. Devbox credentials are outside this policy.


Browser secret capture uses `read_secret` (with `read_recovery` as a compatibility alias), the element's own HTTPS frame origin and the private credential channel. `vault_secret_capture` and the stdin setters share `_store_captured_secret`: write budget, isolation, snapshot/grant reach, shape validation, then an audited generated-credential write. Captured values enter browser redactions before a store refusal can return. Recovery formats and spent indices live in `recovery_code_state`; export prefixes spent lines with `(used) `. The dependency-free `lib/secret_shapes.py` receives the existing TOTP parser from its caller, because `lib/` leaves cannot import each other.
