# Sandbox, task runtime and process boundaries

The boundaries a task runs inside and the modules that build them. `executor.md` owns `execute_task()`; this file owns the environment it hands over. The devbox bullet is in `devbox.md`.

## Security posture

**Multi-user vaults need a sandbox.** With more than one configured user (vault or not), vaults require `effective_sandboxing` or `[security] allow_unsandboxed_multi_user_vaults = true` (default false). `credentials.names.vault_isolation_refusal` gates import/export, task credential loading and proxy writes; it withholds cached credentials without deleting rows. Doctor fails and the settings card refuses; with the opt-in doctor still warns (same-uid exposure). Restart services and stop tasks after changing the policy or adding users. Manifest-injected credentials are unaffected.

- **Sandbox** (`bwrap`): per-user filesystem isolation. Linux + bubblewrap is the only supported deployment.
- **Every brain's tools run in the sandbox, one namespace per attempt.** `NativeBrain` spawns `istota.sandbox.tool_server` per attempt via `build_bwrap_cmd(..., profile=NATIVE)` (`BrainRequest.tool_server_wrap`), places it in the task cgroup from `preexec_fn` and reports its pid via `req.on_pid`; the daemon holds proxies (`session/tools/remote.py`). On `claude_code` the CLI spawns the same wrapped process through `sandbox/tool_launcher.py`, which reports its pid down a FIFO; the harness authorizes it only when it descends from the CLI, and it inherits the task cgroup from the CLI (`brain.md`, "The CLI tool harness"). The `claude` CLI itself runs outside the sandbox with its machine-acting built-ins denied (`brain.md`, "The tool server"). `SandboxProfile` has one member, `NATIVE`, for this release: `CLAUDE` and its binds (`~/.local/bin`, `~/.local/share/claude`, `~/.local/state/claude`, the `~/.claude` tmpfs, `.credentials.json`, `settings.json`, `projects`, `debug`, `todos`, the system-prompt file) went with the in-sandbox CLI, and `build_mount_plan` / `build_bwrap_cmd` / `build_daemon_sandbox` lost `cli_auth_mode`. Before ISSUE-389 file tools ran on daemon threads behind `executor.native_fs_roots` and `Bash` built a namespace per call with the CLI's runtime block. The roots are still enforced: the error-message layer, and the only confinement on unsandboxed shapes. Transport is an inherited socketpair for native and the CLI's stdio for `claude_code` (nothing listens, no peer to authenticate); `close_fds` keeps the socketpair from Bash children, and the `--mcp` front end moves the stdio stream off fds 0 and 1. No enable flag, deliberately (it would keep two tool paths); `build_bwrap_cmd` returns the command unchanged where bwrap is unavailable. Rollback is a revert.
- **No databases in the sandbox.** `build_bwrap_cmd` ends by masking `db_path.parent` and `module_db_root()` with an empty read-only tmpfs, last so no earlier bind shows through, with `--remount-ro` and `--disable-userns` (plus required `--unshare-user`) where supported: a writable mask lets `sqlite3` create a zero-byte file that reads as corruption, and a tmpfs can be unmounted from a nested userns. So keep `sandbox_ro_paths` narrow; the mask does not make a broad entry safe. Nothing binds the framework DB (`sandbox_admin_db_write` retired), `sandbox_ro_paths` defaults to `[]`, `native_fs_roots` matches. Host-side skill CLIs scoped by `ISTOTA_USER_ID` are the per-user boundary; masks are defence in depth.
- **Session logs are unbound: an absence, not a guard.** Native transcripts (assembled prompt, `USER.md`) go to `{db_path.parent}/logs/{user_id}/` (`/data/db/logs` on Docker), bound nowhere, in no `native_fs_roots` root. Kept out by `security.sandbox_ro_paths` defaulting to `[]` (its old `/srv/app` default exposed every DB) and, where `workspace_path` equals `db_path.parent`, no `user_resources` row naming it. The mask backs this on the stack, whose run contract lets bwrap run; it does not where nothing is sandboxed (`native_fs_confinement_active` gates on `effective_sandboxing`), and `_mask_dir` refuses where the database sits in the workspace. `doctor`'s `runtime.session_log_dir` asks `executor.mask_shadowed_by`, reporting availability (`executor.effective_sandboxing`, not `sandbox_enabled`, ISSUE-381) then placement; under `probe=False` it uses `effective_sandboxing_if_known` and reports unestablished. Never `user_temp_dir`. Tasks read transcripts via `istota-skill tasks transcript`.
- **One admin's repos are not in another's sandbox.** `build_bwrap_cmd` binds `{repos_dir}/{user_id}` (holding `{namespace}/{project}.git`), never the root; `native_fs_roots` matches; `DEVELOPER_REPOS_DIR` comes only from developer `setup_env`; `sandbox.host_paths.resolve_under_repos` scopes `--worktree`. The cache is derived at `{repos_dir}/{user_id}/.package-caches` (same mount as a venv for `link(2)`; retired the ISSUE-319 sibling masks). **Gated on `sandbox_cache_is_derived`, the repos bind's condition including `is_admin`; a boundary** (ISSUE-320): the later repos bind buries a symlink swapped in between check and `mount`. Non-admins get the fallback root or none; no separate cache write root in `native_fs_roots`. `maintenance/repos_relocate.py` moves old trees.
- **Config dir out of the sandbox.** Prompt-text files and `config.toml` live in `config/`, never bound, `config/system-prompt.md` included: `NativeBrain` reads it in the daemon, and the CLI, which opens it via `--system-prompt-file`, runs outside the sandbox. `executor._sandbox_bind_targets` still lists `~/.local`, `~/.claude` and that file, though nothing binds them, because the daemon runs the CLI from them and a `sandbox_cache_dir` at or above one would hand the model write access to the binary or the token.
- **Network proxy**: `--unshare-net` + CONNECT proxy on a Unix socket, `host:port` allowlist (`executor._build_network_allowlist`: PyPI under `allow_pypi`, `extra_hosts`, then skill-gated hosts). **The name is not the check** (ISSUE-883): every upstream connect, raw or brokered (`intercept._requests` through `network_proxy.checked_connection`), resolves once through `net_guard.checked_addresses` and connects to the checked address; a non-public answer is a 403 unless the name is one the operator wrote (`executor._network_private_hosts`: `extra_hosts` and the configured forge and Nextcloud URL hosts), so only the built-in defaults must resolve public. `[security.network] private_hosts` is retired: parsed, warned about, never read, since requiring a second listing of a host the operator already allowlisted guarded nothing. A raw tunnel answers 200, then `read_client_hello` must find one SNI equal to the CONNECT host (none only for an IP literal) before a byte goes upstream; otherwise it closes. Residual: HTTP `Host` inside the TLS is unseen, so domain fronting through an allowed shared front still works; ECH is refused. No Anthropic host: nothing in the sandbox calls a model, so `api.anthropic.com:443` and `mcp-proxy.anthropic.com:443` left the defaults and the `anthropic` provider's base-URL host is not added under "api_key"; a task that needs one names it in `extra_hosts`. TLS interception only for credential-bound hosts in the task snapshot, when the broker is enabled.
- **Skill proxy.** Strips secret env vars; CLI calls go through a Unix socket injecting credentials server-side, decoupled from skill selection. Required wherever the sandbox is (`istota-skill` refuses under `ISTOTA_SANDBOXED`). DB paths (`ISTOTA_DB_PATH`, manifest `proxy_only`) go to the proxy only. Requests: `credential` (manifest lookup for git and forge helpers), `vault_list` / `vault_credential` / `vault_entry` (map from `task_env`, capped by `vault_fetch_limit_per_task`, which counts distinct credentials: a `(channel, type, name)` already served in full this attempt is free, anything not yet served is charged every time, absent or refused; keyed by channel so a value a skill got privately is not free to the model; ISSUE-743). `sandbox/credential_shim.py` goes to `{user_temp_dir}/.istota/istota-credential` (0700) on the model's PATH only, never `proxy_base_env`'s; `.istota` is re-bound read-only after the workspace (like `.developer`). The shim is a convenience, not a gate. **The socket gates which task asks** (ISSUE-550): 0600 stops other uids, not other tasks. The proxy serves only kernel-reported peers descending from pids its task registered: the brain child via `on_pid` (to `authorize_pid` first) and spawned skills (`sandbox.peer_process.reporting_pid`, revoked on exit), pinned to start time against pid cycling. Narrows rather than closes cross-task access on unsandboxed multi-user hosts; `security.proxy_peer_check` warns. Env nonce rejected (same uid reads env). A brain skipping `on_pid` gets every skill call refused.
- **Host work per task is bounded** (#890). `UnixSocketServer` takes `max_connections`: past it a connection is answered `busy_reply` and closed from the accept loop, so a refusal costs no thread. `stop()` shuts down every live connection through a dup, since `wrap_socket` detaches the socket a handler was given. The network proxy caps a request head at 64 KiB and its arrival, and a ClientHello's and the broker's head arrival, at 30s absolute (`unix_server.arm_until`, because a socket timeout restarts on every read), answers 431, 408 and 503, and shuts its raw tunnels' upstreams at stop, which have no timeout. A tunnel in use has no deadline. The skill proxy caps a request at 4 MiB and 30s, holds at most `skill_proxy_max_concurrent` running skills (the rest wait inside what the client's wait leaves after the skill's timeout and the margin), and runs each through `run_capture` with `max_output_bytes`, which kills the group past `skill_proxy_max_output_mb`. A skill joins the task cgroup from `preexec_fn` (`SkillProxy.task_cgroup`, set by the caller once the cgroup exists), so it shares the task's limits and `cgroup.kill` reaches a descendant that left its group; `stop()` kills the groups of skills still running, and the task cgroup is released after both proxies stop, so a queued skill cannot start into a dead one. A call whose client left while it queued never runs. A CRON `skill:` job's output has the same cap and no cgroup. An accept failing with `EMFILE` or `ENFILE` never counts toward ending the listener. Residuals: without a cgroup a skill is on the daemon's budget and a descendant in its own session survives; threads and buffers in the daemon itself are bounded in number and size, not accounted to the task; on an unsandboxed shape another task's process can occupy connection slots for the peer check's few seconds. Deferred-file consumption is #878's.
- **Host paths in skill CLIs.** A model-chosen host path is an arbitrary read or write unless scoped. **The disposition sits on the argument** (ISSUE-447): `skills/_hostpath.host_path` stamps it; `skills/_cli.parse_and_resolve` resolves before dispatch and writes back; refusal is `reason: host_path_refused`. Modes by where bytes end up: `READ` (deferred dir, own workspace, own channel, the task's attachment copies under `ISTOTA_ATTACHMENTS_DIR`, mirroring binds); `WRITE` (minus read-only roots); `EGRESS` (workspace and deferred dir, for content mailed, indexed, uploaded or persisted); `REPO`, `REMOTE`, `NOT_A_PATH` resolve nothing. Never the mount whole; no directory is created at parse. `open_resolved` walks every component of the validated absolute name from the filesystem root without following links, then checks the opened leaf is regular. Readers retain that descriptor; `write_resolved` creates parents through directory descriptors and checks the leaf before truncation. Consumers that only accept pathnames use `stage_resolved`, a private copy removed after the call. Feeds exports return bytes to the facade for a confined write. Deferred health sources use the same open at replay.
- **Coverage.** `tests/test_skill_host_paths_coverage.py` builds every parser (`build_parser`, Click `build_cli`) and requires each path-shaped argument to have a stamp or registry record (`UNSCOPED` is gone). `tests/test_skill_host_paths_refusals.py` drives each resolving stamp for refusal and acceptance. **`google_workspace` is bounded by an argv scan, a weaker claim**: `gws` cannot be walked, so `scan_argv` classifies tokens (absolute, `~`, `..`, existing relative, `=` split, short-flag tail, leading `@`) and resolves them under the read rule (`drive +upload` takes a Talk attachment). An admitted file is copied through `open_resolved` into launcher-owned staging and made read-only; directories are refused. The workspace is used only to interpret relative inputs. Execution uses a private non-writable cwd, so a not-yet-existing relative token cannot write into the workspace. Local output files are unsupported. `skill_file_env` gives the proxy, scheduled skill runner and direct skill client the same staging lifetime, including cleanup after exec or timeout.
- **Nothing narrows what the daemon itself may read**; argument scoping is the only layer. Cut: a systemd read allowlist (leaves `{istota_home}` and the mount readable) and a bwrap `SandboxProfile.SKILL` (needs a conditional DB mask, `config/` bound, an ISSUE-390 carve-out, a per-skill table).
- **No Docker API in the sandbox.** No socket bound, no `DOCKER_HOST`; a `docker` binary fails at connect. The per-user `/var/run/docker.sock` proxy is retired (`docker exec` through it lost exit status, forcing the exec transport).
- **The web container reaches every live browser's display, and nothing else in the browser container.** The `browser-console` volume (`/run/istota-browser-console`) is mounted in `browser` and `web` only, never the daemon, so no task sandbox can see it; `tests/test_browser_console_exposure.py` holds that. Each x11vnc listens there on `<console_socket_name(user)>` (`lib/browser_console.py`, vendored to `docker/browser/lib/` by `scripts/sync-devbox-lib.sh`), mode 0660, group 10001, in a 2710 directory the web uid can traverse and not list. The web container stays off the browser network (ISSUE-699), so it has no route to the browser API on 9223. It can still drive every signed-in Chrome over VNC, unauthenticated where `VNC_PASSWORD` is unset: the admin console's step-up gates the admin's request, not the process, so code execution in the web process now reaches the browsers. Accepted, since that process already holds the stack's credentials and every admin session. The console also trusts the browser container's `browser` user, which owns the directory and writes every socket: a compromised browser container could map one user's socket name to another display or to a fake RFB server, and `connect_no_follow` refuses only a symlink or a non-socket at the leaf. Accepted, since that container already holds every user's profile. Loopback 6080 (websockify and noVNC) is the break-glass path.
- **The browser's firewall holds without Chrome's help** (#884). `host/istota-devbox-egress.sh` drops the browser's traffic to the ranges a devbox may not reach, in `DOCKER-USER`, for a renderer that opens its own sockets past the proxy. It matches one address, never the network: the daemon joins `browser` and can take its default route through it (measured), so a subnet-wide drop would cut it off from every private service. `docker/docker-compose.browser-network.yml` fixes that address (`.2`, with Docker handing out only the upper half), and only `istota-stack`'s `compose()` adds the file, because the daemon creates this network on every stack and the testbed's stacks could not share a subnet. Replies get a RETURN first, since `DOCKER-USER` runs ahead of Docker's own conntrack accept. The rules land in front of the host-loopback block, whose RETURNs would otherwise let the browser through. `[browser] private_hosts` is the only setting, and there is deliberately no second list of addresses: `istota-stack browser-grant-addresses` (no lock) resolves the names, keeping what the firewall drops, and `istota-browser-grants.timer` runs `istota-devbox-egress --browser-grants` every five minutes, as does `stack_up` for a changed config. That mode adds before it removes and writes nothing unchanged, because a full run deletes and re-inserts every rule and on a timer would open a gap each tick. It fails closed: a moved address is dropped until the next run, and a name that will not resolve grants nothing and warns. Like every `DOCKER-USER` rule this filters forwarded traffic only, so the VM's own addresses, reached through `INPUT`, are not covered; a devbox has the same gap. Witness `tests/vm/test_browser.py::TestTheFirewallOutsideChrome`, control `no-browser-firewall`.
- **The browser API takes a user's name only from a holder of its token** (#884). `browser_server.dispatch` refuses every path but `/health` without `Authorization: Bearer <token>`, in front of the queue and of the off-thread `/instances`, and a service with no token refuses with 503 rather than opening. `/health` stays open for its capability flags and, without the token, leaves out `instances` and `cdp_last_error`, since those name users and pages. The token is a service identity: the daemon and the skill CLIs still assert which user they act for in `X-Istota-User`. It is the secrets file `istota_browser_api_token`, generated by `istota-stack` (`ensure_secret_files`) and mounted on the daemon and the browser, never on web. The daemon gets it from `istota-secrets`, and `browser_call` and `admin_browsers.snapshot` send it. `browse` and `markets` get it through `SKILL_DAEMON_CREDENTIAL_VARS`, so it is in no model environment and blocked from proxy lookup. In the container, `entrypoint.sh` reads the file as root and exports it after the other children start, and `browse_api` pops it before Chrome starts. A compromised renderer runs as the same uid as the API and can read `/proc/<pid>/environ`, so this stops peers and pages, not that. `tests/test_browser_api_identity.py`, and the forged-header probe in `tests/image/test_browser_image.py::test_the_browser_service_starts_on_the_layer`.
- **The browser reaches public addresses only** (#884). `docker/browser/egress_proxy.py` is a forward proxy in the container, on loopback, and `chrome.launch_chrome` is the one launch and carries its flags (`--proxy-bypass-list=<-loopback>` matters most: Chrome otherwise sends loopback direct, and that is the API and the debugging ports). Chrome resolves nothing behind a proxy, so the check covers redirects, subresources, WebSockets and a changing DNS answer, with the rule in `lib/istota_net_guard.py`. WebRTC's UDP skips a proxy and `--force-webrtc-ip-handling-policy` did nothing (measured), so `chrome-policy.json` is a managed policy at a root-owned path. `[browser] private_hosts` is the operator's exact-name grant, shared with `pdf_text.py`, which fetches directly under the same rule. The container mounts no config (it runs hostile pages, and a config can hold inline credentials), so `istota-stack`'s `compose()` reads the list and exports it as `BROWSER_PRIVATE_HOSTS`, empty rather than unset so `.env` cannot supply one, and a config change reaches it through `restart_for_config`'s `stack_up`; no grant reaches loopback, and a granted name resolving to the container's own network address reaches an API that wants a token the page does not have. It is a second proxy beside `sandbox/network_proxy.py` deliberately: that one imports `istota`, listens on a Unix socket and enforces an allowlist. Not a boundary against a compromised renderer (Chrome runs `--no-sandbox`, same uid). `tests/image/test_browser_image.py::test_chrome_reaches_nothing_private_through_the_egress_proxy` holds it with its control arm in the same run.
- **Native WebFetch** (`session/tools/web_fetch.py`): daemon netns, outside the CONNECT allowlist, credential-free (`trust_env=False`), SSRF-hardened (each resolved IP checked per hop and pinned, GET/text only, caps, untrusted delimiter). **Every brain**: a `claude_code` task gets it through the harness's second MCP server, `istota_web` (`HarnessSpec.web_fetch`, `brain/_web_fetch_mcp.py`: unwrapped, the CLI's env cleared, never reported to the proxies), and the CLI's own WebFetch is denied, which widened CLI-brain egress from the CONNECT allowlist to any public host. **Every user** (ISSUE-449): the `[brain.native.web_fetch]` egress policy bounds all alike; `admin_only = true` restores the gate (read by `build_allowed_tools`, not mapped onto `WebFetchPolicy`). `require_url_provenance` as non-admin default rejected: its corpus is the user half, so WebSearch-then-read fails. See `brain.md`.
- **Deferred DB**: sandboxed tasks write JSON to temp; the scheduler applies it after success. Identity (`user_id`, `conversation_token`) from the task, never the JSON. Subtasks admin-only, capped by `max_subtasks_per_task`, `max_subtask_depth`, `max_subtask_prompt_chars`.

### The credential store

`credentials/store.py` is the only live store. `names.py` owns slugging, password generation and the multi-user isolation gate. `kdbx_import.py` parses an upload and applies selected entries; `kdbx_export.py` is the sole KeePass writer and saves only to memory. Generated credentials stay in the table. `vault_retire.py` keeps one final reader and the legacy storage path resolver for one release; it imports without deletion, leaves the file unchanged, deletes the stored passphrase and old KV state, and records a retirement marker. Database startup converts leftover source values only after this marker, so startup cannot erase the ownership information the final import needs.

History is limited to `vault_entries`, ten versions per field and the configured age. Audit records names, actors and bounded metadata, never values. Web exports, recovery reveals, recipient changes, restores and purges require an emailed code tied to the native identity, action and session. The optional age backup includes credentials only, excludes connected-service secrets and wallet cards, and writes ciphertext to the user's exports folder. Keep the server secret key outside database backups.

## Shared rooms and groups in the mount plan

A turn runs with its sender's reach (ISSUE-576). `rooms.scopes.reach_for_task(conn, task)` is the one derivation, returning a `Reach` (the withheld set, the `turn_author` posture, the allowance); `withheld_for_task` is its set: every scope on a guest's turn, every scope on a task in a shared room no member asked there (no origin surface, as for a subtask, CLI or heartbeat task), nothing otherwise, a member's turn with a guest present included. **A correspondent's turn withholds all but an allowlist** (`turn_author` answers `correspondent`: mail somebody else wrote, on an email thread room or roomless, and any subtask or `!retry` of it): `all_scopes - correspondent_scopes(...).scopes`, whose default is `CORRESPONDENT_DEFAULT_SCOPES` (`email`, `skills`, `transcribe`, `whisper`, `markets`), so a skill added later starts out of reach. `user_profiles.correspondent_scopes` widens it per user, read from the row at every seam: skill names, plus `web` for the native web tools, which is not a scope. `files`, `memory`, `recall` and `memory_search` are refused by every writer and dropped by the reader. `transcribe` and `whisper` read the mail's staged copies under `ISTOTA_ATTACHMENTS_DIR`, a `READ` root that stays when `files` is withheld; `tests/test_email_thread_reach.py::TestTheDefaultsWorkWithFilesWithheld` holds that through each CLI's parser. **`USER.md` and overlays still load** (`Reach.standing_memory_loads`, read by the executor and the `skills` CLI), since they are fixed text the host wrote and the turn cannot write them; dated memories, recall, knowledge facts, playbooks and the pins block do not, because the mail would be the query and the reply a way out, and no setting turns them on. No `Groups/<id>` bind and no group notebook either, with or without a room (`task_group_ids`). **The host's own tasks on an email thread room withhold nothing** (`rooms.scopes.is_email_thread_room`, a binding with `surface='email'` on the canonical token, asked before the origin-surface rule, since the poller marks every thread turn a group chat), and `ambient_memory_off` answers False there ahead of the roster and audience. `record_inbound` skips the guest branch on a thread, so a correspondent's task has no `guest_participant_id`; its posture comes from the stored author or the `processed_emails` row. `turn_author` also answers for `private_replies.my_notes_room`, `assignments.caller` and the skill proxy's `mail_account` channel (`not_owner_turn`). A read error on either check withholds every scope, and an unreadable author loads no standing memory. `executor._task_reach` is the one per-task read; `_task_withheld_scopes` is its set. **A member's own schedule counts as their turn** (ISSUE-594): a `scheduled` task whose `scheduled_job_id` names a job row owned by the task's user, or a `briefing` task with a `briefing_name`, in a room that user is a current member of, withholds nothing (`rooms.scopes._members_own_schedule`). The job lives in the user's workspace and names the room as where its answer is read, which is the consent a live turn carries. Under bwrap a guest's turn and a restricted task cannot write that file; on an unconfined shape a guest's tools can, which `security.room_scope_confinement` names, though such a job could already be aimed at the host's private room at full reach. Membership is a `room_members` row plus, where the user has any principal participant row, a present one, because Talk records a departure only as `left_at`. A job row owned by someone else, an owner who left the room, or a scheduled task flagged `is_group_chat` still withholds every scope. A read error on the second case withholds everything. Read by `effective_disabled_skills`, the proxy's `cli_skills`, `derive_authorized_skills` and identity env (`reach_index`), setup-env hooks (env dropped), and the mount plan. A member's turn in a shared room loses only ambient memory, in prompt assembly (`.claude/rules/prompts.md`). Per-room grants, `!room share` and `[rooms] shared_room_data_policy` are gone; `room_data_grants` is dropped by migration. Rules: `transport.md` ("Multiplayer rooms"), `docs/features/shared-rooms.md`.

What a restricted task gets:

- **No workspace without `files`**: `{mount}/Users/{user_id}` and per-resource mounts unbound. Without `developer`, repos and cache go too, dropped in `resolve_sandbox_cache_dir` so bind and `UV_CACHE_DIR` agree (ISSUE-320).
- **Own temp dir**: `{temp}/{user}/emissary-task-<id>` for a guest, `room-task-<id>` otherwise, also `ISTOTA_DEFERRED_DIR`, since a guest-planted op file in the persistent per-user dir would replay at the host's authority. `executor.task_deferred_dir` reads the choice from disk (restriction can change before drain); all deferred and `email_output` readers use it. A symlink there fails the task by return.
- **No Talk bind, for any task** (ISSUE-880, below).
- **`ISTOTA_WITHHELD_SCOPES`** is in the proxy base env only. `env_host_roots` drops the workspace without `files`; `sandbox.host_paths.memory_refusal` refuses memory dirs; the `skills` guard unions it with `withheld_for_task` over `ISTOTA_TASK_ID`; nextcloud `_scoped` refuses file and share verbs without `files`, and memory paths without `memory`, after collapsing a leading `//`. Without `memory`, `files list --depth` and `files search` drop entries inside memory dirs. Residual: `share list` (`--subfiles` or no path) and `files trash list` still show them.
- **`ISTOTA_TURN_AUTHOR`** (`own`, `guest` or `correspondent`, from `Reach.author`) sits beside it in the proxy base env, on every task and never in the model's env. The `email` CLI refuses on it (`skills.md`). Both variables exist only through the proxy: with `skill_proxy_enabled = false` neither is set, so the CLI refusal and `host_paths`' drop do not apply. `tests/smoke/test_sandbox_shared_room.py::TestACorrespondentsTurn` runs this through the live proxy.
- **Talk writes check the live roster**: `nextcloud talk send`, `share-file`, `rename`, `describe`, `invite`, `leave`, `delete` refuse unless participants are caller plus bot; posting into the task's own room is exempt, changing a shared room never; `invite` takes only the caller; an unfetchable roster refuses. Unchecked outside a task.
- **Vault withheld whenever anything is**: `vault_credentials={}`, `vault_write_limit=0`, no prompt line. Calendar discovery skipped without `calendar`.
- **`Groups/<id>`**: each group in `rooms.scopes.task_group_ids` bound read-write as `nextcloud_group_dir` after the channel bind, sorted, de-duplicated, via `sandbox.user_scope.scoped_user_dir`. `Groups/` never bound. Empty for a guest turn, stored-mixed turn, any guest/agent/unmapped participant, no recorded readers, or readers the members do not cover; `rooms.group_id` narrows. `project_fs_roots` carries it. `ISTOTA_TASK_GROUPS` (proxy env only) gates kv/memory `--group` (`skills/_group_access`, whole-id); deferred kv re-derives from the task row.

## Group web access and managed writes

`groups.policy` checks current membership on member web reads and writes, independent of owner management authority. ## sandbox/tool_server.py

`python -m istota.sandbox.tool_server --fd N`, one per **task attempt** on either brain, via `build_bwrap_cmd(..., profile=NATIVE)`, placed in the cgroup from `preexec_fn`. Builds one `ToolEnv` from `hello` and binds the core tools (`build_default_tools`) (ISSUE-389). Holds no image library (see `lib/image_sniff.py`) and must not import `istota.skills` (`tests/test_tool_server_env.py::TestTheServerDoesNotImportTheSkillsPackage`; why `sandbox/git_hardening.py`, `sandbox/forge_bin.py`, `lib/untrusted.py` live outside `skills/`).

- **Wraps nothing**: nested bwrap under `--unshare-user --disable-userns` fails, so `ToolEnv` lost the field.
- **Places nothing**: membership is inherited at fork; `cgroup.procs` is unbound.
- **Every call goes through one `ToolDispatcher`** (`build_dispatcher`, #862): the hello's `tools` subset (absent = all of them, `[]` = none), argument preparation, the readers-writer lock (Bash, Write, Edit, KillShell alone; Read, Grep, Glob, BashOutput together) and the hello's `text_cap`. Native's `request_hello` sends `tools` as its grant narrowed to `SANDBOXED_TOOL_NAMES` and no cap; the loop prepares arguments too, which is safe because preparation is idempotent on its own output (`tests/test_tool_server.py`).
- **Background jobs** (`session/tools/bash_jobs.py`, #865): Bash `run_in_background` forks a job the way a foreground command is forked, so it holds the namespace and the task cgroup by inheritance; BashOutput reads it and KillShell kills its group. One table per server, at most `MAX_RUNNING_JOBS` running and `MAX_KEPT_JOBS` kept. A job has no timeout unless the call names one, since the attempt bounds it. Output follows Bash's rules: the first `max_output_bytes` in memory, the rest in a `bash_output_*` spill file unless `bash_spill_full_output` is off, read back from the open descriptor. The spill stops at `JOB_OUTPUT_LIMIT_BYTES`, because `temp_dir` is tmpfs on the stack, and the status line says how much was not kept. **A job leads its own session, so a signal to the server does not reach it, and neither does `aclose`'s group kill.** `tool_server.main` kills every job in a `finally` and from SIGTERM and SIGHUP handlers, which then re-raise so the exit stays a signal death (`remote._TERMINATED_PREFIX`). Under bwrap `--unshare-pid` ends a job even after a SIGKILL to the server (`tests/linux/test_tool_server_lifecycle.py`). A job has ended once its pipe is closed and its command has exited, so `server & echo up` stays running and killable through the group number (`_kill_group`, because `kill_group_if_live` stops once the leader is reaped), and `exec > log; build` is not killed for closing the pipe. Residuals: unwrapped, a SIGKILL to the server leaves a job running, and a child that redirected away from the pipe has detached and is left to the namespace, as with a foreground command. **No Monitor tool, by decision**: BashOutput's `wait_seconds`, capped at the Bash timeout, waits for a job to end, and neither brain can deliver a result between turns. The running status carries the elapsed time, so polling a quiet job does not trip native's loop detector. A job does not survive into another attempt or task.
- **A second front end, `--mcp --hello PATH`** (#862): MCP over stdio through `mcp_stdio.serve_stdio`, the hello read once from a 0600 file in the control dir (`O_NOFOLLOW`, regular file), the calls through the same dispatcher. An optional `gate` FIFO in the hello holds every `tools/call` until one byte arrives, read once; `initialize`, `tools/list` and `ping` are never held. The MCP stream is moved off fds 0 and 1 at start, which become /dev/null and stderr, so a Bash child cannot read or write the CLI's stream. `tests/test_tool_server_mcp.py`.
- **Merges `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY` from its own env** into `subprocess_env`, since the wrapper `exec env`s them onto this process and the frame env came from the bridge-less daemon. `NO_PROXY` is deliberately empty, so the merge tests presence; the wrapper wins collisions (the loopback bridge is the only reachable proxy).

Nothing raises past `main` (sends `fatal`); frame contents are never logged.

## sandbox/tool_launcher.py

`python -I -m istota.sandbox.tool_launcher --report FIFO --env-file PATH -- ARGV...`, the command the `claude` CLI runs as its MCP server (#862). In order: `os.environ.clear()`; report its pid down the FIFO (`O_WRONLY | O_NONBLOCK | O_NOFOLLOW`, `S_ISFIFO` by `fstat`); read the env file (`O_NOFOLLOW`, regular, a JSON object of strings) and unlink it; `execve` with that env. The pid survives the exec, so the daemon authorizes the tool server and never the CLI. The report comes before the env file so a respawned launcher still reports and is refused. `ARGV[0]` must be absolute; nothing searches `PATH`. Every refusal, an exec failure included, exits 2 before running anything, with one line on stderr and no values. The child's env is the file's because `execve` is passed it explicitly; the clear covers only the launcher's own life before the exec. stdlib-only, imports nothing from the package. `tests/test_tool_launcher.py`.

## sandbox/tool_server_protocol.py

stdlib-only, one `ProtocolError`. 4-byte big-endian length plus UTF-8 JSON; `MAX_FRAME_BYTES` (32 MiB) enforced on both ends. `hello` carries two optional fields, `tools` and `text_cap`, with no version change. Messages: `hello` / `call` / `abort` / `shutdown` down, `ready` / `update` / `result` / `fatal` up. `ToolResult.details` does not cross (only `agent/loop.py` reads it); content blocks are plain dicts. `FrameDecoder.close()` raises on leftover bytes: a missing result is a broken server, not an unmade call.

## sandbox/cgroup.py

A cgroup v2 group per task (A6): `<unit cgroup>/task-<id>-<attempt>/` with `memory.max`, `pids.max`, `cpu.max`. A sibling of the daemon's `supervisor/` leaf (v2 forbids controllers under a process-holding cgroup). `resolve_root` takes the last `.service`/`.scope` (the first is `user@N.service`). **In the container** it first takes `ISTOTA_TASK_CGROUP_ROOT`, the private namespace's root the entrypoint's root phase remounted and delegated to uid 10001, but only when `declared_root_problem` finds it a cgroup2 directory on a mount rooted at `/`, in a cgroup namespace of the container's own (this process's `0::` path is `/`, the `supervisor` leaf or a `task-*` cgroup), with a writable `cgroup.subtree_control`: a bind of the host's `/sys/fs/cgroup` reads `/../..`, and `cgroup: host` reads `/` with the process at the VM's path for the container (`/system.slice/docker-<id>.scope/…`); both are writable once remounted, probe clean, and are the VM's whole tree. The root phase refuses both before writing anything, the second by requiring its own cgroup to read `0::/`. The mount lookup is `lib/mountinfo.covering_mount`, shared with the entrypoint's rclone preflight. `doctor`'s `security.task_cgroups` FAILs on a declared root with a problem or a failed `probe()`, WARNs where nothing declares one (a host unit without `Delegate=`, the web container), and SKIPs off Linux and in a task. A successful `memory.max` write is the delegation proof, so startup calls `probe()`, not `resolve_root`. Placement is `preexec_fn` since bwrap forks during setup (ISSUE-285): parent opens `cgroup.procs`, child writes `0`, `verify_placement` reads back. `place()` is the after-the-fact backstop for a pid a brain reports without having spawned it through a `preexec_fn`. `destroy` writes `cgroup.kill` on `EBUSY` (5.14+); `read_events` names an OOM kill before `rmdir`. Fails open without `Delegate=`, said at startup. stdlib-only, never raises.

## sandbox/host_paths.py

**One rule, one implementation, two derivations** (ISSUE-447). Containment: `path_under_roots` / `resolve_in_roots`. Roots: only `workspace_roots`, which scopes `{mount}/Users/{user_id}` via `sandbox.user_scope.scoped_user_dir`, guards the conversation token, and drops what it cannot scope. Per-argument dispositions live in `skills/_hostpath.py`.

**A path a user names in their own config** (CRON.md `prompt_file`, HEARTBEAT.md `file-watch`, a briefing source's `path`) has no task env and no roots to derive, so it takes `owner_path_parts` (ISSUE-596): `/Users/<owner>/...` by exact id, no `.`/`..`/empty component, then a walk with `sandbox.confined.open_dir` (`O_NOFOLLOW` at every directory) and an fd-relative leaf open. The fixed-name files in `{bot_dir}/config/` (TASKS.md both ways, the BRIEFINGS.md import) go through `read_user_config_file` / `write_regular_file` like the rest of that directory. HEARTBEAT.md `url-health` is admin-only, beside `shell-command`.

**A `folder` or `shared_file` resource is walked, never resolved** (ISSUE-782). `linked_resource_parts(workspace, resource_path)` refuses an empty, `.` or `..` component, walks from the workspace root with `sandbox.confined.open_dir`, and requires the leaf (stat with no follow) to be a directory or a regular file. `sandbox.plan.user_data_mounts` binds `mount.joinpath(*parts)` and skips one whose spelling is under `Users/<user_id>`; `workspace.places.list_places` applies the same rule. A link an operator placed in the workspace to reach a directory elsewhere no longer works as a resource. The check is not what the mount gets: a resource is bound from a descriptor (`sandbox/bind_launcher.py`, below). A resource spelled with an empty, `.` or `..` component is refused too, without a log line, since `user_data_mounts` neither logs nor writes.

`scheduler_deferred`'s `import_csv` arm read `source_path` unchecked on every shape (any daemon-readable file into the health DB); it now uses `_resolved_source_path`. Replay is a boundary everywhere, so `health upload` / `import-csv` / `attach-document` are `EGRESS`, matching replay's accepted set.

**A spawner passes task identity, or every path is refused.** `whisper`'s `out_of_process` spawn lacked `ISTOTA_USER_ID` and `_pre_transcribe_attachments` logs only at debug. `--trusted-caller` and daemon-detection rejected. `executor._audio_in_reach` stages the out-of-roots Talk shape into the task temp dir first.

**An attachment is opened, never resolved** (ISSUE-610). `sandbox/attachment_source.py` is the one rule for audio staging, image preparation and `executor.stage_attachments`: under a root, a walk with `O_NOFOLLOW` at every component and a regular-file leaf; under none, only where the daemon writes attachments itself: `{NC_DATA_ROOT}/<user>/files/Talk/<name>` (`download_talk_attachments`), `{temp_dir}/whatsapp-media/<name>` and `{temp_dir}/attachments_<id>/<name>` (the WhatsApp and email upload-failure copies), and a caller's `extra` directory (audio passes the task's control dir, for `room-attachments`). A new daemon-side attachment location has to be added there, or it is refused. Residual: in-root audio is still handed to the whisper child by name, so a concurrent task can swap a component during model load; closing it means giving the child a daemon-only root. ## sandbox/bind_launcher.py

**A linked resource is bound from a descriptor, never by name** (ISSUE-881). Anyone who can write the resource's tree can swap a name: the owner of another home a resource points into, or a concurrent task when an operator-written resource sits under a `Channels/<token>` or `Groups/<id>` it can write. `Mount.walk_root` marks these entries. `render_bwrap_argv` touches no name for them: it emits `--ro-bind-fd <fd> DEST` or `--bind-fd <fd> DEST` and wraps the command as `python -I -m istota.sandbox.bind_launcher --binds JSON -- /abs/bwrap ...`. A task with no such resource keeps a bare `bwrap` and its argv is unchanged. The launcher pairs each `{root, parts}` in order with a placeholder before bwrap's `--`, walks from the daemon-composed root with `confined.open_dir`, opens the leaf `O_PATH | O_NOFOLLOW`, requires a directory or a regular file, and execs bwrap holding the fd. bwrap turns the fd into a name through `/proc/self/fd`, mounts that, compares the mount's device and inode against the fd, and dies with "Race detected binding fd" before running anything on a mismatch.

It is a process because the `claude` CLI spawns the command on that brain and hands a child no descriptor of ours; `tool_launcher` execs it like any other command, and the pid survives both execs. **A resource that fails the walk loses its bind and the task runs**, since failing the namespace would let a task in one home stop another user's tasks through a name they share. The price is that a swap landing in bwrap's own window fails that one attempt, which the owner of the tree can cause on purpose. bwrap's path is absolute, from the daemon's `PATH` (`executor._bwrap_fd_bind_binary`), because the launcher runs with the task's env. A bwrap without the flag (older than Debian 13's) loses every linked resource with an ERROR rather than falling back to a bind by name. `tests/linux/test_resource_bind_identity.py` races a swap of the leaf and of a parent against the real mount builder, with a control that runs the same race against a bind by name and requires the canary to appear. `tests/smoke/test_sandbox_in_stack.py::TestALinkedResourceBindsByDescriptor` runs it unprivileged under the shipped seccomp profile. Docker Desktop ignores AppArmor, so the `istota` profile was checked by hand in enforce mode on the test VM: the fd bind passes. Its `deny mount ... /proc/**` rule does not read on this, since bwrap names a source under `/oldroot`. `doctor`'s `security.linked_resource_binds` warns on a bwrap without the flag. `project_fs_roots` still resolves the source by name. Under the sandbox those roots are the error-message layer, so a swap changes a message and a symlink loop there fails that one attempt. **Any spawn with a task's env makes a bare name absolute first** (`shell_exec.on_daemon_path`, used by the native spawn and the CLI harness): given a bare `bwrap`, `subprocess` searches the task's `PATH`, which starts under the model-writable temp dir.

## sandbox/guarded_http.py

The HTTP half beside `net_guard`'s address rule, for daemon-side fetches to a host a user or a remote server chose. `pinned_request` builds a request against a checked address with the `Host` header and TLS SNI on the name, so DNS cannot answer differently between check and connect; the caller's headers never replace `Host`, nor `Authorization` when `auth` is given. `new_client` is the client both skill clients used to build by hand: `trust_env=False`, no automatic redirects, the trust store still reading `SSL_CERT_FILE`. The `wordpress` and `servarr` clients build their requests with `pinned_request` and keep their own send loops, because both refuse redirects and carry retry and `outcome_unknown` rules of their own; their unchanged tests are the check on the extraction.

`guarded_send` is the whole path for callers with no such rules (the shared-source fetchers and the RSS poller): a required `deadline_seconds` bounding the whole call (hops and body included, checked after every chunk), because httpx's timeouts are per read and a server dripping one byte inside each would hold a web worker thread for hours; plain `http` only to a host on `private_hosts` unless the caller passes `allow_plain_http` (the RSS poller alone: the user chose the scheme, and the request carries nothing the daemon adds), a non-public address only for a listed host either way, each checked address in turn on a refused connection, the body read to `max_bytes`, and no redirect unless `max_redirects` allows. Each hop is checked from scratch; a hop may reach a non-public address only when its host is listed **and** is the original request's host, so a public feed cannot bounce the daemon onto an internal one, and a hop to another origin drops `auth` and any `Authorization` header for the rest of the chain. A 303, or a 301/302 to a method other than GET or HEAD, becomes a GET with no body. Every refusal is a `GuardRefused` with one of `host_refused`, `too_large`, `redirect_refused`, `connection_failed`, `timeout`, and its text is that code alone: a feed URL and a share secret are bearer credentials, so neither the URL's path or query nor any response text reaches an exception. The answer comes back with its body decoded and the wire headers (`Content-Encoding`, `Content-Length`, `Transfer-Encoding`) dropped. `session/tools/web_fetch.py` is not converted (async, tool-server leaf, its own policy). Nor is the heartbeat `url-health` check, deliberately: it is admin-only (ISSUE-596), and the check exists to probe internal services the guard would refuse. It is the one thing HEARTBEAT.md still does from the daemon's network, so an injected admin task, a limited one included, can do two things with it: read a status code from an internal address (ISSUE-886), and send data out, since the GET goes to any URL it wrote, redirects followed, with private data in its host, path or query. That is open pending a decision; see "The egress decision" below and `docs/architecture/egress.md`. The RSS poller is converted (#838, `feeds/poller._guarded_get`, `[feeds] private_hosts`). Tests: `tests/test_guarded_http.py`, loopback servers named in `private_hosts`, plus httpx's mock transport for the rules that need a public name.

## Credential broker CA

Grants allow every HTTP method; legacy `credential_grants.methods` is kept for compatibility, neither exposed nor enforced. Exact host and port, auth-header restrictions, the HTTP override and live revocation still apply.

`credentials/broker/ca.py`: CA under `{db_path.parent}/credential-broker` (`0700`, atomic `0600` P-256 key plus ten-year cert, cross-process lock). ## Private skill credential channel

Each skill invocation gets a socketpair via `ISTOTA_CRED_FD` / `pass_fds`, never the model; the skills package marks it close-on-exec before loading skill code. `_credref` resolves at parse time over a per-name duplicate. The proxy accepts only credential reads there, sets provenance itself, and charges the attempt budget. With the broker on it checks the grant (room scope, `allow_scheduled`, revision), refusing `credential_not_granted` or `credential_changed`; a grant read error refuses. ### Connected mail accounts on the channel

A second per-row, non-vault type beside `wallet_card`: `{"type": "mail_account", "account_id": N, "purpose": "read" | "send"}`, asked by the email CLI through `credential_shim.fetch_mail_account` once it has resolved `--account <slug>` to a row itself (`mail.accounts.get_account`, scoped by `ISTOTA_USER_ID`). `SkillProxy._serve_mail_account` answers for `self.user_id` and `self.task_id`; the request contributes only the id and the purpose. Refusals, in order, a closed set: `skill_not_permitted` (the invoking skill is not `email`; `_credential_channel` carries the skill name the proxy spawned), `account_not_found` (a malformed id, or `mail.accounts.resolve_for_daemon` finding no enabled row for this user: one answer for both, so ids cannot be probed), `invalid_credential_request`, `account_channel_unavailable` (no config, user or task), `mail_accounts_disabled`, `not_owner_turn`, `permission_denied` (`send` on a `read` account, or `[mail_accounts] allow_send` off), `password_missing` (absent, or undecryptable without the master key). The public socket answers `account_channel_unavailable` to the type and serves nothing; so does a `skill:` job, which spawns the CLI with no proxy and no fd. A `command:` job's CLI goes through the proxy like a task's.

**The turn check is the channel's alone.** `not_owner_turn` fires unless `rooms.scopes.turn_author` answers `own` (`skill_proxy._owners_own_turn` is its wrapper): the task's row, or any ancestor's on the `parent_task_id` chain, is not this user's, has a `guest_participant_id`, or its stored turn was written by someone else; a missing ancestor, a cycle or a chain past 64 is refused too. A subtask has the host's user id and the room's token but no `messages` row, so a check of its own row alone passed a correspondent's turn. A correspondent's mail runs as the host, so without this a prompt-injection mail could read the host's other mailboxes; `email` is on its allowlist, which makes this check the backstop behind the verb refusal rather than a formality. An email task with no stored row, or a stored row naming nobody, (an approved held mail no room admitted) is read from its `processed_emails` sender and counts as someone else's unless that is one of the user's own addresses (ISSUE-874); the proxy, the deferred KV replay and the `kv` and `briefings_config` CLIs (`skills/_turn_access.calling_turn_passes`) pass the config's addresses, and with no config the check falls back to `db.own_addresses_without_config`, which can only under-trust. A `!retry` copy of an email task has no ledger row and leaves the decision to its parent on the chain. `resolve_for_daemon` applies every other refusal and is what `drafts.release`, the briefing source (`imap:<id>`) and the connection test call; they run daemon-side with no turn to check.

The answer is `{"imap": {...}, "smtp": {...} | null}`, with `smtp` only for `send`, so a `read` account's SMTP password never leaves the daemon. The CLI boxes each password in `_credref.SecretValue` (the shim is copied standalone into the sandbox and cannot import it). Not charged against the vault fetch budget: it is not a vault entry. Every serve and refusal logs `task_id`, `account_id`, `purpose` and the reason, never a host, username or password; an unexpected error answers `mail_account_error` and logs the exception type only. The passwords are `secrets` rows under `service='mail_account'`, keys `{id}.imap_password` / `{id}.smtp_password`, outside `CONNECTED_SERVICE_SCHEMA`, so `istota secret` and the generic secret routes cannot write them and no manifest, `credential_env` or `istota-credential env` lookup reaches them (`tests/test_skill_proxy_mail_account.py` builds a runtime for a user with two accounts and checks none of their values is in `credential_env`, `base_env` or the lookup allowlist). Connections go through `mail/connect.py`: verified TLS, the resolved address checked against `net_guard` unless the host is in `[mail_accounts] private_hosts`, and the socket connected to the checked address.

## The egress decision

`Reach.egress_hosts` says where a task may send bytes: None for any public host, else the exact hosts its owner approved. `rooms.scopes._egress_for` decides once per `reach_for_task`, for an own task only, from the root of the `parent_task_id` walk (`_turn_chain`, which `turn_author` also walks), so a subtask or `!retry` copy gets its root's answer. Attended (`origin_surface_for_source_type` names a surface other than `istota_file`, or `cli`) and research are None, and so is a job whose current row digest has an `open:` grant. Everything else unattended is limited: `cron:<name>`, `briefing:<name>`, `assignment:<id>` and `tasks-file` have grants to read, and any other source type has the empty set, as does a read failure (`egress_decide_failed`) and no database.

**A public job has open web and holds nothing** (`Reach.public`). `egress.public_job_approved` needs both the row's `reach = 'public'` and a `public:` grant on its current digest, asked ahead of `open`, so turning the job back to `private` takes effect without removing the grant and an owner who approved both gets the narrower. A subtask or `!retry` copy takes it from the root. `withheld` is research's set (`PUBLIC_KEPT_SKILLS`: `browse`, `skills`, `untrusted_input`, plus `files` and `memory`) and `sandbox.user_scope.ROOM_NOTES_WITHHELD`, which is not a scope: research has no room, and a public job keeps its room for delivery, whose `Channels/<token>` is the user's own notes in a private room. So that directory is not bound, not loaded and not a host-path root. `restricted` is true, so the temp dir is its own and there is no vault. `executor.public_posture_refusal` is the research gate's capability check, shared by `execute_task`, `confined_command` and `_execute_skill_task`, and a missing capability fails the task with research's reasons. `execute_task` then sets `use_context = False` and no resources; groups read the reach rather than a second query, with `task_group_ids` answering `[]` for its other callers. `is_admin` stays real, since `[brain.native.web_fetch] admin_only` reads it and every admin-only skill is already withheld. `_drain_deferred_ops` keeps `PUBLIC_JOB_KEPT_SUFFIXES` (`subtasks`) and purges the rest, because the directory is model-writable and the model is reading strangers' pages. **The posture is on the task row** (`tasks.egress_posture`): `executor.record_egress_posture`, on all three paths, writes `public` or `private` once before the model runs, and a public task whose write fails does not run. `scopes.job_posture` reads the column for the occurrence (`_decision_root`: the nearest job occurrence up the chain, so a job re-run decides for itself from the job as it stands, and a subtask or `!retry` copy takes its occurrence's answer) and consults the job row only while NULL. `private` is what lets a `once` job's writes survive the row going in the completion transaction. NULL with no job row is `unknown`: the drain purges and a descendant withholds every scope. `egress.record_posture` has one caller, and no skill or deferred handler names the column (`tests/test_egress_grants.py`). `_execute_skill_task` has no proxy, so it refuses a withheld skill itself (`public_job_skill_withheld`, logging no entry, since no grant allows it) and sets `ISTOTA_BROWSER_PROFILE` and `ISTOTA_WITHHELD_SCOPES` in its own env.

`rooms/egress.py` holds the entries and the tables. **Only an authenticated person writes a grant**: `add_grant`'s callers are held to a list by `tests/test_egress_grants.py`, and no skill or deferred handler imports the module. `job_digest` covers `prompt`, `command`, `skill`, `skill_args`, `publish_shared_kv` and `publish_shared_kv_trusted`, length-prefixed, NULL reading as empty so a seeded row survives its first sync. `_row_approved` also needs the occurrence's own fields, read from the table, to match the row. `db._migrate_egress_seed_open` brings every existing job in as `open`, once, with the table's absence as the marker and the table and the seed in one transaction. `_module.*` rows are seeded too; they run through `_execute_skill_task` and their skills are `local`, so the grant does nothing.

**A limited task loses each `external` skill with no `skill:` grant, and only that.** They join `withheld` so the menu, proxy, mount and credential gates apply, and are named again on `Reach.egress_withheld`. That includes the exec socket: `developer` is `local` and stays, and the mount plan binds the socket only with `devbox` not withheld, since the container has open egress. `withheld`'s truth used to mean the restricted posture (own temp dir, no vault, the room card's "no member asked"), which is for input somebody else wrote, so those sites read `Reach.restricted` (`withheld` minus `egress_withheld`), and `build_task_runtime` takes it as `restricted`. `_execute_skill_task` checks `egress_withheld` itself: a pure `istota-skill` row in CRON.md is promoted to a skill task with no proxy, and a model can write that row.

**The CRON.md sync owns the lifecycle** (`cron_loader._sync_job_approvals`). A new row starts from nothing, whatever an old job of that name left. An edit to what a job dispatches drops its `open:` and `public:` rows, keeps host and `skill:` entries and adds the matching row to `egress_refused`, reopening one the owner dismissed. `reach = "public"` is stored and asks once, on the tick it appears, and grants nothing. `db.delete_scheduled_job` forgets the subject, so every row removal does; the module sync's prefix delete does not, and its rows are inert. A `prompt_file` that fails to read for now keeps its row (`CronDocument.unread_names`), since its approvals would not come back. The sync returns the subjects it asked about and the scheduler hands them to `egress.raise_refused_bell` after the commit.

**The network seams read it.** WebFetch, on either brain, takes `WebFetchPolicy.exact_hosts` from `session.tools.web_fetch_policy_for_task`: `_validate_url` checks it on every hop, before anything resolves, beside `allow_hosts`. None is no limit and an empty tuple refuses everything, so `_web_fetch_mcp` keeps the two apart. The executor puts `egress_hosts` and `egress_log` on `BrainRequest` for native and on `HarnessSpec.web_fetch` for the CLI's `istota_web`. `_build_network_allowlist(..., egress_hosts=)` is, for a limited task, `extra_hosts`, the Nextcloud host and each grant at 443; registries and forges come back only if granted. The Tools section names the approved hosts. A cron `command:` job takes its task's reach in `confined_command`, and a heartbeat check states `frozenset()` itself and records nothing. WebSearch is unchanged.

**The verb rules read `ISTOTA_EGRESS_LIMITED`** (`lib/egress_log.py`), `1` whenever `egress_hosts` is not None, set by `build_task_runtime` in the proxy's snapshot beside `ISTOTA_TURN_AUTHOR` and by `scheduler._execute_skill_task` in its own env, since a `skill:` job has no proxy and CRON.md can name any verb of a `local` skill. Never in the model's env; a client's value goes nowhere, because the child's env is the snapshot. `feeds add`, `feeds import-opml`, `bookmarks add` (with `--text` too) and `ntfy send --topic` refuse with `reason: egress_limited` and log nothing, since no grant could allow a verb. So do `briefings_config shared-block set`, `set-prompt`, `run` and `remove`, and `group save` and `group set`, because research runs with open web on the prompt and sources they write; the reads, and the group verbs that write neither (`run`, `delete`, `delivery`, `revoke-approval`), stay. `mail.outbound_policy.effective_policy` answers `all` in such a process whatever the floor and the user's setting say, so mail to anyone but the user's own addresses is held. Mail naming the bot's address (`mail.ownership.is_bot_address`, plus addresses included, To, Cc or Bcc) is refused in `_outbound_gate`, not held: from a connected account it returns as the user's own email turn, which is attended and open, and approving a draft reads as sending a mail rather than as granting that. The `room` verbs read no flag: `room post` is refused from any task with no private origin (`unsupported_origin`) and names only a room its user is in, and `room whisper` goes to the user alone from a shared room they are in. With `skill_proxy_enabled = false` nothing sets the variable, as with `ISTOTA_TURN_AUTHOR`, so these rules do not apply there.

**A bound credential does not widen the list.** `NetworkProxy` refuses a target off `allowed_hosts` before it asks the broker, on CONNECT and on absolute-form HTTP, and the list reads no binding. So a limited task keeps its vault and its grants and can send a placeholder only to a host its owner approved. A granted host that is also bound is intercepted as usual.

**A refusal goes to `egress-refused.jsonl`** (`lib/egress_log.py`) in the task's control directory: `web_fetch` and `connect` log the host, the skill proxy logs `skill:<name>` for a name in `Reach.egress_withheld`, and `browse` logs `open` for a credential verb on the isolated profile. The CONNECT proxy logs only for a limited task. An address refusal is not logged, because the host is already on the list. `executor.record_egress_refusals` reads it after the proxies stop, on its own connection, since nothing holds one across a task, and `confined_command` does the same. `egress.entries_from_log` decides by channel, so `https://open/` cannot read as a request for full access nor `CONNECT skill:browse:443` as one for a skill, and drops what no grant could hold. A subject comes from the root (`scopes.egress_subject`); a task with none files nothing. A CRON `skill:` job has no proxy and no log file, so `_execute_skill_task` files straight to the row. `raise_refused_bell` runs after the commit, only when an entry still asks. Without bwrap or the network proxy, WebFetch and the skill gates still apply and the shell is unbounded.

**The surfaces.** `webui/egress_routes.py` is Settings, Network access: `GET /settings/network`, and `POST` to `/grants`, `/grants/remove`, `/refused/dismiss` and `/approvals`. The user comes from the session and no parameter names one, so an admin gets nothing extra, and a subject that is not the caller's is the same 404 as one that does not exist. Bodies are bounded and parsed by hand, because a validation error echoes its input and a refused hostname can carry data; no log line names a host or a job. `/grants` refuses an `open:` or `public:` entry: those go through `egress.approve_job`, the second writer, which compares the digest the page showed with the row under the write lock (409 `stale_job`) and refuses `public` for a row not asking for it. `istota egress list|grant|revoke` is the operator's door and prints the text an `open` approves. `describe_subject` is the one view of a subject for both. What is deliberately open, and the residuals, are in `docs/architecture/egress.md`.

**A personal briefing's source writers refuse too.** `briefings` `sources add`, `sources set`, `blocks add` and `blocks save` answer `egress_limited`: a source is gathered in the daemon, past every limit on the task, and needs no admin. The refusal is in each Click command (`briefings.cli._refuse_if_limited`), not the facade, because the facade sees argv and a leading `--` walks past a check on its first words. The operator CLI shares the tree and its environment has no flag.

**HEARTBEAT.md `url-health` is open.** A limited admin task can plant a URL the daemon fetches with no egress limit; `sandbox/guarded_http.py` above has why the check is daemon-side. It stays that way pending a decision.

## The isolated browser profile

`__isolated__` is one Chrome profile for every browse use that should hold no user data (#899): a correspondent's turn with `browse` allowed, research, a group source, a limited job with `skill:browse`, and anything else that reaches browse with every scope withheld. `browse` is `shared_room: private`, so a guest's turn does not reach it at all. `Reach.isolated_browser` decides, defaulting to true, and only `reach_for_task`'s own-turn arm answers false, with nothing withheld and open egress. It reaches a skill CLI as `ISTOTA_BROWSER_PROFILE` in the proxy's base env, beside `ISTOTA_TURN_AUTHOR`, and `browser/owner.browser_headers` and `with_browser_owner` read it instead of `ISTOTA_USER_ID`. A client cannot set it: the proxy's child env is its snapshot. `_execute_skill_task` has no proxy and sets it in its own env. With `skill_proxy_enabled = false` the variable is unset and the CLI keeps its user's profile, except `__briefings__`, which is a task identity and never names a profile. The container refuses that old name with 403 so it cannot reopen as an ordinary profile, and `pool.remove_retired_profiles` deletes its directory at boot. `Config.get_user` answers `None` for `__isolated__`, so no configured person shares that jar.

Tasks share the cookie jar, so a session belongs to its `X-Istota-Owner` (the task id, or a fresh uuid per daemon call), and another owner's session id is a 404 before anything touches the page. `MAX_SESSIONS` counts per owner under `MAX_TOTAL_SESSIONS`, and a foreground detail is fixed text there, since the window title can be another task's page. It has every browse verb except `state` and `forget`; `/evaluate` and `/render-document` stay refused. Credential fills, OTP, cards, purchases, recovery captures and `--find-secrets` are refused in the skill before parsing, because parsing fetches the value, and again in `browse_api._asks_for_a_secret`, with `isolated_browser_credentials_refused`.

Residuals. A job that signs in by typing with `--fill` or `--type` leaves that session in the shared profile. All isolated tasks hold one of `MAX_INSTANCES` (2) Chrome slots: two users with live tabs refuse it with a 503 until a tab passes `SESSION_TTL` (600s), and a kept isolated tab holds a slot against a third user likewise. At `MAX_TOTAL_SESSIONS` (4) a new owner's tab still replaces the oldest tab anywhere, another task's or a user's. Input to the shared X display is serialized by the single API thread and `_foreground`'s per-action focus, so concurrent tasks take turns rather than run in parallel. `tests/test_browser_profile.py`; the container half also in `tests/image/test_browser_image.py::test_the_isolated_profile_in_the_shipped_api`.
