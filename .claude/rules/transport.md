# Transport abstraction (`src/istota/transport/`)

A uniform seam over messaging surfaces. Inbound, a `Transport` normalizes messages into `IncomingMessage` and `ingest_message` makes tasks. Outbound, `deliver` / `edit` push a result to a resolved channel. `TransportRegistry` resolves one transport per task. Eight ship: Talk, Email, Sms, WhatsApp, Ntfy, IstotaFile, Repl, Web. **Matrix is the designed-for next consumer**: one `Transport` subclass plus a `make_registry` line.

`surface_class`: **push** delivers via `deliver()`; **stream** (repl, web) means an interactive task's result is the `task_events` log (`routing._STREAM_SURFACES`, governing that alone). `ReplTransport.deliver` is a no-op; `WebTransport.deliver` appends a `role='system'` row for anything routed to `web` (ISSUE-121), never for a web task's own result. `conversation_token` stays the opaque per-surface channel id and `source_type` the routing key.

## Layout

`_types.py`, `registry.py`, `routing.py`, `ingest.py`, `participants.py`; subpackages `talk/`, `email/` (`inbound.py`, `outbound.py`, `threads.py`), `sms/` (`.claude/rules/sms.md`), `whatsapp/` (Cloud and Baileys, `.claude/rules/whatsapp.md`), `ntfy/` (`send_ntfy_async`, the single ntfy POST), `istota_file/`, `repl/`, `web/`. Low-level clients stay outside (`istota.nextcloud.talk.TalkClient`, `istota.skills.email`); shared non-transport email helpers are `istota.mail.support`.

## Core types (`_types.py`)

- **`IncomingMessage`**: `channel_token` → `conversation_token`, `delivery_token` → `talk_delivery_token`, `platform_message_id` → `talk_message_id`, `reply_to_message_id` → `reply_to_talk_id`; multiplayer `author`, `addressed_to_bot`, `classified`, `is_command`, `room_container`. `sender_address` is untrusted, sanitized by `db.external_email_sender`. `queue` defaults `foreground`; email passes `[scheduler] email_task_queue` (default `background`) so a flood at `bot+user@` cannot take chat slots (ISSUE-250).
- **`TransportCapabilities`** (frozen): edit, threading, progress-ack, typing, `max_message_length`, `surface_class`, `user_routable` (False for `istota_file`, `repl`; `registry.routable_names()` is what the UI offers, `_validate_descriptor_surfaces` still accepts the rest), and the three room fields.
- **`DeliveryOptions`**: `title`, `priority`, `tags`, `markdown` (opt-in; ntfy's `Markdown: yes` bypasses `encode_header_value` so the ASCII retry cannot drop it).
- **`Transport`** protocol: `poll`, `deliver(target, text, *, task, reply_to, reference_id, threaded) -> int | None` (task-aware), `edit`, `download_attachment`, `resolve_target`.

## Registry (`registry.py`)

`make_registry(config)` does no I/O, so `send_notification` can build one on demand. Talk, email, sms, whatsapp register on `enabled`; the rest always, gated per user later. `_surface_for_source_type` is the **delivery** map: email, sms, whatsapp, repl, web map to themselves (web resolves to no push transport); everything else → `talk`.

## The room model (`src/istota/rooms/surfaces.py`)

A room is one conversation bound to several surfaces. Four questions:

1. **Inbound room role** (`inbound_room_role`; `room_role` in the leaf): `member` registers, binds and adds membership (talk, web, sms, whatsapp; the two phone surfaces each own one private room per user, see "Phone rooms"); `guest` joins an existing room's transcript, never mints one (email; ISSUE-136 "existence, never creation"); `None` is never a room turn. A multi-party email thread is promoted per message via `IncomingMessage.room_container` and `rooms.surfaces.is_room_member_for`, and so is the user's private email room (`record_phone_turn` passes `room_container` for email; see "Phone rooms"). The spec asked for email's row to become `member`; it stays `guest` because `webui.app._user_row_display` marks a row external by `not is_room_member(origin_surface)`, so `member` would render a correspondent's row as the user's own, and the scheduler, `!retry` and `routing` read the same predicate for email tasks (the thread-hash and emissary reasons went with email on rooms stage 4); a WhatsApp group still sets `room_container` and registers through its own path, though the surface is a member anyway.
2. **Where the transcript lives** (`room_view`): `canonical` (web, our `messages`), `external` (Talk), `None` (email, sms, whatsapp, ntfy, istota_file, repl). Answered by the **durable-place test**: a durable, addressable place a person reads the whole conversation, that we can write into. An email thread fails it.
3. **Assistant fan-out**: derived; `_expand_room_destinations` pushes to `external`, skips `canonical` (the row is the delivery).
4. **`user_turn_mirror`** (`as_user`, `attributed`, `None`): a refinement of `external`. It does not carry body policy: an email-origin repost carries sender and subject, never the body (the wrapped untrusted prompt).

Bidirectional sync is (1) and (2) both non-`None`, not a setting. The leaf is static, stdlib-only (`transport` imports `db`), never raises, takes `object`, and answers conservatively for anything unrecognised. Transports keep their own literals; `tests/test_surface_capability_agreement.py` and `tests/test_surface_facts.py` (`SurfaceRoomFacts`, no defaults) hold them in step.

A phone thread (sms, whatsapp) satisfies (1) alone: it fails the durable-place test (it shows only its own half, and we can append only our own sends), so it owns a room without being a view of it.

**Two readers of `room_view`.** `rooms.surfaces.room_view()` is a code fact; `routing._room_view()` asks about live transports and collapses "not a view" with "not resolvable", safe only for `_expand_room_destinations` and `is_canonical_room_view`. Elsewhere, with `talk.enabled = false`, `webui.app._user_row_display` would render Talk turns as external.

**Two source-type maps.** `rooms.surfaces.origin_surface_for_source_type` answers origin: surface-named types pass through; briefing, cli, doctor, heartbeat, scheduled, subtask and `""` give `None`. The delivery map would flip seven of thirteen, and the negated confirmation gate would park cron and heartbeat tasks with nowhere to ask until `expire_stale_confirmations`.

**Sites reading the leaf** (`tests/test_surface_model_equivalence.py`): `record_inbound` room gate; `routing._room_for_destination` (after the `surface == "room"` dispatch, else `room:` descriptors drop, ISSUE-247); `!steer` and `_record_retry_user_turn`; `webui.app._user_row_display` (negated, raw column; the one site where "unknown" is unsafe); the scheduler's `store_turn_message` gate and confirmation mirror gate (`is_room_view`, negated).

The store gate and the confirmation mirror gate are where the membership and view axes diverge: sms and whatsapp are members with no view, so the store gate writes a phone-origin answer into its room while the confirmation gate (read negated) puts no prompt on a mirror leg. That is why the two were never merged.

**Four literals stay literals**, each commented: `commands._record_confirm_exchange` on `db.TRANSCRIPT_SURFACES` (web, talk, email, sms, whatsapp: member plus guest; `is_room_member` would stop an email `!confirm` recording its authorization; on sms and whatsapp the webhook already stored the answer, so the exchange writes nothing and the reply is mirrored after the send, see "Phone rooms"), `db._CONVERSATIONAL_SOURCE_TYPES` (completeness), the cleanup migration's DELETE (tracks `TRANSCRIPT_SURFACE_FILTER` plus `scheduled`), `db.TASK_ROOM_SCOPE_SQL` (read as `webui.app._AUX_ROOM_SCOPE` and by `db.task_shown_in_room`). `tests/test_surface_table_is_load_bearing.py` stops `TRANSCRIPT_SURFACES` being widened by coincidence. Email `!confirm` records its exchange while email `!retry` does not: an open product question. Name collision: `rooms.surfaces.is_room_member(surface)` vs `db.is_room_member(conn, token, user_id)`.

## Multiplayer rooms

A room can hold several humans: a Talk group, a multi-member web room, a Baileys WhatsApp group, an email thread with two or more humans besides the bot. One core pipeline decides speaker, authority, audience and reach; surfaces only normalize. Every rule is a no-op with one human (private goldens stay byte-identical). User docs: `docs/features/shared-rooms.md` (private replies and My notes included), `room-veto.md`; the developer-facing walkthrough is `docs/architecture/rooms.md`.

**Record, then decide.** `ingest.record_inbound` stores the user row (`task_id` NULL), asks the speech gate, and creates the task only on speak, returning `InboundResult` with `outcome` `created` / `recorded` / `dropped` / `replayed`. Dedup is `_prior_turn`. Only stored turns are gated; roomless email always gets a task. A private phone turn is stored in a one-human room, where the gate speaks; web refuses a member add to a private phone room for that reason, since a phone turn never sets `addressed_to_bot` and `mention` mode would record texts without answering them (a room shared before the refusal behaves that way until the added member is removed). An unanswered turn has no `Bot:` line; `!export` uses a `last_msg_id` cursor. A declined web turn returns `task_id: null`, `status: "recorded"`.

**The speech gate**, `rooms.speech_gate.should_speak`, first match wins: `agent_author`, `host_lost`, then on a guest's turn only `guest_command`, `guest_reply_off`, `loop_cap` (record), `not_multi_human`, `addressed` (speak), then mode: `mode_off` speaks, `mode_mention` records, `classifier` asks the model and fails closed. `rooms.policy.effective_speech_mode`: the room's, else the deployment's; an email thread room defaults to `mention` on a classifier deployment. The classifier never runs under a write lock: `ingest.classify_ahead` decides on its own read connection into `IncomingMessage.classified` (WhatsApp: `groups.classify_group_event`). Audited in `speech_gate_decisions` (no body). `addressed_to_bot`: Talk `is_bot_mentioned`; web `@name` not followed by a word char or hyphen, or the name first; WhatsApp `mentions_bot`, a quote of a stored bot message, or the name first; email on a thread room decided by the intake table (`threads.intake_facts`, `threads.thread_addressed`, email on rooms stage 2): the host's own mail asks with the bot address (or plus address) in To, or the bot named in the new text (`threads.addressed_in_new_text`: `threads.new_text` cuts at the attribution line or a forward marker and drops `>` lines, then the web rule with `any_line=True`, so a greeting can come first; ISSUE-607); anyone else's mail asks when it names the bot or when none of the host's addresses (`mail.support.own_addresses`, folded) is on To or Cc, the bot in To counting for nothing, since every reply-all on a bot-started thread has it there. The last case marks `tasks.host_absent`. A correspondent's reply-all the host is on that does not name the bot is recorded only.

**Participants, not members** (D1). `room_members` is sidebar membership; `room_participants` is everyone who wrote or is on a roster (`kind` principal / guest / agent, `left_at` history, unique on `(room_token, surface, surface_ref) WHERE left_at IS NULL`), named by `messages.author_participant_id`. `transport.participants.classify` decides kind in core because it depends on membership (a non-member istota user is a guest). `db.room_is_shared` counts distinct present humans; `participants.is_multi_human` is the one predicate gate and `classify_ahead` share. Presence: Talk roster sync, WhatsApp `group_roster`, email thread union, `remove_room_member`. `db.note_member_turn` is the one place a member's turn re-adds membership and un-hides, reached before Talk's `!command`, relay and confirmation branches.

**Talk records every human turn.** `config.users` decides authority, not recording; only the bot's own posts are skipped. An unmentioned group turn only records; the side effects (`!model`, `!command`, relay and confirmation answers, channel-gate notice, cancelling confirmations) stay behind `engaged = addressed or not is_multi_user`. The mention is always stripped. Group replies thread to the trigger, `@user` only for a Talk-origin non-guest task.

**Principal and host** (D2, D14). A principal's turn runs as that principal. A guest's speaking turn runs as the room's host (`room_policy`), `tasks.guest_participant_id` set, text fenced (`frame_untrusted`, `GUEST MESSAGE`) in `tasks.prompt` (transcript stays raw). Emissary mode: all scopes withheld, native WebSearch/WebFetch removed, deferred ops purged, own `emissary-task-<id>` temp dir, no memory extraction, confirmations to the host privately. The host is sticky; a departed host clears `host_user_id` and the room goes record-only until `!room host` (WhatsApp: bot leaves). Guest `!commands` ignored except the veto. `guest_reply` is `direct` on Talk and web, `held` on WhatsApp (D11); an email thread room has no guest mode (below), so `_ask_policy` reads it as `direct`, `guest_reply_mode` answers `direct` and the room settings do not show it; `held` makes a `room_post` proposal put to the host through the privately routed confirmation path (`rooms.private_replies.propose_guest_reply`). Loop cap (D9), guest turns only (`ingest._ask_policy`): assistant rows since the last istota-authored user row (default 3); a member's turn is never capped, and nor is a correspondent's on an email thread room (email on rooms stage 3: mail before thread rooms had no cap, and the inbound volume budget, ISSUE-250, is what bounds a mail loop). `max_bot_turns_without_human` is read but has no writer yet. `room_policy.speech_mode` is the host's (`rooms.policy.set_speech_mode` behind `speech_mode_refusal`, from `!room speak` and the web PATCH; refused on an email thread room; `default` writes NULL). It overrides the deployment both ways, so every classifier pre-pass gates on `rooms.policy.classifier_in_use` rather than on `[speech_gate] mode` (ISSUE-640): gating on the deployment let a room opt out but never in.

**Audience** (D3): `rooms.policy.audience_class` `private` / `principals` / `mixed`, stored in `tasks.audience`. Since ISSUE-576 `mixed` withholds no scope from a member's turn (the guest's presence is the member's choice); it still keeps group material out and leaves ambient memory out of the prompt (`.claude/rules/prompts.md`). **Epochs**: `room_epochs` splits when someone joins a room others already read, boundaries on `messages.id`, `tasks.id`, cached Talk id. `db.front_stage_cutoff` (highest boundary of an epoch whose joiner is present) bounds every front-stage history, recall and extraction read; not a linked turn's parent transcript or `!export`. A Talk join always splits; a web add acknowledges history. Epochs never bound `CHANNEL.md` (D19).

**Room containers** (D6, D10). `rooms.surfaces.SURFACES` keeps email `guest` (see the surface table above), and email's rooms come through the container override; whatsapp is `member` since phone rooms, and a group is told apart from the private chat by its binding (the group JID, never the user's private ref) and registered by `groups.py`, not by the phone mint. WhatsApp group token `whatsapp-group-<sha256[:24]>` of the JID. An email thread room (`transport/email/threads.py`) is minted when the thread has two or more humans besides the bot, is the host's, and passed the untrusted-sender gate; token `email-thread-<sha256[:24]>` of the root Message-ID. **Stranger first contact** (stage 3): a mail routed by plus-address counts as the host's with one human on it (`resolve_thread(plus_address=True)`), so an admitted stranger's mail at `bot+<user>@` is a thread room turn at the host's reach (the `office` case). A held mail mints nothing; `confirmations.approve` calls `threads.admit_approved_mail`, which rebuilds the mail from its `processed_emails` row, mints or syncs the room (private email room for the user's own mail), stores the user row with the task's id, repoints the task (`conversation_token`, `output_target='email'`, `host_absent`, `is_group_chat`, `audience`) and sets `processed_emails.thread_id` so `reply_all` finds it; `_restore_transcript_mirror` runs only when nothing was admitted. `_mint` refuses a root starting `email-`, the shape of a private ref, since the sender chooses the Message-ID. **A thread the bot starts is minted at the send** (email-on-rooms stage 1): every `sent_emails` writer (`outbound._record_sent_email`, `skills/email._record_sent_email_direct`, the deferred replay in `scheduler_deferred`, `drafts.release`) calls `threads.register_sent_thread` after its row, which mints through the same `_mint` as `resolve_thread` when a recipient is not the user's own address, writes the sent mail as the room's first row (`threads.record_sent_mail`, an outgoing-mail card, no `task_id`, since the sending task ran in another room), or syncs the recipients into an existing room only when the user hosts it. The existing room is found through the binding alone (`_bound_room`), never `find_thread_room`'s stored-mail arm, whose `sent_emails` row for this very send names the sending task's room. Because the ids can come from a model-written deferred file, it also mints nothing for a thread any of whose ids is stored for another user, nor for a user not in the config. It runs in a savepoint and never raises. `email send` and `email reply` record Cc (and `email reply` its threading headers) in the deferred entry; `sent_emails.to_addr` is To and Cc joined. A reply on a thread sent before that has no room: the `sent_emails` row (`ownership.match_thread`) resolves the user when nothing else does (routing `thread_room`), and the reply mints with one person on it (`resolve_thread(ours=True)`, the plus-address threshold) in `poll_emails` before the prompt is built, with the `sent_emails` row (no body) as the first row. The gate runs before the prompt for that reason. There is no emissary wrapper and no `thread_match` route (stage 4). Routing rung `thread_room` sends its mail to the host, the only member; held mail is not admitted. **An email thread room takes no members** (ISSUE-606): `_chat_add_member` refuses with 409 for an `email` binding, the members listing carries `email_thread` so the pane shows a caption, and `db._migrate_email_thread_members` (`email_thread_members_v1`) dropped every earlier non-host membership and re-marked those users' email participant rows `guest`. Another istota user on the thread is a correspondent. **No guest mode on email** (email on rooms, section 2a): every admitted turn on a thread room runs as the host at full reach with ambient memory loaded, exactly as an email turn always has; `record_inbound` keeps the correspondent as a guest participant and the row's author but sets no `guest_participant_id` and adds no guest fence (`rooms.scopes.is_email_thread_room`). The email wrapper, the admit gate and the outbound gate bound it. The card is `executor._email_room_card`. **The thread records the mail** (hidden email threads, stage 2): for a task whose room is a thread room (`threads.thread_room_for_task`), the scheduler stores the mailed body as the assistant row (`outbound.composed_email_body`, which peeks the deferred `email output` file, then the envelope), and no row when nothing was composed; the model's report never reaches the thread. A private-email-room task still stores its result text. **One note per mail** (#636, stage 4): after `post_result_to_email`, `scheduler._write_email_note` reads the outcome off the thread row's `outgoing_mail.state` (`sent` / `held` / `failed`; `failed` too when the post failed with no state; else `none`, logged at info when the row is missing) and asks `private_replies.email_note_due`: always when `host_absent`, else only for `held`, `parked`, `failed`, or `none` with a remark (a `NO_ACTION:` reason does not count as one when the host was on the mail). Its own transaction, then `send_private`; a failure is a warning and never fails the task. `deliver_email_note` keeps kind `pass_on` and reference `<task>:pass-on`, so a retry returns the first row and `context.build_talk_context` still drops `private-pass_on:` posts. `email_note_body` is code-built through the remark: the user row's `author_label` (`You` for the host's own mail) and the room name, `, without you on the message` when `host_absent`, the new text quoted (`parse_email_prompt` then `threads.new_text`, capped at `QUOTE_CHARS`, which a guest proposal shares), one outcome line (`NOTE_OUTCOMES`), then the remark (`email_note_remark`: the result without an `ACTION:` / `NO_ACTION:` marker or the envelope, dropped when `db.mailed_body_differs` says it repeats the mailed body). A parked question on a thread is the note itself (`outcome='parked'`, `Question for you.`) and writes no `pass_on` row; `NO_ACTION:` on any thread turn never parks. A host-absent turn that wrote `email output` and then answered `NO_ACTION:` mails the composed body, since the thread row already records it. With no private room the note is a `private_note` bell row. The loop cap does not apply to a correspondent's turn (stage 3, above). **The host's own question is not held** (ISSUE-607): the poller marks `processed_emails.host_asked` when the turn is addressed, its author is the host, the sender claims the host's address and `_authentication_verdict` is a DMARC `pass`; `threads.host_asked` releases `deliver_email_result`'s thread reply with `approved=True` only for the task that row names, no guest turn, and a plan whose recipients equal that mail's reply-all. Every other reply on the thread keeps the gate. The answer is a reply-all through `_hold_if_unapproved`, which checks every recipient. **Mail awaiting approval is a draft** (decision B, stage 4): `private_replies._post_destination` refuses an email-bound room with `email_thread`, so `room post`, a guest proposal and a queued post on a thread all close there; `deliver_thread_post` and the D20 recipient pinning are gone. **Every mail into the thread is recorded on the room row that carries it** (ISSUE-612): `_send_thread_reply` stamps `messages.outgoing_mail` (to, cc, subject, state, `draft_id` while held, `body` only where `db.mailed_body_differs`) on the row the scheduler already stored, which on a thread room is the mailed body itself, and never creates a row; `drafts.release` / `discard` settle a held one through `db.settle_draft_mail`. An approved `room post` is a `role='assistant'` row on every surface, tied to the task only when that task ran in the same room (a guest proposal, `private_replies._post_answers_task`), so a member's private task trace never renders in the shared room.

**A received mail's card is stored at intake** (hidden email threads, stage 3). `transport/email/mail_card.py` holds the column's schema: `received_mail_meta` is the one builder and `stored_received_mail` the one reader (the web card and `threads._admit_approved_mail` both go through it, re-asserting the same caps and `sender_check` set; ISSUE-642). The builder stores from and its name, To and Cc as written (never Bcc), date, subject, Message-ID, In-Reply-To, the attachment manifest with the inbox path where a copy was written, `sender_check` and `trusted`. `sender_check` is `verified` only for an aligned DMARC pass under `[email] authserv_id` (the pass `_own_address_claim_counts` accepts, from `_authentication_verdict`, now run for every sender rather than only self-claims), `failed` for a failure and `none` otherwise; `trusted` is the trust list alone (`include_own_addresses=False`). Lists cap at 50 entries and strings at 320 characters. It rides `IncomingMessage.mail_meta` into `record_inbound` and `record_phone_turn`, which write `messages.received_mail` through `db.set_received_mail` in the turn's transaction, and the poller's main intake call stores the same JSON in `processed_emails.mail_meta` (the discarded, quiet, throttled and read-error ledger rows carry none), from which `threads._admit_approved_mail` copies it onto a held mail's row at approval. The card reads stored fields only, never raw headers at read time. Both columns are migrations (the uidvalidity rebuild's DDL copy carries `mail_meta`), so the upgrade tier is owed before release.

**Delivery refuses a shared room for personal content** (SG 10). `routing.refuse_shared_rooms` drops a talk or web leg whose canonical room is shared, for every purpose, exempting only the room the task ran in. Order in `resolve_delivery_plan`: `rooms.private_replies.pin_plan`, refusal, reply-to-origin fallback. Notifications apply it per purpose including log; `send_notification(task_room=)` exempts the conversational notice. `db._usable_as_delivery_default` and `db.configured_default_room` skip shared rooms. `record_inbound` refuses a mirror-only turn into a shared or vetoed room. Briefings get no exemption.

**Private replies** (ISSUE-608, which retired side rooms). What a shared room has for one member (a confirmation, a `room whisper`, a held guest proposal, a `room answer-privately` question) goes to that member's own existing private room, never a system-created one: `rooms.private_replies.private_room_for` tries the shared room's own surface first (the private WhatsApp room for a group, a private Talk room for a Talk room, the default web room for a web-only room; an email thread room has none, and the private email room is never a destination), then web, Talk, WhatsApp, each re-checked by `db.is_private_room_of`, the relay default room's predicate. SMS is never a destination. Two phases: `deliver_private` writes one `role='system'` row tagged `messages.about_room_token`, keyed `private-<kind>:<reference>`, inside the caller's transaction (the reference index is global, so the kind and the task or request id are both in it); `send_private` posts after commit, never raises and never sends under a writer lock: Talk after `verify_private_audience`, stamping `external_ids` so a Talk reply resolves; WhatsApp under `private-reply:<messages.id>` (`.claude/rules/sms.md`). Nothing is mailed: the heads-up mail for an email-thread parent was removed (email on rooms stage 5), so a web-only private room reports not delivered and the park's bell row is pushed, room-free (`.claude/rules/notifications.md`). With no private room nothing is written into any room: a park's `confirmation` bell row is delivered rather than withheld, a whisper becomes a `task_alert` (`private_note`), and the shared room gets the fixed `SHARED_ROOM_NOTICE`, naming nobody (a WhatsApp group's under its own `private-notice:` key). **`tasks.private_park` is the gate's predicate, not the message reference**: a park routed to the bell writes no `messages` row, so a reference-keyed predicate could not see it and the park held the shared room's dispatch gate for every member and was cancelled by the asker's next message there. The scheduler sets it on every privately routed park; `set_task_confirmation` clears it. **Linking is strict**: `record_inbound` sets `tasks.about_room_token` only when the new turn's resolved parent is in the same room and tagged (web reply-to; Talk parent through the stamped external id; a WhatsApp quote through `private_replies.quoted_private_reply`, which reads the `private-reply:` key, or `task-result:` for a linked turn's answer, which the scheduler tags with the same link), and `queue_private_answer` sets it on the question it asks again. **One second route, web only and email threads only** (hidden email threads, section 0c): "Discuss in private chat" on a mail card with no note has no tagged row to reply to, so the web send body carries `about_room: <token>`, and the send route links the turn only when `private_replies.about_room_link` passes three checks inside the write transaction: the token is an email thread room (`rooms.scopes.is_email_thread_room`) and not archived (which `linked_room` would drop at run time), the sender is a current member of it (`is_current_member`, what `linked_room` asks at run time), and the room sent into is the sender's private room for it (`private_room_for` resolves to it). Any failure is 400 `cannot link this message to that room`, one body for every cause, with no task and no cancel of a parked question. On success the route passes `about_room_token` to `record_inbound`, which skips `linked_about`. A reply-to row outranks it: with one, `about_room` is ignored and the row decides. Other shared rooms still link by reply alone; widening this is its own decision. Nothing carries forward. A linked task that is still a current member gets the fenced parent transcript, and `pin_plan` drops every leg into the linked room. `room post` runs from a private room (refused `not_a_private_room` in a shared one) into the linked room or `--room` (`rooms.lookup.resolve_room`; list numbers only for `!room notes`), and refuses a preview a phone origin would not show whole (`invalid_preview`). `answer-privately` records the member's original text through `record_inbound`, or `record_phone_turn` for a WhatsApp room, under the private room's own model, effort and brain defaults (ISSUE-420), not the shared room's. A bare yes in a private room resolves the one parked task whose private question is there (`private_replies.parked_here`); on WhatsApp only `!confirm <id>` reaches it, since the webhook's own match runs Path B alone. **My notes** are `{bot_dir}/config/rooms/<canonical token>.md`, inside `memory_dir_parts` with no new entry; `my_notes_room` loads them on the member's own speaking turn on Talk, web, WhatsApp or email (an email turn only when the stored row is theirs, since an outside correspondent's mail runs as the host with no guest id) and on a held-guest turn for the host, never under `direct`. `!room notes` is refused in every shared room, whatever the surface. Room deletion removes every member's notes. `db._migrate_private_replies` deleted the side rooms and dropped `rooms.side_of` / `side_for_user`; it is a migration, so the upgrade tier (`scripts/test-upgrade.sh`) is owed before release. User docs: `docs/features/shared-rooms.md` ("Private replies", "My notes").

**The veto** (D8, D12), `rooms/veto.py`: any participant's `!<bot name> off` stops recording until a member's `!<bot name> on` and every vetoer agreed or left; routed ahead of the guest-command filter. Removing the bot from a WhatsApp group is a veto with no vetoer row. The web app queues replies in `room_notices`; the scheduler's `room-notices` gate posts them and the one-time announcement. The announcement is an opening (default in the default persona's voice, or the operator's `config/room-announcement.md`, never a file in a user's tree, since a user's files are writable from their sandbox and everyone in the room reads it) plus two fixed sentences, the guest one read from `guest_reply` (a held room does put a guest's answer to the host) and the closing with the off switch and the way back; the whole is collapsed to one line, so an opening can neither drop them nor forge a second closing. An email thread room is never announced (ISSUE-605: `needs_announcement` answers no for an `email` binding). Its disclosure, when `[email] thread_disclosure_footer` is on, is one plain line on every mail into the thread, added in `outbound._send_thread_reply` and in the guest proposal's preview by `veto.with_email_footer`, which recognises an already-footed body by the fixed second sentence so a held proposal is not footed twice.

## Phone rooms (SMS and private WhatsApp)

**The private email room** (email on rooms, stage 3) is the same mechanism for mail between the user and the bot alone (`threads.is_private_mail`: every human on From/To/Cc, bot addresses dropped, is the user's own address). The poller records it through `record_phone_turn(surface="email", surface_ref=email_conversation_token(user))` (`transport/email/private_room.py`, re-exported from `transport.email`), which passes `room_container` for email, the email queue and the sender address; the task's plan is `email` and `deliver_email_result` answers with the sender-only reply, since `threads.thread_room_for_task` excludes it. Every thread predicate (`threads.thread_binding`, `find_thread_room`, `_token_by_stored_mail`, `_bound_room`, `rooms.scopes.is_email_thread_room`) treats an email binding whose ref is its creator's private token as not a thread, so nothing threads into it by Message-ID. `routing.private_surface_room` (the new name of `private_phone_room`, which stays as an alias) and `private_phone_ref` gained an `email` arm, `private_phone_rooms` includes it (the prompt header says `target = "email"`), and `phone_room` / `phone_transcript_surface` answer `email` for it only, never for a thread room. `db.room_has_phone_binding` counts it, so it is never a default or relay room. Mail the bot sends only to the user's own addresses lands there as an outgoing-mail row once the room exists (`threads._record_in_private_room`, skipped when the sending task's answer is already a row there). There is no backfill and no `_room_backfill` pass for it.

A user's SMS thread and private WhatsApp chat each own one room, minted on the first accepted inbound turn (room-surface-model Phase 6). Both surfaces are singletons per user, so there is no "which room" question and no promotion verb. `rooms.surfaces.SURFACES` records both as `room_role="member"`, `room_view=None`, `user_turn_mirror=None`, and each transport declares the same. The operator-facing version is in `docs/features/sms.md` and `docs/features/whatsapp.md`; the web half is in `.claude/rules/web-chat.md` ("Phone rooms are read-only").

**`room_view=None` keeps the phone out of fan-out, and it needed a guard to mean that.** `_expand_room_destinations` used to skip only a canonical view, and only when an origin leg existed, then append every other binding. It now skips any binding whose static `room_view` is `None` first, so an answer delivered into a phone room from another origin never becomes a text; a disabled Talk transport is not caught by this, since Talk's static answer is `external`. `plan_user_turn_mirrors` drops the bindings separately on `user_turn_mirror`. A text goes out only when the task originated on the phone or something names `sms` / `whatsapp` explicitly, which is the metered-surface rule.

**The mint rides the webhook's own transaction.** Both webhooks call `ingest.record_phone_turn` under the `BEGIN IMMEDIATE` they already hold, for an accepted task, a `!command`, a confirmation answer, a WhatsApp button and a relay reply. It runs `record_inbound` with `surface_ref` set to the per-user hash token (`sms-<hash>`, `whatsapp-<hash>`), so `db.register_bound_room` mints an `rm_` token, binds the surface, adds the member and stores the user row, and then writes a `room_token_migration` row mapping the hash to the room with `ON CONFLICT DO NOTHING`. That last clause is what keeps a deleted room's alias a tombstone: a room minted again on the same binding gets no history and no memory of its predecessor. `record_only=True` stores the turn and creates no task, which is how a command and a consumed confirmation answer are recorded. Nothing mints, and nothing is recorded, for an unknown sender, STOP / START / HELP, an empty text, a WhatsApp text from an opted-out user, an unsupported or failed media message, a vetoed turn, a delivery status, a redelivered id (the dedup claim stops it first) or a push. Racing first texts converge because each webhook holds `BEGIN IMMEDIATE` before `resolve_room_token`, so the second resolves the room the first minted. The UNIQUE index `idx_room_bindings_unique_ref` over `(surface, surface_ref)` is the singleton's backstop rather than the mechanism: a collision that ever reached it is refused by `register_bound_room`, which removes the room it just minted and returns None, and `record_inbound` drops the turn rather than storing it in a room no surface reaches (ISSUE-581). `add_room_binding` itself never raises, because the Talk poller binds inside a whole-batch transaction; it returns False and logs a WARNING when another room holds the ref, and returns False quietly when the room is bound to a different ref on that surface, the state every room the token migration rewrote is in. `db._migrate_room_binding_uniqueness` creates that index in `init_db` ahead of every other migration and raises on existing duplicate bindings rather than picking one of them. A failed batch rolls back to the webhook's own 503, mint included. WhatsApp groups keep their own path (`groups.py`, bound by the group JID).

**Four predicates name a phone room, and they answer different questions.** `routing.private_phone_room(conn, surface, user_id, channel=None)` finds the user's own room by the derived ref, existence only, and refuses a room another human reads or a WhatsApp channel that is not the private chat; it is the destination test for every writer below. `routing.is_private_phone_room` compares a token against it and is the one test for "the webhook already stored this turn here", read by `!steer` and the two webhooks' `_ack_in_private_room` helpers; `_record_confirm_exchange` gates on the surface instead. `routing.phone_room(conn, room_token)` is the web send refusal's test: any sms or whatsapp binding, with `group` set when the ref is not the creator's private one (ISSUE-585). `routing.phone_transcript_surface(conn, room_token)` is its private-thread half, read by the confirm, decline and member-add refusals: the room's binding ref must equal its creator's own private ref (the rule `whatsapp.outbound.is_group_task` applies), the token is resolved through the alias first so a task still carrying the pre-mint hash answers the same, and a room another member was added to still counts, since adding a reader does not make a phone thread writable from web.

**What lands in the room.**

- Every accepted inbound turn, as a `role='user'` row with `origin_surface` `sms` or `whatsapp`. `db.TRANSCRIPT_SURFACES` gained both, and the spared list in `_migrate_nonconversational_transcript_cleanup`'s DELETE gained them in the same change, so a re-run on an unmarked database cannot sweep live phone turns. Widening the filter also made WhatsApp group turns render in web, as Talk group turns and email thread turns already did.
- A phone-origin task's answer, written by the scheduler's conversational store before the send, as for Talk and web, because the task carries the room token.
- An explicit push (`output_target` `sms` or `whatsapp`, a cron job, a reminder) once the room exists, stored in the completion transaction ahead of the network call so a blocked send (window closed, budget, opt-out) still leaves its row. The scheduler asks `is_group_task` first and skips the WhatsApp arm for a group turn, so a group whose binding is gone never has its answer stored in a member's private room.
- A notification routed to a phone leg (heartbeat, task alerts): `notifications.delivery.mirror_phone_to_room`, the phone counterpart of `mirror_talk_to_room`, writes a `role='system'` row after the send on its own short-lock connection, whatever the send returned, keyed `<surface>-notification:<user>:<reference id>` so a raise the ledger refuses as a duplicate writes nothing twice. A push never mints.
- A `!command`'s reply: `notifications.delivery.mirror_phone_command_reply` writes it after the send as a `role='system'` row keyed `<surface>-command-reply:<user>:<ledger key>`, only when the command was recorded in the user's own phone room. A WhatsApp group member's command is answered in their private chat, and its reply lands in neither room. Both webhooks write it through `asyncio.to_thread`, off the runtime loop, and SMS does so in a `finally` so a send that raises still leaves the row. A phone `!confirm` leaves its ack to this writer. The bare-yes and button acks are not commands and are written by `confirmations.record_ack` inside the webhook transaction, beside the user row. `cmd_steer` writes no row of its own in a phone room, since the webhook already stored the typed `!steer`.
- A relay answer: `relay.relays.create_recipient_task` records the answer text (or the rejection context) through `record_sms_turn` / `record_whatsapp_turn` and creates the recipient's task, so it lands as an ordinary turn. The literal `!relay reply <id> …` line is not stored, nor is a WhatsApp relay candidate still waiting to settle.
- A transcribed WhatsApp voice note's words, **written into its user row after the fact** (ISSUE-613), the one place a stored user row is edited. In the completing transaction that writes the transcript into `tasks.prompt`, `db.replace_voice_notes_in_turn` finds the task's earliest `role='user'` row, replaces the body with `Transcribed voice message: <text>` when it is still the `describe_attachment_only_message` stand-in (typed text is kept and the line appended), and drops that note from `attachments` and `attachment_paths` by its position in the task's attachment list. Which notes is `scheduler.transcribed_voice_notes`, the same answer the inbox delete acts on, so a chip leaves the room exactly when its file is about to go; a note whose transcription failed, and every note on a failed or parked task, keeps its placeholder and chip. Both columns are written as lists, `[]` included, because `webui.app._row_attachment_names` falls back to the task row's paths for a NULL column and would bring the chip back; that reader now treats a stored empty list as an answer. Nothing keys on the stand-in body: the backfill is idempotent on `(room_token, origin_surface, role, task_id)`, and read state and `external_ids` go by id. Residual: the room-event stream cursors on `messages.id`, so a tab already showing the stand-in sees the transcript only on its next history load. The web view sets the words after the label in italics on a WhatsApp row, keyed on the label text (`lib.audio_sniff.VOICE_TRANSCRIPT_LABEL`, held equal to `Message.svelte`'s copy by a test) rather than on a stored flag, so typed WhatsApp text that starts a line with the label is italicized too; accepted, since it is cosmetic and adding a flag means a column. A second completion of the same task leaves an already-rewritten body alone.
- Not stored: the parked question. The web view renders a parked task from `tasks.confirmation_prompt` only inside `db.TASK_ROOM_SCOPE_SQL` (web, Talk and email tasks), so a phone room's history does not show it (a tab already open on the room may get the task stream's live card); its push is the text, and the bell row when that fails (#635).

**The prompt header names the phone as the scheduling target.** For a private phone room `executor.room_identity_line` says the room is readable but not writable in web chat and gives `target = "sms"` (or `"whatsapp"`) with `room = "<token>"`, never `web:<token>`: a reminder asked for by text has to arrive by text. The bare destination resolves the user's binding and the scheduler records the push in the room. `tests/golden/prompts/room_sms.txt` and `room_whatsapp.txt` pin both.

**History from before the mint is backfilled lazily, never in the webhook.** The scheduler's `phone-room-backfill` gate (every 60 seconds, background) finds phone-bound rooms with no marker and replays each one through `db.backfill_room_messages_from_tasks(alias_owner=)`, widened for this rather than copied: tasks on the room's valid aliases (`room_ref_tokens` without surface refs), the owner's own turns only, never a withheld or guest turn, and only `TRANSCRIPT_SURFACES` plus `scheduled` as source types, since any other source type would write its synthetic prompt as a user row. One transaction per room; a failure is logged and retried on the next pass, and the room works meanwhile with a transcript that starts later. The marker is a per-user reserved KV entry in `_room_backfill`, keyed by room token, written only once no task on an alias is pending, locked, running or parked, which is what puts an answer to a pre-mint task that finished after the mint into the transcript. That check runs before the read, because plain SELECTs share no snapshot and a task completing between the two would otherwise be missed for good. A reader whose web cursor was caught up before the pass is moved past the backfilled rows.

**Recall follows the alias.** `executor._recall_memories` adds `channel:<alias>` for each valid alias beside `channel:<token>`, through the same `room_ref_tokens` call, so memory indexed under the hash before the mint is recalled in the room while the reconcile sweep and reindex catch up. A failed alias lookup falls back to the current namespace alone. Old phone sleep-state rows are left as they are: canonical enumeration reads valid aliases and never revisits them.

**Room settings apply to phone turns.** `record_inbound`'s room branch reads `rooms.model`, `rooms.effort` and `rooms.brain` for any member surface, so a `!room model` or `!brain` pin on a phone room (set from the phone, since a command runs against the minted room token) applies to texted turns too.

**The target, membership and delete.** `routing.private_phone_rooms` maps a reader's own phone rooms to their surface, and the prompt header, `istota-skill rooms list` and the `nextcloud talk create` refusal all pass it to `room_target_descriptor`, so a private phone room is scheduled into by `sms` / `whatsapp` on all three, from one decision. `_chat_add_member` refuses a member add to a private phone room with 409 and `read_only: true` (`phone_transcript_surface`), because a shared phone room is answered, recorded into and backfilled by nothing; the settings pane shows a caption in place of the add control, a WhatsApp group room still takes members, and removing a member added before the refusal stays possible. Deleting a phone room from web deletes every task on its tokens, the pre-room hash alias included, so the SMS or WhatsApp task history from before the mint goes with it. Both busy guards (`count_active_web_tasks`, `count_active_room_tasks`) count the room's permanent aliases as well as its token, so an unfinished task on the alias refuses the delete with 409. The alias row stays in `room_token_migration` after the delete, a tombstone, so the room the next text mints reaches none of it.

**Residuals.** A phone room shared before the member-add refusal still has the shared-room behaviour above until the added member is removed. For a WhatsApp group room, an email thread room or such a shared phone room the header says a scheduled job cannot post there, while `rooms list` and the `talk create` refusal still hand back `web:<token>`; that disagreement predates phone rooms. The backfill re-checks every WhatsApp group room and every shared phone room on each pass, since `private_phone_room` refuses them and no marker is written. `!retry` of a pre-mint task after the room is marked creates a task on the hash token, and nothing backfills its turn. `!search` and the `memory_search` skill read only `channel:<current token>`. A web reader with unread rows keeps every backfilled row unread, since an id cursor cannot say "old rows read, newer not". After a delete the next text mints a new, empty room.

## Inbound

**Talk and email create tasks inside `poll`** so `create_task` shares the poll's `db.get_db` transaction with the cursor and side effects; a failure re-polls instead of losing messages (a split collect/ingest was reverted for that). `poll` returns `[]`. `ingest_message` maps onto `db.create_task` (duplicate Talk ids return the existing task). `record_inbound` stamps the surface id into `external_ids` (echo ledger, read-sync cap).

### Talk poll

`transport.talk.inbound.poll_talk_conversations` owns listing, the `lastMessage` gate and full sweep, long-poll, filtering, the @mention test, `!model`, `!command`, confirmation replies, the active-task gate, attachments, and ingest.

- **The room pass awaits with no connection open** (ISSUE-406): `_plan_room_pass` reads, `_fetch_room_pass` fetches, `_apply_room_pass` writes and re-reads every condition (a cursor is initialised only if still absent; a vanished room is skipped). The results block still awaits Talk POSTs under its write lock; fixing that means hoisting awaits, not splitting the transaction.
- **`db.set_talk_poll_state` uses `MAX`**, never rewinding, since the side effects below the cursor are not idempotent.
- **Every `db.get_db` reachable from the runtime loop is behind one `asyncio.Lock` per loop** (`transport/talk/_db_lock.py`), bounded `busy_timeout_ms`: a synchronous writer inside an await of a lock-holding coroutine deadlocks the loop thread (a `threading.Lock` would too). Nothing else opens a connection on the loop thread; `WebTransport.deliver` uses `run_in_executor`.
- **`talk_poll_txn`** (`_timed_poll_txn`, `_await_in_txn`) logs slow awaits and long holds.
- Inbound caches are module-global and unlocked; a registry-driven inbound driver would race them first.

### Email poll

`transport.email.inbound.poll_emails` owns IMAP, routing precedence (plus-address → sender → thread), attachments, prompt assembly and the gate, and ingests in the same transaction as the gate and `mark_email_processed`.

**Email confirmation gate.** One decision per email, before `ingest_message`, because it also sets `IncomingMessage.suppress_transcript_mirror` (the mirror commits in the task's transaction and `db.cancel_task` touches only `tasks`).

- `plus_address` / `sender_match`: gated unless `is_trusted_email_sender(..., include_own_addresses=_own_address_claim_counts(config, auth_result))`. One rule for both, since `From: <user>` + `Cc: bot+<user>@` resolves as `plus_address` (ISSUE-227).
- `thread_room` (ISSUE-234): gated on a self-claim, or unless the sender is one of the room's present people; on a thread sent before rooms were minted at send (no room yet), unless `mail.ownership.thread_reply_from_correspondent` finds the sender among the exact To addresses on the matched `sent_emails` row (a Message-ID is a bearer token; never domain, never the `References` chain). Then the same trust call.
- Residuals: one approval plus a bot reply makes the sender a correspondent; `sent_emails` has no age bound; nothing gates the thread route on the DMARC verdict.
- A gated thread reply sits under a real room token (`TestThreadMatchConfirmationGate`); it parks the foreground queue only under `email_task_queue = "foreground"`.

**`confirm_sender_match`** (`off` | `verify` | `gate`; ISSUE-227, ISSUE-249 Gap 3) switches only the own-address trust branch. `_own_address_claim_counts`: `off` True, `gate` False, `verify` True only for `verdict == "pass"`, failing closed on `None`. `verify` needs `authserv_id` (refused at load, re-asserted locally). Default `off` declares the MTA enforces DMARC upstream; an unanswered hold auto-cancels. A self-claim prompt offers plain yes/no (`yes trust` would exempt the spoofer's identical address). A `verify` hold is always logged. With `authserv_id` blank, `_note_observed_authserv_id` logs the id only on a `pass`; canary alerts carry `_AUTHSERV_ID_ADVICE` naming no id, since a spoofer can trigger them. Alerts state policy, never the message's fate.

**Inbound volume budget** (ISSUE-250). Before `ingest_message`: `email_sender_rate_limit_messages` per `(user, sender)` then `email_rate_limit_messages` per user. Over budget is filed (`routing_method="throttled"`, no task), never dropped, which is why it is not in `ingest.py`. Past `_MAX_PROMPTS_PER_SENDER_WINDOW` (3) prompts collapse into the throttle notice; tasks stay addressable by `!confirm <id>`. The budget is in the DB, so a restart grants nothing.

**The DMARC canary** (ISSUE-228). `_check_dmarc_canary` warns and alerts when a self-claim (`claims_to_be_user and routing_method in ("plus_address", "sender_match")`) lacks `dmarc=pass`. It never blocks (`dmarc_canary` is safe on by default), but `poll_emails` computes the `_AuthResult` and passes it in because `verify` decides on it. A detector of drift, not a control.

- **`[email] authserv_id` decides which headers are read** (ISSUE-249): blank reads the top header; set, `_our_headers` keeps every matching one (non-pass wins) and a missing stamp is loud (`unstamped`). `dmarc_canary_warn_on_missing` covers our stamp with no verdict (`unevaluated`). Rejected headers are counted, never quoted.
- **A pass is checked for alignment either way**: every `header.from` from `_dmarc_header_from` must pass `_domains_align` (exact or parent/child), else `misaligned`. Absent is quiet, unreadable loud. Limit: a property wholly inside a comment reads as absent. `dmarc=none` is a failure. Echoes truncate at `_ECHOED_VALUE_MAX`.
- **The parser exists to stop the canary going quiet**: `_dmarc_result` anchors `dmarc=` to a methodspec, splits on `;` outside comments and quotes, lets any non-pass beat a pass, and reports an incomplete read (unbalanced delimiter, or `_DMARC_RAW` counting more tokens than attributed) as `malformed`, never `pass` or `None`; unknown tokens bucket to `other`.
- Dedup is in-process `(user_id, sender.lower(), verdict)`, 24h, opened only on a delivered alert; the WARNING is never deduped. `_deliver_dmarc_alerts` runs after the batch outside every transaction (a web route opens a second connection).

**Answering a gate is surface-agnostic** (ISSUE-241, ISSUE-243). `notifications.delivery.send_confirmation_prompt` resolves `alert` and returns `(delivered, talk_message_id)` (feeds `talk_response_id`, Path A), sent after the transaction (`_deliver_confirmation_prompts`). The prompt names its task id (`!confirm <id> [no|trust]`, `!yes` / `!no`). `istota.confirmations` holds the verbs, `parse_answer`, `resolve` and `apply_answer`; the web POST intercepts a bare answer before `_chat_create_web_task` (which cancels the room's pending confirmations). Held mail shows only in the notification inbox, never history (`.claude/rules/web-chat.md`). `confirmations.approve` writes the withheld user row into an existing room; a bare "yes" resolves only with one open question; `_dispatch`'s talk leg mirrors the prompt as a `role='system'` row (ISSUE-242); expiry notices route by `alert`. A gated email is still marked processed at ingest, or each poll re-ingests it.

**No origin reply routing** (email on rooms stage 4). `routing.origin_descriptor(task, conn)` still stamps `sent_emails.origin_target` (`room:<canonical_token>` for a live room, else `web:`/`talk:`; an email task yields nothing beyond its room), read by drafts and the room relocation, but nothing routes a reply on it: a reply is a turn in the thread's room. `email_reply_routing`, `upgrade_legacy_origin` and `routed_notification_room` are gone, and `user_profiles.email_reply_routing` is dropped at init. An email task's `conversation_token` is its room (a thread room or the private email room) or NULL for a held mail; the subject-and-sender thread hash is gone, and `processed_emails.thread_id` is the room token or NULL.

**`room:<token>` from a scheduled job** (ISSUE-511). `_expand_room_destinations` skips bindings an origin leg covered only when `origin_surface_for_source_type` names a surface; asking the delivery map made a `scheduled` job deliver nowhere. `room` is in `cron_loader._KNOWN_TARGET_SURFACES`. `routing.room_target_descriptor` (`talk:<t>`, `web:<t>`, or `web:<t>,talk:<ref>` for promoted) is the recommended spelling, shared by `rooms list`, the `nextcloud talk create` refusal and the prompt's `Room:` line; `room:` re-expands by live bindings instead.

**Mail the user sends themselves is their private email room** (ISSUE-254, ISSUE-275, email on rooms stage 3). Every admitted mail is a turn in its own room, so no exchange is copied into a room it is not part of, and the mirror flags are gone (stage 4): `IncomingMessage.mirror_to_room`, `record_inbound(mirror_to_room=)`, the poller's `self_addressed_mail`.

**`tasks.withheld_from_room`** (ISSUE-255) is no longer written or read by code; the column stays (no `tasks` rewrite). The SQL readers (the history fallback, `get_previous_tasks`, skill stickiness, the channel sleep cycle) keep `COALESCE(withheld_from_room, 0) = 0`, which keeps rows written before stage 4 out of their origin rooms.

**Failures with no channel.** A permanent or SMTP failure for a task in the user's private email room alerts via `purpose="alert"`, carrying the answer (`email_transcript_body`). Gate: `scheduler._in_private_email_room` (the task's room is a private email room, `routing.phone_transcript_surface == "email"`), never "plan is email-only", which would fire for a thread room's correspondents (`TestAPermanentFailureReachesTheUser`).

**Who wrote a row.** `messages.author_user_id` or the pre-sanitized `author_label`, one or neither (owner); readers test the label first. Resolved at write time by `transport.ingest.resolve_author`, or `db.author_for_email_task` without a `Config` (pass `email_addresses`; the DB fallback misses TOML-only addresses). Every user-row writer sets it.

**Per-room defaults.** `record_inbound` fills `model`/`effort` (inline `!model` wins as a unit) and `brain` from the room inside the `room_surface` guard, so email continuations, cron, heartbeat, briefing and skill tasks do not take them. New per-room defaults go in that block; hoisting `existing` out of the guard reverses ISSUE-136. Set via `!room` or the room-settings PATCH.

## Talk inbound over the signaling event stream (`[talk.signaling]`)

Off by default. Enabled, `_talk_poll_loop` does not run (one driver); messages arrive over the HPB WebSocket. `signaling.py` is the protocol leaf; `supervisor.py` decides rooms, effects and timing. No credential by design (the internal-client secret could join any room). Talk `internal` mode or no `websockets` refuses boot.

- **A watcher joins only tokens the current `list_conversations` returned**, since `ParticipantService::joinRoom` self-enrols in listable rooms; `_may_watch` is checked at start and at the POST.
- **Room context is required, no default**: `conv_types.get(token, 1)` means DM and skips the @mention gate (`tests/test_talk_trigger_path.py`). Cursor init comes before a watcher, or history is ingested.
- **Safety net**: each reconciliation compares `lastMessage.id` with the cursor; `doctor` reads `rooms_behind`.
- **Trigger mode** (default) fetches via `_process_poll_results`. `payload_direct = true` ingests the relayed message; a payload-less event forces a fetch, `id > cursor` applies on that path only, payloads queue for the drain (its in-flight flag is the one serializer, which `catch_up` defers to), and a failed drain forces a fetch.
- **Coalescing**: one fetch in flight per room, a dirty bit re-runs once; in-flight clears in `finally`, the dirty bit survives failure without re-waking the drain. `doctor`: `stale_dirty`.
- **404 from `participants/active` is fatal to its watcher** (ISSUE-414): `joinRoom` and `getSettings` share brute-force action `talkRoomToken` per IP, so retries throttle every room up to 25s, past `TalkClient.DEFAULT_TIMEOUT`.
- **Never-connected is not reconnecting** (ISSUE-416): `RoomWatcher.ever_connected`, replaced after `_NEVER_CONNECTED_SECONDS`; `settings()` shares failures too.
- Tests: `tests/test_talk_signaling*.py`, `tests/test_talk_trigger_path.py`, `tests/full/test_signaling_e2e.py`. Payload-direct skips end to end, since `nextcloud:30-apache` (Talk 20.1.11) sends only `{'refresh': true}`.

## Post-as-user mirroring + echo prevention (user-scoped OAuth)

With `[web] token_storage = "encrypted"` and `ISTOTA_WEB_TOKEN_KEY`, `webui.app._mirror_web_turn_as_user` posts a web send into a Talk-bound room as the user (`referenceId = WEBMIRROR_REF_PREFIX + <message id>`) and stamps the Talk id on the user row, suppressing the scheduler's repost (`db.user_turn_has_external_id`). Echo guards: the referenceId fast-path in the poller (race-free) and `db.message_has_external_id(..., exclude_origin=surface)` in `record_inbound` (same-origin re-polls still reach dedup). Talk→web read pull per `[web.chat] talk_read_sync_interval`, capped at `db.room_max_talk_synced_message_id`. All of it degrades to the attributed repost.

## Outbound

- **`TalkTransport.deliver` / `.edit`** use `async_runtime.get_talk_client(config)` (`.claude/rules/scheduler.md` "Persistent asyncio runtime"). `deliver` splits at `max_message_length` and threads the first part when `threaded=True`. `notifications.delivery._send_talk` delegates here.
- **A failed Talk post is retried only behind an idempotency readback** (ISSUE-405), `None` meaning nothing posted (ISSUE-404). A timeout does not prove non-storage, so a re-post needs a connect-class failure or `_posted_message_id` not finding it, matched on `referenceId` and actor (`talk.bot_username` or `nextcloud.username`; any participant can set a `referenceId`). A split send gets no readback (one reference for all parts); anything unanswerable holds back. Retries: transport errors and 5xx, not 404/403/429. `_may_have_been_stored` gates the readback, not `_is_transient`.
- **`EmailTransport.deliver`** uses `transport.email.outbound.deliver_email_result`; `scheduler.post_result_to_email` calls it directly for its success bool.
- **`process_one_task`** gates the progress ack on `supports_progress_ack` and `source_type == "talk"`; the ack target is `_talk_target_for_delivery`, resolved once behind those guards (so it only redirects an ack that would have posted anyway) and carried on `TalkEventSubscriber.target_token`, never `conversation_token` (ISSUE-400).
- **`LogChannelSubscriber`** sends the log to `notifications.delivery.effective_log_destinations` (`routing["log"]` > `log_channel` > off): live edits where `supports_edit`, else one summary from `scheduler._finalize_log_channel`.

### Briefing email bodies

`transport/email/outbound._briefing_email_bodies` returns `(plain, html, content_type)` for all three send sites. With `briefing_email_html` on, a briefing goes `multipart/alternative` (`strip_markdown` plus `render_briefing_html`, or `_strip_html` for an `html` body); off, single-part plain. `skills/email._set_body` treats an empty `html_body` as none, so render failure degrades to plain.

## Outbound delivery routing (`routing.py`)

The single source of truth for where a result goes; `output_target` is a comma list of `surface[:channel]`.

- **`parse_output_target`** (pure): expands `both` / `all`, dedups, drops `none`.
- **`resolve_delivery_plan`**: explicit `output_target` > reply-to-origin (talk, email, repl) > source-type default > drop with WARNING. Never raises; an empty interactive plan falls back to reply-to-origin.
- **`talk_channel_for_task`**: Talk room for results and, since ISSUE-400, the ack, edits and streamed text. Rungs: **(0)** `tasks.talk_delivery_token` absolutely; **(1)** the room's `talk` binding (`_canonical_room_token(..., cross_surface=False)`, since a ref is unique only within its surface; `cross_surface` has no default); **(2)** `conversation_token` for non-email tasks; an email task gets None past its room's binding, since its token is a room or nothing. Rung 0 stays while anything writes the column (ISSUE-057).
- **`plan_has_surface`** replaced string checks; `process_one_task` precomputes `plan_talk` / `plan_email` / `plan_ntfy` / `plan_file`. A confirmation prompt needs Talk in the plan and not ntfy.

### Purpose-keyed routing table (`notifications/delivery.py`)

`PURPOSES = (reply, alert, log, briefing, notification)` in `user_profiles.routing`. `resolve_destinations`: `routing[purpose]` > legacy fields > `default_destination` > `[talk]`. `send_notification`: explicit `surface` wins, else `purpose`. Every daemon-raised notice uses `alert`, the only route the settings page can move. Nothing sends or routes on `notification` (ISSUE-476).

## Deliberate residuals (ISSUE-113, closed)

- **No `TalkClient` construction outside the singleton** in `async_runtime.py`; daemon paths use `get_talk_client` via `run_coro`.
- **One exemption, `nextcloud.talk.transient_client(config)`**, for the `nextcloud` skill CLI only (no persistent runtime). `web_app` bearer clients are the separate OAuth case.
- **The delivery shims stay**: `post_result_to_talk`, `post_result_to_email`, `edit_talk_message` carry the Talk `target_token` override (synthetic email tokens, promoted rooms), email's bool return, and `edit`'s exception → `False`; newer surfaces call `registry.get(surface).deliver(...)`.

## How to add a transport (e.g. Matrix)

1. Implement `Transport` and register it in `make_registry` behind its flag, no network on construction.
2. A new `source_type` extends `_surface_for_source_type`; the origin map derives from the surface table.
3. Set the three room fields and add the `rooms.surfaces.SURFACES` row (the surface tests fail otherwise); a `member` row changes seven sites.
4. Inbound: `poll()` then `ingest_message`, or self-create like email. Outbound: `registry.for_task(task).deliver(...)`.
5. Tests mock the wire layer.

Web chat (ISSUE-121): inbound is the `/chat` POST; `default_web_room_token` resolves bare `web` to `general`. Matrix: `Drafts/Matrix messaging surface spec.md`.

## Unified Talk / web room sync

`rooms`, `room_bindings`, `messages` (role, `task_id`, `origin_surface`, `external_ids`), `room_read_state`. `get_conversation_history` falls back to `tasks` until every completed turn is mirrored. `_store_room_turn` (ISSUE-176) stores an assistant turn when `scheduler._room_turn_belongs_here` holds: the plan delivers into that room (a landing Talk leg, or a canonical push, ISSUE-164) or the room already holds the question; else it would be an answer-only bubble. `TRANSCRIPT_SURFACE_FILTER` (user rows web/talk/email/sms/whatsapp) differs from `_CONVERSATIONAL_SOURCE_TYPES` (talk, web) because email history is not guaranteed complete (ISSUE-136). The `nonconversational_transcript_cleanup_v1` DELETE spares the surfaces `TRANSCRIPT_SURFACE_FILTER` keeps plus `scheduled`, and has to stay in step with it: it re-arms on failure and re-runs on restored snapshots.

**The transcript room** (ISSUE-247), `routing.transcript_room_for_task`, is what every room-row writer keys on. Ladder: the room holding the task's user row; `conversation_token` if registered; for email only, a room named by `output_target` (bare `talk` reads `talk_delivery_token` first, matching rung 0). The user's notification route is not a rung (it would put a correspondent's body in the alerts room). Existence, never creation. `scheduler._talk_result_mirror_body` remains only for a Talk room that is not the transcript room; Talk gets `_format_email_user_repost` (sender and subject, never the body). Kept deliberately: a first-contact email parks a confirmation-shaped answer in the room; `delivering_into_room` keeps "plan has a Talk leg" for the task's own token; external bodies reach the room's context behind the `<email_content>` guard and `context._speaker_label` (ISSUE-226).

**Mirror-only surfaces** (ISSUE-136). `record_inbound`'s `mirror_only` path records a non-member turn when the transcript room exists, with no other room side effect. The stored body is the prompt verbatim, guard included.

**Fan-out**: `output_target="room"` goes by live bindings; web→Talk pushes, Talk→web does not. A confirmation mirrors only when the origin is not a room view (`rooms.surfaces.is_room_view` negated). On web→Talk the question arrives as the user's own post (OAuth) or the attributed repost (`_format_mirror_user_repost`, never stored).

**Membership** drives the web room list (`db.list_member_rooms`, per-user `web_chat_rooms` handles, ISSUE-134). The Talk poll registers any conversation the bot is in (canonical token via binding first) and seeds members by the `actor_id in config.users` + `actorType == "users"` authority test (`room_members_v1` backfill). Hide writes a `room_dismissals` tombstone cleared only by the user's own next turn (`undismiss_room`). `rooms.archived` belongs to `db.archive_orphaned_talk_rooms` (guarded against an empty fetch). Promote (`POST /chat/rooms/{id}/promote`) creates a Talk conversation with two-way rename.

## User-scoped Nextcloud OAuth (post-as-user + read sync)

The key reaches the web unit only (Ansible `web-secrets.env`, Docker `/data/.web_token_key`); `webui/tokens.py` has its own salt and `web_user_tokens`. `get_access_token` refreshes within 60s under a per-user lock (`invalid_grant` deletes, transient failures keep). Consumers: post-as-user mirroring, web→Talk read push (`_mark_read_as_user`, same 401 retry as `_post_as_user`), Talk→web read pull.

**No web→Talk unread leg**: system and bot messages count in Talk's `unreadMessages` but never reach `messages`, and `db.initialize_room_read_state` seeds cursors, so the obvious guard is unsound and a push without `lastReadMessage` marks everything read. It needs seeded-vs-earned provenance.

**Credential and session lifetimes are independent** (ISSUE-333): the cookie rolls forward while the pair can be deleted, and only login rewrites it. Both deletion sites call `webui.tokens.note_credential_lost` (`connected_service`, `object_id = "nextcloud"`; not for transient errors or never-stored), closed by `store_tokens`. `GET /istota/reconnect` re-runs authorize, returning via allowlisted `_POST_LOGIN_TARGETS`. A scheduler keepalive was rejected: it would put the web-only key in a second unit.
