# Web UI

Rationale behind the frontend rules. **Building or changing frontend code? Read
`web/AGENTS.md` first** — the component inventory, color tokens, page skeletons,
and the `npm run lint:design` check live there, along with the rationale behind
each. This file is not a substitute for them, and deliberately does not restate
them: it carries the **backend and admin-pane** side of the web UI. Web chat has
its own file: `.claude/rules/web-chat.md`.

Lives in `web/AGENTS.md`, not here: the component inventory, the semantic color
roles and what is deliberately not tokenized, the design-lint rules, the page
skeletons and stylesheet layering, the shared primitives, the settings-page
shape and the `HeaderSave` registry, the money record-table shell, the iOS shell
facade and its version gates, the viewport/keyboard height model, the 16px
control floor and the field tier, and client-local preferences.

SvelteKit (`web/`, `adapter-static`, base `/istota`) + FastAPI (`web_app.py`). Nextcloud-hosted OAuth2 (the legacy generic OIDC fallback was retired — Docker provisions the OAuth2 client via `provision-nc.sh`; Ansible templates `[web.oauth2]` directly), 7-day session. Routes: dashboard, chat, feeds (reader + sprocket-icon settings page served by `istota.feeds.routes` against per-user SQLite), location (today + history with cluster discovery; `/location/settings` for Overland ingest token), money (`/istota/money/*`, whose Business section is **Work | Invoices | Clients** — the Work tab is a full CRUD surface over the file-based work-entry store, addressing entries by their stable `uid` rather than the shifting display index and using per-entry etags so a concurrent agent edit 409s instead of being silently reverted; the Clients tab and the money settings **Invoicing** section are the CRUD surface over the _invoicing config_ — clients, entities and services — through the `/config/*` routes, so nothing about invoicing needs the CLI any more; see `.claude/rules/skills.md` under the `money` skill), health, briefings, settings, admin (read-only system health at `/istota/admin`, gated by a `_user_is_web_admin` helper that uses the `/etc/istota/admins` allowlist and **fails closed on an empty allowlist** — distinct from `Config.is_admin`, which retains its back-compat "empty = all admin" rule for sandbox/skill/command checks). Single-payload `GET /istota/api/admin/stats` aggregator (each section best-effort — a failure returns an `error` string rather than aborting the payload; includes a `models` section from `_admin_models_section()` = active brain kind, effective default model/effort, native endpoint/provider, and live `fast`/`general`/`smart` role resolutions via the brain's own `resolve_alias`); all timestamps normalized to canonical ISO 8601 UTC via `_iso_utc()`. Dev: `VITE_MOCK_API=1 npm run dev` for in-process mock backend.

**Admin pane** (ISSUE-203). `/admin` is a sidebar section — **Status** (the dashboard above), **Configuration**, **Logs** — with the `AppShell`/`ShellHeader` in `routes/admin/+layout.svelte` and each section a sub-route. Logs is the payload that justified the frame; Configuration is read-only for now and shaped so it can become the config editor without the nav changing.

**Logs** (`admin_logs.py`, `GET /admin/logs/sources` · `/admin/logs/{source}` · `/admin/logs/{source}/stream`). Two sources and deliberately no more: `app` — the `[logging] file` plus its `RotatingFileHandler` siblings, read as one stream newest-first (on a stock server deploy `output = "both"`, so this _is_ the scheduler/poller/brain output) — and `tasks`, the `task_logs` table. Per-task execution traces are excluded: they already have a reader at `/admin/tasks/{id}/events`, and the JSONL session store under `~/.claude/projects/` is not path-scoped to anything this module could confine.

The security posture is three properties. Every route is `_require_admin`, which fails closed on a blank `/etc/istota/admins` (unlike `Config.is_admin`'s permissive empty rule). **A request names a source id, never a path** — the only place a path is derived is `resolve_app_log_chain`, which symlink-resolves every candidate and confines it to the log directory, so traversal is not a reachable class of bug. And records are returned as JSON data rendered into text nodes; nothing treats log content as markup. Cross-user exposure is real and intended — `task_logs` embeds truncated task results — so every record carries its `user_id` and the source is filterable by user; clicking a `task N` cell filters to that task.

Reads are byte-bounded in both directions. Paging scans **backward in windows** so the last screenful of a 200 MB log costs a few hundred KB, with a scan cap so a filter matching nothing can't walk the archive (`truncated` says the budget was spent, distinct from `next_before === null` = nothing older). Two non-obvious invariants: a window always ends on a **record** boundary, not merely a line boundary, or a multi-line traceback is split and its tail lines are discarded as leading orphans by the next read; and the live tail grows its window rather than returning an unchanged cursor when it finds no boundary, since a cursor that doesn't advance leaves the tail silent forever while the UI still says "Live". Rotation is detected by the file **shrinking** below the cursor and reported as `reset` so the client clears rather than appends. Timestamps are **labelled, not converted** (the file source is server-local, `task_logs` is UTC) — shifting them into the viewer's zone makes a line un-greppable against the file it came from.

The toolbar deliberately exposes **no logger-prefix field**, though the `logger` query param the reader accepts is still a prefix match. One was built and removed: it needed you to already know a namespace to be worth anything, and `q` is matched against the logger name as well as the message, so the plain search box narrows to a subsystem by substring without a second control or a suggestions endpoint to keep fed. Search is therefore an ordinary sans field — it takes prose, not an id.

The SSE tail polls (the writer is the scheduler process, so there's no in-process bus) at a deliberately human cadence, and carries its cursor **inside the payload with no SSE `id:`** — a file cursor is `name:offset`, not an integer, so `Last-Event-ID` resume would hand back a value the client must reconcile with a `reset` anyway. The client therefore handles reconnects itself, re-opening from the cursor it has actually reached: the browser's own retry re-requests the URL as built, i.e. from the seed cursor, replaying everything since. Because two paths legitimately redeliver a record (that reconnect, and a record re-read once its continuation lines arrive), `lib/admin/logRecords.mergeRecords` is keyed on cursor and **replaces** rather than appends — the transcript is a keyed `{#each}` and Svelte throws on a duplicate key in production, so an append-only merge would turn a network blip into a blank page. The server's own failure frame is named `stream_error`, not `error`, because a frame named `error` lands on EventSource's built-in connection-error listener and is discarded unread.

**Configuration** (`admin_config_view.py`, `GET /admin/config`). The loaded `Config` walked into ordered sections of typed fields, each carrying a dotted `key`, a `type` and a `secret` flag — field-level rather than a TOML dump so the same payload can back an editable form later. Redaction is the whole safety story: a credential is emitted `value: null` with `set: true|false`. Matching is by field name against `SECRET_NAME_PATTERNS` (hyphens folded, so an HTTP header name matches too), with `_ALWAYS_SECRET_KEYS` for a field whose *contents* are credentials though its name isn't (`brain.native.extra_headers`, which `llm/openai_compat.py` merges over the `Authorization` header) and a dotted-key `NON_SECRET_KEYS` allowlist for the operational settings the patterns catch on a substring (`web.token_storage`, `brain.native.max_tokens`, `brain.tmux.bypass_*_marker`, …). A name-pattern rule is only as good as its coverage, so the tests assert coverage by **value**: a sentinel is stuffed into every credential-shaped leaf of a real `Config` and must not appear in the payload. The earlier name-shaped version of that test re-applied the implementation's own predicate to its own output and could not fail — which is how the `extra_headers` leak shipped past it.

Settings split (modules refactor, Phase 2): `GET /settings/services` returns only Connected services (`karakeep`, `google_workspace`); module-owned services (`monarch`, `feeds.tumblr_api_key`, `overland.ingest_token`) live on the per-module settings page and are reachable via `GET /settings/module-services/{module}`. Both endpoints share `_build_service_card`. `GET /settings/modules` returns the module registry plus per-user `disabled_modules` so the Preferences card can render the opt-out multiselect. Secret PUT/DELETE accept any service in `_all_known_services()` (connected ∪ module). Each per-module page calls `getModuleServices(<module>)` first; when `module_enabled=false`, it shows a "Module disabled — enable in /settings → Preferences" banner instead of the configuration UI. `/location/settings` adds an `/location/settings-info` endpoint that returns the webhook-URL placeholder (`https://<host>/webhooks/location?token=<token>`) and read-only place-detection knobs.
