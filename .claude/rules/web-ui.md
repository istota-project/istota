# Web UI

Rationale behind the frontend rules. **Building or changing frontend code? Read
`web/AGENTS.md` first** — the component inventory, color tokens, page skeletons,
and the `npm run lint:design` check live there, along with the rationale behind
each. This file is not a substitute for them, and deliberately does not restate
them: it carries the **backend and admin-pane** side of the web UI. Web chat has
its own file: `.claude/rules/web-chat.md`.

Lives in `web/AGENTS.md`, not here: the component inventory, the semantic color
roles and what is deliberately not tokenized, the design-lint rules, the page
skeletons and stylesheet layering, the shared primitives, the settings-page
shape and the `HeaderSave` registry, the money record-table shell, the iOS shell
facade and its version gates, the viewport/keyboard height model, the 16px
control floor and the field tier, and client-local preferences.

SvelteKit (`web/`, `adapter-static`, base `/istota`) + FastAPI (`web_app.py`). Nextcloud-hosted OAuth2 (the legacy generic OIDC fallback was retired — Docker provisions the OAuth2 client via `provision-nc.sh`; Ansible templates `[web.oauth2]` directly), 7-day session. Routes: dashboard, chat, feeds (reader + sprocket-icon settings page served by `istota.feeds.routes` against per-user SQLite), location (today + history with cluster discovery; `/location/settings` for Overland ingest token), money (`/istota/money/*`, whose Business section is **Work | Invoices | Clients** — the Work tab is a full CRUD surface over the file-based work-entry store, addressing entries by their stable `uid` rather than the shifting display index and using per-entry etags so a concurrent agent edit 409s instead of being silently reverted; the Clients tab and the money settings **Invoicing** section are the CRUD surface over the _invoicing config_ — clients, entities and services — through the `/config/*` routes, so nothing about invoicing needs the CLI any more; see `.claude/rules/skills.md` under the `money` skill), health, briefings, settings, admin (read-only system health at `/istota/admin`, gated by a `_user_is_web_admin` helper that uses the `/etc/istota/admins` allowlist and **fails closed on an empty allowlist** — distinct from `Config.is_admin`, which retains its back-compat "empty = all admin" rule for sandbox/skill/command checks). Single-payload `GET /istota/api/admin/stats` aggregator (each section best-effort — a failure returns an `error` string rather than aborting the payload; includes a `models` section from `_admin_models_section()` = active brain kind, effective default model/effort, native endpoint/provider, and live `fast`/`general`/`smart` role resolutions via the brain's own `resolve_alias`, and a `usage` section from `_admin_usage_section()` = fleet-wide token/cost totals plus per-model, per-brain and per-origin splits); all timestamps normalized to canonical ISO 8601 UTC via `_iso_utc()`. Dev: `VITE_MOCK_API=1 npm run dev` for in-process mock backend.

**Admin pane** (ISSUE-203). `/admin` is a sidebar section — **Status** (the dashboard above), **Health**, **Configuration**, **Logs** — with the `AppShell`/`ShellHeader` in `routes/admin/+layout.svelte` and each section a sub-route. Logs is the payload that justified the frame; Configuration is read-only for now and shaped so it can become the config editor without the nav changing. Health sits beside Configuration because it answers the neighbouring question: Configuration says what the process loaded, Health says whether the machine actually has what that describes.

**Health** (`doctor.py`, `GET /admin/doctor`). The runtime self-check registry rendered as status rows, in the same payload shape `istota doctor --json` emits — the pane and the image test tier read one vocabulary rather than two. The response adds a `summary` count and one overall `status` (worst of `fail` > `warn` > `ok`; skips don't count) so the header can be coloured without the client re-deriving it.

**Redacted before it leaves the process**, like `admin_config_view`: doctor's `detail` carries observed paths and raw exception text, and telling check authors not to put a credential there is not the same as it never happening — so `doctor.redact()` runs over every result on the way out, against a `_config` **snapshotted once** at the top of the handler (a SIGHUP rebinding it mid-run would otherwise scan text built from the old config against the new config's secret list). **`run_checks` is synchronous and spawns `--version` subprocesses**, so it goes to a thread; on the event loop it would stall every other request for its duration.

**A deep request runs in two phases**, and the reasons are all things the one-phase version got wrong. Phase one is the ordinary registry; phase two is `only=DEEP_CHECKS, deep=True` — the checks that spawn a bubblewrap namespace. Splitting them means the outer timer bounds only what it can actually bound: under one bound, `doctor.DEEP_TIMEOUT` (30s, the bwrap subprocess) was unreachable, because the same 30s also had to cover a dozen probing checks at `PROBE_TIMEOUT` each, so a healthy host could blow the outer timer with nothing wrong. It also means a deep probe that overruns costs the operator the deep result and nothing else, instead of discarding every shallow finding they may have opened the page to read. The timeout is `doctor.DEEP_TIMEOUT + headroom`, derived rather than restated, and is reported as a failing check named **`doctor.deep_run`** — deliberately not a registry name, since blaming `sandbox.masks` would assert a verdict on a check that may never have been reached.

**Single-flight is a `threading.Semaphore` the worker thread releases in its own `finally`, on a dedicated single-worker executor** — not an `asyncio.Lock` released by the awaiting request. `asyncio.wait_for` cancels the *await*, never the OS thread `to_thread` submitted, so releasing on timeout reports "nothing is running" while bwrap is still spawning, and the next request walks into a second concurrent namespace. The gate is taken with `acquire(blocking=False)`, one atomic operation, rather than a `.locked()` pre-check that is safe only by CPython's uncontended fast path having no suspension point. The executor is its own because an abandoned deep thread pins a worker for as long as its subprocess runs, and on the default pool — shared with every other `to_thread` caller in a single-process uvicorn — repeated timeouts would degrade unrelated admin endpoints. A second concurrent deep request gets **409**, not a queue slot; a shallow read is never blocked.

The pane groups by the first dotted segment in registry order, matching what `istota doctor` prints on a terminal, and mutes `skip` rows — on a healthy install they are the majority and the least interesting, and a skip is not a problem, only a check that does not apply here.

**Logs** (`admin_logs.py`, `GET /admin/logs/sources` · `/admin/logs/{source}` · `/admin/logs/{source}/stream`). Two sources and deliberately no more: `app` — the `[logging] file` plus its `RotatingFileHandler` siblings, read as one stream newest-first (on a stock server deploy `output = "both"`, so this _is_ the scheduler/poller/brain output) — and `tasks`, the `task_logs` table. Per-task execution traces are excluded: they already have a reader at `/admin/tasks/{id}/events`, and the JSONL session store under `~/.claude/projects/` is not path-scoped to anything this module could confine.

The security posture is three properties. Every route is `_require_admin`, which fails closed on a blank `/etc/istota/admins` (unlike `Config.is_admin`'s permissive empty rule). **A request names a source id, never a path** — the only place a path is derived is `resolve_app_log_chain`, which symlink-resolves every candidate and confines it to the log directory, so traversal is not a reachable class of bug. And records are returned as JSON data rendered into text nodes; nothing treats log content as markup. Cross-user exposure is real and intended — `task_logs` embeds truncated task results — so every record carries its `user_id` and the source is filterable by user; clicking a `task N` cell filters to that task.

Reads are byte-bounded in both directions. Paging scans **backward in windows** so the last screenful of a 200 MB log costs a few hundred KB, with a scan cap so a filter matching nothing can't walk the archive (`truncated` says the budget was spent, distinct from `next_before === null` = nothing older). Two non-obvious invariants: a window always ends on a **record** boundary, not merely a line boundary, or a multi-line traceback is split and its tail lines are discarded as leading orphans by the next read; and the live tail grows its window rather than returning an unchanged cursor when it finds no boundary, since a cursor that doesn't advance leaves the tail silent forever while the UI still says "Live". Rotation is detected by the file **shrinking** below the cursor and reported as `reset` so the client clears rather than appends. Timestamps are **labelled, not converted** (the file source is server-local, `task_logs` is UTC) — shifting them into the viewer's zone makes a line un-greppable against the file it came from.

The toolbar deliberately exposes **no logger-prefix field**, though the `logger` query param the reader accepts is still a prefix match. One was built and removed: it needed you to already know a namespace to be worth anything, and `q` is matched against the logger name as well as the message, so the plain search box narrows to a subsystem by substring without a second control or a suggestions endpoint to keep fed. Search is therefore an ordinary sans field — it takes prose, not an id.

The SSE tail polls (the writer is the scheduler process, so there's no in-process bus) at a deliberately human cadence, and carries its cursor **inside the payload with no SSE `id:`** — a file cursor is `name:offset`, not an integer, so `Last-Event-ID` resume would hand back a value the client must reconcile with a `reset` anyway. The client therefore handles reconnects itself, re-opening from the cursor it has actually reached: the browser's own retry re-requests the URL as built, i.e. from the seed cursor, replaying everything since. Because two paths legitimately redeliver a record (that reconnect, and a record re-read once its continuation lines arrive), `lib/admin/logRecords.mergeRecords` is keyed on cursor and **replaces** rather than appends — the transcript is a keyed `{#each}` and Svelte throws on a duplicate key in production, so an append-only merge would turn a network blip into a blank page. The server's own failure frame is named `stream_error`, not `error`, because a frame named `error` lands on EventSource's built-in connection-error listener and is discarded unread.

**Token usage on the dashboard.** Two places, deliberately not the same thing. Per-user usage joins the **existing Users rows** (`usage_tokens_24h`, `usage_cost_24h`, `usage_by_origin_24h`, …), so "how much is this user costing" is answered where "how much is this user running" already is rather than in a pane the reader correlates by hand. The fleet pane (`_admin_usage_section`) carries per-model, per-brain and per-origin and **no** top-5-by-user list: duplicating per-user data in two places gives it two chances to disagree.

Three rules the section must keep. **Two cutoff formats live in one function**: the task queries compare against `tasks.created_at` (`datetime('now')`, space-separated) while the usage queries compare against `task_usage.created_at` (ISO-Z). `' '` sorts below `'T'`, so reusing one bound for the other silently drops every row on the boundary day — no error, a plausible smaller number. They are built by two differently-named helpers (`_iso_z` against `strftime`) so a caller needing both has to choose. **Cost is a map keyed by basis, never a scalar**: one user's rows can span bases when an operator switches the CLI's auth mid-window, and nothing sums across them. And **`usage_rows_24h` can exceed `tasks_last_24h` by design** — it includes spend with no task row at all (a nightly sleep cycle, health OCR), which `usage_by_origin_24h` is what makes legible rather than leaving it to read as an arithmetic error.

The render rule is one sentence and every surface applies it to the same data: **a currency figure appears only where `cost_basis = 'api'`, and it is the whole of what the column says**. A subscription's list-price equivalent and a catalog estimate (which prices an unknown model at zero) show a dash. On a subscription deployment that means no cost at all, only tokens — the accepted trade, since a dashboard that quietly invents an invoice is worse than one that declines to guess. `cost_usd` and `cost_basis` are stored on every row regardless, so reversing this is a display change rather than a migration. The rule has one implementation per language and no more. The frontend half lives in `web/src/lib/usageFormat.ts`, extracted from the page precisely so the rule is testable; the Python half is `src/istota/usage_render.py` (`render_cost`, `fmt_money`, `fmt_int`, `fmt_context`, `COST_PLACEHOLDER`), which used to be private to `cli.py` and moved out when `!usage` became a second importer — `commands.py` is on the Talk polling path and cannot import the CLI entry point. `tests/test_cli_render_cost.py` and `usageFormat.parity.test.ts` pin the two languages to each other.

A mixed group used to append the other bases to the figure — `$0.18 +subscription+unknown`. That is gone. It overflowed `col-cost` (7rem, and the `.grid` is `table-layout: fixed` with no cell `overflow`, so it painted over `Last active`), and it named a distinction the reader cannot act on. The full map is still on the wire in `cost_by_basis`, and `istota usage --json` emits it.

**Claude Code subscription on the dashboard.** A second card, above Token usage and deliberately not folded into it (`_admin_subscription_section` in `web_app.py`, riding the existing `GET /admin/stats` in its own best-effort try/except, so a failure is `subscription: {"error": …}` and never a 500). The pairing is the point: on a subscription deployment the cost column below is all dashes by the rule above, and the plan's rate-limit windows are the budget that column cannot report. One card would put a live external reading, with its own failure mode and its own staleness, under the same heading as an aggregate over `task_usage`, leaving one card half-stale and half-fresh with two error branches. Everything on the wire comes from `subscription_usage.get_snapshot`, which the doctor check and `!usage` read too, so no surface holds a second copy of the endpoint's shape and the dashboard's 60s poll costs one fetch per TTL for the whole deployment.

Three things about that payload. `warn_percent` and `high_percent` ride it because the tile tints by them, and the alternatives were both worse: literals in the TypeScript would ignore a configured threshold without saying so, and a second endpoint would let the tint and the number it tints come from two different reads. They are configuration, not credentials, and the operator reading the dashboard is the one who set them; a payload carrying neither (an older backend) gets no tint rather than a guess. The server's own `severity` is on the wire and unused — its scale is undocumented and we have only seen `"normal"`, and two surfaces applying one rule to one number always agree. And the `subscription` key is **absent unless there is a card to draw** — the section returns `None` when Claude Code is neither the brain nor the configured fallback, and when the reading could not be obtained. It used to emit `available: false` with a reason so the card could render a one-line note instead of disappearing, which was right while a missing reading meant something was wrong. It is not: the endpoint answers the long-lived setup-token credential both server shapes deploy with a persistent `HTTP 429`, so that note was permanent on every such host and named nothing anyone could act on. The gate is `kind` **or** `fallback`, not `kind` alone — a `native` deployment failing over to `claude_code` burns the plan, which is the case the card exists for — and it short-circuits before the fetch, so a deployment that cannot use the subscription never polls Anthropic about it. `runtime.subscription_usage` carries the reason now, as a **SKIP**: every no-data branch of that check skips rather than warns, so the Health pane is not amber on a host with nothing wrong with it, and only real utilization still WARNs. `token_source` is the resolver's branch name (`env` / `file` / `keychain`) and never the token.

**The Extra usage tile does not break the `cost_basis` render rule.** That rule refuses to price plan-equivalent *tokens* at list, because a derived figure read as spend is an invented invoice. Pay-as-you-go credits are not derived: they are money the account has already committed, reported by the endpoint in minor units with an explicit currency and an explicit `exponent`. The divisor comes from that `exponent` and never a hardcoded 100 — the removed 2026-03 `!usage` divided by 100 and was wrong for any currency that is not two-decimal. This percentage is also the one that renders **unclamped**, unlike a plan window's: above 100 here is a real overage, and clamping it would hide one while the two money figures beside it still showed it. The tile appears only when `spend.enabled`.

It is a tile in the same grid as the plan windows rather than a note under them, so the card reads as one row of meters the way the system banner at the top of the page does, and it comes last. Its **value is the money spent** while every window beside it shows a percentage — the cap and the share of it ride the sub-line, where the two read together — because this is the one figure on the card that is money rather than a share of a quota. It still tints on the same `warn_percent` / `high_percent` pair, so a row of four meters has one colour rule rather than one tile sitting uncoloured.

**Configuration** (`admin_config_view.py`, `GET /admin/config`). The loaded `Config` walked into ordered sections of typed fields, each carrying a dotted `key`, a `type` and a `secret` flag — field-level rather than a TOML dump so the same payload can back an editable form later. Redaction is the whole safety story: a credential is emitted `value: null` with `set: true|false`. Matching is by field name against `SECRET_NAME_PATTERNS` (hyphens folded, so an HTTP header name matches too), with `_ALWAYS_SECRET_KEYS` for a field whose *contents* are credentials though its name isn't (`brain.native.extra_headers`, which `llm/openai_compat.py` merges over the `Authorization` header) and a dotted-key `NON_SECRET_KEYS` allowlist for the operational settings the patterns catch on a substring (`web.token_storage`, `brain.native.max_tokens`, `brain.tmux.bypass_*_marker`, …). A name-pattern rule is only as good as its coverage, so the tests assert coverage by **value**: a sentinel is stuffed into every credential-shaped leaf of a real `Config` and must not appear in the payload. The earlier name-shaped version of that test re-applied the implementation's own predicate to its own output and could not fail — which is how the `extra_headers` leak shipped past it.

Settings split (modules refactor, Phase 2): `GET /settings/services` returns only Connected services (`karakeep`, `google_workspace`); module-owned services (`monarch`, `feeds.tumblr_api_key`, `overland.ingest_token`) live on the per-module settings page and are reachable via `GET /settings/module-services/{module}`. Both endpoints share `_build_service_card`. `GET /settings/modules` returns the module registry plus per-user `disabled_modules` so the Preferences card can render the opt-out multiselect. Secret PUT/DELETE accept any service in `_all_known_services()` (connected ∪ module). Each per-module page calls `getModuleServices(<module>)` first; when `module_enabled=false`, it shows a "Module disabled — enable in /settings → Preferences" banner instead of the configuration UI. `/location/settings` adds an `/location/settings-info` endpoint that returns the webhook-URL placeholder (`https://<host>/webhooks/location?token=<token>`) and read-only place-detection knobs.

**Avatars** (`avatars.py`, `GET /api/avatars/bot` · `/api/avatars/user/{user_id}` · `PUT`/`DELETE /api/settings/avatar` · `PUT`/`DELETE /api/admin/avatar`). Profile pictures for the identities the UI renders, normalized to a 192px WebP in two framework tables rather than in `user_profiles` (whose readers `SELECT *`, one of them over every user at config load). `/me` carries a content hash for the caller's own picture and for the bot icon, so the client can build an immutable URL for each without a round trip; a third party's hash deliberately travels nowhere, and the client pays one conditional request per author per session instead of a field on every row of the byte-budgeted room-event stream.

Three properties carry the security of it. **A co-member's picture is served, and never as `immutable`** — the endpoint answers when the subject is the caller or `db.shares_room_with` finds a room in common, and membership is revoked by code that already exists, so a year-long cache entry would make the predicate unenforceable exactly when it starts mattering; the self and bot cases are not revocable and keep the long cache, a co-member gets `max-age=300`. **Every refusal is one 404** — no picture, no shared room and no such user are byte-identical, the rule message stars already follow, because a distinguishable 403 turns the endpoint into a user-directory oracle and an avatar is a face. And **the upload cap is enforced before the body exists in memory**: the declared `Content-Length` first, then the running total as the stream arrives, which is why the route takes a `Request` rather than an `UploadFile` (FastAPI parses the body before it solves dependencies, so a check written as a dependency runs after the spool it was meant to bound). The decode runs on a **dedicated single-worker executor** for the reason the doctor deep check has one: Pillow decompresses a PNG's text chunks inside `Image.open` before any ceiling the app can see, so one upload's peak is far above its byte cap, and the only knobs that would fix it at the source are module globals shared with the executor's attachment pre-shrink in another thread.

The second source in the precedence chain is **imported, on a scheduler cadence, and only where Nextcloud says the picture is user-set**. `scheduler.check_avatar_import` (gated on `[web] enabled`, `storage_is_nextcloud`, `[web] avatar_import_from_nextcloud` and `[scheduler] avatar_import_interval`) walks `config.users` — never the `user_avatars` table, since a user with no row is exactly the one needing a first import — fetching each user's avatar with the ETag stored beside their row and holding no transaction across a fetch. Nextcloud answers that endpoint with a picture whether or not one was set, generating a coloured letter when it was not, so `nextcloud/avatars.py` imports only on the `X-NC-IsCustomAvatar` header (observed on `nextcloud:30-apache`, `1` and `0`; `tests/full/test_nextcloud_avatar_header.py` is what holds that). A server that does not send it imports nothing and logs once, because degrading to today's initial chip is right and degrading to Nextcloud's version of the same chip — indistinguishable from a photograph at every call site afterwards — is not. Each fetched image goes through the same `avatars.normalize` an upload takes. `doctor`'s `web.avatar_import` reports on all of this and **opens no socket**, so the tick writes what it saw into `shared_kv` (`_avatar_import`/`last_tick`) for it to read; that is the only thing able to tell "nobody has set a Nextcloud avatar" from "the header never arrives here, so nothing will ever be imported".

**Five call sites, split by what they know rather than by where they are.** The two identities `/me` names — the viewer and the bot — are drawn with a hash and so an immutable URL: the chat gutter's own rows and its bot rows, the Settings preview, the `/admin` bot-icon card, and the confirmation card's actor, which draws the bot and exists because a confirmation lands on a continuation row as often as not, and that row has no author header to say who is asking. **A third party is drawn bare**, since no hash for one travels (D13): a co-member's turn in the gutter, off `author_id` (see `.claude/rules/web-chat.md`), and the `/admin` users table. One consequence worth stating, because the cache table above reads as a description of what happens: **branch 5 (`v` matches, a co-member, `max-age=300`) is unreachable from the shipped client**, since a bare request has no `v` to match. Every third-party render takes branch 3 and revalidates on an ETag, which is stricter than the 300s that branch defends; branch 5 is there for a client that learns a hash some other way. The admin case is the other one to be clear about: an admin is *not* privileged on this endpoint, so a row for someone they share no room with 404s and falls back to the chip, at one 404 per user per thirty seconds (branch 1's negative cache). Widening the predicate for admins would be a decision about the endpoint, not about the table.

Note that co-membership is wider than it reads: the Talk poll seeds `room_members` for every istota user in a conversation, so the real predicate is "anyone who can put A in a Talk room with them can read A's face". Accepted for a face, and stated so a future source with more to disclose does not inherit it unexamined. See `.claude/rules/config.md` under `WebConfig` for `max_avatar_kb`.

**The bot icon** is one row in `bot_avatar`, written by `PUT`/`DELETE /api/admin/avatar` under `_require_admin` + `_verify_origin` — the first mutating admin routes in `web_app.py`, though not in the app: they copy the three `briefings/routes.py` already ships. Both take `_read_avatar_upload` whole rather than a second copy of the two size checks and the one-at-a-time decode budget, and neither is a trusted-input path — an admin's upload takes the same decode as anyone's. Not in config and not in `shared_kv`: TOML cannot carry binary, a path in config means a file placed on the host by hand that the Ansible template and the Docker render are both free to overwrite, and `shared_kv.value` is TEXT, so it would be base64 in a namespace the model-facing `kv` skill can list. `istota bot-icon set/clear/show` is the headless door — `set` is idempotent by the content hash of what is *stored* and reports `STATE: created|updated|noop`, `clear` reports `updated|noop`, and `show` reports the row (mime, size, hash, `updated_at`, never the bytes) and no `STATE:` line at all — so a play can call `set` on every deploy and read `changed_when` off stdout. `[web] max_avatar_kb = 0` switches the *upload endpoint* off, including the admin one, and deliberately does not reach the CLI: that setting is about an unauthenticated network body, while this reads a local file as the operator, so it falls back to the shipped default. An unmigrated database is a named refusal and exit 1 rather than a traceback, because the play runs before the migrations on exactly one ordering. It is **not** the bot's Nextcloud Talk avatar and cannot become one — `POST /index.php/avatar` is a session-and-CSRF-guarded web route and the daemon holds an app password — so the admin card names the Nextcloud account and says the two are separate.

The server-rendered login and sign-in-failure cards inline it as a `data:` URI rather than gaining a route. That is **not** privacy: the same page already serves the favicon and the sigil to an unauthenticated browser off the static mount, and the inlined icon is public by the same token — it is one fewer route for one image on one page, with the base64 memoized on `bot_avatar_hash` so a page load costs a `SELECT content_hash` and never a BLOB. Two things there are easy to get wrong. `_login_page_mark` never raises, because it runs on the unauthenticated login path and on the failure path, and a decoration that could take either down is worse than a missing picture. And the icon carries a class opting out of `.mark`'s light-theme `invert(1)`: that filter exists to flip a flat near-white silhouette, and a photograph through it is a negative — the same reason `Avatar.svelte` applies none.

Three smaller things there, each of which is a defect if reversed. The hash is queried **before** the memo is consulted, so a *cleared* icon takes the early return above it — reading the memo first is the obvious way to save the connection and it serves a deleted icon on the login page forever, which is why a test holds the ordering rather than a comment. The resolution runs on a **dedicated single worker**, for the reason the doctor deep check and the avatar decode each have one: this is the app's only unauthenticated route that touches SQLite, and the default pool is shared with every other `to_thread` caller in a single-process uvicorn. And the stored `mime` is escaped on the way into the `src` attribute — unreachable through `put_bot_avatar`, which binds the literal constant, but `get_bot_avatar` reads the column back and the app ships no CSP (a deliberate non-goal), so the guarantee belongs to the line that renders rather than to a different function. An operator's own nginx adding `img-src 'self'` would break the inlined icon with no fallback, since the sigil branch is taken only when the *database* says there is no icon.

**`GET /api/map/basemap`** hands the frontend the resolved tile spec for the calling user — style URLs and attribution, a CARTO key only already embedded in the URL, never as a field (ISSUE-334). It is a thin read over `istota/map_basemap.py`, which is deliberately the **only** place the URL shapes exist: doctor's `web.basemap` check reads the same resolver, and a second copy there would let the check pass while the map rendered CARTO's "API KEY REQUIRED" watermark. A user's own stored `location`/`carto` key selects CARTO for them, overriding the operator's `[web.map] provider`. See `.claude/rules/config.md` under `WebMapConfig` for why the check opens no socket.
