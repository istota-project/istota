# Istota - Claude Code Bot

Claude Code-powered assistant bot with Nextcloud Talk interface.

**Production server**: `your-server` (SSH, installed at `/srv/app/istota`).

For module-specific internals, see `.claude/rules/`:

- `brain.md` — Brain protocol + ClaudeCodeBrain + NativeBrain (in-process agent loop)
- `executor.md` — `execute_task()`, env mapping, prompt assembly, security
- `scheduler.md` — daemon loop, worker pool, DB tables, deferred ops
- `config.md` — every dataclass field + TOML mapping
- `skills.md` — skill metadata, single-axis selection (eager vs menu), CLI modules
- `transport.md` — Transport seam over messaging surfaces (Talk + email; Matrix / web chat designed-for)

## Architecture

```
Talk Poll ──►┐
Email Poll ──►├─► SQLite Queue → Scheduler → Brain → Talk/Email Response
TASKS.md ────►│
CLI ─────────►┘

GPS Webhook ──► Location DB → Place detection → ntfy/Talk
Web App ──► Nextcloud OAuth2 → Dashboard / Feeds / Location / Money / Health / Settings / Admin
```

- **Talk poller**: daemon thread, long-poll per conversation, WAL-mode DB.
- **Email poller**: routing precedence — plus-address → sender match → thread match (`sent_emails`). Plus-addressed emails from untrusted senders are held in `pending_confirmation`.
- **Task queue**: atomic locking with `user_id` filter, exponential backoff (1, 4, 16 min).
- **Scheduler**: per-user worker pool, three-tier concurrency (instance fg/bg + per-user).
- **Executor**: builds prompt + env, hands a `BrainRequest` to the configured Brain.
- **Brain**: pluggable model backend. Three brains ship: `ClaudeCodeBrain` (default, wraps headless `claude -p` CLI), `NativeBrain` (Istota's in-process agent loop against any OpenAI-compatible model; loop in `agent/`, providers in `llm/`, turn state in `session/`), and `TmuxClaudeBrain` (drives the interactive `claude` TUI in a detached tmux session to keep traffic on subscription billing; full-switch via `brain.kind = "tmux_claude"`, with `claude_code` as the automatic fallback + circuit breaker — see `.claude/rules/brain.md`). Each brain owns its own model namespace — canonical IDs and a unified `DEFAULT_ALIASES` table holding both the portable tiers (`fast`/`general`/`smart`) and the provider shortcuts (`opus`/`sonnet`/`haiku`), base names only. Consumers always go through `make_brain(config.brain).resolve_alias(...)` / `.resolve_model_name(...)`. Effort is an orthogonal `:effort` modifier on any reference (`opus:high`, `smart:low`), split off at resolution — never baked into an alias name. Operator alias overrides via `[models.aliases]` TOML are **per-namespace**: each brain has a `model_namespace` (`anthropic` for the CLI brains, `openai_compat` for native) and resolves an alias in its own namespace, so one `[models.aliases.smart]` block carries an `anthropic` value and an `openai_compat` value that never cross-contaminate; a custom alias flagged `portable = true` re-resolves across the cross-brain fallback boundary. A legacy flat `smart = "string"` still works (namespace-agnostic). The old `[models.roles]` key is a hard rename (stale one logs a migration warning; old `opus-high`-style forms no longer resolve). See `.claude/rules/brain.md` "Model identity". **Brain fallback** (`[brain] fallback`): when the primary brain is unavailable (subscription usage limit → `stop_reason="usage_limit"`, missing binary → `not_found`, tmux launch failure → `fallback`) the executor reruns the _same attempt_ through a configured fallback brain (e.g. `claude_code` → `native`). Portable role tiers (`fast`/`general`/`smart`) re-resolve across the provider boundary; a provider-specific pin drops to the fallback's default (with a visible note). A process-global availability breaker skips an unavailable primary for `fallback_cooldown_seconds`. The old hardcoded tmux→claude_code path folds into this. See `.claude/rules/brain.md` "Brain fallback".
- **`!model <alias> <prompt>`**: per-task model override prefix in Talk. Aliases (resolved by the active brain, base names): `default`, role tiers (`fast`/`general`/`smart`/custom), provider shortcuts (`opus`, `sonnet`, `haiku`), plus an optional orthogonal `:effort` modifier on any of them (`opus:high`, `smart:low`, `claude-opus-4-8:xhigh`). Stored canonical (model + separate effort) on the task row so the DB stays version-pinned. Companion: `!models` lists the resolved table.
- **Task-control commands**: `!stop` cancels; `!steer <text>` (alias `!inject`) is its additive counterpart — the note reaches the model at its next loop boundary as an extra user turn, without discarding work in progress. Backed by the `task_steers` table (per-task monotonic seq, pending/consumed/dropped) and the `Brain.supports_steering` flag; the executor supplies a `poll_steers` callback only to steering-capable brains and the scheduler drops undrained steers at finalization. Only `native` is wired (the command layer's `_STEERABLE_KINDS` allowlist) — `claude_code`'s stdin is closed after the prompt; `tmux_claude` declares support but is gated out. Room-scoped, depth-capped at 10 pending, mirrored into the room transcript (display-only, `task_id=NULL`) and the live event log. `!retry` / `!resume` (ISSUE-189) re-run a `failed`/`cancelled` interactive task — `!retry` from scratch, `!resume` with the failed attempt's `execution_trace` prepended as a "continue from where you left off" frame (degrading to `!retry` when no trace was captured). Both create a _new_ task with `parent_task_id` + copied delivery fields rather than re-queueing, so the failed attempt stays in history and out of the automatic backoff; attachments are deliberately not copied. All live in `commands.py` — no DB migration, no executor change.

## Key Concepts

### Identity

- Technical IDs (package, env vars, DB, CLI): always `istota`.
- User-facing identity: `bot_name` config (default "Istota"). `bot_dir_name` sanitizes for filesystem use.
- Templated docs use `{BOT_NAME}`, `{BOT_DIR}`, `{user_id}` placeholders.

### Prompt Layers

1. **Emissaries** (`config/emissaries.md`) — constitutional principles, global only.
2. **Persona** (`config/persona.md` or user `PERSONA.md`) — character.
3. **Custom system prompt** (`config/system-prompt.md`, opt-in) — replaces CC default.

### Admin / Non-Admin Isolation

Admin user IDs in `/etc/istota/admins` (empty = all admin). Non-admins: scoped mount, no DB write, no subtasks, `admin_only` skills filtered.

### Modules vs resources vs connected services

- **Resources** — after the Resources sunset, only `folder` (an out-of-workspace sandbox mount) is declarable. The path-shaped types (`calendar`, `todo_file`, `notes_folder`, `email_folder`, `reminders_file`) were retired: calendars are CalDAV-discovered; todo/reminders/notes read an explicit path (a briefing-source `path`, or a deprecated `todo_file`/`reminders_file` resource override) — no convention-default filename, and the `notes/` folder is prompt guidance for the model only; email folders have no consumer. `shared_file` survives as internal organizer state. Live in `[[users.X.resources]]` + the `user_resources` DB table; `folder` is operator-only (CLI/Ansible, no web UI).
- **Modules** — on-by-default features with their own UI tab and a settings page reachable via a cog icon (`feeds`, `money`, `location`, `health`). Names live in `istota.modules.MODULE_NAMES`. Per-user opt-out via `disabled_modules`. Single source of truth: `Config.is_module_enabled(user_id, module)`. Names that also appear in `EXPERIMENTAL_MODULES` are AND-gated on the matching `[experimental] features` flag — disabled-by-default until the operator opts in, after which they behave like any other module. (`EXPERIMENTAL_MODULES` is currently empty; the mechanism is kept for future modules.) A module whose optional install extra is missing is treated as **unavailable** rather than half-present: `modules.MODULE_DEPENDENCIES` maps a module to the import names its extra provides (`money → beancount`), `modules.module_available()` probes them with `importlib.util.find_spec` (cached), and `is_module_enabled` returns False for an unavailable module _before_ the per-user DB read. This is what lets the lean local install omit `money` entirely (no beancount) while a `uv tool install 'istota[local,money]'` lights it up — hidden everywhere at once (scheduler `_sync_module_jobs`, `/api/me`, web nav) through the single gate.
- **Connected services** — per-user external API credentials consumed by skills / modules (`karakeep`, `google_workspace`, `ntfy`, `garmin`). Stored encrypted in the `secrets` table (Fernet over scrypt-derived key from `ISTOTA_SECRET_KEY`); the bookmarks skill resolves both `KARAKEEP_BASE_URL` and `KARAKEEP_API_KEY` from there. Provisioned via `istota secret ensure|list|remove` (Ansible) or `/istota/settings` (web). Schema for both surfaces lives in `secret_schema.py`. `garmin` is cross-module (Health daily summaries + Location GPS-track import share one token blob): its auth surface is the module-agnostic `garmin_routes.py` router (not health-gated), its card is `custom_ui` (an interactive email/password→MFA flow, not writable fields), and `health.garmin.acquire_client` is the single sanctioned way to get an authenticated client — it re-persists rotated tokens under a per-user lock so the two consumers can't invalidate each other's blob.

### Experimental features

Operator-scoped feature flags for in-tree-but-off-by-default work. Configured via `[experimental] features = [...]` in `config.toml` (or `istota_experimental_features` in Ansible). Off by default; never exposed in the web UI; not toggleable per user. The flag list flows to every subprocess builder as `ISTOTA_EXPERIMENTAL_FEATURES` (CSV), so subprocess-paths see the same gate as the LLM path. Four surfaces honor the gate:

- **CLI subcommands** — `@requires_feature("name")` Click decorator (`src/istota/experimental.py`). Gated-off calls emit the standard `{"status":"error","error":"…"}` JSON envelope; in `_execute_command_task` / `_execute_skill_task` the envelope detector reclassifies stdout-OK exits as task failures with the human-readable message intact. Currently used by `money lots` (`money_tax`) and `money wash-sales` (`money_wash_sales`).
- **Skills** — `experimental: true` in `skill.md` frontmatter requires `skill_<name>` in the enabled set. The gate fires in the selection main loop, the sticky path, the companion pull-in, and the menu-catalogue filter (`eligible_skill_names`) so a gated-off skill reaches neither selection nor the on-demand menu.
- **Modules** — `EXPERIMENTAL_MODULES` mapping in `modules.py` (currently empty). When populated, `Config.is_module_enabled` AND-s the flag in before the per-user DB read; the `/settings/modules` web endpoint and `_coerce_profile_value("disabled_modules", …)` validation consult the same gate so a disabled experimental module never appears in the user-facing surface at all.
- **Web routes** — module-shaped surfaces only register when the gate is on; `/api/me` filters its `features` payload through the same check.

`istota experimental list` prints the `KNOWN_FEATURES` registry with on/off status from the loaded config. Unknown names in TOML log a warning but don't fail startup, so graduating a feature in code stays a code-only change. Naming convention: `module_<x>` for module gates, `skill_<x>` for skill gates, free-form for CLI subcommand gates. See `docs/EXPERIMENTAL.md` for the registry and graduation policy.

### ntfy push notifications

ntfy is a per-user connected service — there is no global `[ntfy]` block. Each user supplies their own server URL, topic, and (optional) auth via the encrypted `secrets` table (web settings or `istota secret ensure -s ntfy ...`). `notifications._send_ntfy` reads everything from the user's secret rows; if the user has no `topic` set, ntfy is a no-op for them. Default priority is hardcoded to `3`; per-call overrides flow through `send_notification(...)`.

Header values are RFC 2047-encoded by `ntfy_headers.encode_header_value` before they reach httpx, which serializes headers as **ASCII** — an emoji/arrow/em-dash title used to raise `UnicodeEncodeError` and lose the whole notification, body included (ISSUE-213); every briefing pushed to a phone was hit, since a briefing title carries an em-dash before the date. Bodies are opt-in **markdown**: `DeliveryOptions.markdown` on the transport, `--markdown` on the skill CLI, both emitting `Markdown: yes`. Opt-in because a plain-text body routinely carries `*`/`_`/`#`, and because ntfy renders markdown in its **web app only** — a phone popup shows the source, which is why `skills/ntfy/skill.md` tells the model to use it for genuinely structured messages rather than to bold a word.

What it IS: a one-way push channel (bot → device) used by heartbeat alerts, scheduled-job output (when `output_target=ntfy`), and `surface="ntfy"` notifications. What it ISN'T: two-way (you can't reply over ntfy), a Talk replacement, operator-shared infrastructure, or required (most users won't configure it).

### Memory System

- `USER.md` — auto-loaded, optional nightly op-based curation. Runtime writes go through the `memory` skill CLI (`istota-skill memory append|add-heading|remove|replace|remove-heading|show|headings`) — never `echo >>`. `remove`/`replace` reach bullets anywhere in a section (top region **and** `### subsections`); `replace` rewrites in place; `remove-heading` drops a whole section; `append --subheading` targets a subsection. The CLI shares the curation `apply_ops` engine, takes a per-file flock (anchor under the per-user deferred dir, not on the Nextcloud mount, so flock stays reliable and the config dir stays clean), and writes a `source="runtime"` audit entry per call.
- `CHANNEL.md` — loaded with `conversation_token`. Same CLI with `--channel TOKEN` (token must match `ISTOTA_CONVERSATION_TOKEN`). Channel writes are not audited (no per-channel audit infrastructure yet) and do not update `USER.md.last_seen.json`; the audit/curation pipeline is USER.md-only.
- `memories/YYYY-MM-DD.md` — last N days auto-loaded (`auto_load_dated_days`).
- Knowledge graph (`knowledge_facts`) — temporal subject/predicate/object triples, freeform predicates, fuzzy dedup (predicate-equality gated), audited. Sandboxed runtime writes via `istota-skill memory_search add-fact|invalidate|delete-fact` are deferred as `task_<id>_kg_ops.json` and applied by the scheduler post-task.
- Classification gate in `memory/skill.md`: temporal events and stable factual claims → KG; behavioral instructions → USER.md; reusable task procedures → playbooks (sleep-cycle-generated in v1).
- Learned playbooks (`playbooks.enabled`, off by default) — per-user markdown task procedures distilled by the sleep cycle from successful multi-step tasks, stored under the user's bot `playbooks/` dir, indexed into `memory_chunks` as `source_type="playbook"`, and recalled by relevance into a "## Learned Playbooks" prompt section. Markdown-only, never executed; excluded from briefings. Lifecycle (ISSUE-174): the extraction prompt distils the _verified_ command from the trace's per-tool `raw` field (the literal Bash invocation, captured by all three brains) rather than a paraphrase, and writes a thin router instead of re-narrating a single-script task; a `pinned: true` file survives re-derivation (kept on disk, re-indexed so the correction reaches recall); retention (`retention_days`, default 90) prunes on **last-use** mtime (stamped on recall), deletes the pruned file's chunks, never prunes a pinned file, and grandfathers existing files on first upgrade. See `.claude/rules/scheduler.md` (generation) + `.claude/rules/executor.md` (recall).
- Nightly curator self-heals: bypass-write detection (`USER.md.last_seen.json` sidecar), sha256 re-read after the LLM call, agents-header migration, Phase-A lint pass logs date-stamped USER.md bullets without migrating them.
- Memory recall (BM25 + vector) — opt-in via `auto_recall`.
- Briefings exclude all personal memory.
- Subsystem lives under `src/istota/memory/`; `memory/sleep_cycle.py` orchestrates.

### Skills

Self-contained `src/istota/skills/<name>/skill.md` (YAML frontmatter + body). **Single-axis model:** a skill is either **eager** (full body in the prompt, because a deterministic rule in `select_skills` picked it — `always_include` / `source_types` / `file_types` / `sticky` / `companions`, minus `excludes`) or in the **menu** (a one-line entry the model pulls in full via `istota-skill skills show <name>`, which also delivers that skill's companions). The menu is the full eligible catalogue (`eligible_skill_names` — every loadable skill not already eager), so the capable main model self-selects from it. Keyword (`triggers`) and `resource_types` matching are NOT selectors (kept as `!skills`-surfaced documentation); `resource_types` survives only as a menu-membership gate. There is no eager/lazy `disclosure` field, no `progressive_disclosure` flag, no `always_eager` list — the menu is intrinsic. CLI skills expose `python -m istota.skills.<name>` and run through the credential-injecting skill proxy. The `skills` core skill is the on-demand loader. (The former LLM "Pass 2 semantic routing" pre-router and the two-axis eager/lazy disclosure model were both removed — the menu replaced them.) Full details in `.claude/rules/skills.md`.

### Nextcloud control plane

The `nextcloud` skill is a multi-group CLI over `src/istota/nextcloud/` (spec `Specs/Done/nextcloud-skill-cli.md`): `capabilities` (a one-call deployment fit-check with `--check` as a shell gate, also `istota nextcloud capabilities`), `user`/`group` lookup (non-admin-safe via `/core/autocomplete/get`; the provisioning verbs name admin rights as the cause of a 997), `share` (incl. `share link` — the ISSUE-193 fix: default expiry, optional password, a synthesized direct-download URL, a revoke loop), `files` (the WebDAV operations the mount can't express — properties, indexed server-side SEARCH, versions, trash, quota, chunked upload; deliberately **no** read/write/mkdir/rm/mv/cp), `talk` (an _agent-facing_ control surface, not a second delivery path), and `notify`/`activity` reads. Every failure raises `OcsError` carrying HTTP status + OCS status + the server's message. Gated by `requires_capability: [nextcloud]` (keyed on `nextcloud.url`, so it vanishes on a standalone install). Inbound text is untrusted-framed; outbound sharing/messaging is confirmation-gated; destructive verbs need `--confirmed`; `files`/`share` paths are scoped to `/Users/<caller>/` for non-admins. `nextcloud_client.py` survives as the `None`-returning shim for four best-effort daemon paths. **Live-verified**: `tests/test_nextcloud_skill_live.py` (`pytest -m integration`, needs `NC_URL`/`NC_USER`/`NC_PASS`) drives `main(argv)` for all 44 verbs against a real server, tiered behind `NC_TEST_ADMIN`/`NC_TEST_TALK`/`NC_TEST_DESTRUCTIVE`/`NC_OTHER_USER`; `TestLiveCoverage` in `tests/test_nextcloud_skill_cli.py` runs in the **default** suite and fails when a new verb ships without a live test (the live file is skipped without credentials, so a guard living there would guard nothing). The first live run found five defects the mocked suite had encoded rather than caught — SEARCH's scope href must be DAV-root-relative (`/files/<user>`, not `/remote.php/dav/files/<user>`, which Sabre 404s); a named activity stream is `/activity/<filter>` while the reserved `filter` segment is for object lookups; `talk send` must unwrap the OCS envelope (`send_message` alone returns the raw body) or it reports no message id; Talk's unified-search `from` param means "the page I'm on" and _excludes_ that conversation, so `--token` filters client-side on `attributes.conversation`; and `share link` expiry bases on **UTC**, since a client west of the server otherwise computes a date the server already calls past. See `docs/features/nextcloud.md`.

### Input Channels

- **Talk**: long-poll, message cache, ack/progress/result via referenceId. `!commands` intercepted in poller.
- **Email**: IMAP poll, attachments to `inbox/`, threaded replies via deferred `email output` JSON. Outbound tracked in `sent_emails` for emissary thread matching. The email skill is a **two-way client** — read (`list`/`read`/`search`/`thread`/`attachments`/`from-senders`/`newsletters`) + richer send (`--cc`/`--bcc`/`--attach`/`reply`/`reply-all`) + gated `mark`/`delete`. Reads are scoped `--scope {mine,shared,all}` via the shared `email_ownership` resolver (plus-address → sender-match → thread-match), so a user only ever sees their own mail plus the unowned shared pool, never another user's. Per-user **quiet senders** (`user_profiles.quiet_email_senders`, fnmatch) file matching mail silently in `poll_emails` — marked processed, no task, read back on demand via `from-senders`. See `.claude/rules/skills.md`.
- **TASKS.md**: 30s poll, `[ ] [~] [x] [!]` markers, SHA-256 identity.
- **REPL** (`istota repl`): interactive terminal loop (`src/istota/repl/`). Confinement is two independent checks: the lexical one reuses the skill CLI's `resolve_scoped_path` (one rule for browser and model) and a `realpath` pass catches a symlink _inside_ the workspace pointing out. No admin bypass — `is_admin=False` always, since this is the most directly reachable read path on the web app. Always `Content-Disposition: attachment` + `nosniff` (the workspace holds user-authored HTML/SVG, which inline would execute on the app's own origin against the session cookie). An rclone deployment has no local workspace → 503 naming the share-link alternative. The model is told to use it by `config/guidelines/web.md`'s "Handing over a file" section — the surface guideline, not the skill, because the trigger is "a task produced a file" and `nextcloud` is a menu skill the model would never reach for on that prompt. Per-room UI: a kebab → `RoomSettings.svelte` modal renames a room (token invariant), sets its **standing model/effort default** (see below), copies its token (for a `web:<token>` route), and hard-deletes it behind a GitHub-style type-the-name confirm. **Per-room model default**: a room carries an optional `model`/`effort` on the shared `rooms` registry (canonical values, so the default is surface-independent — a Talk message and a web message in the same room resolve the same default). `transport.ingest.record_inbound` fills a task's model/effort from the room default when the message carried no inline `!model` override (the inline prefix wins as a unit — effort follows model, so an explicit model choice keeps its alias's own effort). Precedence: inline `!model` > room default > `config.model`. Settable on both surfaces via the `!room` command (`!room` shows current, `!room model <alias>` / `!room effort <level>`, `default` clears) and in the web room-settings modal (model + effort dropdowns fed by `GET /chat/commands`'s alias table; the PATCH validates against the brain's known models + effort levels and writes `db.set_room_model_effort`). Room-global by design — in a shared room one participant's setting applies to every sender. Deep link `/chat?room=<token>` selects a room on load (`selectRoomByToken`), silently falling back for an unknown/foreign token; the optional `&task=<id>` extension jumps to a specific turn after selecting the room (`jumpToTask` → pages up to 5 older history pages to locate it, scrolls the `data-cid`-anchored row into view with a ~2s highlight pulse). **`!search` result cards**: `cmd_search` returns a structured `command_data` payload (`kind="search_results"`) alongside its plain-text body via `CommandContext.result_data` → `dispatch` → the web POST; the store renders `SearchResults.svelte` (conversation cards carry a "Jump to reply" button = `jumpToTask`; memory cards show source + preview) instead of markdown, falling back to markdown for any other/absent `data`. Talk ignores `data` and keeps the text body + deep links. The read path (`commands._search_memory`) searches the `channel:{token}` namespace + all memory source types and classifies each hit on an `is_memory` axis (conversation rows room-scoped, recovering the room from the `messages` store via `db.get_message_room_for_task` past `tasks` retention); `cmd_search` runs a strict prefix pass, scope-filters, then retries once in OR mode only if the _scoped_ result is empty (forgiveness keyed on scoped emptiness, not global BM25 emptiness). The executor recall path + skill CLI keep strict AND (no prefix / no OR fallback) via unchanged `memory.search.search` defaults. `!commands` (and the `!model <alias>` prefix) work identically across surfaces — `commands.dispatch(... surface=...)` runs the handler over a `CommandContext` and delivers via the resolved transport on a push surface (Talk) or returns the text inline on a stream surface (web → `inline_result`); per-user rate limit counts `source_type='web'` rows in `tasks`. **Command autocomplete**: typing `!` in the composer opens a live-filtered dropdown of available commands (arrow-nav, Tab/Enter to accept, Escape to dismiss); `!model ` completes model aliases via the same mechanism. Built as a reusable prefix-autocomplete primitive in `web/src/lib/components/chat/autocomplete/` (a trigger-agnostic engine + per-trigger `CompletionProvider`s — `commandProvider`, `modelAliasProvider`) fed by one cached `GET /chat/commands` endpoint (`{commands, model_aliases}` serialized from `commands.COMMANDS` + the active brain's `list_aliases()`); adding a new trigger is a new provider, not a composer change. **Composer**: one bordered pill (`Composer.svelte`) holding `+` (file picker), the field, and mic + send on the right; once the text wraps, the field takes the full width and the controls drop below it (a CSS `order` swap on a `multiline` class). Two non-obvious invariants. (1) **Wrap detection is measured at the single-row width, never the field's current width** — wrapping moves the controls out of the field's row, which widens the field, which can un-wrap the text, which flips it back; measuring the live width makes the decision depend on its own output and the field alternates one/two rows on consecutive keystrokes. `wrapsAtSingleRowWidth` pins the _wrapper's_ inline `flex-basis` for the measurement (the field is a flex item with `flex: 1`, so its own `width` is ignored for sizing), and height sizing is a separate pass after `await tick()` so it measures the width the field ends up with. `<svelte:window onresize>` re-evaluates, since the wrap point moves with the container. (2) **Control sizing is `em`-relative with `font: inherit` on the buttons** — a `<button>` does not inherit font, so without it the `em` sizes resolve against the UA's ~13px and the controls stay fixed while the text-size preference scales the type around them. Voice messages: `useRecorder.svelte.ts` wraps `getUserMedia` + `MediaRecorder` (webm/opus on Chrome/Firefox, `audio/mp4` named `.m4a` on iOS) and hands the result to the ordinary attachment upload — `executor._pre_transcribe_attachments` transcribes any audio attachment into the prompt, so this needs no dedicated endpoint (needs the `whisper` extra; `webm` is in `attachment_extensions`). The mic hides itself when `navigator.mediaDevices` is absent, which is what makes it disappear outside a secure context rather than failing on tap. Stored attachment names lead with a sanitized stem (`_attachment_stem`, `[A-Za-z0-9._-]` only, `Path.stem` drops any directory component) plus a random suffix, so the inbox is browsable without trusting a client-supplied filename. **Attachment chips are persisted, not just optimistic**: a turn's chip labels live on the canonical `messages` row (`messages.attachments`, JSON display names, written by `record_inbound` via `transport.display_attachment_names`) and are emitted on every user-row history/stream payload. They used to exist only in the composer's in-memory file list, so leaving a room and coming back silently dropped the record that a file was part of the turn. The names are duplicated off `tasks.attachments` (paths) deliberately — retention GCs the task row, while the transcript has to keep showing the file; a turn predating the column falls back to basenames of the joined task paths. The client supplies the display names (`attachment_names` on the send, positional, discarded wholesale on a count mismatch) because the _stored_ filename carries the collision suffix above — a basename-derived chip would read `note-a1b2c3d4.txt` where the live one read `note.txt`. Every other surface (Talk) falls back to the basename, which is also what gives a Talk-attached file a chip in web chat. **A chip is also a link to the file it names** (ISSUE-206), pointed at the same session-scoped `GET /chat/files?path=` handover described above — the user opening a file they already own, so nothing becomes public. A minted Nextcloud share link is the wrong tool here for the same reason it's the right one for handing a file to someone else. The link needs a _workspace_ path (`/Users/<uid>/…`) while the attachment is stored as a host path, so `transport.ingest.workspace_attachment_paths` translates once at ingest and the result rides the message row as `messages.attachment_paths` — a JSON array positional against `attachments`, stored beside the names for the same reason they are (the host paths live only on the `tasks` row retention deletes, so deriving at read time would make every link rot after a few days). A `null` entry means "not servable" and renders the inert chip it always was: a Talk attachment lives under `/Talk`, and a mountless (rclone) deployment has no local workspace at all. The read path re-scopes to **the caller's own** workspace rather than trusting the stored value, because rooms are shared — a co-member sees the chip but `/chat/files` would refuse them the file, and offering a link that 403s is worse than offering none. `POST /chat/attachments` returns `workspace_path` alongside the host `path` so the composer's optimistic chip is a working link immediately; without it the just-sent chip would stay inert for the whole session, since the optimistic row is deduped against the streamed echo rather than replaced by it. **Attachment intake.** Five entry points through one `upload()` sink in `Composer.svelte`: the `+` menu's three native rows (photo library, camera, document picker — shell 0.3.0), the plain file input off-shell, paste, drop, and the voice recorder. The server publishes its own limits at `GET /chat/config` (`max_attachment_mb`, `attachment_extensions`) and the composer pre-checks against them, **fail-open** — `limits` stays null until the config lands, so an unreachable endpoint never becomes a client-side refusal and the server's 413 is the backstop. The app default is 25 MB but the Ansible role deploys **100** and renders nginx's `client_max_body_size` from the same variable; splitting them means nginx answers its own HTML error page, which the client cannot parse (`uploadFromShell` tolerates that shape deliberately). `heic` is in the accepted set because that is what an iPhone photo is — the gallery picker usually re-encodes to JPEG, but a HEIC dragged off a Mac was being refused on extension. A native-picked file need not enter the page at all: with `IstotaUploader` present the shell posts it straight from disk with URLSession (absolute URL, `file` field), and otherwise the file is read in 3 MiB windows into a `File` backed by the WebKit blob store rather than the JS heap — which is what made the client-side ceiling removable. The temp copy is deleted on every path. A send with **no text** is accepted when attachments are present; `_describe_attachment_only_message` stores a descriptor as the prompt ("Voice message (see attached audio)." for an all-audio turn) so the transcript, the LLM context and the Talk mirror all read something. Relatedly, `_pre_transcribe_attachments` now **appends** a transcript rather than replacing the prompt — text typed alongside a voice memo used to be discarded. **Drafts** (ISSUE-205): unsent composer text survives leaving the room and leaving the page, held client-side in `localStorage` (`stores/drafts.ts`, one map under `chat.drafts`) rather than round-tripped through the server — a draft belongs to the machine it is being typed on, and publishing text the user has not decided to send is the one thing a draft is not. The page hands the composer a `draftKey`; without one the field behaves exactly as it did. The key is `<user>:room:<token>`, and both halves earn their place: the **token** rather than the room id because `web_chat_rooms.id` is `INTEGER PRIMARY KEY` **without** `AUTOINCREMENT`, so SQLite hands a freed rowid straight back out and a deleted room's draft would be inherited by whichever room takes its id next; and the **user** in front of it because a shared Talk room has one token across every member, so on a browser profile two people take turns using, a bare token would hand one person's half-written message to the other. The composer is mounted once and never keyed on the room, so before this a draft did not merely vanish on a tab switch — it also followed you into the next room; `switchDraft` writes the outgoing room's text down before restoring the incoming one's, which closes both halves at once, and clears the attachment chips on the way (they are not drafted, an uploaded file being server-side already, but re-picking one costs a tap while posting it to the wrong room does not undo). Writes are debounced (`DRAFT_SAVE_DEBOUNCE_MS`) with an immediate flush on every departure the component can see: a key change, unmount, `pagehide` (a reload or a close — the event a WKWebView delivers where `unload` is not) and `visibilitychange` → hidden, which is the **only** callback a backgrounded iOS app gets before the page may be discarded; without that one the exposure is 400ms of _idle_ rather than of typing, since continuous typing never reaches a debounce. **Two null-key cases that look identical from the prop and want opposite treatment.** Text typed before the room list answers is carried into whichever room lands, since there is no earlier room to attribute it to — but a stored draft always outranks it, or one keystroke during that window would destroy the draft the user came back for. A key going null _later_ means the room was deleted, archived or removed by another client, all of which leave the view on `room` with the composer mounted; there the field is cleared, because carrying that text is exactly the leak. The carry is therefore gated on a one-shot "has ever had a key" flag, not on the previous key being null. Bounded by a 30-day TTL (checked on read as well as on write, so an expired draft is never restored) and a 50-entry cap, because a room that is deleted or never revisited would otherwise leave its draft behind forever and nothing else collects it; writing an unchanged draft is a no-op so that merely _visiting_ a room neither re-serializes the map nor pushes its age out.

**Send lifecycle on the user's own row** (ISSUE-200). The composer appends the user turn and an assistant placeholder optimistically, then POSTs — so a message had exactly one appearance whether or not it ever reached the backend. Worse, the one failure that was handled (an HTTP error response) was written into the *assistant* placeholder, which made "your message never left" present as "the assistant errored replying", and the failure the issue actually reports took a path with no handling at all: `fetch` **rejects** rather than resolving when the backend is unreachable, so the throw escaped an un-awaited caller, `status` was never reset off `'sending'`, and the composer stayed locked in Stop mode until reload. The ack itself already existed — the endpoint returns `{task_id, status: "pending", …}` — and is unchanged; this is entirely client-side. `sendChatMessage` now **classifies instead of throwing** (`SendFailure` = `unreachable | timeout | auth | rate_limit | rejected`, plus a `SEND_TIMEOUT_MS` bound `fetch` has none of), the row carries a `sendState` lifecycle, and `failSend` **removes** the assistant placeholder rather than repurposing it — the turn produced no assistant message. Absence of `sendState` is the settled state, deliberately with no `'sent'` member: every row rebuilt from history is settled by construction, and the ack's visible form is the pending mark clearing rather than a receipt we have no read-receipt semantics to back. Four non-obvious constraints. **Retry reuses the failed row's `cid`**, because `appendStreamedRow` dedups on `(role, task_id)` — stamping the retry's new id onto the existing row is what folds the canonical echo into it, where appending a fresh row would leave the failed one behind and show two bubbles for one message. It therefore needs the original `ChatAttachment[]` stashed on the row (`sendPayload`): the rendered row holds display names and *workspace* paths, not the host paths the POST body takes. **Retry is gated on an idle status** (and its button disabled while busy) because `runTurn` is not re-entrant — it drains the single `pendingSend` echo buffer on entry, so retrying during another send would release that send's rows before its task id was stamped, and would silently reset `cancelRequested`. `send` was gated by the composer's `busy`; Retry was the first entry that wasn't. **The POST is not idempotent and carries no client id**, so a timeout (or a socket dropped after the request was processed) leaves a row marked failed whose task is really running; `appendStreamedRow` reconciles that by **adopting** an echo whose `(role, text)` matches a failed, task-less row instead of appending it — matched on the body precisely so a send the server rewrote (an attachment-only descriptor, a stripped `!model` prefix) falls through to the old duplicate rather than claiming a wrong row. **`failSend` only sets `'idle'` when its turn's room is still on screen**: switching rooms isn't gated on `busy`, so a send failing after a switch would otherwise unlock the composer over a room with a live stream. Retry is withheld where it cannot succeed — an expired session, and any other 4xx that is a verdict on the request (409 archived, 400 over-cap, 413) — mirroring the server's own transient/permanent split. Per `web/AGENTS.md`, a failed send is **in-band** and raises no `notify()`. Durability across a reload, and an offline outbox, are deliberately out of scope and belong to ISSUE-202, whose queue plugs into this same `sendState` union.

**Per-turn message actions** (ISSUE-210). One action row under each message body — copy, star, delete, left to right in ascending consequence — revealed on hover or on tap, keeping its layout box either way so revealing it never reflows the transcript. Copy takes `messageCopyText`: the turn's prose groups only, tool traces excluded, as **markdown source** rather than rendered HTML (which is why a fenced code block needs no copy button of its own). It is withheld mid-stream, because half an answer is not an answer; the star is not, because it marks the row rather than the text. **Delete is `DELETE /chat/messages/{message_id}` → `db.delete_message`** and it is _room-wide_, not per-user: the `messages` row is gone for every member, and authorization is membership (`db.is_room_member`), not authorship — the opposite of stars, which are per-user in `message_stars`. Unknown id and non-member both return **404**, deliberately indistinguishable so neither becomes an id oracle for the other (the same rule the star endpoint follows); a turn whose task is still in flight returns **409**, because the scheduler writes the assistant row at completion and the delete would silently undo itself. It is a hard delete, not a tombstone: every read path would have to learn to filter a tombstone, and the row would still occupy its slot in the `(room_token, role, task_id)` unique index, so re-running the turn would collide with a message the user believes they removed. It touches `messages` and `message_stars` only — never `task_events` or `tasks` (unlike a room delete) — and leaves `room_read_state` alone, since a read cursor is a high-water mark rather than a reference. **The `message_deletions` ledger exists because the room stream has a second cursor.** That stream tails `messages.id > cursor`, and a vanished row can carry nothing, so deletions get their own monotonic `message_deletions.id`; the `message_deleted` frame therefore carries no SSE `id:` (that cursor belongs to the message tail) and instead rides its cursor _inside_ the payload, which the client passes back as `since_deletion_id` on both `/chat/stream` and `/chat/events` — without it a reconnect after a delete silently resurrects the message. Like the message tail, the deletion cursor advances to the max id **scanned**, not the last one sent, or a client sitting behind someone else's invisible deletions never catches up and the O(1) gate stops short-circuiting. Rows are pruned after a fixed 30 days in `run_cleanup_checks` (`_MESSAGE_DELETION_RETENTION_DAYS`, deliberately not a config knob — the row is tiny and nothing about it is worth tuning). Propagation into a bound Talk room is best-effort and fire-and-forget, trying the user's own OAuth token first and the bot's second, because Talk lets only the author or a moderator delete and a mirrored user turn is authored by the _user_ while a reply is authored by the bot — so a 403 is the ordinary "not yours", not an error. A Talk failure never fails the web delete, which has already committed. Client-side the removal is **pessimistic**, unlike `toggleStar`: a row removed and then restored would reappear mid-transcript after the user watched it go.

**App shell and caching.** There is no service worker: static responses carry two cache classes — hashed `_app/immutable/` assets immutable for a year, everything else (the HTML shell, `version.json`, the manifest, icons) `no-cache` and revalidating. Sending neither let an installed home-screen app pin the shell indefinitely and then request hashed chunks the server had deleted. A new build is surfaced rather than forced: SvelteKit's version poll drives a toast with a Reload button (a tap, because a reload discards a half-typed message), re-checked on `visibilitychange` since the poll timer is throttled in a background tab and stopped in a suspended PWA. The web unit passes `--timeout-graceful-shutdown` for a related reason — `GET /chat/stream` is session-lived and exits only on client disconnect, which server shutdown does not trigger, so a restart with any browser tab open used to sit out the full stop timeout and die on SIGKILL. Docker's web service has no equivalent flag.

Knobs under `[web.chat]`. Frontend engine in `web/src/lib/stores/chat.ts` (SSE with polling fallback) + widgets in `web/src/lib/components/chat/`. **Body render model**: an assistant turn is an ordered list of `text`/`tool`/`thinking` segments (`segments.ts`); `renderGroups` reduces it to interleaved render groups — substantial prose blocks (trimmed length ≥ `SUBSTANTIAL_TEXT_CHARS`, mirrors the backend gate) render as prominent markdown in true order, consecutive tools coalesce into one `ActivityTrace` chip, short lead-in narration + reasoning are dropped, and the trailing text is always the answer. This keeps a meaty intermediate block (analysis the model wrote, then acted on) visible as its own prose block instead of vanishing when the next tool settles it — the live stream and a reloaded-from-`execution_trace` turn build the same groups. Not a Talk replacement — an in-app companion. Web chat is also a _delivery_ surface (ISSUE-121): alerts, the verbose execution log, and notifications routed to `web` are appended to a room as unsolicited system messages (distinct from task-backed turns, written into the canonical `messages` store as `role='system'` rows) and merged into room history by time. See `WebTransport` in the Transport abstraction section. **Unread indicators**: the sidebar bolds a room name and shows a count chip for rooms with unseen messages. Counts are server-computed in the `/chat/rooms` payload (`db.count_unread_messages` — `messages` past the per-user/per-surface `room_read_state` cursor, excluding `role='user'` so your own/Talk-mirrored turns don't ring your own room); `db.initialize_room_read_state` seeds a freshly-surfaced room's cursor to its current max so a backlog doesn't read as unread. Opening a room (or `POST /chat/rooms/{id}/read` → `_chat_mark_room_read`) advances the cursor to the room's newest message; the client persists on open / stream-append / stream-settle / `visibilitychange` (visibility-gated). The active room is held at 0.

**Live room-event stream** (`live-web-chat-room-stream` spec). The per-task SSE stream only ever covered a task the client itself started; everything else — a Talk-originated turn, a routed alert, an unread badge, a rename — rode `setInterval`. `GET /chat/stream` is a sibling of `chat_task_stream` that tails the canonical `messages` store instead of `task_events`, carrying **every room the user is a member of over one session-lived connection**. The seam between the two: the room stream is the "something happened" bus, the task stream stays the "here is the token-level detail" bus — a streamed `user` row whose task is still unsettled makes the client open a task stream for it, which is `pickUpNewInFlightTasks` made event-driven (and fixes the `pending_confirmation` skip, since the persisted `confirmation` event now replays). Cursor is `messages.id` alone — one monotonic integer over user turns, assistant turns and system rows — which is what closes the fast-turn hole _structurally_: a Talk turn that starts and finishes inside 200ms still writes two rows and both are tailed, so timing stops mattering. The producers are in a different process from the web server (separate systemd units / containers), so the web tier polls SQLite exactly as `events.py` prescribes; the change is _where_ the polling lives — server-side at ~1s as an indexed `id > :cursor` scan behind an O(1) `MAX(id)` gate, pushing deltas, instead of client-side at 5s refetching a 50-row page per open room. `db.list_room_events_since` shares SQL fragments with `db.list_messages_across_rooms` so the visibility predicate (membership minus dismissals minus archived) cannot fork, and rows are emitted in the **same shape the history endpoints emit** (`_cross_room_message_dict`) so `buildHistoryMessage` builds a streamed row and a reloaded row identically. Frame kinds: `message` (carries `id:`), `gap` (carries `id:`), `room` (metadata delta — rename / model / effort / added / removed; **no** `id:`), `message_deleted` (**no** `id:` — see below), and a `: ping` keepalive (**no** `id:`) — auxiliary frames must omit `id:` or EventSource's resume cursor lands in the wrong place. The **gap threshold** is split because neither side can see the other's variable: the server decides on _cost_ (`room_stream_max_batch` rows AND `room_stream_max_bytes` — a joined assistant row carries `execution_trace`, so row count alone measures the wrong thing), the client on _age_ (~60s of silence on reconnect or after a hidden tab, since a star toggled elsewhere or a Talk-synced read cursor is state the stream doesn't carry). Both converge on one recovery routine: reload rooms + the open room, then adopt the cursor — which is the server's max id **scanned**, not the last one sent, or the truncated rows are stranded. Frames landing during that reload are buffered and re-applied. The notif poller is gone; the rooms poll is demoted to a 30s metadata reconciler and **kept only because `GET /chat/rooms` drives the Talk→web read-state pull**. Aggregate views (All / Unread) and background-room previews are fed from the same frames. Knobs under `[web.chat] room_stream_*`; `GET /chat/events` is the polling-fallback snapshot; `_admin_chat_section` reports live connection count (the metric that would justify the deferred shared per-user broker).

### Unified Talk / web room sync

Talk and web chat share one surface-independent **room** model (spec in `Specs/Done/unified-talk-web-room-sync.md`). A `rooms` registry (PK = canonical `conversation_token`, `origin` talk|web) + `room_bindings` (per-surface ref) + a canonical `messages` store (role user|assistant|system, `task_id`, `origin_surface`, `external_ids`) + `room_read_state` supersede the de-facto `tasks`-as-history store; a markered one-time migration folds `web_chat_rooms`/`web_chat_messages`/distinct Talk tokens in and backfills. `get_conversation_history` reads `messages` with task-id re-pairing behind a self-healing dual-read (falls back to `tasks` until the store is caught up — a _completeness_ check: every completed turn mirrored, not just the newest, so a partial migration / mid-rollout window can't truncate history to the mirrored subset); Talk keeps its metadata-rich `_build_talk_api_context` for Talk-origin context. Inbound flows through one `transport.ingest.record_inbound` choke point (resolve canonical token → echo-check → store user turn → create task), used by `ingest_message` (Talk/email) and the web POST. The scheduler stores the assistant turn on completion via `_store_room_turn(conn, task, body)` — one general producer that mirrors **any** room-delivered bot post (subtask, scheduled, briefing, heartbeat, an email round-trip into its own web room, …) as an assistant spine row when the room exists, replacing the old per-source-type `_store_scheduled_room_turn` / `_store_web_room_turn` (canonical-room-transcript spec, ISSUE-176). Storage is universal (any web-visible room gets the row, `origin_surface` = the real source type as provenance, not a visibility gate); only conversational turns additionally carry a `user` row and gate the caught-up dual-read (`_CONVERSATIONAL_SOURCE_TYPES = ('talk','web')`, unchanged). The render filter `TRANSCRIPT_SURFACE_FILTER` is correspondingly assistant-any / user-conversational; a markered `nonconversational_transcript_cleanup_v1` migration drops the synthetic `user` rows the old `unified_rooms_v1` blanket backfill inserted for non-conversational tasks (restoring the "user rows conversational-only" invariant so non-conversational posts can't re-pair into LLM context) and normalizes backfilled briefing bodies from raw JSON to the delivered body. `output_target="room"` fans out by live bindings with an **asymmetric mirror** — web→Talk is a real push, Talk→web pushes nothing (the web loader already renders Talk turns from the shared store), and confirmations never mirror. On a web→Talk mirror leg the user's question reaches Talk one of two ways: with user-scoped OAuth enabled (see the next section) the web process already posted it _as the user_ at send time and the scheduler suppresses its repost (`db.user_turn_has_external_id(task_id, "talk")`); otherwise the bot reposts it attributed (`💬 <name> (via web):`) before its reply — a pure Talk-surface artifact never written to the canonical `messages` store, so web history/context is unaffected (`_format_mirror_user_repost`). The web room list is **membership-driven** (`db.list_member_rooms`, a `room_members` join) rather than keyed on the single-owner `rooms.user_id`, so a _shared_ room (one token, one transcript) surfaces for every participant — a group Talk room with the bot plus two humans appears in _both_ humans' web lists, each via their own `web_chat_rooms` handle (`UNIQUE(user_id, token)`, not globally unique). Membership is added by `register_room`, by every inbound sender (`record_inbound`), and by the **Talk poll itself**: on first sight the poller registers any conversation the bot participates in (`origin='talk'`, resolving the canonical token via the binding first so a _promoted_ web room isn't duplicated) and seeds membership from the human participants — mapped to istota users via the same `actor_id in config.users` + `actorType == "users"` gate as message processing, bot excluded — so a room the bot merely _lurks_ in surfaces in web chat without anyone having to message it first. This no longer depends on a `tasks` row existing for the token (the task-keyed `unified_rooms_v1` migration + the old `record_inbound`-only path left a polled-but-never-addressed room — e.g. a quiet `#sysadmin` — invisible, since its history is rebuilt from Nextcloud but its tasks were never carried over). The participant fetch (cached `_get_participants`, 5-min TTL) runs only for a genuinely new room, not every poll; DMs need no fetch (the other party comes from the conversation name). Thereafter membership for active users is kept current in the poll's message loop (any observed message from an istota user re-adds them) and by `record_inbound`. Backfilled for existing deploys by the `room_members_v1` migration. A per-user delete/hide writes a **dismissal tombstone** (`room_dismissals`, keyed `(room_token, user_id)`) _and_ drops that user's membership; `list_member_rooms` excludes a tombstoned room even while membership is later re-added, so the hide is durable. The tombstone is cleared by the user's **own** next message in the room — `record_inbound` → `undismiss_room` for an addressed message, and the poll message loop for a non-`@mention` post in a multi-user room (which never reaches `record_inbound`) — "re-engagement un-hides"; a co-member's hide is left intact. The web delete UI reflects this: an imported (Talk-origin) room is a one-click **Hide** with no type-the-name confirm, while a web-origin room keeps the destructive type-to-confirm **Delete**. The global `rooms.archived` flag stays reserved for `archive_orphaned_talk_rooms` — "the bot left the Nextcloud room", which a fresh inbound un-archives. Fixes ISSUE-134, where a group room was visible to only one arbitrary participant. Room titles are backfilled from Talk's `displayName` every poll cycle, not just on the next inbound message, so a migrated room stops showing the generic "Talk room". The same poll cycle reconciles the other direction (`db.archive_orphaned_talk_rooms`): a Talk room the bot is no longer in (deleted in Nextcloud / bot removed) is archived so it stops surfacing in web — guarded against a transient empty conversation fetch, archive-not-delete so mirror history survives. An "Also open in Talk" promote (`POST /chat/rooms/{id}/promote`) creates a real Talk conversation via new OCS `TalkClient` methods, with two-way rename propagation, and a Talk turn streams live into an open web room. Full reference in `.claude/rules/transport.md`.

### User-scoped Nextcloud OAuth (post-as-user + read sync)

Opt-in retention of the web login's OAuth pair so the web process can act as the user against Nextcloud Talk (spec in `Specs/Done/user-scoped-nextcloud-oauth-talk-sync.md`). Gate: `[web] token_storage = "encrypted"` **and** `ISTOTA_WEB_TOKEN_KEY` (≥32 chars) present — the key is delivered to the **web unit only** (Ansible `web-secrets.env`, Docker `/data/.web_token_key`), never the scheduler/webhooks units or any task env, and the module (`web_tokens.py`) uses a distinct scrypt salt + table (`web_user_tokens`: Fernet ciphertext pair + plaintext `expires_at`) so "who can decrypt" stays auditable by grep. `callback()` persists the pair at every login (self-heals a dead refresh token); `get_access_token` refreshes within 60s of expiry under a per-user lock (NC rotates refresh tokens — persistence is atomic, `invalid_grant` deletes the row, transient failures keep it); the settings page shows a status card with Disconnect (`DELETE /api/settings/nextcloud-token`); `/api/me` carries `nextcloud_token: {connected, expires_at} | null`. Three consumers, all web-process, all falling back to legacy behaviour when the gate is off or no live token exists: **(1) Post-as-user mirroring** — a web send into a Talk-bound room posts the prompt to Talk immediately as the user (`TalkClient(config, bearer_token=…)`, `referenceId = istota:webmirror:<msg_id>`), stamps the Talk id on the canonical user row, and the scheduler skips its attributed repost; echo prevention is the referenceId fast-path in the Talk poller (race-free — the marker travels in the message) plus the `record_inbound` external-ids ledger as backstop (which excludes same-origin rows so a re-polled duplicate still hits `create_task`'s dedup). Inbound Talk messages now stamp their Talk id into `messages.external_ids` at ingest. **(2) Web→Talk read push** — mark-read/read-all call `mark_conversation_read` (fire-and-forget) only when the web cursor actually advanced. **(3) Talk→web read pull** — the rooms poll, throttled per user by `[web.chat] talk_read_sync_interval` (default 60s, 0 disables), fetches the user's conversation list with their bearer token and advances the web cursor of fully-read Talk-bound rooms, capped at `db.room_max_talk_synced_message_id` so web-only system messages stay unread. Star sync is out of scope (Talk has no per-message star API).

### Transport abstraction

A uniform seam over messaging surfaces (`src/istota/transport/`). Inbound, a `Transport.poll()` normalizes a surface's messages into `IncomingMessage`; `ingest_message` maps those onto `db.create_task`. Outbound, `deliver` / `edit` push a task's result to a resolved channel; `resolve_target` picks the channel. `TransportRegistry` (`make_registry(config)`, no I/O on construction) holds the enabled surfaces and `for_task(task)` resolves the primary one by `source_type` (`email`→email, `repl`→repl, everything else→talk). Six transports ship — `TalkTransport`, `EmailTransport`, `NtfyTransport`, `IstotaFileTransport` (all `surface_class="push"`), `ReplTransport` (`surface_class="stream"` — `deliver` is a no-op; outbound is the `task_events` log a terminal tails), and `WebTransport` (`surface_class="stream"`, `user_routable=True`) — and **Matrix is the designed-for next consumer** (a new surface = one `Transport` subclass + a `make_registry` line). `WebTransport` is the web chat _delivery_ surface (ISSUE-121): an interactive `source_type="web"` task still streams its own result over `task_events` (routing short-circuits `web` to a stream destination), but the transport's `deliver()` is a real write — alerts, the verbose execution log, and any notification routed to `web` append an unsolicited system message to the user's room as a `role='system'` row in the canonical `messages` store, rendered merged into the room transcript and pushed live by the room stream. Because it's `user_routable`, web auto-appears in every routing UI that reads `registry.routable_names()`. `conversation_token` stays the opaque per-surface channel id and `source_type` the routing key — neither renamed; no DB/config change. Talk delivery/edit (the only `TalkClient` construction outside the CLI) and `notifications._send_talk` flow through `TalkTransport`; email delivery flows through `EmailTransport`; `scheduler.post_result_to_talk` / `edit_talk_message` / `post_result_to_email` are thin shims. The progress-ack subscriber is gated on `capabilities.supports_progress_ack`. Both surfaces are subpackages with both directions co-located (`__init__.py` seam + `inbound.py`; email adds `outbound.py`) and both self-create their tasks inside `poll` via the shared `ingest_message` (the `create_task` must share the inbound `db.get_db` transaction with the poll-cursor advance, or a create failure would lose messages): Talk's inbound body is `transport/talk/inbound.py` (`poll_talk_conversations`), email's is `transport/email/inbound.py` (`poll_emails`); both transports' `poll` return `[]`. Email's shared non-transport helpers live in `istota.email_support`; the low-level clients stay outside the seam (`istota.talk.TalkClient`, `istota.skills.email`). Outbound fan-out (a task delivering to several surfaces) is `transport.routing.resolve_delivery_plan`'s job: it parses `output_target` (`talk`/`email`/`ntfy`/`istota_file`/`stream`/`both`/`all`/`surface:channel`/comma lists), resolves channels, and drops unregistered/unconfigured destinations with a warning. Separately, the per-user **purpose-keyed routing table** (`UserConfig.routing`, purposes `reply`/`alert`/`log`/`briefing`/`notification`) routes _notifications_ via `notifications.send_notification(..., purpose=…)`; the `log` purpose additionally drives the verbose per-task execution log to any user-routable surface (`notifications.effective_log_destinations`, opt-in: `routing["log"]` > legacy `log_channel` > off; Talk streams live, email/ntfy get one final summary). Full reference in `.claude/rules/transport.md`.

### Task Event Streaming

One persistent, typed event stream per task feeds every output surface. The executor adapts the brain's (widened) `StreamEvent` union into `TaskEvent`s via an `EventWriter` (`events.py`), which persists them to the `task_events` table (WAL, shared scheduler ⇄ web) and notifies in-process subscribers. Event kinds: `task_started`, `tool_start`, `tool_end` (NativeBrain only — carries loop-measured `duration_ms`), `tool_progress` (NativeBrain, SSE only), `progress_text`, `text_delta` (stream surfaces only — incremental answer text coalesced by the executor at ~250ms/120char/boundary; pruned on the terminal path once the canonical `result` lands, so steady state retains zero. **Narration gate (a substance classifier):** a text run streams nothing until it crosses `scheduler.stream_text_gate_chars` (default 280) without an intervening tool call. At a tool boundary the two cases split (`executor._settle_deltas_at_tool_boundary`): a short lead-in ("Let me check…") that stayed under the gate is _dropped_ (it never streamed, so it can't flash in the answer area); a SUBSTANTIAL block that crossed the gate is _kept_ — its unflushed tail is flushed so the full block reaches the stream surface, where the web client renders it as its own prose block (analysis the model wrote, then acted on, is content — not throwaway narration). The gate is thus not an answer-vs-narration split: the final answer (after the last tool) always streams, and a short _final_ answer that never crosses the gate still arrives whole via `result`. The earlier 250ms-timer flush _raced_ the tool boundary and leaked narration permanently; the gate has no time-flush while held. Tune against the `stream_gate:` logs the executor emits per flush/discard. `0` disables the gate), `context_management`, `confirmation`, `result`, `error`, `cancelled`, `done`. Consumers: `TalkEventSubscriber` (edits the ack message in place), `LogChannelSubscriber` (accumulating edit), `PushNotificationSubscriber` (ntfy on long tasks) are in-process subscribers; the web SSE endpoint (`/istota/api/chat/tasks/{id}/stream`), the snapshot endpoint (`…/events`), and the admin endpoint (`/api/admin/tasks/{id}/events`) poll the table directly — the table is the bus, no IPC. **Retry continuity:** the event log is kept across retry-eligible failures (it is _not_ wiped). `set_task_pending_retry` leaves the rows in place, the retry branch emits a `progress_text` "⏳ Attempt failed — retrying in N min…" notice, and the next attempt's `EventWriter` resumes `seq` from `db.get_max_task_event_seq` so it stays monotonic (no UNIQUE(task_id, seq) collision) and a watching web client's resume cursor stays valid — it sees the notice and the next attempt's events instead of a silent spinner. The live view therefore accumulates across attempts (attempt 1's tools, the notice, attempt 2's tools); history reconstruction is unaffected (it reads `execution_trace`, the final attempt's). **Terminal backstop:** the SSE + snapshot endpoints (`web_app._synthetic_terminal_events`) synthesize a terminal frame from the task row — numbered above the client's cursor — whenever a task is terminal in the DB but has no `done` deliverable to that client (a crash that skipped `finish()`, or any future log-reset path). A terminal task always yields a terminal frame. `seq` is monotonic per task, assigned by the writer; events are hand-deleted only in `cleanup_old_tasks` (the `ON DELETE CASCADE` clause is decorative — `PRAGMA foreign_keys` is unset). The brain owns dispatching the executor callback off any event loop (NativeBrain's `run_in_executor` hop), keeping the synchronous subscribers' `asyncio.run` calls safe (ISSUE-111 generalized). Config under `[scheduler]`: `progress_show_tool_use`, `progress_show_text`, `event_log_enabled`, `stream_text_gate_chars`, `push_notification_threshold_seconds`, `push_notification_sources`.

### Briefings

First-class **block/source content module** (`src/istota/briefings/`, spec `Specs/Done/briefings-first-class-module.md`, Stages 1–6 shipped; 7–8 deferred). **Blocks are the sole content model** — the legacy component generator, boolean-defaults expansion (`BriefingDefaultsConfig`/`[briefing_defaults]`), TOML `components =`/`--components-json` authoring, and the executor's legacy fallback were all retired (retire-legacy-briefing-components spec). A briefing is an ordered list of **blocks** — each with a title, an optional synthesis directive, a render mode (`synthesis`/`structured`), and 1..N **sources** — gathered and synthesized into one section per block at generation time. Source kinds (`sources/*`): `rss` (a Feeds subscription/category, soft-degrades when Feeds is off), `email` (shared-pool newsletters, windowed, owner-filtered, fail-closed without the framework DB), `browse` (a bundled preset or arbitrary URL frontpage via the browser skill), `markets`, `calendar`, `todos`, `reminders`, `notes`. The `todos`/`reminders`/`notes` sources read a file whose `path` (a source `config` property; no default — blank reads nothing) resolves **relative to the user's own `/Users/<uid>/` folder** (`sources.builtins._resolve_user_path`), so `shared/…` reaches a bot-shared file and `istota/…` the bot workspace; a path already rooted at the user's own folder passes through, `..` segments are stripped, and a path naming another user resolves under the caller's own folder (never a cross-user read). The web editor offers a **server-side-filtered** file autocomplete (`GET /briefings/path-suggest?q=` — the query walks the workspace so a deep/late file still surfaces as the user types, not a fixed on-load pool) via the reusable `ui/AutocompleteInput` component, and shows an **advisory** existence hint (`GET /briefings/path-check`, debounced): it never blocks the save, since the resolver is fail-soft (a missing file contributes a provenance note), so a not-yet-created or transiently-unreachable path can't trap the editor. Gathering is **concurrent** (bounded thread pool, each worker on its own framework connection — SQLite conns aren't thread-safe) and **fail-soft** — a down/unknown source contributes a provenance note, never raises, never kills the briefing (`resolve_source` backstop); per-block output order is deterministic (reassembled by slot, not completion). Blocks/sources/archive live in a per-user SQLite module DB on **local disk** (`Config.module_db_path(user, "briefings")`, WAL); user-facing workspace stays on the mount. Gated by `Config.is_module_enabled(user, "briefings")` (`briefings` in `MODULE_NAMES`); own web tab (reader landing page + archive) and a block/source **+ schedule/delivery** settings editor. Each archived result in the reader sidebar carries a kebab → **Delete** (shared `ConfirmDialog`) that hits `DELETE /api/briefings/archive/{id}` → `db.delete_archived` (single-row, 404 on a missing id) — a user-driven prune alongside the age-based `archive_retention_days` sweep; the sidebar removes the row optimistically and re-points the reader to a neighbour. Content is managed via `istota briefings blocks|sources|archive …` (operator, `cli_briefings.py`), the `briefings` skill facade (`BRIEFINGS_USER`, `untrusted_input` companion, error-envelope exit contract), or the web settings page; **scheduling + delivery stay framework-owned** (cron in user TZ, real `briefing_configs.output` column, `enabled=0` mutes; provision via `istota briefings schedule ensure` or the web UI). **Deterministic titles**: a briefing's title is composed by `briefings.generate.resolve_briefing_title` from its configured `briefing_configs.title` (blank → `default_briefing_title` humanizes the _name_, so `morning` → "Morning Briefing") plus the run date in the user's timezone, appended by the renderer ("Morning Briefing — Monday, 27 July"). `scheduler.briefing_title_for_task` dates it from the task's `created_at` (the cron fire) and is called independently by all three consumers — archive `subject`, email subject, ntfy title — so a pure function of `(task, config)` keeps them identical without plumbing a value between them. The model no longer supplies a title: the envelope is `{"body": …}` (the `subject` key is dropped from both the prompt and `skills/briefing/skill.md`, though `parse_briefing_json` still tolerates one from an in-flight run — it is ignored). Previously the archive stored the model's free-styled `subject` (emoji, dates, a summary clause — different every run) while email discarded it and re-derived "Morning Briefing"/"Evening Briefing" by regex-scraping the _prompt_, keyed on the clock (`resolved.hour < 12`) rather than the briefing's name — so an "evening" briefing firing at 11am mailed as "Morning Briefing" and the two surfaces disagreed about the same run. That regex survives as `transport/email/outbound._legacy_briefing_subject`, reached only when no caller title is supplied. Editable via `istota briefings schedule ensure --title`, `[[users.X.briefings]] title` / `[[default_briefings]] title` TOML (Ansible `istota_default_briefings`), and the briefings-settings **Schedule** card, whose rows gained an edit affordance (the POST was already an idempotent upsert keyed on `name`, so an edit is a save with the name held fixed — the table had been add/delete only). At generation the executor's deferred-prompt path (`build_deferred_briefing_prompt` → `_build_module_briefing_prompt`) is the only path — `ensure_initialised` runs the one-time components→blocks migration first, then `assemble_briefing_input`; a briefing with no blocks after migration returns `None` → the task fails with the existing quiet retry (no legacy render). Generation runs on the ISSUE-143 **deferred-prompt worker** (source fetch never touches the dispatch thread); on completion the scheduler archives the delivered briefing and prunes by `[briefings] archive_retention_days` (default 90). Legacy component-based briefings migrate once into blocks/sources **per briefing** (`_migrate.py`, sentinel `migrated_from_components:<name>` — `blocks_from_components` is kept **only** as this one-time migration; `_migrate._migrate_components` prefers a briefing's config `blocks` over the components translation). **Config-authored rich blocks** (config-authored-rich-briefing-blocks spec): an operator authors the full block/source shape in `[[users.X.briefings.blocks]]` + `[[...blocks.sources]]` TOML (per-block `title`/`directive`/`render_mode`/`options` + 1..N sources of any `kind` with arbitrary `config`), seeded once via the per-briefing sentinel, then the briefing is an ordinary editable per-user briefing (operator re-runs never re-clobber). `blocks` is an **in-memory-only `Config` field** (never stored in `briefing_configs`): parsed by `_parse_briefing_specs`, threaded through `_apply_user_briefings` (re-attached to the DB-shadowed entry by name) + `get_briefings_for_user`. **Default briefings**: a canonical shared set defined once in top-level `[[default_briefings]]` config (Ansible `istota_default_briefings`) is seeded by name into each opted-in user (per-user `default_briefings` flag, default on; user's own briefing wins) in `_apply_user_briefings` — seed-once + edit-preservation fall out of `import_from_user_configs` + the block sentinel for free. The Ansible path renders content-only `[[users.X.briefings]]` stubs (`istota_briefing_blocks_toml` filter) and the `[[default_briefings]]` section (`istota_default_briefings_toml` filter); schedule/delivery flow through `istota briefings schedule ensure` + `istota user ensure --default-briefings/--no-default-briefings`. The `briefing` skill (singular) is the output-formatting guideline selected on `source_types:[briefing]` and returns `{body}` JSON; the `briefings` skill (plural) is the content-management CLI facade. **Shared curated content** (shared-kv-curated-briefing-content spec): a cross-user **`shared_kv`** table (namespaced JSON, open reads / admin-only writes via the fail-closed `Config.is_shared_kv_writer` — _not_ `is_admin`'s empty-means-all) is the substrate for content that's identical across users. One consuming source kind: `shared_block` (`{name, max_age_hours}` → namespace `briefing_shared_blocks`, key `name`; trust taken from the stored value, not the consumer). The writer picks granularity by value shape — `{"items":[…]}` (share the fetch → per-user synthesis) vs `{"text":…}` (share the synthesis → verbatim splice into a `structured` block); freshness-gated (stale/missing → omitted, fail-soft) and untrusted-wrapped unless `trusted:true`. Writes reach `shared_kv` three ways, all converging on the gate: sandboxed skill (`istota-skill kv set --shared`, deferred `scope:"shared"` op gated on `task.user_id` at apply time in `_process_deferred_kv_ops`), direct skill/CLI (`istota kv set --shared`), all admin-only; set-ops reject `--shared`. **Module-owned shared blocks** (batteries-included): top-level `[[briefing_shared_blocks]]` config (`BriefingSharedBlock`; canonical `world-headlines`/`markets-summary` seeded via `DEFAULT_SHARED_BLOCKS` when unset; Ansible `istota_briefing_shared_blocks`) are one-block briefings generated **once globally** under the reserved `__system__` identity — `scheduler.check_shared_blocks` (cron in the operator-configured shared-block timezone `[briefings] shared_block_timezone` / Ansible `istota_briefing_shared_tz`, default UTC; `cron_max_staleness_minutes`-gated, off-dispatch worker thread) runs `briefings.shared_blocks.run_shared_block` (user-agnostic gather over `browse`/`markets`/`email` only — `rss` + personal built-ins dropped; section-only synthesis via the general-alias Brain) and does a **trusted daemon** `db.shared_kv_set(..., written_by="__system__")` (no `is_shared_kv_writer` gate — the module writing its own content isn't a user task), stamping `briefing_shared_block_state.last_run_at`; an all-empty gather skips the write (last-known-good). The seeded default morning briefing reads `world-headlines` via a `shared_block` source, so the N-way frontpage fetch + synthesis collapses to one generation. Escape hatch for arbitrary content: an admin CRON `command:` job writing `shared_kv` directly (`scripts/examples/shared_kv_curation.sh`). **Admin-editable shared blocks** (admin-shared-briefing-blocks spec): shared-block definitions are DB-backed and admin-manageable, not config-only. A `shared_block_configs` framework table (CRUD in `db.py`, `SharedBlockConfigRow`) is seeded once from `DEFAULT_SHARED_BLOCKS`/`[[briefing_shared_blocks]]` (`shared_blocks_store.import_from_config`) and DB-wins thereafter (`config._apply_shared_blocks` overlay — same seed-once + edit-preservation contract as `default_briefings`), so `check_shared_blocks` reads DB-authoritative definitions. Managed via admin-gated web routes on the briefings router (`GET/PUT/DELETE /shared-blocks` + `POST /shared-blocks/{name}/run` behind `require_admin` = `Config.is_shared_kv_writer`, fail-closed; validates cron/`render_mode`/slug + source kind ∈ `ALLOWED_SHARED_SOURCE_KINDS` in `briefings.models`) and the `istota briefings shared list|ensure|remove|run` CLI. The briefings-settings web page renders an admin-only "Shared blocks" card (reusing the extracted `SourceConfigFields.svelte`, shared with the per-user editor) and any user gets a **Shared block** per-user source kind picking from `GET /shared-block-options`. **Verbatim structured generation**: `render_mode="structured"` now **skips the synthesis brain entirely** (`run_shared_block` → `_assemble_verbatim`, concatenating gathered source text in slot order) — self-formatting data (the markets quote table) is stored verbatim with zero LLM passes; `markets-summary` flipped to structured + `trusted`. The stored value carries a `trusted` flag; the read side (`sources/kv.py`) honors the **stored value's** `trusted` for the `briefing_shared_blocks` namespace (a consuming user can never flip it) and a live `shared_kv` key with no definition row is a valid custom-published block, not "unknown". **`publish_shared_kv` job attribute**: a scheduled job can publish its result text into `shared_kv` on success (`scheduled_jobs.publish_shared_kv` = `"<ns>/<key>"` or bare key → `briefing_shared_blocks`; `publish_shared_kv_trusted`; `cron_loader` parse/round-trip). `process_one_task`'s success path calls `_publish_result_to_shared_kv` — a gated post-success write in the `_process_deferred_*` genre (NOT an `output_target` surface): the identity is always `task.user_id`, gated on `is_shared_kv_writer`; an unauthorized/failed publish is **fail-loud** (ERROR + operator alert + job-failure increment that the success reset withholds), an empty result is a clean skip (last-known-good). This lets an admin's agentic deep-browse prompt (full sandbox + tools) publish its digest for every user to read, keeping the built-in generator tool-less under `__system__`. **Newsletter article links + HTML briefing email** (briefing-newsletter-links-html-email spec): the two halves of "a cited story should be clickable". _Input_ — the `email` source used to flatten newsletter HTML with `skills/briefing._strip_html`, whose blanket tag strip deletes every `<a href>` and keeps only the anchor text, so a newsletter story could never be cited to its own article the way an RSS item (structured `url`) can. `briefings/sources/_html.html_to_markdown` does the same flattening but rewrites each surviving anchor as **inline** `[anchor](url)` (inline, not a trailing reference block, because the story↔link adjacency is what lets the model pick the _right_ article). Newsletters are link soup, so extraction is aggressively filtered: text-less anchors dropped whole, non-`http(s)` dropped, unsubscribe / view-in-browser / preferences / social-share dropped by URL **and** by anchor label (a tracking-wrapped unsubscribe hides the keyword in an opaque redirect, but its label doesn't), duplicates collapsed, and a `[briefings] newsletter_max_links_per_source` cap (default 20, 0 = unlimited) so link soup can't flood the prompt — a filtered or over-cap anchor keeps its text and loses only the destination. Redirect unwrapping is a **conservative** allowlist (`?url=`/`?u=`/`?redirect=`/`?target=`/…) that fires only when the param holds an absolute `http(s)` URL, so `?u=<user-id>` and an opaque `/click/<hash>` are kept rather than mangled — a working tracked link still lands on the article. `bleach` (the `feeds` extra) is preferred for the parse, with a regex fallback that still preserves links, so the feature never depends on the extra. Non-obvious invariant: each emitted link is spliced in **after** the flattening pass via a control-char placeholder, because that pass ends in `html.unescape` and `&copy`/`&reg` are valid entities without a semicolon — an already-decoded URL inserted before it would silently lose part of its query. _Output_ — `skills/briefing.render_briefing_html` renders the skill's constrained markdown subset (links, bold/italic, single-level bullets, `---`, paragraphs; a stray `## ` marker dropped as `strip_markdown` already does) to bare HTML, and `skills/email.send_email`/`reply_to_email` take an `html_body` that makes the send `multipart/alternative` (plain fallback + HTML). `transport/email/outbound._briefing_email_bodies` is the single decision point mapping `(task, body, format)` → `(plain, html_body, content_type)` for all three send sites. **No styling at all** — no `style` attributes, no `<head>`/`<style>`, just a bare `<html><body>` shell so each mail client's own default typography renders (a test asserts this against regression). Escaping happens _first_ and only `http`/`https`/`mailto` reach an `href`, so newsletter-derived `<script>` or a quote inside a URL can never become markup; emphasis is applied by walking link matches rather than one `re.sub`, so an underscored URL can't sprout an `<em>` inside its own `href`. Both halves are fail-soft: a render/parse failure returns empty / falls back to the old tag-strip and the briefing still delivers as plain text. Per-user opt-out `user_profiles.briefing_email_html` (default on) via `istota user ensure --no-briefing-email-html`, Ansible `briefing_email_html: false`, or the briefings-settings **Email delivery** card; off is byte-identical to the pre-feature single-part plain delivery. The toggle lives on `/briefings/settings` rather than the `/settings` Preferences card because it governs only how a briefing reaches the inbox — which put the first page-level (non-per-record) edit on that page, so it registers with the `useSettingsSave` app-bar Save and the briefings layout gained a `HeaderSave` in its `tools` snippet (the feeds-settings pattern). The per-record source/shared-block forms there keep their own buttons, unchanged.

### GPS Location

Overland webhook → `webhook_receiver.py`. Asymmetric place detection (hysteresis on entry, continuous away on exit). Reconciler re-derives closed visits. Discovered clusters dismissable. Per-user `location.db` on **local disk** at `Config.module_db_path(user, "location")` (default `{db_path.parent}/modules/{user}/location.db`; moved off the FUSE mount so it runs WAL — see "Module DB storage" below) holds `location_pings`, `places`, `visits`, `location_state`, `dismissed_clusters` — module package at `src/istota/location/` with `resolve_for_user(user_id, config) -> LocationContext` (mirrors `feeds` / `money`). Skill CLI subcommands and web routes that need reverse-geocoding open a second connection to framework `istota.db` for the global `geocode_cache` / `reverse_geocode_cache` tables (cross-user Nominatim dedup); `location.db.with_geocode_conn(framework_db_path)` is the dual-conn entry point. One-time framework→per-user migrator at `python -m istota.location._migrate`, gated in Ansible by a `location_pings`-presence check.

**Ping identity + replay.** `location_pings.client_id` (schema v3) is a per-point UUID the native client mints; a partial unique index (`WHERE client_id IS NOT NULL`) plus `INSERT OR IGNORE` makes a re-sent batch idempotent, so stock Overland and the Garmin importer — which send none — never collide. An empty-string `client_id` is coerced to NULL, since an empty string is a valid unique key and would collapse a device's whole history onto its first point. Dedup short-circuits **before** `_update_state_machine`, not merely before the row write: every ping at the current place increments the open visit's `ping_count`, which the reconciler and walk-by filter read, so a replay would inflate a visit that never grew. `insert_ping` returns `0` rather than a rowid on an ignored insert (`lastrowid` still holds the previous successful one, so it is not a substitute). The index is created in `_migrate_schema`, never `SCHEMA_SQL` — `init_db` runs `executescript` first, so on a v2 DB it would index a column the `ALTER TABLE` has not added yet.

**Provisioning.** `POST /api/settings/secrets/overland/ingest_token/generate` mints a token and returns it **once** — the only endpoint that puts a secret in a response body, because a token nobody sees cannot reach a phone. It refuses (503) when `ISTOTA_SECRET_KEY` is missing, and (409) when the location module is off for the user (the receiver builds no token map for them, so the token would be refused on first use) and when `[site] hostname` is unset (the assembled URL would be relative, which the QR decoder rejects for not being https; only reachable in no-auth mode, since Nextcloud auth already 403s a blank hostname at the origin check). Both checks run before minting, so a refusal never rotates a working token. `/location/settings` renders the token as a QR carrying a JSON envelope (`web/src/lib/location/provisioning.ts`) — deliberately not the webhook URL, which every generic scanner including iOS Camera would offer to _open_, putting the token in browser history. A write to the `overland`/`ingest_token` secret stamps a sentinel beside `istota.db` (`istota.location.ingest_signal`) that the receiver `os.stat`s once per ingest request, since the two run in different processes. `reload_config` reads the stamp _before_ loading secrets, so a token written mid-reload is not marked already-loaded, and concurrent threads claim the new stamp under a lock so one rebuild serves them all. Stamping is best-effort — a failure degrades to restart-only — and **`istota secret ensure` does not stamp at all**, so a CLI-provisioned token applies on the receiver's next restart or SIGHUP.

**Per-device tracker settings** live on the device and nowhere else — one account can have two phones, so a server-side setting would have them overwriting each other's row. The shell-gated "This device" card (`web/src/lib/components/location/DeviceTrackerCard.svelte`) talks to the `IstotaLocation` plugin through `web/src/lib/platform/nativeLocation.ts`, the capability facade (see `web/AGENTS.md` and the native-shell spec); in a browser it renders one stand-in line rather than nothing, so an absent section reads as deliberate. Both ingest sources — Overland and the shell's own tracker — post to `/webhooks/location`, authenticated per-user by the ingest token as a `?token=` query parameter (Overland) or an `Authorization: Bearer` header (the tracker); missing is 401, unknown 403. Exposed: on/off, profile (Detailed / Places), permission + a route into iOS Settings, tracking state, queue depth / last sent / last error, send now, rescan. Send interval and batch size are deliberately not exposed — the interval follows the profile. The Tracking row reads **Paused** (`--status-info-fg`, information rather than warning) when `TrackerStatus.paused` is set, with Stop still available because tracking is still armed — iOS keeps `tracking` true throughout a pause, so `paused` is not the inverse of it. The field is optional rather than version-gated: a shell older than 0.8.0 omits the key, and "absent reads as false" is exactly that shell's behaviour. A permission problem outranks a pause in the card's single warning slot — a pause resolves itself, while a missing authorization is why nothing is being logged at all, and showing both lands neither. The whole point of the card is making "is my tracker alive?" trustworthy, and "On" beside an empty queue and an hours-old last-sent is what a silently dead tracker looks like.

**Under `istota serve`** the receiver is not a separate process: `_maybe_mount_webhooks` _includes_ `webhook_receiver.location_router` into the web app and registers `reload_config` as a startup handler, so the endpoint is `/webhooks/location` on the **web** port and `webhooks_port` is unused. Mounting it as a sub-app instead produced `/webhooks/webhooks/location` and, worse, never ran the sub-app's lifespan — so the token map stayed empty and every correctly-tokened request 403'd. That shape has no SIGHUP handler, so the sentinel is its only reload path.

### Feeds

Native RSS/Atom/Tumblr/Are.na (`src/istota/feeds/`), per-user SQLite, no Miniflux. **Are.na runs on the v3 API**: `content`/`description` arrive as `{markdown, html, plain}`, so real HTML is rendered instead of v2's HTML-escaped markdown, and `image.src` is already the original. Block ids are identical across v2 and v3, so `guid` stayed stable and the switch re-inserted nothing. Six block types have typed builders (`Text`, `Image`, `Link`, `Embed`, `Attachment`, `Channel`) over a generic fallback, so a type Are.na adds later still renders; a builder that raises degrades to the safe generic rather than failing the poll, and `_ensure_renderable` guarantees no blank card. An `Embed` sets `feed_entries.embed_url` and an `Attachment` sets `file_url` — the provider's own `embed.html` iframe is deliberately discarded rather than allowing `<iframe>` through the shared sanitizer, so the web side resolves a player URL from a **host allowlist** (YouTube / `youtube-nocookie` / Vimeo, ids re-validated) and both the card and the reader use the same three helpers. **Inline `<video>` is allowed but bounded.** The tag was always through the sanitizer; what it now keeps is `loop` and `muted` alongside `src`/`controls`/`poster`/`preload`/`playsinline`. `autoplay` stays out — a grid of cards all playing on scroll is not the same request as playing one — and so do `width`/`height`, since a stored width is what made a clip run off the side of a card; both surfaces bound video with CSS the way they already bounded `<img>`. Stripping `autoplay` alone would have stored a tag nothing could start (a GIF-as-mp4 is authored as an autoplaying muted loop with _no_ controls, precisely so it doesn't look like a player), so `_ensure_video_controls` runs as a post-pass on both sanitize branches and injects `controls` when absent — after sanitisation, so it only ever sees tags the allowlist already passed and escaped `&lt;video&gt;` in prose stays text. The reader's Images toggle hides inline video along with pictures: it already hid the embed hero, so leaving a clip drawn made the chip mean "some of the media". **A poll refreshes an entry it already holds** rather than discarding it, so a provider fix reaches entries already on file; user state (`status`, `starred`, `starred_at`) and `fetched_at` are never overwritten, and a field is only overwritten by a non-empty value, so a sparser re-fetch cannot blank a title. The "N new" count still means newly inserted. **Repeat-image suppression** (`image_dedupe.py`) is a display-time decision, never a row mutation: an image is suppressed on the older of two entries carrying the same identity key within a look-back window (`feeds_settings.image_dedupe_window_days`, default 14, `0` = off, distinct from unset), so the newest carrier always keeps the tile and re-surfacing after the window renders again. The key is `netloc + path` with query/CDN signature ignored, plus a Tumblr rule dropping the shard and `/sWxH/` size segment. Scoped to the slice the reader is showing (feed / category / starred), deliberately **not** by read state.

### Health

Body stats, bloodwork panels, biomarker trends, medical history (encounters + diagnoses), immunization tracking, and Garmin Connect integration. On by default; per-user opt-out via `disabled_modules`. Per-user SQLite on **local disk** at `Config.module_db_path(user, "health")` (moved off the FUSE mount for WAL — see "Module DB storage") with stats, panels, biomarkers, biomarker_explainers, biomarker_refs, encounters, diagnoses, diagnosis_encounters, immunizations, immunization_refs, documents, document_links, profile, display settings; user-facing uploads (source PDFs) stay in the workspace on the mount. All measurements stored metric (kg, cm, °C, mmHg, bpm); display layer converts to the user's preferred units. Module package at `src/istota/health/` with `models`, `db`, `units`, `routes`, `workspace`, `_loader`, `_migrate`, `ocr`, `explainer`, `garmin_sync`, `documents`. Bundled `biomarker_refs.json` seeds 60+ canonical markers with sex-specific reference ranges, alias lists, and one-paragraph clinical descriptions; Istota's canonical ranges drive flagging (lab-printed ranges are preserved per-row but not the flagging source). Blood-pressure / resting-HR biomarker rows fan out to `stats` so the unified time series picks them up. Bundled `immunization_refs.json` seeds 19 adult-relevant vaccine schedules; `immunization_explainers.json` provides static clinical detail per vaccine.

OCR pipeline (`ocr.py`): PDF via `pdftotext`/`pypdf` with `pdftoppm` + Tesseract fallback; image via Tesseract. Extracted text plus the canonical marker list goes to the active brain (general role alias) which returns structured JSON; values >10× outside the widest canonical range surface as a likely-OCR-error warning. Optional deps degrade gracefully.

Biomarker explainer (`explainer.py`): out-of-range marker pages display an educational alert generated by the active brain. Hard guardrails in the prompt (never diagnose, never prescribe, always hedge, JSON-only output); strict response parsing rejects malformed output and falls back to a fixed safe payload so the UI never shows raw model output. Cached per-user per `(name, direction)` in `biomarker_explainers`; fallback responses are NOT cached so later brain availability still produces real content.

Surfaces: FastAPI router at `/istota/api/health/*` (stats CRUD + series + latest; panels CRUD + upload + extract + source streaming; biomarker trend + summary + canonical refs + matrix endpoint + cached explainer; CSV import/export at `/csv/import` (multipart, `on_collision=skip|replace|append`) and `/csv/export` (text/csv stream of confirmed panels in the same layout); encounters CRUD + history summary; diagnoses CRUD + resolve; immunizations CRUD + refs + coverage + parse + bulk + explainer; Garmin status/connect/mfa/sync/disconnect; profile / display settings; dashboard aggregator). SvelteKit pages under `/health/*` — `/stats` (netdata-style grid with sparklines), `/bloodwork` (dates-as-rows × markers-as-columns spreadsheet with category bands and flag-colored cells, plus Import/Export CSV controls), `/bloodwork/panel?id=…` (panel detail + inline-edit table + source preview), `/bloodwork/upload` (drag-and-drop OCR review-and-confirm), `/bloodwork/marker?name=…` (trend chart with out-of-range zones shaded, related-marker chips, clinical description, history table, LLM explainer card), `/health/history` (timeline + conditions list), `/health/history/encounter?id=…` (per-encounter detail), `/health/history/diagnoses` (diagnoses list, with per-condition document modal), `/health/history/import` (encounter import from paperwork), `/health/immunizations` (coverage strip + quick-log), `/health/immunizations/paste` (parser preview), `/health/immunizations/detail` (per-record edit), `/health/immunizations/vaccine` (drill-down + explainer), `/health/immunizations/import` (paste-text + screenshot/PDF upload), `/health/settings` (DOB/height/sex + display preferences + Garmin connect/disconnect). The two formerly-dynamic routes use query params because `adapter-static` can't crawl runtime-only ids (commit 629c2ac).

**Conditions across encounters** (`SCHEMA_VERSION` 4): a condition is seen at as many appointments as it is seen at, so `diagnoses` ↔ `encounters` is a many-to-many over `diagnosis_encounters` (`PRIMARY KEY (diagnosis_id, encounter_id)`). Unlike `document_links` — polymorphic, so it can carry no FK — both columns here point at exactly one table and carry **real** foreign keys with `ON DELETE CASCADE`, which every caller gets because `connect()` sets `PRAGMA foreign_keys = ON`; deleting either end clears the links without a hand-written sweep. `diagnoses.encounter_id` survives as a legacy scalar: still written by `insert_diagnosis` for an old reader, read by nothing current. `_migrate_diagnosis_encounters` is a **backfill only** (the table itself comes from `CREATE TABLE IF NOT EXISTS`), gated on the stored `schema_meta.version < 4` rather than on the join table being empty — the legacy column is deliberately not cleared, so an emptiness gate would resurrect links the user had removed on every subsequent start. The bug that motivated it: `insert_diagnosis(..., reconcile=True)` correctly recognised a repeated condition as one condition and then **returned early**, so an import naming the same condition at three appointments kept only the first — the condition vanished from the later visits and those visits vanished from its history. It now adds a link on the reconciled row. `PUT /diagnoses/{id}` takes `encounter_ids` as a **full replace** (empty list clears) and it wins over the legacy scalar; `POST /diagnoses/{id}/encounters` and `DELETE /diagnoses/{id}/encounters/{eid}` are the single-link verbs, with re-linking a no-op success. `GET /diagnoses` carries `encounter_ids` per row via one chunked `encounter_ids_for_diagnoses` query, so the list costs no N+1. Agent-side the verbs are `link-encounter` / `unlink-encounter` (the `@ref` grammar resolves an encounter created earlier in the same sandboxed batch); sandboxed they defer `link_diagnosis_encounter` / `unlink_diagnosis_encounter`. Web-side the encounter page lists its conditions with an unlink kebab (worded, and styled, as non-destructive — the condition is kept), the conditions list edits the whole set as chips, and the encounter-create form stages conditions and links them after the insert, degrading to a non-fatal warning if a link fails so a saved encounter is never reported as lost.

**Documents** (health-document-attachments spec): the paperwork behind a record. Three import paths used to OCR a PDF and delete it — `/encounters/extract` said so in its own docstring — so a referral letter that produced three encounters and two diagnoses was unrecoverable the moment extraction returned, and an immunization row was an unevidenced claim (proof of immunization is a document people are actually asked to produce, not merely a fact to recall). Two tables in the per-user health DB: `documents` (one row per blob — sanitized `filename`, `mime`, `byte_size`, `content_hash`, `stored_path`, `ocr_text`, `source` ∈ manual|import|agent) and `document_links`, a **polymorphic** `(document_id, entity_type, entity_id)` join over `encounter | diagnosis | immunization` (`db.DOCUMENT_ENTITY_TYPES`, validated in every function that takes one). Many-to-many from the first import, because one PDF routinely produces several encounters _and_ several diagnoses, and a hand-added diagnosis with `encounter_id NULL` must still carry its own paperwork. Panels are deliberately **not** an entity type: they keep `panels.source_file` and `/panels/{id}/source` unchanged rather than eat a live-DB path-rewriting migration for no user-visible gain. `entity_id` carries no FK (it points at one of three tables), so an entity delete clears its links by hand inside `delete_encounter` / `delete_diagnosis` / `delete_immunization`. Both tables are new, so `CREATE TABLE IF NOT EXISTS` inside `executescript(SCHEMA_SQL)` covers an existing DB and no migration function exists — stated in a code comment so its absence doesn't read as an oversight.

Bytes live at `{uploads_dir}/documents/{id}/{stored_name}` — under the same `uploads_dir` root the panel-source route already guards, so one containment rule (`relative_to(uploads_dir)`) covers both, and the tree stays inside the Nextcloud-synced workspace where the user can see and back up their own paperwork. `stored_name` is the _sanitized original_ filename rather than a UUID or `original.bin`, since that workspace is user-facing; the numbered parent directory makes collisions structurally impossible, so sanitisation (`documents.sanitize_document_filename`: `Path(...).name`, then `[^A-Za-z0-9._-]` → `_`, collapse runs, strip leading dots, 100-char stem, `document.bin` fallback) doesn't have to guarantee uniqueness. `store_document` inserts the row _before_ writing the bytes, so a crash between them leaves a row pointing at a missing file (a 404 the readers already handle) rather than an unreferenced invisible blob, and writes via a `.part` sibling + `os.replace` so a torn write is never visible under the final name. `content_hash` (sha256) is UNIQUE and dedups: uploading identical bytes **reuses the row and adds a link** — attaching one discharge summary to both the encounter and the condition it produced is the normal case and should cost one file — with the `IntegrityError` from a concurrent racer resolving to the same outcome. `store_document` writes the bytes _before_ the caller commits (no caller commits mid-function), so the sweep has to reclaim in both directions.

`sweep_orphan_documents` therefore runs two passes and rides `_migrate.ensure_initialised`, collecting abandoned import uploads without a new scheduler job. The **row pass** deletes linkless documents whose `last_touched_at` is older than 24h — _not_ `created_at`, which was the first version and destroyed any document older than the window the instant its last link went, i.e. exactly the detach-then-reattach-elsewhere correction the delay exists to protect. `last_touched_at` is stamped on create, link, unlink, and on a dedup hit (`db.touch_document`), so a month-old discharge summary detached on its way to another encounter gets a fresh window, and a re-uploaded old scan survives its own review screen (dedup returns the existing row, keeping its original `created_at`, so a sweep would otherwise have deleted the id `/bulk` was about to link — failing the import _and_ losing the file). An abandoned upload is still collected: nothing touches it after the insert. The **directory pass** removes `{uploads_dir}/documents/<id>/` directories with no row, mtime-gated on the same window (a document being written right now legitimately has a directory and no committed row yet) — without it a rollback after `store_document` returns strands a blob that no DB-driven enumeration could ever reach. `store_document` also clears its target directory first, since AUTOINCREMENT hands an id back after a rollback and the leftover would otherwise share the directory with the live document and block the `rmdir` on delete.

A dedup hit additionally **heals missing bytes**: if the matched row's file is gone (a manual workspace edit, a failed sync), the bytes are rewritten. Without that, re-uploading the identical file was a silent no-op — the hash matched, the broken row came back, and the document stayed 404 forever while the upload reported success.

Routes on the existing router: `POST /documents` (multipart, optional `entity_type`/`entity_id`), `GET /documents` (all, or scoped to one record), `GET /documents/{id}` (+ resolved link labels), `GET /documents/{id}/file`, `POST /documents/{id}/links`, `DELETE /documents/{id}/links/{type}/{id}`, `DELETE /documents/{id}`. `_document_to_dict` never emits `stored_path` — the client gets a `url` to stream from. The file route always sets `Content-Disposition: attachment` + `nosniff`, **unlike** `/panels/{id}/source`, which serves inline: a document can be an email attachment the agent filed, i.e. content from outside the trust boundary, and attacker-supplied HTML/SVG served inline on the app's own origin would execute against the session cookie (the same reasoning recorded for web chat's `GET /chat/files`). `<iframe>`/`<img>` render PDFs and images regardless. MIME resolves declared → `mimetypes.guess_type(filename)` → magic-byte sniff (`_sniff_mime`; a saved email attachment routinely has no extension, and refusing a good scan for want of a `.pdf` is a poor answer), then is allowlisted (`_ALLOWED_DOCUMENT_MIMES` — PDF, JPEG/PNG/HEIC/HEIF/WebP/TIFF, plain text → 415 otherwise) and size-capped by `[health] max_document_bytes` (default 25 MiB, `0` = unlimited; Ansible `istota_health_max_document_bytes`) → 413. The three detail GETs gained `documents`; the three list GETs gained `document_count` per row via `document_counts_for_entities` (one chunked query, so a paperclip badge costs no N+1).

Import flow: `/encounters/extract` and `/immunizations/extract` now **keep** the upload (`source="import"`, `ocr_text` carried) and return `document_id`; the review screen passes it to `/bulk`, which links it to every row it creates. A storage failure still returns the extracted rows with `document_id: null` and a warning — losing the file is bad, losing both is worse. An unknown `document_id` is a 400 checked _before_ any insert, so a bad id can't leave half an import behind.

Agent access: `attach-document` / `detach-document` / `documents` / `document` on the `health` skill, with a `TYPE:ID` grammar (`_parse_entity_ref`; `encounter:@NAME` also resolves an encounter created earlier in the same sandboxed batch, mirroring `add-panel --ref`). Sandboxed they defer `attach_document` / `detach_document` ops that `_process_deferred_health_ops` replays. **Every writer validates the target exists first** (`db.entity_exists`, which the web route's `_entity_exists` also delegates to): `entity_id` is polymorphic with no FK, so a link to a record that isn't there leaves a document invisible on every page _and_ permanently exempt from the orphan sweep — it does have a link — so `attach_document` raises `UnknownEntity` before writing a byte. The op file is written inside the sandbox, so its `source_path` is untrusted text and the daemon — which is _not_ sandboxed — confines it to the task's deferred dir or the user's base workspace `{mount}/Users/{uid}`. `_resolved_source_path` resolves symlinks and hands back the approved path, and the read uses _that_: resolving twice would leave a window in which a symlink under the workspace is swapped between the check and the read. `register_upload` goes through the same guard (it had none). Both agent paths also read the operator's `max_document_bytes` (`_health_max_document_bytes` / the skill's `_document_max_bytes`) rather than falling through to the library default, so `0` = unlimited applies to an agent-filed document too. The base dir, not merely the bot subdir, because the driving case is an email attachment the executor dropped in `inbox/`. `skill.md`'s "Filing paperwork" section tells the model to attach to the most specific record a document evidences (the immunization, not merely the visit) and that it files files _the user supplied_ — it does not go looking through the workspace for medical documents. Deletion stays a web-UI action: an irreversible destructive action on medical records should need a human click.

Web UI: `DocumentList` / `DocumentCard` in `web/src/lib/components/health/` (3-across card grid with a dashed drop zone as the last cell; kebab with Open / Detach / Delete, both behind `ConfirmDialog`, and the delete confirmation names how many _other_ records it would strip the file from). A Documents section on the encounter page, "Proof of immunization" on the immunization detail page, and — since conditions have no detail page — a paperclip badge plus a kebab entry opening a `Modal` on the conditions list.

CSV import/export (`src/istota/health/csv_io.py`): 3-row header (category banner + `Marker (unit)` headers + reference range) followed by `date, lab, value…` data rows. Aliases (`Hgb` → Hemoglobin, `LDL-C` → LDL, `Na` → Sodium, `D3 Total` → Vitamin_D, etc.) resolve via `biomarker_refs`; unknown markers store under the printed name and land in the matrix's "Other" category. Imported panels are written confirmed (`draft=0`) and the BP/HR fan-out to stats mirrors the OCR confirm flow.

SvelteKit (`web/`, `adapter-static`, base `/istota`) + FastAPI (`web_app.py`). **Admin pane** (ISSUE-203). `/admin` is a sidebar section — **Status** (the dashboard above), **Configuration**, **Logs** — with the `AppShell`/`ShellHeader` in `routes/admin/+layout.svelte` and each section a sub-route. Logs is the payload that justified the frame; Configuration is read-only for now and shaped so it can become the config editor without the nav changing.

**Logs** (`admin_logs.py`, `GET /admin/logs/sources` · `/admin/logs/{source}` · `/admin/logs/{source}/stream`). Two sources and deliberately no more: `app` — the `[logging] file` plus its `RotatingFileHandler` siblings, read as one stream newest-first (on a stock server deploy `output = "both"`, so this _is_ the scheduler/poller/brain output) — and `tasks`, the `task_logs` table. Per-task execution traces are excluded: they already have a reader at `/admin/tasks/{id}/events`, and the JSONL session store under `~/.claude/projects/` is not path-scoped to anything this module could confine.

The security posture is three properties. Every route is `_require_admin`, which fails closed on a blank `/etc/istota/admins` (unlike `Config.is_admin`'s permissive empty rule). **A request names a source id, never a path** — the only place a path is derived is `resolve_app_log_chain`, which symlink-resolves every candidate and confines it to the log directory, so traversal is not a reachable class of bug. And records are returned as JSON data rendered into text nodes; nothing treats log content as markup. Cross-user exposure is real and intended — `task_logs` embeds truncated task results — so every record carries its `user_id` and the source is filterable by user; clicking a `task N` cell filters to that task.

Reads are byte-bounded in both directions. Paging scans **backward in windows** so the last screenful of a 200 MB log costs a few hundred KB, with a scan cap so a filter matching nothing can't walk the archive (`truncated` says the budget was spent, distinct from `next_before === null` = nothing older). Two non-obvious invariants: a window always ends on a **record** boundary, not merely a line boundary, or a multi-line traceback is split and its tail lines are discarded as leading orphans by the next read; and the live tail grows its window rather than returning an unchanged cursor when it finds no boundary, since a cursor that doesn't advance leaves the tail silent forever while the UI still says "Live". Rotation is detected by the file **shrinking** below the cursor and reported as `reset` so the client clears rather than appends. Timestamps are **labelled, not converted** (the file source is server-local, `task_logs` is UTC) — shifting them into the viewer's zone makes a line un-greppable against the file it came from.

The SSE tail polls (the writer is the scheduler process, so there's no in-process bus) at a deliberately human cadence, and carries its cursor **inside the payload with no SSE `id:`** — a file cursor is `name:offset`, not an integer, so `Last-Event-ID` resume would hand back a value the client must reconcile with a `reset` anyway. The client therefore handles reconnects itself, re-opening from the cursor it has actually reached: the browser's own retry re-requests the URL as built, i.e. from the seed cursor, replaying everything since. Because two paths legitimately redeliver a record (that reconnect, and a record re-read once its continuation lines arrive), `lib/admin/logRecords.mergeRecords` is keyed on cursor and **replaces** rather than appends — the transcript is a keyed `{#each}` and Svelte throws on a duplicate key in production, so an append-only merge would turn a network blip into a blank page. The server's own failure frame is named `stream_error`, not `error`, because a frame named `error` lands on EventSource's built-in connection-error listener and is discarded unread.

**Configuration** (`admin_config_view.py`, `GET /admin/config`). The loaded `Config` walked into ordered sections of typed fields, each carrying a dotted `key`, a `type` and a `secret` flag — field-level rather than a TOML dump so the same payload can back an editable form later. Redaction is the whole safety story: a credential is emitted `value: null` with `set: true|false`. Matching is by field name against `SECRET_NAME_PATTERNS` (hyphens folded, so an HTTP header name matches too), with `_ALWAYS_SECRET_KEYS` for a field whose *contents* are credentials though its name isn't (`brain.native.extra_headers`, which `llm/openai_compat.py` merges over the `Authorization` header) and a dotted-key `NON_SECRET_KEYS` allowlist for the operational settings the patterns catch on a substring (`web.token_storage`, `brain.native.max_tokens`, `brain.tmux.bypass_*_marker`, …). A name-pattern rule is only as good as its coverage, so the tests assert coverage by **value**: a sentinel is stuffed into every credential-shaped leaf of a real `Config` and must not appear in the payload. The earlier name-shaped version of that test re-applied the implementation's own predicate to its own output and could not fail — which is how the `extra_headers` leak shipped past it.

**Native iOS shell.** The web app also runs inside a Capacitor WKWebView pointed at the deployment URL (its own repo, `istota-mobile`; the URL is the only build-time coupling). `web/src/lib/platform/` is the facade, and it holds two rules: every export degrades to plain-web behaviour off the shell, and every shell-dependent capability is gated on the shell version that introduced it — the web deploys in minutes while the binary lags a TestFlight cycle, so an older app must get a page that says what it cannot do rather than a control that silently fails. **Detection is the `IstotaApp/<version>` user-agent token, not `window.Capacitor`**: the UA is present on the first request, survives SSR, and carries a version the injected bridge does not, and a page can carry a `Capacitor` shim without being in the shell at all — so a plugin object's presence is not evidence of the shell. Route every call through a single accessor checking both gate and plugin, or the two diverge: six of eight tracker calls shipped gated on the plugin alone. Capabilities: keyboard geometry (0.2.0), pickers (0.3.0), upload-from-disk (presence-detected), the location tracker (0.6.0) and the QR scanner (0.7.0) — the last two gated separately so a 0.6.0 app tracks but says it cannot scan. Where a capability's _shape_ changed rather than its existence, feature-detect the response instead of spending a version.

**Viewport and the keyboard.** `lib/viewport.ts` publishes `--app-height` and `--kb-height`; body height is `calc(var(--app-height, 100dvh) - var(--kb-height, 0px))`. `--app-height` is written **only in standalone** — in a browser tab `innerHeight` is the layout viewport and does not track a collapsing toolbar, which is what `dvh` was adopted for — and it exists because an iOS 26 WebKit bug leaves the visual viewport short after a keyboard dismissal, with `dvh` following it down. The published height is the **tallest viewport seen** and short readings are never published: a keyboard can only shrink a viewport, so a smaller reading is never evidence of how tall the app should be, and holding a slightly-too-tall height briefly beats a band nothing corrects. The single path that adopts a smaller baseline is a shrink outlasting the whole settle window with nothing focused — a split view, not a keyboard. The keyboard gate takes focus as the signal and overrules a focused field only when **both** viewports are back within tolerance; requiring both is what makes it right on either platform, since an installed app resizes the layout viewport and a browser tab only the visual one, and testing one turned an intermittent gap into a permanent one. `--kb-height` bypasses the settle machinery entirely — it comes from the shell's `keyboardWillShow`, at the start of the animation rather than after it. `?vpdebug=1` prints the shell version and live geometry on-device, which is the only way to see a gate with no height behind it without a rebuild.

**Client-local preferences** — theme (`lib/stores/theme.ts`) and text scale (`lib/stores/fontSize.ts`) are localStorage-persisted per browser, not profile fields: they must apply before first paint, and profile data arrives after it. Both follow the same shape — a `writable` seeded from `loadSetting`, a normalizer that folds any unrecognized value onto the default, an `apply*` that sets an attribute on `<html>` (`data-theme` / `data-font-size`), and a matching branch in the single blocking `<script>` in `app.html` (the anti-FOUC pre-paint pass; add to that script, don't add a second one). Text scale is `small` (the historical unscaled size — no CSS rule, so the browser's own base size stands) | `medium` (110%, **default**) | `large` (120%), applied as a **root** `font-size` percentage in `app.css`. Percentages rather than px so a user who raised their browser font size keeps that gain at every level. Note the normalizer inverts the usual shape — it matches `small`/`large` and falls through to `medium` — so an unrecognized stored value lands on the default while `small` stays explicitly selectable; the `app.html` pre-paint branch must mirror it or the two disagree for one frame. Root-scaling is deliberate: the `--text-*` tokens and nearly all spacing are `rem`, so type and the space around it grow together and the layout keeps its proportions — scaling only the type tokens would grow text inside fixed padding. Sizes fixed in `px` (borders, the health SVG chart labels) don't scale by design. Surfaced in the **Appearance** card on `/settings`, which sits outside the `{#if profile}` block and applies on change (no Save) — keep client-local controls out of the profile cards, whose fields need the shared Save button.

Frontend primitives in `web/src/lib/components/ui/` (AppShell, ShellHeader, Sidebar, Chip, Badge, Button, IconButton, Select, Input, TextArea, Field, Modal, ConfirmDialog, etc.); shared settings primitives in `web/src/lib/components/settings/` (`SecretField`, `ServiceCard`, `HeaderSave`). **A settings page has one Save, and it lives in the app bar** (`HeaderSave` + the `useSettingsSave` registry in `stores/settingsSave.svelte.ts`). Once `/settings` and `/admin` grew their own `AppShell`, the `ShellHeader` `tools` slot became a place a page-level action could live, and the per-card buttons stopped being the only option: `/settings` had been carrying three copies of the same-looking button (Identity and Preferences both edit the profile; Karakeep edits a secret), and a fourth card would have added a fourth. The registry **aggregates contributors rather than replacing them** — that is the whole design, because a page's edits genuinely span several endpoints (the profile PUT, one secret PUT per `ServiceCard` field), and one button has to drive them all while asking only the parts holding edits. It also means `ServiceCard` registers itself and owns no button, so `/money/settings` and `/location/settings` get a working Save from their cards alone with no page-level code. Contributors are keyed by a per-call-site `Symbol`, so teardown order between an outgoing and incoming page is irrelevant, and a `null` return withdraws (a page whose module is off, an OAuth card with no fields). Two layout constraints, both about not moving a target the user is aiming at: `HeaderSave` renders **before** the section's cog so the cog keeps the bar's right edge, and the "Unsaved changes" badge is always in the layout at `visibility: hidden` when clean — `.header-tools` is right-aligned, so a badge that materialized as you typed would shove everything left of it sideways mid-edit. Per-record forms keep their own buttons (briefings' "save this source", money's entity/service modals), and clearing a secret stays immediate and separately confirmed: a deletion is not an edit awaiting a Save. The money layout's ledger picker is suppressed on `/money/settings` for the same crowding reason — nothing there is ledger-scoped. **`SettingsField` supplementary text is three-slotted by whether the user must see it**: `hint` is optional guidance and renders in a `HintPopover` behind a "?" beside the label (it used to render inline under the input, where a long hint stretched the field grid); `warning` (`--status-warn-fg`) and `error` (`--status-danger-fg`) stay inline, because a hover popover is _discoverable_, not seen. That distinction is load-bearing: the money forms' legacy-value notices ("this client is never invoiced automatically", "it bills as hours") had been passed as `hint` for want of a slot, and converting them wholesale would have hidden a data-integrity warning behind a hover. `HintPopover` (`ui/HintPopover.svelte`) is a bits-ui **`Popover`** with `openOnHover`, not a `Tooltip` — bits-ui tooltips are hover/focus-only by design, which would leave every hint unreachable on a phone. Its trigger is rendered through the `child` snippet as a `<span role="button">` rather than the default `<button>`: `SettingsField` wraps its label text _and_ its control in one `<label>`, and a `<button>` is a labelable element, so a button trigger preceding the input in tree order would become the label's control and clicking the field name would focus the "?" instead of the input. The trigger's own click handler `preventDefault`s (the click would otherwise also activate the enclosing label) and re-invokes the spread handler it shadows. **Mobile sidebar disclosure**: below 768px a `Sidebar` is an overlay drawer opened by `SidebarToggle`, which belongs in `ShellHeader`'s `leading` slot (before the title — Material's navigation-icon slot); pages that want a second hit target pass `ShellHeader`'s `onTitleClick`/`titleActionLabel` so the title drives the same toggle. Two constraints hold it together: its layout box is `1.5rem` tall to match the title's line box, so adding it can never make the bar taller, and the touch target is an out-of-flow `::before` overlay (~44×48) that costs no layout height. Sole exception is `money/transactions`, whose drawer belongs to a sub-route while the app bar is owned by `money/+layout.svelte` — it sits at the leading edge of `.money-section-tools` instead. This replaced a `position: fixed` tab pinned to the viewport's left edge: tethered to no layout landmark, it had to be conspicuous to be findable, and so competed with the content it floated over. The money section's list pages (work, invoices, clients, transactions) are one **record-table shell** — `:global(.money-toolbar)` / `.money-notice-bar` / `.money-table` / `.money-table-header` / `.money-table-row` / `.money-sortable` / `.money-status` / `.money-amount` / `.money-kebab-spacer` / `.money-table-empty`, defined once in `routes/money/+layout.svelte` beside the existing `.money-section-*` globals, with a `--tree` modifier on the row for the denser accounts and report trees. The three report pages share a second shell, `.report-frame` in `routes/money/reports/+layout.svelte` — deliberately _not_ `.money-*`-prefixed, since the `stray-money-global` lint rule reserves that prefix for the layout above. Each had declared `:global(.section-toggle)` byte-identically, and a `:global()` in a route file leaks app-wide, so which copy was in effect came down to stylesheet order. A page styles only its own columns (widths, alignment). They had been four private copies that drifted apart on the inline edge (toolbar at 1rem, rows at 1.25rem, section nav at 0.75rem, so no two left edges on a page matched); the shell fixes them all at **0.75rem**, with rows carrying the inline padding themselves so a hover fill spans the full width. Two invariants worth keeping: a status chip needs a `min-width` (set per page — the label set differs) or its variable width shifts every column after it per row, and `.money-toolbar` carries a `min-height` so a bar holding only a result count is the same height as one holding filters. Destructive/irreversible actions use one shared `ConfirmDialog` (bits-ui `Dialog` over `Modal`): imperative title + full "Are you sure…" body, a red-outline `danger` `Button` variant for the confirm, and an optional `challenge` (type-the-name) gate for hard deletes. No native `window.confirm` or hand-rolled `.modal-backdrop` confirms remain.

**The design language is enforced, not merely documented** (`web/scripts/design-lint.mjs`, rules in `design-lint-rules.mjs` with their own tests). Nine rules: a colour literal in any notation, a `var()` naming a token nothing defines (two rules, split by whether a fallback is written — a bare one is invalid at computed-value time and _inherits_, which is how seven `<h1>`s shipped at body-text size), a spacing value off the `--space-*` ramp, a redefined primitive class, a per-page theme override, a native `confirm`/`alert`, a deep import past the `ui/` barrel, and a `:global(.money-*)` written outside the money layout. Three token _scales_ back them and are asserted in `web/src/lib/styles/tokens.test.ts` rather than merely written down: the `--space-*` ramp, an ordered `--z-*` ladder (which replaced six components all sitting on a tied `z-index: 100` and settling their order by stylesheet accident), and `--control-height-{sm,md}` — `Button`, `Chip` and the `Select` trigger each used to compute their own box and landed on four answers, so a `Select` beside a `Button` sat ~2.6px short _by an amount that changed with the text-scale setting_. The same test holds theme parity, so a token added to one theme block only now fails there instead of shipping a dark fill onto white. One global `:focus-visible` ring at 2px (the WCAG 2.2 floor) replaced twenty disagreeing rules, two of which rang in a colour that could never resolve. The rules are tested because a lint whose regex quietly stops matching reports a clean tree: for a long time the colour rule matched hex only, so 87 literals written as `rgba()`/`hsla()` were invisible — and an `accept="image/*"` attribute opened a block comment that never closed, exempting four whole files from every rule. `--accent` is the primary-action fill (`Button`'s `primary`); `--accent-blue` is the interactive accent for tabs, focus rings and cross-references, **not** primary buttons — health carried a second `.btn` system that believed otherwise, which is how `primary` came to mean two opposite things. Health has no `.btn`, `.msg` or `.badge` of its own any more; its page shell (`.card`, `.table-scroll`, `table.grid`) lives in `routes/health/+layout.svelte` the way money's does in its own layout.

**Semantic colors** — every recurring meaning-bearing color is a token in `app.css`, each defined in **both** the `:root` and `:root[data-theme='light']` blocks, so nothing built on them needs a per-page light override. Six roles:

- `--status-{danger,warn,success,info}-{fg,bg}` — severity. `-fg` is a bare status label, `-bg` a filled chip's fill (pairs with the same `-fg`). Covers error/warn/info messages, status chips and badges, severity scales, danger buttons and delete links. `--status-critical-{bg,fg}` sits above danger for a value that is not merely out of range but clinically critical, and inverts the pattern — a solid saturated fill, so its `-fg` is the text laid _on_ `-bg`.
- `--status-dot-{ok,bad,warn,info}` — the admin dashboard's live-status dots. Deliberately off the `-fg` tint scale and deliberately **one value in both themes**: a dot is a 8px disc carrying no text, so it needs saturation a tint can't give it, and a theme-tracking dot reads as two different states rather than one.
- `--accent` — the primary-action fill, which `Button`'s `primary` variant uses. Normative: health's forked `.btn` outlined `primary` in `--accent-blue` instead, and shipping both would have made `primary` mean two opposite things.
- `--accent-blue` — the _interactive_ blue: active tabs, focus rings, in-app cross-references — **not** primary buttons. Distinct from `--status-info-fg`: it marks something actionable, not a severity.
- `--accent-amber` (+ `--accent-amber-fill{,-hover,-fg}`) — the bot's identity accent, also the "starred" color; the `-fill` trio is the filled-button form of it.
- `--money-{income,expense}` — signed-amount direction. Deliberately off the status scale: an expense is not an error and income is not a success, even though the hues rhyme.

`--link` is the one decision point for content-link color: chat, the briefings reader and the feeds reader had each styled links locally, so briefing links were not visibly links and feed links were grey and permanently underlined. A surface joins by putting `prose` on its container — **not** by writing a local `a` rule. Hover is the underline only, since the color already marks the link and changing both makes the hover read as a state change.

The anti-pattern these replace: hardcode a dark-theme hex, then hand-write a `:global(:root[data-theme='light'])` rule beside it. Doing that per page is how the app accumulated ~10 different reds for one meaning and how several chips ended up with no light rule at all, rendering dark-theme fills on white. **Reach for a token rather than a new hex**; if a genuinely new meaning appears, add a token pair to both theme blocks instead of a local override.

Deliberately **not** tokenized: (a) categorical palettes, where the hue encodes a _kind_ rather than a severity — the health encounter-type badges (nine tuned hues with their own light block), the admin `SOURCE_COLOR` constants, the location activity/speed palettes; collapsing them would erase the distinction they carry; (b) data-viz — MapLibre paint specs, Chart.js datasets; (c) fixed-surface colors (lightbox chrome, avatar fills). The purple `series_incomplete` status _was_ in that list and is not any more: it turned out to be one meaning carried on two pages, each with its own light override, so it became `--status-partial-{bg,fg}` — a pair beside the severity scale rather than on it, since ranking "part-done" against "overdue" would say something false. The raw neutral greys that were open (`#555`/`#666`/`#888`/`#aaa`) are closed too: they are now the definitions of `--border-hover` / `--text-dim` / `--text-muted`, each with a light counterpart, and every remaining literal in the tree is a MapLibre paint spec, a `chartTheme` value or a `!important` override of vendor markup — all three already-documented exemptions.

Settings split (modules refactor, Phase 2): `GET /settings/services` returns only Connected services (`karakeep`, `google_workspace`); module-owned services (`monarch`, `feeds.tumblr_api_key`, `overland.ingest_token`) live on the per-module settings page and are reachable via `GET /settings/module-services/{module}`. Both endpoints share `_build_service_card`. `GET /settings/modules` returns the module registry plus per-user `disabled_modules` so the Preferences card can render the opt-out multiselect. Secret PUT/DELETE accept any service in `_all_known_services()` (connected ∪ module). Each per-module page calls `getModuleServices(<module>)` first; when `module_enabled=false`, it shows a "Module disabled — enable in /settings → Preferences" banner instead of the configuration UI. `/location/settings` adds an `/location/settings-info` endpoint that returns the webhook-URL placeholder (`https://<host>/webhooks/location?token=<token>`) and read-only place-detection knobs.

### Module DB storage (local disk + WAL)

The framework `istota.db` and the four per-user module DBs (feeds/health/location/money) all run **WAL on local disk**. Rationale + the stall they fixed:

- **Framework `get_db`**: WAL is set once in `init_db`, never re-issued per open (re-issuing `PRAGMA journal_mode=WAL` takes a write lock that races sibling readers — the dispatch-loop stall root cause). `get_db` sets `synchronous=NORMAL` per open and accepts `busy_timeout_ms=` for the main loop's read-only scans (a lock past the budget → skip the tick instead of blocking 30s and tripping the watchdog; knob `scheduler.main_loop_read_timeout_ms`, default 2000).
- **Module DBs**: previously forced onto `journal_mode=DELETE` because WAL's mmap'd `-shm` SIGBUSes on the rclone FUSE mount (ISSUE-157) — DELETE gave zero reader/writer concurrency, so a per-minute reader could serialize the whole dispatch loop (ISSUE-156). They now live on local disk at `Config.module_db_path(user, module)` (default `{db_path.parent}/modules/{user}/{module}.db`; explicit `module_data_dir` is refused under `nextcloud_mount_path`) and run WAL. **Only the `.db` moved** — user-facing workspace files (health uploads, money ledgers, feeds exports) stay on the mount via each loader's unchanged `data_dir`.
- **Migration**: `python -m istota.db_relocate` (idempotent; copies each on-mount DB → local, `init_db` flips DELETE→WAL, `quick_check`, archives old as `*.migrated-<ts>`). Ansible runs it once with services stopped, gated on a `find` for legacy on-mount `*.db`.
- **Durability**: local DBs left the Nextcloud-synced workspaces, so `db_backup.backup_databases` snapshots them (SQLite online-backup API, consistent live copy) to `{mount}/istota-db-backups/<YYYY-MM-DD>/…` on a timer (`scheduler.db_backup_*`, default daily). Each run writes its own **dated** dir (not a single overwritten slot), retention keeps the `db_backup_retention` newest dirs (default 7) but never prunes a dir holding the newest _good_ copy of a DB, and a **collapse guard** (reusing `db_relocate._data_row_count`) quarantines a snapshot as `*.suspect` when a DB that previously held data comes back empty/unreadable — the same empty-shadow signal that protects relocation (exact-zero only: framework `tasks` legitimately shrinks under retention cleanup, so no fractional guard). The scheduler fires a `purpose="alert"` operator notification on any errored/suspect DB and on backup **staleness** (persisted last-run older than 2× the interval → backups silently stopped); both sends are bounded (run on a short-lived thread with a join timeout) so a wedged Talk can't stall the dispatch loop. Backup tree is `0700`/files `0600`. **Mount-liveness guard**: a mount-derived destination is written only when `os.path.ismount` is true — if the rclone FUSE mount is down, the run is skipped (never writes to local disk under a stale mountpoint) and the last-run clock is left stale so the staleness alert fires; an explicit `db_backup_dir` is trusted without the ismount check. The persisted clock advances **only when ≥1 DB snapshotted OK**, so an all-error run can't suppress the staleness net. Force an immediate backup with `python -m istota.db_backup` (ignores the interval — used right after a deploy to close the first-run gap). Restore via `db_restore` (`python -m istota.db_restore --all`), which copies the newest good cold copy back, clears stale `-wal`/`-shm` sidecars, and refuses to run while the scheduler daemon holds its flock (a copy over a live WAL DB would corrupt it); `init_db` re-flips WAL on next start. `db_health`'s `quick_check`+`REINDEX` sweep is kept as a backstop but the FUSE-corruption class it existed for is largely gone. **Both the sweep and the snapshot run off the dispatch thread** (`scheduler._spawn_background_check`, ISSUE-144 Tier 1): each goes on a short-lived daemon thread, skipped while a prior run is still in flight, so a slow sweep or a degraded mount can't starve `pool.dispatch()` — and neither needs the `LoopWatchdog.suspended()` muzzle any more. Tier 2 put the nightly sleep cycles on the same mechanism (`scheduler._run_sleep_cycles`), so no known-long check runs on the loop thread and no `suspended()` call site remains — the watchdog covers the whole loop.

### Local single-user install (standalone shape)

A second, first-class deployment shape alongside the server/Ansible/Docker one: a slimmed-down local install a single person runs on their own machine (spec in `Specs/Done/local-single-user-install.md`, docs in `docs/getting-started/local-install.md`). No Nextcloud, no server, no bwrap, no auth. Mostly config — the `use_mount=True` branch is already plain POSIX I/O, so pointing `nextcloud_mount_path` at a local dir (default `~/.istota`) lights up the whole workspace layout on local disk; `talk.enabled=false` drops Talk; sandbox/proxies are independently guarded and no-op cleanly. The genuinely new code:

- **No-auth web mode** — `[web] auth = "nextcloud" | "none"` (default `"nextcloud"`; env `ISTOTA_WEB_AUTH`). In `"none"` mode `web_app._require_api_auth` early-returns a fixed local-user dict (the single configured user, `Config.local_user_id`), `_user_is_web_admin` is True for that user, and `_verify_origin` is a no-op — all gated on `_no_auth_mode()`, an in-function flag check (not `dependency_overrides`) so it survives SIGHUP reloads. `_resolve_session_secret` generates a random per-process key in no-auth mode instead of crashing import. **Loopback guard**: `assert_no_auth_bind_safe(auth, host)` refuses to serve no-auth on a non-loopback bind (structural, not just documented). The frontend never redirects to `/login` because `/api/me` always 200s.
- **`istota serve`** (`serve.py` + `cli.cmd_serve`) — combined launcher: runs `scheduler.run_daemon(config, install_signal_handlers=False, ready_event=…)` on a worker thread (signal handlers are main-thread-only) and uvicorn on the main thread in one process, so web-chat `source_type="web"` tasks flow through the normal worker pool. `scheduler.request_shutdown()` sets the shared `_shutdown_requested` flag; `run_daemon` now clears it at start, sets `ready_event` before the loop, and raises `_DaemonAlreadyRunning` (instead of `return`) on flock contention so `serve` reports "already running" (the standalone `main()` catches it → clean exit). `bootstrap_checks` fails with a "run `istota setup` first" error when the DB/user is missing. `serve` sources `~/.config/istota/istota.env` (non-clobbering) before config load and sets `ISTOTA_CONFIG_PATH` so the web app's own `load_config()` (in its lifespan) sees a `-c` path. The daemon lock path is the module constant `scheduler.DAEMON_LOCK_PATH` (overridable in tests).
- **`istota setup`** (`setup_wizard.py` + `cli.cmd_setup`) — interactive first-run wizard: workspace, brain detection (`shutil.which("claude")` → offer the subscription backend, else collect an OpenAI-compatible base_url/model/key), user identity, port, and a grouped module-enablement block (location → money → email). Money is on by default (server parity); opting out writes `disabled_modules` to both the TOML block and the profile row (the row is what `is_module_enabled` reads first). Writes `~/.config/istota/config.toml` + a `0600` sibling `istota.env`, inits the DB, upserts the user profile, seeds the workspace via the shared `storage.ensure_workspace_for_user`. Idempotent; `--force` overwrites, `--yes` non-interactive (`--no-money` opts out of money in a `--yes` run). The wizard's renderers are pure functions and I/O is injected (`input_fn`/`which_fn`) for testing.
- **Standalone admin notice** — `Config.is_standalone` (blank `nextcloud.url` + `web.auth == "none"`) drives a `runtime: {mode, caveats}` block on `GET /api/admin/stats` (`web_app._admin_runtime_section`); caveats are **derived from what's actually disabled** (security caveat always present in standalone), and the SvelteKit admin page renders a collapsible banner when `runtime.mode == "standalone"`.
- **CalDAV decoupling** — new optional `[caldav] url/username/password` override the NC-derived `caldav_*` properties, so a local user can point calendar at any external CalDAV server; off unless configured.
- **Packaging** — `local` extras = web+feeds+calendar+email+markets (`install.sh --standalone` installs `istota[local,money,location]`, adding those two modules' deps on top); the release build (`scripts/build-web-static.sh`) copies `web/build` → `src/istota/web_static` (gitignored, `artifacts`-forced into the wheel), and `web_app._pick_static_dir` falls back to the packaged dir when the repo-relative `web/build` is absent. `schema.sql` lives at the repo root (outside the package dir) but `db.init_db` needs it at runtime, so it is `force-include`d into the wheel as `istota/schema.sql`; `db._resolve_schema_path()` prefers that packaged copy and falls back to the source-tree `<repo>/schema.sql`, so a non-editable `uv tool install` works with no checkout.
- **Bare-port redirect** — the whole UI lives under `/istota` (the base is baked into the SvelteKit build and, on the server, nginx routes `/istota/` → web). A standalone/direct-uvicorn run has no nginx, so `web_app._root_redirect` (`@app.get("/")`) 307-redirects `/` → `/istota/` and `serve` prints the bare-port URL. On the server nginx owns `/` (→ Nextcloud), so this app-level handler is only reached on direct access.
- **`install.sh` mode prompt** — run with no flag, `install.sh` asks Server vs Standalone (`--bare`/`--docker`/`--standalone` skip the prompt; a non-interactive run keeps the historical `--bare` default). `run_standalone` refuses root, ensures `uv`, installs from the local checkout (cloning first when curl-piped — to a **durable** `${XDG_DATA_HOME:-$HOME/.local/share}/istota/src`, not `/tmp`, so `istota update` can re-fetch it), best-effort builds the web assets when `npm` is present, runs `istota setup`, then writes install provenance (`write_install_record`).
- **`istota update`** (`updater.py` + `cli.cmd_update`) — self-update for the standalone shape only (`Config.is_standalone`; refuses on a server deploy so it can't contend with the Ansible auto-update cron). Provenance lives in `~/.config/istota/install.json` (`{method, source, extras, ref, channel}`), written by `install.sh`. **Update channel** (`--channel stable|main`, persisted back to install.json so it sticks): `stable` (the default for fresh installs — install.sh writes it) tracks the newest `v*` release tag; `main` tracks the recorded branch `ref` tip. A record predating the field falls back to `main` so an existing main-tip install is never silently `git reset --hard`-ed _backwards_ onto an older release tag (existing users opt into stable with one `--channel stable`); a checkout on a non-`main` feature branch installs as `main` (track that branch). Checkout method: dirty-gate (`git status --porcelain --untracked-files=no`; refuse unless `--force`) → resolve target per channel (stable: `git fetch origin --tags` → newest `v*` by `--sort=-version:refname`; main: `git fetch origin <ref>` → **`FETCH_HEAD`**, robust on a shallow single-branch clone where the remote-tracking ref isn't reliably updated) → compare HEAD vs target → no-op if equal → `git reset --hard <tag|FETCH_HEAD>` → rebuild web assets → `uv tool install --force --reinstall "<source>[<extras>]"` → migrations. Migrations shell out to the **freshly-installed** `istota init` (not the stale in-process `db.init_db` — nothing on the daemon/serve/web startup path runs framework migrations). On an install/migrate failure the checkout is rolled back to the pre-update commit so a retry re-detects the update instead of falsely reporting "already up to date". Every external effect (git/uv/web-build/migrate/daemon-flock probe) is injected for testing. `method="pypi"` is reserved (points at `uv tool upgrade`) but not yet implemented.
- **Security logging** — the "sandbox disabled" startup WARNING is softened to an INFO with intended-single-user-posture wording when `config.is_standalone`, still visible; the dev-only WARNING stays for a non-standalone sandbox-off config.
- **Storage-agnostic vocabulary** — a local session used to describe files as a "Nextcloud mount" even when the workspace is a plain local folder. The storage I/O was already backend-agnostic (the `use_mount` branch is plain POSIX), so this is purely prompt/skill _vocabulary_: `config.storage_backend` / `storage_label` (keyed on `bool(nextcloud.url)`, **not** `is_standalone`) drive a three-mode file-access block in the executor and storage-neutral skill bodies that reference paths via `{workspace}` / `{storage}` placeholders. Local mode adds a bullet clarifying the workspace is the _managed_ area, not the limit of what an unsandboxed local bot can read. Server/Nextcloud prompts are byte-unchanged. Spec in `Specs/Done/storage-agnostic-vocabulary.md`.

Nothing here changes the server/Ansible/Docker path: every field defaults to the server behaviour (`auth="nextcloud"`, `[caldav]` blank, `is_standalone` False).

### Security

- **Sandbox** (`bwrap`): per-user filesystem isolation. Linux + bubblewrap is the only supported deployment.
- **Network proxy**: `--unshare-net` + CONNECT proxy on Unix socket; allowlist of `host:port`. No MITM.
- **Skill proxy**: strips secret env vars from Claude; CLI calls go through Unix socket that injects credentials server-side. Authorization decoupled from skill selection.
- **Native WebFetch tool**: the native harness ships a daemon-side `WebFetch` tool (`session/tools/web_fetch.py`, native-only, `[brain.native.web_fetch]`). It runs in the daemon netns (not gated by the CONNECT allowlist), but is credential-free (`trust_env=False`, no cookies) and SSRF-hardened — every resolved IP validated against a private/reserved blocklist on each request and redirect hop, connection pinned to the validated IP (DNS-rebinding mitigation), GET/text-only, size/time capped, content wrapped in an untrusted-content delimiter (`untrusted_input` folded into the eager set when enabled). Off via `enabled = false`; `require_url_provenance` locks fetches to task-seen URLs for sensitive deployments. See `.claude/rules/brain.md`.
- **Deferred DB**: sandboxed Claude writes JSON to temp dir; scheduler processes after success. Identity (`user_id`, `conversation_token`) always from task, not JSON. Subtasks rate-limited (`max_subtasks_per_task`, `max_subtask_depth`, `max_subtask_prompt_chars`), admin-only.

## Deployment

**Ansible**: role at `deploy/ansible/` (symlinked from the operator's `ansible-server` checkout). When adding config fields, update `defaults/main.yml` + `templates/config.toml.j2`. The role runs `files/validate_config.py` against the rendered TOML before any handler can restart the scheduler — structural bugs fail the play instead of the running daemon. Three systemd units (`istota-scheduler`, `istota-web`, `istota-webhooks`) all read `ISTOTA_ADMINS_FILE` and `ISTOTA_SECRET_KEY` from the same EnvironmentFile.

**Docker**: `docker/docker-compose.yml` brings up nginx (single host port, reverse-proxies `/` → Nextcloud and `/istota/` → web service) + nextcloud + postgres + redis + istota (multi-stage Dockerfile builds the SvelteKit frontend; separate scheduler / web / webhooks services). The image installs `bubblewrap` + `tmux`, and the entrypoint defaults `sandbox_enabled = true` and `skill_proxy_enabled = true` (overridable via `ISTOTA_SECURITY_SANDBOX_ENABLED` / `ISTOTA_SECURITY_SKILL_PROXY_ENABLED`); the network proxy is off (`[security.network] enabled = false`) since the container's own network is the boundary. The container runs as **root** (no `USER` directive), so the CLI brains' `--dangerously-skip-permissions` is accepted via `IS_SANDBOX=1`, which `ClaudeCodeBrain`/`TmuxClaudeBrain` set automatically when running as root; bwrap doesn't `--clearenv`, so it propagates into the sandboxed `claude`. The entrypoint auto-provisions `#general`, `#logs`, `#alerts` group rooms (lookups are scoped by `USER_NAME` participation, so identically-named rooms across users on a shared NC don't collide), registers an OAuth2 client in NC via inline PHP, generates `LOCATION_INGEST_TOKEN` + `ISTOTA_SECRET_KEY` (persisted to `/data/.secret_key`), and seeds workspace files. Modules default on (`ISTOTA_*_ENABLED=true`). Key env: `CLAUDE_CODE_OAUTH_TOKEN`, `ADMIN_PASSWORD`, `USER_NAME`/`USER_PASSWORD`, `BOT_PASSWORD`, `POSTGRES_PASSWORD`, `DOMAIN`, `ISTOTA_WEB_INSECURE_COOKIES` (toggle for plaintext localhost).

**Nextcloud mount**: `/srv/mount/nextcloud/content` via rclone (`istota_use_nextcloud_mount: true`).
